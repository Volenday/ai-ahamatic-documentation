## 3. The Scaling Model and HA/Failover Topology Atop the Fixed Deployment Shape

### 3.1 The Deployment Shape, Cited

`architecture-realization-design.md` §7 fixes one deployable per product: the seven component modules and the guardrail module, built from one source tree, running as one process type, horizontally scaled by identical stateless replica instances behind a load balancer, with no per-tenant or per-application split at the deployment layer. Every replica can serve any tenant's request, resolving that request's schema via the registry lookup at request time (§4.3 of that document). This document takes that shape as fixed and designs the scaling triggers, the failover topology, and the connection-pool mechanism that operate within it — the two risks that document names as sharpened but unresolved (§12 there).

### 3.2 Scaling Triggers

The deployment shape's replicas are stateless and interchangeable; a scale-out event adds a replica to the load-balanced pool and a scale-in event removes one, with no data migration and no per-replica configuration step, because tenant and application context is resolved per request rather than baked into a replica (`architecture-realization-design.md` §4.3, §7.2). This document fixes what triggers that event:

| Signal | Scale-Out Condition | Why This Signal |
|---|---|---|
| Per-replica CPU/memory utilization | Sustained above a fixed utilization threshold across a short rolling window, per replica. | The direct resource-exhaustion precursor to a p95/p99 breach of `06-non-functional-requirements.md` §4. |
| In-flight request concurrency / request-queue depth | Approaching the level at which the synchronous contract-request budget (NFR §4: p95 ≤ 400 ms end to end) would be put at risk by queuing delay alone. | Queuing delay, not compute exhaustion, is frequently the first-observed symptom of insufficient replica count; gating only on CPU/memory misses it. |
| Connection-pool utilization (§4.1) | Sustained checkout-wait time or pool saturation above a fixed threshold. | Ties the compute-scaling trigger to the connection-pooling mechanism designed in §4 — pool pressure is itself a scale-out signal, not a separately-tracked concern, because a saturated pool degrades every replica identically regardless of that replica's own CPU headroom. |

Scale-in reverses the same three signals, sustained below their thresholds, and is always preceded by connection-draining: a replica marked for removal stops receiving new requests from the load balancer but completes its in-flight requests before terminating, so no in-flight request is ever dropped by a scale-in event.

**The specific numeric thresholds (the utilization percentage, the queue-depth figure, the pool-saturation percentage) are not fixed by this document.** They are operational tuning parameters that must be validated against real load, not an architectural property; fixing them here would misstate a tuning decision as a design decision. What this document fixes is that these three signals, and no others, are the scale-out/scale-in decision inputs, and that they are each independently sufficient to trigger scaling — the mechanism, not the dial position, is this document's to design.

### 3.3 HA/Failover Topology — Compute

The replica pool is distributed across no fewer than three replicas, spread across at least two — and, where the operating provider offers it within the portable-subset constraint of ADR-010 (`technology-stack-design.md` §20.1), three — availability zones within the region, so that a single zone's failure removes at most a minority of the pool's capacity rather than the pool as a whole. The load balancer health-checks every replica continuously; a replica that fails its health check is removed from rotation immediately, and the container orchestrator replaces it, without any human decision in the path, on the order of seconds to low minutes. Because replicas carry no state (§3.1), a replacement replica requires no data restoration or reconfiguration before serving traffic — it is provisioned identically to every other replica and begins serving any tenant's request as soon as it passes its own health check.

### 3.4 HA/Failover Topology — Data Layer

The platform's PostgreSQL datastore (ADR-004) runs as a primary instance with at least one standby replica, using the managed-HA offering of the operating provider within the portable-subset constraint of ADR-010 — no provider-specific API or behavior is depended on for correctness, per `architecture-realization-design.md` §9's stack-portability convention applied here to the data layer's own HA mechanism. Failover from primary to standby is automated: a primary-health failure triggers promotion of the standby without a human decision in the path, on the order of low minutes.

**The standby replication mode is synchronous, or synchronous-quorum, not asynchronous.** This is not an independent design choice with two live alternatives to weigh — it is the direct structural consequence of NFR §7's zero data-loss tolerance on committed data: an asynchronously-replicated standby can be promoted while a small window of already-committed transactions on the failed primary has not yet reached it, which is precisely the nonzero data-loss incident that target forbids. A synchronous (or synchronous-quorum) standby accepts a small write-latency cost in exchange for the guarantee that no promotion can lose a transaction the primary had already committed. This is stated as a reasoned consequence of the cited target, not recorded as an ADR (§8), because the requirement leaves no genuine alternative to weigh once the zero-tolerance floor is taken as fixed.

### 3.5 Extension-Failure Confinement

NFR §6 requires that an extension instance's failure, fault, or resource exhaustion never reduce platform-core availability, for any tenant not using that extension, below the availability floor — and confines any degradation, for the tenant using it, to that tenant's own use (`05-integration-and-extensibility-spec.md` §7, core and tenant confinement). Under the shared, stateless-replica deployment shape (§3.1), every replica serves every tenant's requests, including a request that invokes an extension for one tenant while another replica-served request, for an unrelated tenant, executes concurrently on the same replica process. Confinement is therefore not automatic from the deployment shape alone; this document designs the mechanism that makes it true:

- **Extension invocations execute in a resource- and concurrency-bounded execution pool, separate from the pool serving ordinary platform-core request handling, on every replica.** A bulkhead: the extension-invocation pool has its own fixed concurrency ceiling and its own resource allocation, sized independently of the platform-core request-handling pool. An extension instance that exhausts its own pool's capacity — through a slow, hung, or resource-heavy invocation — can starve only other invocations queued in that same bounded pool; it cannot consume capacity the platform-core request-handling pool depends on, because the two pools do not share their concurrency budget.
- **The existing hard time ceilings are enforced as pool-level timeouts, not merely as a courtesy the extension is trusted to honor.** The ≤ 5-second synchronous and ≤ 15-minute asynchronous ceilings (`06-non-functional-requirements.md` §4, §8) are enforced by the extension-invocation pool itself: an invocation exceeding its ceiling is terminated by the pool, and the resource slot it held is reclaimed, regardless of the extension's own behavior.
- **This confines the blast radius to the tenant using the failing extension, structurally.** A tenant not using the extension in question never has its own requests routed into the extension-invocation pool at all — its requests are served entirely by the platform-core request-handling pool, whose capacity the extension-invocation pool cannot consume. The tenant using the extension may see its own extension-mediated actions degrade — the confinement rule's own carve-out — but its ordinary platform-core requests continue to draw from the unaffected platform-core pool.

## 4. Connection Pooling and the Crossover Point

### 4.1 The Pooling Mechanism: One Shared Physical Pool, Role Switched Per Request

`tenant-isolation-and-access-control-design.md` §5.1 fixes one database role per schema as the connection-scoping unit, and fixes that the Context Resolution Point's connection-acquisition step switches the active database role to the one matching the Resolved Request Context's `schema_name` via `SET ROLE` before any query executes. This document's pooling mechanism is designed to make that switch cheap and to keep pool size decoupled from schema count — the finding that resolves the crossover question of §4.4.

- **A single, shared pool of physical PostgreSQL connections per replica**, sitting behind an external connection pooler (a pooler such as PgBouncer, named illustratively of a category of tool, per `architecture-realization-design.md` §9's convention for a specific tool named without ecosystem-maintenance weight — not a load-bearing claim) operating in transaction-pooling mode, multiplexes many logical, request-scoped checkouts onto a bounded number of physical connections to the primary database.
- **A connection is checked out for the duration of one request's database work only, never for a session's lifetime.** The Context Resolution Point's connection-acquisition step (`tenant-isolation-and-access-control-design.md` §4.2) checks out a physical connection from the pool, issues `SET ROLE` to the role matching the Resolved Request Context's `schema_name`, performs the mandatory self-verification read (§5.2 of that document) and the request's own queries, then issues `RESET ROLE` before releasing the connection back to the pool. The connection returns to a neutral, unprivileged state before it can be reused for a different tenant's or application's request.
- **This is the mechanism that decouples pool size from schema count.** `SET ROLE` is an in-memory privilege-context change on an already-open physical connection — it opens no new connection and requires no new authentication handshake. A pool of a fixed size can therefore serve requests against any number of schemas, one request at a time per checked-out connection, because the pool's physical connection count is driven by concurrent in-flight database work, not by how many distinct schema roles exist to switch into. Growing the schema count from ~100 toward the NFR horizon does not, by itself, require growing the pool.
- **What pool size is actually driven by:** the platform's concurrent in-flight request volume — bounded by the scaling model of §3.2, not by concurrent session count (§5.1) or schema count. A saturated pool (checkout-wait time or utilization above the threshold §3.2 names) is itself a scale-out trigger, feeding back into the compute-scaling mechanism of §3 rather than requiring a separate connection-pool-specific scaling mechanism.

### 4.2 The Authentication Session Read as a Fixed Cost

`authentication-and-identity-design.md` §4.2 and §8.1 (ADR-019) fix that every request re-reads the `platform.sessions` row referenced by its bearer token — an indexed, primary-key lookup by `session_id` — before the Context Resolution Point runs. This is a fixed input this document accounts for, not a hypothetical addition:

- **The session-authority read and the schema-scoped work of one request share a single connection checkout, not two.** The Authentication Gate's session-validity read against `platform.sessions` (a platform-global table, read under the connection's base role before any schema role is assumed) executes on the same physical connection the Context Resolution Point subsequently issues `SET ROLE` on for the request's schema-scoped work — one checkout from the pool of §4.1 serves both steps of one request, in sequence. ADR-019's added read therefore adds one indexed point-lookup query per request; it does not add a second connection checkout, and does not by itself change the pool-sizing analysis of §4.1.
- **The read itself is not a throughput concern.** A primary-key lookup on `platform.sessions` is sub-millisecond and does not materially erode the p95 ≤ 250 ms server-side contract-processing budget (`06-non-functional-requirements.md` §8) or the 100 requests/second per-client throughput floor (§8 of the same document).
- **The write side of session carriage is the actual pressure point, and this document designs its mitigation.** `authentication-and-identity-design.md` §4.5 advances `last_active_at` "on ordinary activity"; read literally as a write on every request, this would add a write to `platform.sessions` for every governed request the platform serves — a materially larger cost than the read side, and one this document's throughput analysis must account for rather than pass through unmitigated. **This document's mechanism updates `last_active_at` only when more than a fixed coalescing window (60 seconds) has elapsed since the value it already holds**, rather than on every request. This is a connection- and write-throughput optimization internal to this document's own load-profile design — it does not alter `authentication-and-identity-design.md`'s session semantics: the idle-timeout comparison (§4.4 of that document, ≤ 30 minutes) still reads the current time against whatever value `last_active_at` holds, and a 60-second coalescing window changes that comparison's precision by an amount two orders of magnitude smaller than the 30-minute ceiling it is checked against — it cannot cause a session to be treated as non-idle materially past the point it would otherwise have expired.

### 4.3 Migration Fan-Out Execution Model

A platform-core schema change that must propagate to every per-application schema (`platform-data-model-design.md` §11's migration-fan-out risk) executes as a **bounded-concurrency batch**, not a single unbounded parallel sweep and not a fully sequential run:

- Migrations against distinct schemas execute concurrently up to a fixed concurrency ceiling — a batch size well inside the pool's own capacity (§4.1), so a mass-migration event does not itself saturate the pool and trigger the scale-out/backpressure behavior §3.2 reserves for ordinary request load.
- Each schema's migration executes in its own transaction, independent of every other schema's — one schema's failure triggers that schema's own safe revert (`03-software-and-architecture/03-data-model-and-entity-spec.md` §7, `06-non-functional-requirements.md` §7's migration ceiling) without blocking, delaying, or reverting any other schema's migration in the same fan-out event.
- At the ~100-schema V1.0 figure (`platform-data-model-design.md` §11, `DECISIONS.md` D-26), with per-schema migration duration averaging ~2.4 minutes (that document's own arithmetic, cited not restated) and a bounded concurrency well below the pool's capacity, a full fan-out across every schema completes in well under an hour of wall-clock time — comfortably inside both the per-schema 4-hour ceiling (NFR §7) and any operationally reasonable release window, with no batching artifice beyond the bounded-concurrency model itself.

### 4.4 Locating the Crossover Point

`platform-data-model-design.md` §11 hands this document one job directly: locate the schema count at which connection-pool pressure and migration fan-out stop being theoretical, verified against ~100 as the actual confirmed V1.0 figure. This section states the finding.

**The pooling mechanism of §4.1 changes what "crossover" even means for connection pooling specifically.** Because pool size is decoupled from schema count (a fixed pool serves any number of schemas via per-request `SET ROLE`), schema count alone does not drive connection-pool exhaustion the way it would under a design with one dedicated physical connection or one dedicated pool per schema. The genuine pressure point as schema count grows is not pool exhaustion but **PostgreSQL catalog and session-cache overhead**: every schema and its per-application role adds rows to the shared system catalogs (`pg_namespace`, `pg_roles`, `pg_class`, and the per-table entries each schema's own entity tables add once `data-model-and-entity-design.md`'s structures exist within them), and every `SET ROLE` privilege check and every new connection's catalog-cache priming cost scales with the total size of those shared catalogs platform-wide, not with any single schema's own row count. This is the same pressure `platform-data-model-design.md` §11 already names ("schema-per-tenant PostgreSQL deployments of this general shape routinely run to the low thousands of schemas before pooling or catalog-lookup pressure becomes measurable") and this document sharpens it to two concrete waypoints rather than leaving it a range:

| Waypoint | Schema Count | What It Means |
|---|---|---|
| Early-warning / monitoring threshold | **~500 schemas** (5× the V1.0 figure) | The point at which this document requires the regression-detection mechanism (§7) to begin actively tracking catalog- and connection-related metrics as a leading indicator — not yet a breach of any target, but the point past which "theoretical" can no longer be assumed without evidence. |
| Engineered-response threshold — the crossover point | **~2,000 schemas** | The point at which the mechanisms this document designs (the shared, role-switched pool of §4.1; the bounded-concurrency migration batching of §4.3) are reasoned to no longer be sufficient on their own: catalog-lookup latency (schema and role resolution, per-connection cache priming, autovacuum scheduling across a proportionally larger relation count) is expected to begin measurably eroding the p95/p99 contract-request budgets of `06-non-functional-requirements.md` §4, and migration fan-out concurrency is expected to need a sharded or multi-cluster execution model beyond the single-primary bounded-batch model of §4.3. |

**This is a reasoned engineering waypoint, not a verified benchmark or a first-principles derivation** — it is derived from the structural behavior of PostgreSQL's shared-catalog architecture (ordinary heap tables scanned via index for most catalog operations, with cost proportional to total catalog size rather than to any single schema) applied to `platform-data-model-design.md` §11's own "low thousands" finding, sharpened to a specific number this document can be held to and revised against, exactly as `06-non-functional-requirements.md` §10 already treats its own judgment values: an initial figure, revisable on first operating data, never cited as though derived from a benchmark this document ran.

**What this finding does not do.** It does not design the sharded or multi-cluster mechanism the 2,000-schema threshold would require — that is beyond V1.0 scope and is flagged forward (§9), consistent with the NFR §5/§7 horizon being deferred as an acceptance gate while retained as a design constraint this shape must not preclude (`platform-data-model-design.md` §11, citing `TICKET.md` Q1a). At the confirmed V1.0 figure of ~100 schemas, both the 500-schema monitoring threshold and the 2,000-schema engineered-response threshold sit well beyond current scale — the honest statement `platform-data-model-design.md` §11 already gives (pooling and fan-out remain theoretical, not pressing, at ~100) is unchanged by this document's mechanism; what this document adds is the concrete number at which that changes, and the mechanism (§4.1, §4.3) that holds until it does.

## 5. Scalability Targets, Realized

`06-non-functional-requirements.md` §5 fixes three targets, each expressed relative to the targets already fixed elsewhere rather than as a standalone figure, so that growth in any one dimension is never traded against a floor another tenant already relies on (INV-01). This section states the mechanism that meets each.

### 5.1 Concurrent Authenticated Sessions per Region (≥ 50,000)

The mechanism is the decoupling §4.1 already establishes: a concurrent session does not hold a database connection for its lifetime — a connection is checked out only for the duration of one request's own database work (§4.1, §4.2) and released immediately after. 50,000 concurrently *authenticated* actors therefore does not imply 50,000 concurrent *database connections*; it implies whatever number of connections the platform's actual concurrent in-flight request rate requires, which is the quantity the scaling model of §3.2 sizes the replica pool and the pool of §4.1 against. This is precisely why the target is safe to state as "sustained... without breaching any target in §4, §6, or §7" rather than as an independent capacity number this document must separately provision for: the mechanism that meets it is the same connection- and compute-scaling mechanism already designed for ordinary load, not a session-count-specific allowance.

### 5.2 Committed Entity Instances per Tenant (≥ 10,000,000)

This target is a data-volume-within-one-schema property, orthogonal to the schema-count axis §4.4 addresses (`platform-data-model-design.md` §11's explicit distinction, restated here as the same distinction this document holds throughout: schema count and per-tenant entity-instance count are different axes, and this document does not conflate them). This document's boundary on this target is narrow and stated precisely: the connection-scoping and pooling mechanism of §4.1 imposes no ceiling tied to a schema's own row count — a connection scoped to a schema holding 10,000,000 rows is checked out, used, and released identically to one scoped to a schema holding ten rows, because the mechanism (role switch, checkout, release) carries no per-row cost. The query-execution and indexing design that keeps a 10,000,000-row schema's own queries within the NFR §4 latency budgets is `data-model-and-entity-design.md`'s to design over the entity structures it defines within that schema (`platform-data-model-design.md` §3.3, §12); this document's finding is only that nothing in the connection- or compute-scaling mechanism above this document owns constitutes a barrier to that document reaching the target.

### 5.3 Per-Tenant Onboarding Overhead: Zero Measurable Degradation

This is the target most likely to be under-designed if left implicit, and this document states the mechanism explicitly rather than asserting the deployment shape alone suffices.

Onboarding a tenant is a data-layer event under the fixed shape (`architecture-realization-design.md` §7.2): new rows in `platform.tenants` and `platform.applications`, a new `tenant_<id>` schema and, per application, a new `tenant_<id>_app_<id>` schema, and the corresponding database roles and grants (`tenant-isolation-and-access-control-design.md` §5.1). It adds no new deployment unit and requires no redeployment of the platform-core service. Two further mechanisms make the resource cost of that provisioning structurally unable to touch an existing tenant's own allocation:

- **Provisioning executes as an isolated, out-of-band operation, drawn from a dedicated connection allocation separate from the shared per-replica pool of §4.1.** The DDL that creates a tenant's or application's schema and role, and issues its grants, does not check out a connection from the same pool ordinary tenant requests draw from — it uses a separate, dedicated allocation sized for provisioning throughput alone. An onboarding event therefore cannot compete with an existing tenant's own request for a pooled connection, because the two draw from disjoint allocations.
- **The one place onboarding does touch shared state — inserting a row into `platform.tenants` or `platform.applications` — is a write PostgreSQL's own MVCC concurrency model does not block existing tenants' reads against.** Every existing tenant's own Registry Accessor reads (`tenant-isolation-and-access-control-design.md` §3.1) are indexed lookups scoped to that tenant's own binding rows; under PostgreSQL's standard multi-version concurrency control, a concurrent insert into the same table neither blocks nor is blocked by a concurrent read, and an existing tenant's own indexed lookup returns in the same time regardless of a concurrent onboarding insert elsewhere in the same table. No lock contention path connects one tenant's onboarding to another tenant's ordinary registry read.

Together, these two facts are what make "onboarding introduces no measurable degradation" a property this architecture holds by default, rather than an operational discipline that could lapse under load: the resource path onboarding uses (a dedicated connection allocation) and the resource path ordinary tenant traffic uses (the shared pool of §4.1) do not overlap, and the one shared table onboarding writes to is one PostgreSQL's own concurrency model already keeps non-blocking for concurrent readers.

## 6. Availability and Reliability Mechanisms

### 6.1 The Availability Floor (≥ 99.9%, ~43 Minutes/Month)

The floor is held by the compute and data-layer HA/failover topology of §3.3–§3.4: the monthly downtime budget is consumed only by the interval between a failure (a replica, an availability zone, or the database primary) and the automated, no-human-in-the-loop recovery from it — a health-check-triggered replica replacement (§3.3, on the order of seconds to low minutes) or a database primary-to-standby promotion (§3.4, on the order of low minutes). Both are rare, automated events under this design, not routine ones; the ~43-minute monthly budget is comfortably inside reach when the interval-per-incident is measured in minutes and incidents of this kind are infrequent, which the multi-replica, multi-AZ topology of §3.3 and the synchronously-replicated standby of §3.4 are designed specifically to make true.

### 6.2 Extension-Failure Confinement

Restated from §3.5 as the availability-floor mechanism it is: the bulkhead between the extension-invocation pool and the platform-core request-handling pool, on every replica, is what prevents one tenant's extension fault from consuming capacity the availability floor depends on for every other tenant. No further mechanism is designed here beyond §3.5's.

### 6.3 Reliability Targets (§7)

| Target | Value (Cited) | Mechanism |
|---|---|---|
| Governed-request error-rate ceiling | ≤ 0.1% of governed requests, platform-core-caused, rolling 24h/region | The health-checked, automatically-replaced replica model (§3.3) removes an error-producing replica from rotation before its own error rate materially affects the aggregate; pool-saturation backpressure (§3.2, §4.1) rejects excess load with an explicit retry signal rather than allowing pool exhaustion itself to surface as a platform-core-caused error, and pool saturation is itself a scale-out trigger (§3.2) rather than a standing condition the design tolerates. |
| Data-loss tolerance on committed data | Zero | The synchronous (or synchronous-quorum) standby-replication mode fixed in §3.4 is the mechanism: no primary-to-standby promotion can lose a transaction the primary had already committed, because the standby is guaranteed to hold it before the primary's commit is acknowledged. |
| Mean time to recovery, platform-core incident | ≤ 60 minutes, detection to restoration | Held by the same automated, no-human-in-the-loop failover mechanisms of §3.3–§3.4: an incident whose cause is a failed replica, availability zone, or database primary is resolved in minutes by automated replacement or promotion, well inside the 60-minute ceiling. An incident whose cause is not resolved by either mechanism — a defect present identically across every replica — falls to the release-rollback protocol's own recovery path, which `04-devops-and-cloud-infra/05-release-and-rollback-protocol.md` owns in full; this document's mechanism covers the infrastructure-failure class of incident, not a bad-release class, and states that boundary rather than assuming its own mechanism covers every incident. |
| Migration duration and downtime ceiling | ≤ 4 hours per migration, no downtime beyond §6's budget | The bounded-concurrency, per-schema-transactional migration model of §4.3: each schema's migration is independently timed against, and independently reverts within, the 4-hour ceiling, and no migration event holds a lock or consumes capacity in a way that forces platform-core unavailability beyond the ordinary availability budget of §6.1. |

## 7. Regression-Detection Boundary

This document states what must be detected and against what threshold; it does not design the detection mechanism, the alerting tooling, or where an alert routes — each is `04-devops-and-cloud-infra/04-observability-and-monitoring.md`'s, not yet written, to design against the points fixed below.

## 8. Design Decision Records

Recorded inline, per the convention `technology-stack-design.md` §9 establishes. `authentication-and-identity-design.md` §8 consumed ADR-019 and left ADR-020 as the next available identifier (ADR-017 remains separately reserved for `mobile-application-delivery-design.md`, `DECISIONS.md` D-25 — unaffected here); this document consumes ADR-020.

### 8.1 ADR-020 — Connection-Pooling Architecture and the Schema-Count Crossover Threshold

- **Status:** Approved (this ticket; no upstream approval gate applies, per `technology-stack-design.md` §9's convention that a design ticket's own decisions do not require separate lead sign-off under `DECISIONS.md` D-16).
- **The question it answers:** Given one database role per schema as the fixed connection-scoping unit (`tenant-isolation-and-access-control-design.md` §5.1) and a V1.0 figure of ~100 schemas that must not structurally foreclose the NFR §5/§7 horizon, what connection-pooling architecture serves an arbitrary and growing schema count without pool size scaling in lockstep with it, and at what schema count does that architecture stop being sufficient on its own?
- **Cost to reverse:** **High** — every request path that acquires a schema-scoped connection depends on the shared-pool-plus-role-switch shape; reversing it to a per-schema dedicated-pool model would mean re-deriving pool sizing, provisioning, and lifecycle management for every schema individually. **Low** for the specific pooler product named illustratively in §4.1 — swapping it for an equivalent transaction-mode pooler, or the analogous mechanism under a different candidate engine, changes tooling only, not the checkout/role-switch/release discipline itself.
- **Upstream decisions assumed:** ADR-004 (`technology-stack-design.md` §14.7 — PostgreSQL, the datastore whose `SET ROLE` and MVCC properties this mechanism depends on); ADR-018 (`tenant-isolation-and-access-control-design.md` §10 — one database role per schema as the connection-scoping unit, and the Context Resolution Point's connection-acquisition step this document's checkout/switch/release sequence extends); ADR-019 (`authentication-and-identity-design.md` §8.1 — the per-request `platform.sessions` read this document's throughput analysis accounts for, §4.2); `platform-data-model-design.md` §11 (the ~100-schema V1.0 figure this ADR's crossover finding is verified against, and the "low thousands" qualitative finding this ADR sharpens to specific waypoints).
- **Criteria applied, and how each resolved:**
  - **Pool size independent of schema count** — **decisive.** A per-schema dedicated connection or dedicated pool would make pool size a direct function of schema count, defeating the goal of a shape that does not need to change as the platform grows from ~100 schemas toward the NFR horizon; a shared pool with per-request role switching decouples the two entirely (§4.1), and this is the property every other candidate below was rejected for lacking.
  - **Compatibility with the fixed connection-scoping unit** — **decisive.** The mechanism must operate against `SET ROLE`-based schema scoping already fixed by ADR-018, not invent a second scoping mechanism; every candidate considered was evaluated on whether it composed with that fixed unit rather than requiring it to be redesigned.
  - **Absorbing the ADR-19 session-read cost without a second connection checkout** — **considered, resolved by design rather than by choosing among alternatives.** No candidate pooling architecture was rejected on this criterion; instead, the sequencing of the session-authority read and the schema-scoped work onto one shared checkout (§4.2) was designed to satisfy it directly.
  - **Locating a genuine crossover point rather than leaving the risk an open range** — **decisive for the second half of this ADR's decision.** `platform-data-model-design.md` §11 explicitly required a specific finding, not a restatement of its own "low thousands" qualitative range; the two-waypoint structure (500 monitoring / 2,000 engineered-response, §4.4) was chosen specifically because a single number would understate the difference between "start watching" and "the current mechanism is no longer sufficient," which are genuinely different operational states.
- **Verified vs. reasoned:** Reasoned throughout — the pooling mechanism follows directly from PostgreSQL's documented `SET ROLE` and MVCC properties and the cited upstream ADRs; the crossover figures (§4.4) are explicitly reasoned engineering waypoints, not verified benchmarks, and are recorded as such rather than presented with unearned precision.
- **Context:** Three upstream documents each explicitly handed this document a named, unresolved piece bearing directly on this decision: `architecture-realization-design.md` §12 (connection-pool and migration-fan-out risk, sharpened but unresolved), `platform-data-model-design.md` §11–§12 (the ~100-schema figure and the explicit instruction to locate the crossover point against it, not an abstract range), and `authentication-and-identity-design.md` §8.1 (the per-request session read as a fixed cost this document's pooling and throughput analysis must account for).
- **Decision:** (1) One shared pool of physical connections per replica, behind a transaction-mode external pooler, with a connection checked out per request and released immediately after (§4.1); (2) schema scoping realized entirely through `SET ROLE` at checkout and `RESET ROLE` at release, never through a dedicated physical connection or dedicated pool per schema; (3) the per-request `platform.sessions` read and the request's own schema-scoped work share one checkout, with `last_active_at` writes coalesced to a 60-second window to bound write throughput (§4.2); (4) migration fan-out executes as bounded-concurrency, per-schema-transactional batches against the same shared pool, not a separate provisioning mechanism (§4.3); (5) a two-waypoint crossover finding — 500 schemas (monitoring activation) and 2,000 schemas (engineered-response threshold, beyond which this document's mechanism is reasoned to need a sharded or multi-cluster successor it does not itself design) (§4.4).
- **Alternatives considered:** *A dedicated physical connection pool per schema* — rejected; pool size would scale linearly with schema count, exactly the coupling this decision exists to avoid, and would require per-schema pool lifecycle management with no corresponding benefit given `SET ROLE`'s low cost. *Fully dynamic, per-request database credentials issued by an external secrets/KMS system* — already considered and rejected by ADR-018 (`tenant-isolation-and-access-control-design.md` §10) as disproportionate at the V1.0 figure, and named there as a candidate for this document to weigh if schema count approaches the NFR horizon; this document's crossover finding (§4.4) supersedes the need to weigh it now, since the 2,000-schema threshold this document identifies is itself the trigger for revisiting that option, not a decision this ADR makes in its place. *Leaving the crossover point as the qualitative range `platform-data-model-design.md` §11 already stated* — rejected; that document explicitly required a specific finding verified against ~100 as the confirmed figure, and restating its own range would not discharge that handover.
- **Consequences:** Binds `04-devops-and-cloud-infra/04-observability-and-monitoring.md` (not yet written) to instrument the detection points and thresholds of §7, including the two schema-count waypoints of §4.4, as first-class metrics rather than a metric that document must independently derive. Binds `testing-and-quality-gates-design.md` to cite the ~100-schema V1.0 figure and the 500/2,000 waypoints as the scale this platform's quality gates are validated against, absent new operating data. Binds any future document engineering a response to the 2,000-schema threshold (a sharded or multi-cluster successor mechanism) to treat that threshold as this document's own reasoned waypoint, revisable on first operating data, not a hard architectural ceiling. No downstream document may design a second connection-pooling mechanism; each consumes this one.

## 11. Binding Rules

These rules hold for every element of this document and are subordinate to the specification and the charter.

- **The deployment shape is realized here, never redefined.** One deployable, stateless horizontal replicas, no per-tenant split (`architecture-realization-design.md` §7) is the shape every mechanism in this document operates within; nothing here adds a per-tenant or per-application deployment unit.
- **Pool size is decoupled from schema count.** Schema scoping is realized entirely through `SET ROLE` at connection checkout and `RESET ROLE` at release, against one shared pool per replica; no mechanism in this document ties physical connection count to the number of schemas in existence.
- **The crossover-point figures (500 / 2,000 schemas) are reasoned engineering waypoints, revisable on first operating data — never cited as verified or derived.** At the confirmed V1.0 figure of ~100 schemas, both waypoints sit well beyond current scale, and connection-pool pressure and migration fan-out remain theoretical exactly as `platform-data-model-design.md` §11 already found.
- **The per-request `platform.sessions` read shares a connection checkout with the request's own schema-scoped work; it never adds a second checkout.** `last_active_at` writes are coalesced to a 60-second window as a throughput optimization internal to this document, without altering the idle- or absolute-expiry semantics `authentication-and-identity-design.md` fixes.
- **Extension invocations execute in a resource- and concurrency-bounded pool separate from the platform-core request-handling pool, on every replica.** No tenant not using a given extension ever has its own requests routed through that extension's invocation pool; the two pools never share their concurrency budget.
- **The standby database replica is synchronously (or synchronous-quorum) replicated, never asynchronously, for as long as NFR §7's zero data-loss tolerance holds.** No failover mechanism in this document may promote a standby that could lack a transaction the primary had already committed.
- **Onboarding a tenant or application is a data-layer event only, executed through a connection allocation dedicated to provisioning and disjoint from the shared pool ordinary tenant traffic uses.** No onboarding operation ever draws from, or competes for, the same pooled connection allocation an existing tenant's own request would use.
- **Every quantified target this document realizes is cited from `06-non-functional-requirements.md`, never restated as this document's own value**, and every mechanism above is designed to meet the cited value without narrowing, widening, or reinterpreting it.
- **Everything in this document remains domain-neutral.** No scaling, pooling, or availability mechanism encodes the characteristics of any single domain, tenant, or application; every mechanism holds identically for any software built on the platform.
