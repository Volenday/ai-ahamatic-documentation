# Integration and Extensibility Design — AI ahaMatic

This document realizes `03-software-and-architecture/05-integration-and-extensibility-spec.md` as concrete, buildable mechanism: the extension and module boundary rules (§4 there), the SDK compatibility contract (§5), and the trust boundary for external extensions (§7) — for the **Extender origin** specifically. It states **how** a builder platform extends itself through modules and a software development kit without weakening the guarantees `03-architecture-realization-design.md` and `02-tenant-isolation-and-access-control-design.md` already make, and it answers, for the Extender origin, the question two written documents each handed here in the same words rather than resolved themselves: what isolation strength Extender-authored code requires, and what mechanism delivers it. It does not revisit the extension boundary's own definition, the SDK's contract shape, or the trust-boundary confinement dimensions the specification already fixes — each is realized here, never redecided.

This is a Design-phase artifact realizing, in addition to `03-software-and-architecture/05-integration-and-extensibility-spec.md` in full: `01-business-and-ux/03-platform-capability-model.md` §4 (C-11, C-12 only); `02-governance-and-security/03-access-control-and-tenancy-model.md` §6 (the Extender's own grant); `03-architecture-realization-design.md` §3.1, §4.1, and §10 in full (the Extension component's registry mechanism, the dependency-direction rule that holds regardless of authorship, and the amended ADR-016 record that names this document as the Extender origin's owner); `04-security-controls-design.md` §5 (the three-origin scope and the platform-team-only manifest this document does not extend); `02-tenant-isolation-and-access-control-design.md` §3, §5, §6 (the connection-scoping mechanism an extension calls through); `05-api-contract-design.md` §2, §4, §5, §9 (the two contract tiers, versioning, compatibility, and the agent-facing surface this document's SDK composition inherits); `01-application-construction-design.md` §4.1, §4.2.2, §6 (the construct/binding vocabulary an extension may reach, cited and never redefined); `02-data-model-and-entity-design.md` §4.1 (the Entity Access Gateway an extension calls through); `02-platform-data-model-design.md` §3 in full (the schema hierarchy any registration or grant state must fit); and `08-audit-and-traceability-design.md` §4.2, §4.3 (the consolidated audit event model this document's evidence populates).

**Verified versus reasoned (`PROCESS.md` §12.3).** Most claims here are reasoned — from the cited specification, the cited upstream design documents, and the structural properties of a capability-scoped execution model. One claim is time-sensitive and is verified: that WebAssembly/WASI capability-based sandboxing is an actively maintained technology category suited to confining untrusted guest code behind an explicit, host-granted import surface, and that under the V1.0 default stack (Node.js), the host language's own built-in `node:wasi` module is *not* a sufficient security boundary for untrusted code by its own maintainers' stated position — checked 2026-08-07 against current sources; Wasmtime and Wasmer are named as verified examples of dedicated, embeddable WASM runtimes suited to this purpose, not adopted as a vendor commitment this document is not positioned to make.

## 1. Purpose and Reading Order

This document answers six questions:

- **What this document owns among the three extension origins ADR-016's amendment fixes**, and what it explicitly does not (§2).
- **How the extension and module boundary rules of the specification's §4 are realized as mechanism**, composing with the structure `03-architecture-realization-design.md` already fixes (§3–§4).
- **What isolation strength Extender-authored code requires, and what mechanism delivers it** — the first-order question this document exists to answer, not a residual detail it may assume settled (§5).
- **How the SDK compatibility contract is realized** by composing with the contract `05-api-contract-design.md` already fixes, rather than defining a second, SDK-specific scheme (§7).
- **Where an extension's registration and grant state physically lives**, constrained against the schema hierarchy `02-platform-data-model-design.md` §3 owns, without this document defining a table in a schema it does not own (§8).
- **How an Extender's reach through the SDK is bounded by mechanisms that already exist**, so that an extension is a caller of the Entity Access Gateway and the tenant-scoped connection, never an exemption from either (§9).

It is structured as a pyramid: the scope and origin boundary first, then the boundary rules every module obeys realized as mechanism, then the trust question this document exists to answer, then the invocation mechanism that question resolves into, then the SDK contract composed rather than reinvented, then where registration state is constrained to live, then the composition with existing access mechanisms, then the marketplace-origin boundary this document does not cross, then the evidence produced, then the design decision record, then the closing sections.

## 3. What an Extension Is, Realized and Not Redefined

`03-software-and-architecture/05-integration-and-extensibility-spec.md` §3 fixes that the platform provides the extension mechanism and never the extension's content, that an extension is always granted and never assumed, and that the extension boundary is where the platform core meets external extension content. `03-architecture-realization-design.md` §3.1 already realizes the Extension component physically: a stable extension-point contract (interfaces only) inside `components/extension`, and an extension registry that resolves a configured extension to its implementation at request time. This document does not redefine either; §6 below states the one place the Extender origin extends the registry's own resolution behavior, not its existence or its interface contract.

**Contract conformance is not vetting, restated at the point this document must not forget it.** `03-architecture-realization-design.md` §10.3 states the distinction this entire document exists to honor: a contract constrains *shape*, never *trustworthiness*. Every section below that composes with the SDK's own contract (§7) does so for shape — versioning, compatibility, request/response conventions — and never treats that composition as having settled whether Extender-authored code invoking the contract should be trusted with what it invokes. The two questions are answered by two different mechanisms in this document, and neither is permitted to stand in for the other.

## 4. Extension and Module Boundary Rules, Realized

`03-software-and-architecture/05-integration-and-extensibility-spec.md` §4 fixes six boundary rules that hold for every module and extension instance, regardless of origin. Each is realized below as a mechanism this design already has available, composed rather than duplicated.

| Boundary Rule | Realization |
|---|---|
| No domain content enters the core. | Extension logic — of any origin — never enters `components/*`; only the stable interface contract does (`03-architecture-realization-design.md` §3.1). For the Extender origin specifically, §5–§6 below place the logic itself entirely outside the platform-core process, which forecloses the question of domain content entering the core by removing the only path (in-process code) through which it structurally could. |
| No primitive depends on an extension instance. | `03-architecture-realization-design.md` §4.1 row 4 (Full coverage) already proves this at build time for every extension origin: `components/extension` may be imported only through its published interface sub-path, never a specific implementation. §6 below extends this without weakening it — the platform core depends only on the sandbox-invocation interface (itself a platform primitive), never on any specific Extender-authored extension's presence. |
| No value crosses the builder/built line. | An Extender's own extension logic is Extender-defined content, stored as data referenced by the platform (§8), never as platform-core source; this is the same treatment `03-architecture-realization-design.md` §5.1 already gives every generated artifact, extended here to Extender-authored code specifically. |
| A grant is never exceeded. | Realized concretely by §5.4's capability-confinement mechanism: every action an Extender-authored extension performs is checked against its own resolved grant at the point of invocation, never assumed from the extension's own claim. |
| No reach crosses a tenant boundary. | §5.4 and §9 below: every sandboxed invocation runs against exactly one already-resolved Resolved Request Context (`02-tenant-isolation-and-access-control-design.md` §4), never a caller-supplied tenant or application identifier. |
| Removing a module affects only its own scope. | Because an Extender-authored extension is invoked per request rather than compiled into the platform-core deployable (§5–§6), deregistering it (§8) removes only the registry's future resolution to it — no residual coupling exists anywhere in `components/*` for the same reason row 2 above holds. |

Where a proposed Extender-authored extension cannot be reconciled with this table, the boundary rule is never relaxed and the extension is refused or narrowed instead — the specification's own §4 closing rule, inherited without exception.

## 5. The Trust Question for the Extender Origin

### 5.1 Why This Question Cannot Be Answered by the Contract, and Must Be Answered Here

`03-architecture-realization-design.md` §10.3 hands this document exactly this question, in these words: what isolation strength does Extender-authored code require, and what mechanism delivers it. `04-security-controls-design.md` §5.3 states its own review-trigger mechanism is scoped to platform-team-authored paths only and "must not be read as extending to either other origin." Both documents are explicit that the answer is a first-order question this document must answer, not a residual detail it may assume settled or defer a third time.

The reason neither document could answer it themselves is structural, not a gap in effort: an Extender's own contract-bound, grant-scoped standing (`02-governance-and-security/03-access-control-and-tenancy-model.md` §6) tells the platform *what shape* a call may take and *what scope* it may act within — it says nothing about whether the code behind that call, which the platform team never wrote and never reviewed, does only what its shape and scope permit. `03-architecture-realization-design.md` §10.4 already withdrew the opposite error — the claim that no untrusted-code path exists at all, and therefore no isolation mechanism is needed — as a narrowing that document was not entitled to make on a since-corrected reading of the specification. Neither error is available here: this document neither treats the contract as sufficient vetting, nor assumes an isolation answer without weighing it.

### 5.2 Isolation Strengths Weighed

Four candidate isolation strengths are weighed against the confinement dimensions `03-software-and-architecture/05-integration-and-extensibility-spec.md` §7 fixes (capability, tenant, core, data, secret confinement) and against the deny-by-default discipline this platform applies everywhere else (`02-governance-and-security/01-system-invariants.md` §3).

| Candidate | Assessment |
|---|---|
| In-process loading (Extender-authored code compiled into, or dynamically loaded within, the platform-core deployable). | **Rejected outright, not weighed further.** In-process code has full ambient authority over the process that also holds tenant connections, KMS-unwrap access, and the Isolation and Trust module's own memory space. No confinement dimension of the specification's §7 table can hold once a payload shares an address space with the platform core; this candidate reproduces exactly the untrusted-payload risk `03-architecture-realization-design.md` §10.3 identifies contract-bound authorship as *not* closing. |
| OS-process isolation (a separate process, optionally hardened with `seccomp`/namespace restrictions). | Contains a crash and limits some blast radius, but its default posture is *allow* — a bare process retains the full OS-level surface (filesystem, network, signals) until something additionally locks it down, and that additional hardening is bespoke per operating system and per container runtime, not a portable structural property. Building a capability-scoped import surface on top of a process boundary means constructing, from scratch, the same default-deny discipline the next candidate already provides natively. |
| VM- or microVM-level isolation (a separate kernel per invocation or per extension instance). | The strongest isolation of the four against a determined adversary — a distinct kernel closes attack surfaces process isolation cannot. Rejected for this platform's shape on proportionality grounds, not on strength: a microVM's cold-start and steady-state resource cost is disproportionate for a request-scoped, potentially high-frequency extension invocation, and naming a specific microVM technology would bind this document's design to a hosting-infrastructure layer rather than a portable structural property — the same category of concern `03-architecture-realization-design.md` §9 already applies to distinguish a structural property from a stack-bound tool choice. |
| WebAssembly/WASI capability-based sandboxing. | **Selected.** A WASM module starts with zero ambient authority; every capability it may exercise — reading a value, calling a host function, reaching a resource — must be explicitly imported by the host at instantiation. This is a default-deny posture *by construction*, not by additional configuration layered on top, which is exactly the discipline this platform applies everywhere else in this design (the Registry Accessor's fixed query shape, the connection-scoping mechanism's schema-level privilege grants, the emission-boundary redaction filter's deny-on-uncertainty rule). Overhead is materially lower than a microVM's and the mechanism is a property of the guest/host interface, not of any one hosting infrastructure — satisfying the same stack-portability discipline `03-architecture-realization-design.md` §9 already applies to this platform's other structural mechanisms. |

**The verified caveat that governs the V1.0 realization.** Under the V1.0 default stack (Node.js), the host language's own built-in `node:wasi` module is explicitly stated by its own maintainers not to provide a sufficient security boundary for untrusted code — its filesystem-sandboxing properties can be escaped and do not constitute a security model on their own. The platform-core service therefore does not rely on `node:wasi` for this mechanism; it embeds a dedicated, purpose-built WASM runtime (Wasmtime or Wasmer are named as verified examples of this category, not adopted as a vendor commitment) as the component that hosts every Extender-authored extension's execution. Under a different candidate server stack, the equivalent is that stack's own dedicated WASM-embedding library — the property (a dedicated, capability-scoped WASM host, never the language runtime's own general-purpose module-loading facility) is stack-neutral; the specific embedding is stack-bound, per the same convention `03-architecture-realization-design.md` §9.2 already applies to its own stack-bound tool choices.

### 5.3 The Mechanism: Capability-Scoped Sandbox Execution

**Extender-authored extension code never executes inside the platform-core process.** It is compiled to WebAssembly by the Extender, registered as an opaque artifact (§8), and executed exclusively inside a dedicated WASM host embedded within the platform-core service, invoked through the **Extension Invocation Point** (§6) — a mechanism inside `components/extension`, alongside the registry `03-architecture-realization-design.md` §3.1 already fixes, never a parallel one.

- **Zero ambient authority at instantiation.** A WASM guest instance hosting an Extender's extension is instantiated with no imports beyond the fixed, platform-defined set of host functions this section defines. It has no filesystem access, no network access, no ability to spawn a process, and no addressable path to any platform-core module's internals other than through an explicit host-function call.
- **Every host function is a capability, not a raw primitive.** Each host function importable into a guest instance corresponds to exactly one operation the Extender's own grant may authorize — never a general-purpose "call the platform" escape hatch. A host function that would let a guest reach outside the closed vocabulary of operations its grant authorizes does not exist; there is no import a guest could request that reaches further than the platform explicitly offers.
- **A host function is itself a caller, never a bypass.** Every host function that would read or write a builder-defined entity's data invokes the Entity Access Gateway (`02-data-model-and-entity-design.md` §4.1) exactly as any other caller would (§9); every host function that reaches a platform capability invokes it through the same SDK surface any other consumer of the contract reaches it through (§7). No host function contains a second, extension-specific access path that skips a check every other caller passes through.

### 5.4 Confinement Mapped to the Five Dimensions

| Confinement Dimension (`05-integration-and-extensibility-spec.md` §7) | How the Mechanism of §5.3 Holds It |
|---|---|
| Capability confinement | A guest instance's only reach into the platform is the fixed host-function import set instantiated for it, drawn from exactly the operations the Extender's own grant authorizes (`02-governance-and-security/03-access-control-and-tenancy-model.md` §6). A capability not imported does not exist for that guest to call — there is no runtime check to bypass, because there is no function to call. |
| Tenant confinement | A guest instance is instantiated fresh per Resolved Request Context (`02-tenant-isolation-and-access-control-design.md` §4.1) — never reused across two different tenants' invocations with residual state intact. No host function accepts a caller-supplied tenant or application identifier as an alternative to the Resolved Request Context already established for the invocation, the same discipline the connection-acquisition function already applies (§9). |
| Core confinement | A guest instance has no addressable path to any structural component's internals other than the fixed host-function imports; it cannot alter, bypass, or extend a component's own logic, because no import exists through which to reach that logic at all — the platform core's own behavior is never made conditional on what a guest does, consistent with `03-architecture-realization-design.md` §5.2. |
| Data confinement | Every host function reaching builder-defined entity data routes through the Entity Access Gateway (§9); the sandbox boundary is an additional, outer confinement layer — it does not replace the Gateway's own checks, and the Gateway does not relax any check because the caller is a sandboxed guest rather than a platform-core module. |
| Secret confinement | No host function ever passes raw secret or key material into a guest's linear memory. Where a host function must authenticate to an external system on the extension's behalf, the authentication is performed host-side, entirely outside the guest's own reach — the same least-privilege discipline `04-security-controls-design.md` §7.3 already applies to the platform's own KMS-unwrap operations. |

**Uncertainty about conformance resolves to refusal.** Where a host function cannot establish that a requested operation is within the invoking extension's own grant, the operation is refused — the same deny-by-default rule the Registry Accessor and the connection-scoping mechanism already apply (`02-tenant-isolation-and-access-control-design.md` §3.1, §5.1), realized here at the sandbox boundary rather than restated as a new rule.

### 5.5 What This Closes, and the Honest Limit

**What the mechanism closes.** An Extender-authored extension cannot reach a platform capability, a tenant's data, a platform-core module's internals, another tenant's context, or a secret beyond what its own grant explicitly authorizes — regardless of what the extension's own code attempts, because the reach to do otherwise does not exist at the guest/host boundary. This is a structural guarantee, verifiable by inspecting the fixed host-function import set for a given grant, not a policy the extension is trusted to honor.

**What it does not close, stated plainly rather than concealed.** Capability confinement bounds *reach*; it does not vet *intent* within a granted reach. An Extender-authored extension that legitimately holds a grant to read one entity and a separate grant to write to an external system through the cross-system data layer can compose the two — reading data it is authorized to read and sending it somewhere its own grant otherwise permits — in a way that may be undesirable, without any confinement dimension above being violated, because no dimension was exceeded. This is a data-flow and intent risk, not a confinement failure, and no isolation mechanism bounds it by definition: it is the same class of residual risk platform-team-authored code carries too, closed there by the review pipeline (`04-security-controls-design.md` §5.2) — a mitigation the Extender origin structurally cannot receive, because the code is never seen by the platform team before it runs. The residual mitigation available to this origin is how narrowly a tenant scopes the grant it issues at registration time (§8) — a grant-configuration decision `02-governance-and-security/03-access-control-and-tenancy-model.md` §6 and `02-tenant-isolation-and-access-control-design.md` §6 already govern, not a gap this document's own mechanism is positioned to close further. This is not a re-deferral of the isolation-strength question — that question is answered in full above — it is the honest boundary of what any isolation mechanism, of any strength considered in §5.2, can guarantee.

## 6. The Extension Invocation Point and the Registry's Extended Resolution

`03-architecture-realization-design.md` §3.1 fixes that the extension registry "resolves a configured extension to its implementation" at request time, inside `components/extension`. This document extends what "implementation" resolves to for the Extender origin specifically, without redesigning the registry itself.

- **For a platform-team-authored extension**, resolution is unaffected by anything in this document: the registry resolves to an in-process module reference inside `components/extension`, governed entirely by `03-architecture-realization-design.md` §3–§5 and `04-security-controls-design.md` §5.2.
- **For an Extender-authored extension**, the registry resolves to an invocation target inside the **Extension Invocation Point** — a mechanism, alongside the registry, that: (1) receives the already-resolved Resolved Request Context and the extension's own registered grant (§8); (2) instantiates or reuses a guest instance in the WASM host, importing exactly the host functions that grant authorizes; (3) invokes the guest with the request's own input, marshaled across the guest/host boundary; and (4) returns the guest's result, or a refusal, to the caller.
- **The dependency-direction rule is unaffected.** `03-architecture-realization-design.md` §4.1 row 4 (Full coverage) already proves the platform core depends on no specific extension's presence; this document adds nothing that weakens that proof. The platform core depends only on the Extension Invocation Point and the WASM host it embeds — both platform primitives, present regardless of whether any specific Extender-authored extension is registered — never on any one extension's continued existence.
- **No second registry.** This document does not add a second configuration mechanism alongside the one `03-architecture-realization-design.md` §3.1 already fixes; it states only what that mechanism's existing resolution behavior does for one of the three origins it already recognizes.

## 7. The SDK Compatibility Contract, Composed With What Already Exists

`03-software-and-architecture/05-integration-and-extensibility-spec.md` §5 fixes that the SDK's own contract surface is an API contract within the meaning of `03-software-and-architecture/04-api-contract-spec.md` §3, governed by that document's versioning, compatibility, and request/response/error conventions without restatement. `05-api-contract-design.md` is now written and realizes exactly those conventions for the platform's own two-tier contract; **the SDK is generated from that same OpenAPI artifact, per ADR-006's own consequence** (`05-api-contract-design.md` §13, Consequences). This document composes with that realization rather than defining a second, SDK-specific scheme.

- **Versioning, deprecation, and backward compatibility follow `05-api-contract-design.md` §4–§5 in full**, tier-1 (platform-primitive) throughout: a semantic version carried in `info.version` and the request path's major segment, deprecation marked via the `deprecated` flag and a `Sunset` header, and a change to the SDK's contract surface backward-compatible only where every existing SDK consumer, including every existing Extender-authored extension, continues to operate correctly without modification. Uncertainty about whether a change is breaking is treated as breaking, exactly as that document's §5.1 already fixes.
- **Request/response and error conventions follow `05-api-contract-design.md` §6 in full.** Every SDK interaction an Extender-authored extension performs — whether invoked directly by platform-tooling code or, for the Extender origin, marshaled through a host function on the guest's behalf (§5.3) — carries the response envelope, the `contract_version` field, and the structured error object that document already fixes; this document adds no second envelope or error shape for the sandboxed case.
- **The `builder-tooling` tag governs which operations an extension may reach.** `05-api-contract-design.md` §3.2 fixes that every operation reachable by a builder or extender carries the `builder-tooling` tag and is served under the reserved `/builder/` path prefix. A host function importable into an Extender-authored extension's guest instance (§5.3) corresponds one-to-one to an operation carrying that tag and falling within the extension's own registered grant — never an operation outside that tagged surface, and never one the grant does not name.
- **A breaking SDK change requires the identical sign-off and reversal path `05-api-contract-design.md` §7–§8 already fixes.** This document does not define a second compatibility scale, a second sign-off trigger, or a second breaking-change detection mechanism for the SDK; the platform-primitive tier's mechanism already governs the SDK's own surface in full, because the SDK's surface is that tier's own contract.
- **The SDK never grants reach beyond a consumer's own scope**, restated here as the property that closes the loop with §5's confinement mechanism: `02-governance-and-security/03-access-control-and-tenancy-model.md` §5's "a client's grant is always a subset of its tenant's own" is what bounds the grant an Extender's registration (§8) may ever record — the SDK is a means of exercising that grant, never of acquiring one beyond it, and the sandbox's host-function import set (§5.3) can never exceed what the grant it is instantiated for already permits.

## 8. Where Extension Registration and Grant State Lives

This document's mechanism requires a registration record per Extender-authored extension: which artifact (the compiled WASM module, held as an opaque reference, never inline platform-core source — the same generated-artifact treatment `03-architecture-realization-design.md` §5.1 already gives every builder-produced content), which grant it is registered under, and which tenant it belongs to. This document states the constraint that record must satisfy and its destination; it does not define the table, following the same discipline `04-workflow-and-process-automation-design.md` §4.1 applies when constraining without owning, and avoiding the schema-ownership gap `BACKLOG.md` §1i already records the cost of.

- **The Extender's own identity binding already has a home.** `02-platform-data-model-design.md` §5 and `02-tenant-isolation-and-access-control-design.md` §6 already place the Extender persona in `tenant_<id>.tenant_users`, "scoped by the grant its extension represents." This document does not duplicate that binding.
- **What is missing, and where it must fit.** A registration record narrowing that binding to a specific extension instance — its artifact reference and the closed set of `builder-tooling`-tagged operations (§7) its grant authorizes — is a further narrowing of an already-tenant-scoped grant, one level below `tenant_user_application_scope` in exactly the sense `tenant_<id>.administrative_scope_grants` is a further narrowing of that same table (`02-platform-data-model-design.md` §3.2, `BACKLOG.md` §1i). It belongs in the **per-tenant schema** (`tenant_<id>`, `02-platform-data-model-design.md` §3.2) — never in `platform`, because an extension's grant is bound to one tenant and never spans tenants (`02-governance-and-security/03-access-control-and-tenancy-model.md` §5, "executes within the isolation of whichever tenant uses it"), and never inside a per-application schema, because the registration is a tenant-level access-scoping fact, not a builder-defined entity.
- **This document does not add the table.** Naming the concrete columns is `02-platform-data-model-design.md`'s to do, on its own schema, exactly as that document's own §12 boundary statement already anticipates for structures this layer requires without itself owning; this document states the constraint (tenant-scoped, artifact-reference-bearing, grant-narrowing) and the destination, so the obligation is claimed rather than left, again, with no assigned home.
- **The Extension Invocation Point (§6) reads this record at resolution time**, through the same privileged, identity-scoped resolution-phase access `02-tenant-isolation-and-access-control-design.md` §4.1's Context Resolution Point already uses to read `tenant_user_application_scope` and `administrative_scope_grants` — never a second, specially-acquired connection for this purpose.

## 9. An Extension Is a Caller, Never an Exemption

Every read or write of builder-defined entity data an Extender-authored extension's host function performs goes through the Entity Access Gateway (`02-data-model-and-entity-design.md` §4.1) exactly as any other caller; every action it performs runs inside a connection `02-tenant-isolation-and-access-control-design.md` §5.1 has already scoped to the invocation's own Resolved Request Context. This is the same discipline `02-data-model-and-entity-design.md` §11 and `04-workflow-and-process-automation-design.md` §5.2 each already applied to their own upstream checks, extended here to the extension surface specifically.

- **No host function acquires its own connection.** The Extension Invocation Point (§6) receives the connection already scoped to the invoking Resolved Request Context; a host function servicing a guest call uses that connection, never a second one it opens for itself. There is no code path by which a sandboxed extension's activity could reach a schema outside the one already resolved for the request that triggered it.
- **No host function bypasses the Gateway.** A host function reaching builder-defined entity data is, structurally, one more caller of the Gateway's single mediation point (§5.4) — it carries no privileged, extension-specific path around the Validation Engine, the Consent and Minimization Check, or classification-tier resolution that Gateway already runs in fixed order for every other caller.
- **The mandatory self-verification read covers extension-triggered writes identically.** `02-tenant-isolation-and-access-control-design.md` §5.2's unconditional read against `application_metadata`, run on every request that resolves a scoped connection, runs on a request an Extender-authored extension triggers exactly as it runs on any other — this document adds no exemption and no second verification.
- **An extension holds no standing to widen a grant.** `02-governance-and-security/03-access-control-and-tenancy-model.md` §5's "grants never exceed the grantor" applies to an extension's own registered grant (§8) exactly as it applies to any other role's grant; nothing in the mechanism of §5–§6 provides a path by which an extension's own execution could request, infer, or be issued a wider grant than the one already registered for it.

## 10. The Marketplace Origin: What Extends, What Doesn't

`06-marketplace-design.md` and `07-connector-marketplace-design.md` own the marketplace origin's own isolation-strength and review-trigger determination, per `04-security-controls-design.md` §5.3 and `03-architecture-realization-design.md` §10.4 — neither is settled by anything in this document, and neither is silently excluded from a decision this document does not make on their behalf.

- **What is available to them, stated as availability, not as a decision.** The capability-scoped WASM sandbox mechanism of §5–§6 is a general-purpose confinement mechanism for untrusted, contract-bound code; nothing about its design is specific to the Extender persona rather than to the property of being externally-authored, contract-bound code the platform did not write. Whether the marketplace documents adopt this same mechanism, a variant of it, a different mechanism entirely, or some combination, is their own first-order question to answer on their own terms.
- **What is not available to them without their own determination.** A marketplace-submitted module is not, by anything in this document, treated as covered by the Extension Invocation Point, registered under §8's tenant-scoped registration record, or granted reach through the `builder-tooling`-tagged SDK surface of §7 on the strength of this document alone. Doing so would be exactly the silent-coverage error this ticket's writing rules forbid — an origin this document does not own would be resolved by a mechanism built for the one it does.
- **The marketplace's own submission constraints remain untouched.** License category, attribution, unresolved-incompatibility blocking, and the mandatory security review (`03-software-and-architecture/05-integration-and-extensibility-spec.md` §6) are realized entirely by the two named documents; nothing in §5–§9 above substitutes for, discharges, or narrows any of them.

## 12. Design Decision Records

### ADR-033 — Extender-Origin Trust Boundary: Capability-Scoped WASM Sandbox Execution

- **Status:** Provisional — Pending Lead Approval, consistent with every design-phase ADR recorded since ADR-021.
- **Cost to reverse:** **High** (`PROCESS.md` §12.1). Every Extender-authored extension registered under this mechanism is compiled to, and invoked as, a WASM guest against a fixed host-function import surface; reversing the isolation strength (for example, retreating to in-process loading, or moving to a different confinement technology) requires every already-registered extension to be recompiled or re-hosted against the new mechanism's own interface, not merely a policy or configuration change. Not Very high or Brutal: no builder-defined entity data or platform-primitive schema is touched by this decision — it governs execution confinement only, and the registration record's own physical shape (§8) is deliberately left to the document that will define it, bounding this decision's own blast radius to the invocation mechanism and the host-function surface.
- **Upstream decisions assumed:** `03-architecture-realization-design.md` §3.1 (the extension registry and its resolve-to-implementation mechanism, extended here for one origin, never redesigned), §4.1 row 4 (the dependency-direction rule this decision's mechanism is built to preserve, not weaken), and §10.2–§10.4 (the amended ADR-016 record naming this document as the Extender origin's owner and withdrawing the narrowing that once assumed no untrusted-code path existed); `02-governance-and-security/03-access-control-and-tenancy-model.md` §5–§6 (the Extender role and grant model this mechanism's capability confinement is built to enforce, never widen); `02-tenant-isolation-and-access-control-design.md` §4–§5 (the Resolved Request Context and connection-scoping mechanism this decision's sandbox instantiation and host functions consume, never duplicate); `05-api-contract-design.md` §3.2, §4–§6 (the `builder-tooling` tag and the SDK contract this decision's host-function surface is generated from, never a second scheme; ADR-032, Provisional); `02-data-model-and-entity-design.md` §4.1 (the Entity Access Gateway every data-reaching host function calls through, never bypasses; ADR-028, Provisional); `01-application-construction-design.md` §4.2 (the closed construct/binding vocabulary bounding what a `builder-tooling` operation can ever expose; ADR-027/ADR-029, Provisional); `04-security-controls-design.md` §5.1, §5.3 (the three-origin scope this decision's own origin boundary matches exactly, and the explicit statement that the platform-team-only manifest does not extend here). **ADR-027, ADR-028, and ADR-032 remain Provisional — Pending Lead Approval and are not assumed settled; this decision depends on their already-designed content (the vocabulary, the Gateway, and the contract shape), never on their approval status** (`PROCESS.md` §12.2) — an approval reversal at any of the three would require this decision's own host-function surface to be regenerated against whatever content replaces them, not this decision's own mechanism to change.
- **Verified vs. reasoned:** Reasoned for the confinement-dimension mapping (§5.4), the boundary-rule realization (§4), and the registration-state constraint (§8) — each derives from the cited specification's own requirements and the structural properties of a capability-scoped guest/host interface. Verified for the claim that WASM/WASI capability-based sandboxing is a currently maintained technology category suited to this purpose, and that Node.js's own built-in `node:wasi` module is explicitly stated by its maintainers not to constitute a sufficient security boundary for untrusted code — checked 2026-08-07 against current sources; Wasmtime and Wasmer are named as verified examples of a dedicated, embeddable WASM host meeting this document's requirement, not adopted as a vendor commitment.
- **Context:** Two upstream documents each handed this exact question here in the same words rather than resolving it themselves: `03-architecture-realization-design.md` §10.3, on the ground that a contract constrains shape but does not establish trustworthiness, and `04-security-controls-design.md` §5.3, on the ground that its own review-trigger mechanism is scoped to platform-team-authored paths only. Both name this document as the Extender origin's first-order owner, not a place to defer the question a third time.
- **The question this ADR answers, phrased for reuse:** Given a specification that requires an external extension be trusted only to the extent of its own grant, verified at the boundary rather than assumed, and given that a contract-bound, grant-scoped authorship model (the Extender role) is not thereby vetted by the platform's own change pipeline — what isolation strength closes the gap between "contract-bound" and "trustworthy" for code the platform team never authored or reviewed, and what concrete mechanism delivers it without duplicating a check, a contract, or a scoping mechanism this design already has?
- **Criteria applied, and how each resolved:**

  | # | Criterion | How It Resolved |
  |---|---|---|
  | 1 | Does contract conformance itself establish trustworthiness, such that no separate isolation mechanism is needed? | **No, decisively** — `03-architecture-realization-design.md` §10.3's own distinction is the premise this entire document exists to honor; treating the SDK's contract-shape guarantees as sufficient would reproduce the exact narrowing ADR-016's amendment already corrected once. |
  | 2 | Which isolation strength satisfies every confinement dimension of `05-integration-and-extensibility-spec.md` §7 by construction (default-deny) rather than by additional, bespoke hardening? | **Decisive for WASM/WASI capability-based sandboxing** (§5.2) — zero ambient authority at instantiation is a structural property of the guest/host interface, not a configuration a deployment could omit, matching the deny-by-default discipline this platform applies everywhere else. |
  | 3 | Does the mechanism compose with the SDK contract and the Entity Access Gateway already fixed, or does it require a second contract and a second access path? | **Decisive for composition** — every host function is generated from the same `builder-tooling`-tagged OpenAPI surface `05-api-contract-design.md` already fixes (§7), and every data-reaching host function is a caller of the Entity Access Gateway (§9), never a parallel path around either. |
  | 4 | Is registration and grant state owned here, or constrained against the schema hierarchy another document owns? | **Decisive for constraining, not owning** (§8) — following `04-workflow-and-process-automation-design.md` §4.1's precedent and avoiding the schema-ownership gap `BACKLOG.md` §1i already records the cost of. |

- **Decision:** (1) Extender-authored extension code never executes inside the platform-core process; it is compiled to WebAssembly and executed inside a dedicated, embedded WASM host, invoked through the Extension Invocation Point alongside the existing extension registry (§5.3, §6). (2) Every reach into the platform from a guest instance is an explicit, host-granted import corresponding one-to-one to an operation the extension's own registered grant authorizes and the SDK's `builder-tooling` tag already exposes — never a general-purpose capability (§5.3, §7). (3) Capability, tenant, core, data, and secret confinement are each realized as a structural property of the guest/host boundary, mapped explicitly in §5.4, with the honest limit stated that confinement bounds reach, not intent within a granted reach (§5.5). (4) Registration and grant state is constrained to the per-tenant schema `02-platform-data-model-design.md` §3.2 owns, as a further narrowing of the Extender's existing `tenant_users` binding, without this document defining the table (§8). (5) Every host function reaching builder-defined data or a platform capability is a caller of the Entity Access Gateway or the SDK surface already fixed, never an exemption from either (§9). (6) The marketplace origin's own isolation-strength determination is left open, with this mechanism's availability stated but not assumed on its behalf (§10).
- **Alternatives considered:** *In-process loading of Extender-authored code* — rejected under criterion 2; no confinement dimension can hold once a payload shares the platform-core process's address space, reproducing the exact untrusted-payload risk this document exists to close. *OS-process isolation alone* — rejected under criterion 2; its default-allow posture requires bespoke, non-portable hardening to reach the same guarantee WASM/WASI provides by construction. *VM- or microVM-level isolation* — rejected on proportionality, not strength; disproportionate cold-start and steady-state cost for a request-scoped invocation, and binds the design to a hosting-infrastructure layer rather than a portable structural property. *Treating the SDK's contract-bound, grant-scoped authorship model as sufficient vetting on its own, with no isolation mechanism* — rejected under criterion 1; this is precisely the narrowing `03-architecture-realization-design.md` §10.4 already withdrew as one this platform's design was not entitled to make. *Deferring the isolation-strength question to `06-marketplace-design.md` or `07-connector-marketplace-design.md` on the reasoning that all externally-authored code shares one answer* — rejected; the Extender origin is this document's own to own per ADR-016's amendment, and re-deferring it would leave the question unanswered a third time, which this ticket's own instructions forbid.
- **Consequences:** Binds every future document designing a capability reachable through the SDK's `builder-tooling` surface (C-19's AI-assisted tooling, C-20's mobile delivery, C-24's cross-system data layer, C-25's connector marketplace) to treat an Extender-authored caller of that surface as subject to this mechanism's confinement, never as an implicit exception. Binds `02-platform-data-model-design.md` to add the per-tenant registration table this document constrains but does not define (§8), on a future, separately-ticketed amendment. Binds `06-marketplace-design.md` and `07-connector-marketplace-design.md` to make their own first-order isolation-strength determination for the marketplace origin, with this mechanism's availability stated but neither assumed nor foreclosed (§10). Adds no obligation to `04-security-controls-design.md`'s platform-team-only manifest, `05-api-contract-design.md`'s contract shape, or `02-tenant-isolation-and-access-control-design.md`'s connection-scoping mechanism — each is consumed exactly as already designed, never extended or re-decided.

## 14. Precedence and Ownership Boundaries

- **The specification prevails.** Nothing in this document narrows, expands, or alters `03-software-and-architecture/05-integration-and-extensibility-spec.md` §3–§7; where a realization choice here appears to conflict with it, the specification governs and this document is corrected, not the reverse.
- **The three-origin boundary is never collapsed.** This document's mechanism governs the Extender origin only; treating platform-team-authored code as needing this mechanism, or treating marketplace-submitted code as already covered by it, would each reproduce the uniform-treatment error the amended ADR-016 record exists to prevent (`03-architecture-realization-design.md` §10.3).
- **Contract conformance is never read as vetting.** Every composition with the SDK's contract shape (§7) is a shape-level composition; none of it is treated as having resolved whether Extender-authored code invoking that shape should be trusted with what it invokes — that determination is made in full by the confinement mechanism of §5, never inferred from contract conformance alone.
- **Invariants are floors, never spent.** INV-01, INV-05, and INV-06, which the boundary rules of §4 and the confinement mechanism of §5 exist to keep true for the Extender origin, are never degraded to ease an extension's reach, meet a deadline, or satisfy a request.
- **A breach overrides apparent gain.** An outcome that would let an Extender-authored extension reach beyond its own registered grant, observe another tenant, alter the platform core's own logic, or receive secret material is refused regardless of the value it appears to create.

This document owns the extension and module boundary rules realized for the Extender origin (§3–§4), the isolation strength Extender-authored code requires and the mechanism delivering it (§5), the extension registry's extended resolution behavior (§6), the SDK compatibility contract's composition (§7), the constraint on where registration and grant state must fit (§8), and the composition of an Extender's reach with the Entity Access Gateway and tenant-scoped connection (§9). It does not own, and none of the following documents' authority is diminished by this one:

## 15. Binding Rules

- **Extender-authored extension code never executes inside the platform-core process.** It executes exclusively inside the dedicated, embedded WASM host, invoked through the Extension Invocation Point, with zero ambient authority at instantiation (§5.3).
- **Every reach a sandboxed extension has into the platform is an explicit, host-granted import corresponding to an operation its own registered grant authorizes.** No capability not imported exists for a guest instance to call; no host function reaches further than the platform's `builder-tooling`-tagged surface already exposes (§5.3, §7).
- **Capability confinement bounds reach, never intent within a granted reach.** This is the honest limit of the mechanism, stated plainly: it does not vet what an in-grant extension chooses to do with the reach its own grant legitimately holds (§5.5).
- **Every host function reaching builder-defined entity data is a caller of the Entity Access Gateway; every sandboxed invocation runs inside a connection already scoped to its own Resolved Request Context.** No host function acquires a second connection or bypasses the Gateway's single mediation point (§9).
- **The SDK compatibility contract is never independently defined for the sandboxed case.** Versioning, deprecation, backward compatibility, and request/response/error conventions are inherited from `05-api-contract-design.md` in full, for every SDK-reaching call regardless of origin (§7).
- **Registration and grant state is constrained to the per-tenant schema, never defined by this document.** This document states the constraint; `02-platform-data-model-design.md` owns the table (§8).
- **This document's mechanism governs the Extender origin only.** It is neither extended to platform-team-authored code, which `04-security-controls-design.md` already governs, nor assumed to cover marketplace-submitted code, which `06-marketplace-design.md` and `07-connector-marketplace-design.md` must determine on their own terms (§2, §10).
- **Contract conformance and trustworthiness are never conflated.** Every place this document composes with the SDK's contract shape does so for shape alone; the confinement mechanism of §5 is what establishes trust, never the contract's own conformance guarantees (§3, §14).
- **Everything remains domain-neutral and platform-level.** No boundary rule, confinement mechanism, or contract composition in this document encodes the characteristics of any single domain; all remain valid for any module, any SDK consumer, and any Extender, in any tenant and any region.
- **This document records exactly one ADR.** ADR-033 (§12) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, boundary, or invariant the cited specification and cited upstream design documents already fix.
