# Data Model and Entity Design — AI ahaMatic

## 1. Purpose and Reading Order

This document realizes `03-software-and-architecture/03-data-model-and-entity-spec.md` in full — the core data-model rules that elaborate INV-04 (§3 there), entity and schema definition (§4), the validation contract (§5), relationships and referential integrity (§6), migration-safety constraints (§7), backward-compatibility for stored data (§8), and temporal integrity and history (§9) — as concrete, physical mechanism. It answers **how** a builder defines an entity and a schema, what makes a definition complete and a write valid, how a relationship stays referentially sound across its full lifecycle, how a schema evolves without breaking what already exists under it, and how stored builder data survives change and time.

It is the second document of the Data, Construction & Contracts layer, depending directly on `01-application-construction-design.md` (H19). It also settles four storage-shape obligations five already-written documents bound to this document by name, and makes one explicit determination on an obligation H19 attempted to hand here but which this document declines.

It is structured as a pyramid: first the physical mechanism that realizes entity and schema definition (§3); then the validation contract and the single mediation point that carries it (§4); then relationships and referential integrity (§5); then migration-safety (§6); then backward-compatibility (§7); then temporal integrity and history, including the erasure mechanism it must carry (§8); then the storage-shape obligations this document discharges or declines, one by one (§9); then the bidirectional boundary against `02-platform-data-model-design.md` (§10); then composition with tenant isolation and authentication (§11); then the evidence this mechanism produces (§12); then the design decision this document records (§13); then its boundaries, precedence, and binding rules (§14–§16).

**Verified versus reasoned (`PROCESS.md` §12.3).** Every finding in this document is **reasoned** — from the cited specification and the cited, already-written upstream design documents. No time-sensitive ecosystem, product, or vendor claim is made anywhere in this document.

## 3. Entity and Schema Definition — the Physical Mechanism

### 3.1 Where Builder-Defined Structures Are Stored

Every builder-defined entity, schema, and relationship exists inside the per-application schema `tenant_<tenant_id>_app_<application_id>` that `02-platform-data-model-design.md` §3.3 already fixes, alongside — never in place of — that document's two platform-owned tables. This document adds three catalog structures and, per entity, one physical instance table, all within that same schema boundary; it opens no new schema, no new isolation mechanism, and no structure outside the boundary already fixed there.

### 3.2 The Schema Catalog — the Five Definitional Elements, Physically Represented

`03-software-and-architecture/03-data-model-and-entity-spec.md` §4 fixes that a schema definition must establish Structure, Constraints, Relationships, Identity, and a Version marker, and that a schema is complete only once all five are established. This document realizes each as a catalog row, never as a convention a consuming component must remember to honor:

| Catalog | Realizes | Key Columns |
|---|---|---|
| `entity_catalog` | The entity itself, as a named, addressable unit within the application. | `entity_id` (UUIDv7, PK); `application_id`; `name`; `current_schema_version_id`; `created_at`. |
| `schema_version_catalog` | The **Version marker** element, and the anchor every migration (§6) and backward-compatibility determination (§7) is evaluated against. | `schema_version_id` (UUIDv7, PK); `entity_id` (FK); `version_marker` (monotonic per entity); `created_at`; `backward_compatible_with_prior` (the §7 determination, recorded at the moment this version is proposed). |
| `field_catalog` | The **Structure** and **Constraints** elements — the attributes an instance holds and the shape and conditions each must satisfy — and the **Identity** element, where one or more fields are flagged as identity-bearing. | `field_id` (PK); `schema_version_id` (FK); `name`; `type`; `constraint_definition`; `identity_role` (boolean); `data_governance_category`; `classification_tier`; `consent_basis_relationship_id` (nullable FK → `relationship_catalog`, §9.2). |
| `relationship_catalog` | The **Relationships** element — how the entity relates to another, and what referential integrity that relationship requires (§5). | `relationship_id` (PK); `schema_version_id` (FK, the referencing entity's own version); `target_entity_id` (FK → `entity_catalog`); `cardinality`; `on_change_behavior` (resolve or refuse, §5); `kind` (§3.3–§3.4). |

**A schema is complete, and governs no data, until every row required by all four catalogs exists for it.** `field_catalog` must carry at least one identity-bearing field before `schema_version_catalog`'s row is eligible to become an entity's `current_schema_version_id`; an entity with an incomplete definition accepts no instance write — the deny-by-default rule the specification's own §3 fixes for data integrity, applied here to definitional completeness itself.

### 3.3 Constructs and Bindings, Represented Through the Same Mechanism

`01-application-construction-design.md` §6 constrains this document to make its physical structures capable of representing, without loss: a construct and its kind; the structural bindings that compose constructs into an application; the behavioral bindings attached to a construct; and the access bindings mapping a tenant role to a construct and a bounded action class. This document discharges that constraint by reuse, not by a second mechanism: a **construct** is represented as an entity instance whose governing schema's `entity_catalog` row is flagged as build-surface content, with its `kind` drawn from whatever closed vocabulary governs it (§3.4); a **structural, behavioral, or access binding** is represented as a `relationship_catalog` row whose `kind` column takes one of the three binding-kind values that same vocabulary fixes.

This is a reuse of the entity/schema/relationship mechanism §3.2 already defines, not a parallel structure invented for build-surface content specifically — the same discipline every document in this layer and the one before it applies when a new requirement can be met by extending an existing mechanism rather than building a second one. This document does not thereby assert that "construct" is a synonym for "entity," or that "binding" is a synonym for "relationship": canonical naming remains `03-software-and-architecture/02-domain-glossary.md`'s to fix, per `01-application-construction-design.md` §2's own working-term caveat. What this document fixes is only that the physical mechanism serving one serves the other without a second one existing.

### 3.4 The Construct/Binding-Kind Enumeration — an Explicit Determination

`01-application-construction-design.md` §4.2–§4.3 fixes that the vocabulary of construct and binding kinds is a closed, platform-owned enumeration a builder instantiates but never extends, and defers naming its concrete members here, on the reasoning that the members depend on how they are physically represented. `BACKLOG.md` §1f identifies this deferral's destination as wrong, and this document makes the determination that item calls for, rather than proceeding as though the question were settled.

**This document declines ownership of the enumeration, and states why.**

- **Representation is not enumeration.** Knowing how a kind is stored — as a `kind` column value on `entity_catalog` or `relationship_catalog`, per §3.3 — does not determine which kind values exist. §3.2–§3.3 already discharge the representation question in full, independent of what the vocabulary's concrete members turn out to be; nothing about the storage design above requires the members to be named to be built.
- **The dependency runs the wrong way, and enumerating here would not fix that.** `implementation-document-map.md` fixes that this document depends on `01-application-construction-design.md`, not the reverse. A document cannot resolve, on its upstream dependency's behalf, a question that dependency itself left open — doing so here would mean this document is retroactively deciding part of what H19 already fixed as closed and platform-owned (§4.2 there), which is a decision about the *build surface's own configuration model*, not about a structure a builder defines. That is the opposite kind of artifact from what this document owns (`implementation-document-map.md`'s own charge for this row: "builder-defined entities, schemas, relationships... structures a builder defines").
- **The map does not assign it here.** This document's charge is structures a builder defines; a fixed, finite, platform-owned enumeration that a builder only ever instantiates and never extends is, by `01-application-construction-design.md` §4.2's own definition, not builder-defined content at all.

**This document declines the enumeration to `01-application-construction-design.md`, by targeted amendment, not to a third document.** `BACKLOG.md` §1f names this as the available alternative if the enumeration's destination is reconsidered: "if the lead prefers it stay with the construction document, that is a one-section amendment to `01-application-construction-design.md` instead." This document takes that alternative as the correct resolution — the vocabulary is platform-owned, closed, and conceptual in exactly the register §4.1–§4.2 of that document already occupies; naming its concrete members is a continuation of that document's own §4.3, not a new document's obligation. This document does not perform that amendment itself — amending another document's content is outside this ticket's scope, and outside what a design document may do to a sibling design document without explicit direction (`PROCESS.md` §3) — it states the determination and the destination so the deferral is claimed rather than left dangling, exactly as `BACKLOG.md` §1f asks.

**What this document holds, regardless of where the enumeration lands.** §3.3's representation stands independent of this determination: whichever document eventually names the concrete kind values, `entity_catalog.kind` and `relationship_catalog.kind` are the columns those values populate, and no change to this document's own schema is required when that enumeration is finally written.

## 4. The Validation Contract and INV-04's Particulars for Builder-Defined Data

### 4.1 The Entity Access Gateway — the Single Mediation Point

No existing mechanism in the design library mediates every read and write of builder-defined entity data the way the Registry Accessor mediates every read of the platform registry (`02-tenant-isolation-and-access-control-design.md` §3.1) or the connection-acquisition function mediates every scoped connection (that document's §4.2). This document creates that mediation point — the **Entity Access Gateway** — as the sole path through which any component reads or writes a builder-defined entity's catalog rows or instance data, inside a connection `02-tenant-isolation-and-access-control-design.md` §5.1 has already scoped (§11 below).

The Gateway is the single chokepoint this document runs every check named below through, in fixed order, never as parallel or independently-reachable gateways:

1. **The Validation Engine** (§4.2) — INV-04's particulars for builder-defined data.
2. **The Consent and Minimization Check**, where the access touches personal or sensitive data (§9.3) — the write-mediation gateway `07-data-governance-and-privacy-design.md` §5.2 required and named as not yet existing.
3. **Classification-tier and data-governance-category resolution** (§9.1–§9.2), folded into the connection's already-resolved obligations, never re-derived by a second mechanism.

**This is the single, reused location this document's own storage-shape obligations discharge through**, not four separately-invoked checks at four separately-reachable points. A component that wants to read or write a builder-defined entity has no function available to it that bypasses the Gateway — the same discipline `02-tenant-isolation-and-access-control-design.md` §4.2 already applies to connection acquisition, extended here one layer deeper, to the entity itself.

### 4.2 What the Validation Engine Inspects, Concretely

`03-software-and-architecture/03-data-model-and-entity-spec.md` §3 fixes that committed data must be valid, consistent, and referentially correct, together and at once. The Validation Engine, invoked inside the Gateway before any write is committed, inspects each concretely:

| Property | What the Engine Inspects |
|---|---|
| Validity | The candidate instance's field values against the entity's `current_schema_version_id`'s own `field_catalog` rows — every field's `constraint_definition` evaluated against the candidate value, and every identity-bearing field present and unique within the scope its own constraint fixes. |
| Consistency | Whether the candidate instance contradicts other committed data governed by the same schema version or the same relationship — evaluated against the entity's own current instances and any instance a `relationship_catalog` row binds it to. |
| Referential correctness | Whether every reference the candidate instance holds — via a `relationship_catalog` row — resolves to a target instance that exists and itself currently satisfies its own governing schema (§5). |

**A write that fails any one of the three does not proceed.** This is the specification's own §3 rule, applied here as the Gateway's own refusal path — never a partial commit, never a commit "corrected" afterward. Where the Engine cannot establish that a candidate instance satisfies all three, the write is refused, per the specification's own §5 deny-by-default rule.

**Definitional and instance validation share the Gateway, not two mechanisms.** A schema-definition or schema-evolution action (a new `schema_version_catalog`, `field_catalog`, or `relationship_catalog` row) passes through the identical Gateway, with the Validation Engine's inspection turned toward §3.2's own completeness rule and §7's backward-compatibility determination rather than toward an instance's field values — one mediation point, two modes of the same inspection discipline, never a second gateway for catalog writes.

### 4.3 Composition with `01-invariant-enforcement-design.md`'s Fixed Check Location

`01-invariant-enforcement-design.md` §5.2 already fixes that INV-04's check runs at every commit boundary, at runtime, before data enters the committed state, and at every migration's execution, in the pipeline — and that this document owns what the check inspects for builder-defined data. This document does not relocate that check: the Entity Access Gateway's Validation Engine (§4.2) **is** the runtime commit-boundary inspection that fixed location already anticipates; §6 below is the pipeline-time inspection for a migration. No second check location is introduced, and the halt-and-escalate behavior on a violation is exactly the one `01-invariant-enforcement-design.md` §3.3, §5.2 already fixes — this document supplies the inspection content, never a second halt mechanism.

## 5. Relationships and Referential Integrity

`03-software-and-architecture/03-data-model-and-entity-spec.md` §6 fixes that every reference resolves, none is left dangling, a dependent removal or change does not proceed unresolved, and this holds across a relationship's full lifecycle — creation, change to either end, and removal.

- **A relationship is enforced at the Gateway, not by a native foreign-key constraint alone.** Because a builder-defined entity's instances are versioned rows (§8), a native database foreign key would bind to one physical version row rather than to the logical record a relationship actually targets, and could not, on its own, express that a reference must remain resolvable across supersession. The Validation Engine (§4.2) therefore resolves every `relationship_catalog` reference against the target entity's own *current* instance at evaluation time, on every write to either end of the relationship — a stronger guarantee than a native constraint would give against this document's own versioned physical shape, not a weaker substitute for one.
- **A dependent removal or change is resolved or refused, never left dangling.** Where a write would supersede or mark-not-current an instance another committed instance still references, the Gateway requires that dependency be resolved — by redirecting the reference, by cascading the change under the relationship's own `on_change_behavior`, or by refusing the write outright — before the write proceeds. Uncertainty about whether a dependency is resolved resolves to refusal, per the specification's own §5 rule applied here to relationships specifically.
- **No relationship resolves across a tenant boundary.** Every `relationship_catalog.target_entity_id` is constrained, at definition time, to an `entity_catalog` row within the same application's own schema — there is no column through which a relationship could name an entity outside the schema boundary `02-platform-data-model-design.md` §3.3 already fixes, which is itself confined to one tenant. This composes with, and does not duplicate, INV-01's own enforcement (`02-tenant-isolation-and-access-control-design.md` §3–§5): the relationship mechanism has no naming path to a foreign tenant's schema at all, the same structural absence that document's §8 already establishes for every other cross-tenant path in this design.

## 6. Migration-Safety

`03-software-and-architecture/03-data-model-and-entity-spec.md` §7 defines a migration as a change to a schema's definition, or to data already committed under it, applied after instances already exist under the prior definition.

- **A migration is a new `schema_version_catalog` row plus, where the row's own `backward_compatible_with_prior` determination (§7 below) is false, a transformation of existing instances into conformance with it.** Where the determination is true, no transformation of existing instances occurs at all — every existing version row remains valid exactly as committed, under its own recorded `schema_version_id`, and only new writes are evaluated against the new version (§7). A migration in the backward-incompatible sense exists only where existing instances must actually be rewritten to remain valid.
- **A migration is all-or-nothing.** Where existing instances must be transformed, the transformation runs as a single unit with respect to validity: either every affected instance is rewritten into a new version row conforming to the new schema and the migration completes, or none is, and every affected instance remains exactly as it was under its prior schema version. No migration this mechanism performs leaves an instance satisfying neither its prior nor its new schema.
- **A migration preserves referential integrity throughout.** Every reference a migrated instance holds or is held by is re-evaluated by the Validation Engine (§5) as part of the same unit of work the migration itself is; a migration that would leave a reference dangling, even transiently, does not complete.
- **A reversible path is a structural consequence of §8's own append-only shape, not a separate mechanism.** Because no instance write is ever a destructive update — every version, including one written as part of a migration, is a new row alongside, never in place of, what it supersedes (§8) — the prior valid state remains physically present and addressable by its own `schema_version_id` for as long as the retention rules `03-software-and-architecture/06-non-functional-requirements.md` set for it, satisfying INV-08's reversible-path requirement as a property this document's own storage shape already carries, not as a second mechanism built to satisfy it.
- **A migration affecting one tenant's or one application's data never touches, depends on, or requires access to another's.** Every migration runs inside the connection `02-tenant-isolation-and-access-control-design.md` §5.1 already scopes to the single schema the migration targets; no migration mechanism this document designs opens a second connection to a different tenant's or application's schema.
- **Numeric duration, downtime, and resource ceilings on a migration are `03-software-and-architecture/06-non-functional-requirements.md`'s, cited and never restated here.** This document fixes the conditions under which a migration may proceed at all, never the thresholds by which its performance is judged.

## 7. Backward-Compatibility for Stored Data

`03-software-and-architecture/03-data-model-and-entity-spec.md` §8 fixes that stored data remains valid, accessible, and correctly related under schema evolution except along a managed, announced path, and that determining whether a given evolution is backward-compatible is this document's own to make.

- **The determination is made once, at the moment a new `schema_version_catalog` row is proposed**, by the Validation Engine operating in its definitional mode (§4.2): whether every instance already committed under every prior `schema_version_id` for this entity remains valid, accessible, and correctly related without being rewritten under the proposed version. The result is recorded on the new row's own `backward_compatible_with_prior` column — never inferred later, never left for a downstream consumer to re-derive.
- **A determination of `true` permits the evolution to proceed as an ordinary change.** No existing instance is rewritten; new writes are evaluated against the new version; §6's migration mechanism is not invoked, because nothing already committed requires transformation.
- **A determination of `false`, or one the Engine cannot establish with confidence, is treated as backward-incompatible.** The evolution does not proceed as an ordinary schema-version row; it follows the managed, announced path `05-meta-operations/08-change-management-and-evolution-policy.md` and gate G-6 own in full — this document fixes only the determination and the point it is made, never the announcement, scheduling, or human-review mechanics of that path.
- **Uncertainty resolves to backward-incompatible, never the reverse.** Where the Engine cannot establish that every already-committed instance remains valid, accessible, and correctly related under a proposed version, the proposal is refused the ordinary path and routed to the managed one — the specification's own §8 deny-by-default rule, applied here at the exact point the determination is made.

## 8. Temporal Integrity and History

`03-software-and-architecture/03-data-model-and-entity-spec.md` §9 fixes effective dating, append-only retention, and full history as a generic, always-on obligation of every builder-defined entity, distinct from the audit trail and never a synchronization mechanism.

### 8.1 The Physical Shape

Every builder-defined entity's instances live in one physical table inside the application's own schema, structured so that every write is an insert, never an update or a delete of a prior row:

| Column | Purpose |
|---|---|
| `version_id` | UUIDv7, primary key — unique per version row. |
| `record_id` | UUIDv7, assigned once when a logical record is first created and carried unchanged through every subsequent version of it — the stable identity §9 requires be reconstructable across a record's full history. |
| `schema_version_id` | FK → `schema_version_catalog` — which schema version this specific version row conforms to. |
| `effective_from` | When the values this version holds are true as of — distinct from `recorded_at`, realizing the specification's own "effective dating is distinct from the write." |
| `recorded_at` | When this version was actually written. |
| `superseded_by` | Nullable, self-referencing `version_id` — the version that supersedes this one, where one exists. |
| one column per builder-defined field | Typed and constrained per the governing `field_catalog` rows (§3.2). |

- **No write ever updates or deletes an existing version row.** A change to a record is realized as a new row sharing the prior row's `record_id`, with the prior row's `superseded_by` set to the new row's `version_id` — the row itself, and every field value it held, remains exactly as committed. "Current" state is the row, per `record_id`, whose `superseded_by` is null; this document does not require a separate materialized pointer, though nothing here forbids one as a performance optimization the physical layer may add without changing this shape.
- **Full history is reconstructable by construction, not by configuration.** Every prior version of a record, and the effective date each held, is directly queryable by `record_id` the moment the entity exists — no builder action enables or configures this, and none can disable it, consistent with the specification's own "auditable by default, not by configuration."
- **This is not the audit trail.** This table records what a builder-defined record's own data *was*; it carries no actor attribution, no tamper-evidence mechanism, and is never consulted in place of `08-audit-and-traceability-design.md`'s own record of what the platform or an actor *did* — the two boundaries the specification's own §9 already draws, held here without restatement.
- **This is not synchronization machinery.** No column above exists for conflict resolution or offline-sync purposes; `superseded_by` is a history pointer, never a tombstone in the sync sense `01-technology-stack-design.md` §21 and `DECISIONS.md` D-11 already exclude from this design.
- **Numeric retention on how long history is kept is `03-software-and-architecture/06-non-functional-requirements.md`'s, cited and never restated here.**

### 8.2 Field-Level Erasure Across Every Retained Version

`07-data-governance-and-privacy-design.md` §4.3 requires that a deletion or de-identification obligation reaching a builder-defined entity's personal-data fields be satisfied across **every retained version, current and historical alike** — not the current version alone — and states this as a binding requirement on this document's own design of the history mechanism.

- **Erasure is a distinct write path, targeting content, never a record's existence or its place in history.** Where a field's `data_governance_category` (§9.2) obligates erasure, the mechanism overwrites that field's stored value, in place, on every version row sharing the affected `record_id` — every `version_id`, every `effective_from`, every `superseded_by` link, and every non-personal field's own value remain exactly as committed. Nothing about this operation removes a row, breaks the `record_id` chain, or shortens the record's own reconstructable history; only the erasable field's content changes, and only where the erasure obligation requires it.
- **This does not contradict §8.1's append-only rule, because the specification itself carves out exactly this case.** `03-software-and-architecture/03-data-model-and-entity-spec.md` §9 states directly that the history obligation "meets, and does not override, the erasure rules `02-governance-and-security/06-data-governance-and-privacy.md` owns," and that this document "owns the structure; the privacy document owns whether, when, and how a record is erased." The retained *shape* of history — that a version existed, when, and in what sequence — is what §8.1 protects; the *content* of a specific field a governing document obligates to be erasable is what this mechanism discharges, and the two are not the same guarantee.
- **The audit trail's own reference to the record remains resolvable, unaffected.** `08-audit-and-traceability-design.md` §7 already resolves the immutability/erasure tension by holding that an audit event's own reference to an entity is an opaque identifier, never the entity's own content, and that erasure "targets the referenced entity's own stored content" without ever needing to reach the audit trail's reference to it. Because this mechanism never touches `record_id` or `version_id` — only field content — every audit event referencing either identifier continues to resolve after an erasure, exactly as that document's own resolution requires.
- **This mechanism does not itself decide whether, when, or how erasure is triggered.** `07-data-governance-and-privacy-design.md`'s Retention Sweep and consent-withdrawal path (§4.2–§5.3 there) own the triggering condition in full; this section fixes only that, once triggered, the mechanism reaches every retained version, not the current one alone.

## 9. The Storage-Shape Obligations Handed to This Document

Five already-written documents each bound a storage-shape obligation to this document by name. Each is discharged or explicitly declined below — none is silently dropped, per the same discipline `08-audit-and-traceability-design.md` already applied when reconciling twenty-two inherited evidence rows.

### 9.1 Region-of-Record and Classification Tier

`06-compliance-and-data-residency-design.md` §10.1 binds "this document (or `02-platform-data-model-design.md`, whichever settles it first)" to supply the region-of-record and classification-tier attributes the Region Boundary Check reads at resolution time. This document resolves the binding differently for the two attributes, because they attach to different kinds of structure.

- **Classification tier — discharged here.** A classification tier is a property of a specific piece of *data*, and every piece of data this document governs is a builder-defined field. `field_catalog.classification_tier` (§3.2) is this document's discharge of that half of the obligation: the tier is intrinsic to the field's own definition, required at schema-definition time (§4.2's completeness rule already refuses an incomplete definition), and read by the Entity Access Gateway at the same point every other check runs (§4.1) — never inferred by a consumer, and never absent-by-default, consistent with `06-compliance-and-data-residency-design.md` §5's own "intrinsic, not an attribute a consumer infers" rule. An unclassifiable or unrecorded tier is treated identically to that document's own rule: the Gateway resolves it to the most restrictive tier, Regime-Governed, until it is explicitly classified.
- **Region-of-record on an actor, tenant, or application — declined to `02-platform-data-model-design.md`.** Region-of-record, per `06-compliance-and-data-residency-design.md` §3.2, is an attribute of the tenant's or application's own registry row — `platform.tenants` or `platform.applications` — not of a builder-defined entity. This document owns neither table (§10 below), and cannot supply a column on a schema it does not own. Neither document has yet added this attribute; this document states that plainly rather than silently treating the obligation as satisfied by classification tier alone, and identifies `02-platform-data-model-design.md` as the document whose schema the attribute belongs on, per that document's own bidirectional boundary with this one.

### 9.2 Data-Governance Category, Retention Obligation, and Consent-Basis Storage

`07-data-governance-and-privacy-design.md` requires all three as traveling properties on governed data elements. Each is discharged as a `field_catalog` property (§3.2), on the same intrinsic-and-required discipline §9.1 already applies to classification tier:

- **Data-governance category** — `field_catalog.data_governance_category`, required at definition time, read by the Gateway alongside classification tier. An unclassifiable or unrecorded category resolves to sensitive personal data by default, per `07-data-governance-and-privacy-design.md` §3.1's own rule.
- **Retention Obligation** — not a fixed catalog value, because a retention obligation's own end condition (purpose end, consent withdrawal, or ceiling) is evaluated per instance, not fixed once per field. `field_catalog` fixes only that a personal-data field carries a Retention Obligation and how it is to be evaluated (a reference to the numeric ceiling `03-software-and-architecture/06-non-functional-requirements.md` owns); the obligation's live state for a given record is read by `07-data-governance-and-privacy-design.md`'s own Retention Sweep directly against this document's `effective_from`/`recorded_at` columns (§8.1) and the field's declared category — this document supplies the readable structure, that document owns the sweep.
- **Consent basis** — never a dedicated catalog column, because the content of a consent basis is builder-defined per `07-data-governance-and-privacy-design.md` §5.1. `field_catalog.consent_basis_relationship_id` (§3.2) declares, for a personal-data field, which `relationship_catalog` entry — an ordinary relationship, per §5 above — resolves to whatever builder-defined record holds that field's own consent-basis content. This reuses the relationship mechanism already designed rather than inventing a second, consent-specific reference type.

### 9.3 The Write-Mediation Gateway for the Consent and Minimization Check

`07-data-governance-and-privacy-design.md` §5.2 fixes the requirement and states directly that "no such gateway exists yet for builder-defined data," binding this document and `01-application-construction-design.md` to supply it. The Entity Access Gateway (§4.1) is this document's discharge: before a write that would collect personal data, or a read that would use it, the Gateway evaluates whether a lawful, disclosed basis — resolved via §9.2's `consent_basis_relationship_id` — covers the specific collection or use attempted, and refuses where it cannot be established, exactly as that document's own §5.2 requires. This is the same chokepoint the Validation Engine and the classification/category resolution already run through (§4.1) — one Gateway discharging three obligations, never three separate gateways.

### 9.4 The Provenance Attribute

`05-ai-tooling-security-design.md` §5 assigns the provenance attribute — an artifact fragment's `ai-suggested`/`builder-approved` state — to "this document or `09-ai-assisted-builder-tooling-design.md`, whichever owns the artifact's own data model."

**This document declines the provenance attribute to `09-ai-assisted-builder-tooling-design.md`, with grounds.** A provenance state describes a suggestion or a proposed change the AI-assisted builder tooling produces — an object internal to that tooling's own suggestion-and-confirmation workflow, never a piece of domain data a builder models to represent something within a built application. It is not builder-defined content in the sense this document's entity/schema mechanism exists to serve (§2); it is administrative state belonging to the tooling whose workflow performs the one legitimate `ai-suggested` → `builder-approved` transition (`05-ai-tooling-security-design.md` §5.2). `09-ai-assisted-builder-tooling-design.md` is the document that designs that workflow and its suggestion model; it is the one positioned to fix where the attribute physically lives, exactly as `05-ai-tooling-security-design.md` §9's own boundary statement anticipates. This document adds no catalog column, no relationship kind, and no accommodation for provenance anywhere in the mechanism above.

## 13. Design Decision Records

### 13.1 ADR-028 — Builder-Defined Entity Physical Realization, the Entity Access Gateway, and the Construct/Binding-Vocabulary Determination

- **Status:** Provisional — Pending Lead Approval.
- **Cost to reverse:** **Brutal** (`PROCESS.md` §12.1), matching the grade `implementation-document-map.md` already assigns this document. This decision fixes the physical shape of every builder-defined entity any builder will ever model — the catalog structure, the versioned-row instance shape, and the single mediation point every read and write of that data passes through. Reversing or materially changing any of the three does not merely change code: every already-committed instance, and every historical version already retained beneath it, is stored against this shape, and a schema-shape reversal requires migrating that entire stored history under a corrected model rather than changing a check or a policy going forward. This is the specification's own most expensive rung (`03-software-and-architecture/03-data-model-and-entity-spec.md`'s own INV-04/INV-08/INV-09 elaboration exists specifically because this shape, once populated, is this costly to move), and is stated honestly at that grade rather than understated to look cheaper than the document it is the design-phase counterpart to (`02-platform-data-model-design.md`, graded identically for the platform's own equivalent decision).
- **Upstream decisions assumed:** `03-software-and-architecture/03-data-model-and-entity-spec.md` §3–§9 (the specification this document realizes in full); `01-application-construction-design.md` §4, §6 (the configuration model this decision's §3.3 represents, and the boundary constraining without owning it); `02-platform-data-model-design.md` §3.3, §9–§10 (the schema boundary this decision's structures live inside, the UUIDv7 key convention, and the D-12 scope resolution this decision realizes for builder-defined entities specifically); `02-tenant-isolation-and-access-control-design.md` §3–§5 (the connection-scoping and self-verification mechanism the Entity Access Gateway composes with, never duplicates); `06-compliance-and-data-residency-design.md` §5 and `07-data-governance-and-privacy-design.md` §3–§5, §8 (the traveling-property discipline this decision's `field_catalog` columns extend); `05-ai-tooling-security-design.md` §5 (the provenance obligation this decision declines); `08-audit-and-traceability-design.md` §4 (the consolidated event model this decision's evidence populates). ADR-021 through ADR-027 remain Provisional and are not assumed settled; this decision depends on none of their approval status.
- **Verified vs. reasoned:** Reasoned throughout. No time-sensitive ecosystem, product, or vendor claim is made; every finding derives from the cited specification and the cited, already-written upstream design documents' own content.
- **Question this answers:** Given a platform that must let a builder define an entity and a schema for any subject matter, with no domain presumed, and given that entity data must survive migration and evolution without breaking a guarantee already made to it, carry effective dating and full history generically, and remain purgeable of personal-data content on demand across every retained version — what is the smallest physical mechanism that realizes all of this, mediates every read and write of it through one reused chokepoint rather than several, and correctly resolves the storage-shape obligations five upstream documents already bound here, including the one this document is positioned to decline?
- **Criteria applied, and how each resolved:**
  1. *One physical table per entity, versioned by insert-only rows, versus a shared, generic value store.* Decisive for one table per entity — a shared generic (entity-attribute-value) store cannot carry native, typed constraints per field, complicates the referential-integrity check §5 requires, and gives the typed query builder `01-technology-stack-design.md` §14.4 already commits to nothing to compose against; a table-per-entity design, generated from the catalog at definition time, keeps every later mechanism (validation, referential integrity, migration, erasure) operating on ordinary typed columns.
  2. *One reused mediation point (the Entity Access Gateway) for validation, consent/minimization, and classification/category resolution, versus separate, independently-reachable checks.* Decisive for one Gateway — the discipline every document in Layers 2–3 has applied consistently (the Region Boundary Check inline in connection acquisition; the Consent and Minimization Check's own required structural placement, `07-data-governance-and-privacy-design.md` §5.2); a component with more than one path to builder-defined data is a path some check could be bypassed through.
  3. *Field-level erasure in place versus row-level or version-level removal.* Decisive for field-level, in place — `07-data-governance-and-privacy-design.md` §4.3 requires purging personal-data content from every retained version, not removing the version itself, and removing a version row would break the `record_id` chain §8.1's own reconstructability guarantee depends on and the audit trail's own reference to that version (`08-audit-and-traceability-design.md` §7).
  4. *Decline the construct/binding-kind enumeration, and decline the provenance attribute, versus accepting both.* Decisive for declining both — `BACKLOG.md` §1f's own analysis (representation is not enumeration; the dependency runs the wrong way) applies with equal force to the enumeration, and the provenance attribute describes tooling-internal suggestion state, not builder-defined domain content, so accepting either would store platform-owned or tooling-internal content inside a mechanism built for builder-defined content specifically — a category error this decision avoids by declining, with grounds, rather than silently absorbing.
- **Context:** This is the second consolidation-shaped ticket of the design phase, after `08-audit-and-traceability-design.md`'s reconciliation of twenty-two inherited evidence rows. This document reconciles four-to-five inherited storage-shape obligations into one entity model, on the same discipline: no obligation is silently dropped, and where one cannot be discharged as handed, that is stated explicitly, with the destination named (§9).
- **Decision:** (1) Every builder-defined entity is realized as one physical, insert-only, versioned table per entity inside the application's own schema, keyed by a stable `record_id` and a per-version `version_id`, with `superseded_by` carrying supersession and no column ever updated or deleted (§8.1). (2) A four-catalog structure (`entity_catalog`, `schema_version_catalog`, `field_catalog`, `relationship_catalog`) physically represents the specification's five definitional elements, and represents constructs and bindings through the identical mechanism rather than a second one (§3.2–§3.3). (3) The Entity Access Gateway is the single, reused mediation point for the Validation Engine, the Consent and Minimization Check, and classification-tier/data-governance-category resolution — never three separately-reachable checks (§4.1, §9). (4) The construct/binding-kind enumeration is declined to `01-application-construction-design.md`, by targeted amendment, on the grounds that it is platform-owned, closed, conceptual content — the opposite kind of artifact from what this document owns (§3.4). (5) The provenance attribute is declined to `09-ai-assisted-builder-tooling-design.md`, on the grounds that it describes tooling-internal suggestion state, not builder-defined domain content (§9.4). (6) Region-of-record on a tenant or application is declined to `02-platform-data-model-design.md`, stated as an open obligation on that document's own schema, not discharged here (§9.1). (7) Personal-data erasure reaches every retained version's field content, in place, never a version's existence or its history-chain identifiers (§8.2).
- **Alternatives considered:** *A shared, generic entity-attribute-value store instead of one table per entity* — rejected under criterion 1; it would weaken every downstream mechanism this document also owns. *Three or more independently-reachable checks instead of one Gateway* — rejected under criterion 2; a defect bypassing one check would leave the others intact but the property none of them alone guarantees (that every access clears all three) false. *Row-level or version-level deletion for erasure* — rejected under criterion 3; it breaks reconstructability and the audit trail's own reference discipline. *Accepting the construct/binding-kind enumeration here, or accepting the provenance attribute here* — both rejected under criterion 4, as a category error importing platform-owned or tooling-internal content into a mechanism built for builder-defined content.
- **Consequences:** Binds `03-data-administration-design.md` and `04-workflow-and-process-automation-design.md` to read and write builder-defined entity data only through the Entity Access Gateway, never through a second access path of their own (`implementation-document-map.md`'s own dependency listing). Binds `01-application-construction-design.md` to receive, by targeted amendment and on the grounds stated in §3.4, the construct/binding-kind enumeration this document explicitly declines. Binds `09-ai-assisted-builder-tooling-design.md` to fix the provenance attribute's own storage shape, per §9.4. Binds `02-platform-data-model-design.md` to close the region-of-record obligation on its own schema, per §9.1 — an obligation this document states as open, not as discharged on that document's behalf. Adds no obligation to `08-audit-and-traceability-design.md`'s record shape, storage, or tamper-evidence mechanism — only three new `event_type` values within its existing model (§12), and concrete integration for two event types that document already owns. Adds no obligation to `02-tenant-isolation-and-access-control-design.md` or `03-authentication-and-identity-design.md` — both are consumed exactly as already designed, never extended.

## 16. Binding Rules

These rules hold for every entity, schema, relationship, and change subject to this model and are subordinate to the charter.

- **Every builder-defined entity is a physical, insert-only, versioned table inside its own application's schema.** No write ever updates or deletes an existing version row; a change is a new row sharing the prior row's `record_id` (§8.1).
- **A schema is complete, and governs no data, only once all five definitional elements are established across the four catalogs.** An incomplete definition accepts no instance write (§3.2).
- **Every read and write of builder-defined entity data passes through the Entity Access Gateway, with no second path.** The Validation Engine, the Consent and Minimization Check, and classification/category resolution each run inside that single mediation point (§4.1).
- **A write that fails validity, consistency, or referential correctness does not proceed.** Uncertainty resolves to refusal (§4.2).
- **No relationship resolves across a tenant boundary, and no dependent removal or change proceeds unresolved.** Referential integrity holds across a relationship's full lifecycle (§5).
- **A migration is all-or-nothing, and a reversible path is a structural consequence of the append-only shape, never a second mechanism.** No migration leaves an instance satisfying neither its prior nor its new schema (§6).
- **A schema evolution's backward-compatibility is determined once, at the point of proposal, and uncertainty resolves to backward-incompatible.** No existing instance is rewritten under a compatible evolution (§7).
- **Personal-data erasure reaches every retained version's field content, never a version's own existence or its history-chain identifiers.** The audit trail's reference to a record remains resolvable after erasure (§8.2).
- **The construct/binding-kind enumeration and the AI-suggested/builder-approved provenance attribute are explicitly declined, not silently absorbed.** Each is routed to the document positioned to own it, with grounds stated (§3.4, §9.4).
- **No storage-shape obligation handed to this document is silently dropped.** Each of the five is discharged, partially discharged with the remainder named, or declined with grounds (§9).
- **Everything remains domain-neutral and platform-level.** No catalog, column, or mechanism in this document encodes the characteristics of any single domain; all remain valid for any software built on the platform.
- **This document records exactly one ADR.** ADR-028 (§13) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, boundary, or invariant the cited specification and cited upstream design documents already fix.
