# Workflow and Process Automation Design — AI ahaMatic

## 1. Purpose and Reading Order

This document realizes `01-business-and-ux/03-platform-capability-model.md`'s workflow-and-process-automation row (C-18) as concrete mechanism: the generic means to model, execute, and govern processes across built software — process modeling, human-task routing, automated rule execution, and process lifecycle management — bound to no predetermined domain. It answers **how**, and it answers it as an **integration boundary around an adopted engine, never as an engine**.

Two standing decisions bound this document before any of its content is fixed, and neither is reopened here. `DECISIONS.md` **D-14** adopts BPMN-style process modeling for C-18. `DECISIONS.md` **D-20** fixes that C-18 is realized by adopting an existing BPMN engine, not by building one, and explicitly selects none — engine selection is a separate evaluation, run under the criteria in force at the time. This document designs integration with an engine; it does not select one, and it does not design one. `01-technology-stack-design.md` §22 (ADR-012) is the worked precedent for this shape: fix the constraints an eventual selection must satisfy, without making the selection.

It is the fourth document of the Data, Construction & Contracts layer, depending directly on `01-application-construction-design.md` (H19) and `02-data-model-and-entity-design.md` (H20). It is structured as a pyramid: first the process-modeling model itself and its boundary against the construct/binding vocabulary (§3); then where a process definition and an in-flight instance's state physically live, and what that requires of any adopted engine (§4) — the sharpest edge of this document, because an adopted engine brings its own execution model and, typically, its own persistence; then the integration boundary around the engine, stated as what this document designs and what it deliberately leaves to the engine (§5); then automated rule execution as a caller of the Entity Access Gateway (§6); then human-task routing, composed with the access-binding model rather than a new one (§7); then process lifecycle management, including what happens to an in-flight instance when its definition changes (§8); then the adopted engine's standing as a licensed, re-evaluated dependency (§9); then the evidence this mechanism produces (§10); then the design decision this document records (§11); then its boundaries, precedence, and binding rules (§12–§14).

**Verified versus reasoned (`PROCESS.md` §12.3).** Every finding in this document is **reasoned** — from the cited specification, the cited upstream design documents' own content, and the structural properties a BPMN-conformant execution engine must have to compose with an already-fixed isolation model. No claim is made anywhere in this document about what any specific engine currently supports, licenses under, or persists how; those are exactly the class of time-sensitive claim `PROCESS.md` §12.3 requires be verified before it decides anything, and no engine has been selected for this document to verify against. Where this document states what an adopted engine "must" provide, that is a structural requirement derived from the platform's own already-fixed guarantees, not an assertion about a candidate's present capability.

## 2. Scope and What This Document Does Not Own

This document owns: the process-modeling model and its boundary against the closed construct/binding vocabulary (§3); the physical-placement and isolation requirements for a process definition and an in-flight instance's state (§4); the integration boundary this platform holds around an adopted engine (§5); the discipline that automated rule execution reaching builder-defined entity data is a caller of the Entity Access Gateway, never a second path (§6); human-task routing, composed with the access-binding model already fixed (§7); process lifecycle management, including definition versioning and the treatment of an in-flight instance under a changed definition (§8); and the adopted engine's standing as a dependency subject to the license-category check and its standing re-evaluation (§9).

This document does **not** own, and does not decide:

- **Which BPMN engine the platform adopts.** `DECISIONS.md` D-20 fixes that decision as a separate evaluation, run under the criteria in force at the time, and explicitly outside this document's charge. Nothing here names, prefers, or ranks a candidate.
- **The engine's own execution mechanics.** Scheduling, state-machine transitions, token semantics, timer and event semantics, and compensation internals are the adopted engine's own concern, realized however that engine's own architecture realizes them. Designing any of these would be designing an engine, exactly what `DECISIONS.md` D-20 forecloses. This document designs the boundary around that mechanism, never its interior.
- **The shape of builder-defined data — entities, schemas, fields, relationships, and their validation, referential-integrity, and migration-safety rules (C-05).** `02-data-model-and-entity-design.md` owns all of it in full. A process's automated rule steps and service-task-shaped steps reach that data only as a caller of the Entity Access Gateway that document already fixes (§6); this document adds no catalog, no column, and no second mediation point to anything that document owns.
- **The Entity Access Gateway itself — the Validation Engine, the Consent and Minimization Check, classification-tier/data-governance-category resolution, and the End-User Record-Reach Check, and their fixed order.** `02-data-model-and-entity-design.md` §4.1 owns the Gateway in full; this document is a caller of it, never a second implementation of any check it already performs.
- **The construction action, the configuration model, or the closed construct/binding-kind vocabulary (C-04, C-06).** `01-application-construction-design.md` owns all three in full, and that document's own §4.2.2 explicitly excludes a process's shape from its construct-kind vocabulary. This document does not reopen, widen, or duplicate that vocabulary; it composes with Surface and Command where a process step crosses into build-surface content (§3.2).
- **The generic administrative interface derived from a builder's own entities (C-27).** `03-data-administration-design.md` owns it in full; this document neither depends on it nor designs any accommodation for it.
- **Authentication, session mechanics, tenant- and application-context resolution, or connection-scoped isolation enforcement.** `03-authentication-and-identity-design.md` and `02-tenant-isolation-and-access-control-design.md` own all of it in full; every action this document designs runs inside the identity and connection those documents already establish, and this document establishes no second identity or scoping mechanism.
- **The license-category check, the third-party dependency policy, its standing re-evaluation, or attribution generation.** `09-licensing-and-dependency-compliance-design.md` owns all of it in full; §9 below states that the adopted engine is subject to that mechanism, and does not redesign it.
- **Audit-event record shape, storage, or tamper-evidence.** `08-audit-and-traceability-design.md` owns all of it; this document's evidence (§10) populates that record and never redesigns it.
- **Any independent technology, topology, or scope decision beyond the one named in §11.** This document records exactly one ADR.

## 3. The Process-Modeling Model

### 3.1 Process Definitions as a Distinct Primitive, Not a Construct Kind

`01-application-construction-design.md` §4.2.2 fixes the concrete construct-kind vocabulary as exactly Surface and Command, and states directly that "the shape of a multi-step process is `04-workflow-and-process-automation-design.md`'s process model (C-18), never a construct kind here." This document takes that exclusion as settled and fixes what fills the space it leaves: a **process definition** is a distinct, builder-authored primitive of this document's own — a directed graph of steps and flows expressing sequence, branching, and concurrency, per the BPMN-style modeling `DECISIONS.md` D-14 already adopts — never a third construct kind, never a fourth binding kind, and never a re-expression of what a structural binding already does.

**Why a process is not reducible to the existing vocabulary.** A structural binding expresses "which constructs belong to which, and in what arrangement" (`01-application-construction-design.md` §4.1) — a static composition relation, not a graph a runtime engine advances a token through, with branching conditions, concurrency, and a notion of "currently at this step" that a static binding has no field to hold. A process is therefore genuinely irreducible to the existing vocabulary, not merely inconvenient to express with it — the identical bar that document's own explicit exclusion (§4.2.2) already applies by naming a process's shape as never a construct kind, confirmed here rather than re-derived, by showing why no composition of the existing vocabulary could express it in the first place.

**What a process definition is, generically.** A process definition has an identity, a version, and is confined to the one application and tenant that authored it — the same confinement `01-application-construction-design.md` §4.1 already states for a construct and its bindings, applied here to a primitive of a different shape. It is builder-authored content in the sense that document's own capability-model framing fixes: created, changed, and removed using this document's own mechanism, never altering the mechanism itself.

### 3.2 The Four Boundary-Crossing Step Kinds

A process definition's internal graph — its gateways, events, sub-processes, and the BPMN-conformant semantics that govern how a token advances through it — is the adopted engine's own execution model (§5) and is not designed here. What this document fixes is the smaller, closed set of points at which a step in that graph crosses out of the engine's own execution model and into a mechanism this platform already governs. Exactly four such crossings exist, and each composes with an existing mechanism rather than duplicating it:

| Step Kind | What It Does | Composes With |
|---|---|---|
| Interaction step | Presents information to, or collects information from, an actor at this point in the process. | An already-configured **Surface** construct (`01-application-construction-design.md` §4.2.2), referenced by opaque identifier — never a presentation shape this document defines of its own. |
| Action step | Invokes one discrete unit of behavior at this point in the process. | An already-configured **Command** construct, referenced by opaque identifier — never a behavior shape this document defines of its own. |
| Automated rule step | Evaluates a condition or executes logic against builder-defined entity data, without human involvement. | The **Entity Access Gateway** (§6), as any other caller — never a second data-access path. |
| Human task step | Pauses the process for an actor holding a qualifying role to act. | The **access-binding model** (§7) that already governs which role may act on a construct — never a new task-assignment authorization mechanism. |

**No fifth crossing exists, and none is admitted by convenience.** Where a step's need appears to fall outside these four, the question is first whether it is in fact an interaction, an action, an automated rule, or a human task described unfamiliarly — the same closed-vocabulary discipline `01-application-construction-design.md` §4.2.2 already applies to its own construct kinds, applied here to this document's own step kinds. A genuinely new crossing point is a platform-core change to this document, reviewed under the identical module-responsibility discipline `01-application-construction-design.md` §4.2.2's own closed-vocabulary rule already relies on, never a build-surface action a builder's own process definition can introduce on its own.

**A process step is never itself a construct or a binding, and neither is widened to accommodate one.** An interaction or action step *references* a Surface or Command; it does not become one, and referencing a construct from a process step adds no new binding kind to the three `01-application-construction-design.md` §4.1 already fixes — the reference is this document's own content, carried on the process definition's own step, never a `relationship_catalog` row of a fourth kind.

### 3.3 Where the Boundary Runs, Stated Bidirectionally

`01-application-construction-design.md` owns the construct/binding vocabulary and the meaning of View and Invoke on a Surface or a Command; this document owns the process graph, the four step kinds above, and the composition rule that lets a step reach a construct without reopening that vocabulary. Neither document anticipates the other's own mechanism: `01-application-construction-design.md` does not know a process exists, and this document does not redefine what a Surface or a Command is, or widen the closed action-class vocabulary of that document's §4.2.4 to accommodate a process's own needs. Where a builder needs a condition to gate an interaction or action step's own invocation independent of the process, that condition is the behavioral binding already attached to the referenced construct (`01-application-construction-design.md` §4.1), composed with the process step that reaches it — never a fifth mechanism duplicating what a behavioral binding already expresses.

## 4. Where Process Definitions and In-Flight Instance State Physically Live

This is the document's sharpest edge, named as such by `DECISIONS.md` D-20: an adopted engine brings its own execution model and, typically, its own persistence, and the platform's isolation is structural — one schema per application, one database role per schema, every read and write of builder-defined entity data mediated by a single gateway. Adopting an engine whose persistence sits beside that structure, rather than composing with it, would leave process state outside every guarantee the rest of this design enforces.

### 4.1 The Platform Is Authoritative for the Process Definition

A process definition, as fixed by §3, is builder-authored content confined to one application and one tenant — the same confinement every other builder-authored primitive in this layer already carries. It is therefore stored, and remains authoritative, on the platform's own schema-scoped storage, inside the boundary `02-platform-data-model-design.md` §3.3 and §4 already fix for that application: never on a store the adopted engine alone controls, and never duplicated as two independently-editable records of the same builder intent.

**What this constrains, without owning.** `02-data-model-and-entity-design.md` §3.1 already fixes that every builder-defined structure exists inside the per-application schema, alongside — never in place of — that application's own platform-owned tables; it does not itself enumerate every structure that will ever live there. `01-application-construction-design.md` §6 already models the move this document needs: it constrains `02-data-model-and-entity-design.md`'s physical schema to be capable of representing a construct and its bindings, without owning a table, a column, or a validation rule itself, because fixing the conceptual shape is this layer's own foundational obligation and the physical realization is a narrower decision that shape must precede. This document is in the identical position for a process definition: it must be representable inside the per-application schema boundary §3.1 already fixes, but designing the specific catalog rows that represent it is `02-data-model-and-entity-design.md`'s charge, not this one's. **This document does not perform that physical design itself** — amending a sibling design document's own schema is outside this ticket's scope and outside what one design document may do to another without explicit direction (`PROCESS.md` §3) — and states the constraint and its destination here (§12) so it is handed off rather than left dangling.

**What the constraint requires, concretely.** Whatever physical structures eventually realize a process definition must be capable of representing, without loss: the definition's own identity and version marker; its step graph, including each step's kind (§3.2) and, for an interaction or action step, the opaque construct reference it carries; and a determination, analogous to `02-data-model-and-entity-design.md` §7's backward-compatibility determination, of whether a new version leaves every in-flight instance of the prior version able to continue (§8.1). None of this is a table, a column, or a validation rule this document fixes — those remain `02-data-model-and-entity-design.md`'s own, on the identical boundary `01-application-construction-design.md` §6 already draws for constructs and bindings.

### 4.2 In-Flight Instance State: the Engine's Execution, the Platform's Anchor

A process **instance** is one execution of one version of a process definition. Its running state — which step it currently occupies, what variables it currently holds, what timers are pending — is exactly the engine's own execution model (§5) and is not designed here; the platform does not build a second execution engine to shadow it, which would be building the engine `DECISIONS.md` D-20 already forecloses.

**The platform nonetheless maintains its own authoritative anchor record for every instance**, independent of the engine's own internal state: the instance's identity; which process definition and which version it is bound to (§8.2); which application and tenant it belongs to; its lifecycle status (running, completed, terminated); and, where the instance operates over builder-defined entity data, the opaque reference to the record or records it correlates to. This anchor is what the platform's own isolation self-verification, evidence (§10), and lifecycle management (§8) act on — **it never depends on reading the engine's own internal state to hold**: a mechanism this document depends on for correctness must not itself depend on a system this document does not control for its own correctness.

**This anchor is not a second authoritative store for the definition or for the entity data a step touches.** It records that an instance exists, what it is bound to, and its lifecycle status — never a duplicate of the process definition's own content (§4.1, authoritative on the platform already) and never a cached copy of entity data an automated rule step reads or writes through the Gateway (§6, authoritative there already). ADR-011's server-authoritative rule is not spent by adding a second execution engine's worth of state to track; it is honored by keeping every authoritative fact in exactly one place and letting the anchor record only what the platform itself needs to enforce isolation and lifecycle over an execution it does not itself perform.

### 4.3 What Must Be True of Any Adopted Engine for Isolation to Hold

`02-platform-data-model-design.md` §4.1 makes tenant-boundary isolation structural by ensuring no cross-tenant structure exists anywhere in the design — not a forbidden query, but an absent one. `01-technology-stack-design.md` §14.5 and ADR-004's own rejected alternative make the same point about application separation within the platform's own datastore: **a shared table distinguished only by a tenant or application identifier column was rejected** because isolation would then rest on every query carrying the right predicate, and one omission breaches it. Both points bind an adopted engine exactly as they bind the platform's own schema, because an engine's own persisted state — wherever it is hosted — is process state about a tenant's or an application's own execution, no less than an entity's instance data is.

**This document therefore states, as hard constraints on the eventual selection rather than as a design of this document's own, what would have to be true of any adopted engine:**

1. **The engine's persisted state must be partitionable at a granularity no coarser than this platform's own application boundary, with no structural path for one partition's data to be reached from another's.** An engine whose only multi-tenancy mechanism is a shared store distinguished by a tenant or application identifier column reproduces exactly the pattern ADR-004 already rejected for the platform's own datastore, and cannot be adopted on that ground alone — the isolation obligation this platform holds does not relax because the state in question is an engine's rather than the platform's own.
2. **The engine must accept its scoping identifier only from the platform's own already-resolved context, never from a caller-supplied value a process definition or a task payload could carry.** This is the identical discipline `02-tenant-isolation-and-access-control-design.md` §5.1's own connection-acquisition mechanism already applies — no function accepts a raw identifier a caller supplies independently of the Resolved Request Context — extended here to the boundary at which the platform hands the engine a scope to execute within.
3. **The engine must never become a second authoritative store for data this platform already holds authoritative.** A process definition's own content remains authoritative on the platform (§4.1); builder-defined entity data remains authoritative behind the Entity Access Gateway (§6); the engine's own persistence is authoritative only for its own execution mechanics — token position, timers, and the variables its own execution model requires to resume — never for either of the two.
4. **The engine must be reachable through a documented external interface — an API, an embeddable library, or an equivalent integration surface — that the platform invokes from behind its own already-resolved connection and context, never through a shared database credential that would let the engine, or a caller through the engine, address a schema or a connection the Resolved Request Context did not resolve.**
5. **Where the engine's own persistence is hosted on infrastructure the platform provisions, it must remain within `01-technology-stack-design.md` §20.1's portable subset** — the same discipline already excluding a provider-unique managed service from anything correctness depends on for the sync layer (§21.4 of that document) and the caching layer (§22.2), extended here to whatever store an adopted engine requires.
6. **The engine's license category must be checked at adoption, on then-current evidence, never assumed from its reputation or its category at some earlier point** — §9 below states this in full, citing the mechanism rather than re-deriving it.

**An engine failing any one of these is not a candidate for adoption, independent of every other merit it might otherwise have.** This is stated plainly, per the ticket's own instruction, so a disqualifying property is found here rather than discovered after a selection is already made — the identical discipline `01-technology-stack-design.md` §22.2 already applied when it recorded a licensing constraint on a future cache before any cache was chosen, rather than leaving it to be discovered at adoption time.

## 5. Engine Integration — the Boundary Around an Adopted Engine

### 5.1 What This Document Designs, and What It Hands to the Engine

This document designs the boundary an adopted engine sits behind, never the engine's own interior. Concretely, this document fixes: the process-modeling model and its four boundary-crossing step kinds (§3); the physical-placement and partitioning constraints any engine's persistence must satisfy (§4); the discipline that every reach into builder-defined entity data from an automated rule step is mediated by the Entity Access Gateway (§6); the discipline that a human task step's routing composes with the access-binding model already fixed (§7); and process lifecycle management at the level of definition versioning and in-flight-instance treatment (§8).

This document hands to the adopted engine, and does not design: how a token advances through the process graph between steps; how a gateway's branching condition is internally evaluated once the condition itself has been supplied; timer and event semantics; compensation and error-boundary semantics; and the engine's own scheduling, retry, and recovery mechanics for its own execution state. Every one of these is "specifying scheduling, state-machine transitions, timer semantics, or compensation internals" in the sense this ticket's own writing rules name as the tell of designing an engine rather than the boundary around one — recognized here explicitly so the boundary is not crossed by accretion, one convenient detail at a time.

### 5.2 No Engine-Originated Exemption from Existing Mechanisms

An adopted engine arrives with its own opinions about identity, storage, and scheduling — the exact temptation this project's own prior sessions have already named and refused for every other new mechanism this layer has added (`03-data-administration-design.md` §5.4's check placed upstream of the Gateway rather than folded into it; `07-data-governance-and-privacy-design.md` §7.3's added match class rather than a second filter). This document holds the same discipline for the engine specifically:

- **No engine-originated identity.** Every action this document's mechanism performs — authoring a process definition, starting an instance, advancing a human task, evaluating an automated rule — runs behind the Authenticated Actor Identity and the Resolved Request Context `03-authentication-and-identity-design.md` and `02-tenant-isolation-and-access-control-design.md` already establish. The engine is never consulted to establish or confirm an actor's identity, and never issued a scope wider than the one already resolved for the request that invoked it.
- **No engine-originated storage exemption.** §4.3 already fixes what the engine's own persistence must satisfy; nothing in this section relaxes it for convenience of integration.
- **No engine-originated scheduling authority over platform-governed data.** An automated rule step's evaluation may be triggered by the engine's own scheduling mechanics, but the data it reaches is never read or written except through the Entity Access Gateway (§6) — the engine schedules *when*; it never gains a second path for *how*.

## 6. Automated Rule Execution and the Entity Access Gateway

`02-data-model-and-entity-design.md` §4.1 fixes the Entity Access Gateway as "the sole path through which any component reads or writes a builder-defined entity's catalog rows or instance data," running the Validation Engine, the Consent and Minimization Check, and classification-tier and data-governance-category resolution, in fixed order, as a single chokepoint no caller bypasses. An automated rule step, and any action step whose invoked Command in turn reaches builder-defined entity data, is a **caller** of that Gateway on exactly the same terms as any other component — the identical position `03-data-administration-design.md` §4.1 already establishes for its own record operations.

**"Engine-originated" confers no exemption.** Whether an automated rule step's evaluation is triggered by the engine's own timer, its own scheduling loop, or an actor's own action reaching the step, the read or write it performs against builder-defined entity data clears the identical Validation Engine inspection, the identical Consent and Minimization Check, and the identical classification resolution any other caller clears. There is no reduced check, no bypass, and no privileged code path reserved for an automated step's own operations — the same discipline `03-data-administration-design.md` §4.1 already states for its own interface, restated here for the engine specifically because an engine is exactly the kind of caller most likely to arrive with its own assumption of privileged access to whatever data source it is pointed at.

**No second write path.** An automated rule step's condition-and-parameter content is carried on the process definition itself (§3.2, §4.1) — this document's own content, never a behavioral binding `01-application-construction-design.md` §4.1 already owns, and never a code path that reaches an entity's instance table directly. Where the step's outcome is a write, it is dispatched as the ordinary instance-write operation the Gateway already exposes (`02-data-model-and-entity-design.md` §4.2), never a new write shape this document invents for the engine's convenience.

**What this section does not resolve.** Whether an automated rule step's own condition logic is evaluated by the platform or handed to the engine's own business-rule execution mechanism is an engine-interior question this document does not reach (§5.1) — this section fixes only that wherever the condition is evaluated, its reach into builder-defined entity data is mediated by the Gateway and nowhere else.

## 7. Human-Task Routing

`02-tenant-isolation-and-access-control-design.md` §6 owns the enforcement model across the platform's five actor classes; `01-application-construction-design.md` §4.1 fixes the access binding, mapping a tenant's already-established role to a construct and a bounded action class (View or Invoke); `03-data-administration-design.md` §5 narrows record-scoped reach for the professional-builder actors that document's own interface serves. A human task step's routing composes with the first two of these, and explicitly not the third.

**Why the access-binding model, and not a fourth mechanism.** A human task step, per §3.2, is realized as an interaction or action step referencing an already-configured Surface or Command — presenting the task's own content, or exposing the action that completes it. Which end-user role may perceive or act on that Surface or Command is already governed by the access binding `01-application-construction-design.md` §4.1 fixes: a role holding View may see the task exists and what it presents; a role holding Invoke may submit or execute it. **Routing a human task is therefore resolving, at the moment the process reaches that step, which already-granted role or roles the referenced construct's own access binding names — never a task-assignment grant this document defines independently of that binding.** Where a process needs to route a task to a narrower group than "every actor holding the construct's own grant" — for example, one specific actor among several who hold it — that narrowing is the engine's own task-assignment or claim mechanics (§5.1, an engine-interior concern), operating only among the actors the access binding already qualifies; it is never a widening of who may act, and never a second authorization decision independent of the one the binding already resolves.

**Why not §6's enforcement model on its own, and why not a fourth mechanism either.** §6 of `02-tenant-isolation-and-access-control-design.md` is where the resolved grant is actually checked at runtime — the same connection-scoped, context-bound enforcement that checks any other actor's action against any other construct. A human task step's completion is checked there, exactly as an ordinary Invoke on a Command construct is checked, because that is what completing a human task step *is*, mechanically (§3.2). This document adds no second, task-specific authorization check upstream or downstream of that enforcement; doing so would be inventing the fourth mechanism this ticket's own instruction refuses.

**Why not §5's record-scoped access.** `03-data-administration-design.md` §5 resolves record-scoped reach for the professional-builder actors that document's own administrative interface serves — a distinct actor population and a distinct interface from the end users a built application's own process instances serve. §5.5 of that document already names, and leaves open, the distinct question of end-user role-scoped access to records reached through a construct-mediated surface — a question no document in this layer yet owns. **This document does not resolve that question either.** A human task step's routing operates at exactly the construct-level grain the access binding already operates at today; where a task's own presented content is entity-backed and a finer, record-level reach is eventually needed, that is the same still-open question §5.5 names, inherited here rather than silently closed by this document's own mechanism.

## 8. Process Lifecycle Management

### 8.1 Definition Versioning and Backward-Compatibility Determination

A process definition evolves by a new version, analogous in shape — though not in mechanism, since a process is not an entity (§3.1) — to `02-data-model-and-entity-design.md` §7's own backward-compatibility determination for a schema. At the moment a new version is proposed, a determination is made: whether every instance already in flight under a prior version can continue to run to completion without its current position, its already-taken branch, or its already-invoked steps being rendered invalid by the new graph.

- **A determination that every in-flight instance remains valid permits the new version to become current for new instances immediately**, with no transformation of any in-flight instance's own state — the same "no existing state rewritten" posture `02-data-model-and-entity-design.md` §7 already fixes for a backward-compatible schema evolution.
- **A determination that an in-flight instance would not remain valid, or that this cannot be established with confidence, does not force that instance onto the new version.** Uncertainty resolves toward preserving the in-flight instance's own original binding, never toward migrating it — the identical deny-by-default posture `02-data-model-and-entity-design.md` §7 already applies to an uncertain schema-compatibility determination, applied here to a process-version determination.
- **This determination is this platform's own to make and to record**, on the anchor record §4.2 already fixes, never delegated to the adopted engine's own versioning conventions where those exist — the platform must be able to state, independent of the engine's own internal bookkeeping, which version any given instance is bound to and why a new version was or was not applied to instances already running.

### 8.2 In-Flight Instances Under a Changed Definition

**An in-flight instance is bound to the version of the process definition it started under, for its entire remaining execution, and is never silently re-bound to a newer version mid-flight.** This is a structural requirement on any adopted engine, not a design choice this document has latitude to relax: a token paused at a step that the new graph has removed, renamed, or reshaped has no well-defined resumption point under the new version, and re-binding it anyway would silently corrupt the instance's own execution rather than merely changing its future behavior — the identical deny-by-default reasoning `02-data-model-and-entity-design.md` §7 already applies where a backward-compatibility determination cannot be established with confidence, applied here to a running instance's version binding.

- **An engine that cannot run multiple versions of a process definition concurrently, with each in-flight instance addressed by the specific version it started under, is disqualified from adoption on this ground** — an addition to §4.3's own list of hard selection constraints, stated here because it follows directly from this section's own reversibility argument rather than from the isolation argument §4.3 makes.
- **A version is retired only once no instance remains bound to it.** The platform's own anchor record (§4.2) is what determines this, by querying every instance's own recorded version binding and lifecycle status — never by assuming retirement is safe because a given elapsed time has passed.
- **This composes with, and does not duplicate, `02-data-model-and-entity-design.md` §7's own backward-compatibility determination.** That mechanism governs a schema evolution's effect on already-committed entity instances; this section governs a process-definition evolution's effect on already-running process instances. The two are distinct kinds of state undergoing distinct kinds of change, and this document does not treat one as discharging the other.

## 9. The Adopted Engine as a Licensed, Re-Evaluated Dependency

The adopted engine is a third-party dependency, and the dependency mechanism it is subject to already exists in full: `09-licensing-and-dependency-compliance-design.md` §3 fixes the license-category check, and §5 fixes that a dependency's category is re-evaluated on two triggers — an event-driven re-check on any change to the dependency, and a periodically scheduled sweep independent of whether anything changed. This document does not re-derive either mechanism; it states that the engine is bound by both, exactly as any other dependency is.

**Checked at adoption, on then-current evidence — never assumed.** `01-technology-stack-design.md` §22.2's Redis relicensing is the standing demonstration already recorded elsewhere in this design of why a dependency's license category cannot be assumed from its reputation or from an earlier point in its history: a permissively licensed dependency can leave that footing without any change to how it is invoked. Whichever engine is eventually selected, its license category is resolved by `09-licensing-and-dependency-compliance-design.md` §3's check against the evidence current at the moment of adoption, not against evidence gathered during whatever evaluation preceded the selection and left unrefreshed thereafter.

**Re-checked on both triggers thereafter.** Once adopted, the engine's license category is re-evaluated on any change to how it is incorporated (a version change, a deployment-topology change) and on the standing License Sweep, exactly as §5 of that document already fixes for every other tracked dependency. Where either trigger resolves the engine's category to Prohibited or No-license/unconfirmed where it previously resolved otherwise, this is a license-incompatibility under that document's own §7, blocking exactly as a first-admission finding would.

**This document adds no new mechanism and states no category in advance.** No engine is selected (§1, §2), so no license category can yet be checked; this section binds whichever engine is eventually selected to the existing mechanism rather than pre-judging its outcome.

Where that check refuses, the refusal is captured by whichever event type already governs a runtime authorization refusal against a construct; this document does not duplicate it.

**Landing category, stated honestly where the fit is imperfect.** `process-definition-authoring` describes a builder's own definition of a process's structure, closely paralleling `application-structure-configuration` and `application-behavior-configuration` — `01-application-construction-design.md` §9 already lands both of those under **Authorization and grant events**, reasoning that each "changes what a subsequently-configured access binding can even apply to." ### 11.1 ADR-031 — Process-Definition and Instance-State Placement, the Engine-Integration Boundary, and Human-Task Composition

- **Status:** Provisional — Pending Lead Approval.
- **Cost to reverse:** **Very high** (`PROCESS.md` §12.1; `implementation-document-map.md`'s own rating for this document, unchanged here rather than softened). This is stated at the same grade the map already carries for this document rather than understated to look cheaper than it is.
- **Upstream decisions assumed:** `DECISIONS.md` D-14 (BPMN-style process modeling, unblocking this document); `DECISIONS.md` D-20 (adopt, do not build, an engine; no engine selected; the isolation, portability, and non-duplicated-authority constraints this decision states in full at §4.3); `01-technology-stack-design.md` §22 (ADR-012, the worked precedent for constraining a deferred selection without making it, including the portability and server-authoritative constraints it cites); `01-application-construction-design.md` §4.1, §4.2.2, §4.2.4 (the closed construct/binding vocabulary, its explicit process exclusion, and the access binding this decision composes with rather than reopens), §6 (the constrain-without-own precedent this decision's own §4.1 follows for the process definition's physical placement); `02-data-model-and-entity-design.md` §3.1 (the per-application schema boundary this decision's placement constraint targets), §4.1–§4.2 (the Entity Access Gateway this decision's automated-rule-execution rule binds to), §7 (the backward-compatibility determination reasoning this decision's own §8 parallels for process versions); `02-platform-data-model-design.md` §3.1–§3.4, §4 (the three-level hierarchy and the two isolation strengths this decision's §4.3 constraints extend to an adopted engine); `02-tenant-isolation-and-access-control-design.md` §3, §5.1 (the connection-scoping mechanism this decision's placement and engine-scoping constraint compose with), §6 (the least-privilege enforcement this decision's human-task routing defers to); `03-data-administration-design.md` §4.1 (the caller-of-the-Gateway precedent this decision's §6 follows), §5.4 (the check-placed-upstream-of-the-Gateway precedent this decision's engine-boundary discipline follows); `09-licensing-and-dependency-compliance-design.md` §3, §5 (the license-category check and standing re-evaluation this decision binds the eventual engine to). ADR-021 through ADR-030 remain Provisional and are not assumed settled; this decision depends on none of their approval status beyond the mechanisms they already fix.
- **Verified vs. reasoned:** Reasoned throughout. No claim is made about any specific engine's current capabilities, licensing, or persistence model — none has been selected — and no time-sensitive ecosystem or vendor claim is made anywhere in this decision. Every constraint follows structurally from the platform's own already-fixed isolation, authority, and dependency mechanisms.
- **Question this answers:** Given a platform whose isolation is structural — one schema per application, one database role per schema, every read and write of builder-defined entity data mediated by a single gateway — and given a standing decision to adopt, not build, a BPMN-conformant execution engine with no engine yet selected, what is the smallest process-modeling model that composes with the existing construct/binding vocabulary rather than duplicating it; where must a process definition and an in-flight instance's own state physically live for the platform's structural isolation to hold through the engine rather than beside it; and what must be true of any candidate engine before it can be adopted at all?
- **Criteria applied, and how each resolved:**
  1. *A process as a fourth construct kind versus a distinct, composing primitive.* Decisive for a distinct primitive — `01-application-construction-design.md` §4.2.2 already excludes a process's shape from its own vocabulary by name, and a process's own runtime notion of "currently at this step" has no field in a static structural binding to hold it (§3.1).
  2. *Platform-authoritative storage for the process definition versus treating the engine's own model repository as authoritative.* Decisive for platform-authoritative — `DECISIONS.md` D-20's own consequence names ADR-011 (never a second authoritative store) as a constraint this document must satisfy, and a builder-authored primitive confined to one application, per every other primitive in this layer, is stored and remains authoritative on the platform's own schema-scoped storage (§4.1).
  3. *Partitioning an adopted engine's persistence at application granularity versus accepting a shared, identifier-distinguished store.* Decisive against a shared store — it reproduces exactly the pattern ADR-004 already rejected for the platform's own datastore, and the isolation obligation binding the platform's own tables does not relax because the state in question belongs to an integrated engine rather than to the platform's own schema (§4.3).
  4. *Binding an in-flight instance to its originating definition version versus permitting silent re-binding to a newer version.* Decisive for version-binding — a token paused at a step the new graph has reshaped has no well-defined resumption point under the new version, the identical deny-by-default reasoning `02-data-model-and-entity-design.md` §7 already applies where a compatibility determination cannot be established with confidence (§8.2).
  5. *Routing a human task through the existing access-binding and enforcement model versus a dedicated task-assignment authorization mechanism.* Decisive for reuse — a human task step is, mechanically, an interaction or action step referencing an already-governed Surface or Command, and inventing a fourth mechanism where three already compose is precisely the failure this document's own ticket instructs against (§7).
- **Context:** This is the fourth document of the Data, Construction & Contracts layer and the first to design around a decision — `DECISIONS.md` D-20 — that fixes the document's own first structural choice (build or adopt) before the document is written, on the model `01-technology-stack-design.md` §22 (ADR-012) already established for a deferred selection with binding constraints.
- **Decision:** (1) A process definition is a distinct, builder-authored primitive, never a construct or binding kind; its graph crosses into governed platform mechanism at exactly four points — an interaction step composing with Surface, an action step composing with Command, an automated rule step composing with the Entity Access Gateway, and a human task step composing with the access-binding model — and nowhere else (§3). (2) The process definition itself is stored on the platform's own schema-scoped storage and remains authoritative there; its physical catalog is a representability constraint handed to `02-data-model-and-entity-design.md`, not designed by this document (§4.1). (3) An instance's running execution state is the adopted engine's own; the platform maintains an independent, authoritative anchor record for every instance's identity, version binding, and lifecycle status, which never depends on the engine's own internal state to hold and is never a second copy of the definition's own content or of entity data an automated rule step touches (§4.2). (4) Any adopted engine must satisfy six named constraints — application-granular partitionability with no cross-partition structural path, platform-resolved scoping only, no second authoritative store, a documented external integration surface, ADR-010's portable subset, and a license category checked at adoption — before it is a candidate for selection at all (§4.3), plus the version-concurrency requirement of §8.2. (5) Automated rule execution reaching builder-defined entity data is a caller of the Entity Access Gateway on identical terms to any other caller, with no engine-originated exemption and no second write path (§6). (6) Human-task routing composes with the access-binding model and §6's own enforcement mechanism; it introduces no fourth authorization mechanism, and it leaves the still-open question of end-user record-scoped access exactly where `03-data-administration-design.md` §5.5 left it (§7). (7) A process definition versions analogously to, but never through, `02-data-model-and-entity-design.md`'s own schema mechanism; an in-flight instance is bound to its originating version for its entire remaining execution and is never silently re-bound (§8). (8) The adopted engine is a dependency subject to `09-licensing-and-dependency-compliance-design.md`'s existing license-category check and standing re-evaluation, checked at adoption on then-current evidence, never assumed (§9).
- **Alternatives considered:** *A fourth construct kind, or a subdivision of an existing binding family, to express a process* — rejected under criterion 1; `01-application-construction-design.md` already excludes it by name, and the irreducibility argument holds independently. *Treating the adopted engine's own model repository as the authoritative record of a process definition* — rejected under criterion 2; it would create the second authoritative store `DECISIONS.md` D-20's own consequence names as a constraint, and would make the platform's own reversal-cost accounting for "stored builder data" untrue of what is actually stored. *A shared, tenant-or-application-identifier-distinguished engine store* — rejected under criterion 3; it is the same structural risk ADR-004 already rejected, restated for a different store. *Allowing an in-flight instance to be transparently upgraded to a newer process-definition version* — rejected under criterion 4; there is no general, well-defined mapping from an arbitrary paused position in one graph to a position in a materially different one, and assuming one exists risks silent corruption rather than a visible failure. *A dedicated task-assignment grant, independent of the access binding a task's referenced construct already carries* — rejected under criterion 5; it would duplicate an authorization decision the construct's own access binding already makes, and is exactly the fourth mechanism this document's own writing rules instruct against inventing. *Extending the entity/relationship mechanism `02-data-model-and-entity-design.md` already uses for build-surface content to represent a process definition as well* — considered and rejected, because that mechanism represents content whose kind is drawn from the closed construct-kind vocabulary `01-application-construction-design.md` §4.2.2 already excludes a process's shape from by name; forcing a process into that mechanism would require widening a vocabulary that document has already closed against exactly this content.
- **Consequences:** Binds `02-data-model-and-entity-design.md` to a representability obligation for a process definition's identity, version marker, and step graph, analogous to the obligation `01-application-construction-design.md` §6 already binds it to for constructs and bindings — discharged by a future, separately ticketed amendment, not by this document. Binds engine selection, whenever it occurs, to the six constraints of §4.3 plus the version-concurrency requirement of §8.2, in addition to the isolation, portability, and non-duplicated-authority constraints `DECISIONS.md` D-20 already names; an engine failing any one is not a candidate, independent of every other merit. Adds no obligation to `01-application-construction-design.md`'s closed construct/binding vocabulary, `02-tenant-isolation-and-access-control-design.md`'s enforcement mechanism, or `03-data-administration-design.md`'s record-scoped-access determination — each is composed with exactly as already designed, never extended or re-decided. Adds two new `event_type` values to `08-audit-and-traceability-design.md`'s existing model (§10), on that document's own closest-fit reasoning, never a new mandatory category. Binds the eventually-adopted engine to `09-licensing-and-dependency-compliance-design.md`'s existing license-category check and standing re-evaluation, pre-judging no category in advance because no engine is yet selected. Leaves open, and names rather than silently absorbs, the distinct question of end-user role-scoped access to records reached through a construct-mediated surface (§7) — `03-data-administration-design.md` §5.5's own open question, unresolved here as there.

## 14. Binding Rules

These rules hold for every actor and every action subject to this model and are subordinate to the charter.

- **A process definition is a distinct, builder-authored primitive, never a construct, a binding, or a fifth boundary-crossing step kind beyond the four fixed here.** A process step crosses into governed platform mechanism at exactly one of: an interaction step (Surface), an action step (Command), an automated rule step (the Entity Access Gateway), or a human task step (the access-binding model) (§3).
- **The process definition is stored and remains authoritative on the platform's own schema-scoped storage; the adopted engine is never a second authoritative store for it, and never a second authoritative store for builder-defined entity data.** The engine's own persistence is authoritative only for its own execution mechanics (§4.1–§4.2).
- **No adopted engine is a candidate for selection unless it satisfies every constraint of §4.3 and the version-concurrency requirement of §8.2.** Application-granular partitionability, platform-resolved scoping only, no second authoritative store, a documented external integration surface, ADR-010's portable subset, a license category checked at adoption, and concurrent multi-version execution are floors, not negotiable trade-offs against any other merit a candidate might offer.
- **Automated rule execution reaching builder-defined entity data is a caller of the Entity Access Gateway on identical terms to any other caller.** "Engine-originated" confers no exemption from the Validation Engine, the Consent and Minimization Check, or classification resolution, and no second write path exists (§6).
- **Human-task routing composes with the access-binding model and the tenant-isolation document's own enforcement mechanism; it introduces no fourth authorization mechanism.** A task's completion is checked exactly as an ordinary Invoke on the construct it references (§7).
- **An in-flight instance is bound to the version of the process definition it started under for its entire remaining execution and is never silently re-bound to a newer version.** A version is retired only once no instance remains bound to it, per the platform's own anchor record (§8.2).
- **The adopted engine is bound by the license-category check and its standing re-evaluation on both existing triggers, checked at adoption on then-current evidence and never assumed from reputation or an earlier point in its history** (§9).
