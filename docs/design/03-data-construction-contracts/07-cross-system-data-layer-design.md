## 1. Purpose and Reading Order

This document answers five questions:

- **What presents platform-resident and external data as one coherent layer**, without the platform core coming to depend on any one connected system (§3).
- **What each of C-24's five named guarantees becomes when the path it protects leaves the platform's own control** — the sharp edge this document exists to resolve, one guarantee at a time, by composing with the mechanism each already has rather than inventing a second one (§4).
- **Where external-system connection and credential state physically lives**, constrained against the schema hierarchy `02-platform-data-model-design.md` §3 owns, without this document defining a table in a schema it does not own (§5).
- **What this layer prevents structurally, what it can only detect, and what no mechanism at any strength can bound at all** — the honest limit, and the residual this document inherits a named share of from `06-integration-and-extensibility-design.md` §5.5 (§6).
- **What evidence this layer's own mechanisms produce**, expressed in the audit model already fixed rather than a parallel one (§7).

It is structured as a pyramid: the unified access model first, then the five guarantees realized at the boundary that breaks each of their founding assumptions, then where connection and credential state is constrained to live, then the honest limit, then the evidence produced, then the design decision this document records, then the closing sections.

## 2. Scope: What This Document Owns, and the Boundaries It Never Crosses

This document owns: the unified access model presenting platform-resident and external data as one coherent surface (§3); the realization, at the cross-system boundary specifically, of strict tenant scoping, credential custody, untrusted-input validation, residency and jurisdictional honoring, and the traveling classification property (§4); the constraint on where external-system connection and credential state must fit in the schema hierarchy, without owning that schema (§5); and the statement of what the resulting mechanism closes, detects, and cannot bound (§6).

This document does **not** own, and does not decide:

- **A builder's own modeling of their own entities and schemas (C-05).** `02-data-model-and-entity-design.md` owns entity and schema definition, the Validation Engine, and referential integrity in full. This document's platform-resident leg is a caller of that document's Entity Access Gateway, never a second definition mechanism, and never a second validator for a builder-defined field's own shape.
- **The module and programmatic-contract extension mechanisms (C-11, C-12).** `03-architecture-realization-design.md` owns the extension registry and the Extension component's module boundaries; `06-integration-and-extensibility-design.md` owns the Extender-origin trust mechanism and the Extension Invocation Point. This document's Connector Resolver (§3.2) dispatches through whichever of those mechanisms already governs a given connector's own origin; it does not design a second invocation point, a second registry, or a second trust boundary.
- **The connector marketplace's own submission, discovery, and review mechanics (C-25).** `07-connector-marketplace-design.md` (not yet written) owns what a connector is, how it is offered, obtained, and reviewed, and what isolation strength a marketplace-submitted connector requires — its own first-order question, left open for that document to answer on its own terms, exactly as `05-integration-and-extensibility-spec.md` §8.5 leaves it. This document owns only how *any* connector's data, once reached, is unified with platform-resident data and made to honor the five guarantees at the boundary — it is agnostic to which document eventually answers the marketplace origin's own trust question, and states that mechanism's availability without deciding it.
- **Tenant isolation, connection-scoping, the Resolved Request Context, secrets scanning and redaction, key custody, the Region Boundary Check, the Resolved Residency Obligation, the data-governance-category handling matrix, and the audit-event model.** Each is owned in full by the document that designed it (`02-tenant-isolation-and-access-control-design.md`, `04-security-controls-design.md`, `06-compliance-and-data-residency-design.md`, `07-data-governance-and-privacy-design.md`, `08-audit-and-traceability-design.md`). This document composes with each at the one new point every one of them was not originally evaluated against — a system the platform does not control — and never redesigns, relocates, or duplicates any of them.
- **Any independent technology, topology, or scope decision beyond the one named in §8.** This document records exactly one ADR.

**Two boundaries, stated bidirectionally, per C-24's own definition.** Against `02-data-model-and-entity-design.md`: that document owns every builder-defined entity, schema, and relationship, and this document's platform-resident leg reaches them only as one more caller of its Entity Access Gateway (§4, `02-data-model-and-entity-design.md` §4.1) — this document absorbs none of that content and defines no second entity model. Against the connector mechanisms of C-11, C-12, and C-25: this document unifies access over whatever connector those mechanisms register and trust; it does not define what a connector is, how it is authored, reviewed, or obtained, and it does not absorb or replace the module or programmatic-contract extension mechanisms those capabilities own. C-24's own definition fixes that it neither absorbs nor replaces C-05, C-11, or C-12, and this document holds that line in both directions, not only from its own side.

## 3. The Unified Access Model

### 3.1 Where This Layer Sits, and the Dependency-Direction Rule That Already Covers It

`05-integration-and-extensibility-spec.md` §8.4 already fixes that the cross-system data layer (C-24) "is an Extension-family surface bound by the boundary rules of §4 and the trust-boundary confinement of §7" — distinct from `components/construction`'s entity/schema modeling (C-05), which governs a builder's own data, never data reached through an external system. This document's mechanism is realized as one more Extension-family surface, never a sibling architectural family and never a second placement.

Because C-24 is an Extension-family surface, the dependency-direction rule `03-architecture-realization-design.md` §4.1 already fixes for any module or extension instance — **Full coverage:** "the platform core depending on the presence, behavior, or continued existence of any specific extension instance," closed by requiring that the extension surface be imported only through its published interface sub-path, never through a specific implementation — already covers this layer without a new rule, because the rule's own wording binds "any specific module or extension instance," not one enumerated instance. This document adds no second import-boundary rule; it states that its own published interface (§3.2) is the sub-path through which every platform-core module and every SDK consumer reaches it, exactly as the extension registry's own published interface already works for an extension implementation.

### 3.2 The Unified Access Interface and Its Two Resolvers

The layer publishes exactly one interface — the **Unified Access Interface** — through which any caller (built software reaching it through the SDK; a platform-core module composing it; an in-grant extension's own host function, per `06-integration-and-extensibility-design.md` §5.3, §9) addresses data regardless of where it resides. Every call to the interface takes the identical shape: an addressable resource, an action (read, write, or query), and the Resolved Request Context already governing the invocation (`02-tenant-isolation-and-access-control-design.md` §4.1) — never a caller-supplied tenant or application identifier as an alternative to it.

Behind that one shape, exactly two resolvers exist, and a caller never distinguishes which one answers a given call:

| Resolver | Handles | Composes With |
|---|---|---|
| **Entity Access Gateway resolver** | A resource addressed inside the requesting application's own per-application schema — a builder-defined entity, per `02-data-model-and-entity-design.md` §3.2. | Dispatches every read and write through the Entity Access Gateway (`02-data-model-and-entity-design.md` §4.1) exactly as any other caller does — the Validation Engine, the Consent and Minimization Check, and classification-tier resolution all run in the fixed order that document already fixes. This layer introduces no exemption and no second gateway for this case. |
| **Connector Resolver** | A resource addressed on an external system, through a registered connector (C-11/C-12-authored, or C-25-obtained; `06-integration-and-extensibility-design.md`'s and, once written, `07-connector-marketplace-design.md`'s to trust and admit). | Dispatches through whichever invocation mechanism already governs the resolved connector's own origin — the Extension Invocation Point (`06-integration-and-extensibility-design.md` §5.3) for an Extender-authored connector, the extension registry's own resolution behavior (`03-architecture-realization-design.md` §3.1) or `07-connector-marketplace-design.md`'s own mechanism for a platform-team-authored or marketplace connector. This document invents no third invocation mechanism; it dispatches through whichever one the connector's own trust boundary already provides. §4 below is what this resolver additionally realizes at the point its own outbound call crosses the platform boundary. |

**No dependency on any one connected system.** Because the interface's shape does not vary by origin, and no platform-core module or SDK consumer imports a resolver directly — only the interface — removing, disabling, or replacing one connector or external system leaves every platform primitive, every other tenant's use of the layer, and every other connector unaffected. This is the same "removing a module affects only its own scope" boundary rule `05-integration-and-extensibility-spec.md` §4 already fixes, realized here for the layer that unifies access across however many systems a tenant has connected.

**A call through this interface is one more caller, never a second access path.** Where the caller is an in-grant extension's own host function reaching the layer, that call is governed identically to any other host-function call `06-integration-and-extensibility-design.md` §9 already fixes: it runs inside the connection already scoped to the invocation's own Resolved Request Context, and it carries no privileged, layer-specific path around either resolver's own composed checks. This document adds no exemption for the cross-system case; §6 below states precisely what that composability does, and does not, bound.

## 4. The Five Guarantees, Realized at a Boundary the Platform Does Not Control

C-24 fixes five obligations. Each already has a designed mechanism, and each of those mechanisms works because the platform controls the entire path the mechanism runs. This section states what each becomes for the Connector Resolver's leg specifically — the leg where the path leaves.

### 4.1 Strict Tenant Scoping (INV-01)

`02-tenant-isolation-and-access-control-design.md` §3, §5 makes tenant isolation structural through schema separation and connection-scoped database privilege — an external system has neither a schema boundary the platform can grant or withhold, nor a privilege model the platform administers. The mechanism this document adds does not attempt to make the external system itself schema-isolated, which is outside the platform's reach; it makes the platform's own side of every crossing incapable of mixing two tenants' invocations, exactly as strictly as it already is for a platform-resident one.

- **One external-system credential per tenant, never pooled or shared.** A connector's registration (§5) is scoped to exactly one tenant, and the Connector Resolver resolves its outbound credential from that registration alone — never from a value another tenant's registration supplied, and never from a credential held in common across two tenants' registrations of the same external system. This is the platform-side expression of tenant scoping at a boundary where the platform cannot grant or revoke a schema privilege on the far side of the connection.
- **The resolver accepts no caller-supplied tenant or application identifier as an alternative to the Resolved Request Context.** Exactly the discipline `06-integration-and-extensibility-design.md` §5.4's tenant-confinement row already fixes for every other caller, drawn from the same Resolved Request Context `02-tenant-isolation-and-access-control-design.md` §4.1 establishes: a Connector Resolver call is parameterized only by the frozen Resolved Request Context already established for the invocation, never by an identifier a guest, an extension, or built software could supply independently.
- **No resolver acquires its own connection.** The connection or outbound credential resolution the Connector Resolver performs runs inside the connection already scoped to the invocation's own Resolved Request Context (`02-tenant-isolation-and-access-control-design.md` §5.1) — exactly the discipline `06-integration-and-extensibility-design.md` §9 already fixes for a host function, extended here to a resolver reaching outside the platform rather than inside it.
- **The sharp edge, stated plainly.** The platform can guarantee, structurally, that it never presents tenant A's credential or context on tenant B's request. It cannot guarantee, and this document does not claim, that the external system's own handling of that credential is itself correctly isolated on its own side — that determination belongs entirely to a system this design does not reach. This asymmetry is the concrete form of the ticket's own framing: the mechanism is structural on the platform's side of the crossing and unverifiable on the far side of it, and this document states that line rather than obscuring it behind a guarantee it cannot make.

### 4.2 Credentials Never Exposed (INV-03)

`04-security-controls-design.md` §2 scans and redacts; §7.2–§7.3 govern key custody for the platform's own key hierarchy. An external-system credential is a new class of held secret for one structural reason none of the platform's own key material shares: every other secret this design library protects is used entirely inside the platform's own process boundary, while an external-system credential is, by definition, used by presenting it — in its unwrapped, native form — to a system the platform does not control.

- **Custody at rest follows the existing hierarchy, without a carve-out.** An external-system credential is stored using the identical `tenant_key`/`application_key` wrapping hierarchy `02-platform-data-model-design.md` §8 already fixes, at whichever level the registration (§5) is scoped to. No second key-material scheme is introduced for this class of secret.
- **Custody in use follows the existing least-privilege and transient-unwrap discipline.** The credential is unwrapped only at the point the Connector Resolver is about to make its outbound call, exists unwrapped only transiently in memory exactly as `04-security-controls-design.md` §7.2 already fixes for any other key material, and is never itself logged — only its access event is (§7.3 of that document; §7 below).
- **The credential never reaches the caller that requested the access.** Where the caller is an in-grant extension's host function, resolution and outbound authentication happen entirely inside the Connector Resolver — host-side, never surfaced to the guest — exactly the discipline `06-integration-and-extensibility-design.md` §5.4's secret-confinement row already fixes for a host function reaching an external system on an extension's behalf. This document extends that discipline to every caller of the layer, not only the extension case.
- **The one boundary-crossing point secret confinement cannot fully close, stated honestly.** Every other secret in this design library is protected because the platform controls both ends of every path the secret ever travels. An external-system credential's very purpose requires the platform to transmit it, in usable form, to a system it does not control — the moment of use is a deliberate crossing, not a leak. What this document's mechanism guarantees is narrower and stated precisely: the credential is never exposed anywhere *other than* that one authorized crossing — never in a log, an error, a response, another tenant's context, or a guest's own reach — and the crossing itself occurs only over a connection protected in transit, consistent with the transit-protection discipline this platform already applies at every boundary its own infrastructure terminates. This is the platform's guarantee about its own side of the crossing; it is not, and cannot be, a guarantee about what the external system subsequently does with a credential it was authorized to receive.

### 4.3 External Data as Untrusted Input, Validated at the Boundary

`04-security-controls-design.md` §3.1 validates the platform's own request-handling surface against a contract-derived schema; `02-data-model-and-entity-design.md` §4.2's Validation Engine validates a candidate instance against a builder-defined entity's own `field_catalog`. A value returned by an external system, reached through an arbitrary third-party shape, conforms to neither mechanism's own precondition by default — there is no OpenAPI-derived schema for a connector's own upstream API, and no `field_catalog` row exists until the value is written into one.

This document introduces no third validation mechanism. It fixes the point at which each existing one runs, for a value entering through the Connector Resolver specifically:

- **Where the caller intends to write the retrieved value into a builder-defined entity**, the value passes through the ordinary Entity Access Gateway write path (§3.2 above) exactly as any other candidate write does — the Validation Engine inspects it against that entity's own `field_catalog` constraints (`02-data-model-and-entity-design.md` §4.2). External origin is not a reason to relax that inspection; it is exactly the reason it must run, and it runs unconditionally, with no origin-based exception anywhere in the Gateway's own mediation.
- **Where the caller consumes the value directly, not as a write into a builder-defined entity**, the Unified Access Interface's own boundary validates the value against a contract-derived schema for that specific operation, before returning it to the caller — the identical mechanism `04-security-controls-design.md` §3.1 already applies to the platform's own request-handling surface, extended here to the layer's inbound boundary from an external system rather than duplicated by a second validator.
- **A value that cannot be established as conforming is refused, not passed through.** The same deny-by-default rule `02-governance-and-security/02-security-policy.md` §5 already fixes: uncertainty about a value's conformance resolves to refusal at this boundary exactly as it does at the platform's own request boundary.
- **Injection prevention holds by the same construction it already does.** Where an external value is later used to compose a platform-side query, it crosses the query-layer boundary as a bound parameter, never as interpolated content (`04-security-controls-design.md` §3.2) — its external origin changes nothing about a mechanism that was never conditional on where a value came from.

### 4.4 Residency and Jurisdictional Obligations Honored

`06-compliance-and-data-residency-design.md` §3.4's Region Boundary Check evaluates every read, write, and transfer against the Resolved Residency Obligation, requiring both regions' permission for a cross-region transfer and applying a classification-tier exclusion independent of either (§5, §7 of that document). Every one of those mechanisms presupposes a resolvable region-of-record on both ends. An external system may have no resolvable region-of-record at all — no `platform.regions`-catalog entry, and no attribute the platform's own registry can read, because the system is not one the platform administers.

This document does not invent a third resolution path for this case. It applies the same deny-by-default discipline `06-compliance-and-data-residency-design.md` §5 already states for exactly this shape of gap — an unresolvable value resolves to the *more* restrictive outcome, never the more permissive one — to a region-of-record specifically:

- **A connector's registration (§5) may carry a declared region-of-record**, an explicit, tenant-supplied attribute on the connection record, referencing the same `platform.regions` catalog `platform.tenants.region_of_record` and `platform.applications.region_of_record` already reference (`02-platform-data-model-design.md` §3.1, §7) — never a second catalog, and read by whichever resolution mechanism already resolves those two columns for the Resolved Residency Obligation (`06-compliance-and-data-residency-design.md` §3.3), folded into that same union exactly as a tenant's or application's own region-of-record already is.
- **Where no declared region-of-record exists for the connection, this resolves to refusal, not to a permissive default.** `06-compliance-and-data-residency-design.md` §5's own rule for an unclassifiable tier — "an unclassifiable or unrecorded tier resolves to the most restrictive tier, not the least" — is, by that document's own statement, the concrete form of the specification's deny-by-default posture applied to residency generally; this document applies the identical posture to an unresolvable region-of-record. A tenant does not gain a residency-free path by connecting to a system that carries no declared region; the absence is treated as an obligation that cannot be established, and the Region Boundary Check refuses the action on that basis, before the Connector Resolver's outbound call is ever made.
- **An outbound call is the transfer case, evaluated exactly as any other.** Sending data to, or receiving it from, an external system through this layer is a transfer within the meaning of `06-compliance-and-data-residency-design.md` §3.4 and §7 — both the originating region's obligation and the (declared or refused-as-unresolvable) receiving region's obligation are evaluated before the transfer proceeds, and the classification tier of the data being moved (§4.5 below) independently governs whether the tier itself excludes the transfer regardless of either region's own permission. This document adds no second transfer rule; the Connector Resolver's outbound leg is simply one more case the existing Region Boundary Check already covers.

### 4.5 The Classification Tier and Data-Governance Category Travel With Data

`07-data-governance-and-privacy-design.md` §3.1 and `06-compliance-and-data-residency-design.md` §5 fix that the classification tier and data-governance category are intrinsic, traveling properties of a data element, read at the point the Resolved Residency Obligation and the Resolved Handling Obligation are resolved. Neither mechanism was evaluated against a value that has never yet passed through either resolution — which is exactly what a value freshly retrieved from an external system is.

**What happens to the property when data crosses out.** A value already resolved inside the platform — a builder-defined field's own `field_catalog.classification_tier` and `data_governance_category` (`02-data-model-and-entity-design.md` §3.2) — carries both properties with it when the Connector Resolver sends it outward. The outbound call is, for the Region Boundary Check's purposes, the transfer case of §4.4 above; for the Resolved Handling Obligation's purposes, it is a "use" under the governance category's own handling matrix (`07-data-governance-and-privacy-design.md` §3.2). Both checks evaluate before the outbound call is issued, at the identical checkpoints already fixed for any other transfer or use — this document opens no second checkpoint for the cross-system case, and neither property is stripped, summarized, or forgotten at the point the value leaves the platform's own schema boundary.

**What tier and category data crossing in carries.** A value read from an external system carries no platform-resolved tier or category at the moment the Connector Resolver receives it — it has not yet been written into any `field_catalog`-governed structure, and no builder configuration has yet classified it. This document applies no new deny-by-default rule for this case; it applies the one both documents already fix for exactly this gap:

- **Until the value is committed to a builder-defined field whose own `field_catalog` row already carries a configured tier and category, the value is treated at the more restrictive end of both scales** — Regime-Governed under `06-compliance-and-data-residency-design.md` §5's "an unclassifiable or unrecorded tier resolves to the most restrictive tier, not the least," and sensitive personal data under `07-data-governance-and-privacy-design.md` §3.1's identical rule for category. This governs any residency or handling evaluation that must run on the value before, or independent of, a committing write — including the read-through, direct-consumption case of §4.3 above, where a value may be returned to a caller without ever being written into a `field_catalog`-governed structure at all.
- **Once written into a builder-defined field, the field's own already-configured tier and category govern**, exactly as they would for a value originating anywhere else — the external origin does not permit the field's own configuration to be bypassed, narrowed, or treated as inapplicable, and it does not override a builder's own more-restrictive configuration with anything less restrictive. Where the destination field itself carries no configured tier or category, the same most-restrictive default above governs until the field is explicitly classified.

This is not a second classification scheme. It is the existing traveling-property mechanism, applied at the one new point of entry this document introduces — a value crossing in from a system the platform's own classification-resolution mechanism has never seen before.

## 5. Where External-System Connection and Credential State Lives

This document's mechanism requires a registration record per connector instance a tenant connects: which external system, which connector governs the connection, which credential reference (§4.2) authenticates it, and — where supplied — the declared region-of-record (§4.4). This document states the constraint that record must satisfy and its destination; it does not define the table, following the same discipline `06-integration-and-extensibility-design.md` §8 and `04-workflow-and-process-automation-design.md` §4.1 each already apply when constraining without owning, and avoiding the schema-ownership gap `BACKLOG.md` §1i already records the cost of.

- **This is not `tenant_host_connections`, and the two are already distinguished on record.** `02-platform-data-model-design.md` §7 already states plainly that host-provider connectivity "concerns where the platform's own infrastructure — not a builder's external integrations, which `07-cross-system-data-layer-design.md` owns — physically runs." `tenant_<id>.tenant_host_connections` records the platform's own infrastructure placement; the structure this document requires records a tenant's own connections to systems the platform does not operate. Neither this document nor that one duplicates the other's structure by reusing its table.
- **What is missing, and where it must fit.** A connection record is tenant-scoped access-and-credential configuration, not builder-defined content — the same class of artifact `tenant_<id>.tenant_host_connections` and `tenant_<id>.administrative_scope_grants` already are (`02-platform-data-model-design.md` §3.2). It belongs in the **per-tenant schema** (`tenant_<id>`), never in `platform`, because a connection is bound to one tenant and never spans tenants, and never inside a per-application schema, because it is a tenant-level access-and-credential fact, not a builder-defined entity — the identical reasoning `06-integration-and-extensibility-design.md` §8 already applies to extension registration, extended here to a sibling but distinct structure.
- **This document does not add the table.** Naming the concrete columns is `02-platform-data-model-design.md`'s to do, exactly as that document's own §7 and §12 already anticipate for structures this layer requires without itself owning; this document states the constraint (tenant-scoped, credential-reference-bearing, declared-region-of-record-carrying, connector-identifying) and the destination, so the obligation is claimed rather than left with no assigned home a second time.
- **The Connector Resolver reads this record at resolution time** through the same privileged, identity-scoped resolution-phase access `02-tenant-isolation-and-access-control-design.md` §4.1's Context Resolution Point already uses to read `tenant_user_application_scope` and `administrative_scope_grants` — never a second, specially-acquired connection for this purpose, and never a connection this document defines independently of the one already scoped to the invoking request.

## 6. The Honest Limit: What This Layer Prevents, Detects, and Cannot Bound

`06-integration-and-extensibility-design.md` §5.5 states that capability confinement bounds *reach*, not *intent within a granted reach*, and names this document's own cross-system data layer as the vector by which an in-grant extension could compose two legitimate capabilities undesirably — reading data it is authorized to read, and sending it somewhere its own grant otherwise permits. That residual is now partly this document's own to state precisely, not to claim it closes.

**What this layer prevents structurally.** Every mechanism §4 composes with is a hard stop, not a policy an actor is trusted to honor: a credential resolved for one tenant's registration is structurally unreachable from another tenant's invocation (§4.1); a credential never reaches a caller's own memory or output (§4.2); a value that cannot be established as conforming does not proceed past the Gateway's Validation Engine or the boundary's own contract-derived check (§4.3); an action whose residency obligation cannot be established is refused before the outbound call is made, never permitted on an assumed default (§4.4); a value with no resolved classification is treated at the most restrictive tier and category until it is explicitly classified, never treated as unclassified in a way that would skip an obligation (§4.5). Each of these is verifiable by inspecting the resolver's own code path, not inferred from the absence of an observed breach.

**What this layer can only detect, never structurally prevent.** Whether the *external system's own* handling of a credential, a request, or a returned value is itself correct is outside this design's reach by definition — the platform does not administer that system's schema, privilege model, or logging. This document's mechanism produces evidence of every crossing on the platform's own side (§7), which supports detecting an anomaly after the fact through the audit trail; it does not, and cannot, verify in advance that the far side of a connection behaves as its own documentation claims. This is not a gap this document failed to close — it is the honest boundary the ticket's own framing names: the mechanism this platform builds works because it controls the path, and the moment the path leaves, "verified" degrades to "evidenced," never further.

**What no isolation, validation, or residency mechanism at any strength can bound at all.** An in-grant extension holding a legitimate grant to read one entity through the Entity Access Gateway resolver, and a separate, legitimate registered connection through the Connector Resolver, can compose the two — reading data it is authorized to read and sending it to a system its own grant otherwise permits reaching — without any single check in §4 above being violated, because no dimension was exceeded: the tenant scoping held, the credential never leaked, the outbound value passed whatever validation applied to it, and the residency and classification obligations were satisfied for the specific transfer performed. This is a data-flow and intent risk, not a confinement failure, and it is not a new residual this document discovers — it is the exact vector `06-integration-and-extensibility-design.md` §5.5 already named this layer as, closed no further here than it was closed there: the only available mitigation is how narrowly a tenant scopes the grant and the connection it registers at the point both are created (§5 above; `02-governance-and-security/03-access-control-and-tenancy-model.md` §5's "grants never exceed the grantor"), never a mechanism this document's own gateway or resolver is positioned to add. This document does not re-open the isolation-strength question `06-integration-and-extensibility-design.md` §5 already answered for the Extender origin; it states, as that document's §5.5 anticipated, what its own share of the same open question looks like from the cross-system-layer side rather than leaving the connection unstated.

## 8. Design Decision Records

### ADR-034 — Unified Access Model for the Cross-System Data Layer: One Interface, Two Resolvers, Five Guarantees Composed at the Boundary

- **Status:** Provisional — Pending Lead Approval.
- **Cost to reverse:** **High** (`PROCESS.md` §12.1). Every connector registered under this mechanism, and every built-application or extension caller reaching data through it, is written against the Unified Access Interface's fixed call shape and the two-resolver dispatch behind it; reversing the interface shape or the resolver split requires every registered connection and every consumer of the layer to be re-registered or re-implemented against the new shape. Not Brutal or Very High: this decision touches no platform-primitive schema and no builder-defined entity data model — `02-data-model-and-entity-design.md`'s own structures are unaffected; only how a value is validated, scoped, and classified in transit through this layer changes, bounding this decision's blast radius to the access-layer mechanism itself, not to the data model or the sync posture beneath it.
- **Upstream decisions assumed:** `05-integration-and-extensibility-spec.md` §8.4 (C-24's own status as an Extension-family surface) and `03-architecture-realization-design.md` §4.1 row 4 (the dependency-direction rule this decision's single published interface is built to satisfy, never weaken); `02-tenant-isolation-and-access-control-design.md` §3, §5 (the connection-scoping mechanism, and the Resolved Request Context it operates on, every resolver call consumes, never duplicates); `04-security-controls-design.md` §2, §3.1–§3.2, §7.2–§7.3 (secrets scanning and redaction, request-boundary validation, and key custody, each extended here to a new secret class and a new point of untrusted entry, never redesigned); `06-compliance-and-data-residency-design.md` §3.3–§3.4, §5, §7 (the Region Boundary Check and Resolved Residency Obligation this decision's declared-region-of-record extension folds into, never replaces); `07-data-governance-and-privacy-design.md` §3 (the traveling classification property and its most-restrictive-default rule, extended to this layer's own inbound-external point of entry); `02-data-model-and-entity-design.md` §3.2–§3.3, §4.1–§4.2 (the entity catalog, and the Entity Access Gateway and Validation Engine the platform-resident resolver reuses in full); `02-platform-data-model-design.md` §3, §7 (the schema hierarchy this decision's connection-and-credential record is constrained against, and the explicit prior statement, already on record there, that a builder's external integrations are this document's concern); and `06-integration-and-extensibility-design.md` §5, §8, §9 (the trust mechanism a Connector Resolver composes with wherever the resolved connector is itself an Extender-authored extension, and the intent-composition residual this decision inherits a named share of, never closes further). None of the Provisional upstream ADRs this decision depends on for content — ADR-023 (region scoping) and ADR-033 (the Extender-origin trust mechanism a Connector Resolver may dispatch through) — are assumed approved; this decision depends on their already-designed content, never on their approval status (`PROCESS.md` §12.2).
- **Verified vs. reasoned:** Entirely reasoned. No claim in this decision is time-sensitive; every element composes with an already-cited mechanism's own structural properties or the cited specification's own requirements.
- **Context:** C-24 fixes five obligations against a platform-resident data model whose own guarantees are structural because the platform controls the entire path. Every one of the five already has a designed mechanism elsewhere in this library, and every one of those mechanisms was designed, and evaluated, against a path the platform administers end to end. No document yet states what a unified access surface looks like, or what any of the five obligations becomes, at the one boundary this platform does not control — an external system.
- **The question this ADR answers, phrased for reuse:** Given a set of guarantees that are structural because the platform controls the path enforcing them, and given a capability whose entire purpose is to extend that path to a system the platform does not control, what interface presents both sides as one coherent surface without the platform core depending on any one connected system, and what does each guarantee become at the exact point the path it protects leaves the platform's own reach?
- **Criteria applied, and how each resolved:**

  | # | Criterion | How It Resolved |
  |---|---|---|
  | 1 | Can each of the five guarantees be realized at the boundary by extending its own existing mechanism, or does the external leg require an independently invented mechanism per guarantee? | **Decisive for extension, in every case** (§4) — tenant scoping extends via per-tenant credential isolation on the platform's own side; secret custody extends via the existing key hierarchy plus a stated, honest limit at the point of necessary transmission; validation extends via the existing Gateway and request-boundary mechanisms; residency extends via a declared region-of-record folded into the existing Resolved Residency Obligation, defaulting to refusal when absent; classification extends via the existing traveling-property mechanism's own most-restrictive-default rule, applied at one new point of entry. No guarantee required a competing, independently invented mechanism. |
  | 2 | Must a caller of the unified layer know whether a given resource is platform-resident or external in order to reach it correctly? | **No, decisively** — a single interface shape dispatching to one of two resolvers keeps origin-specific behavior confined entirely inside the resolver, never leaked into the caller's own contract, satisfying the "one coherent layer" requirement without a caller-visible branch. |
  | 3 | Where exactly does a structural, verifiable guarantee end and an unverifiable trust in a third party's own behavior begin? | **Decisive for the honest-limit statement (§6)** — the platform's own side of every crossing is structural and verifiable by inspecting the resolver's own code path; the external system's own handling of what it receives is, by definition, outside this design's reach, and this decision states that line rather than implying a guarantee the mechanism cannot make. |
  | 4 | Is external-system connection and credential state owned here, or constrained against the schema hierarchy another document owns? | **Decisive for constraining, not owning** (§5) — following `06-integration-and-extensibility-design.md` §8's and `04-workflow-and-process-automation-design.md` §4.1's precedent, and honoring `02-platform-data-model-design.md` §7's own prior statement that this document, not that one, owns a builder's external integrations. |
- **Decision:** (1) The cross-system data layer publishes exactly one **Unified Access Interface** from `components/extension`, reached by any caller through the identical call shape regardless of what is behind it (§3.2). (2) Exactly two resolvers implement that shape: an Entity Access Gateway resolver for platform-resident data, reusing that Gateway's own mediation in full, and a Connector Resolver for external-system data, dispatching through whichever invocation and trust mechanism already governs the resolved connector's own origin (§3.2). (3) Each of C-24's five guarantees is realized, for the Connector Resolver's own leg, as an extension of its existing platform mechanism at the exact point the path leaves the platform: tenant-scoped, never-pooled credential resolution (§4.1); host-side, transient credential custody with an honestly stated limit at the point of necessary transmission (§4.2); mandatory validation through the existing Gateway or request-boundary mechanism before a value is trusted (§4.3); a declared region-of-record folded into the existing Resolved Residency Obligation, defaulting to refusal when unresolved (§4.4); and the existing traveling-classification mechanism's own most-restrictive default, applied to a value entering with no platform-resolved classification (§4.5). (4) Connection and credential state is constrained to the per-tenant schema `02-platform-data-model-design.md` owns, distinct from `tenant_host_connections`, without this document defining the table (§5). (5) The intent-composition residual `06-integration-and-extensibility-design.md` §5.5 already named this layer as the vector for is stated as this document's own inherited share of that same open question, closed no further here than it was there (§6).
- **Alternatives considered:** *A bespoke, per-connector-type isolation, validation, and residency mechanism, invented fresh for each new external-system category* — rejected under criterion 1; this would multiply mechanisms exactly where the design library's own discipline is to compose with what already exists, and would leave five separately-maintained boundary treatments where one composition suffices. *Trusting the external system's own claimed multi-tenancy or access control as the isolation boundary, rather than scoping the platform's own credential per tenant* — rejected under criterion 3; this is the "assumed, not verified" posture `02-tenant-isolation-and-access-control-design.md` §5.1 already rejects for the platform's own predicate-based alternative, and this decision does not adopt for a third party what this design library already refused for itself. *Treating an unresolvable external region-of-record as a permissive default, proceeding unless a rule is later found to forbid it* — rejected under criterion 3 and the deny-by-default convention `06-compliance-and-data-residency-design.md` §5 already fixes for exactly this shape of gap. *Defining the connection-and-credential table inside this document* — rejected under criterion 4, for the same schema-ownership reason `06-integration-and-extensibility-design.md` §8 already states and `BACKLOG.md` §1i already records the cost of ignoring.
- **Consequences:** Binds `07-connector-marketplace-design.md` (not yet written) to treat every connector it admits and distributes as a Connector Resolver implementation reached exclusively through this document's Unified Access Interface, never a second access path a marketplace-obtained connector could open independently. Binds `02-platform-data-model-design.md` to add the per-tenant connection-and-credential table this document constrains but does not define (§5), on a future, separately-ticketed amendment, distinct in content from `tenant_host_connections`. Adds no obligation to, and does not extend, `02-tenant-isolation-and-access-control-design.md`'s connection-scoping mechanism, `04-security-controls-design.md`'s secrets or validation mechanisms, `06-compliance-and-data-residency-design.md`'s Region Boundary Check, `07-data-governance-and-privacy-design.md`'s handling matrix, or `02-data-model-and-entity-design.md`'s Entity Access Gateway — each is consumed exactly as already designed, extended only at the one new point of entry or exit this document's own boundary introduces.

## 11. Binding Rules

- **The cross-system data layer presents exactly one Unified Access Interface, published from `components/extension`.** No platform-core module or SDK consumer imports a resolver directly; every caller reaches the layer through the identical call shape regardless of what is behind it (§3.2).
- **A caller never distinguishes platform-resident from external data by the layer's own contract.** Origin-specific behavior is confined entirely inside whichever resolver answers a given call; the interface's own shape does not vary by origin (§3.2).
- **Every one of C-24's five guarantees is realized at the cross-system boundary as an extension of its own existing mechanism, never a second, competing one.** Tenant scoping, secret custody, boundary validation, residency, and classification each compose with the mechanism the document owning it already designed (§4).
- **An unresolvable region-of-record for an external connection resolves to refusal, never to a permissive default.** The same deny-by-default discipline `06-compliance-and-data-residency-design.md` §5 already fixes for an unclassifiable tier governs this case exactly as it governs any other unresolvable value (§4.4).
- **A value entering from an external system with no platform-resolved classification is treated at the most restrictive tier and category until it is explicitly classified.** No value bypasses a residency or handling obligation by virtue of arriving unclassified (§4.5).
- **An external-system credential never reaches a caller of the layer, and is transmitted only over the one authorized, TLS-protected crossing its own use requires.** Every other exposure path is closed exactly as for any other secret this design library protects (§4.2).
- **Connection and credential state is constrained to the per-tenant schema, distinct from `tenant_host_connections`, never defined by this document.** This document states the constraint; `02-platform-data-model-design.md` owns the table (§5).
- **Capability confinement bounds reach, never intent within a granted reach, and this document closes that residual no further than `06-integration-and-extensibility-design.md` §5.5 already did.** An in-grant extension composing a legitimate read with a legitimate registered connection is a data-flow and intent risk this layer's own mechanisms cannot bound by definition, mitigated only by narrow grant-and-connection scoping at registration (§6).
- **This document neither absorbs nor replaces C-05, C-11, or C-12.** A builder's own entity modeling and the module and programmatic-contract extension mechanisms remain distinct surfaces this document unifies access over, never redefines (§2).
- **Everything remains domain-neutral and platform-level.** No resolver, boundary rule, or composed mechanism in this document encodes the characteristics of any single domain or any single external system; all remain valid for any connector, any tenant, and any region.
- **This document records exactly one ADR.** ADR-034 (§8) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, boundary, or invariant the cited specification and cited upstream design documents already fix.
