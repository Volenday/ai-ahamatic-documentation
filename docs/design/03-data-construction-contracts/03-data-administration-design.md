# Data Administration Design — AI ahaMatic

## 1. Purpose and Reading Order

This document realizes `01-business-and-ux/03-platform-capability-model.md`'s data-administration row (C-27) as concrete mechanism: the generic create/read/update/delete interface over records that follows automatically from an entity definition, with no application configured and no further authoring step. It answers **how** — what the derivation reads, what it produces, and how every operation the derived interface exposes reaches the one mediation point `02-data-model-and-entity-design.md` already fixes for every read and write of builder-defined entity data.

It is the third document of the Data, Construction & Contracts layer, depending directly on `01-application-construction-design.md` (H19) and `02-data-model-and-entity-design.md` (H20). It additionally depends on `02-platform-data-model-design.md`, added as a dependency by the `BACKLOG.md` §1i amendment: that document defines the physical table (`tenant_<id>.administrative_scope_grants`, its own §3.2) this document's administrative-scope grant (§5.3) cites rather than defines. It also makes the explicit determination `BACKLOG.md` §1h names as owed here: whether, and how, record-scoped access — which records a role may reach through this interface — is this document's to design.

It is structured as a pyramid: first the derivation mechanism itself, what it reads and what it produces (§3); then how every operation the derived interface exposes runs through the Entity Access Gateway and nowhere else (§4); then the record-scoped-access determination (§5); then the three boundaries that keep this capability distinct from its nearest neighbors, stated bidirectionally (§6); then the empty state the specification protects (§7); then the evidence this mechanism produces (§8); then the design decision this document records (§9); then its boundaries, precedence, and binding rules (§10–§12).

**Verified versus reasoned (`PROCESS.md` §12.3).** Every finding in this document is **reasoned** — from the cited specification and the cited, already-written upstream design documents. No time-sensitive ecosystem, product, or vendor claim is made anywhere in this document.

## 2. Scope and What This Document Does Not Own

This document owns: the derivation mechanism that produces a create/read/update/delete interface over a builder-defined entity's records directly from that entity's own catalog definitions, with no further authoring step (§3); the discipline that every operation the derived interface exposes is dispatched into the Entity Access Gateway `02-data-model-and-entity-design.md` §4.1 already fixes, never a second access path (§4); the record-scoped-access determination §1h names, including the mechanism that discharges it for the professional-builder actors this interface serves (§5); and the three bidirectional boundaries against C-05, C-06, and C-07 that keep this capability distinct from its nearest neighbors (§6).

This document does **not** own, and does not decide:

- **The shape of builder-defined data — entities, schemas, fields, relationships, their validation, referential-integrity, and migration-safety rules (C-05).** `02-data-model-and-entity-design.md` owns all of it in full. This document consumes the four catalogs that document already fixes; it adds no column, no catalog, and no validation rule to any of them.
- **The Entity Access Gateway itself — the Validation Engine, the Consent and Minimization Check, and classification-tier/data-governance-category resolution, and their fixed order.** `02-data-model-and-entity-design.md` §4.1 owns the Gateway in full; this document is a caller of it, never a second implementation of any check it already performs.
- **The construction action, the configuration model, or the closed construct/binding-kind vocabulary (C-04, C-06).** `01-application-construction-design.md` owns all three in full. This document presumes no application has been configured through that model, and excludes build-surface content from its own derivation (§3.3) rather than redesigning what a construct or a binding is.
- **Running, operating, or observing a constructed and configured application for its own end users (C-07, C-08, C-09).** The Operation family's own layer owns the built application's runtime; this document's mechanism never renders, serves, or substitutes for a built application's own end-user surface.
- **Process and workflow modeling (C-18), AI-assisted builder tooling (C-19), the platform's own published programmatic contract (C-12, `05-api-contract-design.md`), or the cross-system data layer (C-24).** Each is a distinct document's concern, built on `02-data-model-and-entity-design.md` and `01-application-construction-design.md` exactly as this document is; none is designed here.
- **Authentication, session mechanics, or tenant- and application-context resolution.** `03-authentication-and-identity-design.md` and `02-tenant-isolation-and-access-control-design.md` own both in full; every action this document designs runs inside the identity and connection those documents already establish and never establishes a second identity or scoping mechanism.
- **The physical table realizing the administrative-scope grant.** `02-platform-data-model-design.md` §3.2 owns it, added there by the `BACKLOG.md` §1i amendment, because it is platform-owned, tenant-level access-scoping configuration — the same kind of structure as `tenant_user_application_scope` — not a builder-defined entity inside a per-application schema. This document fixes the grant's semantics, its columns' meaning, and the Administrative Authorization Check that reads it (§5); it does not define, or restate the definition of, the table itself.
- **Audit-event record shape, storage, or tamper-evidence.** `08-audit-and-traceability-design.md` owns all of it; this document's evidence (§8) populates that record and never redesigns it.
- **Any independent technology, topology, or scope decision beyond the one named in §9.** This document records exactly one ADR.

## 3. The Derivation Mechanism

### 3.1 What It Reads

`02-data-model-and-entity-design.md` §3.2 fixes four catalogs as the complete, physical representation of an entity's definition: `entity_catalog` (the entity itself), `schema_version_catalog` (its current version marker), `field_catalog` (its structure, constraints, and identity elements, together with the classification tier and data-governance category every field already carries), and `relationship_catalog` (how it relates to another entity, and what referential integrity that relationship requires). A schema governs no data until every row these four catalogs require exists for it (`02-data-model-and-entity-design.md` §3.2's own completeness rule).

The derivation mechanism this document fixes — the **Derivation Function** — reads exactly these four catalogs, resolved to one entity's `current_schema_version_id`, and nothing else. It reads no builder-supplied configuration, no construct, and no binding: an entity that satisfies §3.2's completeness rule is, by that fact alone, sufficient input to the Derivation Function. This is the concrete mechanism that realizes "a new entity yields an administrative interface with no further authoring step" — there is no intermediate authoring action a builder performs between an entity becoming complete and that entity's administrative interface becoming usable, because the Derivation Function's only input is the catalog state the completeness rule already requires to exist.

### 3.2 What It Produces, and Why

The Derivation Function produces an **Interface Description** — a data structure, computed fresh on every invocation, that states: the entity's fields, each carrying its `name`, `type`, `constraint_definition`, `identity_role`, `classification_tier`, and `data_governance_category` exactly as `field_catalog` records them; and the entity's relationships, each carrying its target entity, cardinality, and `on_change_behavior` exactly as `relationship_catalog` records them. This is the minimum content a caller — whatever component ultimately presents the interface to the builder — needs to offer create, read, update, and delete operations over the entity's records and to navigate a relationship to another entity's own administrative interface.

**This document produces an Interface Description consumed at runtime, never a generated, stored artifact.** The choice is deliberate, not a default:

- **A stored artifact would need regeneration on every schema evolution, and nothing in this design regenerates one.** `02-data-model-and-entity-design.md` §7 fixes that a schema evolves by a new `schema_version_catalog` row, evaluated for backward compatibility at the moment it is proposed; an entity's `current_schema_version_id` can change at any time, independent of any action this document's own mechanism takes. A materialized interface artifact would either go stale the moment a schema evolves, or require a second, dedicated mechanism to detect the evolution and regenerate the artifact — exactly the synchronization machinery `02-data-model-and-entity-design.md` §8.1 already excludes from its own storage shape ("this is not synchronization machinery"), reintroduced here for no reason this document has evidence to justify.
- **A runtime-computed description cannot drift from what it describes, because it has no separate state to drift from.** Reading `entity_catalog`, `schema_version_catalog`, `field_catalog`, and `relationship_catalog` afresh on every invocation and rendering the caller's Interface Description from that read is a stronger correctness guarantee than any cache-invalidation or regeneration discipline could offer over a stored alternative, and it costs nothing in additional storage or additional mechanism — the Derivation Function is a read, not a write.
- **No new construct, binding, or code artifact is generated.** The Derivation Function's output is presentation-agnostic data — the fields and relationships a caller needs, not a rendered form, a generated code module, or a stored schema of its own. It is consumed by whatever component ultimately presents the administrative interface to a builder; this document does not design that component's rendering technology, layout, or user experience, only the data it is derived from.

### 3.3 Exclusion of Build-Surface Content

`02-data-model-and-entity-design.md` §3.3 fixes that a **construct** — build-surface content belonging to `01-application-construction-design.md`'s configuration model — is represented through the identical entity/schema mechanism this document's own input relies on: an `entity_catalog` row flagged as build-surface content, with its `kind` drawn from the closed construct-kind vocabulary (`01-application-construction-design.md` §4.2.2). The Derivation Function excludes every `entity_catalog` row so flagged. This is not a filter added to work around an edge case; it is the concrete instantiation of this document's own boundary against C-06 (§6.2): the entities this document derives an administrative interface from are entities in C-05's sense — a builder's own modeled data — never a construct a builder has configured through the build surface. A construct's own administrative surface, where one is ever needed, is `01-application-construction-design.md`'s and `03-data-administration-design.md`'s to design jointly if and when a ticket assigns that question; it is not designed here, and no accommodation for it is added to the Derivation Function.

## 4. Record Operations Through the Entity Access Gateway

### 4.1 No Second Access Path

`02-data-model-and-entity-design.md` §4.1 fixes the Entity Access Gateway as "the sole path through which any component reads or writes a builder-defined entity's catalog rows or instance data," running the Validation Engine, the Consent and Minimization Check, and classification-tier/data-governance-category resolution, in fixed order, as a single chokepoint no caller bypasses. This document's interface is a **caller** of that Gateway, on exactly the same terms as any other component that reads or writes a builder-defined entity's records. It designs no second Gateway, no parallel validation step, and no code path through which a record operation this interface exposes could reach an entity's catalog rows or instance data without passing through the Gateway `02-data-model-and-entity-design.md` already fixes.

**"Administrative" confers no exemption.** Every create, read, update, or delete operation this interface performs is subject to the identical Validation Engine inspection, the identical Consent and Minimization Check, and the identical classification-tier and data-governance-category resolution that governs any other write or read of the same entity's data, from any other caller. There is no reduced check, no bypass, and no privileged code path reserved for this interface's own operations — the same discipline `02-tenant-isolation-and-access-control-design.md` §3.2 already states for a platform steward role's registry-wide visibility ("the steward governs the boundary without entering it") applies here in the opposite direction: this interface's builder-facing, administrative character governs nothing about the *data* it touches, and enters that data on exactly the same terms as any other caller of the Gateway.

### 4.2 The Four Operations, Mapped to the Gateway's Existing Vocabulary

`02-data-model-and-entity-design.md` fixes exactly two record-level operations at the Gateway: a read of an entity's current instance, and a write — either an instance write conforming to the entity's `current_schema_version_id` (§4.2), or a write that supersedes or marks an existing instance not-current, resolved or refused under the target relationship's own `on_change_behavior` where another committed instance depends on it (§5). This document's four administrative operations map onto that existing vocabulary without adding a third:

| C-27 Operation | Gateway Operation It Dispatches | Notes |
|---|---|---|
| Create | An instance write with no prior `record_id` — the first version of a new logical record. | Subject to the Validation Engine's full inspection (validity, consistency, referential correctness) before it proceeds. |
| Read | A read of the entity's current instance(s), by `record_id`. | The administrative interface's default read is the current version; the full version history `02-data-model-and-entity-design.md` §8.1 guarantees remains queryable through that document's own mechanism, unaltered here. |
| Update | An instance write sharing the prior row's `record_id` — a new version, per §8.1's supersession discipline. | Identical Validation Engine inspection to Create; no distinct check exists for "this is an update" versus "this is a new record." |
| Delete | A write that marks the current instance not-current, resolved or refused exactly as `02-data-model-and-entity-design.md` §5 already fixes for any write that would cause a dependent instance to lose what it references. | This document invents no tombstone column, no second deletion mechanism, and no exemption from the dependency-resolution rule §5 already states; a delete a dependent reference cannot resolve is refused, not silently permitted. |

No operation this interface exposes is a write shape the Gateway does not already accept. This document adds no new instance-write variant, no new read shape, and no code path around the Validation Engine, the Consent and Minimization Check, or classification resolution for any of the four.

### 4.3 What Runs Before the Gateway, and Why It Is Not a Second Gateway

An operation reaches the Gateway only after the actor invoking it has already passed the Authentication Gate and the Context Resolution Point (`03-authentication-and-identity-design.md` §5.2; `02-tenant-isolation-and-access-control-design.md` §4.1) and, per §5 below, the Administrative Authorization Check this document adds. This ordering — identity and tenant/application context resolved first, a caller-specific authorization decision next, the Gateway's own fixed-order checks last — is the identical composition `01-application-construction-design.md` §7 already uses for its own construction and configuration actions: an actor's already-resolved standing is checked before the action runs, and the mechanism the action itself invokes downstream is never altered to accommodate that check. The Administrative Authorization Check is this document's own gate on **who may invoke an operation at all**; the Gateway remains the sole gate on **whether the operation itself is valid, consented, and correctly classified**. Neither substitutes for the other, and neither is folded into the other's fixed sequence.

## 5. Record-Scoped Access — the §1h Determination

### 5.1 The Determination

`BACKLOG.md` §1h finds that no design document expresses role-scoped access to *records* — only to *constructs*. `01-application-construction-design.md` §4.1 and §4.2.4 fix an access binding as construct-scoped: it grants a tenant role View or Invoke on a Surface or Command. `02-data-model-and-entity-design.md`'s `field_catalog` carries a classification tier and a data-governance category, but no role-access column, and its Entity Access Gateway performs no role-based record authorization — classification resolution there governs how a value is *treated* once access is otherwise established, never *whether* a given role may reach it at all. `02-tenant-isolation-and-access-control-design.md` §6 governs the five platform actor classes' least-privilege boundaries, not a builder-defined end-user role's reach into builder-defined data. The specification states the obligation directly: `02-governance-and-security/03-access-control-and-tenancy-model.md` §5 fixes that for end-user personas, "the specific actions an end-user role may perform, and the content it may reach, are set by the builder alone."

**This document determines that record-scoped access for the actors this interface serves is this document's to design, and designs it below (§5.3–§5.4).** The grounds:

- **C-27 is a professional-builder-facing capability, and the actors who invoke it are builder personas, not end users.** `01-business-and-ux/02-prd.md` §4's own row for C-27 fixes that it "operates strictly within the professional-builder model, extended only by the administrative access a tenant grants (C-03)." No end-user persona ever reaches this interface — it presumes no application has been configured, and every end-user persona's own scope is confined to exactly one already-*built* application (`02-governance-and-security/03-access-control-and-tenancy-model.md` §6). The gap this determination closes is therefore the professional-builder-facing slice of "which records a role may reach": which entities, and which of the four operations on them, a given builder role may exercise through this interface.
- **The map assigns the adjacent question here.** `implementation-document-map.md`'s charge for this document is "how tenant isolation and access control bind to an interface no builder explicitly configured" — a question that cannot be answered by citing an existing mechanism, because no existing mechanism reaches below the level of "which application's schema is this connection scoped to" (`02-tenant-isolation-and-access-control-design.md` §5.1) to "which entities within that schema may this specific role administer through this interface." That finer grain is what this determination supplies.
- **A record-scoped grant is genuinely new content, not a restatement of an existing one.** `01-application-construction-design.md`'s access binding targets a construct; this interface presumes no construct exists (§3.3). Widening that binding's target to include an entity directly would reopen §4.1 of that document — a closed, platform-owned vocabulary this document has no charge to reopen. What this determination adds is a distinct mechanism, scoped to this document's own capability, that composes with the tenant- and application-scoping structures already fixed rather than duplicating or widening them (§5.3).

### 5.2 What Is Already Composed With, and What Remains Missing

`02-tenant-isolation-and-access-control-design.md` §6 already fixes where a builder persona's grant lives — `tenant_<id>.tenant_users`, narrowed by `tenant_<id>.tenant_user_application_scope` where the role is application-scoped — and how the connection-scoping mechanism (§5.1 of that document) turns that grant into a database-privilege boundary: a connection carries privilege on exactly the schema(s) the actor's own binding covers, never more. Because every entity this document derives an interface from lives inside one application's own schema (`02-data-model-and-entity-design.md` §3.1), that existing mechanism already bounds *which application's* entities a given builder role's connection can reach at all — this document adds nothing to that bound, and narrows nothing wider than it.

**What remains missing is the grain below the application.** A builder role whose grant is application-scoped, or tenant-wide, today reaches every entity inside the schema its connection is scoped to identically — there is no mechanism anywhere in the design library that lets a tenant narrow that reach further, to specific entities, or bound it to specific operations (only some of Create, Read, Update, or Delete) rather than all four at once. This is exactly the gap §1h names, restated precisely: not "which schema," which is already solved, but "which entities within an already-reachable schema, and which of the four operations on them."

### 5.3 The Administrative-Scope Grant

This document fixes a new grant, the **administrative-scope grant**, that closes the gap identified in §5.2 by narrowing, never widening, the reach an actor's existing application-scoped or tenant-wide grant already establishes. Its semantics are fixed here; its physical table is `tenant_<id>.administrative_scope_grants`, defined by `02-platform-data-model-design.md` §3.2 (`BACKLOG.md` §1i) — never a table this document defines itself, because it is platform-owned access-scoping configuration of the same kind as `tenant_user_application_scope`, composing with the tenant- and application-scoping structures that document already owns, not a builder-defined entity inside the per-application schema this document's own Derivation Function reads (§3).

That table's columns:

| Column | Purpose |
|---|---|
| `grant_id` | UUIDv7, primary key. |
| `tenant_user_id` | FK → `tenant_users`, this same tenant schema — the builder actor's own tenant-level binding, verified against the Resolved Request Context at the moment the Administrative Authorization Check (§5.4) runs. |
| `application_id` | FK → `platform.applications`, constrained to this tenant's own applications — which application's entities the grant reaches. |
| `entity_id` | Nullable; where non-null, an identifier for an `entity_catalog` row inside that application's own per-application schema — carried as a plain value rather than an enforced foreign key, because `entity_catalog` lives one schema down and no foreign key in the tenant schema may resolve there. This is the identical discipline `02-data-model-and-entity-design.md` §5's own referential-integrity rule already applies within one schema, extended here to a reference that, by construction, can never cross the schema boundary it would otherwise cross. Null means the grant covers every entity in the named application not separately narrowed by a non-null row for the same `tenant_user_id`. |
| `action_classes` | One or more of the closed vocabulary **Create, Read, Update, Delete** — drawn directly from C-27's own definition (`01-business-and-ux/02-prd.md` §4) rather than invented independently. |
| `granted_at`, `revoked_at` | Standard grant lifecycle fields. |

**This is platform-owned access configuration, never a builder-defined entity, and is therefore never mediated by the Entity Access Gateway.** The Gateway `02-data-model-and-entity-design.md` §4.1 fixes mediates access to "a builder-defined entity's catalog rows or instance data" — this table is neither; it is access-configuration structure at the tenant level, alongside `tenant_users` and `tenant_user_application_scope`, read at the same resolution-phase point `02-tenant-isolation-and-access-control-design.md` §4.1's Context Resolution Point already reads `tenant_user_application_scope` from, and written through its own configuration action, checked against the granting actor's own already-resolved standing, on the identical discipline `01-application-construction-design.md` §3 and §7 already use for a construction or configuration action: an actor without the grant to configure access is refused before the write runs; the write itself is not a call into the Entity Access Gateway.

**Who may write this grant.** The access administrator persona — whose own scope, per `02-governance-and-security/03-access-control-and-tenancy-model.md` §5, is "define roles, permissions, and access policy for the tenant and for the software it builds" — writes and revokes rows in this table, within its own tenant's applications. This is a narrowing action only: an administrative-scope grant can restrict a builder role's reach to fewer entities or fewer operations than its existing application-scoped or tenant-wide grant already covers; it can never widen that reach beyond the schema the actor's connection is already scoped to (`02-governance-and-security/03-access-control-and-tenancy-model.md` §6, "access scopes below the tenant, never above it").

**Absence is absence of authority.** A builder actor with no administrative-scope grant row for a given entity, and no null-`entity_id` row covering it, has no reach into that entity through this interface — regardless of how broad its underlying application-scoped or tenant-wide role grant otherwise is. This is the deny-by-default posture `02-governance-and-security/03-access-control-and-tenancy-model.md` §8 fixes ("no authority is held by default"), applied here at the entity grain this document's own mechanism adds.

### 5.4 The Administrative Authorization Check

Before any of the four operations of §4.2 reaches the Entity Access Gateway, the **Administrative Authorization Check** — running immediately after the Context Resolution Point, exactly at the position §4.3 fixes — resolves whether the acting builder identity holds an administrative-scope grant (§5.3) covering the target entity and the requested action class. It reads `tenant_<id>.administrative_scope_grants` through the same privileged, identity-scoped resolution-phase access `02-tenant-isolation-and-access-control-design.md` §4.1's Context Resolution Point already uses to read `tenant_user_application_scope` — an extension of that established reading, never a second, schema-scoped connection acquired specially for this check. Where the grant is not found, the operation is refused before the Gateway is ever invoked; where it is, the operation proceeds to the Gateway on exactly the same terms as any other caller (§4.1).

This check is this document's own addition, run by this document's own component, never a fourth step folded into the Gateway's fixed three-step order (§4.3). It is checked against the connection already scoped by `02-tenant-isolation-and-access-control-design.md` §5.1 — the Administrative Authorization Check never accepts, and has no code path to accept, a caller-supplied entity or application identifier as an alternative to the one the Resolved Request Context already carries.

### 5.5 What This Determination Does Not Resolve

This determination resolves record-scoped access for the professional-builder actors who invoke this interface directly. It does not resolve, and does not attempt to resolve, the distinct question of which records an **end-user** role may reach once a construct — a Surface, presenting entity-backed content — has been configured and bound to that role through an access binding (`01-application-construction-design.md` §4.1). That question is mediated by a construct in a way this interface, by definition, never is (§3.3, §6.2), and it belongs to whichever document eventually designs how a Surface's presented content is bound to the entity data underlying it — a mechanism no document in this layer yet owns. This document names that as a distinct, still-open question rather than treating it as resolved by the mechanism above, and rather than silently absorbing it into a determination that was never asked to cover it.

## 6. Three Boundaries, Stated Bidirectionally

### 6.1 Against C-05 — `02-data-model-and-entity-design.md`

**What this document does.** It reads the shape `02-data-model-and-entity-design.md` fixes and operates on the records held within it. It owns no catalog, no column, no validation rule, and no representation of an entity, a field, or a relationship; every one of those remains exactly as that document defines it.

**What `02-data-model-and-entity-design.md` does not do.** It defines the shape of data and the single mediation point every access to it passes through; it designs no consumer-facing operation surface over the records held in that shape, and its own scope section states this directly: "the generic administrative interface (C-27)... is a distinct, later document's concern... none is designed here." Neither document absorbs the other: one fixes what a record *is*, the other operates on the records that already exist in that shape.

### 6.2 Against C-06 — `01-application-construction-design.md`

**What this document does.** It presumes no configured application. No construct, no structural binding, no behavioral binding, and no access binding needs to exist for this interface to derive from, and operate on, an entity's records — the derivation reads only the four catalogs `02-data-model-and-entity-design.md` fixes (§3.1), and explicitly excludes any `entity_catalog` row flagged as build-surface content (§3.3). The **minimal** application row and per-application schema that C-04's construction action produces (`01-application-construction-design.md` §3) already exists wherever this interface operates, because that is where `02-data-model-and-entity-design.md` §3.1 fixes that an entity's catalog rows physically live — but that minimal row carries no structure, behavior, or access **configuration**, and this interface requires none of it either. "No application configured" is the precise boundary; it is never "no application constructed."

**What `01-application-construction-design.md` does not do.** It owns the configuration model — constructs and the three binding kinds — for a *built* application, and its own construct-kind enumeration explicitly excludes this capability by name: "the generic administrative surface derived automatically from a builder's entities (C-27, §2) presumes no construct a builder configures at all" (`01-application-construction-design.md` §4.2.2). This document does not ask that vocabulary to widen to accommodate a fifth kind, and that document's closed vocabulary is not reopened anywhere in this document.

### 6.3 Against C-07 — running built software for end users

**What this document does.** Every operation this interface performs is a professional-builder actor administering its own entities' records, checked against the actor's own administrative-scope grant (§5.3–§5.4), never a run-time journey (`01-business-and-ux/05-user-journeys.md` §2). No end-user persona ever invokes this interface, and this interface never renders, serves, or substitutes for a built application's own end-user surface.

**What running a built application for its end users does not do.** The Operation family's own mechanism — not yet written in this layer, and out of this document's scope — runs already-**configured** software for the end users it admits, through whatever construct-mediated path (a Surface, an access binding) that configuration establishes. That the two ultimately reach the same Entity Access Gateway for the same underlying record operations (§4.1) does not make them the same capability: the actor, the trigger, the authorization path (§5 here, versus a construct-mediated access binding there), and the presumption of a configured application versus none all differ. Neither this document nor a future Operation-layer document may treat one as a substitute for the other.

## 7. The Empty State

`01-business-and-ux/05-user-journeys.md` §7.1 fixes that "a data model with entities defined but no application yet built" is a valid empty state, in which this interface "is usable and presents no records to create, read, update, or delete," and that this state is "structurally distinct" from the built-application empty state — "exactly its boundary against C-06 and C-07."

This document's mechanism produces that state as a structural consequence of §3, never as a guarded special case:

- **Zero entities defined.** Where `entity_catalog` holds no row for the tenant's applications the actor may reach, the Derivation Function (§3.1) returns an Interface Description naming no entity. The interface is usable — it presents "there is nothing yet to administer," not an error — because the Derivation Function's input is simply empty; no code path exists that treats an empty catalog as a failure to derive from.
- **Entities defined, no instances yet recorded.** Where an entity satisfies §3.2's completeness rule but its instance table holds no row, the Derivation Function returns a complete Interface Description — every field and relationship the entity's current schema version fixes — and the Read operation (§4.2) returns no record. Create remains available; the interface is fully usable and simply has nothing yet to show.
- **No configuration required to reach either state.** Exactly as `01-application-construction-design.md` §3 makes the newly-constructed-application empty state a property of the construction action's own minimality rather than a state a later step must additionally guarantee, this document's empty state is a property of the Derivation Function's own minimality: it requires no builder action, no configuration, and no administrative-scope grant beyond the ordinary deny-by-default posture (§5.3) to produce a coherent, usable, empty interface.

This is structurally distinct from a built application's own empty state (`01-application-construction-design.md` §8, "a newly constructed application exists before any data is modeled or any end user is admitted") because that state presumes the construction action has run and configuration is what is absent; this document's empty state presumes only that entities exist, or do not yet, and presumes no configuration was ever a precondition to begin with.

## 8. Evidence Produced

Each mechanism this document fixes is a place a specific kind of audit evidence originates, expressed in `08-audit-and-traceability-design.md` §4.2's consolidated base record and discriminated event-type model. One of this document's mechanisms populates an event type another document already owns; two are new.

| `event_type` | Origin | `source_mechanism` | `outcome` |
|---|---|---|---|
| `data-administration-grant-configuration` | New — this document. | The administrative-scope grant's own configuration action (§5.3), checked against the granting access administrator's own resolved standing. | `applied` (grant written or revoked) or `refused` (actor lacks the grant to configure access, or the grant would widen reach beyond the actor's own application/tenant scope). |
| `data-administration-action` | New — this document. | A Create, Update, or Delete operation invoked through this interface (§4.2), preceded by the Administrative Authorization Check (§5.4). | `applied` (Administrative Authorization Check passed and the downstream Gateway operation succeeded) or `refused` (the Administrative Authorization Check found no covering grant, or the Gateway itself refused the operation — the `result` field states which, never conflating the two, per the same discipline `08-audit-and-traceability-design.md` §4.3 already applies to distinguishing a basis-refusal from an authority-refusal). |
| `invariant-check` (`invariant_id = INV-04`) | Already defined, `01-invariant-enforcement-design.md` §6.1 / `02-data-model-and-entity-design.md` §12. | The Validation Engine's own inspection of every Create, Update, and Delete operation this interface dispatches into the Gateway (§4.1–§4.2). | Per that model's own vocabulary; this document supplies no new inspection content and no new event type for it. |

**Read is not separately captured.** No document in this design library — including `02-data-model-and-entity-design.md`'s own evidence list and `08-audit-and-traceability-design.md`'s consolidated model — treats an ordinary read as a consequential action requiring a dedicated audit event; only writes, refusals, and checks are. This document follows that same convention rather than introducing a first exception to it: the Read operation of §4.2 produces no dedicated evidence row of its own.

**Landing category, stated on the same precedent `02-data-model-and-entity-design.md` §12 already established.** `data-administration-grant-configuration` is, in substance, the builder's own definition of a role-to-entity-and-action-class grant structure — the same shape `01-application-construction-design.md` §9 already places under **Authorization and grant events**, and this document places it there identically, a direct fit. `data-administration-action` does not describe an authorization decision on its own terms (the authorization decision it rests on is the grant-configuration event above, and the Administrative Authorization Check's own pass/fail is folded into this event's `result` field, not a separate category); it is, in substance, a record coming to exist, being changed, or ceasing to be current — the same reasoning `02-data-model-and-entity-design.md` §12 already applied to land its own three new event types under **Data-lifecycle events** ("each governs how a builder-defined data structure or its instances come to exist, evolve, or persist — a lifecycle concern in substance"). This document adopts that identical reasoning for `data-administration-action` rather than re-deriving it, and lands it under **Data-lifecycle events** alongside them.

### 9.1 ADR-030 — The Derivation Mechanism, the Administrative Authorization Check, and the Administrative-Scope Grant

- **Status:** Provisional — Pending Lead Approval.
- **Cost to reverse:** **Moderate** (`PROCESS.md` §12.1). This decision fixes a derived interface over builder data this document does not own — the four catalogs and every committed instance remain exactly as `02-data-model-and-entity-design.md` fixes them, untouched by anything this decision changes. Reversing or materially changing the Derivation Function's own shape, the Administrative Authorization Check's position, or the administrative-scope grant's own semantics requires replacing this document's own interface and the Administrative Authorization Check that reads the grant table `02-platform-data-model-design.md` §3.2 defines; it requires no migration of entity, schema, field, or relationship data, and no change to the Entity Access Gateway or to any already-committed record. This is a materially lower cost than the Brutal grade `02-data-model-and-entity-design.md`'s own ADR-028 carries for the physical shape this document builds on, and is stated at that lower, honest grade rather than inflated to match the document it depends on.
  - **Amended, `BACKLOG.md` §1i (schema-ownership gap closed).** This decision's grant table was originally described here as living inside the per-application schema, with `tenant_user_id` carried as a plain, unenforced value to avoid naming a tenant-schema row from an application-schema table. `02-platform-data-model-design.md` §3.3's own boundary statement fixes that schema as holding only its two platform-owned tables plus everything `02-data-model-and-entity-design.md` defines as builder content — a grant structure fit neither description. The table is relocated to `tenant_<id>.administrative_scope_grants`, defined by `02-platform-data-model-design.md` §3.2, because it is platform-owned, tenant-level access-scoping configuration — the same kind of structure as `tenant_user_application_scope` — never a builder-defined entity. This relocation lets `tenant_user_id` resolve as an ordinary same-schema foreign key; the corresponding, honestly-stated cost moves to `entity_id`, now the cross-schema reference, carried as a plain value for the identical reason its predecessor was. This changes no semantics, column meaning, check position, or narrowing rule this ADR already fixed — it corrects only which document owns the table's physical definition.
- **Upstream decisions assumed:** `02-data-model-and-entity-design.md` §3.2–§3.3 (the four catalogs this decision's derivation reads, and the construct/binding representation this decision's exclusion rule depends on), §4.1–§4.2 (the Entity Access Gateway and Validation Engine this decision's four operations dispatch into), §5 (the mark-not-current outcome this decision's Delete operation resolves to), §8 (the versioned-instance shape this decision's Read and Update operations compose with); `02-platform-data-model-design.md` §3.2 (the `administrative_scope_grants` table this decision's grant is physically realized in, per the `BACKLOG.md` §1i amendment above); `01-application-construction-design.md` §3 (the minimal construction action whose output this decision's entities live inside), §4.1–§4.2.4 (the closed construct/binding vocabulary and its own explicit C-27 exclusion), §7 (the construction/configuration-action composition pattern this decision's Administrative Authorization Check reuses); `02-tenant-isolation-and-access-control-design.md` §4, §5.1, §6 (the Context Resolution Point, connection-scoping mechanism, and application-scope narrowing pattern this decision's own grant table composes with and narrows further); `03-authentication-and-identity-design.md` §5.2 (the Authentication Gate this decision's actions run behind); `02-governance-and-security/03-access-control-and-tenancy-model.md` §5–§6, §8 (the role matrix, the scoping-narrows-never-widens rule, and the deny-by-default posture this decision's grant mechanism realizes); `08-audit-and-traceability-design.md` §4 (the consolidated event model this decision's evidence populates). ADR-028 and ADR-027/ADR-029 remain Provisional and are not assumed settled; this decision depends on none of their approval status beyond the mechanisms they already fix.
- **Verified vs. reasoned:** Reasoned throughout. No time-sensitive ecosystem, product, or vendor claim is made; every finding derives from the cited specification and the cited, already-written upstream design documents' own content.
- **Question this answers:** Given four already-fixed catalogs and a Gateway that mediates every read and write of the records they govern, and given the specification requires a create/read/update/delete interface to follow automatically from an entity's definition, with no application configured and no builder-defined role-to-record binding designed anywhere yet — what is the smallest mechanism that derives a usable interface directly from the catalogs' current state without a materialized, driftable artifact; dispatches every operation into the Gateway without opening a second access path; and closes the still-open record-scoped-access gap for the professional-builder actors who use this interface, without reopening the closed construct/binding vocabulary or widening any grant beyond what tenant and application scoping already bound?
- **Criteria applied, and how each resolved:**
  1. *A runtime-computed interface description versus a generated, stored artifact.* Decisive for runtime computation — a stored artifact would require regeneration on every schema evolution, reintroducing exactly the synchronization machinery `02-data-model-and-entity-design.md` §8.1 already excludes from its own storage shape; a runtime read of the catalogs' current state can never drift from them because it never holds a separate state to drift from.
  2. *Reusing the Gateway's existing read/write/mark-not-current vocabulary versus inventing a dedicated deletion mechanism.* Decisive for reuse — `02-data-model-and-entity-design.md` §5 already names the "mark-not-current" outcome a delete resolves to; inventing a second, tombstone-specific write shape would be this document altering a mechanism it does not own, and no evidence anywhere in the cited documents shows the existing outcome is insufficient.
  3. *A new, narrowing-only administrative-scope grant versus treating existing application-scope narrowing as sufficient.* Decisive for a new grant — existing application-scope narrowing bounds which schema a connection may reach, never which entities within an already-reachable schema a specific role may administer through this interface specifically; treating it as sufficient would leave §1h's gap open and would repeat the re-defer-without-a-destination failure this document was explicitly directed to avoid.
  4. *Checking the administrative grant upstream of the Gateway versus folding a fourth step into the Gateway's own fixed order.* Decisive for upstream — the Gateway's three-step order is fixed by `02-data-model-and-entity-design.md` §4.1 and is, by that document's own design, never a role-based record-authorization check; adding a fourth step here would be this document altering a mechanism it does not own, the identical failure criterion 2 already rejects in the opposite direction.
- **Context:** This is the third document of the Data, Construction & Contracts layer, and the first to make the determination `BACKLOG.md` §1h names as owed — surfaced at H20a's close by asking what the newly-fixed construct-scoped action-class vocabulary does and does not reach, and left open rather than answered there on the correct grounds that the question belongs to whichever document C-27's own subject matter forces it upon first.
- **Decision:** (1) An entity's administrative interface is derived at runtime, on every invocation, directly from `entity_catalog`, `schema_version_catalog`, `field_catalog`, and `relationship_catalog`'s current state, never a generated or cached artifact spanning a schema-version change (§3.1–§3.2). (2) Every Create, Read, Update, and Delete operation this interface exposes is dispatched as the read, instance-write, or mark-not-current operation the Entity Access Gateway already exposes, never a second write shape or a second access path (§4.2). (3) A new administrative-scope grant, narrowing a builder role's already-resolved tenant or application scope to specific entities and to a closed Create/Read/Update/Delete action-class vocabulary, is checked by an Administrative Authorization Check upstream of the Gateway, resolving §1h for the professional-builder actors this interface serves (§5.3–§5.4); its physical table is `tenant_<id>.administrative_scope_grants`, defined by `02-platform-data-model-design.md` §3.2 per the `BACKLOG.md` §1i amendment, never by this document. (4) `entity_catalog` rows flagged as build-surface content are excluded from derivation entirely, the concrete instantiation of this document's own boundary against C-06 (§3.3, §6.2). (5) The empty state is a structural consequence of the Derivation Function reading an empty or partially-empty catalog set, never a guarded special case (§7).
- **Alternatives considered:** *A generated or materialized interface artifact, regenerated on schema evolution* — rejected under criterion 1; it reintroduces synchronization machinery this design's own upstream document already excluded, for no benefit this document has evidence to justify. *A bespoke deletion or tombstone mechanism specific to this interface* — rejected under criterion 2; the outcome it would duplicate is already named and owned elsewhere. *Treating existing application-scope narrowing as already sufficient for §1h, leaving the gap open* — rejected under criterion 3; it is the re-defer-without-a-destination failure this document's own ticket names as the one to avoid. *A fourth, Gateway-internal role-authorization step* — rejected under criterion 4; it alters a mechanism owned by a document this one only calls. *Widening an access binding's own target beyond a construct, to include an entity directly* — considered and rejected as unnecessary once a separate, C-27-scoped grant closes the gap without touching `01-application-construction-design.md`'s closed vocabulary at all.
- **Consequences:** Binds no obligation onto `02-data-model-and-entity-design.md`'s catalogs, Gateway, or storage shape — every operation this decision fixes is a caller of that mechanism exactly as already designed, never an extension of it. Binds no obligation onto `01-application-construction-design.md`'s construct/binding vocabulary — this decision's grant mechanism is additive and entity-scoped, never a widening of an access binding's own target. Adds two new `event_type` values to `08-audit-and-traceability-design.md`'s existing model (§8), on that document's own closest-fit reasoning, never a new mandatory category. Leaves open, and names rather than silently absorbs, the distinct question of end-user-role-scoped access to records reached through a construct-mediated, built-application surface (§5.5) — a question for whichever document eventually designs that binding, not resolved here. **Amended, `BACKLOG.md` §1i:** binds one obligation onto `02-platform-data-model-design.md` that did not exist at this ADR's original approval — that document now owns the administrative-scope grant's physical table (its own §3.2), added there because the table is platform-owned, tenant-level access-scoping configuration, never a builder-defined entity. This document continues to own the grant's semantics, its columns' meaning, and the Administrative Authorization Check that reads it; it cites the table rather than restating or redefining it.

## 12. Binding Rules

- **A new entity's administrative interface requires no further authoring step.** The Derivation Function's only input is the four catalogs `02-data-model-and-entity-design.md` §3.2 already requires to exist for a complete schema; no builder action, configuration, or generation step stands between an entity's completeness and its interface's usability (§3.1).
- **The Interface Description is computed at runtime, never generated or cached across a schema-version change.** No mechanism in this document introduces a stored, driftable artifact or a synchronization step to keep one current (§3.2).
- **Build-surface content is excluded from derivation entirely.** An `entity_catalog` row flagged as a construct is never a candidate for this interface (§3.3).
- **Every operation this interface exposes is dispatched into the Entity Access Gateway, with no second path.** The four C-27 operations map exactly onto the Gateway's existing read, instance-write, and mark-not-current vocabulary; none is a new write shape (§4.2).
- **"Administrative" confers no exemption.** Every operation clears the identical Validation Engine, Consent and Minimization Check, and classification resolution any other caller of the Gateway clears (§4.1, §4.3).
- **Record-scoped access for this interface's own actors is resolved here, by a narrowing-only administrative-scope grant checked before the Gateway is ever invoked.** Absence of a grant is absence of authority; the grant can restrict an actor's existing scope further but never widen it, using the table `02-platform-data-model-design.md` §3.2 defines, never a table this document defines itself (§5.3–§5.4).
- **The distinct question of end-user-role-scoped, construct-mediated record access remains open and is named, not silently absorbed.** No determination in this document resolves it, and no future document may cite this one as having done so (§5.5).
- **The empty state is a structural property of the derivation, never a guarded special case.** Zero entities and entities-with-zero-instances both produce a usable, coherent interface with no record to act on (§7).
- **No storage-shape obligation, catalog, or Gateway check is altered by this document.** Every mechanism this document designs composes with what `02-data-model-and-entity-design.md`, `01-application-construction-design.md`, and `02-tenant-isolation-and-access-control-design.md` already fix; none is restated, narrowed, or duplicated.
- **Everything remains domain-neutral and platform-level.** No field, relationship, grant, or event type in this document encodes the characteristics of any single domain; all remain valid for any software built on the platform.
- **This document records exactly one ADR.** ADR-030 (§9) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, boundary, or invariant the cited specification and cited upstream design documents already fix.
