## 3. The C-19/C-26 Boundary — Held Absolutely, Stated First

`01-business-and-ux/02-prd.md` fixes C-19 and C-26 as two capabilities that "must never be conflated," and states the distinction in C-26's own row: *"C-19 is active, build-time AI assistance offered to the professional builder as suggestions during construction, whereas C-26 is AI automation that executes inside the built application at runtime."* C-26 is one of exactly two Future / Not-Yet-Authorized capabilities (§4, that document) — recorded for completeness only, "neither designed nor built," and "must not be implemented, expanded, or relied upon by any other capability." `01-application-construction-design.md` §2 and §13 already hold this boundary for the construction primitives this document assists a builder in using ("The build surface... assumes neither the tooling's presence nor its absence" and "closed to runtime AI automation... no capability for C-26 exists anywhere in this document"); this document holds the identical boundary for the tooling itself.

**Nothing designed below runs inside a built application at runtime.** Every mechanism this document fixes operates strictly at build time, against a builder's own construction, configuration, entity, schema, or process-definition content, before any application it touches serves a single end-user request. A built application's own runtime (C-07, `04-operation-reach-distribution/01-application-runtime-and-lifecycle-design.md`) never invokes this tooling, never depends on its presence, and never carries any trace of it: the only thing a built application's runtime ever consumes is already-committed, builder-approved content written through the same construction and entity mechanisms any builder-authored change uses (§5.4 below) — content that is, by the confirmation mechanism's own design, structurally indistinguishable from a builder's own direct work the moment it is committed. No suggestion, no provenance marker, and no assistance-history record is ever read by, exposed to, or reachable from a built application's own runtime surface.

**The boundary is stated as a rule and checked against every section below, not asserted once and forgotten.** §4's suggestion model produces content addressed to a builder, never to an end user. §5's confirmation gate is exercised by a builder deciding about their own not-yet-committed artifact, never by any actor or process operating inside a running built application. §7's four assistance kinds are realized entirely as suggested *configuration* of already-existing build-time primitives (constructs, bindings, entities, schemas), never as logic that executes when a built application handles a request. §8's programmatic interface is tagged `builder-tooling` and served under the reserved build-time path prefix `05-api-contract-design.md` §3.2 already fixes, never under a built application's own end-user-facing surface. This document introduces no hook, extension point, or accommodation — named or implicit — that a C-26 capability could later occupy without a fresh authorization and a fresh design ticket, exactly as `01-application-construction-design.md` §5 already holds for the construct/binding vocabulary's own closure.

## 4. The Suggestion Model

### 4.1 What a Suggestion Is

A **suggestion** is a single, tracked unit of AI-produced candidate content addressed to one builder, targeting one application, proposing a change expressible entirely in terms of the closed construction primitives `01-application-construction-design.md` and `02-data-model-and-entity-design.md` already fix — a construct, a structural/behavioral/access binding, an entity or schema element, or a process-definition element (§7 states the mapping per assistance kind). A suggestion is never itself a committed artifact: it exists to be reviewed, and its own existence changes nothing about the application it targets until the confirmation mechanism of §5 acts on it.

Every suggestion carries, from the moment it exists:

- **A provenance state**, `ai-suggested` at creation — the intrinsic, required property `05-ai-tooling-security-design.md` §5.2 fixes, never absent-by-default and never inferable as approved.
- **A disposition**, one of `pending` (awaiting a builder decision), `confirmed` (the builder accepted it, in whatever final form, and the write of §5.4 has been performed), or `discarded` (the builder declined it; no write ever occurs). The vocabulary is closed; a suggestion holds exactly one disposition at a time, and a disposition, once `confirmed` or `discarded`, is never reopened — a builder who wants a different outcome requests a fresh suggestion.

### 4.2 What Produces a Suggestion

A suggestion is produced by a **generation action** — the AI-assisted tooling's own act of composing candidate content in response to a builder's request for assistance of one of the four kinds §7 fixes. The generation action is an action the platform's own autonomous agent takes, at the platform layer, inside the authority `05-meta-operations/01-agent-operating-charter.md` §2 already grants it over "the platform core and builder tooling" — never an action a builder takes directly, and never an action any part of a built application's own runtime takes. §6 below fixes precisely how a generation action composes with the agent kernel.

**Every origin of grounding content the generation action reads is content-channel, never authority-channel**, exactly as `05-ai-tooling-security-design.md` §3.2 already fixes: the builder's own request, the application's existing constructs, bindings, entities, and schemas, and any data surfaced from a built artifact or an extension the generation action is permitted to read, are each packaged as material for the tooling to reason about. What the generation action is permitted to read, and what content the resulting suggestion may target, is resolved exclusively from the requesting builder's own already-resolved authorization grant — the identical Authenticated Actor Identity and Resolved Request Context `01-application-construction-design.md` §7 and `02-data-model-and-entity-design.md` §11 already establish for every other construction, configuration, and entity action in this library. This document introduces no second identity or scoping mechanism for the generation action; it composes with both exactly as every other document in this layer already does.

### 4.3 What Happens to a Suggestion

A `pending` suggestion has exactly two possible futures, both exercised by the requesting builder and by no one else:

- **Confirmed** (§5) — the builder's own explicit act transitions the suggestion's provenance state to `builder-approved` and, in the same act, triggers the write of §5.4.
- **Discarded** — the builder declines the suggestion. Its provenance state remains `ai-suggested` permanently; no write of any kind occurs; the record is retained (§9) as assistance history, never deleted, but is never again read by any commit path.

**A suggestion is never auto-applied, auto-expired into either state, or resolved by any actor other than the requesting builder.** There is no code path by which a `pending` suggestion becomes `confirmed` without the confirmation mechanism of §5 running, and no code path by which the passage of time, a subsequent unrelated action, or any other event changes its disposition. This is the concrete realization, for this document's own structure, of `05-ai-tooling-security-design.md` §5.2's rule that the `ai-suggested → builder-approved` transition has "exactly one legitimate path."

## 5. The Mandatory Human-Builder Confirmation Gate

### 5.1 The Distinction the Ticket Asks to Be Held, Stated First

This is a **builder** confirming their own not-yet-committed artifact — never the autonomous agent's own approval gate `03-human-in-the-loop-design.md` (H43) owns. The two are easy to conflate because both involve a human decision gating an AI-produced or AI-proposed outcome; they are nonetheless structurally distinct, and this section states the distinction precisely rather than assuming either answer, per the ticket's own instruction.

### 5.2 Checked Against H43 §9.1 — Confirmed, Not Re-Derived

H43 §9.1 already reconciled two cases that look similar to an enumerated charter §7 trigger but are not: a builder-facing Production-promotion gate (`02-builder-facing-environment-management-design.md`) and a steward's exceptional tenant-access grant (`02-tenant-isolation-and-access-control-design.md` §3.2). Its own rule for telling them apart is exact: *"this document's trigger-enforcement mechanism (§4) is scoped exclusively to actions H41's kernel classifies — the autonomous agent's own platform-layer conduct... This document's request/record/resolve mechanism (§5–§6) is general-purpose infrastructure that any other already-designed document may compose with for its own, non-agent-autonomy approval need."* H43 §13 goes further and names this document's own confirmation gate directly, by the identical reasoning, without waiting for this ticket to ask: *"That document's own mandatory human-builder confirmation gate for an AI-suggested artifact is a distinct instrument from this document's approval gates — a builder confirming their own AI-assisted suggestion, never the autonomous agent's own conduct stopping at a charter §7 boundary."*

**This document confirms that finding rather than re-deriving it, and the check is exact rather than assumed.** A charter §7 trigger stops the *autonomous agent's own conduct* at a boundary past which it may not act alone — it is a property of what the agent was about to do unsupervised. The confirmation gate governs no such moment: the agent was never going to commit a suggestion unsupervised in the first place, because C-19's own row fixes, unconditionally, that "no AI-generated output is committed without mandatory human-builder confirmation" — there is no autonomy boundary here for a builder's confirmation to be *the human side of*, because there was never an autonomous commit path on the other side of it to begin with. The confirmation gate is not the agent stopping at a boundary and handing a decision to a human; it is a structural precondition on the write itself (§5.4), no different in kind from a builder directly composing a construct and choosing to save it. This holds for exactly the reason `01-application-construction-design.md` §8's own AI-assisted-building clause already states: the confirmed write is, from that document's mechanism's own perspective, indistinguishable from one the builder performed directly.

### 5.3 What This Document Owns, and What It Deliberately Does Not Reuse

H43 §13 states plainly that it "does not absorb that confirmation gate," and that this document "does not inherit this document's [H43's] trigger-enforcement mechanism for its own confirmation step." This document takes that as license to build the lighter mechanism the situation actually calls for, rather than reusing H43's heavier machinery by default:

- **No routing.** H43's request/record/resolve mechanism exists to find "a human holding the required authority" who was not necessarily present when the gate fired, and to make a pending decision durably findable by that human across sessions (H43 §10). None of that is needed here: the confirming builder is the same actor who requested the suggestion, present in the same interaction or returning to the same tooling surface, never a third party being routed to. This document's own confirmation record (§4.1's disposition field) is sufficient; it needs no cross-session, human-findable pending-approval structure of H43's own shape.
- **No resolution vocabulary beyond confirm/discard.** H43 §6.1 constrains its own resolution vocabulary (`authorize`/`decline`/`redirect`) by trigger shape, because an autonomous agent's halt-shaped triggers forbid `authorize` outright. No such constraint applies here — there is no halt-shaped case, because there is no autonomous commit the builder's confirmation is standing in the way of. This document's own vocabulary (`confirmed`/`discarded`, §4.1) is the complete set a builder confirming their own suggestion needs.
- **What is genuinely shared.** The confirmation mechanism, like every action in this library, still clears charter §5's preconditions where it acts as an autonomous kernel step (§6.2 below states precisely which parts of confirmation are kernel-governed and which are not), and its outcome is still recorded to `08-audit-and-traceability-design.md`'s own standard (§10). Nothing here is exempt from the platform's baseline traceability; what is not reused is H43's specific approval-routing infrastructure, because the fact pattern it exists to serve — a human who must be found and authorized to decide on someone else's behalf — does not arise.

### 5.4 The Write the Confirmation Performs

Confirming a suggestion is a single builder action carrying, at minimum, the suggestion's own identifier and, optionally, edits to its proposed content. That action:

1. **Re-clears security validation on the final content actually submitted, never the originally generated content alone.** `05-ai-tooling-security-design.md` §4.1 fixes that "builder confirmation" and "security validation" are each independently necessary and neither substitutes for the other; because a builder may edit a suggestion before confirming it, this document fixes that the gates named in that section (secrets-scanning, vulnerability classification, and the request-boundary and query-layer construction the artifact's own content touches) run against whatever content the confirmation action actually submits — never against a stale snapshot from generation time. Where security validation fails on the submitted content, the confirmation is refused, the suggestion's disposition remains `pending`, and the builder may revise and retry; no partial or provisional write ever occurs.
2. **Performs the ordinary construction, configuration, or entity-definition action the suggestion's own content describes**, through the identical mechanism `01-application-construction-design.md` §3–§4 and `02-data-model-and-entity-design.md` §4.1's Entity Access Gateway already fix for every such action — no second write path, no AI-origin exemption, and no bypass of the Validation Engine, the Consent and Minimization Check, classification/category resolution, or the End-User Record-Reach Check. The write is authored by the confirming builder's own already-resolved identity and context, exactly as `01-application-construction-design.md` §3's "who performs it" rule already fixes for direct construction.
3. **Sets the suggestion's own provenance state to `builder-approved` and disposition to `confirmed`, in the same transaction as the write.** There is no window in which the write exists without its provenance already recorded as approved, and no window in which the provenance is marked approved without the write having occurred — the two happen together, which is what makes "no other code path may set or infer approval" (`05-ai-tooling-security-design.md` §5.2) true by construction rather than by discipline.

**The written artifact itself carries nothing back to the suggestion that proposed it.** The confirmed construct, binding, entity, schema element, or process-definition element is written as an ordinary row in the mechanisms those two documents already fix, with no provenance column, no tooling-origin flag, and no foreign key referencing the suggestion record. Only the suggestion record (§9) carries a forward reference — `resulting_reference` — to what its own confirmation produced. This asymmetry is deliberate and is reasoned about independently in §11's ADR.

## 6. Inheriting the Meta-Operations Guardrails — What Differs, and Why

`01-business-and-ux/02-prd.md` C-19 fixes that the tooling "inherits the platform's Meta-Operations safety guardrails," naming the operating charter and the human-in-the-loop protocol by row. `implementation-document-map.md` additionally names prompt-and-context management as the third inherited guardrail and states this document is "the only capability design that reaches into Layer 6." The ticket calls this the most interesting question in scope; this section states it precisely rather than flattening it in either direction, distinguishing two different actions this document's own mechanism performs, because they inherit differently.

### 6.1 Two Actions, Not One, With Two Different Relationships to the Kernel

§4–§5 above already draw the line the rest of this section rests on: **generation** is an action the platform's autonomous agent takes; **confirmation** is an action the builder takes. The Meta-Operations guardrails govern the agent's own platform-layer conduct (charter §2); they do not, and were never designed to, govern a human builder's own direct decision about their own artifact. Inheritance is therefore not a single, uniform fact about "the tooling" — it is a fact about the generation action specifically, and a non-fact, correctly, about the confirmation action.

### 6.2 What Generation Inherits, in Full

A suggestion-generation action is an ordinary kernel-governed action, composing with `01-agent-runtime-and-control-design.md`'s already-built mechanisms exactly as any other platform-layer agent action does — no parallel authority model, no exemption, and no second classification or precondition mechanism:

- **Classification and precondition-clearing (H41 §4–§5).** A generation action carries the identical declared shape (target, kind, triggering task) every other agent action carries, tested against charter §6's permitted classes and charter §7's approval-required classes as the same closed lookup. The overwhelming majority of generation actions — proposing candidate content that changes nothing until confirmed — fall within the permitted-autonomous class: they are reversible by construction (§4.3's discard path always exists, and confirmation is a distinct, later, separately-gated act), invariant-holding (the content-channel/authority-channel separation of §4.2 and `05-ai-tooling-security-design.md` §3.2 prevents a generation action from ever acquiring authority beyond the requesting builder's own grant), and within scope (bound to one builder, one application, the four assistance kinds §7 fixes). A generation action whose declared shape happens to match a charter §7 class — for example, one whose target is a fixed architectural decision, or one a security-review trigger reaches — stops and routes to `03-human-in-the-loop-design.md`'s already-built mechanism exactly as any other agent action would; this document adds no exemption and no separate path for that case.
- **Context assembly (H44 §5).** A generation action assembles the baseline every task assembles (the full invariant set, the authority grant and authorized scope, the precedence order, the current reconstructable state) plus, per H44 §5.1's declared-shape lookup, the closest-fitting rows of that document's closed table: "Producing or applying a platform-layer change" (for the structural, contract, and data-model boundaries a suggestion's content must conform to) and "Undertaking a security-relevant change" (for the threat model, secrets-handling, and vulnerability-severity content `05-ai-tooling-security-design.md`'s own gates are measured against — that document itself realizes `02-governance-and-security/02-security-policy.md`, the identical specification this H44 row keys to). Per H44 §5.1's own closing rule that "the required set is a floor, not a ceiling," this document's own generation actions additionally assemble the design-level construction-primitive content those two rows' spec-level citations do not themselves name — `01-application-construction-design.md`'s configuration model and `02-data-model-and-entity-design.md`'s entity/schema mechanism — because a generation action cannot compose valid candidate content without holding the primitives it is composing in view. This is stated honestly as the closest fit among H44's closed rows, not as a claim that a task type named "AI-assisted builder tooling" exists in that table; it does not, and this document mints no eighth row, per H44 §2's own rule that the table is closed and this document may not extend it.
- **The precedence engine, the loop guard, and the token/compute budget.** A generation action that surfaces a genuine content-level contradiction routes to H41 §6's engine exactly as any other action's assembled context would (H44 §6); it counts against the requesting task's iteration and retry counters exactly as any other pass through the kernel does (H41 §7–§8); and it draws against H42's existing token/compute/cost accumulators exactly as any other action does, minting no second envelope.

### 6.3 What Confirmation Does Differently, and Why That Is Correct Rather Than a Gap

A confirmation action is **not** classified against charter §6/§7, does **not** pass through H41's precondition-clearing gate as a kernel action in its own right, and is **not** a trigger `03-human-in-the-loop-design.md` enumerates — because it is not the autonomous agent acting at all. It is the builder's own direct action against builder-facing tooling, on the identical footing `01-application-construction-design.md` §3's "who performs it" rule already establishes for direct construction, and `02-data-model-and-entity-design.md` §11 already establishes for every write through the Entity Access Gateway: an authenticated actor, acting within its own already-resolved context, is a valid actor for that mechanism regardless of what proposed the content it is now committing. The write §5.4 performs clears the Entity Access Gateway's own four checks (§5.4's second step) — that is where the confirmed content is held to every guarantee the platform requires — but it is not additionally passed through the agent kernel's classification pipeline, because doing so would misattribute the builder's own act to the agent's conduct, contradicting the reconciliation §5.2 already confirms.

**This is the real difference the ticket asks to be named, stated plainly: the kernel governs what the agent may do unsupervised; the builder is never unsupervised over their own confirmation.** Inheriting the guardrails "wholesale" would mean subjecting the builder's own decision to an approval-gate mechanism built for a different actor's autonomy boundary — a category error, not a stronger guarantee, because there is no autonomy at the confirmation step for a guardrail to bound. Discarding the guardrails entirely, in the other direction, would mean the generation action that produces a suggestion in the first place runs unsupervised by the kernel — which this document does not do, and §6.2 states precisely how it does not. The guardrails are inherited exactly where the agent acts, and are not extended past the point where a human, not the agent, is the one deciding.

## 7. What the Tooling Assists With — Composing With the Construction Primitives, Introducing None

## 11. Design Decision Records

### 11.1 ADR-056 — The Suggestion Model as a Staged, Pre-Commit Structure; the Confirmation Gate as a Distinct Instrument From H43's Trigger Set; and the Provenance Boundary's Independence Reasoned Directly

- **Status:** Provisional — Pending Lead Approval.
- **Cost to reverse:** **Moderate**, matching `implementation-document-map.md`'s own pre-assigned grade for this document — *"build-time assistance whose outputs are never committed without builder confirmation; reversal replaces the tooling and leaves approved artifacts intact."* That rationale is a design claim this ADR tests directly, on two independent grounds, rather than accepting it because the map states it. **First, storage independence.** §5.4 and §9's row-by-row check both fix that a confirmed write carries no provenance marker, no tooling-origin flag, and no foreign key referencing the suggestion that proposed it — only the suggestion record itself (`ai_suggestions.resulting_reference`) points forward to what it produced, never the reverse. Removing or entirely replacing the tooling (deleting every suggestion record, replacing the generation mechanism, redesigning the confirmation interface) therefore touches nothing already committed: every already-confirmed construct, binding, entity, schema element, or process-definition element remains exactly as stored, indistinguishable from builder-direct content, because its own storage never depended on, or referenced, the tooling that suggested it. **Second, no downstream document depends on this document's own mechanism shape.** Unlike a document owning a schema other documents are built against, nothing in this library reads `ai_suggestions` or depends on the generation/confirmation split this document fixes — `01-application-construction-design.md` and `02-data-model-and-entity-design.md` already state their own build surface and Entity Access Gateway are "agnostic to whether a construction or configuration action originates from a human builder... or from AI-assisted tooling" (`01-application-construction-design.md` §2, §8), so reversing this document's own mechanism requires no change to either. Both grounds independently support Moderate over a higher grade: not Brutal or Very High, because no builder or platform data already stored is touched by a reversal; not High, because no published contract or component topology outside this document's own three operations (§8) is bound to this document's own internal shape; Moderate because the tooling itself — the generation mechanism, the confirmation interface, and the suggestion structure — is what would be re-done, on the identical reasoning `implementation-document-map.md`'s own row already states for `03-data-administration-design.md`'s parallel case ("reversal replaces the interface and leaves the underlying entities and their records intact").
- **Upstream decisions assumed:** `01-business-and-ux/02-prd.md` C-19 and C-26 (the capability this document realizes, and the boundary it holds absolutely); ADR-022 (`05-ai-tooling-security-design.md` §8.1 — the provenance-gate enforcement point this document's design structurally avoids ever needing to invoke in the ordinary case); ADR-027 and ADR-028 (`01-application-construction-design.md` §10.1, `02-data-model-and-entity-design.md` §13.1 — the construction mechanism and the Entity Access Gateway a confirmed write passes through unchanged); ADR-032 (`05-api-contract-design.md` §13 — the contract shape and the `builder-tooling` tag this document's own operations compose with); ADR-052, ADR-053, ADR-054, ADR-055 (`01-agent-runtime-and-control-design.md`, `02-token-and-compute-budget-design.md`, `03-human-in-the-loop-design.md`, `04-prompt-and-context-assembly-design.md` — the kernel mechanisms a generation action composes with, and the reconciliation §5.2 above confirms rather than re-derives). All named ADRs remain Provisional; this decision depends on their already-designed content, never their approval status (`PROCESS.md` §12.2).
- **Verified vs. reasoned:** Reasoned throughout. No claim asserts any model's, agent framework's, or vendor's current code-generation capability, accuracy, or behavior; every mechanism (the suggestion's own staged shape, the generation/confirmation split, the storage-independence argument, the H44 task-type mapping) is a structural argument from the cited capability row and the already-designed upstream documents' own content.
- **Question this answers:** Given a capability that must offer AI-native, build-time assistance across four kinds without ever committing an output unconfirmed, and given an already-fixed security boundary that requires the AI-suggested/builder-approved distinction to be structural rather than conventional, what is the smallest mechanism that (a) makes the confirmation gate genuinely mandatory by construction rather than by discipline, (b) correctly places itself outside `03-human-in-the-loop-design.md`'s own trigger set rather than inside or unrelated to it, and (c) keeps every already-confirmed artifact's own storage independent of the tooling that proposed it, such that the map's own Moderate cost-to-reverse grade is a finding this document can defend on its own terms rather than one it merely inherits?
- **Criteria applied, and how each resolved:**
  1. *Does the suggestion's provenance marker live on the suggestion record, or on the artifact it eventually produces?* Decisive for the suggestion record alone (§5.4, §9) — a marker on the committed artifact would require `02-data-model-and-entity-design.md` to carry a column it has already, and correctly, declined to own (§9.4 there), and would make every downstream consumer of that catalog responsible for filtering by a fact irrelevant to its own concern; keeping provenance on the suggestion record alone is what makes the confirmed artifact indistinguishable from builder-direct content, which is the property `01-application-construction-design.md` §8 already requires.
  2. *Does the confirmation gate reuse `03-human-in-the-loop-design.md`'s request/record/resolve mechanism, or build its own?* Decisive for its own, lighter mechanism (§5.3) — that document's own machinery exists to find and route to a human who was not necessarily present when a trigger fired; the confirming builder is always the requesting builder, present in the same or a later session of their own tooling use, so the routing problem that machinery solves does not arise here, and reusing it would import unneeded complexity for a fact pattern H43 §9.1 and §13 already state does not fit its own trigger set.
  3. *Does a generation action bypass the agent kernel, or compose with it as an ordinary action?* Decisive for full composition (§6.2) — charter §2 explicitly places "builder tooling" within the agent's platform-layer authority scope, and a generation action that skipped classification, precondition-clearing, or context assembly would be exactly the kind of parallel authority model this project's writing rules forbid building.
  4. *Is the Moderate cost-to-reverse grade accepted from the map, or independently re-derived?* Decisive for independent re-derivation, on two separate grounds (storage independence; no downstream structural dependency) — per the ticket's own instruction that the map's rationale "holds only if the provenance boundary genuinely keeps approved artifacts independent of the tooling," which is a claim this document is positioned to test rather than assume.
- **Context:** This is the closing document of Layer 3 (Data, Construction & Contracts) — every other document in the layer (`01-application-construction-design.md` through `08-coding-standards-and-patterns-design.md`) already names this one as the last outstanding dependency, per each of their own citations of "H45, not yet written" — and the one document `implementation-document-map.md` names as reaching cross-layer into Layer 6, the first whose own map row states the cost-to-reverse rationale as a testable claim rather than a bare grade.
- **Decision:** (1) A suggestion is a staged, pre-commit record — never itself a committed artifact — carrying an intrinsic provenance state and a closed disposition vocabulary, produced by a generation action that is an ordinary kernel-governed agent action (§4, §6.2). (2) The mandatory human-builder confirmation gate is a distinct instrument from `03-human-in-the-loop-design.md`'s own approval gates, confirmed against that document's own §9.1 reconciliation and its explicit §13 naming of this exact case, never assumed onto either side of it (§5.2). (3) Confirmation builds its own lighter mechanism rather than reusing H43's request/record/resolve infrastructure, because the routing problem that infrastructure solves does not arise where the confirming actor is always the requesting builder (§5.3). (4) A confirmed write re-clears security validation on the final, possibly-edited content and performs an ordinary construction/entity-mechanism write in the same transaction as the provenance transition, with no window in which one occurs without the other (§5.4). (5) The written artifact carries no reference back to the suggestion that proposed it; only the suggestion record references forward to what its own confirmation produced (§5.4, §9.1). (6) The Moderate cost-to-reverse grade is independently confirmed on two grounds — storage independence and the absence of any downstream structural dependency on this document's own mechanism (this ADR). (7) A new per-tenant structure, `ai_suggestions`, is owed to `02-platform-data-model-design.md`, named as the fifth instance of the pattern `BACKLOG.md` §1aa records (§9.1).
- **Alternatives considered:** *A provenance column on the committed artifact's own catalog row, rather than on the suggestion alone* — rejected under criterion 1; it would re-open a schema `02-data-model-and-entity-design.md` has already, correctly, declined to carry this content, and would break the indistinguishability `01-application-construction-design.md` §8 requires. *Reusing `03-human-in-the-loop-design.md`'s full request/record/resolve mechanism for the confirmation gate* — rejected under criterion 2; it solves a routing problem this fact pattern does not have, and H43 §9.1/§13 already state the confirmation gate is outside its own trigger set rather than an unaddressed instance of it. *Exempting generation actions from the agent kernel, on the reasoning that they only produce suggestions and never commit anything* — rejected under criterion 3; charter §2's own scope bullet places builder tooling within the agent's platform-layer authority, and an unclassified, unguarded generation action would be a gap in kernel coverage, not a simplification. *Accepting the map's Moderate grade without independent testing* — rejected under criterion 4, per the ticket's own explicit instruction to reason the rationale rather than cite it.
- **Consequences:** Binds `02-platform-data-model-design.md` to the new `ai_suggestions` structure named in §9.1, for discharge in a future, separately-ticketed amendment, on the identical "constrain, never own" precedent every prior Layer 3/4 handover to that document already follows. Confirms, and alters none of, `05-ai-tooling-security-design.md`'s manipulation-resistance mechanism, insecure-output-prevention gates, and provenance-gate enforcement point; `01-application-construction-design.md`'s construction action and closed vocabulary; `02-data-model-and-entity-design.md`'s Entity Access Gateway and its own decline of the provenance attribute; `05-api-contract-design.md`'s contract shape, `builder-tooling` tag, and `provenance` field; and `01-agent-runtime-and-control-design.md`'s, `03-human-in-the-loop-design.md`'s, and `04-prompt-and-context-assembly-design.md`'s own kernel mechanisms — each document's own content stands exactly as already designed. Adds no new `event_type` to `08-audit-and-traceability-design.md`'s model (§10). Closes the cross-layer dependency `implementation-document-map.md` names for this document, and formally completes Layer 3 (Data, Construction & Contracts) per that map's own row.

## 14. Binding Rules

These rules hold for every element of this document and are subordinate to the charter and the capability model.

- **Nothing in this document runs inside a built application at runtime.** Every mechanism is build-time only; a built application's own runtime never invokes, depends on, or carries any trace of this tooling (§3).
- **No AI-generated output is committed without mandatory human-builder confirmation.** A `pending` suggestion has exactly two possible futures — `confirmed` or `discarded` — both exercised by the requesting builder alone, never auto-applied, auto-expired, or resolved by any other actor (§4.3).
- **Provenance is intrinsic and transitions through exactly one path.** A suggestion is `ai-suggested` at creation and becomes `builder-approved` only through the confirmation mechanism of §5.4, in the same transaction as the write it authorizes — never before, never inferred, and never through any other code path.
- **The confirmation gate is a distinct instrument from `03-human-in-the-loop-design.md`'s own approval gates, confirmed against that document's own §9.1 reconciliation, not assumed onto either side of it.** A builder confirming their own suggestion is never routed through the agent kernel's classification or that document's trigger-enforcement mechanism.
- **A generation action is an ordinary kernel-governed agent action, in full.** It clears the identical classification, precondition-clearing, context-assembly, precedence-engine, loop-guard, and budget mechanisms every other platform-layer agent action clears; no exemption and no parallel authority model exists for it.
- **A confirmed write re-clears security validation on the final, possibly-edited content, never the originally generated content alone**, and performs an ordinary construction, configuration, or entity-definition write through the already-existing mechanism, with no AI-origin exemption anywhere in that mechanism's own gate set.
- **A committed artifact carries no reference to the suggestion that proposed it; only the suggestion carries a forward reference to what its own confirmation produced.** This asymmetry is what keeps every already-confirmed artifact independent of the tooling, reasoned directly in ADR-056 rather than assumed from the map's own grade.
- **The tooling introduces no new construct kind, binding kind, action class, or entity-modeling primitive.** Every assistance kind is realized entirely against the closed vocabulary `01-application-construction-design.md` and `02-data-model-and-entity-design.md` already fix (§7).
- **This document mints no new stored schema of its own and no new audit-event type.** The one structure it owes `02-platform-data-model-design.md` is named, not designed, per §9.1; every fact this document's own mechanism produces reuses an already-existing event type (§10).
- **Everything in this document remains domain-neutral.** No construct, binding, field, relationship, or example in this document encodes the characteristics of any single domain; every illustration is stated in structural terms only.
