# Tenant Isolation and Access Control Design — AI ahaMatic

This document designs the concrete mechanism that makes **INV-01 (tenant isolation)** and **INV-02 (authorization before access)** hold at runtime, and realizes `02-governance-and-security/03-access-control-and-tenancy-model.md` as an enforcement model. It states **how** a tenant-scoped actor is prevented from seeing or affecting another tenant's data, how a request's tenant context is resolved once and bound for its whole execution, how a bridge's grant is issued and verified, and how least privilege is enforced across every actor class the specification now recognizes. It does not re-derive the tenant boundary, the steward plane, the role-and-permission matrix, or the forbidden-crossing rule — each is fixed and cited, never restated.

This is a Design-phase artifact realizing `02-governance-and-security/03-access-control-and-tenancy-model.md` in full, and closing three named handovers from documents already written: `platform-data-model-design.md` §12 (registry scoping, bridge-grant issuance and verification, boundary proof — none of which that document designs); `architecture-realization-design.md` §4.1 row 2, §4.3, §7.1 (the Partial-coverage runtime portion of cross-tenant-instance prevention); and `invariant-enforcement-design.md` §8 (the mechanism underneath the INV-01/INV-02 check locations that document already fixes, named there as "the sharpest boundary this document holds"). It reads `platform-data-model-design.md` §3–§4 and `technology-stack-design.md` §14.5, §14.7 as already-fixed structure and decision, and cites rather than re-derives them.

**Verified versus reasoned (`PROCESS.md` §12.3).** Every claim in this document is **reasoned** — from the cited specification, the cited upstream design documents, and the structural properties of the schema and datastore `platform-data-model-design.md` and `technology-stack-design.md` already fix. No claim rests on a time-sensitive ecosystem, tooling-maintenance, or adoption fact.

## 1. Purpose and Reading Order

This document answers six questions:

- **How access to the shared platform-global registry (`platform.tenants`, `platform.applications`) is scoped**, so a tenant-scoped actor's query never returns more than its own row (§3).
- **How a request's tenant/application context is resolved once, at the point of entry, and bound for the whole of that request's execution** — the runtime portion `architecture-realization-design.md` §4.3 hands here (§4).
- **How isolation is proven at the boundary rather than assumed** — the connection-level enforcement and the mandatory self-verification underneath the check locations `invariant-enforcement-design.md` §5.1 already fixes for INV-01 and INV-02 (§5).
- **How least privilege is enforced across all five actor classes the specification now recognizes** — builder, extender, end user, the autonomous platform-operating agent, and the external contract consumer (§6).
- **How a bridge's grant is issued, scoped, and verified**, and how cross-tenant access is rendered structurally impossible rather than merely forbidden by policy (§7–§8).
- **Whether the partitioning shape or the exclusion of native row-level security should be reconsidered on an isolation-strength finding, distinct from the portability finding that excluded it originally** (§9).

It is structured as a pyramid: the isolation mechanism at the data boundary first, then runtime context resolution, then the invariant-check mechanisms that boundary supports, then role-and-permission enforcement, then bridging and grants, then the cross-tenant-impossibility synthesis, then the row-level-security reconsideration, then the design decision record, then the boundaries and handovers, then precedence and binding rules.

## 3. Scoping the Shared Registry: `platform.tenants` and `platform.applications`

`platform-data-model-design.md` §4.1 states the problem precisely: the registry "necessarily hold[s] every tenant's row, because the platform must route a request to the correct schema before it can act," and hands this document the job of ensuring a tenant-scoped actor's access to it "never returns more than that actor's own row." This section designs that mechanism.

### 3.1 The Registry Accessor: the Sole Read Path

**No component outside the Isolation and Trust module (`architecture-realization-design.md` §3.1) ever issues a raw query against `platform.tenants` or `platform.applications`.** Every read of either table passes through one function, the **Registry Accessor**, whose signature accepts only an **already-authenticated actor identity** (`platform_user_id`, established by `authentication-and-identity-design.md` before this function is ever called) — never a client-supplied `tenant_id` or `application_id` used to widen a result set.

The Registry Accessor's query shape is fixed and is not parameterized by anything the caller controls beyond the following:

| Actor's Standing | What the Registry Accessor Returns | Why It Cannot Return More |
|---|---|---|
| Holds one or more `tenant_users` bindings (builder personas, extender) | Exactly the `platform.tenants` and `platform.applications` rows referenced by that actor's own binding rows (`tenant_<id>.tenant_users`, joined against `platform.applications.tenant_id`). | The query's `WHERE` clause is bound to the actor's own binding rows, resolved server-side from the authenticated identity — never to a `tenant_id` the caller supplies. A caller that names a different tenant in a request parameter is not denied by a check; there is no code path in the Registry Accessor that accepts such a parameter as a filter-widening input at all. |
| Holds a `platform.steward_role_bindings` row (one of the four steward roles, §6.1 below) | The full `platform.tenants` and `platform.applications` tables — the visibility `01-business-and-ux/04-personas-and-roles.md` §5 and `02-governance-and-security/03-access-control-and-tenancy-model.md` §4 require for governing "above all tenants." | This is the one legitimate case where registry-wide visibility is correct, not a leak — governance requires seeing that tenants exist to admit, suspend, or govern them. The boundary this visibility must never cross is stated in §3.2. |
| Holds neither | Nothing. | Deny-by-default (`02-governance-and-security/01-system-invariants.md` §3): an actor with no binding and no steward role has no path to any registry row, including its own — because it has none. |
| An actor requests narrowing to a specific application within its own tenant's scope (e.g., "act as application X") | The named application's row, but **only** after the Registry Accessor confirms that application's `tenant_id` matches one the actor's own binding already covers. | This is a narrowing selection over an already-established result set, never a widening one — the actor cannot use this parameter to reach an application outside its own binding's tenant. |

### 3.2 What Steward Visibility Does Not Confer

A steward role's registry-wide read access is bounded by the same rule `02-governance-and-security/03-access-control-and-tenancy-model.md` §4 and §7 already fix: **the steward governs the boundary without entering it.** Concretely, holding a `platform.steward_role_bindings` row grants the Registry Accessor's registry-wide read path (§3.1) and nothing else:

- It confers **no** connection-scoping grant (§5.1) to any `tenant_<id>` or `tenant_<id>_app_<id>` schema. A steward role can see that a tenant and its applications exist, admit or suspend them, and observe the registry-level facts §3.1's fixed catalog tables hold — it cannot open a connection scoped to read a tenant's own `tenant_users`, `application_bridges`, or any application's builder-defined data, because no such grant exists (§5.1's connection-scoping mechanism grants schema access per tenant/application binding, and a steward role holds none).
- Where a specific steward action genuinely requires entering a tenant's own schema (an operational necessity, not a routine one — for example, executing an approved, human-authorized data-recovery action), that action requires a distinct, explicitly-issued grant scoped to exactly that tenant and that action, issued and revoked around the operation — it is never a standing property of holding a steward role. Designing that distinct grant's issuance mechanism, and the human-in-the-loop protocol that authorizes it, belongs to `05-meta-operations/04-human-in-the-loop-protocol.md`; this document states only that no steward role holds it by default.

### 3.3 Why This Is Verifiable

The claim "a tenant-scoped actor's query never returns more than its own row" is checkable two ways: (1) the Registry Accessor's own source has exactly one code path per row of §3.1's table, none of which accepts a caller-supplied identifier as a widening filter — reviewable directly, and testable by a fixed suite of adversarial inputs (a request naming a foreign `tenant_id` must return the same result as a request naming none); (2) no other module in `components/*` imports the platform-schema data-access module for `platform.tenants`/`platform.applications` at all — enforced by the same import-boundary mechanism `architecture-realization-design.md` §4.2 already builds, extended with one additional rule this document owns (§5.3).

## 4. Runtime Tenant-Context Resolution

`architecture-realization-design.md` §4.1 row 2 proves, at build time, that no component module hardcodes a tenant identifier and no per-tenant code variant exists — and explicitly rates itself only **Partial**, handing "the runtime portion — correct per-request tenant resolution and enforcement" here (§4.3, §7.1). This section designs that runtime portion.

### 4.1 The Context Resolution Point

Every request that reaches the platform core passes through exactly one **Context Resolution Point**, inside the Isolation and Trust module, before any other component module's handler runs. At that point:

1. The request's already-established actor identity (`authentication-and-identity-design.md`'s output — this document consumes it, never establishes it) is passed to the Registry Accessor (§3.1).
2. The Registry Accessor returns the actor's tenant binding(s), any application-level narrowing (`tenant_<id>.tenant_user_application_scope`), and the resolved `schema_name` (`platform.applications.schema_name`) the request's action targets.
3. These are assembled into one **Resolved Request Context** object: `{ platform_user_id, actor_class, tenant_id, application_id (where scoped), schema_name (where resolved), role, permission scope, grant reference (where the actor is a client, extender, or external contract consumer — §6, §7) }`.
4. The object is **frozen at creation** — no subsequent step in the request's execution may mutate any field of it.

### 4.2 Binding Every Subsequent Operation to the Resolved Context

The Resolved Request Context is threaded through the request's entire execution via the runtime's own request-scoped storage mechanism (under the V1.0 default stack, Node.js's `AsyncLocalStorage`; under a different candidate stack, the equivalent request-scoped or ambient-context primitive, per `architecture-realization-design.md` §9's stack-portability convention — the property is stack-neutral, only the primitive that carries it is stack-bound).

The binding is structural, not conventional, for one reason: **the function that acquires a database connection (§5.1) accepts only the Resolved Request Context object as its input — never a raw tenant or application identifier a caller could supply independently.** A component module that wants to read or write tenant- or application-scoped data has no function available to it that takes an identifier string; it has only one that takes the context object already resolved for the request it is handling. This closes the gap `architecture-realization-design.md` §4.3 names: there is no code path by which a request's execution could name a tenant or application other than the one resolved for it at entry, because every downstream call is parameterized by the frozen object, not by a value any later step could substitute.

### 4.3 No Mid-Request Context Switch

Because the Resolved Request Context is frozen at creation (§4.1) and every downstream call is parameterized by that same object (§4.2), no operation within one request's execution can resolve against a different tenant or application than the one established at entry — including for a multi-step operation (an API-mediated bridge call, §7.1) that in effect asks the platform to act "as" a second application. Where such a call is legitimate, it is modeled as a **new**, independently-resolved request against the second application's own contract (§7.1), carrying its own Resolved Request Context — never as a mutation of the first request's context.

## 5. Connection-Scoped Isolation and Boundary Self-Verification

This section is the mechanism `invariant-enforcement-design.md` §8 names as its "sharpest boundary": that document fixes that INV-01 and INV-02 are checked, where each check runs, and what a violation looks like (§5.1 of that document) — it explicitly does not design how isolation is verified at the data boundary or how a bridge's grant is verified. This section supplies that mechanism, without restating the check locations already fixed.

### 5.1 Structural Access: Schema-Scoped Database Privilege, Not a Predicate

`technology-stack-design.md` §14.5 excludes native row-level security on portability grounds and requires isolation to be "structural rather than predicate-based." This document realizes that requirement as **database-privilege grants scoped to exactly one schema**, using ordinary `GRANT`/`REVOKE` — a mechanism every candidate engine (PostgreSQL, MySQL/MariaDB, SQL Server) supports natively, unlike RLS.

- **One database role per application schema**, created at the same time as the application's schema (`tenant_<id>_app_<id>`, `platform-data-model-design.md` §3.3), granted `USAGE` and the necessary table privileges on **that schema only**. **One database role per tenant schema** (`tenant_<id>`), granted identically, scoped to that tenant's own schema only.
- **No schema is granted to a role by default.** Every candidate engine denies access to an unnamed schema unless a grant exists; this document adds no new deny-by-default rule, it relies on the one every candidate engine already enforces at the privilege layer. Provisioning a new tenant or application (§11's onboarding case) is exactly one additional `GRANT` statement, issued once, at creation — there is no companion `REVOKE` step to remember for every other schema, because no other schema was ever granted.
- **The Context Resolution Point's connection-acquisition step (§4.2) switches the active database role to the one matching the Resolved Request Context's `schema_name`** before any query in that request executes (`SET ROLE`, or the equivalent contained-schema/contained-database mechanism under MySQL or SQL Server). A query issued under this connection has no privilege to name, address, or read any schema other than the one the Resolved Request Context resolved — not because a predicate filters it out, but because the privilege to open that path does not exist for this connection.

This is materially stronger than the predicate-based isolation `technology-stack-design.md` §14.5 rejected ("a `tenant_id` predicate the abstraction layer is trusted to append on every query is closer to assumed than verified"): a missing `WHERE` clause in a shared-schema design is a silent, in-band failure; a missing schema grant in this design means the connection has no privilege to run the query at all, and the query fails loudly, before any row is returned.

### 5.2 The Self-Verification Read: Proving the Boundary, Not Assuming It

`02-governance-and-security/03-access-control-and-tenancy-model.md` §3 requires isolation to be "verified at the tenant boundary itself, not assumed from the absence of an observed breach." Connection-scoping (§5.1) makes a crossing structurally hard to reach; this section adds the check that would catch it if some defect in the connection-acquisition step ever mis-scoped a connection regardless.

- **At the application level:** immediately after the connection role is switched (§5.1), the mechanism performs one mandatory read of `<schema>.application_metadata` (`platform-data-model-design.md` §3.3 — the table that exists precisely "so any query executed inside the schema can independently confirm which application and tenant it belongs to, without trusting an external join") and compares its `application_id`/`tenant_id` against the Resolved Request Context. **A mismatch is an INV-01 violation, full stop** — the request halts before any further query executes, per the halt behavior `invariant-enforcement-design.md` §3.3, §5.1 already fixes; this document supplies the read that feeds that check, not a second check location.
- **At the tenant level** (a request whose scope is tenant-wide, not narrowed to one application — e.g., an access administrator's own action), the equivalent check reads the connection's own resolved schema name via the database driver's standard schema-introspection call (`current_schema()` under PostgreSQL; the equivalent under MySQL or SQL Server) and compares it against `tenant_<Resolved Request Context.tenant_id>`. This uses a capability every candidate engine already exposes and requires no new table — consistent with reading `platform-data-model-design.md` §3, not restating or inventing structure inside it.
- **This read is mandatory and unconditional**, run on every request that resolves an application- or tenant-scoped connection, never only when a defect is suspected. It is what makes "verified at the boundary" concrete rather than aspirational: the boundary is checked by executing a read against the schema's own self-description and comparing it to what was resolved, every time, not inferred from the connection-scoping mechanism's own correctness.

### 5.3 The One Additional Import-Boundary Rule This Document Owns

`architecture-realization-design.md` §4.1 fixes five import-boundary rules, none scoped to registry-table access specifically. This document adds a sixth, run by the same tool (`architecture-realization-design.md` §4.2 — dependency-cruiser or the ESLint boundary-rule set under the V1.0 default stack, or the stated equivalent under a different stack), owned here because it is specific to this document's own concern:

**No module outside `components/isolation-and-trust` may import the platform-schema data-access module for `platform.tenants` or `platform.applications`.** Full coverage: every other module receives only the Resolved Request Context object (§4.1) or the connection already scoped by it (§5.1) — never a handle capable of querying the registry tables directly. This closes, at build time, the one remaining path by which a defect elsewhere in the codebase could bypass the Registry Accessor (§3.1) rather than merely failing to call it correctly.

## 6. Least-Privilege Enforcement Across Five Actor Classes

`02-governance-and-security/03-access-control-and-tenancy-model.md` §4–§8 fixes the steward plane, the role-and-permission matrix, and least privilege as the standing posture. The specification now recognizes **five** actor classes; this section states, for each, where its grant lives and how the mechanisms of §3–§5 enforce it.

| Actor Class | Where the Grant Lives (`platform-data-model-design.md` §5) | How §3–§5's Mechanism Enforces Its Least-Privilege Boundary |
|---|---|---|
| **Builder personas** (tenant owner, access administrator, application builder, operator, publisher) | `tenant_<id>.tenant_users`, narrowed by `tenant_<id>.tenant_user_application_scope` where the role is application-scoped. | The Resolved Request Context (§4.1) carries exactly the scope (`tenant-wide` or the named applications) the binding row states; the connection-scoping mechanism (§5.1) grants no schema beyond that scope. A tenant owner or access administrator (always tenant-wide, per the tenancy model §6) is granted the tenant schema and, where an action targets one application, that application's schema — never a second tenant's. |
| **Extender** | `tenant_<id>.tenant_users`, scoped by the grant its extension represents. | "Bound entirely by its own grant" (`02-governance-and-security/03-access-control-and-tenancy-model.md` §5) is enforced identically to a builder persona's application-scoped grant (row above) — the Resolved Request Context's permission scope is drawn from the extension's own binding, never from the platform primitive it extends. `architecture-realization-design.md` §4.1 row 4 (no core dependency on a specific extension) is unaffected and orthogonal — that rule protects generality; this row protects tenant/application scope — and holds regardless of the Extender authorship question that document's §10 leaves open. |
| **End-user personas** (authenticated end user, public consumer, end-user administrator) | Not a platform structure (`platform-data-model-design.md` §5) — builder-defined content, recognized through the generic access primitive (C-03). | The Context Resolution Point (§4) resolves the **application's own tenant and schema** identically to any other request against that application; the end-user identity and its permission content are `data-model-and-entity-design.md`'s and `authentication-and-identity-design.md`'s to define, but the connection they act through is scoped by this document's mechanism exactly as any other actor's is — end-user scope is always exactly one application (`02-governance-and-security/03-access-control-and-tenancy-model.md` §6), and no mechanism in §3–§5 grants a connection wider than the one application resolved for the request. |
| **Autonomous platform-operating agent** (`05-meta-operations/01-agent-operating-charter.md`) | `platform.steward_role_bindings`, identically to a human holding the same steward role — the agent "operates the platform's own lifecycle... a role entirely internal to the platform" (`01-business-and-ux/04-personas-and-roles.md` §5), not a tenant-scoped actor. | Governed by exactly §3.1's steward row and §3.2's boundary: registry-wide visibility for governance, no standing connection-scoping grant to any tenant's or application's own schema. "The agent's authority never extends to observing, affecting, or disclosing one tenant's state to another" (`05-meta-operations/01-agent-operating-charter.md` §2) is the same boundary §3.2 already states for any steward role — this document creates no separate, weaker, or stronger enforcement path for autonomous versus human-directed steward action; only the audit trail (owned by `audit-and-traceability-design.md`) distinguishes actor type, never this document's grant mechanism. |
| **External contract consumer** (T70, 2026-08-03) | A client grant within the meaning of `02-governance-and-security/03-access-control-and-tenancy-model.md` §6 — "the scoping identity of an external caller... authorized to act against platform capabilities on a tenant's behalf" — issued by a tenant, scoped to whatever the tenant grants and never wider. | Resolved identically to any other client-scoped grant (§7.2's grant-verification mechanism): the Resolved Request Context carries the grant's own scope, drawn from the tenant's own permissions and never exceeding them (`02-governance-and-security/03-access-control-and-tenancy-model.md` §6, "a client's grant is always a subset of its tenant's own"). It holds no implicit authority and no exemption from §3–§5's connection-scoping or self-verification mechanism by virtue of acting externally or autonomously — the mechanism does not distinguish a human-directed external caller from an autonomous one; both are bound by the same issued grant, checked the same way. |

**No authority is held by default, for any of the five.** Every row above resolves to an explicit grant record the Registry Accessor or the tenant-scoped binding tables already hold; where no such record exists for a given actor and a given action, the Context Resolution Point (§4.1) resolves no scope, the connection-scoping mechanism (§5.1) grants no schema, and the action is refused — the same deny-by-default posture stated once here rather than restated per row.

## 7. Bridging: Grant Issuance and Verification

`platform-data-model-design.md` §4.2 fixes two bridging mechanisms and the `application_bridges` record; it hands this document how a bridge's grant is actually issued and verified. Both mechanisms stay inside one tenant's own boundary — neither is available, or made available by this document, across tenants (§8).

### 7.1 API-Mediated Bridge

No schema-level change occurs. Application A's client identity calls application B's own published contract exactly as any other consumer would (`api-contract-design.md`'s contract, C-12).

- **Grant issuance.** When a tenant creates a `tenant_<id>.application_bridges` row naming applications A and B with `bridge_type = api-mediated`, this document's mechanism issues no new database privilege — the call is authorized through the same INV-02 decision point every request passes (§4.1), with one addition: **the authorization decision for a cross-application call within one tenant additionally checks that an active `application_bridges` row exists naming exactly this pair, before the call proceeds.** Absent that row, the call is refused identically to a call from an entirely unrelated, ungranted client — there is no special "same-tenant" exemption that bypasses this check.
- **Grant verification.** The check reads: (a) both applications' `tenant_id` values from the registry (§3.1) are equal — establishing the call is same-tenant, never cross-tenant; (b) an active `application_bridges` row exists naming this exact pair; (c) the row's `bridge_type` authorizes the specific action requested. All three conditions are evaluated before application B's handler is invoked, at the same authorization decision point INV-02 already fixes (`invariant-enforcement-design.md` §5.1) — this is the verification mechanism underneath that check, not a second check location.

### 7.2 Schema-Level Bridge

A direct database-level grant between two application schemas, available only because both already sit inside the same tenant's connection and credential scope (`platform-data-model-design.md` §4.2).

- **Grant issuance.** When a tenant creates a `tenant_<id>.application_bridges` row with `bridge_type = schema-level`, the platform-core service, in the **same database transaction** as the row's insertion, issues the corresponding `GRANT SELECT` (or the narrower grant the bridge's declared access scope requires) on the named tables or a view of application A's schema, to the database role of application B's schema (§5.1). Because both statements commit atomically, no state exists in which the bridge row is recorded without the grant, or the grant exists without the recorded row.
- **Grant verification.** Removing the `application_bridges` row is, symmetrically, a transaction that both deletes the row and issues the corresponding `REVOKE` in the same commit. No separate reconciliation step is needed, and none exists, because the row and the grant are never allowed to diverge — the database's own transactional guarantee is the verification mechanism, not a periodic audit that checks the two agree.
- **What makes this impossible across a tenant boundary.** The transaction that issues the `GRANT` is only ever invoked from the same code path that creates the `application_bridges` row, and that row's own foreign keys are constrained to two applications sharing one `tenant_id` (`platform-data-model-design.md` §4.1) — there is no code path by which this document's grant-issuance mechanism could be invoked with two applications of different tenants, because the record that triggers it cannot itself name that pair.

## 8. Cross-Tenant Access as Structurally Impossible

`02-governance-and-security/03-access-control-and-tenancy-model.md` §7 requires cross-tenant access to be framed as forbidden absolutely, and `platform-data-model-design.md` §4 requires the two bridging mechanisms to stay inside one tenant's boundary. This section states why a crossing is not merely disallowed by policy but has no structural path to occur, synthesizing three independent facts established above — **all three would have to fail simultaneously**, not just one, for a crossing to succeed:

1. **No naming path exists.** `platform-data-model-design.md` §4.1 already establishes that no table, view, or foreign key in the schema can name two different tenants together. Even an actor that somehow obtained a second tenant's schema name has no query construct through which to address it from this fact alone.
2. **No grant path exists.** Even given a name, §5.1's connection-scoping mechanism grants a connection privilege on exactly the schemas the Resolved Request Context (§4.1) resolves for the current actor and request — never on a schema belonging to a tenant the actor holds no binding in. §7.2 shows the one case where a cross-schema grant is created at all (the schema-level bridge) is itself incapable of naming two tenants, because the record that triggers it cannot.
3. **No silent path exists.** Even if a defect in §5.1's provisioning ever mis-scoped a connection despite (1) and (2), §5.2's mandatory, unconditional self-verification read would detect the mismatch against the Resolved Request Context and halt the request as an INV-01 violation before any cross-tenant data is returned — converting what would otherwise be a silent breach into a blocked, escalated, auditable event.

**No actor class of §6, and no bridging mechanism of §7, is exempt from all three.** The marketplace (`02-governance-and-security/03-access-control-and-tenancy-model.md` §7) is the sole mediated builder-to-builder interaction, and it is not a fourth path around these facts: a marketplace transaction exchanges a published artifact — an object one tenant obtains, not a grant that lets it reach into another tenant's own schema, connection, or registry visibility. Nothing in §3–§7 provides such a grant, and none is added here.

## 9. The Row-Level-Security Reconsideration

`platform-data-model-design.md` §12 explicitly authorizes this document to overturn the partitioning shape "on a scalability or enforcement finding" — distinct from `technology-stack-design.md` §14.5's exclusion of native row-level security, which was decided **on portability grounds only** ("MySQL/MariaDB has no native equivalent"). This section makes the isolation-strength assessment that exclusion never received.

**Finding: no reconsideration is warranted.** The mechanism designed in §3–§5 already achieves, structurally and portably, what RLS would add, and does so more strongly than RLS could for the case where RLS would actually apply:

- **RLS is a predicate-based mechanism that operates within one shared schema.** It has no application to the per-tenant and per-application schemas of `platform-data-model-design.md` §3.2–§3.3, because those are already separated at the schema level — a connection either has the privilege to address a schema or it does not (§5.1), which is a stronger, non-predicate guarantee than any row-filtering predicate could add on top of an already-separate namespace.
- **The one place RLS would genuinely apply — the shared `platform.tenants`/`platform.applications` tables — is exactly where §3's Registry Accessor mechanism already achieves RLS's row-filtering effect, portably.** A native RLS policy and the Registry Accessor's identity-scoped, deny-by-default query (§3.1) both return only the rows an actor's own binding covers; the Registry Accessor achieves this in ordinary application code, verifiable by direct code review and by a fixed adversarial test suite, on every candidate engine identically — where a native RLS policy's correctness would depend on an engine-specific feature (present differently in PostgreSQL and SQL Server, absent in MySQL/MariaDB) that this platform's portability obligation (`technology-stack-design.md` §2.5) requires it to avoid depending on regardless of isolation strength.
- **The self-verification read (§5.2) is a check RLS does not provide.** RLS enforces a filter; it does not itself prove, after the fact, that the filter was applied correctly for the connection in use. This document's mandatory read-and-compare against the schema's own self-description (or the connection's resolved schema name) is a distinct, additional guarantee neither the shape this document inherited nor RLS would supply on its own.

**Conclusion: the partitioning shape stands, and RLS's exclusion stands — now for an isolation-strength reason independently sufficient on its own, in addition to the portability reason `technology-stack-design.md` §14.5 already recorded.** Per the same discipline `invariant-enforcement-design.md` §7 applied when no genuine decision was owed: no ADR is recorded for *not* overturning the shape, because there is no decision here with a real alternative this document is choosing among — the mechanism of §3–§5 was the genuine decision, and it is recorded in full in §10.

### 10.1 ADR-018 — Tenant-Isolation Enforcement Mechanism: Connection-Scoped Structural Access, Registry-Scoped Identity Resolution, and Boundary Self-Verification

- **Status:** Approved (this ticket; no upstream approval gate applies, per `technology-stack-design.md` §9's convention that a design ticket's own decisions do not require separate lead sign-off under `DECISIONS.md` D-16).
- **The question it answers:** Given schema-per-application partitioning nested under a per-tenant level (ADR-004) and the specification's requirement that isolation be verified at the boundary rather than assumed, what concrete mechanism makes a tenant-scoped actor's access to the shared registry return only its own row, makes a connection unable to address a schema outside its resolved scope, and proves that boundary at runtime rather than assuming it — and does an isolation-strength finding (distinct from ADR-004's portability finding) warrant reconsidering the exclusion of native row-level security?
- **Cost to reverse:** **Brutal** for the core mechanism — the connection-scoping and registry-accessor pattern is the enforcement layer every subsequent access to stored tenant and application data depends on; reversing it means re-securing every schema's access path, matching the grade `implementation-document-map.md` already assigns this document (`PROCESS.md` §12.1's most expensive rung). **Low** for the specific engine-level provisioning primitive (`SET ROLE` versus a contained-schema/contained-database equivalent) — swapping the provisioning mechanism for a different candidate engine changes tooling only, not the grant shape, the Registry Accessor's query discipline, or the self-verification read.
- **Upstream decisions assumed:** ADR-004 (`technology-stack-design.md` §14.7 — per-application schema partitioning, nested per-tenant, RLS excluded on portability grounds); `platform-data-model-design.md` §3–§4 (the schemas, registry, and bridge record this mechanism runs against); `architecture-realization-design.md` §4 (the import-boundary tool this document's one additional rule, §5.3, runs on) and §4.3, §7.1 (the runtime-resolution handover this ADR discharges); `invariant-enforcement-design.md` §5.1, §8 (the INV-01/INV-02 check locations this mechanism supplies the verification for).
- **Verified vs. reasoned:** Reasoned — the mechanism is derived directly from the cited specification's requirements (verified at the boundary, structural not predicate-based, portable across every candidate engine) and the structural properties of the datastore and schema already fixed; no time-sensitive ecosystem or tooling-maintenance claim is made.
- **Context:** Three upstream documents each explicitly handed this document a named, unresolved piece: `platform-data-model-design.md` §12 (registry scoping, bridge-grant issuance and verification, boundary proof); `architecture-realization-design.md` §4.3, §7.1 (the runtime portion of cross-tenant-instance prevention its own mechanism rates only Partial); `invariant-enforcement-design.md` §8 (the mechanism underneath INV-01/INV-02's already-fixed check locations, named there as this document's sharpest boundary). `platform-data-model-design.md` §12 additionally authorized reconsidering the partitioning shape on a scalability or enforcement finding, distinct from ADR-004's portability-only exclusion of RLS.
- **Decision:** (1) A Registry Accessor as the sole, identity-scoped read path to `platform.tenants`/`platform.applications` (§3); (2) a Context Resolution Point that resolves tenant/application context once per request into a frozen Resolved Request Context threaded through the request's entire execution via request-scoped storage (§4); (3) schema-scoped database-privilege grants, switched per request, as the structural access-control primitive — never a trusted predicate (§5.1); (4) a mandatory, unconditional self-verification read against each schema's own self-description (or the connection's resolved schema name) as the boundary proof (§5.2); (5) one additional import-boundary rule restricting registry-table access to the Isolation and Trust module (§5.3); (6) bridge-grant issuance and verification for both bridging mechanisms, atomic with the `application_bridges` record (§7); and (7) no reconsideration of the partitioning shape or the RLS exclusion — the mechanism above already exceeds RLS's isolation strength for the shared registry and is inapplicable in the already-separated per-tenant/per-application schemas (§9).
- **Alternatives considered:** *A trusted `tenant_id`/`application_id` predicate appended by the abstraction layer* — rejected; this is precisely the "assumed, not verified" failure mode `technology-stack-design.md` §14.5 already named, and this document's job was to design something stronger, not restate the rejected default. *Native row-level security on `platform.tenants`/`platform.applications` specifically* — rejected; unchanged on portability (absent in MySQL/MariaDB) and, newly assessed, not stronger than the Registry Accessor's identity-scoped, deny-by-default query, which is verifiable in application code and tests on every candidate engine identically rather than dependent on an engine-specific feature's correctness (§9). *Fully dynamic, per-request database credentials issued by an external secrets/KMS system, rotated per request* — rejected as disproportionate operational cost at the ~100-schema V1.0 figure (`DECISIONS.md` D-26); named as a candidate hardening for `scalability-availability-and-performance-design.md` to weigh if and when schema count approaches the NFR §5/§7 horizon `platform-data-model-design.md` §11 already sharpens, not a V1.0 requirement this document imposes now.
- **Consequences:** Binds every document that reads or writes tenant- or application-scoped data to route through the Resolved Request Context and the connection-scoping mechanism rather than inventing its own access path — named directly: `authentication-and-identity-design.md` (must supply the authenticated identity the Context Resolution Point consumes, and inherits INV-02's grant and session mechanics per `invariant-enforcement-design.md` §8); `data-model-and-entity-design.md` and `application-construction-design.md` (builder-defined entities and the construction surface are read and written only through a connection this mechanism has already scoped); `data-administration-design.md`, `cross-system-data-layer-design.md`, and `integration-and-extensibility-design.md` (each inherits this mechanism as the access path underneath its own derived or extension-facing surface); `scalability-availability-and-performance-design.md` (connection-pool design must accommodate one database role per schema at the ~100-schema V1.0 figure, and at whatever figure the NFR horizon eventually requires); `security-controls-design.md` (the Registry Accessor and connection-scoping mechanism are governed platform-core code, reviewed under the platform's own pipeline, not an untrusted surface). No downstream document may design a second tenant-scoping mechanism; each consumes this one.

## 13. Binding Rules

These rules hold for every element of this document and are subordinate to the specification and the charter.

- **No component outside the Isolation and Trust module ever queries `platform.tenants` or `platform.applications` directly.** Every access passes through the Registry Accessor, whose query shape accepts only an already-authenticated actor identity — never a client-supplied identifier used to widen a result set (§3.1); this rule is enforced both by the Registry Accessor's own fixed query shape and by the import-boundary rule of §5.3.
- **A steward role's registry-wide visibility confers no schema-connection grant to any tenant's or application's own data.** The steward governs the boundary without entering it (§3.2); any exceptional entry requires a distinct, explicitly-issued grant outside this document's standing mechanism.
- **Every request resolves its tenant/application context exactly once, at entry, into a frozen object bound to that request's entire execution.** No subsequent step may mutate it, and no downstream function accepts a raw tenant or application identifier as an alternative to it (§4).
- **Database access is scoped by schema-level privilege grants, switched per request, never by a trusted predicate.** No engine-native construct is used without an equivalent for every supported engine (`technology-stack-design.md` §14.5, §25), and no isolation guarantee in this document rests on an application-layer filter a caller could omit (§5.1).
- **Isolation is proven, not assumed, on every request that resolves a scoped connection.** The mandatory self-verification read of §5.2 runs unconditionally; a mismatch is an INV-01 violation that halts before any further query executes.
- **All five actor classes — builder, extender, end user, the autonomous platform-operating agent, and the external contract consumer — are bound by the same mechanism.** No actor class holds an exemption from connection-scoping, self-verification, or the deny-by-default posture of §6 by virtue of acting autonomously, externally, or on a grant rather than a persona-defined role.
- **A bridge's grant is issued and verified atomically with its record, for both bridging mechanisms, and neither mechanism can name two different tenants.** The API-mediated path checks the bridge record at the same INV-02 decision point every request passes (§7.1); the schema-level path issues and revokes its database grant in the same transaction as the record itself (§7.2).
- **Cross-tenant access requires all three of §8's structural facts to fail at once, not merely one.** No naming path, no grant path, and no silent, unverified path exist simultaneously for any actor class or bridging mechanism this document governs.
- **The partitioning shape and the RLS exclusion stand, affirmed on an independent isolation-strength basis (§9).** No ADR is recorded for this non-decision, exactly as the discipline `invariant-enforcement-design.md` §7 already set when no genuine alternative was being chosen among.
- **This document records exactly one ADR.** ADR-018 (§10) is the genuine, independent decision this document makes; every other design choice above realizes a location, structure, or boundary the cited specification and the three upstream design documents already fix.
