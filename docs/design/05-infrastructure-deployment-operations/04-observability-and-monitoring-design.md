## 1. Purpose and Reading Order

This document answers six questions:

- **What concrete instrumentation realizes the required metrics, logs, and traces**, against the runtime's own already-fixed request-resolution, check, and dispatch points (§3).
- **How a runtime signal becomes an alert, and how its severity is attached**, without minting a new number or a new scale (§4).
- **How alerting binds differently across the environment tiers**, without a tier branch anywhere in the evaluation mechanism itself (§5).
- **What signals and thresholds may trigger bounded self-correction or a rollback**, stated as an input handed to the mechanisms that carry either out, never as those mechanisms themselves (§6–§7).
- **How the scalability document's named instrumentation obligation is discharged concretely**, correcting its own citation slip along the way (§8).
- **Where an observability signal stops and an audit event begins, and where a guardrail metric stops and an invariant or a gate begins** — the two distinctions this document must never let collapse (§9–§10).

It is structured as a pyramid: first the signal types themselves as concrete instrumentation (§3), then the alert and severity mechanism that gives a signal its urgency (§4), then how that urgency binds per tier (§5), then the reactions a signal may trigger within bounded autonomy (§6) and the signals beyond that bound (§7), then the named instrumentation obligation discharged (§8), then the two load-bearing distinctions (§9–§10), then the built-versus-platform boundary (§11), then the storage check (§12), evidence (§13), the design decision (§14), and the closing boundaries, precedence, and binding rules (§15–§17).

## 3. Required Metrics, Logs, and Traces — Realized as Concrete Instrumentation

Spec §4 fixes that the health of every structural component and every guardrail-layer guarantee must be determinable from emitted signals, expressed domain-neutrally. This section states the concrete instrumentation, against the runtime's own already-fixed structure, that makes that true.

### 3.1 The Runtime Is the Primary Signal Source — Completing the Pair

`01-application-runtime-and-lifecycle-design.md` §9.3 states its own side of this boundary: *"This document's mechanism — every request §3 resolves, every check §4–§5 clear or refuse, every audit event §10 composes with — is a source of the signals that document will measure, alert on, and feed to self-correction; this document does not itself define what is measured, what threshold triggers an alert, or what signal mandates escalation."* This document is the other side of that pair: every point that document names — the Operation component's request resolution (`components/operation`, cited by that document's §3.1); the access, structural, and behavioral resolution steps of Surface materialization (§4 there); the access-check, behavioral-resolution, and effect-dispatch steps of the Construct Invocation Point (§5 there); and the composition points where an invocation's effect reaches the Entity Access Gateway, the process engine, the Extension Invocation Point, or the Connector Resolver (§5.1 there) — is a concrete instrumentation point this document requires be emitted from, at the moment each step executes, never derived after the fact from a different signal.

### 3.2 Metrics

| Instrumentation Point | Concrete Metric | Grounded In |
|---|---|---|
| The Operation component's own request handling, per replica | Request latency (matched to the percentile windows `06-non-functional-requirements.md` §4 fixes), throughput, and error rate, tagged by which contract operation and which construct kind (Surface or Command) the request resolved to. | `01-application-runtime-and-lifecycle-design.md` §3, §9.3; `06-non-functional-requirements.md` §4 |
| Every access check, behavioral-resolution step, and Entity Access Gateway call the runtime issues (§4.1, §5.1 of that document) | A pass/refuse count, tagged by which of the Gateway's four checks was exercised — never the content of what was checked, only that a check ran and its outcome. | `01-application-runtime-and-lifecycle-design.md` §4.1, §5.1 |
| The extension-invocation and connector-dispatch points (§5.1 of that document) | Invocation count, duration against the synchronous and asynchronous ceilings (`06-non-functional-requirements.md` §4, §8), and a bounded-pool saturation gauge, per `04-scalability-availability-and-performance-design.md` §3.5's extension-confinement bulkhead. | `01-application-runtime-and-lifecycle-design.md` §5.1; `04-scalability-availability-and-performance-design.md` §3.5 |
| Every runtime invariant, guardrail-metric, and non-functional target this document's alert mechanism keys to (§4 below) | A current-value gauge per target, refreshed on the same window the target's own definition uses (a rolling 24-hour window for §7 targets, a monthly window for §6's availability floor, a point-in-time gauge for a guardrail metric's own nonzero-or-zero state). | `06-non-functional-requirements.md` §4–§9; `01-business-and-ux/06-value-proposition-and-success-metrics.md` §5 |
| Resource use per replica (the scale-out/scale-in decision inputs) | Per-replica CPU/memory utilization, in-flight request concurrency or queue depth, and connection-pool checkout-wait time or saturation — the three signals `04-scalability-availability-and-performance-design.md` §3.2 names as scaling decision inputs, instrumented here as the metrics that mechanism consumes, without this document fixing the operationally-tuned threshold at which each fires (that document's own §3.2 reservation, unaltered). | `04-scalability-availability-and-performance-design.md` §3.2 |

### 3.3 Logs

Every non-happy-path outcome the runtime's own mechanism already produces is emitted as a structured, diagnostic log entry at the point it occurs — never reconstructed after the fact from a metric alone:

- **Every refusal, halt, or held state** the runtime composes with — an access-check refusal (INV-02), a Region Boundary Check refusal, transfer, or held state (INV-07), an Entity Access Gateway refusal at any of its four checks — captured with what was inspected and the outcome, at the identical point `01-application-runtime-and-lifecycle-design.md` §10 already names as producing the corresponding audit event, so the log and the audit event describe the same occurrence without one substituting for the other (§9 below states this boundary explicitly).
- **Every scale-out, scale-in, and replica-replacement event** `04-scalability-availability-and-performance-design.md` §3.2–§3.3 fixes, captured with the triggering signal and the resulting replica count.
- **Every flaky-test resolution outcome that reaches a production-adjacent tier** — not a new obligation this document invents, but the runtime-visible continuation of the pre-deploy record `03-testing-and-quality-gates-design.md` §8 already fixes, logged here only where its own effect (a blocked promotion) is itself a runtime-observable event at the tier boundary (§5 below).

### 3.4 Traces

A trace identifier is assigned at the point a request first reaches the Operation component (`01-application-runtime-and-lifecycle-design.md` §3.1) and is propagated, unbroken, across every boundary crossing that request's own handling makes: the Authentication Gate and Context Resolution Point composition (§3.2 there), the Entity Access Gateway (§4.1, §5.1), and, where the request's effect dispatches further, the process engine, the Extension Invocation Point, or the Connector Resolver (§5.1). This is sufficient, per spec §4's own trace requirement, to locate where a fault, a latency breach, or a boundary crossing occurred, because every point a fault or a breach could occur at is a point this section already instruments with the identifier that ties it back to the originating request.

### 3.5 What Binds Every Signal Type, Realized

- **Every consequential behavior instrumented above is tagged, at definition time, to the guarantee it bears on** — an invariant, a guardrail metric, a non-functional target, or none — the mechanism §4.1 below reads to attach severity without computing it independently.
- **No secret and no unredacted sensitive data ever appears in a signal.** Every log entry §3.3 defines is a structured-logging-writer emission, and passes through the identical emission-boundary redaction filter `08-audit-and-traceability-design.md` §4.3 already cites at `04-security-controls-design.md` §2.2 for that same channel before it is written; this document adds no new redaction mechanism and opens no channel beyond the ones that filter already names. Every metric (§3.2) and trace span (§3.4) carries only the categorical tags and numeric values those sections define — an operation name, a construct kind, a check identifier, a duration, a count — never free-text or personal-data-shaped content; no field in this document's own metric or trace definitions is capable of carrying a secret or personal data in the first place, the identical by-construction argument `08-audit-and-traceability-design.md` §7 already makes for its own actor and target references being "opaque identifiers only, by construction."
- **Every signal is scoped to one tenant and one region.** Because every instrumentation point in §3.2–§3.4 fires from inside the runtime's own request handling — which never resolves more than one tenant or one application per request (`01-application-runtime-and-lifecycle-design.md` §3.2, §8.2) — a signal this document instruments is structurally scoped to that same single tenant and region by construction; an aggregate metric (a per-replica gauge, a platform-wide catalog-count) is computed only over values that carry no tenant-identifying content, never by summing tenant-scoped values into a shape from which one tenant's contribution could be isolated.
- **No new signal class is introduced.** Every instrumentation point above realizes one of spec §3's own four concepts — a metric, a log, a trace, or a health signal composed from them — and this document adds none beyond that closed set.
- **No signal in this document bears on the open import-boundary question `BACKLOG.md` §1u records.** That entry concerns a static, source-graph property — whether a module outside `components/isolation-and-trust` imports the platform-schema data-access module for `platform.tenants` or `platform.applications` — checked at build time by the dependency-direction mechanism (`03-architecture-realization-design.md` §4.1), never by a runtime-observed metric, log, or trace. None of §3's instrumentation points is a candidate for detecting it, because a compliant and a non-compliant import produce identical runtime behavior from this document's own vantage point; this document neither resolves nor obscures that open item, and states only that it has none of its own to contribute.

## 4. Alert Thresholds and Runtime Signal Severity — the Concrete Mechanism

Spec §5 fixes that an alert threshold is keyed to a value another document already owns, and that severity is set by the guarantee a signal bears on, never computed independently. This section states the mechanism that makes both true without inventing a number or a scale.

### 4.1 Severity Attribution as a Fixed Tag, Never a Runtime Inference

Every metric, log-emission point, and trace span defined in §3 carries, as part of its own definition, a `severity_source` tag identifying exactly which already-owned instrument its measurement is the runtime form of: an invariant identifier (INV-01 through INV-09, `02-governance-and-security/01-system-invariants.md` §4), a guardrail-metric identifier (`01-business-and-ux/06-value-proposition-and-success-metrics.md` §5), a vulnerability class (`02-governance-and-security/02-security-policy.md` §6), a non-functional-target identifier (`06-non-functional-requirements.md` §4–§10), an anti-metric identifier (`01-business-and-ux/06-value-proposition-and-success-metrics.md` §6), or none (a monitoring-gap-only signal, §7 below). The tag is set once, at the point in §3 the signal is defined — never recomputed at evaluation time, and never inferred from the magnitude of a breach.

At evaluation time, the alert-evaluation mechanism reads this tag and attaches exactly the severity spec §5.2's own table already fixes for that class — Critical for an invariant tag, at minimum High (Critical where the invariant it quantifies is itself violated) for a guardrail tag, the inherited Critical/High/Moderate/Low class for a vulnerability tag, the graded severity spec §5.2 fixes for a non-functional-target tag, and Warning for an anti-metric tag. This document adds no severity-computation logic beyond this lookup; **severity is never derived from how far or how long a threshold has been breached**, only from which guarantee the breached tag names — the concrete realization of spec §5.2's own rule that "severity is set by impact, never by convenience."

### 4.2 When a Signal Becomes an Alert, Realized

The alert-evaluation mechanism runs continuously over every metric §3.2 defines, comparing its current value against the target value it is tagged to — read directly from `06-non-functional-requirements.md` §4–§10's own configuration, `01-business-and-ux/06-value-proposition-and-success-metrics.md` §5's zero-tolerance guardrail floor, or `02-governance-and-security/01-system-invariants.md` §4's continuously-held property — over the rolling window that target's own definition already fixes (a 24-hour rolling window for §7's reliability targets, a monthly window for §6's availability floor). This document mints no new comparison rule beyond spec §5.1's own six: a breach of a non-functional target or its §11 regression condition, a nonzero guardrail measurement, an invariant breach, an active vulnerability, a rising anti-metric, and uncertainty about whether a threshold was crossed — each realized as exactly the comparison against the cited value, tagged and read as §4.1 states, never a comparison this document derives independently.

**The operationally-tuned scale-out/scale-in thresholds are not fixed here, on the identical reservation `04-scalability-availability-and-performance-design.md` §3.2 already states for its own three decision inputs.** This document instruments the three signals that mechanism names (§3.2 above) as metrics; the specific utilization percentage, queue-depth figure, and pool-saturation percentage at which each fires are operational tuning parameters validated against real load, not an architectural property, and remain unset by this document exactly as they remain unset by the document that names them.

## 5. Tier Applicability — Realized as Deploy-Time Configuration, Never a Branch

Spec §6 fixes that an invariant- or guardrail-quantifying signal binds at every tier, that the full threshold set binds Production in full, and that only non-invariant alerting may be relaxed at an earlier tier. This section states how that rule is realized without a tier-conditional branch anywhere in the evaluation mechanism itself.

- **Tier is externalized to deploy-time configuration, extending the identical discipline already fixed for component code.** `01-environment-and-configuration-design.md` §4.1 fixes that "no component module in `components/*` or `guardrail/` contains a hardcoded tier identifier, a per-tier subclass, or a per-tier branch," with tier supplied by an ordinary deploy-time configuration value injected at process start. This document extends that discipline to the alert-evaluation mechanism specifically: the mechanism that computes a severity tag (§4.1) and compares a metric against its threshold (§4.2) is identical code at every tier, and contains no branch keyed to which tier is running it. What differs per tier is a deploy-time configuration value the same infrastructure-as-code module set (`01-environment-and-configuration-design.md` §3.4) supplies alongside the `(tier, provider, region)` triple it already provisions: which non-invariant alerts route to an urgency SLA at all, and at what urgency, at Development and Staging.
- **Invariant- and guardrail-quantifying signals carry an identical configuration value at every tier.** Because §4.1's severity tag is fixed at signal-definition time and is not itself a tier-scoped configuration value, an invariant- or guardrail-tagged signal's severity and escalation disposition are the same configuration at Development, Staging, and Production alike — there is no tier-scoped override table for this class of signal to read from, which is what makes the "never relaxed at any tier" rule structural rather than a discipline the configuration author must separately remember.
- **A non-functional-tagged signal's urgency, and only its urgency, is the one tier-scoped configuration value.** Where a signal's tag is a non-functional target that is not itself the quantified form of an invariant or a guardrail metric, the deploy-time configuration for Development or Staging may set a lower urgency (a longer response-time SLA, a lower-priority routing destination) without that being a monitoring failure at that tier — realizing spec §6's own rule that "earlier tiers may relax only non-invariant alerting" as exactly one configuration value's difference, never a difference in which signals are evaluated or how severity is computed.
- **Production's own per-region instantiation (`01-environment-and-configuration-design.md` §3.3) carries its own configuration, never a shared one.** Because each Production region is its own structurally separate instantiation, its alert-evaluation configuration is provisioned once per `(tier, region)` intersection exactly as every other configuration value is (`01-environment-and-configuration-design.md` §4.2) — a signal scoped to one region's instantiation never crosses silently into another's evaluation, the identical rule that document's §4.4 already fixes for configuration generally, applied here to alert-routing configuration specifically.

## 6. Health Signals That Trigger Self-Correction or Rollback — the Signal and Its Bound

Spec §7 fixes that this document owns which signals may trigger a reaction and the bound within which it is permitted, and that it does not own how the reaction is carried out. This section states the signal and the bound; it hands the mechanism to `05-meta-operations/07-self-correction-and-fallback-protocol.md` for the ladder and to `05-release-and-rollback-design.md` (Layer 5, not yet written) for the rollback itself, exactly as `02-ci-cd-pipeline-design.md` §12.1's own Consequences hand its gate-placement fact to `03-testing-and-quality-gates-design.md` "never redesigning what it measures" — the identical shape of handover, stated from this document's side to the two it feeds.

### 6.1 The Triggering Signal, as a Concrete Payload

A runtime regression signal (§4.2) that is within bounds triggers the fallback ladder `05-meta-operations/07-self-correction-and-fallback-protocol.md` §5 already lists as an input from this document, by producing exactly the payload that protocol's own detection-signal table requires: which target breached (the `severity_source` tag, §4.1), the severity attached to it, its measured persistence past the threshold, and whether the tag names an invariant or a guardrail-metric quantification. This document supplies that payload at the moment §4.2's evaluation fires; it does not decide which rung of the ladder responds to it, does not decide whether the response is an in-place correction or a rollback, and does not decide when the ladder's own bound is reached — every one of those is that protocol's own mechanism, cited and never redesigned.

### 6.2 The Bound Within Which a Reaction Is Permitted

Consistent with spec §7's own rule, this document's signal is eligible to trigger an autonomous reaction only where three conditions the signal itself carries evidence of are met: the condition is reversible and recoverable (the `severity_source` tag does not name INV-08 as itself breached), it breaches no invariant (the tag does not name an invariant already violated — such a signal is never routed here at all, §7 below), and it stays within the limits `05-meta-operations/07-self-correction-and-fallback-protocol.md` §7 and `04-scalability-availability-and-performance-design.md` §6.3's mean-time-to-recovery floor already set. This document does not compute whether a given reaction attempt stays within those limits — that determination is the protocol's own, made rung by rung — it fixes only that the signal it hands over never itself asserts eligibility beyond what its own tag content supports.

### 6.3 The Rollback-Triggering Case, Handed to H39 Precisely

Where §6.1's signal is not resolved by in-place correction, the protocol's own Rung 3 invokes a rollback (`05-meta-operations/07-self-correction-and-fallback-protocol.md` §6). This document's own contribution to that invocation is exactly the same payload §6.1 already produces — it mints no second, rollback-specific signal shape. **This document does not design the rollback mechanism, the staged-promotion path a rollback traverses, or the rollback-specific time-to-recover target** — each is `04-devops-and-cloud-infra/05-release-and-rollback-protocol.md`'s, to be realized by `05-release-and-rollback-design.md` (H39, Layer 5, not yet written). Binds that document, once written, to consume the triggering signal and threshold of this section as the input its own release-and-rollback mechanism composes with, never redesigning what triggers it — stated here, from this document's side, precisely as `02-ci-cd-pipeline-design.md` §12.1 already stated the identical shape of handover to `03-testing-and-quality-gates-design.md`.

### 6.4 A Critical Signal Never Enters This Section

A signal whose tag names an invariant already violated, or a vulnerability already classified Critical, is never routed through §6.1–§6.3 at all — it halts and escalates immediately under `02-governance-and-security/01-system-invariants.md` §3, bypassing the ladder entirely, exactly as spec §7's own rule and `05-meta-operations/07-self-correction-and-fallback-protocol.md` §6's "a signal that forbids a correction bypasses the ladder entirely" rule already fix. §7 below is where such a signal is handled.

## 7. Signals That Mandate Human Escalation — Composing With Existing Routing

Spec §8 enumerates the signals that mandate escalation and fixes that this document defines them, never how an escalation is requested, routed, recorded, or resolved. `05-meta-operations/04-human-in-the-loop-protocol.md` §5 already names this specification document, by path, as the owner of one of its own enumerated triggers — *"Escalation-mandating runtime signal or incident | Any runtime signal at the escalation-mandating conditions... | `04-devops-and-cloud-infra/04-observability-and-monitoring.md` §8"* — so this section discharges that document's own dependency on this one.

### 7.1 The Signal Set, Realized Against §4.1's Tag Mechanism

Every signal spec §8 enumerates resolves to a concrete condition on the tag and evaluation mechanism §4 already fixes, with no new evaluation logic beyond what §4.1–§4.2 already establish:

| Spec §8 Trigger | Realized As |
|---|---|
| Any runtime invariant violation | A `severity_source` tag naming an invariant, evaluated as violated (§4.1) — the same condition §6.4 routes away from the ladder entirely. |
| Any nonzero guardrail metric | A `severity_source` tag naming a guardrail metric, evaluated nonzero (§4.1, §4.2). |
| Any Critical or High vulnerability active at runtime | A `severity_source` tag naming a vulnerability class, inheriting Critical or High from `02-governance-and-security/02-security-policy.md` §6 (§4.1). |

| Exhaustion of the autonomous reaction bound | Identical to the row above — the bound itself is that protocol's own §7, cited and not restated. |

| Uncertainty about whether escalation is required | §4.2's own uncertainty-resolves-to-alerting rule, carried forward: where the tag mechanism cannot establish a signal falls outside every row above, it is treated as matching one. |

### 7.2 A Monitoring Blind Spot, Captured Without a New Event Shape

Where an instrumentation point §3 requires cannot be emitted or observed at all, the resulting escalation is captured under the same discriminated shape as the guarantee it can no longer confirm: where the unconfirmable point is an invariant- or guardrail-tagged signal, it is captured as that same tag's own event, with a result value stating the guarantee could not be established rather than that it was measured held or violated — the identical `unresolved`-style discipline `08-audit-and-traceability-design.md` §3.1 already applies to an unattributable actor, applied here to an unconfirmable guarantee. Where the unconfirmable point carries no invariant or guardrail tag, the escalation is captured under the closest `mandatory_category` that document's §5 already resolves toward on uncertainty. §13 below confirms this requires no new event type.

### 7.3 What This Document Does Not Do

This document does not design the request, routing, or recording mechanics an escalation triggers — `05-meta-operations/04-human-in-the-loop-protocol.md` §6 already fixes that "the request is made before the action," "carries what a human needs to decide," and "is routed to a human holding the required authority," none of which this document redesigns — and it does not design how a resolution is reached or how autonomy resumes, which that document's §7 owns in full.

## 9. Observability Signal Versus Audit Event — the Boundary, Enforced

Spec §3's own table fixes the distinction load-bearingly: an observability signal is "a measurement or record of runtime behavior, from which health is determined after deploy," while an audit event is "the attributable, tamper-evident record of a consequential action," owned by `02-governance-and-security/07-audit-and-traceability.md` and realized by `08-audit-and-traceability-design.md`. This section states how this document's own instrumentation holds that boundary rather than merely citing it.

- **A metric, a log entry, or a trace span is never itself an audit event, and this document mints no audit-event field on any of them.** The base record `08-audit-and-traceability-design.md` §4.2 fixes (`event_id`, `stream`, `sequence_no`, `actor_reference`, `target_reference`, and the rest) has no analogue anywhere in §3's instrumentation; a metric gauge carries a value and a tag (§4.1), never an actor, an approval reference, or a correction chain, because it is not attributable evidence of who did what — it is a measurement of platform health.
- **Where the same occurrence produces both a log entry (§3.3) and an audit event, the two are captured independently, by independent mechanisms, and neither substitutes for the other.** A refused access check is logged here (§3.3, for operational diagnosis — what was checked, in what state, with what outcome) and is separately captured as an `invariant-check` audit event by the mechanism `01-application-runtime-and-lifecycle-design.md` §10 already fixes (for attributable, reconstructable evidence) — the same occurrence, two independent records, exactly as spec §3's own "where the two overlap... both may be recorded as logs" language anticipates without conflating them.
- **A metric is not evidence, and an audit event is not a health signal.** This document's own alert-evaluation mechanism (§4) never reads an audit-event record as its input — it reads only the metrics, logs, and traces §3 defines — and `08-audit-and-traceability-design.md`'s own record model never derives an event from this document's alert state; the two mechanisms consume disjoint inputs by construction, not merely by convention.
- **Retention differs, and this document does not narrow the audit trail's own floor.** `03-software-and-architecture/06-non-functional-requirements.md` §10 fixes a ≥13-month audit and log retention floor for mandatory audit events; this document's own operational metric, log, and trace retention is a monitoring-system operational concern this document does not itself set a floor for, distinct from — and never a substitute for — the audit floor that document already fixes for the audit trail specifically.

## 10. Guardrail Metric Versus Invariant Versus Gate — the Three-Instrument Distinction, From the Metric Side

`PROCESS.md` §11 fixes three instruments that must never collapse into one another: an **invariant** is a binary property holding continuously; a **gate** is a checkpoint a change must pass to advance; a **guardrail metric** is a measured value that must not degrade. `03-testing-and-quality-gates-design.md` §9.1 held this distinction from the gate side; this section holds it from the metric side, where this document's own instrumentation sits closest to the boundary.

- **A guardrail metric, instrumented here, is a measured value — never a checkpoint and never treated as binary in the way an invariant is, even though its floor is exactly zero.** §3.2's guardrail-tagged gauge reports a current value continuously; it is not evaluated once at a checkpoint the way §9's gate is, and it is not itself the invariant it may be the quantified form of — `06-non-functional-requirements.md` §9.2 already states the guardrail floor is exactly zero without collapsing the metric into the invariant it measures, and this document's own tag mechanism (§4.1) preserves that: a guardrail tag and an invariant tag are two distinct values a signal may carry, never merged into one.
- **This document's alert-evaluation mechanism is not a gate, and does not produce a pass/fail admission decision.** `03-testing-and-quality-gates-design.md` §9.1 fixes its own gate as "the composite condition spec §3 already defines," evaluated, per that same section, "pass/fail at a checkpoint" — quoting `PROCESS.md` §11's own gate definition, "a checkpoint a change must pass to advance." This document's mechanism runs continuously, at runtime, after deploy — it never blocks a change from advancing, because there is no further pipeline stage for a runtime signal to advance past. A signal this document raises may trigger the self-correction ladder (§6) or mandate escalation (§7), but neither of those is this document reproducing a gate; both are reactions to a measured or breached value, which is exactly the guardrail-metric and invariant-monitoring role this document owns, never the gate role `03-testing-and-quality-gates-design.md` owns pre-deploy.
- **Where a specific signal's own subject is also an invariant or also a guardrail-metric floor, that reflection remains the other instrument's own**, exactly as `03-testing-and-quality-gates-design.md` §9.1 already holds for its own layers touching the same targets. A `severity_source` tag naming an invariant does not make this document's metric mechanism an invariant-checking mechanism in the sense `01-invariant-enforcement-design.md` owns — this document observes the runtime state that mechanism's own check already established; it does not perform a second, competing check.
- **No signal in this document is ever described as a gate.** Nothing in §3–§8 uses "pass," "fail," or "admit" in the sense §9 of `03-testing-and-quality-gates-design.md` already reserves for its own composite condition; this document's own vocabulary throughout is "signal," "alert," and "severity" — measurement and urgency, never admission.

## 11. What This Document Measures About Built Applications Versus the Platform

Spec §2's own scoping bullet states this document's boundary directly: *"The platform provides observability as a primitive (C-09) with which a builder can observe their own built artifact's behavior; what metrics, alerts, or thresholds a builder configures for the logic of their own built artifact is builder-defined content and is never absorbed into this document."* This section states how the instrumentation of §3 holds that line rather than merely citing it.

- **Every instrumentation point in §3 is identical code for every built application it serves, because the runtime it instruments already is.** `01-application-runtime-and-lifecycle-design.md` §6 and its §14 binding rule fix that "the runtime dispatches only on a construct's or binding's own generic, closed-vocabulary shape, never on domain content," and that "the same runtime code path serves every application; the difference between applications is entirely in the catalog rows the Gateway returns, never in the runtime code that reads them." This document's own metrics, logs, and traces (§3.2–§3.4) are emitted from inside that identical code path — a request-latency metric, an access-check log, or a trace span carries no branch keyed to what a builder's construct or binding is "for," only the generic tags (which contract operation, which construct kind, which check) that runtime's own generic dispatch already carries. Instrumenting the runtime therefore cannot assume anything about what a built application does, because the mechanism being instrumented already cannot.
- **What this document measures about the platform is platform-core health; what a builder observes about their own built artifact is generic reach into the identical instrumentation, never a second, domain-specific mechanism this document builds for them.** The observability-coverage success metric (`01-business-and-ux/06-value-proposition-and-success-metrics.md` §4, quantified at `06-non-functional-requirements.md` §9.1) measures "the share of consequential platform and built-software behavior that is observable" — this document's §3 instrumentation is what makes both halves of that share observable, through the same generic mechanism, never a platform-side mechanism and a separate built-application-side mechanism.
- **A builder's own domain-specific alert configuration — what threshold matters for their own built artifact's own logic — is never designed, stored, or evaluated by this document.** This document's §4 alert-evaluation mechanism evaluates only the platform-tagged signals of §4.1; a builder reaching the platform's observability primitive to configure their own built artifact's own alerting is exercising a primitive this document makes available generically, on terms this document does not narrow, exactly as `01-application-construction-design.md`'s own construct/binding vocabulary is available generically without this document adding a domain-specific instrumentation branch for any one builder's use of it.

### 14.1 ADR-049 — Signal-to-Instrument Attribution, Tier Configuration Without a Branch, and No New Schema or Evidence Type

- **Status:** Team-Approved.
- **Cost to reverse:** **Moderate.** Reasoned independently, distinct from the Low and High grades already in use elsewhere in this layer. (6) The scalability document's named instrumentation obligation is discharged concretely against its own §7 detection-point table and its two schema-count waypoints, with the citation slip in its own Consequences field corrected rather than forced (§8). (7) An observability signal is never described, stored, or evaluated as an audit event, and a guardrail metric is never described as an invariant or a gate, held explicitly through every section that touches either (§9–§10). (8) This document owes no new structure to `02-platform-data-model-design.md` and mints no new audit event (§12–§13).
- **Alternatives considered:** *A dedicated, parallel measurement mechanism per signal type, independent of the runtime's own instrumentation surface* — rejected under criterion 1; it duplicates a surface `01-application-runtime-and-lifecycle-design.md` already fixed and risks a second, drifting source of truth for what a request actually did. *Computing severity from raw threshold-breach magnitude at evaluation time* — rejected under criterion 2; it would let this document silently re-derive a classification another document already owns, and would make severity depend on how a breach is measured rather than on what guarantee it bears on. *A tier-conditional branch inside the alert-evaluation mechanism* — rejected under criterion 3; it directly contradicts the no-branch discipline `01-environment-and-configuration-design.md` §4.1 already fixes for component code generally, and this document has no principled reason to be the one exception. *A dedicated `monitoring-alert-raised` or `health-signal-triggered` audit-event type* — rejected under criterion 4; each candidate's content is a strict subset of an already-minted type or an already-owned reaction mechanism's own record, and minting either would be the exact near-duplicate risk `BACKLOG.md` §1v names. *A new `platform.observability_configuration`-adjacent table for metric series, alert state, or threshold configuration* — rejected under criterion 5; each is monitoring-system telemetry, a runtime-computed value, or fixed text this document already carries, produced before any platform-core schema is relevant to it.
- **Consequences:** Binds `05-release-and-rollback-design.md` (Layer 5, not yet written) to the fixed rollback-triggering signal and threshold of §6 as the substrate its own release-and-rollback mechanism composes with, never redesigning what triggers it. ## 16. Precedence and Ownership Boundaries

- **The charter prevails**, and the specification this document realizes prevails over this design wherever the two appear to conflict; this document is corrected to match the specification, never the reverse.
- **An alert threshold, a severity attribution, or a tier-applicability rule is never relaxed to quiet a signal, ease an escalation, or simplify a deployment.** This document enforces the values and rules the cited specification and the upstream design documents already fixed; where enforcement appears strict (an invariant- or guardrail-tagged signal binding at every tier, a Critical signal bypassing the ladder entirely), the strictness is stated, never softened.

## 17. Binding Rules

These rules hold for every signal, alert, and reaction subject to this model and are subordinate to the charter.

- **Every required signal is instrumented against the platform's already-fixed structure, never a second, parallel measurement path** (§3).
- **Severity is attached via a fixed tag set at signal-definition time and read, never computed, at evaluation time** (§4.1).
- **No alert threshold is minted independently of an already-owned value; this document keys to `06-non-functional-requirements.md`, `01-business-and-ux/06-value-proposition-and-success-metrics.md` §5, `02-governance-and-security/01-system-invariants.md` §4, and `02-governance-and-security/02-security-policy.md` §6, and mints no sixth source** (§4.2).
- **Tier applicability is realized as deploy-time configuration only; no branch inside the alert-evaluation mechanism is ever keyed to which tier is running it** (§5).
- **This document defines the health signal and its bound; it never designs the self-correction ladder or the rollback mechanism the signal feeds** (§6).
- **This document defines the signals that mandate escalation; it never designs how an escalation is requested, routed, recorded, or resolved** (§7).
- **The scalability document's named instrumentation obligation is discharged concretely, against its own detection points and waypoints, with the waypoints' reasoned-not-verified status carried forward and never upgraded** (§8).
- **An observability signal is never described, stored, or evaluated as an audit event, and neither substitutes for the other where both describe the same occurrence** (§9).
- **A guardrail metric is never described as an invariant or a gate, and this document's own mechanism is never described as a gate** (§10).
- **Instrumentation of a built application's runtime never assumes anything about what that application does; the same runtime code path, and the same instrumentation, serves every application** (§11).
- **This document owes no new structure to `02-platform-data-model-design.md` and mints no new audit event** — every signal resolves into an already-owned instrument, an already-owned reaction mechanism, or fixed configuration this document's own text carries (§12–§13).
- **This document records exactly one ADR.** ADR-049 (§14) is the genuine, independent set of instrumentation, attribution, and configuration decisions this document makes; every mechanism it observes remains owned, in full, by the document that designed it.
- **Everything remains domain-neutral and platform-level.** No signal, threshold, or reaction in this document encodes the characteristics of any single domain; all remain valid for any tenant, in any operating region, on any provider-neutral monitoring tooling.
