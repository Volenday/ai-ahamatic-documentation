## 1. Purpose and Reading Order

This document answers six questions:

- **What an environment tier physically is**, given the fixed one-deployable-per-product shape and the per-region instantiation `08-multi-region-distribution-design.md` already fixes for Production (§3).
- **How a configuration value is scoped to one tier-and-region intersection at once**, without either axis becoming a branch in core component code (§4).
- **How a secret reaches a running deployment without ever being committed**, and how its scope is bounded to exactly one configuration boundary (§5).
- **How the platform's own Production is protected as a promotion target**, reachable only through a governed, explicit act (§6).
- **What infrastructure-as-code discipline governs every mechanism above**, and whether anything this document introduces falls outside ADR-010's portable subset (§7).
- **How each of the five provisioning obligations already handed to this document by name is discharged**, and where the platform's own configuration state does and does not need a new structure (§8–§9).

It is structured as a pyramid: first what a tier is (§3), since nothing else can be stated before it; then the configuration boundary that tier and region jointly define (§4); then the secret-injection mechanics that keep every boundary free of committed secrets (§5); then Production's own protection (§6); then the infrastructure-as-code discipline binding everything above (§7); then the five named obligations, discharged in turn (§8); then the storage-obligation check (§9); then the boundary completed against the builder-facing side (§10); then evidence (§11); then the design decision (§12); then boundaries, precedence, and binding rules (§13–§15).

## 3. Environment-Tier Realization

`04-devops-and-cloud-infra/01-environment-and-config-spec.md` §4 fixes three tiers — Development, Staging, Production — ordered, asymmetrically protected, and orthogonal to region and tenant. This section realizes each as a concrete deployed thing.

### 3.1 A Tier Is a Structurally Separate, Complete Instantiation

**Each environment tier is its own complete, independently provisioned instantiation of the entire platform topology — never a flag, a branch, or a shared database distinguished by a column.** Concretely, each tier has: its own provider-account-level isolation boundary (a separate project under GCP, or the equivalent account- or subscription-level boundary under AWS or Azure, per ADR-010 §20); its own managed PostgreSQL instance(s) holding its own, entirely separate `platform` schema and every tenant and application schema that tier's own operators or builders populate; its own object-storage location; its own key-management-service binding (§8.3); and its own container-orchestration deployment target. No structure anywhere in this design connects two tiers' own infrastructure — this is the identical discipline `02-platform-data-model-design.md` §4.1 already uses to make tenant isolation structural rather than assumed, realized here one level up, between tiers rather than between tenants.

This is what makes the spec's own "configuration never crosses a boundary silently" (§5) true for the tier axis specifically, before any mechanism inside this document runs: there is no shared storage across tiers for a value to cross into. A Development-scoped configuration value and a Production-scoped one are not two rows distinguished by a tier column in one database — they are rows in two databases that share no connection, no credential, and no network path by default.

### 3.2 The Same Artifact, Promoted, Never Rebuilt

`03-architecture-realization-design.md` §7 fixes one OCI container image per deployable, built from one source tree. This document realizes tier promotion as movement of that same, already-built artifact between tiers — never a tier-specific rebuild, and never a tier-specific source variant. This directly realizes the spec's own §6 rule that "promoting a change carries its code and configuration content forward": the artifact validated in Staging is the exact artifact deployed to Production, bit-for-bit; only the configuration and secrets injected at each tier's own boundary differ (§4–§5). No component module, and no build step, branches on which tier it is being built for — a tier-specific branch in the artifact itself would be exactly the kind of drift `03-architecture-realization-design.md` §6.1's first failure mode warns against, realized here for the tier axis rather than the domain-content axis that section addresses.

### 3.3 Production's Own Instantiation Is Per-Region; Development and Staging Need Not Be

`08-multi-region-distribution-design.md` §3.2 fixes that Production is realized as N regional instances of the identical image, one per operating region, each with its own regionally-resident managed PostgreSQL instance. This document's own tier realization composes directly: **Production is the one tier whose own "complete instantiation" (§3.1) is itself further instantiated once per operating region**, exactly as that document fixes; Development and Staging carry no equivalent multi-region requirement, because no specification or design document fixes one. Staging may realize a topology structurally identical in shape to whatever regional footprint Production currently operates, at whatever region count is practical for validating region-specific mechanisms (the Region Resolution Point, cross-region replication) "under conditions representative of Production" (spec §4); this document fixes no minimum region count for Staging, since the quality floors that bind Production in full (spec §4's fourth bullet) do not bind an earlier tier's shortfall of a non-invariant target.

### 3.4 What Provisions Each Tier

Every element of §3.1–§3.3 is provisioned by one parameterized infrastructure-as-code module set (§7), instantiated once per tier and, for Production, once per operating region within that tier. The module takes a `(tier, provider, region)` triple as input and provisions the managed PostgreSQL instance, the container-orchestration deployment target, the object-storage location, and the key-management-service binding for that exact intersection — never a hand-provisioned, undocumented instance for any tier. This is the concrete mechanism that makes a tier "a deployment stage of the platform's own infrastructure" (spec §3) rather than an abstract label.

## 4. Per-Region and Per-Environment Configuration Boundaries

Spec §5 fixes a configuration boundary as the intersection of one environment tier and one region, populated explicitly, never assumed to extend beyond it. This section states how that boundary is realized, composing with `08-multi-region-distribution-design.md` §3's finding that every region runs the identical platform-core image, with only the regionally-resident connection differing.

### 4.1 Neither Axis Is a Branch in Core Component Code

**Tier and region are both externalized entirely to deploy-time configuration injection, never to a hardcoded value or a conditional branch inside any component module.** `08-multi-region-distribution-design.md` §3.1 already fixes that no component module contains a hardcoded region identifier; this document extends the identical discipline to tier: no component module in `components/*` or `guardrail/` contains a hardcoded tier identifier, a per-tier subclass, or a per-tier branch. A running platform-core replica is told which tier and which region it is running in by ordinary environment configuration supplied at the moment it starts (§5.2) — never compiled in, never inferred from source, and never read from a database row that would itself have to differ per tier before the replica could even connect to one.

**Concrete instance: the value the Region Resolution Point compares against.** `08-multi-region-distribution-design.md` §6.3 step 3 requires each regional instance to know which region it is, in order to compare that value against a resolved tenant's own `region_of_record`. This document fixes that value's source: an ordinary deploy-time configuration value (e.g., a `REGION_ID` value), injected identically to any other non-secret configuration value (§4.2), never derived from source code, a naming convention, or an inference over network topology. The Region Resolution Point's own comparison logic (that document's, unaltered) is unaffected; this document supplies only where the comparison's second operand comes from.

### 4.2 Non-Secret Configuration Injection

A configuration value that is not itself a secret (§5 covers the secret case) is supplied to a running deployment through the same deploy-time injection mechanism as a secret — environment configuration resolved at process start, from the infrastructure-as-code module instantiated for that exact `(tier, region)` intersection (§3.4) — but is not subject to §5's access-scoping and rotation discipline, because it carries no confidentiality obligation. The distinction between the two is made once, at the point a value is defined in the infrastructure-as-code module (§7): a value that could satisfy the deny-by-default "treated as a secret on uncertainty" test (spec §6, §5.4 below) is injected through the secret path; every other value is injected through this one. No third path exists.

### 4.3 A Region's Obligations Bind Every Tier Operating There

Spec §5's second rule fixes that a region's residency obligations bind every tier operating in it, not only Production, from the moment the platform begins operating there. This document does not narrow that rule: where Staging or Development is provisioned into a region the platform also operates Production in, that tier's own instantiation (§3.4) is provisioned under the identical region-admission discipline §8.1 below fixes for Production — there is no "lesser" provisioning path for an earlier tier operating in a residency-obligated region. Where an earlier tier operates in a region the platform's Production presence has never reached, this document introduces no exception permitting that; whether such a topology is ever authorized is a governance question this document does not decide.

### 4.4 Uncertainty Resolves to Refusal, at the Point Provisioning Occurs

Spec §5's closing rule fixes that a configuration value whose owning tier or region cannot be established is refused rather than applied. For this document's own mechanism, that determination is made and enforced at infrastructure-as-code apply time (§7), not at application runtime: a module invocation that cannot resolve which `(tier, region)` intersection it is provisioning for fails the apply, and no deployment target is created or configured on an assumed or default intersection. This is a deploy-time realization of the identical deny-by-default posture `02-governance-and-security/01-system-invariants.md` §3 fixes generally, applied here before any running process exists to misapply a value at all.

## 5. Secret-Injection Mechanics

This section is the environment-specific mechanics `02-governance-and-security/02-security-policy.md` §4 deferred in full to spec §6, which in turn deferred the concrete injection mechanism to this document. It is the complementary, non-overlapping half of INV-03's realization: `04-security-controls-design.md` §2 stops a secret from being committed (pipeline scanning) or emitted (runtime redaction); this section is how a secret reaches a running deployment in the first place, in place of ever being committed.

### 5.1 The Injection Point

**A secret is supplied to a running platform-core replica, or to any other deployed component this design names (the web presentation tier, the mobile-delivery build/release tooling, an infrastructure-as-code apply step itself), only at the moment and place it executes — never authored alongside, and never committed together with, the code or configuration it serves.** Concretely: the container-orchestration deployment target for a given `(tier, region)` intersection (§3.4) mounts or injects secret values from the tier-and-region-scoped secret store at process start; no secret value is baked into the OCI image (§3.2), no secret value is written into the infrastructure-as-code module's own source, and no secret value is passed as a plain build argument at image-build time, because the image is built once and promoted unchanged across every tier (§3.2) — a secret baked in at build time would be the Development tier's secret running, unchanged, in Production, which §5.3 below forbids by construction.

### 5.2 One Secret Store Per Configuration Boundary

**Each `(tier, region)` intersection — and, where a secret is further scoped to one tenant, that tenant within it — has its own dedicated secret-storage scope, never a single, platform-wide store partitioned only by naming convention.** This is the direct realization of spec §6's "a secret is valid for one tier-and-region pair... and is never assumed valid across a different tier, a different region, or a different tenant by default": the boundary is structural, not conventional, because the store itself is scoped, not merely the keys within a shared store. A Development-scoped secret's own store is never reachable from a Production-scoped deployment's own injection path, on the identical account-level isolation boundary §3.1 already fixes between tiers generally.

### 5.3 Promotion Never Carries a Secret Across a Boundary

Because the artifact promoted between tiers is the same, unchanged image (§3.2), and because a secret is never baked into that image (§5.1), promotion structurally cannot carry a secret from one tier to the next: there is no secret-shaped content in the promoted artifact for a promotion to carry. The destination tier's own deployment target resolves its own secrets from its own scope (§5.2), independently, at the moment the promoted image starts running there — never inherited, copied, or carried over from the source tier's own injection.

### 5.4 Least Privilege Over Who May Hold or Provision a Secret

Consistent with spec §6's least-privilege rule, the infrastructure-as-code identity that provisions a `(tier, region)` intersection's own secret store (§3.4, §7) is itself scoped to that intersection alone — a service identity authorized to provision Development's own secret store holds no standing grant over Staging's or Production's. A human steward's own access to read or set a secret value follows the identical tier-narrowing discipline `04-devops-and-cloud-infra/01-environment-and-config-spec.md` §4's access-narrowing rule already fixes generally for tier access: reaching a later tier's secret scope never follows automatically from holding a grant at an earlier one, and this document adds no exception for infrastructure-provisioning identities.

### 5.5 Uncertainty Resolves to Treating a Value as a Secret

Where the infrastructure-as-code module (§7) defining a configuration value cannot establish that the value is free of secret content, it is routed through the secret-injection path of §5.1–§5.2, never the non-secret path of §4.2, on the identical deny-by-default rule spec §6's closing bullet already fixes. This document adds no separate classification mechanism of its own for making that determination at the infrastructure-as-code-authoring stage — it is a discipline applied by whoever authors the module, checked at the same commit-time secrets-scanning gate `04-security-controls-design.md` §2.1 already applies to every other committed content, including infrastructure-as-code source itself.

## 6. Production as a Protected Promotion Target

Spec §7 fixes that Production is reachable only through explicit, deliberate promotion, and that any other path is a breach refused or reversed. This section states the infrastructure-level mechanism that makes an unpromoted path structurally absent, composing with — never substituting for — the pipeline gates `02-ci-cd-pipeline-design.md` (Layer 5, not yet written) owns.

### 6.1 No Standing Deploy Credential Reaches Production Directly

**The only identity holding write or deploy permission against Production's own infrastructure (its container-orchestration deployment target, its managed PostgreSQL instance's migration path, its own secret store) is the pipeline's own service identity — scoped to Production alone, per §5.4's tier-narrowing discipline — and no human steward holds a standing credential of equivalent reach.** This is the concrete, infrastructure-level realization of spec §7's "no code, configuration, or secret reaches Production other than through a deliberate promotion action": because the only credential capable of writing to Production belongs to the pipeline, and the pipeline's own gates are what `02-ci-cd-pipeline-design.md` owns, every path into Production necessarily passes through those gates — there is no second, credential-bearing path this document's own provisioning leaves open. A human steward wishing to change Production does so by causing the pipeline to run, never by reaching Production's infrastructure directly.

### 6.2 The Credential Itself Is an Ordinary Injected Secret

The pipeline's own Production-scoped deploy credential is provisioned and injected under the identical mechanics §5 fixes for any other secret: scoped to the Production `(tier, region)` intersection it deploys into (§5.2), never committed, never carried over from a Staging-scoped equivalent (§5.3), and rotated under the same least-privilege discipline (§5.4). This document introduces no second, credential-specific mechanism for the pipeline's own deploy identity; it is one more instance of §5's general mechanism, not an exception to it.

### 6.3 Composition With, Never Substitution For, the Pipeline's Own Gates

This document's own contribution stops at making a credential-bearing path to Production structurally singular (§6.1) and that path's credential itself properly secret-scoped (§6.2). Whether a given pipeline run is permitted to use that credential — the Merge Gate, the Deploy Gates, the mandatory-check list, and the no-bypass rule for a failed gate — is `04-devops-and-cloud-infra/02-ci-cd-pipeline-spec.md`'s own mechanics, realized by `02-ci-cd-pipeline-design.md`, never redesigned here. This document does not decide, and does not narrow, which checks a promotion into Production must pass; it decides only that no path exists to Production that could skip having to pass them.

## 7. Provider-Neutral Infrastructure-as-Code and the Portable Subset

`01-technology-stack-design.md` §20.1 (ADR-010) fixes two disciplines binding this document by name: infrastructure defined in a provider-neutral tool (Terraform or OpenTofu), never a provider's own console or proprietary template language; and adoption of only the portable subset — containers, managed PostgreSQL, object storage — for anything correctness depends on.

### 7.1 Every Mechanism Above Is Terraform/OpenTofu-Defined

The tier-instantiation module (§3.4), the per-`(tier, region)` configuration- and secret-injection scoping (§4, §5), the Production deploy-credential scoping (§6.2), and the region-admission and anchor-provisioning mechanisms (§8.1–§8.2) are each defined as Terraform or OpenTofu modules, parameterized by `(tier, provider, region)` — never hand-configured through a provider's own console, and never expressed in a provider-proprietary template language. This is the concrete realization of ADR-010's own rule that infrastructure configuration is "at least translatable rather than re-discovered" — a module written once and parameterized, rather than a per-region or per-tier console click-through no later engagement could reconstruct.

### 7.2 What This Document Introduces, Checked Against the Subset

## 8. The Five Provisioning Obligations, Discharged

Five already-written documents each hand this document a provisioning obligation by name. Each is discharged in turn, honoring the constraint it arrived with.

### 8.1 Obligation One — The Per-Region Read Replica and the Region-Admission Sequence

`08-multi-region-distribution-design.md` §3.2, §9.1, and §13.1's Consequences hand this document: the per-region read-only replica of the platform-global schema, including where its single authoritative write location sits, and the region-admission infrastructure sequence — both explicitly left undesigned there.

**The authoritative write location.** One region is designated, at the platform's own initial deployment, as the platform-global write-authority region — the sole region whose managed PostgreSQL instance ever accepts a write against the `platform` schema (`platform.tenants`, `platform.applications`, `platform.platform_users`, and the rest of `02-platform-data-model-design.md` §3.1). This designation is itself a `(tier, region)`-scoped configuration value (§4), never a value inferred at runtime by any component; every regional platform-core replica, in every operating region, is configured with the write-authority region's own connection endpoint for the rare platform-global write, and with its own local replica's endpoint for every read — the identical read/write split `08-multi-region-distribution-design.md` §3.2 already reasons is necessary to avoid a cross-region round trip on the platform's single most frequent code path. Changing the write-authority region after initial deployment is an explicit, governed migration this document does not design — the write-authority designation, once fixed, is not a value this document's own mechanism revisits automatically.

**The replication mechanism.** Each operating region's own read-only replica of the `platform` schema is kept current by ordinary PostgreSQL logical replication — a publication on the write-authority region's own instance, and a subscription on each other region's own instance — a portable capability present on every ADR-010-evaluated provider's managed-PostgreSQL offering (§7.2), never a provider-unique replication product. This is the concrete mechanism `08-multi-region-distribution-design.md` §3.2 names only abstractly ("ordinary PostgreSQL streaming or logical replication... a portable, provider-neutral capability").

**The region-admission sequence, as infrastructure-as-code.** `08-multi-region-distribution-design.md` §9.1 fixes region admission as: provisioning a regionally-resident managed PostgreSQL instance; deploying an identical platform-core deployable instance connected to it; establishing a read-only replica of the platform-global schema into that instance; and adding the new region's row to `platform.regions`. This document realizes the first three steps as one parameterized Terraform/OpenTofu module invocation — the identical tier-instantiation module of §3.4, invoked for Production at a new `(Production, provider, region)` triple, provisioning the managed PostgreSQL instance, the container-orchestration deployment target, and the logical-replication subscription against the write-authority region in one applied change set. The fourth step — inserting the new region's `platform.regions` row — is not an infrastructure-provisioning action; it is an ordinary, Registry-mediated write against the now-existing write-authority instance, performed once the first three steps' infrastructure exists and is reachable, composed with — never performed by — this document's own module. `08-multi-region-distribution-design.md` §9.2 already fixes that the whole sequence is gated by the Production Deploy Gate's own residency clause before it may proceed; this document's module is what that gate's approved promotion actually executes, not a second gate of its own.

### 8.2 Obligation Two — The External Anchor's Storage Medium and Immutability Configuration

`08-audit-and-traceability-design.md` §6.3 and §10.1's Consequences hand this document the external anchor's storage medium and its own immutability configuration — the periodic write, outside the audit store's own write path, that lets a later recomputation of the hash chain be checked against a point that a full-table-privileged rewrite could not also have compromised.

**Storage medium: object storage, inside ADR-010's portable subset (§7.2).** The chain-tip digest is written, on the cadence `08-audit-and-traceability-design.md` §6.3 fixes as "periodically," to an object-storage location distinct from — and holding no credential shared with — the managed PostgreSQL instance the audit store itself lives in, for the identical `(tier, region)` intersection its own tenant- or platform-scoped stream belongs to. A write to this location is performed by an identity scoped narrowly to that single write operation (§5.4's least-privilege discipline, applied here); the identity that operates the audit-event writer itself holds no broader privilege over the anchor location than "append a new object," and no privilege at all to modify or delete a prior anchor object.

**Immutability configuration.** The object-storage location is configured with its own provider's write-once/retention-lock capability — a generic object-storage feature present in some form on every ADR-010-evaluated provider (§7.2) — set to a retention period no shorter than the audit-retention floor `08-audit-and-traceability-design.md` §11 already cites from `03-software-and-architecture/06-non-functional-requirements.md` §10 (≥13 months). This is the concrete answer to that document's own open question, "whether the anchor's storage medium is configured with its own write-once retention property" — it is, and the retention window is bound to the same floor that already governs the audit trail it anchors, rather than a separately chosen value this document invents.

**What this does not close.** `08-audit-and-traceability-design.md` §6.3 already states the honest limit of the anchor mechanism itself — that a rewrite compromising the anchor's own storage location is outside what the mechanism can detect. This document's own contribution is provisioning that location with the strongest generic protection available (write-once retention, least-privilege write access); it does not, and cannot, close that document's own stated limit, and does not claim to.

### 8.3 Obligation Three — Provisioning the Key-Management Service's Access Credentials

`04-security-controls-design.md` §8.1's Consequences (cited correctly here per this document's own front-matter correction) hand this document: provisioning the chosen key-management service's access credentials through this document's own secret-injection mechanics, never embedded in code or configuration.

**Discharged directly by §5, with no new mechanism.** The key-management-service access credential each platform-core replica needs to perform a wrap/unwrap operation (`04-security-controls-design.md` §7.2–§7.3) is one further instance of an ordinary, tier-and-region-scoped secret, injected under §5.1's injection point, stored in §5.2's dedicated per-`(tier, region)` scope, never carried across a promotion (§5.3), held only by an identity meeting §5.4's least-privilege discipline, and treated as a secret on any classification uncertainty (§5.5). No credential-specific injection path is introduced for it. This is a deliberate non-decision, stated as one: `04-security-controls-design.md` §7.3 already fixes the operational access model the credential serves (least-privilege scoping of the unwrap operation itself, to the key-hierarchy level a request's own context resolves to); this document's own obligation is only that the credential reaching that model is never committed and never embedded — a property §5's general mechanism already guarantees for every secret, this one included.

### 8.4 Obligation Four — Which External Key-Management Service a Region Assignment Resolves To

`02-platform-data-model-design.md` §8.3 names this document, jointly with `04-security-controls-design.md`, as making the provider-binding decision for which external key-management service is used. `04-security-controls-design.md` §8.1 (ADR-021) has already fixed the *default*: the default cloud target's own managed key-management service (Google Cloud KMS, consistent with ADR-010's default), with AWS's and Azure's own equivalents recorded there as "viable, symmetric alternatives should the default provider change." What remains for this document is the concrete, per-provider **resolution table** — which specific service a tenant's or region's own resolved host-provider assignment (`platform.host_providers`, `02-platform-data-model-design.md` §3.1; `tenant_<id>.tenant_host_connections`, that document's §7) actually reaches — completing, never re-deciding, ADR-021's own default.

| `platform.host_providers` Value | Key-Management Service Resolved | Status |
|---|---|---|
| Google Cloud Platform | Google Cloud KMS | Default, per ADR-021 (`04-security-controls-design.md` §8.1). |
| AWS | AWS Key Management Service | Symmetric alternative, named in ADR-021's own Alternatives Considered; provisioned identically to the default under this document's own module (§7.1) should a region operate under this provider. |

### 8.5 Obligation Five — Backup Provisioning: Storage Medium, Granularity, Consistency, Retention, Residency-Scoped Placement, and the Backup Catalog

`06-incident-response-and-recovery-design.md` §6.2, §6.3, and §11's ADR-051 Consequences hand this document a fifth provisioning obligation.

**A correction to `BACKLOG.md` §1aa's own summary of it, per `BACKLOG.md` §1t's standing rule.** That entry's table row describes the obligation as "backup storage medium, retention discipline, and catalog locatability" — narrower than, and in one respect different from, what §6.2 and §11 actually state, each read directly rather than taken from the entry's own paraphrase. §6.2 fixes three properties the backup mechanism must be shown, at provisioning time, to deliver: a backup granularity sufficient to meet the zero data-loss tolerance a restore is held to; a backup consistency guarantee sufficient to meet the invariant-holding requirement a restore target must satisfy; and a retention window meeting the audit and log retention floor of `03-software-and-architecture/06-non-functional-requirements.md` §10 (≥ 13 months). Only retention overlaps §1aa's own summary; "storage medium" is this document's own means of delivering the other two, not a fourth property §6.2 names in its own right. §6.3 separately hands this document the residency-scoped placement requirement. The backup catalog's own locatability is not §6.2's obligation at all, confirming what §1aa's own phrasing suggested but did not establish: it is named at §11 there, on the finding that a restore must locate a backup without depending on the system it may be recovering, and is folded into the same §6.2 handover as the storage medium itself, never into `02-platform-data-model-design.md`'s schema. This document discharges what §6.2, §6.3, and §11 actually state.

**Storage medium and technical means, chosen here.** Each `(tier, region)` intersection's managed PostgreSQL instance is provisioned with continuous point-in-time recovery — write-ahead-log archiving to the identical class of object-storage location already provisioned for the external anchor (§8.2) — never a scheduled snapshot cadence. This is the technical means §6.2 leaves this document to choose, and the choice is decisive rather than arbitrary: a scheduled cadence, however tightly bounded, carries a nonzero recovery-point gap, and the zero data-loss tolerance `06-incident-response-and-recovery-design.md` §6.4 already cites from `03-software-and-architecture/06-non-functional-requirements.md` §7 ("Zero. No rolling window may record a nonzero count of data-loss incidents affecting committed data.") is a ceiling only a zero-gap mechanism can be shown to meet. Continuous write-ahead-log archiving is an ordinary capability of managed PostgreSQL on every ADR-010-evaluated provider (§7.2), never a provider-unique feature.

**Consistency, delivered by the identical mechanism, not a second one.** A point-in-time-recovery target reconstructed from a base backup plus its write-ahead log is, by the mechanism's own construction, a transactionally consistent database state at the instant named — never a torn, mid-write capture. This is what §6.2's own consistency requirement asks to be shown, and it is shown by the mechanism chosen above, not by a separate consistency-checking step this document adds.

**Retention, bound to the identical floor as the external anchor.** The object-storage location holding the write-ahead-log archive and base backups is configured with the identical provider-native write-once/retention-lock capability §8.2 already provisions for the external anchor, set to the identical retention period — no shorter than `03-software-and-architecture/06-non-functional-requirements.md` §10's own audit and log retention floor (≥ 13 months) — because a backup must remain available for at least as long as the audit trail that would reference an incident it recovers from, exactly as `06-incident-response-and-recovery-design.md` §6.2 states.

**Residency-scoped placement, extending §4.3's own rule rather than adding a second one.** The backup archive's own object-storage location is parameterized by the identical `(tier, region)` module invocation that provisions everything else at that intersection (§7.1), so that a Jurisdiction-Restricted or Regime-Governed tenant's own backup is provisioned within the region(s) its own Resolved Residency Obligation permits — the direct application of §4.3's already-fixed rule that a region's own obligations bind every tier operating there, extended here to a mechanism `06-compliance-and-data-residency-design.md`'s own Region Boundary Check does not itself reach (that mechanism's own §3.5, cited at `06-incident-response-and-recovery-design.md` §6.3, states its guarantee binds only the platform's own code path, never an infrastructure-level capture beneath it). This document's own provisioning is what closes the gap that mechanism itself declines to claim, never a second code-path check competing with it.

**The backup catalog: the storage medium's own structured listing, never a database row.** `06-incident-response-and-recovery-design.md` §11 finds that a restore must locate a backup without depending on the system being restored, and folds the catalog into this same handover rather than into `02-platform-data-model-design.md`'s schema. This document discharges it as the object-storage location's own naming or tagging convention — which tier, region, and backup point each archived object represents — reachable by listing the object-storage location directly, independent of any tier's own live database instance. No second catalog structure is provisioned; the archive location named above is the catalog.

### 12.1 ADR-046 — Structurally Separate Tier Instantiation, Deploy-Time-Injected Tier/Region Identity, and Discharge of the Five Named Provisioning Obligations Inside ADR-010's Portable Subset

- **Status:** Team-Approved.
- **Cost to reverse:** **Moderate**, reasoned independently of, but consistent with, `implementation-document-map.md`'s own pre-assigned grade. Reversing this document's own decisions — the tier-instantiation module's shape, the write-authority region designation, the replication mechanism, the anchor's storage medium, the backup mechanism's own storage medium and technical means (point-in-time recovery versus a snapshot cadence), or the per-provider key-management-service resolution table — is an infrastructure exercise: rewriting Terraform/OpenTofu modules and re-provisioning managed services. No stored tenant or builder data changes shape under any reversal here — `02-platform-data-model-design.md`'s schema is untouched (§9's own finding), no application code changes (§3.2's promoted-artifact discipline is unaffected by which infrastructure hosts it), and no published contract changes. This is `01-technology-stack-design.md` §20.1's own reasoning stated plainly: "the application is portable, the infrastructure is not" — reversal re-does the infrastructure, it does not touch what the infrastructure holds.
- **Upstream decisions assumed:** ADR-005 (`03-architecture-realization-design.md` §7 — the one-deployable-per-product shape this document's tier and region instantiation extends); ADR-010 (`01-technology-stack-design.md` §20 — the portable subset and provider-neutral infrastructure-as-code rule this document's every mechanism stays inside); ADR-021 (`04-security-controls-design.md` §8.1 — the key-management-service default this document's resolution table completes, never re-decides); ADR-023 (`06-compliance-and-data-residency-design.md` §10.1 — the residency obligations this document's per-region tier provisioning honors, §4.3); ADR-025 (`08-audit-and-traceability-design.md` §10.1 — the tamper-evidence mechanism this document's anchor provisioning serves); ADR-039 (`02-builder-facing-environment-management-design.md` §11 — the builder-facing stage model this document's own tier model is completed against, never merged with, §10); ADR-045 (`08-multi-region-distribution-design.md` §13.1 — the region topology and placement unit this document's replica and admission provisioning realizes); ADR-051 (`06-incident-response-and-recovery-design.md` §13.1 — the backup-and-restore guarantee, the zero data-loss tolerance and residency-reach limit it holds this document's own backup provisioning to, and the backup-provisioning and backup-catalog handover naming this document the fifth obligation). ADR-021 through ADR-051 remain Provisional and are not assumed settled; this decision depends on their already-designed content, never their approval status (`PROCESS.md` §12.2).
- **Verified vs. reasoned:** Reasoned throughout. Every infrastructure mechanism named (logical replication, object-storage retention locking, provider-native container orchestration, continuous write-ahead-log archiving) is treated as a generic, portable capability inside ADR-010's subset, never a specific product's currently-verified feature; the reversal-cost argument and the portable-subset compliance table (§7.2) are structural arguments from the cited specification and design documents' own content.
- **Question this answers:** Given the platform's own fixed environment-tier specification, a region topology already fixed elsewhere that composes with it, and five independently-sourced provisioning obligations named to this document by five different upstream documents, how is each environment tier realized as a concrete, structurally separate deployment; how is a configuration value scoped to one tier-and-region intersection without either axis becoming a branch in core component code; how does a secret reach a running deployment without ever being committed; how is Production protected as a promotion target using only infrastructure-level means, composing with — never substituting for — the pipeline's own gates; and how is each of the five named obligations discharged within ADR-010's portable subset, honoring the specific constraint each arrived with?
- **Criteria applied, and how each resolved:**
  1. *Does every mechanism this document introduces stay inside ADR-010's portable subset, or does correctness come to depend on a provider-unique managed service?* Decisive throughout (§7.2) — every element introduced either falls inside the named subset directly (managed PostgreSQL, container orchestration, object storage, continuous write-ahead-log archiving) or is infrastructure configuration ADR-010 §20.1 and ADR-021 already accept as provider-specific-but-necessary (key-management-service binding, IAM/account-boundary scoping), never a new correctness dependency on a provider-unique feature.
  2. *For each of the five named obligations, does an already-fixed mechanism discharge it directly, or must this document design a new one?* Resolved per obligation (§8) — four of the five (the replica/admission sequence, the anchor's storage medium, the key-management credential, and the backup mechanism's own provisioning and catalog) are discharged by applying this document's own general mechanisms (the tier-instantiation module, §5's secret-injection mechanics, §8.2's own object-storage/write-once-retention pattern reapplied at §8.5) to the specific case named, requiring no obligation-specific mechanism beyond choosing which already-portable technical means meets the obligation's own stated requirement (§8.5's point-in-time-recovery choice); the one exception (the per-provider resolution table, obligation four) required one new, but genuinely small, operational fact — a static provider-to-service correspondence — completing, never re-deciding, ADR-021's own default.
  3. *Does per-tier or per-region identity require a new database structure, or can it be resolved entirely by deploy-time configuration injection?* Decisive against a new structure (§9) — a database-stored answer to "which tier/region am I" is circular for the identical reason `08-multi-region-distribution-design.md` §6.2 already reasons region resolution cannot reuse an already-authenticated read path; every candidate structure checked, including the backup catalog's own storage-location reference, resolved to "not owed."
  4. *Does Production's own protection require a new gate this document owns, or does infrastructure-level credential scoping compose with the existing pipeline gate?* Decisive for composition, never a new gate (§6) — the pipeline's own mandatory-check list and no-bypass rule are `02-ci-cd-pipeline-design.md`'s in full; this document's own contribution is making the credential-bearing path to Production structurally singular, so that whatever gates that document fixes cannot be bypassed by a second, undocumented path.
- **Context:** This is the first document of Layer 5, opening it with an unusually dense inheritance: five already-written documents across Layers 1, 2, 4, and 5 each named this document, explicitly, as the place a provisioning obligation they could not discharge themselves would be discharged — the fifth, `06-incident-response-and-recovery-design.md`, itself a Layer 5 document, the first of the five obligations to arrive from this document's own layer rather than from an earlier one. Discharging all five, honoring each one's own stated constraint, is this document's own defining task, not an appendix to its environment-tier and configuration-boundary design.
- **Decision:** (1) Each environment tier is a structurally separate, complete infrastructure instantiation, sharing no database, credential, or network path with another tier by default; the same built artifact is promoted between tiers unchanged, never rebuilt (§3). (2) Tier and region identity are both externalized to deploy-time configuration injection, never hardcoded or branched on inside any component module (§4). (3) A secret reaches a running deployment only by injection at the point it runs, from a store scoped to exactly one `(tier, region)` intersection, never carried across a promotion (§5). (4) Production is protected by making its own credential-bearing infrastructure path structurally singular — held only by the pipeline's own Production-scoped service identity — so every path into Production necessarily passes through whatever gates `02-ci-cd-pipeline-design.md` fixes, without this document redesigning those gates (§6). (5) Every mechanism above is Terraform/OpenTofu-defined and stays inside ADR-010's portable subset, with every non-strictly-portable element (key-management-service binding, IAM/account-boundary scoping) justified by the identical reasoning ADR-010 and ADR-021 already established for infrastructure-configuration-versus-correctness-dependency (§7). (6) Each of the five named provisioning obligations is discharged: the per-region read replica and region-admission sequence via one parameterized tier-instantiation module and logical replication from a designated write-authority region (§8.1); the external anchor's storage medium as object storage with provider-native write-once retention bound to the existing audit-retention floor (§8.2); the key-management-service access credential as an ordinary instance of this document's own general secret-injection mechanics, with no obligation-specific mechanism (§8.3); the per-provider key-management-service resolution as a small, static table completing ADR-021's default (§8.4); and the backup mechanism's storage medium, granularity, consistency, retention, residency-scoped placement, and catalog locatability, discharged via continuous point-in-time recovery to the identical class of object storage already provisioned for the external anchor, bound to the identical retention floor, and parameterized by the identical `(tier, region)` module invocation (§8.5). (7) This document owes no new structure to `02-platform-data-model-design.md` (§9). (8) One new audit event type, `secret-injection-refusal`, is added, for the one genuinely new definitional fact this mechanism introduces (§11).
- **Alternatives considered:** *A single, shared database distinguished by a tier column, rather than structurally separate per-tier instantiation* — rejected under criterion 3 in shape and under §3.1's own reasoning; it would make tier isolation an application-layer predicate a query must remember to apply, the identical failure mode already rejected for tenant isolation and for builder-facing stage isolation. *Storing tier/region identity, or the write-authority region designation, as a database row* — rejected under criterion 3; each is circular, requiring a replica to already know which database to query before it could learn the answer stored there. *A dedicated key-management-service resolution table, distinct from `platform.host_providers`* — rejected under criterion 2; the existing column's own deliberately generic shape already accommodates the content without a new structure. *A second, dedicated Production-admission gate distinct from the Production Deploy Gate's own residency clause* — not adopted, consistent with `08-multi-region-distribution-design.md` §9.2's own prior rejection of the identical alternative for the same reason: the existing clause already reaches this action, and a second gate would duplicate rather than strengthen it. *Treating the key-management-service binding as falling outside ADR-010's subset and requiring a new portability exception* — rejected under criterion 1; `04-security-controls-design.md` §8.1 already reasoned this correctly, and this document applies the identical reasoning rather than re-opening it. *A scheduled snapshot cadence for the backup mechanism, rather than continuous point-in-time recovery* — rejected under criterion 2; a scheduled cadence, however tightly bounded, carries a nonzero recovery-point gap that cannot be shown to meet the zero data-loss tolerance §8.5 discharges. *A dedicated backup catalog table inside `02-platform-data-model-design.md`'s schema* — rejected under criterion 3, on the identical circularity reasoning already applied to tier/region identity and the write-authority designation: a restore must locate a backup without depending on the very database instance it may be recovering.
- **Consequences:** Binds `02-ci-cd-pipeline-design.md` to the fact that Production's own deploy-credential path is structurally singular (§6.1) — that document's own gates are what the pipeline's sole credential is permitted to exercise, and this document predetermines neither the gates nor their mechanics. Binds `04-observability-and-monitoring-design.md` and `05-release-and-rollback-design.md` to the tier-and-region-scoped infrastructure shape of §3–§4 as the substrate their own mechanisms instrument and release against, without this decision designing either. Discharges, in full, the provisioning obligations `08-multi-region-distribution-design.md` §13.1, `08-audit-and-traceability-design.md` §10.1, and `04-security-controls-design.md` §8.1 each named to this document; the provider-binding obligation `02-platform-data-model-design.md` §8.3 named jointly to this document and to `04-security-controls-design.md`; and the backup-provisioning and backup-catalog obligation `06-incident-response-and-recovery-design.md` §6.2, §6.3, and §11 named to this document. Adds no obligation to `02-platform-data-model-design.md`'s schema (§9) and exactly one new `event_type` to `08-audit-and-traceability-design.md`'s model (§11).

## 15. Binding Rules

These rules hold for every tier, region, secret, and configuration value this document governs, and are subordinate to the charter.

- **Each environment tier is a structurally separate, complete infrastructure instantiation.** No tier shares a database, credential, or network path with another by default; the same built artifact is promoted between tiers unchanged, never rebuilt (§3).
- **Production is the one tier whose own instantiation is itself further instantiated once per operating region**, composing directly with `08-multi-region-distribution-design.md` §3.2; Development and Staging carry no equivalent minimum (§3.3).
- **No component module contains a hardcoded tier or region identifier.** Both are resolved entirely through deploy-time configuration injection, never a branch in source (§4.1).
- **A configuration value is refused, not applied, where its owning `(tier, region)` intersection cannot be established** — enforced at infrastructure-as-code apply time, before any deployment target exists to misapply it (§4.4).
- **A secret is never committed, in any tier, and reaches a running deployment only by injection at the point it runs**, scoped to exactly one `(tier, region)` intersection and never carried across a promotion (§5).
- **No standing human credential reaches Production's own infrastructure directly.** The only credential capable of writing to Production belongs to the pipeline's own Production-scoped service identity, itself an ordinary injected secret under this document's own mechanics (§6).
- **Every mechanism this document fixes stays inside ADR-010's portable subset**, defined in Terraform or OpenTofu; any element that is infrastructure configuration rather than a portable-subset member is justified explicitly against ADR-010's and ADR-021's own reasoning, never adopted silently (§7).
- **Each of the five named provisioning obligations is discharged as stated in §8, honoring the constraint it arrived with** — none is silently dropped, and none is redesigned beyond what the constraint required.
- **The backup mechanism is provisioned as continuous point-in-time recovery, never a scheduled snapshot cadence** (§8.5), because only a zero-gap mechanism can be shown to meet the zero data-loss tolerance the mechanism is held to; its own object-storage archive is retention-locked to the identical ≥ 13-month floor as the external anchor, parameterized per `(tier, region)` so a Jurisdiction-Restricted or Regime-Governed tenant's backup is provisioned only within its own permitted region(s), and its own catalog is the archive's own structured listing, never a `02-platform-data-model-design.md` schema row.
- **This document owes no new structure to `02-platform-data-model-design.md`.** Every fact its own mechanisms need is either already generically accommodated by an existing structure or is deploy-time infrastructure configuration that cannot live inside the database it configures access to (§9).
- **This document's own tiers, credentials, and infrastructure-as-code modules share no mechanism with `02-builder-facing-environment-management-design.md`'s builder-facing stages, promotion, or evidence** (§10).
- **Every control this document fixes produces the evidence §11 names**, landing under Security events as the closest fit; no event is recorded for an ordinary, successful injection or a routine provisioning action.
- **Everything remains domain-neutral and platform-level.** No jurisdiction, regulatory regime, geographic region, or cloud-provider-unique product is named as a correctness dependency anywhere in this document; every mechanism above remains valid for any tenant, in any operating region, on any ADR-010-viable provider.
- **This document records exactly one ADR.** ADR-046 (§12) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, boundary, or obligation the cited specification and cited upstream design documents already fix.
