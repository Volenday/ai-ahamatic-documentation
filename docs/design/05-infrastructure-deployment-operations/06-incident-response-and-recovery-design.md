## 3. Incident and Incident Recovery, Realized as Concrete Mechanism

Spec §3 fixes an incident as "a classified condition in which the platform has failed, or is failing, to hold a guarantee it must — an invariant, a guardrail floor, a security posture, or a non-functional target — such that the failure requires containment and recovery rather than routine reaction," containment as "the act of bounding an incident so it does not spread or worsen," and incident recovery as "the restoration of the platform to a **last known-good state**... together with the learning that follows." This section states what each is over the mechanisms this library already fixes.

### 3.1 An Incident Is a Declared, Evidenced Condition — Not a Second Runtime Check

An incident is never independently detected by a mechanism this document builds. It is **declared** — from a runtime signal `04-observability-and-monitoring-design.md` §6–§7 already produces, from a security-review or vulnerability finding `04-security-controls-design.md` §4–§5 already classifies, or from a direct human report reaching the same escalation routing `05-meta-operations/04-human-in-the-loop-protocol.md` already owns — and, once declared, is classified (§4), contained (§5), and recovered (§6, §9) under this document's own ordering. This document introduces no second detection surface parallel to observability's own signal mechanism; a condition this document has no signal, finding, or report evidencing is not an incident this document's mechanism can act on, consistent with the deny-by-default rule already binding every mechanism this document composes with.

### 3.2 The Three Boundaries, Held From This Document's Side

- **A monitoring signal is not an incident.** `04-observability-and-monitoring-design.md`'s own §4 mechanism grades a runtime signal to determine alerting and the bound on autonomous reaction; this document grades the resulting incident for containment and recovery, per §4 below. Spec §3's own words hold exactly: "the signal and its threshold remain owned by `04-devops-and-cloud-infra/04-observability-and-monitoring.md` and are never redefined."
- **Incident recovery is broader than a rollback and than a self-correction.** A rollback (`05-release-and-rollback-design.md`) reverses a released change; a self-correction (`05-meta-operations/07-self-correction-and-fallback-protocol.md`, Layer 6, not yet written) corrects a running change in place; an incident recovery may invoke either, or a restore from backup (§6, this document's own genuine contribution), as the incident requires — this document owns the containment-first ordering, the restore guarantee, and the learning response that surround whichever recovery action is invoked, and redefines none of them (§9).
- **Recovery is carried out over numbers and mechanisms other documents own.** A recovery restores a state holding every invariant of `02-governance-and-security/01-system-invariants.md` §4 and every applicable quality floor of `03-software-and-architecture/06-non-functional-requirements.md`, within the mean-time-to-recovery floor and the data-loss and migration ceilings of its §7; this document requires the guarantee and cites the number, minting none.

## 4. Incident Severity Classification — Its Relationship to Signal Severity

This is the document's first genuine decision, and it is made explicit before anything else is designed on top of it, per the ticket's own instruction.

### 4.1 The Relationship, Stated Explicitly

**Incident severity and signal severity are not two independently computed classifications, and they are not the same classification under two names. They are one severity value, resolved once, read at two distinct points for two distinct purposes.** `04-observability-and-monitoring-design.md` §4.1 already fixes that every metric, log-emission point, and trace span carries a `severity_source` tag, fixed at signal-definition time, and that at evaluation time "the alert-evaluation mechanism reads this tag and attaches exactly the severity spec §5.2's own table already fixes for that class... severity is never derived from how far or how long a threshold has been breached, only from which guarantee the breached tag names." Spec §4's own second rule states the identical discipline from this document's side: "Severity is inherited, never invented... where it corresponds to a runtime signal, it carries the runtime severity `04-devops-and-cloud-infra/04-observability-and-monitoring.md` §5 assigns." Where an incident is declared or fed by one or more runtime signals, this document's own classification act is a **read of the already-computed tag value**, never a second, independent severity determination — the identical "attach, never recompute" discipline `04-observability-and-monitoring-design.md` §4.1 already holds, extended here to the incident it feeds rather than reargued from scratch.

Where an incident is declared or fed by more than one signal, its severity floor is the **highest** severity value among the contributing signals' own tags — a `max()` over already-resolved values, never a re-derivation of any one of them. Where an incident is declared with no originating signal at all — a direct human report, or a condition established by a mechanism other than observability's own (a security-review finding, a compliance-review escalation) — this document classifies it directly against the identical Critical/High/Moderate/Low scale `02-governance-and-security/02-security-policy.md` §6 already owns, per spec §4's own table, because that is the only case in which no already-computed tag value exists to read.

### 4.2 Why This Is Not Two Competing Vocabularies

Both classifications trace to the identical scale, owned by the identical document (`02-governance-and-security/02-security-policy.md` §6), inherited and never redefined by either `04-observability-and-monitoring-design.md` or this document. What differs is what each classification is *of* — observability's own tag classifies a **measurement**; this document's own classification grades the **condition the measurement may declare or feed**, per spec §3's own boundary. This is why spec §3 states the two are "complementary and never redundant" without stating they are independent: complementary describes two facets of one value, applied to two different subjects, never two values that could disagree.

### 4.3 What This Document Adds Beyond the Inherited Value

Three rules bind an incident's own classification beyond the inherited severity floor, none of which observability's own signal-severity mechanism owns or needs, because none of them concerns a measurement — each concerns the response to the condition the measurement declares:

- **A runtime invariant violation is always a Critical incident, never routed through this document's own classification step at all.** `04-observability-and-monitoring-design.md` §6.4 already fixes that a signal whose tag names an invariant already violated, or a vulnerability already classified Critical, "is never routed through §6.1–§6.3 at all — it halts and escalates immediately... bypassing the ladder entirely." This document inherits the identical bypass: such a condition is never classified by this document's own mechanism as though it required a determination — it is Critical by the tag's own content, and it halts and escalates per `02-governance-and-security/01-system-invariants.md` §3, exactly as observability's own signal does.
- **Production weights urgency, never severity.** Consistent with observability's own §5 finding — that tier-scoped configuration governs only a non-invariant-tagged signal's *routing urgency*, never its severity — this document's own tier-urgency rule (spec §4's "Production weights urgency upward") is realized as the identical, already-fixed tier-scoped urgency configuration `04-observability-and-monitoring-design.md` §5 already provisions, extended here to containment priority and response-team routing rather than reargued as a second tier-weighting mechanism. An incident's severity class is identical at every tier for an identical inherited value; only how urgently a response proceeds differs.
- **Uncertainty resolves upward, at the incident level, independently of the signal level.** Where an incident's own scope spans more than what any single contributing signal's tag establishes — a compound condition, a still-developing report — and the incident's own severity cannot yet be bounded by the inherited maximum alone, it is classified at the highest severity its possible impact allows, per spec §4's own uncertainty rule and the deny-by-default discipline every mechanism in this library already applies.

## 5. Containment-First Ordering — Enforced in Mechanism

Spec §5 fixes that containment precedes recovery, always; that containment never itself breaches a guarantee; that recovery restores a last known-good, invariant-holding state within the floor `03-software-and-architecture/06-non-functional-requirements.md` §7 owns; and that a response closes with learning. This section states how the ordering is enforced structurally rather than declared as a discipline an actor could disregard.

### 5.1 What "Containment" Concretely Is, Realized Against Already-Fixed Boundaries

Containment is not a new isolation mechanism this document invents. It is the act of **confining a response's own reach to the incident's own already-structurally-enforced boundary**, before any recovery action is invoked:

- **Where an incident is tenant- or application-scoped**, containment is realized by the fact that every write and read this library's own mechanisms permit already passes through the Registry Accessor, the Context Resolution Point, and the connection-scoping function `02-tenant-isolation-and-access-control-design.md` §3–§5 fixes — a response confined to the incident's own tenant or application schema cannot, by that same structural chokepoint, spread beyond it. This document adds no new confinement mechanism for this case; it inherits the one already-structural guarantee tenant isolation already provides.
- **Where an incident is region-scoped and release-caused**, containment is realized concretely as **halting the region-sequential rollout before it advances to the next region**, reusing `05-release-and-rollback-design.md` §11.1's own mechanism directly: because a Production release is "a region-sequential rollout, never an atomic all-region cutover," a release-caused incident detected in one already-reached region is contained the moment the rollout's own next-region advance does not proceed — bounding the incident's own spread before any rollback of the regions already affected is even attempted. This is the concrete realization of spec §5's "bound before it is widened" register, composing directly with a mechanism this document does not own and does not redesign.
- **Where an incident is actor- or credential-scoped**, containment is a response confined to the specific actor or grant the incident traces to, never a platform-wide action, on the identical least-privilege discipline `02-governance-and-security/03-access-control-and-tenancy-model.md` §8 already fixes and this library already applies throughout.

### 5.2 The Ordering Itself, Enforced Structurally

**Containment precedes recovery because classification (§4) precedes both, and no recovery action this document may invoke — a rollback, a self-correction, or a restore — carries its own severity or scope determination independently of this document's own classification step.** Every recovery action's own mechanism (`05-release-and-rollback-design.md` §4–§5's mandatory-path check; the self-correction ladder's own per-precondition clearing; §6.4 below's restore guarantee) requires, as a precondition already fixed by its own owning document, that the change or action be shown — not assumed — invariant-holding and within bounds before it proceeds. A recovery action attempted before an incident's own scope has been established therefore cannot clear that precondition, because the reference state ("last known-good," "within bounds") is exactly what classification and containment establish. This is not a rule an actor could choose to disregard: it is the same structural fact `05-release-and-rollback-design.md` §4.3 already reasons for its own mandatory-path check — a further condition inside a chokepoint every recovery action already passes through, never a second gate this document builds beside it.

- **Containment never itself breaches a guarantee.** No containment action — a rollout halt, a session or grant revocation, a confinement to an already-isolated boundary — degrades tenant isolation, authorization, secret confidentiality, data integrity, residency, or backward compatibility; a containment step that could only bound the incident by breaching one is refused and escalated (§7) instead, per the identical precondition-clearing gate every action in this library already passes through.
- **Recovery restores a last known-good, invariant-holding state within the floor `03-software-and-architecture/06-non-functional-requirements.md` §7 owns**, discharged by whichever recovery action is invoked (§9) — this document cites the mean-time-to-recovery floor (≤ 60 minutes, restoration of the availability floor) and the migration duration and downtime ceiling (≤ 4 hours, zero data loss on committed data) without minting either.
- **The response closes with learning.** The attributable, tamper-evident record of the incident and its response is owned by `08-audit-and-traceability-design.md` (§12 below); how a post-incident review is requested, routed, recorded, and resolved is owned by the Meta-Operations documents this document composes with and does not design. This document requires the learning step; it does not define how the review is carried out — spec §5's own closing bullet, and this document adds nothing to it.
- **The ordering holds on every path**, urgency, tier, and severity alike; a low-severity or earlier-tier incident is contained and classified in the identical order, never skipped ahead to recovery because it appears low-risk.

## 6. Backup and Restore Guarantees

This is the largest genuinely open area in this ticket. A grep for "backup" across `docs/design/` returns no hit outside `implementation-document-map.md`'s own row for this document — no prior design document has realized any part of spec §6.

### 6.1 The Boundary Against Rollback, Stated Explicitly

A **rollback** (`05-release-and-rollback-design.md`) reverses a **released change** to its immediately-prior artifact version, or — for a state-changing release — to the state a migration's own recorded, re-confirmed reversal procedure restores. It is scoped to one release's own delta, and its "last known-good" reference is captured at the moment that specific release's own Deploy Gate evaluation begins.

A **restore**, this document's own mechanism, recovers committed data from an independently-maintained **backup** — a point-in-time snapshot of a tier's own committed data, taken on a schedule independent of any release. Restore is the recovery action a response invokes where the loss or corruption is **not release-shaped at all** — an operational error, a hardware or infrastructure fault, a data-affecting incident whose migration's own reversal procedure has itself failed or been exhausted, or corruption whose cause cannot be traced to any specific release's own rollback path. Restore may also reach further back in time than any release's own last-known-good reference preserves, because a backup's own retention is independent of how many releases have occurred since.

**The two compose, never substitute for each other.** Where an incident is release-caused and a rollback path exists and has been shown, at release time, to meet its ceiling (`05-release-and-rollback-design.md` §4–§5), rollback is the recovery action of first resort — it is the narrower, faster, already-validated path. Restore is the recovery action a response reaches for where no such path exists, or has failed, or the loss did not originate in a release at all. This document does not design a second reversal mechanism competing with rollback's own; it designs the recovery action rollback does not cover.

### 6.2 The Provisioning Obligation, Handed to `01-environment-and-configuration-design.md`

**No mechanism cited to this document already provisions backup infrastructure.** `01-environment-and-configuration-design.md` §8 discharged four named provisioning obligations — none of them a backup or snapshot mechanism. This document is the first to hand that document a fifth: the backup storage medium, its snapshot or point-in-time-recovery mechanism, and its retention configuration, each provisioned per `(tier, region)` intersection on the identical infrastructure-as-code discipline that document's §7 already fixes for every other mechanism it provisions — never a new provisioning pattern this document invents.

This document requires, and does not itself design the provisioning of, three properties the backup mechanism must be **shown**, at provisioning time, to deliver — the identical "shown, not assumed" discipline `05-release-and-rollback-design.md` §4.2 already applies to a rollback path:

- **A backup granularity sufficient to meet the zero data-loss tolerance a restore is held to (§6.4).** Whether this is met by point-in-time recovery (continuous write-ahead capture) or by a scheduled snapshot cadence bounded tightly enough is a technical means this document does not choose — that choice, and the showing that it meets the ceiling, is `01-environment-and-configuration-design.md`'s to design when it discharges this obligation, exactly as it already independently chose the replication mechanism for the platform-global read replica (its own §8.1) without this document, or any document naming the obligation to it, dictating the mechanism.
- **A backup consistency guarantee sufficient to meet the invariant-holding requirement a restore target must satisfy (§6.4).** A backup captured mid-write, without a database-consistent capture discipline, would not itself be a "last known-good, invariant-holding state" — this document requires the provisioned mechanism deliver a consistent capture; it does not design the consistency mechanism itself.
- **A retention window meeting the audit and log retention floor already fixed** (`03-software-and-architecture/06-non-functional-requirements.md` §10, ≥ 13 months), so that a backup remains available for at least as long as the audit trail that would reference an incident it recovers from.

### 6.3 Where a Backup May Be Stored — the Residency Interaction, and Its Honest Limit

A backup is committed data at rest somewhere, and `06-compliance-and-data-residency-design.md` §7 already fixes that "storage and processing location follows the attaching obligation, never convenience" for Jurisdiction-Restricted and Regime-Governed data. **This document does not claim the Region Boundary Check already covers backup placement, because it does not.** That mechanism's own §3.5 states its honest limit plainly: its structural guarantee binds only "the platform's own code path" — a request reaching a scoped connection through the Registry Accessor and connection-acquisition function — and explicitly is "not a claim about where bytes are physically stored, replicated, or routed at the infrastructure layer." A backup or snapshot mechanism operating beneath the application code path (an infrastructure-level, database- or volume-level capture) is not a request that mechanism's own code-path guarantee reaches.

**This document's own requirement, folded into the same handover as §6.2:** the infrastructure-as-code module `01-environment-and-configuration-design.md` provisions for the backup mechanism must itself be parameterized so that a Jurisdiction-Restricted or Regime-Governed tenant's own backup is provisioned within the region(s) its own Resolved Residency Obligation permits — the identical `(tier, region)`-scoped provisioning discipline that document's §4 already applies to every other structure it provisions, extended here to a mechanism that operates outside the code-path boundary the Region Boundary Check governs. This is a provisioning-time requirement, discharged when the obligation of §6.2 is discharged, never a runtime check this document invents to compensate for a boundary residency's own mechanism honestly states it does not reach.

### 6.4 The Guarantee, Realized

Spec §6's six bullets are realized as follows, each citing rather than minting the numeric floor it depends on:

- **Committed data is recoverable to a valid state.** The provisioned backup mechanism (§6.2) is the means; a restore never returns committed data to an invalid, inconsistent, or partially applied state, because the consistency guarantee §6.2 requires be shown rules out a torn capture from ever being a valid restore target.
- **A restore records no data loss**, consistent with the zero data-loss tolerance of `03-software-and-architecture/06-non-functional-requirements.md` §7 — "Zero. No rolling window may record a nonzero count of data-loss incidents affecting committed data." This document requires the guarantee and cites the tolerance without restating the number; the residual limit this guarantee carries is stated plainly at §6.5.
- **A restore returns to a last known-good, invariant-holding state** — the backup's own point-in-time capture, shown consistent at capture time (§6.2), never a state assumed valid because a backup exists in principle.
- **A restore never recovers by breaching a guarantee.** No restore degrades tenant isolation, moves data across a region boundary in violation of residency, or exposes a secret; a restore that could only complete by breaching a guarantee is refused and escalated (§7) instead. A restore of a tenant's own schema restores that tenant's schema alone, on the identical isolation boundary every other write in this library already respects (§5.1); a credential column already stored ciphertext (`tenant_<id>.external_system_connections.credential_ciphertext`, `02-platform-data-model-design.md` §3.2) before it was ever backed up, so a restore never re-exposes a secret a backup mechanism this document requires be no more permissive than the write path that produced the content it captures.
- **A restore completes within the ceiling `03-software-and-architecture/06-non-functional-requirements.md` §7 owns.** Because restoring committed data is, by construction, always data-affecting, a restore is always measured against the migration duration and downtime ceiling — "completes... within 4 hours, and introduces no downtime beyond the availability budget of §6" — never the narrower, code-level 60-minute floor `05-release-and-rollback-design.md` §8.1 reserves for a rollback that requires no data reversal. This document mints no third ceiling; it reads the existing split rather than collapsing the two into one.
- **A restore is itself a governed, observable, reversible action.** A restore is captured as evidence (§12), is subject to every invariant exactly as any other consequential change is, and reaches Production only through the identical structurally singular Production credential `05-release-and-rollback-design.md` §9.2 already fixes — a human authorization is permission for the pipeline to execute the already-designed mechanism, never a channel through which the authorizing human writes to Production directly — this document composes with that argument rather than re-deriving it, because a restore, like a rollback, is an infrastructure write to a tier a human steward never holds a standing credential for.

### 6.5 Two Residual Limits, Stated Plainly Rather Than Overclaimed

**First — the recovery-point gap.** Whether the provisioned backup mechanism achieves a zero-gap recovery point (continuous capture) or a bounded-but-nonzero gap (a scheduled snapshot cadence) is a technical choice this document does not make (§6.2). Where the provisioned mechanism cannot be shown to deliver a zero-gap recovery point, committed data written after the most recent backup and before the incident is not restorable by this mechanism — a real limit this document states rather than assumes away, analogous in kind, though not in cause, to `05-release-and-rollback-design.md` §5.3's own erasure limit: a guarantee this document requires be met is not automatically met by the existence of a backup mechanism, and the showing that it is met belongs to whichever document discharges §6.2's obligation.

**Second — restore is a terminal instrument, not an infinitely regressing one.** A restore's own reversibility is bounded by whether an earlier backup point exists to fall back to if the restore itself proves wrong. Where none does — the incident being recovered from predates every retained backup, or the restore consumes the oldest retained point — this document does not claim a further, guaranteed reversible path beneath it; the mandatory human-escalation threshold this document fixes (§7) is what a response reaches for instead of an infinite chain of guaranteed reversibility this mechanism cannot honestly provide.

## 8. Prohibited Unilateral Recovery Actions — Enforcement, Not Policy

Spec §8 enumerates nine prohibited actions. A prohibition that is technically reachable is a policy, not a mechanism; this section states, for each, the structural gate that makes it unreachable rather than merely disallowed.

**The single enforcing fact, stated once rather than nine times.** `05-meta-operations/01-agent-operating-charter.md` §5 already fixes that *every* autonomous action — including every recovery action a response invokes — clears five preconditions before it proceeds: granted authority, in-scope, invariant-holding, a reversible/recoverable path, and minimum traceability; and that "where any precondition above cannot be established, the action is not taken autonomously; it is halted and escalated" — before that same bullet continues, uncited here, to key the rule to the deny-by-default rule of `02-governance-and-security/01-system-invariants.md` §3. That document's own §6 further fixes that the agent may "contain an incident and recover to a last known-good state within the containment-first ordering of `04-devops-and-cloud-infra/06-incident-response-and-recovery.md`, provided the response takes no prohibited unilateral recovery action (that document's §8) and crosses no mandatory escalation threshold (its §7)." This document does not build a second gate that checks its own prohibitions — it supplies the *content* the charter's own already-structural precondition-clearing mechanism checks against, exactly the same "consume a fixed gate, supply its content" pattern `05-release-and-rollback-design.md` §9 and `04-observability-and-monitoring-design.md` §7 already use for their own trigger sets. A prohibited action is therefore not reachable by any autonomous path in this library, because no autonomous action of any kind proceeds without first clearing the charter's own gate against this document's own content.

| Spec §8 Prohibition | What Makes It Technically Unreachable |
|---|---|
| A recovery that breaches an invariant or guardrail floor | Every recovery action (rollback, self-correction, restore) re-clears every invariant as one of the charter's own five preconditions before it proceeds; a breaching action fails that precondition and is refused before execution, never merely disallowed after the fact. |
| A recovery that sacrifices committed data | The identical invariant precondition (INV-04) applies; every recovery action reaches data only through the Entity Access Gateway / connection-acquisition function this library's every write already passes through, which never grants a code path around INV-04's own check. |
| An unpromoted change to Production | `01-environment-and-configuration-design.md` §6.1's structurally singular Production credential — consumed and not redesigned by `05-release-and-rollback-design.md` §9.2 — means the only identity capable of writing to Production is the pipeline's own service identity; a recovery reaching Production without a governed promotion has no credential to write with — there is no second, credential-bearing path this document's own mechanism could use even in error. |
| An irreversible recovery | The charter's own reversible-path precondition (INV-08) is checked before any action proceeds; `05-release-and-rollback-design.md` §4's "shown, not assumed" discipline and this document's own §6.2 provisioning requirement both feed that same precondition — an action lacking a validated path fails it structurally. |
| Recovery past the autonomous bound | The self-correction ladder's own attempt ceiling and `05-release-and-rollback-design.md` §8.4's recovery-target escalation condition are both, per §7's table above, mandatory-escalation triggers this document's own content feeds into the charter's gate; reaching either forbids further autonomous action per the ladder's own §8. |
| Suppression of the incident record | `08-audit-and-traceability-design.md` §6.2 already fixes that the only permitted write to an `audit_events` table is an insert, enforced at the database-role privilege level — no code path this document's mechanism uses holds update or delete privilege against the record of an incident, regardless of intent. |
| Reclassifying to avoid a response | §4 above fixes that severity is a read of an already-computed tag value, never a value this document's own mechanism computes fresh at will; there is no code path by which a response lowers a severity that traces to an inherited tag, because the tag, not a discretionary judgment, is what §4.1's mechanism reads. |
| Continuing a breaching change | `02-governance-and-security/01-system-invariants.md` §3's halt-and-escalate rule is not a step this document's mechanism could skip — every invariant check that establishes a breach is the identical mechanism that halts execution immediately, per that document's own binary, blocking-check design. |
| Uncertainty resolves against unilateral action | The charter's own deny-by-default precondition-clearing rule already applies this by construction: where a precondition cannot be established, the action is refused, never permitted on a favorable assumption. |

- **Criteria applied, and how each resolved:**

## 16. Binding Rules

These rules hold for every incident and response subject to this model and are subordinate to the charter.

- **An incident is declared from an already-owned signal, finding, or report; this document builds no second detection surface** (§3.1).
- **Incident severity is a read of an already-resolved value, never an independent computation** — the maximum across every contributing signal's own tag where more than one applies, and classified directly against the same scale only where no signal originates it; a runtime invariant violation or an already-Critical vulnerability bypasses this document's own classification step entirely (§4).
- **Containment is confinement to already-structural boundaries, never a new isolation mechanism**, and containment-before-recovery ordering is structural because every recovery action's own precondition-clearing mechanism requires the reference state classification and containment establish (§5).
- **Restore is a recovery action distinct from rollback**, invoked where the loss is not release-shaped or where a release's own rollback path has failed or does not exist; the two compose and never substitute for each other (§6.1).
- **Backup-mechanism provisioning, its residency-scoped placement, and its own catalog's locatability are each a named handover to `01-environment-and-configuration-design.md`, never designed or quietly provisioned here** (§6.2–§6.3, §11).
- **A restore's guarantee is realized against already-owned ceilings, never a third one this document mints; its residual limits — the recovery-point gap and its own bounded reversibility — are stated plainly, never implied closed** (§6.4–§6.5).
- **Every mandatory-escalation trigger composes with routing already fixed elsewhere; this document states which condition matches which enumerated class, never the request/routing/resolution mechanics** (§7).
- **Every prohibited unilateral recovery action is content fed to an already-structural precondition-clearing gate, never a second gate this document builds; a prohibition that were merely declared would be a policy, not a mechanism** (§8).
- **Rollback and self-correction are recovery actions this document invokes and never redesigns** (§9).
- **G-5 is discharged in full by `05-release-and-rollback-design.md`'s own prior realization; this document's own contribution runs to C-16's continuous, non-release-gated guarantee** (§10).
- **This document owes no new structure to `02-platform-data-model-design.md` and adds exactly three new audit-event types** — `incident-declared`, `incident-contained`, and `restore-executed`, none reconstructable from an already-existing record (§11–§12).
- **This document records exactly one ADR.** ADR-051 (§13) is the genuine, independent set of severity-relationship, containment-enforcement, prohibition-enforcement, and backup/restore decisions this document makes; every mechanism it composes with remains owned, in full, by the document that designed it.
- **Everything remains domain-neutral and platform-level.** No severity rule, containment mechanism, backup guarantee, or escalation threshold in this document encodes the characteristics of any single domain; every mechanism above remains valid for any tenant, in any operating region, on any provider-neutral infrastructure tooling.
