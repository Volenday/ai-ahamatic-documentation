This section states what each means as a concrete, testable obligation over the platform's own already-designed structure, without adding or removing a layer.

| Layer | What Spec §4 Requires | Realized Against |
|---|---|---|
| Unit | Each single-component unit of platform-layer code behaves correctly in isolation, holding only its attributed component's responsibility. | The seven component modules and the `guardrail/` module `03-architecture-realization-design.md` §3 fixes; a unit test's own attribution is checkable against the module a piece of code physically lives inside. |
| Integration | Behavior across a permitted dependency direction is correct, and no forbidden or reverse dependency is exercised. | The dependency-direction mechanism (ADR-014, `03-architecture-realization-design.md` §4) proves the structural absence of a forbidden direction at build time; an integration test is the runtime complement, exercising an *allowed* edge's actual behavior — the mechanism proves a forbidden edge cannot exist in the source graph, an integration test proves an allowed edge behaves correctly when exercised. | Contract | A change to a builder-, built-app-, or integration-facing contract does not silently break an existing consumer outside a managed, announced path. | `05-api-contract-design.md`'s breaking-change detection (ADR-032), already placed at the Merge Gate (`02-ci-cd-pipeline-design.md` §5.1) — this document's contract-test obligation is satisfied by that existing mechanism's own finding; this document adds no second detection mechanism. |

## 4. Minimum Coverage and Pass-Rate Thresholds, Enforced

Spec §5 fixes the coverage and pass-rate floors; spec §6 fixes their tier applicability. This section states how each is enforced as mechanism.

### 4.1 Coverage Thresholds, Enforced

| Category | Floor (Spec §5.1) | Enforcement |
|---|---|---|
| Invariant- and guardrail-enforcing paths | 100% | Measured per code path against the coverage-instrumentation tool's own path-level report; a path is attributed to this category where it is exercised by, or gates on, one of the nine checks `01-invariant-enforcement-design.md` §5 specifies, a release gate of `01-business-and-ux/02-prd.md` §5, or the shared `guardrail/` module `03-architecture-realization-design.md` §3 fixes. The Isolation and Trust module's own coverage obligation (§6 below) is a further, non-generic bar layered atop this floor for that module specifically — not a substitute for it. |
| All other platform-layer code | ≥ 90% | Measured identically, over every path not attributed to the row above. |

Coverage is measured over platform-layer code only, per spec §5.1's own scope rule; a builder's own tests for their own built artifact are never counted toward or against either floor, consistent with the builder/built separation `03-architecture-realization-design.md` §5–§6 already makes architecturally true.

### 4.2 Pass-Rate Threshold, Enforced

Spec §5.2 fixes a 100% pass-rate floor with no partial-pass or tolerated-failure percentage. Enforcement is binary at the gate: the required test set applicable to a gate (§9.1 below) either reports every test passing, or the gate's own pass condition for this document's contribution is not met. A test whose result cannot be established as deterministic is governed by §8, never counted toward this pass rate — the same rule spec §5.2 already states, realized as a concrete resolution procedure there.

### 4.3 Tier Applicability, Enforced

Spec §6 fixes that invariant-quantifying thresholds bind at every tier, that the full threshold set binds Production in full, and that a later tier re-evaluates fresh rather than inheriting an earlier tier's pass, naming Development, Staging, and Production directly as the tiers in question. This document enforces that rule against those same three tiers, without redefining them:

| Rule (Spec §6) | Enforcement |
|---|---|
| Invariant-quantifying thresholds bind at every tier | The 100% coverage floor for invariant- and guardrail-enforcing paths, and the 100% pass rate for the invariant-conformance, security, tenant-isolation, and data-integrity test sets, are evaluated identically at Development, Staging, and Production — the same required-test set runs at each tier's own quality gate, never a narrowed set at an earlier tier. |
| The full threshold set binds Production in full | Every threshold in §4.1–§4.2, including the ≥ 90% floor and the complete non-functional set (§5), is evaluated at the Production Deploy Gate with no relaxation. |
| An earlier tier may fall short only of a non-invariant threshold | Where a change at Development or Staging falls short of the ≥ 90% coverage floor or a non-functional target that is not itself an invariant- or guardrail-metric quantification, that shortfall is not treated as a failed gate at that tier — it remains a failed gate the moment the same change reaches a tier where the threshold binds in full, per the row above. |
| A later tier re-evaluates fresh | Each of this document's required-test-set evaluations at a Deploy Gate (`02-ci-cd-pipeline-design.md` §6.1's "required tests" row) is a fresh run against the destination tier's own applicable thresholds, never a carried-forward result from an earlier gate's pass. |

**This section enforces the rule; it does not restate the reasoning behind it.** Why the split exists — that an invariant or guardrail metric is always-on regardless of tier while a non-invariant threshold may legitimately differ across an environment still under construction — is spec §6's own reasoning, cited here and not re-argued; the environment tiers themselves, their promotion ordering, and their own provisioning mechanics remain `04-devops-and-cloud-infra/01-environment-and-config-spec.md`'s and `01-environment-and-configuration-design.md`'s, neither read nor restated by this document beyond the three tier names spec §6 itself already uses.

## 5. The Non-Functional Test Layer's Fixed Input

`04-scalability-availability-and-performance-design.md` §2 states directly that this document's "crossover-point finding is cited forward by that document; it does not itself set a coverage threshold" — naming this document as the consumer of its own findings, never their re-deriver. ### 5.1 What the Non-Functional Layer Validates

This document does not restate any numeric target; each row of the non-functional test suite cites the specification value it validates against, exactly as spec §4's own closing line requires ("it references that document's number; it never sets, restates, or varies it").

### 5.2 The Mechanism Under Test Is Already Designed, Not This Document's to Redesign

`04-scalability-availability-and-performance-design.md` §3–§6 already designs the mechanism each target's test validates: the scaling triggers and HA/failover topology (§3 there), the connection-pooling mechanism (§4.1–§4.3 there), the concrete realization of each scalability target (§5 there), and the availability/reliability mechanisms (§6 there). This document's non-functional test layer exercises that already-designed mechanism under load and failure conditions; it does not design a second mechanism to validate a first, and a non-functional test failing is evidence the *already-designed* mechanism did not hold under the tested condition, never evidence this document's own test design is wrong.

### 5.3 Regression Is the Binding Form, Consistent With Spec §11 of the Cited Specification

`06-non-functional-requirements.md` §11 fixes a regression as any of: a breach of a stated floor or ceiling, a degradation exceeding 10% against the immediately preceding release's baseline for a performance/resource/latency target, or a nonzero guardrail-metric measurement. This document's non-functional test layer is what produces the measurement that rule is checked against; every regression it detects blocks release exactly as that specification's §11 and this document's own §9 (below) already require, and this document introduces no fourth regression condition of its own.

### 5.4 The Crossover-Point Figures, Carried Forward With Their Stated Status

`04-scalability-availability-and-performance-design.md` §4.4 fixes two schema-count waypoints — approximately 500 schemas (monitoring activation) and approximately 2,000 schemas (the point at which that document's own connection-pooling and migration-fan-out mechanisms are reasoned to no longer be sufficient) — and states explicitly that these are "a reasoned engineering waypoint, not a verified benchmark or a first-principles derivation," revisable on first operating data. That document's own §7 regression-detection boundary states plainly that "the detection mechanism, instrumentation, and alert routing" for this waypoint are "entirely" `04-devops-and-cloud-infra/04-observability-and-monitoring.md`'s to design — a runtime, post-deploy concern this document does not absorb. This document's own, narrower contribution is a pre-deploy one: the non-functional test suite includes a schema-count check, evaluated against both waypoints as a leading indicator at whichever tier's data most closely approximates production scale, so that a change is not the first place either waypoint's crossing is discovered. **This document inherits, and does not launder, the reasoned-not-verified status of both figures**: a test asserting the platform's behavior at or beyond either waypoint is itself validating a reasoned projection, not a confirmed capacity ceiling, and this document's own test results at that boundary must be read with that inherited status intact — never cited elsewhere as though this document had independently verified the figures itself.

### 5.5 What This Document Does Not Do With the Fixed Input

This document does not redesign the pooling mechanism, the scaling triggers, the HA/failover topology, or the crossover-point figures' own derivation; it does not set a schema-count threshold of its own; and it does not treat the 500- or 2,000-schema waypoints as a threshold this document could tighten or loosen — both remain `04-scalability-availability-and-performance-design.md`'s own reasoned findings, tracked here as a non-functional test-layer metric, never re-derived.

## 6. The Isolation and Trust Module's Higher Bar, Discharged

`03-architecture-realization-design.md` §4.4 names this document directly, by title, as owing "a first-order, non-generic obligation to hold the Isolation and Trust module's own implementation to a higher coverage and correctness bar than the other six components, as the second half of the compensating control." Its Boundaries section restates the same handover: "this document does not set the coverage threshold or the test-layer mechanics — only that this module is where that document's general quality bar must bind hardest." This section discharges that obligation concretely.

### 6.1 Why the Obligation Exists, Cited Not Re-Argued

`03-architecture-realization-design.md` §4.4 states the gap this bar exists to compensate for: the dependency-direction mechanism (ADR-014) proves, at build time, that no forbidden import exists between the seven component modules — it "proves nothing about whether the Isolation and Trust module's own implementation... is itself logically correct." That document's own §4, introduction, additionally states that a compiled, nominally-typed stack's compile-time type verification over this same module was a real, forgone advantage — traded for criterion 6 and Blazor's unfitness for arbitrary published web output (`01-technology-stack-design.md` §18.3–§18.7), not found unnecessary. `08-coding-standards-and-patterns-design.md` §9 (ADR-035) already names the coding-standard half of the compensating control: strict-mode TypeScript configuration and minimized `any` usage at this module's own boundaries. This document owes the test-layer half.

### 6.2 The Concrete Bar

The Isolation and Trust module (`components/isolation-and-trust`, `03-architecture-realization-design.md` §3.1) is held to a bar strictly higher than the ≥ 90% floor §4.1 fixes for the other six component modules, on two dimensions:

| Dimension | The Other Six Components | Isolation and Trust |
|---|---|---|
| Unit-test coverage floor | ≥ 90% (§4.1's general floor) | **100%** of the module's own logic — every branch, not only every line, given identity resolution, authentication-state handling, authorization decisioning, and the tenant-boundary primitives this module holds (`03-architecture-realization-design.md` §3.1's own description of the module's contents) are exactly the surface that document's own §4 introduction identifies, citing `01-technology-stack-design.md` §18.6, as "the static core where INV-01-critical logic concentrates." |
| What a passing test must establish | That the module's public interface behaves correctly for its stated inputs (spec §4's own unit-test definition). | The same, **plus** an explicit boundary-condition test for every point this module's own code crosses an `any`-typed or externally-sourced value into a typed internal structure — the exact erasure gap `03-architecture-realization-design.md` §4.4 names ("TypeScript's structural, erasable type system does not give an equivalent guarantee once a value crosses an `any`-typed or externally-sourced boundary"). A boundary crossing with no test asserting the value's shape and validity at that crossing point is a coverage shortfall under this bar, even where the surrounding branch coverage is otherwise complete. |

**Why 100%, not a lesser increment above 90%.** `03-architecture-realization-design.md` §4.4 names this module's own logic correctness as a residual gap a compiled, nominally-typed stack's compile-time checker would have closed generally — not partially. A test-coverage bar that closed only part of the gap (for example, 95%) would leave an unmeasured remainder in exactly the module that document's own §4 introduction names as the static core where INV-01-critical logic concentrates; the specification's own existing 100% floor for invariant- and guardrail-enforcing paths (§4.1 above) already establishes that this platform holds its most safety-critical code to a complete, not partial, coverage floor, and this obligation applies that same standard to the one module named as carrying the compensating control's second half.

### 6.3 How This Differs From the Generic Quality Bar, Concretely

This bar is not a restatement of §4.1's general ≥ 90% floor at a higher number. It is a **named, module-specific obligation** with two properties the generic floor does not carry: it applies to exactly one of the seven component modules, by name, rather than uniformly; and it requires the boundary-crossing test class above, which the generic unit-test definition (§3) does not itself name as mandatory for any other module. A change to `components/construction`, `components/operation`, `components/reach`, `components/extension`, `components/distribution`, or `components/evolution` is held to §4.1's ≥ 90% floor and the unit-test definition of §3 without the boundary-crossing requirement; only Isolation and Trust carries both the 100% floor and that requirement, because only Isolation and Trust is the module `03-architecture-realization-design.md` §4.4 names as the second half of the compensating control.

### 6.4 Enforcement

This bar is enforced identically to §4.1's other coverage floors — evaluated by the same coverage-instrumentation tool, attributed to `components/isolation-and-trust` by the module boundary `03-architecture-realization-design.md` §3.3 already fixes (a module's own public-interface boundary), and blocking under §9 exactly as any other coverage shortfall blocks. This document adds no second enforcement mechanism for this module specifically; it raises the floor and adds one requirement, both evaluated through the identical mechanism §4 already establishes.

### 6.5 What This Bar Does Not Close

Consistent with `03-architecture-realization-design.md` §4.4's own honest statement, this bar does not close the general compile-time-verification advantage a nominally-typed, compiled stack would have delivered across a broader class of errors than this bar's own scope — it closes the coverage and boundary-testing gap over this one module's own logic, to the standard §6.2 states. It does not extend to the other six components at this same standard, and it does not substitute for, or duplicate, `08-coding-standards-and-patterns-design.md` §9's strict-mode/`any`-minimization obligation over the same module — the two are the coding-standard half and the test-layer half of one compensating control, each realized by its own owning document.

## 7. Security Verification Baseline, Realized

Spec §9 fixes that the security test layer verifies conformance to the baseline `02-governance-and-security/02-security-policy.md` §9 names, and that verification against it is subject to the identical coverage and pass-rate floors as any other required test type. `04-security-controls-design.md` §7.4 already fixes that baseline as **OWASP ASVS 5.0 Level 2**, cited here, never renegotiated.

### 7.1 What the Security Test Layer Verifies

Every control `04-security-controls-design.md` §2–§7 fixes — the secrets-scanning gate and redaction filter, request-boundary validation and the query-layer boundary, vulnerability classification, the security-review trigger, and the transit, at-rest, and key-custody mechanisms — is a control that document's own §7.4 states "must satisfy" the ASVS 5.0 Level 2 baseline. This document's security test layer is the mechanism that runs the ASVS-mapped verification suite against those controls and produces the pass/fail result §4.2's pass-rate floor applies to.

### 7.2 The Vulnerability-Severity Blocking Condition

`04-security-controls-design.md` §4.2 already fixes the four-class severity vocabulary (Critical, High, Moderate, Low) and the translation rule mapping a scanner's finding into it. This document's security test layer consumes that classified finding as its own pass/fail input: a Critical or High classification is a failing security-test result under §4.2's pass-rate floor, and a Critical classification additionally halts and escalates per that document's own §4.2 rule (which itself cites `01-invariant-enforcement-design.md` §5.1) — this document does not redesign the classification step, only consumes its output as the security layer's own required-test result.

### 7.3 Evidence Composition, Not Duplication

`04-security-controls-design.md` §6.1 already fixes that an ASVS 5.0 Level 2 verification run produces an `assurance-run` evidence record (`08-audit-and-traceability-design.md` §4.3's own table, landing under Security events). This document's security test layer is what executes the run that record evidences; it mints no second record for the same run, and §11 below confirms this reuse.

### 7.4 What This Document Does Not Do

This document does not set the ASVS level, does not restate the data-protection obligations the baseline accompanies, and does not design the scanning technology, the redaction mechanism, or the classification step's own translation rule — each is `04-security-controls-design.md`'s in full, cited here as the fixed target this layer's tests are written to.

## 8. Flaky-Test Handling, Realized as a Deterministic Procedure

Spec §7 fixes that a flaky test is never a passing test, is never cleared by re-running, is fixed rather than silenced, and is never quarantined out of an invariant-quantifying obligation. This section states the concrete procedure that enforces each rule.

### 8.1 Detecting a Flaky Result

A test's result is treated as non-deterministic where either condition holds: the same test, executed against the same, unchanged platform-layer code, has produced both a pass and a fail across its execution history within the current change's own required-test run, or the test's determinism cannot otherwise be established with confidence at the point its result is consumed. The second condition is spec §7's own uncertainty rule, restated here as a concrete trigger rather than left implicit: where a test's own execution environment, timing dependency, or external-state coupling makes its determinism unverifiable at evaluation time, the test is treated as flaky under this procedure, not assumed deterministic by default.

### 8.2 A Correctness Signal, Not Only an Annoyance

A flaky test is evidence of one of two defects: the code path it exercises is itself non-deterministic under conditions the test legitimately reproduces (a race condition, an unbounded timing dependency, an unhandled ordering assumption), or the test itself is poorly isolated (shared mutable state between test runs, an external dependency the test does not control). Either defect is a correctness finding about the platform-layer code or the test suite itself — never a tooling inconvenience to be routed around. This document treats a flaky result identically regardless of which of the two defects caused it: the resolution procedure below does not differ by cause, because determining the cause is itself part of fixing the test, not a precondition for applying the rule.

### 8.3 The Resolution Procedure

- **The result resolves to failure, immediately and without exception.** A test detected as flaky under §8.1 is recorded with a failing result for the gate currently evaluating it; it does not contribute to the §4.2 pass rate, and any code path it is the sole exerciser of does not count toward the §4.1 coverage floor for that evaluation.
- **No re-run clears the gate.** The gate does not re-execute the flaky test seeking a passing run, and no mechanism in this document's own procedure selects a passing result from among a test's mixed execution history to satisfy §4.2. A change blocked by a flaky test remains blocked until the test itself is corrected and re-evaluated as a new, deterministic result — not until a subsequent run happens to pass.
- **The test is fixed, not removed from the required set, quarantined, or weakened.** Correcting a flaky test means resolving the non-determinism at its source (§8.2) so the test produces the same result on every execution against the same code. Removing the test from the required set, marking it as expected-to-fail, or loosening its assertion to stop flagging the non-determinism is not a resolution under this procedure — each would satisfy the gate's pass-rate arithmetic without correcting the defect the flakiness signals, which spec §7 forbids directly ("never by weakening, ignoring, or deleting the test to make a gate pass").
- **An invariant- or guardrail-enforcing path is never left uncovered because its test is flaky.** Where a flaky test is the sole exerciser of a path §4.1 attributes to the 100% floor (including a path within the Isolation and Trust module's own 100% floor, §6.2), removing that test from the required set to clear the gate is prohibited outright — the gate remains failed until the test is made deterministic, exactly as spec §7's own rule states, with no exception carved out for either coverage category this document fixes.

### 8.4 Why This Is Not a Quiet Bypass

A gate blocked by a flaky test remains a **failed gate**, recorded and evaluated identically to a gate blocked by a genuine, reproducible failure — §9's own no-bypass argument applies to it without distinction. The procedure above gives an engineer a path to resolve the block (fix the non-determinism), not a path to pass the gate without resolving it; nothing in §8.1–§8.3 permits a change to advance while a required test's result remains non-deterministic, and the uncertainty rule of §8.1's second condition resolves every ambiguous case toward failure rather than toward a pass. A flaky test that is never fixed blocks its change indefinitely, exactly as spec §7's own binding rule requires — this is the mechanism by which flaky-test handling stays a correctness discipline rather than becoming a second, informal route around §9's gate.

## 9. The "No Passing Gates, No Deploy" Constraint, Held as a Gate

`PROCESS.md` §11 fixes three instruments that must never collapse into one another: an **invariant** is a binary property holding continuously; a **gate** is a checkpoint a change must pass to advance; a **guardrail metric** is a measured value that must not degrade. `implementation-document-map.md` assigns this constraint to this document explicitly as the third of these — a gate — and this section holds that distinction throughout rather than letting a coverage threshold read as a metric or an invariant.

### 9.1 What This Document's Gate Is, and Is Not

This document's quality gate is the composite condition spec §3 already defines: the required test types of §3 present, coverage at or above the floor of §4.1 (and, for Isolation and Trust, §6.2), the pass rate of §4.2 met, and no flaky result counted as a pass under §8. It is **not** a binary property holding continuously (an invariant) — a change may exist mid-development without yet satisfying it, and that state is not itself a violation the way an invariant breach is. It is **not** a measured value optimized while not degrading (a guardrail metric) — it is not tracked as a trend line; it is evaluated pass/fail at a checkpoint, exactly as `PROCESS.md` §11's own gate definition already distinguishes ("a checkpoint a change must pass to advance"), a distinction spec §3's own table restates in this document's own terms as a condition "a change must satisfy at a point in its pipeline before it advances." Where this document's own test layers happen to validate a property that is *also* an invariant (§3's invariant-conformance layer, citing `01-invariant-enforcement-design.md`) or *also* a guardrail metric's zero-tolerance floor (§5.3, citing `06-non-functional-requirements.md` §9.2), that reflection remains the other instrument's own — this document's gate is the checkpoint form, never a restatement of either.

### 9.2 What the Gate Measures, at the Placement Already Fixed

`02-ci-cd-pipeline-design.md` §5.1 and §6.1 already place this document's quality gate as one further, independent bullet at the Merge Gate and at every Deploy Gate — that document's own §12.1 Consequences state plainly that its own placement is made "never redesigning what it measures." This document supplies exactly that: at every placement, the gate evaluates the composite condition of §9.1, drawing on the coverage and pass-rate state of §4, the layer-specific results of §3 (including the non-functional layer of §5 and the security layer of §7), the Isolation and Trust bar of §6, and the flaky-test resolution of §8. This document does not redesign the placement, the ordering relative to other checks at the same gate, or the no-bypass mechanics — each remains `02-ci-cd-pipeline-design.md`'s own, cited here as the fixed location this document's measurement fills.

### 9.3 No Change Advances While a Required Test Does Not Pass

Consistent with spec §8's own binding rule, a change does not advance past whichever pipeline gate is currently evaluating it while any condition of §9.1 is unmet. Concretely, each of the following independently blocks, at whichever gate it is discovered:

- Required-test coverage below the applicable floor of §4.1, including the Isolation and Trust module's own 100% floor of §6.2.
- Any required test failing to pass, at a pass rate below the 100% of §4.2.
- A flaky test counted or presented as a pass, contrary to §8.
- A vulnerability at the Critical or High severity classes surfaced by the security layer of §7, or a mandatory security review (`04-security-controls-design.md` §5.2) whose completion has not been confirmed.
- A measured regression against any target of `06-non-functional-requirements.md` applicable to the destination tier, including any nonzero guardrail-metric measurement (§5.3).
- A required test establishing that an invariant would be, or has been, violated — which halts and escalates per `01-invariant-enforcement-design.md` §3.4, rather than being resolved by adjusting this document's own thresholds.
- Uncertainty about whether any condition above is met — resolved as though the condition were unmet, per the deny-by-default posture every cited document already applies.

### 9.4 No Deploy Without a Passing Quality Gate

No change deploys to a tier whose applicable quality gate (§4.3's tier-applicability table) it has not passed. Passing this document's gate is necessary, never sufficient on its own, for deployment — the other checks `02-ci-cd-pipeline-design.md` §5.1 and §6.1 place at the same gates (secrets-scanning, the provenance-gate check, the residency clause, and so on) apply independently and are not restated or absorbed here.

### 9.5 A Failed Gate Is Never Bypassed

No urgency, deadline, authority, or steward role waives a failed instance of this document's gate; no coverage floor, pass-rate threshold, or flaky-handling resolution is relaxed to let a specific change through. A failed gate is resolved only by fixing the change or the test and re-evaluating against the same, unaltered thresholds — the identical no-bypass posture `02-ci-cd-pipeline-design.md` §8 already establishes structurally for the pipeline as a whole, which this document's gate inherits as the environment it runs inside rather than re-arguing independently.

## 15. Binding Rules

These rules hold for every change subject to these gates and are subordinate to the charter.

- **Every required test layer is realized against an already-designed mechanism where one exists, and no layer substitutes for another** (§3).
- **Coverage and pass-rate floors hold without exception, at the numbers spec §5 fixes, enforced identically across the environment tiers per spec §6's own rule** (§4).
- **The non-functional layer validates against `06-non-functional-requirements.md`'s cited targets and `04-scalability-availability-and-performance-design.md`'s already-designed mechanism; the crossover-point figures carry their reasoned-not-verified status forward and are never cited as though this document independently verified them** (§5).
- **The Isolation and Trust module is held to a 100% unit-coverage floor plus a mandatory boundary-crossing test class — a concrete, module-specific bar strictly higher than the general 90% floor, discharging `03-architecture-realization-design.md` §4.4's named obligation in full** (§6).
- **The security test layer verifies against OWASP ASVS 5.0 Level 2, consuming, never redesigning, `04-security-controls-design.md`'s vulnerability-classification output** (§7).
- **A flaky test resolves to a failing result immediately, is never cleared by re-running, and is fixed rather than silenced or quarantined out of an invariant-quantifying obligation — a blocked gate remains blocked, never a quiet bypass** (§8).
- **The "no passing gates, no deploy" constraint is held as a gate, never an invariant or a guardrail metric, even where a specific test layer's own subject is also one of the other two instruments** (§9).
- **No change advances past a pipeline gate, and no change deploys to a tier, while any condition of this document's own gate is unmet; a failed gate is never bypassed, overridden, or worked around, by any actor, for any reason** (§9).
- **This document owes no new structure to `02-platform-data-model-design.md` and mints no new audit event** — every layer's result is reused from its owning mechanism where one exists, and the gate's own composite pass/fail is reconstructable from those results, never a new definitional fact (§10–§11).
- **This document records exactly one ADR.** ADR-048 (§12) is the genuine, independent set of threshold and procedure decisions this document makes; every mechanism it enforces remains owned, in full, by the document that designed it.
- **Everything remains domain-neutral and platform-level.** No test type, threshold, or blocking condition in this document encodes the characteristics of any single domain; every rule above remains valid for any tenant, in any operating region, on any provider-neutral testing tooling.
