## 3. Release and Rollback, Realized as Concrete Mechanism

Spec §3 fixes a release as the act of promoting a validated change into a tier so the tier runs it, staged promotion as the discipline of advancing through the ordered tiers, a rollback as the act of reversing a released change to its last known-good state, and a fallback as the defined route by which that reversal is accomplished. This section states what each is concretely, over the pipeline and infrastructure already fixed, without redefining any of the four.

### 3.1 A Release, Concretely

A release is the act of causing a tier's own container-orchestration deployment target (`01-environment-and-configuration-design.md` §3.4) to run a specific, already-pipeline-validated artifact version in place of whatever version it was previously running — for Production, one operating region's own structurally separate instantiation (`08-multi-region-distribution-design.md` §3.2, realized at §11 below). This composes directly with, and adds nothing to, `01-environment-and-configuration-design.md` §3.2's own "same artifact, promoted, never rebuilt" discipline: the artifact a release deploys is bit-for-bit the one that already passed the Merge Gate and the destination tier's own Deploy Gate; a release never builds, compiles, or varies the artifact, and this document introduces no second build step anywhere in the release act.

### 3.2 Staged Promotion Is Realized Entirely by the Pipeline Already Fixed

`02-ci-cd-pipeline-design.md` §3.2 already fixes the staged-promotion mechanism this document rides on: Staging Promotion advances automatically on a Merge Gate pass; Production Promotion requires a distinct, explicit trigger action by an actor holding a Production-scoped grant, whose own privilege is permission to request the promotion, never the capability to write to Production directly (`01-environment-and-configuration-design.md` §6.1's structurally singular deploy credential, cited and not redesigned). This document does not re-place, reorder, or duplicate that mechanism — it is the staged-promotion mechanism spec §4 requires, already realized, and this document's own release act (§3.1) is what executes once that mechanism admits a change into a tier.

**Exposure bounded before it is widened** (spec §4's second bullet) is realized by two composed facts, neither of which this document adds: the Staging Deploy Gate already validates a change "under conditions representative of Production" (`02-ci-cd-pipeline-design.md` §3.2's citation of spec §4) before a Production trigger is even available to an actor holding the grant; and, for Production specifically, this document's own region-sequential rollout (§11) bounds exposure a further, additional step within Production itself — a release is never widened to every operating region at once.

### 3.3 A Rollback, Concretely

A rollback is the act of causing the affected tier's (and, for Production, the affected region's) container-orchestration deployment target to run the tier's own last known-good artifact version in place of the version a release most recently deployed there — the reverse of §3.1's own act, using the identical mechanism. Where the release being reversed changed committed data, a rollback additionally executes the reversal procedure §5 below requires be established before that release was ever permitted to proceed. A rollback is never a rebuild, and it is never a forward fix disguised as a reversal: it restores the tier to a state that already existed and already held every invariant and quality floor (spec §5's own third bullet, cited and not restated).

### 3.4 The Three-Instrument Distinction, Held From the Release Side

`PROCESS.md` §11 fixes that an invariant, a gate, and a guardrail metric must never collapse into one another. This document's own mechanism touches all three without becoming any one of them on its own account: the mandatory rollback path (§4) is this document's own realization of INV-08's release-time form, a binary property this document checks and never gates on its own separate schedule; the Deploy Gate a release must pass (`02-ci-cd-pipeline-design.md` §6) remains that document's own checkpoint, never restated here as though this document owned it; and no release or rollback metric in this document is described as a continuously measured guardrail floor. Where this document's own release act composes with a check owned elsewhere, that check's own instrument identity is preserved, never relabeled.

## 4. The Mandatory Rollback Path Before Any Release

Spec §5 fixes that every release must have a defined, reversible rollback path before it may proceed, and that this is the release-level elaboration of INV-08 — *"No change advances the platform or built software into a state it cannot safely leave; every change retains a reversible, recoverable path"* (`02-governance-and-security/01-system-invariants.md` §4.4) — and the guarantee release gate G-5 (C-16) protects: *"A release with no reversible, recoverable path may not be promoted; every release must be reversible without harm"* (`01-business-and-ux/02-prd.md` §5). `01-invariant-enforcement-design.md` §5.4 already fixes that INV-08's release-time reinforcing check — as distinct from the runtime, authoring-time check that document owns in full — is this document's own to design. This section is that design: it is simultaneously the release-level, binary form of INV-08 and the checkpoint form of gate G-5, held distinct throughout per §3.4 above, both discharged by the identical mechanism below.

### 4.1 How the Path Is Established, in Mechanism

Before a release is permitted to advance past the destination tier's own Deploy Gate, this document's own reinforcing check establishes and records two facts, neither assumed:

- **Which specific artifact version constitutes the tier's (and, for Production, the region's) last known-good state.** This is the version currently deployed there, captured at the moment the release's own Deploy Gate evaluation begins — never inferred after the fact from telemetry, a CI artifact, or a build log, each of which answers a different question (§13 below states why).
- **Whether that captured version, or the reversal procedure a state-changing release additionally carries (§5), can be shown to restore the tier to a state holding every invariant and quality floor** — never assumed real because a fallback exists in principle. A rollback path that cannot be shown to restore the last known-good state is treated as absent under spec §5's own second bullet, and the release does not proceed.

### 4.2 What Makes the Path Real Rather Than Nominal

For a release that changes no committed data, the path is real by construction rather than by assertion: `01-environment-and-configuration-design.md` §3.2's "same artifact, promoted, never rebuilt" discipline means the tier's own immediately-prior artifact version is not a hypothetical fallback — it is the literal, already-built, already-validated artifact that was running immediately before this release, having already passed the identical Merge Gate and Deploy Gate sequence the current release is passing. Establishing this path costs nothing beyond capturing which version that was (§4.1); there is no separate construction step, because the fallback already exists as a consequence of every prior release having passed through the same gates this one is passing through now.

For a release that changes committed data, the path is real only where the constraint §5 below states is satisfied — this document does not treat a data-affecting release's path as established merely because a code-level artifact rollback exists, since redeploying prior code does not, by itself, reverse a schema migration or a data transformation already applied.

### 4.3 What Makes the Path Mandatory in Mechanism, Not Only in Policy

`02-ci-cd-pipeline-design.md` §8.1 already establishes the structural argument this document inherits rather than re-derives: the only identity capable of writing to a tier's own infrastructure is the pipeline's own service identity, scoped to that tier (`01-environment-and-configuration-design.md` §6.1 and §5.4), and every path into that infrastructure necessarily passes through the pipeline's own gates because no second, credential-bearing path exists. This document's own reinforcing check (§4.1) is one further condition inside that same structural chokepoint, evaluated at the identical Deploy Gate `02-ci-cd-pipeline-design.md` §6.1 already places invariant conformance at — the "invariant conformance at the destination tier" row that document's own table already fixes as running fresh at every Deploy Gate. This document supplies exactly the content that row consumes for INV-08 specifically: no release advances past that gate while this check's own result is `violated` or cannot be established, for the identical reason no release advances while any other invariant's check fails there. The mandate is therefore structural — there is no second, ungated path a release could take that skips this check — never a rule an actor could choose to disregard.

## 5. The Hard Case: The Rollback Path for a State-Changing Release

A release that has already changed persistent state cannot be reversed by redeploying prior code alone. This section confronts that directly, as the ticket requires, rather than assuming a code-level rollback closes the reversibility question for every release.

### 5.1 The Constraint a Migration Must Satisfy

`03-software-and-architecture/03-data-model-and-entity-spec.md` §7 already fixes the constraint at the data-model level: *"A migration does not proceed without a reversible, recoverable path back to the prior valid state"* and *"A migration is all-or-nothing with respect to validity"* — a migration never leaves data satisfying neither the prior nor the new schema. That constraint is established and checked before a migration ever enters the system, at INV-08's own runtime, authoring-time gate (`01-invariant-enforcement-design.md` §5.4's "autonomous change, runtime" row; `08-audit-and-traceability-design.md` §9's minimum-traceability gate, which already requires the reversible-path element be establishable *before* the change enters the system).

This document's own contribution is the release-time reinforcement of that already-established constraint, applied at the point a release carrying one or more migrations reaches a Deploy Gate:

- **The migration's own recorded reversal procedure must still be re-executable at the moment of release**, not merely have been valid when the migration was authored — a further migration or a data change landed since could have invalidated a reversal target the original procedure assumed was still intact. Where this cannot be re-confirmed, the constraint fails and the release does not proceed (§4.1's second bullet).
- **The reversal procedure must itself be shown to complete within the migration duration and downtime ceiling** `03-software-and-architecture/06-non-functional-requirements.md` §7 fixes — four hours, with no downtime beyond the availability budget of that document's §6 — because a reversal is itself a migration, and spec §7's data-model rule binds it identically to a forward migration. A reversal that cannot be shown to complete within that ceiling has no real path under §4.2 above, and the release does not proceed.
- **The reversal must not itself breach a guarantee to complete** — spec §5's own fourth bullet, cited and not restated: no rollback proceeds by degrading tenant isolation, referential integrity, or any other invariant or floor; committed data remains valid and is never corrupted or dropped to accomplish a reversal. A reversal procedure that could only complete by breaching a guarantee is not a real rollback path, and the release does not proceed.

### 5.2 What Happens When the Constraint Cannot Be Met

The release does not proceed — full stop, no override, and no partial admission. This is spec §5's own deny-by-default rule applied at exactly the point this constraint is evaluated: *"A rollback path that cannot be shown to restore the last known-good state is treated as absent, and the release does not proceed."* This document introduces no mechanism by which a migration lacking a re-confirmable, re-executable, ceiling-meeting reversal is admitted anyway on the strength of the value it would deliver — spec §9's own "a breach overrides apparent gain" rule, inherited and not restated. A migration that fails this constraint is not released in its current shape; it is decomposed by its own authors into a sequence of steps each individually reversible under this section — an additive step that retains what preceded it, followed later by a separate release that removes what is no longer needed, each cleared through this same check on its own account — or it is not released at all. This document does not design that decomposition discipline; it states only that a release failing this section's constraint has exactly one path forward under this document's own check: satisfy it, or do not proceed.

### 5.3 The Residual Limit, Stated Plainly Rather Than Overclaimed

Even where §5.1's constraint is fully satisfied, one honest limit remains, and this document states it rather than implying closure. `03-software-and-architecture/03-data-model-and-entity-spec.md` §9 fixes that every builder-defined entity carries generic, always-on effective dating, append-only retention, and full history — removal is expressed as a further state in a record's history, never an erasure of what preceded it — which is precisely what makes an ordinary migration's data-level reversal structurally tractable in the first place: nothing was overwritten to begin with, so reversal is a matter of returning to a prior state that the platform never discarded. That same section states, and this document inherits without weakening, that this obligation "meets, and does not override, the erasure rules" `02-governance-and-security/06-data-governance-and-privacy.md` owns — a specific record or field that has been erased or anonymized under that document's own managed path is, by that path's own design, no longer present to be restored.

**This document's mandatory-rollback-path guarantee does not, and cannot, extend to content a governed erasure has already removed.** Where a release's own migration is composed with, or follows, an erasure action taken under that managed path, this document's constraint (§5.1) is satisfied for the migration's schema shape and for every value the erasure did not touch; it is never satisfied, and is never claimed to be satisfied, for the specific erased content itself, because no reversible path to already-erased content can exist without contradicting the erasure obligation that removed it. This is not a gap this document introduces or fails to close — it is the identical erasure/immutability boundary `08-audit-and-traceability-design.md` §7 already draws for its own audit record, restated here for committed entity data specifically, and inherited rather than independently re-derived. A release whose own rollback path would need to restore erased content does not, and cannot, meet §4's mandatory-path requirement for that content; every other aspect of that release remains bound by §5.1 in full.

## 6. Rollback Triggers

Spec §6 fixes that a rollback is called when a signal establishes that a released change no longer holds what it must, that the triggering signals are owned by `04-devops-and-cloud-infra/04-observability-and-monitoring.md`, and that this document defines only what each obligates at the release level. `04-observability-and-monitoring-design.md` §6 already supplies the fixed payload this document consumes — which target breached (the `severity_source` tag), the severity attached to it, its measured persistence past the threshold, and whether the tag names an invariant or a guardrail-metric quantification — and ADR-049's Consequences bind this document to consume that payload "as the substrate its own release-and-rollback mechanism composes with, never redesigning what triggers it." This document mints no second triggering vocabulary.

### 6.1 What the Payload Obligates at the Release Level

A rollback-triggering health signal, consumed as that fixed payload, obligates exactly one thing at the release level: reversal of the released change that introduced the condition to its tier's own last known-good state (§3.3), executed under §4–§5's own mechanism, where in-place self-correction is unavailable or insufficient. This document does not evaluate the payload's own severity, persistence, or invariant/guardrail status — those are already fixed by the tag `04-observability-and-monitoring-design.md` §4.1 attaches at signal-definition time — it consumes the payload as given and identifies which release, on which tier and region, the payload's own `target_reference` traces back to (§14's evidence supplies that trace).

### 6.2 The Concrete Trigger Set, Realized Against the Payload

Every bullet spec §6 enumerates resolves to a condition on the payload `04-observability-and-monitoring-design.md` §4–§7 already fixes, with no second evaluation this document performs independently:

| Spec §6 Trigger | Realized As |
|---|---|
| A rollback-triggering health signal | The §6.1 payload, where the tag names neither an already-violated invariant nor an already-Critical vulnerability (§6.4 below) — reversal proceeds under §4–§5. |
| A runtime regression not correctable within bounds | The identical payload, where the self-correction ladder (`05-meta-operations/07-self-correction-and-fallback-protocol.md` §6, composed with at §7 below) reports in-place correction unavailable or insufficient. |
| A post-release invariant breach | Never routed here at all — halts and escalates immediately per §6.4 below; this document's rollback mechanism is never the resolution path for an active breach. |
| A post-release Critical or High vulnerability | A Critical vulnerability is never routed here (§6.4); a High vulnerability that cannot otherwise be resolved without leaving real use exposed is reversed under §4–§5, on the identical `severity_source` tag `04-observability-and-monitoring-design.md` §4.1 already attaches. |
| A backward-compatibility break outside the managed path | Reversed under §4–§5, composing with §10 below without a second detection mechanism. |
| Autonomous rollback proceeds only within bounds; otherwise it escalates | Realized at §7's composition with the self-correction ladder's own bounds, and at §9's human-authorization trigger for a rollback that cannot complete within them. |
| Uncertainty resolves toward rollback | The identical deny-by-default rule already fixed at `04-observability-and-monitoring-design.md` §4.2 for the payload's own evaluation, carried forward without a second uncertainty rule of this document's own. |

### 6.3 What This Document Does Not Compute

This document does not decide whether a given payload's severity or persistence crosses any threshold — those determinations are `04-observability-and-monitoring-design.md`'s own, fixed before the payload ever reaches this document. This document's own contribution begins at the payload's arrival: identifying the released change it traces to, and executing the reversal §4–§5 already define.

### 6.4 A Critical Signal Never Reaches This Section

Consistent with spec §6's own rule and `04-observability-and-monitoring-design.md` §6.4's identical finding, a payload whose tag names an invariant already violated, or a vulnerability already classified Critical, is never routed through §6.1–§6.3 at all — it halts and escalates immediately under `02-governance-and-security/01-system-invariants.md` §3, bypassing this document's rollback mechanism entirely. Where a human, resolving that halt, later directs a rollback as the corrective action, that rollback is executed under this document's own §4–§5 mechanism, but as a human-authorized action under §9 below, never as an autonomous trigger under this section.

## 7. Composition With the Self-Correction Ladder's Rung 3

`05-meta-operations/07-self-correction-and-fallback-protocol.md` §6 fixes the ladder's third rung: *"Where in-place self-correction is unavailable or insufficient, the agent reverses the change to its last known-good state. The rollback path, its triggers, and its time-to-recover target are owned by `04-devops-and-cloud-infra/05-release-and-rollback-protocol.md` §5–§7; the ladder invokes that rollback and redefines none of it."* This document is the owner that citation names.

- **This document owns the rollback mechanism; the ladder owns when it is reached.** Whether Rung 3 is the correct response to a given error — as opposed to Rung 1 (retry) or Rung 2 (safe alternative) — is that protocol's own ordering decision, never this document's; this document supplies only what Rung 3 executes once reached.
- **A rollback invoked as Rung 3 is bound by the identical bounds §6 states, and by that protocol's own outer bounds.** An autonomous rollback proceeds only where it is itself reversible and recoverable, breaches no invariant or floor, and stays within the maximum self-correction attempts `03-software-and-architecture/06-non-functional-requirements.md` §10 fixes; a rollback exceeding those bounds is never retried autonomously and mandates human authorization under §9 below, exactly as spec §6's own sixth bullet requires.
- **A rollback that cannot complete within its own bounds is itself an escalation-mandating condition**, per the identical rule spec §7's closing bullet fixes and §8.4 below states concretely — this document does not redesign the escalation itself, only supplies the condition that triggers it.

## 8. Time-to-Recover Target

Spec §7 fixes the rollback-specific recovery target as a condition keyed to a number `03-software-and-architecture/06-non-functional-requirements.md` already owns, minting no new figure of its own. This document does the same: it reads the actual figures rather than assuming one, and states how its own mechanism is shown to meet them.

### 8.1 The Two Figures, Read Rather Than Assumed

`03-software-and-architecture/06-non-functional-requirements.md` §7 fixes two distinct ceilings this document's recovery target composes with, neither restated here beyond its exact value:

| Target | Value | Applies To |
|---|---|---|
| Mean time to recovery, platform-core incident | ≤ 60 minutes from detection to restoration of the availability floor of §6 | A rollback restoring a tier's own last known-good state, code-level (§3.3, §4) |
| Migration duration and downtime ceiling | ≤ 4 hours, with no downtime beyond the availability budget of §6 | The reversal of a state-changing release, where §5's constraint applies |

Spec §7's own second bullet fixes that the general figure governs unless the recovery is itself data-affecting, in which case the wider, migration-specific ceiling applies instead — this document reads that split directly from spec §7's own text rather than collapsing the two figures into one.

### 8.2 How the Mechanism Is Shown to Meet the Code-Level Target

`01-environment-and-configuration-design.md` §3.2's "same artifact, promoted, never rebuilt" discipline is what makes the ≤ 60-minute floor structurally meetable rather than merely hoped for: the artifact a code-level rollback deploys (§3.3) is already built and already validated — it requires no compilation, no re-validation, and no second pass through the pipeline, only the same container-orchestration redeploy action §3.1 already performs for a forward release, run in reverse. This is a structural argument about what a redeploy of an already-built artifact requires relative to what a build requires, reasoned rather than verified against any specific orchestration product's own measured latency (`PROCESS.md` §12.3) — this document asserts no time-sensitive claim about how fast any particular tool completes the action, only that the action itself carries no build-time cost the floor would need to absorb.

### 8.3 How the Mechanism Is Shown to Meet the Data-Affecting Ceiling

The ≤ 4-hour, zero-data-loss ceiling is met by construction rather than by runtime hope: §5.1's own constraint already requires that a migration's reversal procedure be shown to complete within that identical ceiling *before* the release carrying it is ever permitted to proceed (§4–§5). A release that could not meet the ceiling never reaches a tier in the first place — it fails §5's mandatory-path gate and does not release. Every data-affecting release that does proceed therefore already carries a reversal shown, at release time, to be completable within the ceiling; this document's own recovery-target obligation at rollback time is discharged by the same gate that admitted the release, not by a separate runtime guarantee this document would otherwise have to assert independently.

### 8.4 The Recovery Target Is Never Relaxed, and Exceeding It Escalates

Consistent with spec §7's third and fourth bullets, no release proceeds on the basis that its own rollback would recover more slowly than the applicable ceiling allows — a fallback shown, at release time, not to meet its ceiling is an inadequate rollback path under §4.2, and the release does not proceed. Where a rollback is nonetheless underway and does not restore the last known-good state within its ceiling, that is itself an escalation-mandating condition: the rollback is never retried indefinitely against the same failing recovery, and the condition mandates human authorization under §9 below (spec §6's own sixth bullet and §7's own fourth bullet, composed rather than restated).

That protocol's own §5 already names this document, by section, as the underlying-condition owner for two of its own enumerated triggers — "Promotion to Production" and "Reaction past an autonomous bound" — and this document's own trigger set realizes all six of spec §8's bullets concretely, composing with the routing already fixed rather than designing a second mechanism.

### 9.1 The Concrete Trigger Set

### 9.2 Authorization Is Permission to Ask, Never Capability to Write

`01-environment-and-configuration-design.md` §6.1 fixes that the only identity capable of writing to Production's own infrastructure is the pipeline's own Production-scoped service identity, and that no human steward holds a standing credential of equivalent reach; `02-ci-cd-pipeline-design.md` §6.2 fixes, for the same reason, that the actor triggering a Production promotion "never itself carries or exercises any credential capable of writing to Production." This document's own human-authorization trigger set inherits that structural fact rather than restating it as policy: authorizing a release or a rollback under §9.1 is, in every case, permission for the pipeline to execute the already-designed mechanism of §3–§8 — never a channel through which the authorizing human writes to a tier's infrastructure directly. This holds identically whether the authorized action is a Production promotion or a rollback: the human's decision is captured as an audit event (§14) and the pipeline's own credential is what then performs the write, exactly as it does for any other gated action `02-ci-cd-pipeline-design.md` §6 already governs.

### 9.3 What This Document Does Not Design

How the request is composed, to whom it is routed, how the decision is recorded, and how autonomy resumes once authorized are each `05-meta-operations/04-human-in-the-loop-protocol.md`'s own mechanics in full (that document's §6–§7, cited and not restated). This document fixes only which releases and rollbacks match a trigger and what the resulting authorization then permits — the resumed execution of §3–§8's own mechanism, never a wider grant.

## 10. Release Gate G-6 and C-15 — Backward-Compatible Evolution

`01-business-and-ux/02-prd.md` §5 fixes gate G-6: *"A release that breaks a guarantee the platform has already made to existing builders or built software may not proceed."* Spec §4's fifth bullet and §6's fifth bullet already bind this document's own release strategy and rollback triggers to that guarantee, citing INV-09 and the managed, announced deprecation policy `03-software-and-architecture/04-api-contract-spec.md` owns. This document realizes both without building a second breaking-change detector — `05-api-contract-design.md` (ADR-032) already places one at the Merge Gate.

### 10.1 How a Release Is Established as Backward-Compatible, Before It Proceeds

`05-api-contract-design.md` §8.1 already fixes that an unresolved breaking change is classified directly into `02-governance-and-security/02-security-policy.md` §6's Critical/High vulnerability vocabulary and consumed by `02-ci-cd-pipeline-design.md` §5.1's own existing vulnerability-classification Merge Gate row — no second bullet, and no second detector. This document's own staged-promotion mechanism (§3.2) already requires a passing Merge Gate as a precondition to any Staging or Production promotion; a release carrying an unresolved breaking change therefore never reaches this document's own release act at all, because it never clears the gate `02-ci-cd-pipeline-design.md` already places upstream of it. `02-ci-cd-pipeline-design.md` §5.3 additionally fixes that this diff-based check runs once, at Merge, and is never re-run at a later Deploy Gate, because the promoted artifact is bit-for-bit unchanged (§3.1 above) — this document introduces no second, redundant diff at any Deploy Gate for the identical reason.

### 10.2 What This Document Supplies to `05-api-contract-design.md`'s `rollback_reference`

`05-api-contract-design.md` §7.3 fixes that its own `contract-breaking-change-detected` event carries a `rollback_reference` field, populated before the event's `outcome` can move from `held-pending-approval` to `proceeded`, and states plainly: *"The reversal mechanics themselves belong to `04-devops-and-cloud-infra/05-release-and-rollback-protocol.md`, cited and not designed here."* This document discharges that handover directly: the value populating `rollback_reference` is the specific rollback path §4–§5 establish for the release carrying the breaking change — for a platform-primitive-tier contract change, the code-level rollback of §3.3/§4.2; for a built-application-tier generation-logic change (`05-api-contract-design.md` §8.3), the identical mechanism applied to the platform release that changed the generation logic, never a second, contract-specific rollback mechanism this document invents. Populating the field with anything §4's own mechanism cannot show restores the last known-good state would itself fail §4.2's "shown, not assumed" requirement, and the event's own `outcome` therefore cannot advance to `proceeded` — this document's own check and that document's own field-population requirement are the same refusal, viewed from two sides.

### 10.3 A Backward-Compatibility Break Discovered After Release

Where a released change is later found to break a guarantee outside the managed path — the detection having slipped past the Merge Gate, or having been introduced by a mechanism the Merge Gate does not diff (`05-api-contract-design.md` §5.3's own stated residual gap, a behaviorally-breaking change that leaves contract shape unchanged) — spec §6's fifth bullet obligates reversal, realized under §6.2's table above: the change is reversed under §4–§5's own mechanism to restore the broken guarantee. This document does not design a second, post-release contract diff to catch this case; it consumes whatever signal establishes the break (a rollback-triggering health signal, an escalated finding, or a direct report routed through `05-meta-operations/04-human-in-the-loop-protocol.md`) and executes the identical rollback mechanism §3.3 already fixes.

## 11. Release Across the Multi-Region Topology

`08-multi-region-distribution-design.md` §3.2 fixes Production as N regional instances of the identical image, each a structurally separate instantiation with its own regionally-resident managed PostgreSQL instance, sharing no database, credential, or network path with another (`01-environment-and-configuration-design.md` §3.1, extended per-region by that document's §3.3). This section states what a release and a rollback are given that topology, rather than assuming a single-region model extends unchanged.

### 11.1 A Production Release Is One Release, Rolled Out Region by Region

**Decision, reasoned independently: a Production release is realized as a sequence of per-region release acts (§3.1), one per operating region's own structurally separate instantiation, never one atomic, simultaneous, all-region cutover.** Three considerations establish this rather than assume it:

- **No shared control plane exists to make an atomic, all-region cutover possible without contradicting the structural separation already fixed.** `01-environment-and-configuration-design.md` §3.1 states plainly that no structure anywhere in that design connects two tiers' — and, per §3.3, two regions' — own infrastructure; a genuinely atomic multi-region deploy would require a cross-region coordination mechanism no cited document provisions, and this document does not invent one.
- **Spec §4's "exposure bounded before it is widened" rule favors sequential rollout independently of the structural fact above.** A defect surfacing in one region's own rollout is caught, and can trigger a rollback of that region alone (§11.2), before it ever reaches a second region — the identical bounded-exposure logic that already governs Staging-before-Production, applied one further level below Production itself.
- **The Production-scoped trigger `02-ci-cd-pipeline-design.md` §3.2 already fixes is a single explicit action; it is not, by that document's own text, an all-regions-simultaneous action.** This document reads that trigger as authorizing the release's own region-sequential rollout to begin, not as itself deploying to every region at once.

### 11.2 Transient Version Skew Across Regions Is Real, and Invisible Within Any One Tenant

**This condition can arise under this document's own design, and this section states it rather than assuming it away.** During a Production release's region-sequential rollout, a region already reached by the rollout runs a different artifact version than a region not yet reached — the platform is, transiently, at more than one Production version at once, across regions. This document does not treat that condition as a defect to eliminate; it is the direct, necessary consequence of §11.1's own bounded-exposure argument.

**What closes the concern the ticket raises is `08-multi-region-distribution-design.md` §4.1's own finding, composed with here rather than re-derived: the tenant is the unit of physical regional placement, and a tenant's entire schema hierarchy is served by exactly one region's own instance at any moment.** From any single tenant's own perspective, there is no skew to observe — a tenant is served by exactly one region, and that region's own version, whatever it is at that moment, is the only version that tenant's own requests ever reach. Skew exists only *across* tenants resident in different regions during the rollout window, never *within* one tenant's own experience of the platform. This document introduces no mechanism to eliminate cross-tenant skew during a rollout, because no guarantee this library fixes requires every tenant to observe an identical platform version at every instant — only that each tenant's own requests are served correctly by whichever version its own region is running, which the Deploy Gate (`02-ci-cd-pipeline-design.md` §6.1) already establishes for every region's own instance independently.

### 11.3 A Rollback Is Correspondingly Region-Scoped

A rollback of a Production release reverses each region the forward rollout has already reached, region by region, using the identical mechanism §3.3–§5 already fix — independently per region, in whichever order the triggering condition's own scope indicates (a region-specific health signal reverses that region alone; a platform-wide condition reverses every region already carrying the release, in reverse rollout order absent a more specific triggering scope). A region the forward rollout has not yet reached needs no rollback action of its own — it is already at its own last known-good state, having never received the release being reversed. The recovery target of §8 applies per region: a region's own rollback is independently measured against the ≤ 60-minute or ≤ 4-hour ceiling for that region's own restoration, regardless of how many other regions are concurrently being reversed, consistent with `03-software-and-architecture/06-non-functional-requirements.md` §6's own per-region measurement of the availability floor that ceiling protects.

### 11.4 What This Section Does Not Redesign

This section does not redesign the region topology, the placement unit, the Region Resolution Point, or the Region Boundary Check — each remains `08-multi-region-distribution-design.md`'s own, cited and composed with, never restated. It does not redesign region admission, which that document's own §9.2 already realizes entirely at the existing Production Deploy Gate residency clause, introducing no second gate — a newly admitted region simply becomes one further region this section's own sequential rollout reaches on its next release, never a special case this document treats differently.

- **Question this answers:** Given a release protocol that requires a mandatory rollback path before any release, a rollback-triggering payload already fixed elsewhere, a recovery target keyed to two distinct, already-owned numeric ceilings, and a Production tier realized as N structurally separate regional instances with no shared control plane — what release strategy realizes staged promotion across that topology; what constraint makes a state-changing release's rollback path real rather than nominal, and what happens, and what residual limit remains, when it cannot be met; and does any of it require a new stored structure or a new audit-event type?
- **Criteria applied, and how each resolved:**
  1. *Does a Production release admit atomically across every region at once, or region by region?* Decisive for region-by-region (§11.1) — no cited document provisions a cross-region coordination mechanism that could make an atomic cutover structurally possible without contradicting the per-region isolation `01-environment-and-configuration-design.md` §3.1 and §3.3 already fix, and spec §4's own bounded-exposure rule independently favors sequential rollout.
  2. *Does a code-level rollback's own recovery-time argument require a claim about a specific tool's speed, or can it rest on a structural property?* Decisive for the structural property (§8.2) — the promoted-artifact discipline (`01-environment-and-configuration-design.md` §3.2) already establishes that a rollback redeploys an already-built artifact, never re-running a build step, which is sufficient to reason the ≤ 60-minute floor is meetable without asserting anything about any specific orchestrator's own measured performance.
  3. *Does the data-affecting recovery ceiling need a separate release-time verification step, or is it discharged by the mandatory-path gate that already runs before release?* Decisive for the latter (§8.3) — because §5.1's own constraint already requires the reversal be shown to complete within the ceiling before the release proceeds at all, a release that reaches a tier has already, by construction, cleared the ceiling; a second, independent runtime check at rollback time would duplicate a determination already made.
  4. *Does the "current deployed version," "release history," or the "designated last-known-good reference" belong in the platform's own schema?* Decisive against, for three distinct reasons rather than one restated three times (§13) — infrastructure-native present-tense state, durable audit-stream content, and a value derived from that same stream at read time, respectively; none is a `platform`-schema fact.
  5. *Does a release or a rollback warrant a new audit-event type?* Decisive for two — `release-promoted` and `rollback-executed` — because neither the Deploy Gate's own composite pass/fail nor a human authorization's own decision event states which specific artifact version a tier now runs or which prior version a rollback restored; every other candidate (an ordinary Staging advance, a gate pass) resolves into an already-reconstructable fact, on the identical H26c test every prior Layer 5 document applies.
- **Context:** This is the fifth document of Layer 5, and the first to confront a topology question — Production release across N structurally separate regions — that no cited upstream document settles on its own terms: `08-multi-region-distribution-design.md` fixes the region topology itself but does not address release mechanics across it; `02-ci-cd-pipeline-design.md` fixes the Production trigger as a single explicit action but does not state whether that action deploys to every region at once. Resolving that question, and confronting the hard case of a state-changing release's rollback path directly rather than assuming a code-level fallback closes it, are this document's own defining tasks.
- **Decision:** (1) A release is the act of causing a tier's own container-orchestration deployment target to run a validated, already-promoted artifact in place of what it previously ran; a rollback is the identical act in reverse, additionally executing a data reversal procedure where the release being reversed changed committed data (§3). (2) The mandatory rollback path is established by capturing the tier's own last-known-good artifact reference before a release proceeds, and is real, not nominal, because that reference is the literal, already-validated predecessor artifact for a code-level release, or a demonstrated, re-confirmed, ceiling-meeting reversal procedure for a state-changing one; it is mandatory in mechanism because it is one further condition inside the identical structural no-bypass chokepoint `02-ci-cd-pipeline-design.md` §8.1 already establishes (§4). (3) A state-changing release's rollback path requires a reversal procedure that is re-confirmable at release time, completes within the four-hour migration ceiling, and never itself breaches a guarantee; a release failing this constraint does not proceed, full stop; the residual limit — content already removed under a governed erasure cannot be restored by any rollback path this document defines — is stated plainly rather than implied closed (§5). (4) Rollback triggers consume the fixed payload `04-observability-and-monitoring-design.md` already produces without a second triggering vocabulary, and a signal naming an already-violated invariant or an already-Critical vulnerability never enters this document's rollback mechanism at all (§6). (5) This document's own mechanism is exactly what the self-correction ladder's Rung 3 invokes, never redesigning the ladder itself (§7). (6) The recovery target reads two distinct, already-owned ceilings — sixty minutes for a code-level rollback, four hours and zero data loss for a data-affecting one — and this document's own mechanism is shown, structurally, to meet each (§8). (7) Six concrete releases and rollbacks require human authorization, realizing spec §8 in full and composing with the routing `05-meta-operations/04-human-in-the-loop-protocol.md` already owns; authorization is permission to ask the pipeline to run this document's own mechanism, never capability to write directly (§9). (8) A release is established as backward-compatible by the Merge Gate's own existing breaking-change detection, never a second detector; this document supplies the concrete content of `05-api-contract-design.md` §7.3's own `rollback_reference` field (§10). (9) A Production release is realized as a region-sequential rollout, never an atomic all-region cutover; transient cross-region version skew is real but invisible within any single tenant's own experience, because the tenant is the unit of physical regional placement; a rollback is correspondingly region-scoped (§11). (10) This document owes no new structure to `02-platform-data-model-design.md` and adds exactly two new audit-event types, `release-promoted` and `rollback-executed` (§13–§14).
- **Alternatives considered:** *An atomic, simultaneous all-region Production cutover* — rejected under criterion 1; no cross-region coordination mechanism exists in this design to make it structurally possible, and it would directly contradict the bounded-exposure rule spec §4 already fixes. *Verifying the code-level recovery-time argument against a specific orchestrator's own published redeploy latency* — rejected under criterion 2; that would be exactly the time-sensitive, unverifiable-in-this-ticket claim `PROCESS.md` §12.3 exists to prevent, where a structural argument already suffices. *A second, runtime-only verification of the migration-reversal ceiling, independent of the release-time gate* — rejected under criterion 3; it would duplicate a determination the mandatory-path gate already makes before the release is ever admitted. *A `platform.release_history` table recording every release and its last-known-good reference* — rejected under criterion 4; the audit-event stream already captures the identical content durably, and a parallel table would duplicate rather than add a fact. *A single `deployment` event type covering both a release and a rollback, distinguished only by a field* — rejected under criterion 5; a release and a rollback carry structurally different content (a rollback references the release it reverses and the recovery target it was measured against, neither of which a release itself carries), and collapsing them into one type would obscure that distinction rather than state it.
- **Consequences:** Binds `06-incident-response-and-recovery-design.md` (Layer 5, not yet written) to the fixed release and rollback mechanism of §3–§11 as one recovery action an incident response may invoke, never redesigning it. Binds `06-self-correction-and-fallback-design.md` (Layer 6, not yet written) to consume the `rollback-executed` event of §14 as the evidence its own ladder's Rung 3 rests upon. Discharges, in full, `05-api-contract-design.md` §7.3's own handover of the `rollback_reference` field's content, and `01-invariant-enforcement-design.md` §5.4's own handover of INV-08's release-time reinforcing check. Confirms, and alters none of, `08-multi-region-distribution-design.md`'s region topology, `02-ci-cd-pipeline-design.md`'s gate placement and no-bypass argument, `01-environment-and-configuration-design.md`'s tier and credential realization, and `04-observability-and-monitoring-design.md`'s triggering payload — each document's own content stands exactly as already designed. Adds no new structure to `02-platform-data-model-design.md`'s schema and exactly two new `event_type` values to `08-audit-and-traceability-design.md`'s model.

## 18. Binding Rules

These rules hold for every release and rollback subject to this model and are subordinate to the charter.

- **A release is a redeploy of a validated, already-promoted artifact; a rollback is the identical act in reverse, plus a data-reversal procedure where committed state changed** (§3).
- **No release proceeds without a mandatory rollback path shown, not assumed, to restore the tier's own last known-good state — real by construction for a code-level release, real only where §5's constraint is met for a state-changing one** (§4).
- **A migration's rollback path must be re-confirmable at release time, complete within the four-hour migration ceiling, and never itself breach a guarantee; a migration failing this does not release, full stop** (§5.1–§5.2).
- **The mandatory-path guarantee never extends to content a governed erasure has already removed — this residual limit is stated, never implied closed** (§5.3).
- **Rollback triggers consume the fixed payload `04-observability-and-monitoring-design.md` already produces; this document mints no second triggering vocabulary, and a signal naming an already-violated invariant or an already-Critical vulnerability never enters this document's rollback mechanism** (§6).
- **This document supplies the rollback mechanism the self-correction ladder's Rung 3 invokes; it never redesigns the ladder itself** (§7).
- **Recovery is measured against two distinct, already-owned ceilings — sixty minutes for a code-level rollback, four hours and zero data loss for a data-affecting one — each shown structurally meetable by this document's own mechanism, never merely asserted** (§8).
- **Six concrete releases and rollbacks require human authorization, realizing spec §8 in full; authorization is permission for the pipeline to execute this document's own mechanism, never capability to write to a tier's infrastructure directly** (§9).
- **A release is established as backward-compatible by the Merge Gate's own existing breaking-change detection, never a second detector; this document supplies the content of `05-api-contract-design.md`'s own `rollback_reference` field** (§10).
- **A Production release is realized as a region-sequential rollout, never an atomic all-region cutover; a rollback is correspondingly region-scoped; transient cross-region skew is real but invisible within any single tenant's own experience** (§11).
- **This document binds platform-layer release and rollback only; a builder's own promotion of their own application triggers none of this document's mechanism** (§12).
- **This document owes no new structure to `02-platform-data-model-design.md` and adds exactly two new audit-event types** — `release-promoted` and `rollback-executed`, neither reconstructable from an already-existing record (§13–§14).
- **This document records exactly one ADR.** ADR-050 (§15) is the genuine, independent set of region-sequencing, reinforcing-check, and evidence decisions this document makes; every mechanism it composes with remains owned, in full, by the document that designed it.
- **Everything remains domain-neutral and platform-level.** No release rule, rollback trigger, or recovery target in this document encodes the characteristics of any single domain; every mechanism above remains valid for any tenant, in any operating region, on any provider-neutral deployment-orchestration tooling.
