# Data Governance and Privacy Design

## 1. Purpose and Reading Order

This document realizes `02-governance-and-security/06-data-governance-and-privacy.md` §3–§8 in full — the data-classification-and-handling matrix built atop the residency tiers, retention and deletion rules, consent and minimization requirements, PII exposure as a blocking violation, and redaction requirements for logs and outputs — as concrete, enforced mechanisms. It answers **how** personal and sensitive data are protected through their full lifecycle rather than observed as a policy a builder or the platform is trusted to honor: how a data-governance category becomes a property that travels with data exactly as a classification tier already does, how a retention obligation is evaluated and made to result in an actual, not merely logical, deletion, where a consent-and-minimization basis is checked before collection or use, why an exposure of personal or sensitive data halts rather than degrades, and what the existing emission-boundary redaction filter already provides for this document's own redaction requirement — and what it does not.

`06-compliance-and-data-residency-design.md` §5 already made classification-tier an intrinsic, traveling property and stopped deliberately at the *residency* consequence of a tier — where data may be stored, processed, or transferred. This document owns the *handling* consequence — what may be done with data at each tier, through its lifecycle — and extends that same property; it does not define a second, competing classification scheme, and the data-governance category this document adds (§3) travels alongside the tier, never in place of it.

**Verified versus reasoned (`PROCESS.md` §12.3).** Every claim in this document is **reasoned** — from the cited specification and the structural properties of the cited, already-written design documents. No claim asserts any jurisdiction's current legal requirement as a checked fact; personal and sensitive data are described structurally throughout, never by reference to a named law's definition, and no specific jurisdiction, regime, or regulation is named anywhere in this document.

It is structured as a pyramid, following the specification's own reading order: first the data-classification-and-handling matrix everything else is measured against (§3), realized as an extension of the traveling property `06-compliance-and-data-residency-design.md` §5 already fixes; then the lifecycle rules built on it — retention and deletion (§4), then consent and minimization (§5); then the blocking-violation rule that protects the whole (§6); then the redaction requirement that gives that rule a concrete, standing safeguard (§7); then the evidence this document's controls must produce (§8); then the design decision this document records (§9); then the boundaries this document does not cross (§10), precedence (§11), and the binding rules that close it (§12).

## 2. Scope and What This Document Does Not Own

This document owns: the data-governance category as a property that travels with personal and sensitive data alongside the classification tier, and the handling matrix built from the two together (§3); retention and deletion as an enforced lifecycle mechanism, including what a concrete deletion is against the storage shapes already fixed or already deferred elsewhere (§4); consent and minimization as enforced constraints at the point of collection or use (§5); PII exposure as a blocking check, realized in the register the security layer already uses for a blocking finding (§6); and what the existing emission-boundary redaction filter already provides for personal- and sensitive-data redaction, and what it does not (§7).

This document does **not** own, and does not decide:

- **The data-classification tiers themselves** — Unrestricted, Tenant-Bound, Jurisdiction-Restricted, Regime-Governed — their residency consequence, the Region Boundary Check, or the Resolved Residency Obligation. Each is `06-compliance-and-data-residency-design.md`'s, already fixed; this document reads and extends the tier as a traveling property and never redesigns how it is resolved or enforced for residency.
- **The Registry Accessor, the Context Resolution Point, connection-scoping, or tenant/application isolation.** Each is `02-tenant-isolation-and-access-control-design.md`'s §3, §5, already fixed; this document's mechanisms compose with the connection this mechanism already scopes and do not design a second access path.
- **The storage shape of the data-governance-category attribute, the consent-basis record, or the retention-obligation attribute** on a platform-primitive identity or on a builder-defined entity — owned by whichever data-model document already owns, or will own, the relevant structure (`02-platform-data-model-design.md` for the platform's own registry and identity tables, already written; `02-data-model-and-entity-design.md`, not yet written, for builder-defined entities). This document fixes only the requirement each attribute must satisfy and the point at which it is read or checked.
- **The build-surface and configuration model a builder uses to define a collected purpose, a consent flow, or a minimization boundary** — owned by `01-application-construction-design.md` (not yet written), realizing C-05/C-06; this document fixes the enforced constraint that model's own write path must satisfy, never the model itself.
- **Numeric retention ceilings.** Owned by `03-software-and-architecture/06-non-functional-requirements.md`, per the specification's own deferral; this document fixes only where and how a resolved ceiling is evaluated, never what the ceiling's value is.
- **The emission-boundary redaction filter's own architecture, placement, or secrets-matching logic** — `04-security-controls-design.md` §2.2, already fixed; this document determines what that filter already provides for personal- and sensitive-data redaction and states plainly what it does not (§7), extending its matching criteria rather than building a second filter beside it.
- **Vulnerability-severity classes, the translation step, or the release-blocking gate's own mechanics** — `04-security-controls-design.md` §4, already fixed; this document's PII-exposure blocking check (§6) feeds that same classification step and does not invent a new severity scale.
- **Referential-integrity and migration-safety particulars behind INV-04** — `03-software-and-architecture/03-data-model-and-entity-spec.md`'s and `02-data-model-and-entity-design.md`'s; this document requires only that deletion never breach that invariant, per §4 below, without restating its particulars.
- **Approval routing, recording, and resolution** for any human-in-the-loop step this document's mechanisms might trigger — `05-meta-operations/04-human-in-the-loop-protocol.md`'s in full.
- **Audit capture, immutable storage, and tamper-evidence** — `08-audit-and-traceability-design.md` (not yet written); this document fixes the evidence list its controls must produce, never the storage mechanism.
- **Any independent technology, topology, or scope decision beyond the one named in §9.** This document records exactly one ADR.

## 3. The Data-Classification-and-Handling Matrix, Realized

`02-governance-and-security/06-data-governance-and-privacy.md` §3–§4 fixes two data-governance categories — personal data and sensitive personal data — that sit alongside the four classification tiers `06-compliance-and-data-residency-design.md` §5 already realizes as an intrinsic, traveling property, and states the handling matrix the two together carry. This section realizes that matrix as mechanism.

### 3.1 The Data-Governance Category Is Intrinsic and Travels, Exactly as the Tier Does

`06-compliance-and-data-residency-design.md` §5 fixes that a classification tier is "intrinsic to the data it classifies, not an attribute a consumer infers," required from the point a data element is created, with storage shape deferred to whichever data-model document owns the relevant structure. This document requires the same discipline for the **data-governance category** (non-personal, personal, or sensitive personal, per the specification's §3): every stored data element this document's mechanism governs carries its category as a required property from the point it is created, resolved and read at the same point the classification tier is resolved (`06-compliance-and-data-residency-design.md` §3.3's Resolved Residency Obligation, and — for platform-primitive identity data specifically — the Registry Accessor's extended return, §3.2 there). This document does not design the storage shape of the category attribute (§2 above); it fixes that the attribute must exist and must be readable wherever the tier is read, as one further intrinsic property carried alongside it — never a second, independently-resolved classification scheme a consumer must reconcile against the tier.

**An unclassifiable or unrecorded category resolves to the more restrictive of the two, not the less.** Where a data element's category cannot be established with confidence at the point it would otherwise be read, it is treated as sensitive personal data until it is explicitly classified — the same deny-by-default discipline `06-compliance-and-data-residency-design.md` §5 already applies to an unclassifiable tier, and the same discipline `04-security-controls-design.md` §4.2 applies to an ambiguous vulnerability-severity mapping, applied here to data-governance category specifically.

### 3.2 The Matrix Translates Category-and-Tier Into a Handling Obligation Set, Read at the Same Points the Tier Already Is

`02-governance-and-security/06-data-governance-and-privacy.md` §4's matrix states, for each category, a floor obligation for retention, consent, minimization, and redaction, and states that a more restrictive tier or regime only adds to that floor, never subtracts from it. This document realizes that cumulative rule mechanically: for a given data element, its **Resolved Handling Obligation** is the union of the floor its data-governance category (§3.1) sets and whatever further obligation its classification tier and any attaching compliance regime (`06-compliance-and-data-residency-design.md` §5–§6) independently add — read at the same point, and by the same discipline, the Resolved Residency Obligation is already read (`06-compliance-and-data-residency-design.md` §3.3): resolved fresh, never cached from an earlier determination, and never narrowed by a more permissive tier or regime once the category floor has set a requirement.

| Data-Governance Category | Retention Obligation It Sets (§4) | Consent/Minimization Obligation It Sets (§5) | Redaction Obligation It Sets (§7) | What a More Restrictive Tier or Regime Adds |
|---|---|---|---|---|
| Non-personal | None on this basis alone. | None on this basis alone. | None on this basis alone, beyond the absolute secrets rule `04-security-controls-design.md` §2 already enforces. | Nothing this document's mechanism enforces; a residency or regime obligation may still attach independently under `06-compliance-and-data-residency-design.md`, unaffected by this document. |
| Personal | Held no longer than its disclosed purpose requires; deleted or de-identified at the end of that purpose, on consent withdrawal, or at a retention ceiling, whichever occurs first (§4). | Requires a lawful, disclosed basis; minimization bounds collection and use to that basis's purpose (§5). | Redacted from any log, output, or artifact not authorized to hold it (§7). | Where the tier is Jurisdiction-Restricted or Regime-Governed, the retention and redaction floor is unchanged by this document but the residency consequence `06-compliance-and-data-residency-design.md` §5 already fixes applies in addition, never in substitution. |
| Sensitive personal | Subject to the same ceiling as personal data, with no extension for operational convenience (§4). | Requires consent explicit and specific to the sensitive category where consent is the basis relied upon; minimization applies with no operational-convenience exception (§5). | Mandatory with no lower-sensitivity exception; exposure is a blocking violation (§6). | Identical in kind to the row above — this document adds no separate sensitive-tier residency rule, because `06-compliance-and-data-residency-design.md` §5 already requires sensitive personal data to carry at least the tier the residency and regime obligations establish for it, and this document's own obligation is cumulative with, never a substitute for, that requirement. |

This table does not redefine the matrix `02-governance-and-security/06-data-governance-and-privacy.md` §4 already fixes; it states the mechanism — a resolved, cumulative obligation read from an intrinsic property at a fixed point — that makes the matrix's floor concretely enforced rather than a table a consumer must remember to apply. Where a tenant's or builder's own configuration independently places a personal-data element under a more restrictive tier or regime, that obligation folds into the same union, per the specification's own §4 closing rule, cited and not restated.

## 4. Retention and Deletion, Enforced

`02-governance-and-security/06-data-governance-and-privacy.md` §5 fixes that personal data is retained only for its disclosed purpose, deleted or de-identified when that purpose ends, when consent is withdrawn, or at a retention ceiling — whichever occurs first — and that deletion must never breach INV-04 or cross a tenant or region boundary it does not own. This section designs the mechanism that makes each rule true, rather than a rule a component is trusted to apply.

### 4.1 The Retention Obligation as a Further Property, Resolved the Same Way

Every personal-data element governed by this document carries a **Retention Obligation** — the disclosed purpose's own end condition, the applicable consent basis (§5), and the numeric ceiling `03-software-and-architecture/06-non-functional-requirements.md` sets for it (this document does not fix or design that ceiling) — as a further intrinsic property resolved alongside the data-governance category and classification tier of §3, on the same deny-by-default discipline: where a Retention Obligation cannot be established with confidence for a given element, it is treated as already expired, not as unbounded, and the deletion mechanism of §4.2 acts on it accordingly. This document does not design the storage shape of the Retention Obligation attribute (§2); it fixes that the attribute must exist, must be resolvable, and must be evaluated on the schedule §4.2 fixes.

### 4.2 The Retention Sweep — an Operationally Scheduled Procedure, on the Same Discipline Key Rotation Already Uses

No existing mechanism in the design library evaluates a data element's own lifecycle state on a schedule; the closest precedent is `04-security-controls-design.md` §7.3's key-rotation procedure, which is "operationally scheduled, using metadata the schema already carries." This document's **Retention Sweep** is designed on that same discipline, because none closer exists to extend: a scheduled procedure reads each governed personal-data element's Retention Obligation (§4.1) and, where the disclosed purpose has ended, the consent basis has been withdrawn (§5.3), or the ceiling has been reached — whichever occurs first — invokes the deletion mechanism of §4.3 against that element. The sweep is mandatory and unconditional wherever a Retention Obligation exists; it is not a background best-effort process a component may omit, and its own execution — what it evaluated and what it deleted — is captured as evidence (§8).

**Withdrawal of consent triggers the sweep's action immediately, not only at the next scheduled pass.** Per §5.3 below, a consent withdrawal is itself an event this document's mechanism must act on; where the platform's own event-handling path can invoke the deletion mechanism directly at the moment of withdrawal, it does so, and the scheduled sweep exists to catch the purpose-end and ceiling cases a discrete event does not itself signal, and to catch any withdrawal-triggered deletion that a defect in the direct path failed to complete.

### 4.3 What "Deleted" Concretely Means, Against the Storage Shapes Already Fixed or Already Deferred

This document does not claim an irreversibility its mechanism does not deliver, and states what deletion concretely means against each of the two storage shapes personal data governed by this document can occupy.

- **Platform-primitive identity data — `platform.platform_users`, `tenant_<id>.tenant_users`, and the binding tables `02-platform-data-model-design.md` §5 fixes.** That document already fixes, for `platform.tenants` and `platform.applications`, that a row is never hard-deleted — it is marked with a terminal status instead, "from INV-08 (reversibility and recovery) and from the referential needs of the audit trail itself" (`02-platform-data-model-design.md` §10). This document does not redesign that convention, and does not assume it extends to `tenant_users` or `platform_users` beyond what that document states. Where a personal-data field sits in a row this document's mechanism cannot cause to be physically removed — because the row's own continued existence is required by an audit-referential or reversibility need this document does not own — **deletion concretely means the personal-data field's own content is overwritten with a non-identifying value; the row, its identifier, and its non-personal audit-referential columns persist exactly as `02-platform-data-model-design.md` §10 already requires.** This is the honest, concrete degradation this document accepts for that shape: field-level erasure of the personal-data content, not row removal, and this document states so plainly rather than claiming a row-level deletion the cited storage shape does not deliver.
- **Builder-defined entity data — the primary personal-data surface, owned by `02-data-model-and-entity-design.md` (not yet written).** `DECISIONS.md` D-12 requires effective dating, append-only records, and full history for every builder-defined entity. The specification's own §5 anticipates exactly this composition problem by stating deletion as "deleted, **or rendered no longer identifiable**" — an explicit alternative to row removal. This document requires that alternative be exercised across **every retained version of a record, current and historical alike**: where a builder-defined entity's history mechanism retains a prior version of a record, a deletion or de-identification obligation reaching that record's personal-data fields is not satisfied by clearing the current version alone — the personal-data content in every historical version must be purged or rendered no longer identifiable in the same operation, while the fact that a change occurred, and when, may remain part of the retained history exactly as D-12 requires. A history mechanism that preserves personal-data content in a historical version after that data's deletion obligation has been triggered does not satisfy this document's requirement, regardless of whether it satisfies D-12's own mandate for structural history. This is a binding requirement this document places on `02-data-model-and-entity-design.md`'s design of that mechanism (§10), not a redesign of D-12 itself — D-12's own history requirement stands; this document requires only that the requirement be met by a mechanism capable of purging content from every version it retains.

### 4.4 The Irreversibility This Document Accepts, and States Honestly

**Once a personal-data element's content has been overwritten or purged under §4.2–§4.3, its original value is not recoverable by this document's own mechanism.** Where a Retention Obligation is later found to have been resolved incorrectly — a purpose-end condition misapplied, a ceiling miscalculated, a consent basis misread — and personal data has already been deleted under the mistaken resolution, no rollback this document designs restores the original content; the deletion is, by construction, a destructive operation over the data it targets, not a soft or logically-reversible one. This is the cost asymmetry `implementation-document-map.md` records for this document and is carried into ADR-024's reversal-cost statement (§9) rather than understated here to make the mechanism look safer than it is.

### 4.5 Deletion Honors INV-04 and Never Crosses a Boundary It Does Not Own

The Retention Sweep's deletion action is itself a write, and is bound by every mechanism that already governs a write of tenant- or application-scoped data: it never proceeds in a way that would corrupt, silently drop, or leave the remaining committed data in an invalid or inconsistent state (INV-04, owned by `03-software-and-architecture/03-data-model-and-entity-spec.md` and `02-data-model-and-entity-design.md`, cited and not restated here), and it reaches a connection only through the same Registry Accessor, Context Resolution Point, and connection-scoping mechanism `02-tenant-isolation-and-access-control-design.md` §3–§5 already fixes — the sweep is not a privileged, cross-tenant, or cross-region process exempted from that mechanism; it is bound by it exactly as any other write is (§4 of that document), and by the Region Boundary Check exactly as any other write against residency-tiered data is (`06-compliance-and-data-residency-design.md` §3.4).

## 5. Consent and Minimization, Enforced

`02-governance-and-security/06-data-governance-and-privacy.md` §6 fixes that personal data may be collected, held, or used only on a lawful, disclosed basis, that consent where relied upon must be informed, specific, and revocable, and that minimization bounds collection and use to that basis's purpose. This section states where each requirement is checked, structurally, rather than recorded as an intention.

### 5.1 Two Distinct Bases, Neither Designed Here as a Content Question

The specification's §6 states directly that "consent and minimization are platform primitives; their specific content is builder-defined" — what a built artifact collects, the purposes it discloses, and the consent it seeks are the builder's own content, never a platform assumption. This document does not design that content. It designs the enforced constraint the platform holds regardless of what content a builder supplies, for two distinct classes of personal data this document governs:

- **Builder-configured, end-user personal data** — the primary target of §6's requirement, recognized through the generic access primitive (C-03) and stored in whatever structure `02-data-model-and-entity-design.md` fixes. The lawful basis here is whatever the builder discloses and, where relied upon, whatever consent the builder's own flow records.
- **Platform-primitive identity data** — a builder persona's, extender's, or steward's own identity and binding data in `tenant_<id>.tenant_users` or `platform.platform_users`. Its lawful basis is the platform's own service relationship with that identity, established at account or tenant-membership creation through whatever onboarding mechanism `03-authentication-and-identity-design.md` and the platform's own terms already govern procedurally — not a builder-configured consent flow. This document does not design that onboarding mechanism or the terms it presents; it states only that this class of personal data is not the case §5.2–§5.4 below's collection-time check is designed against, because its lawful basis is established once, procedurally, rather than per-collection.

### 5.2 The Basis Check Runs at the Point of Collection or Use, Before It Proceeds

For builder-configured, end-user personal data, this document requires a **Consent and Minimization Check**: before a write that would collect personal data, and before a read or processing step that would use personal data for a purpose, the check evaluates whether a lawful, disclosed basis exists for that collection or use, on the scope that basis's own disclosed purpose covers. No existing platform-core mechanism mediates every write and read of builder-defined entity data the way the Registry Accessor mediates every read of the platform registry — `02-data-model-and-entity-design.md` and `01-application-construction-design.md`, the documents that own the build-surface and the entity structure this data occupies, are not yet written (§2 above). This document therefore fixes the requirement and its structural placement — before the collection or use proceeds, never after, on the same deny-by-default discipline every other check in this document and its cited upstream documents applies — and binds whichever write-mediation mechanism those two documents design to run this check inline, exactly as the Region Boundary Check runs inline within the existing connection-acquisition function rather than as a second gateway (`06-compliance-and-data-residency-design.md` §3.4, the precedent this requirement follows). This document does not invent a second write-mediation gateway in advance of those documents' own design; it fixes the property the gateway they design must have.

- **Refusal, not a warning, on a missing or insufficient basis.** Where the check cannot establish that a lawful, disclosed basis covers the specific collection or use attempted, the collection or use is refused — never accepted with a flagged deficiency for later review. This mirrors the pipeline's own "no merge-with-warning outcome" discipline for a secrets-scan match (`04-security-controls-design.md` §2.1) and the Region Boundary Check's refuse/proceed discipline (`06-compliance-and-data-residency-design.md` §3.4), applied here to the basis check.
- **Minimization is the same check, evaluated against scope rather than existence.** Where a basis exists but the specific data elements a collection or use would touch exceed what that basis's disclosed purpose requires, the check refuses the excess collection or use on the same basis — minimization is not a separate check run afterward, it is the same evaluation applied to the *scope* of what a basis covers rather than only to *whether* a basis exists.

### 5.3 Withdrawal Ends the Basis and Triggers Deletion

`02-governance-and-security/06-data-governance-and-privacy.md` §6 fixes that withdrawing consent "removes the basis for holding the personal data it covered and triggers the retention and deletion rules of §5" — realized here as: a recorded consent withdrawal immediately invalidates the Retention Obligation (§4.1) that consent basis supported, and is itself the event §4.2's Retention Sweep mechanism acts on without waiting for a purpose-end or ceiling condition to be reached independently. Where a builder's own basis for a given personal-data element was never consent (a different lawful, disclosed basis), withdrawal has no purchase against it — only a consent-supported basis is capable of being withdrawn, consistent with the specification's own framing of consent as one basis type among others.

### 5.4 Consent Never Widens Access

`02-governance-and-security/06-data-governance-and-privacy.md` §6 fixes that "a basis to hold or use personal data is never a substitute for the role-and-permission matrix... an actor without an access grant gains none by virtue of a data subject's consent." This document adds no mechanism that could be read otherwise: the Consent and Minimization Check of §5.2 is evaluated in addition to, never instead of, the connection-scoping and grant mechanism `02-tenant-isolation-and-access-control-design.md` §3–§8 already fixes; an actor holding a valid consent basis for a piece of personal data still reaches it only through a connection that mechanism has already scoped to that actor's own grant.

## 6. PII Exposure as a Blocking Violation

`02-governance-and-security/06-data-governance-and-privacy.md` §7 fixes that exposure of personal or sensitive data is never tolerated as a degradation, is classified using the existing severity classes, additionally halts and escalates where it coincides with an invariant breach, and resolves any uncertainty toward treating exposure as having occurred. This section places that rule in the register `PROCESS.md` §11 fixes and `01-invariant-enforcement-design.md` already applies, rather than inventing a fourth enforcement instrument.

### 6.1 PII Exposure Is Not Itself a Numbered Invariant, and Is Not Treated as a Metric

`02-governance-and-security/06-data-governance-and-privacy.md` §1 states directly that this document's redaction rule "extends, and never replaces, INV-03 (no secret exposure)... a distinct concern" from the secrets that invariant governs absolutely — and none of INV-01 through INV-08 names personal- or sensitive-data exposure as its own numbered property. `PROCESS.md` §11 fixes that an invariant, a release gate, and a guardrail metric are three distinct enforcement instruments that must never collapse into one another. A PII exposure is neither: it is a **blocking check**, evaluated at the same points a vulnerability finding already is, and it is never optimized against as a measured value the way a guardrail metric is — the specification's own "never tolerated as a degradation" line is the concrete rejection of the metric register for this finding, stated here so a later reader does not mistake the severity classification of §6.2 for a metric threshold rather than a blocking one.

### 6.2 The Finding Is Classified Through the Same Translation Step, Never a New Scale

`04-security-controls-design.md` §4.2 already designs the translation step that maps a scanning finding to `02-governance-and-security/02-security-policy.md` §6's four severity classes, run immediately after detection and before any gate consumes the result. This document adds no second scale, per the specification's own §7 instruction; it adds the criteria a PII-exposure finding is checked against within that same translation step:

| Policy §6 Class | The Additional Criterion a PII-Exposure Finding Is Checked Against |
|---|---|
| Critical | The exposure would breach INV-01, INV-02, or INV-03 concurrently (cross-tenant reach, authorization bypass, or secret exposure) — classified Critical on that basis alone, identical to any other Critical finding under `04-security-controls-design.md` §4.2's own rule, and additionally halts and escalates as an invariant breach in its own right (§6.3 below), not merely as a PII finding. |
| High | The finding is an exposure of **sensitive** personal data with no concurrent invariant breach — the specification's own floor ("carries at minimum a High-severity impact"), applied as a lower bound the translation step may not classify below, never as a ceiling preventing a Critical classification where §6.1's row applies. |
| Moderate | Reserved for a finding that degrades a control governing personal-data exposure without itself exposing data — for example, a defect in the basis check of §5.2 discovered before it produced an actual exposure. |
| Low | **Never used for an exposure of personal data.** The specification's own floor ("exposure of personal data more broadly is never classified as Low") is an absolute exclusion, not a default the translation step may fall back to on an ambiguous finding. |

**Deny-by-default on an ambiguous PII-exposure mapping resolves to the higher class in contention**, exactly as `04-security-controls-design.md` §4.2 already fixes for any ambiguous mapping, and exactly as §3.1 above fixes for an unclassifiable data-governance category — the same discipline, applied a third time at this document's own decision point.

### 6.3 Halting, Where Exposure Coincides With an Invariant Breach

Where a PII-exposure finding also breaches INV-01, INV-02, or INV-03, it halts and escalates under `02-governance-and-security/01-system-invariants.md` §3 and the check locations `01-invariant-enforcement-design.md` §5.1 already fixes for those invariants, in whatever lifecycle phase it is found — this document adds no second halt mechanism and does not move either invariant's own check location; the PII-exposure rule stands alongside that halt, never substituting for it, exactly as the specification's own §7 states.

### 6.4 Uncertainty Resolves to Treating Exposure as Having Occurred

Where it cannot be established that an output, log, or artifact is free of personal or sensitive data beyond its authorized handling, this document's mechanism treats it as exposing that data and refuses the action producing it — the deny-by-default rule `02-governance-and-security/01-system-invariants.md` §3 already fixes, applied here to PII exposure specifically, and the same posture the redaction mechanism of §7 below applies at the emission boundary itself.

## 7. Redaction of Logs and Outputs

`02-governance-and-security/06-data-governance-and-privacy.md` §8 fixes that personal and sensitive data are redacted wherever not authorized to appear, that redaction applies at the point data would otherwise be captured, that redaction never substitutes for retention, deletion, or consent obligations, and that uncertainty resolves to redaction. This section determines, explicitly, whether the existing emission-boundary redaction filter is the mechanism this requirement rides on.

### 7.1 What the Existing Filter Already Provides

`04-security-controls-design.md` §2.2 fixes a single, mandatory choke point per emission channel — the structured-logging writer, the error/exception serializer, and the API-response serializer — through which every value passes before emission, never after, with no code path that bypasses it. This architecture is exactly the shape this document's own redaction requirement needs: one mandatory choke point per channel, invoked by construction, blocking before emission, deny-by-default on an unclassifiable value. **This document reuses that same choke point and builds no second one** — the discipline every design document in this layer has now applied consistently, and the discipline this document's own ticket requires explicitly.

### 7.2 What the Existing Filter Does Not Provide, Stated Plainly

`04-security-controls-design.md` §2.2's own matching logic is scoped to **secret-shaped** values: field-name classification against credential-shaped names (`password`, `token`, `secret`, `key`, `credential`, `authorization`, and their structural variants), and value-shape classification using the same pattern- and entropy-based techniques §2.1 there designs for scanning committed content. Neither technique, as that document fixes it, is built to catch a personal name, an email address, a phone number, a physical address, or a government-issued-identifier-shaped value: these are not high-entropy or credential-shaped in the sense the value-shape classifier targets, and their field names (`email`, `full_name`, `date_of_birth`, `phone_number`) are not among the secret-shaped names the field-name classifier recognizes. **The existing filter's architecture is the right mechanism for this document's requirement; its matching criteria are not sufficient on their own, and this document states that plainly rather than assuming coverage it has not checked.**

### 7.3 The Extension: Two Additional Match Classes, Added to the Same Filter

This document extends `04-security-controls-design.md` §2.2's filter with two further match classes, run at the identical choke point and under the identical blocking and deny-by-default rules that document already fixes — never as a second filter, and never invoked from a second code path:

- **Classification-driven matching.** Because a data-governance category and classification tier already travel with a governed data element as an intrinsic, resolved property (§3.1 above; `06-compliance-and-data-residency-design.md` §5), the filter is extended to consult that already-resolved property directly at the point of emission: a value bound to a field the resolved property marks personal or sensitive is redacted on that basis alone, independent of whether the value's own shape or field name would otherwise be recognized. This is a strictly stronger signal than shape-inference alone, because it does not depend on the value looking like anything in particular — it depends on what the platform already knows the value *is*, resolved once and carried forward rather than re-inferred at each emission.
- **PII-shape and PII-field-name matching, for the case the resolved property is unavailable.** Where an emitted value's governing classification cannot be resolved at the point of emission (an ad hoc log statement over a value not yet routed through the resolution mechanism), the filter is extended with a further pattern set recognizing personal-data-shaped structure — an email-address structure, a phone-number structure, a government-issued-identifier-shaped structure — and a further field-name set recognizing personal-data-shaped names, run alongside, never in place of, the secrets-matching criteria §2.1–§2.2 there already fix.

### 7.4 Deny-by-Default and the Redaction/Obligation Separation, Both Inherited Unchanged

- **Uncertainty resolves to redaction**, exactly as `04-security-controls-design.md` §2.2 already fixes for a secret-shaped value it cannot confidently classify, extended here to a value this document's own matching classes cannot confidently classify either way: it is redacted, not passed through.
- **Redaction does not substitute for retention, deletion, or consent.** Redacting a personal-data value from a log or output satisfies this document's §7 requirement alone; it has no bearing on whether that same data must still be deleted under §4 or held only on a valid basis under §5 — each obligation is checked and enforced independently, exactly as the specification's own §8 states.
- **Key material remains subject to `04-security-controls-design.md` §2's mechanisms with no exception**, unaffected by this document's extension — this document adds match classes for personal and sensitive data; it does not alter, narrow, or relax the secrets-matching criteria already fixed there.

## 9. Design Decision Records

### 9.1 ADR-024 — Personal- and Sensitive-Data Lifecycle Enforcement: the Traveling Category, the Retention Sweep, the Collection-Time Basis Check, and the Redaction-Filter Extension

- **Status:** Approved (`DECISIONS.md` D-47, 2026-08-18).
- **Cost to reverse:** **Very high**, matching the grade `implementation-document-map.md` already assigns this document. The classification, retention, and deletion mechanism this decision fixes acts directly on stored data: reversing or materially weakening it does not merely change code, it requires re-classifying every governed record under the corrected mechanism and re-establishing, for every element already swept, whether the deletion or de-identification already performed was consistent with what the corrected mechanism would have required. Data destroyed under a superseded retention rule is not recoverable (§4.4) — a deletion already performed under a mistaken resolution cannot be undone by reversing the decision that produced it, which is a materially different and worse failure mode than a merely expensive migration. This is stated at that grade honestly, not understated to make the decision look cheaper than it is.
- **Upstream decisions assumed:** `06-compliance-and-data-residency-design.md` §5 (the classification tier as a traveling property, and the most-restrictive-default discipline this decision extends rather than re-derives) and its ADR-023 (the Region Boundary Check and Registry Accessor extension this decision's own mechanisms compose with, never duplicate); `02-tenant-isolation-and-access-control-design.md` §3, §5 (the Registry Accessor, Context Resolution Point, and connection-scoping mechanism the Retention Sweep and the Consent and Minimization Check are both bound by); `04-security-controls-design.md` §2.2 (the emission-boundary redaction filter this decision extends) and §4.2 (the vulnerability-severity translation step this decision's PII-exposure classification composes with); `02-platform-data-model-design.md` §10 (the never-hard-deleted convention for `platform.tenants`/`platform.applications`, and the reasoning — INV-08 and audit-referential need — this decision's §4.3 reads deletion against for the platform-primitive identity case). ADR-021 (KMS selection), ADR-022 (provenance enforcement point), and ADR-023 (region scoping and the split residency-approval gate) remain Provisional and are not assumed settled; this decision depends only on ADR-023's already-designed mechanism, not on its approval status.
- **Verified vs. reasoned:** Reasoned throughout. The argument is structural — extending an already-traveling property rather than creating a second one, scheduling a sweep on the same discipline an existing operational procedure already uses, checking a basis before rather than after collection, and extending an existing filter's match criteria rather than building a second filter — and makes no claim about any specific jurisdiction's current legal requirement, regulation, or regime.
- **Question this answers:** Given that `06-compliance-and-data-residency-design.md` already made classification tier an intrinsic, traveling property and stopped at its residency consequence, what concrete mechanism realizes the *handling* consequence — retention, deletion, consent, minimization, and redaction — atop that same property without creating a second classification scheme or a second scoping path; how is a retention obligation evaluated and made to result in an actual deletion against storage shapes this document does not itself own; where is a consent-and-minimization basis checked before collection or use rather than reviewed for afterward; and does the existing emission-boundary redaction filter already cover personal- and sensitive-data redaction, or does it need extending?
- **Criteria applied, and how each resolved:**
  1. *Extend the traveling property already established, rather than define a second one.* The data-governance category is resolved and read at the same points, and under the same deny-by-default discipline, the classification tier already is — decisive; a second, independently-resolved classification scheme would require every consumer to reconcile two properties instead of reading one, and the specification's own §3 frames the category as sitting "alongside," never in competition with, the tier.
  2. *Compose the retention and collection-time checks with the nearest existing precedent, rather than invent an unrelated shape.* No existing mechanism evaluates a data element's own lifecycle state on a schedule; the nearest precedent, `04-security-controls-design.md` §7.3's key-rotation procedure, was extended in kind for the Retention Sweep. Decisive for the sweep. For the Consent and Minimization Check, no existing write-mediation gateway for builder-defined entity data exists yet to extend — this criterion is therefore only partially decisive here; the check's structural placement (before collection or use, never after) is fixed now, and its concrete integration point is bound onto `02-data-model-and-entity-design.md`'s and `01-application-construction-design.md`'s own not-yet-made design, exactly as `06-compliance-and-data-residency-design.md`'s ADR-023 bound its own obligation model onto `08-multi-region-distribution-design.md`'s not-yet-made topology.
  3. *Determine, rather than assume, whether the existing redaction filter suffices.* Checking `04-security-controls-design.md` §2.2's own matching criteria against the shape of personal data (structured, often low-entropy, non-credential-named) shows the architecture is right and the matching criteria are not sufficient — decisive: the filter is reused at the same choke point, extended with two further match classes (§7.3), never duplicated by a second filter.
  4. *Reuse the existing severity-classification step for PII exposure, rather than a new scale.* The specification's own §7 states the exposure rule "never a new scale" directly; decisive, and mechanically realized by adding criteria to `04-security-controls-design.md` §4.2's existing translation table rather than defining a fifth severity axis.
- **Context:** `06-compliance-and-data-residency-design.md` §2 named this document, by its own citation, as the owner of "the full data-handling matrix built atop the classification tiers... retention, deletion, consent, minimization, and redaction" — this decision is the first design act discharging that handover in full.
- **Decision:** (1) The data-governance category (non-personal, personal, sensitive personal) is resolved and read as a further intrinsic, traveling property alongside the classification tier, on the same deny-by-default discipline, resolving to sensitive personal data by default where unclassifiable (§3.1). (2) A Retention Sweep — an operationally scheduled procedure on the same discipline the existing key-rotation procedure already uses — evaluates each element's Retention Obligation and triggers deletion or de-identification on purpose end, consent withdrawal, or ceiling, whichever occurs first (§4.1–§4.2). (3) Deletion is realized concretely against each storage shape it can occupy: field-level erasure of personal-data content where the row itself is never hard-deleted for a reason this document does not own, and a purge or de-identification reaching every retained historical version where a builder-defined entity's history mechanism would otherwise retain the content indefinitely — a binding requirement this decision places on `02-data-model-and-entity-design.md`'s design of that mechanism (§4.3). (4) A Consent and Minimization Check is required at the point of collection or use, refusing rather than flagging a missing basis or an excess-of-scope collection, its structural placement fixed now and its concrete integration point bound onto the not-yet-written construction and entity documents (§5.2). (5) PII exposure is classified through `04-security-controls-design.md` §4.2's existing translation step, with a sensitive-personal-data floor of High and an absolute exclusion of Low for any personal-data exposure, and halts additionally where it coincides with an INV-01–INV-03 breach (§6). (6) The existing emission-boundary redaction filter is extended with classification-driven matching and a PII-shape/field-name match class, at the same choke point, never a second filter (§7.3).
- **Alternatives considered:** *A second, independently-resolved classification scheme for the data-governance category, separate from the residency tier* — rejected under criterion 1; it would require every consumer to reconcile two properties where the specification itself frames one as riding alongside the other. *An entirely new, purpose-built scheduling mechanism for the Retention Sweep, designed without reference to the key-rotation precedent* — rejected under criterion 2; the precedent's shape (operationally scheduled, reading metadata the schema already carries) transfers directly and avoids inventing a second scheduling discipline this layer would then have to reconcile against the first. *Building a second, PII-specific redaction filter at each emission channel, running alongside the existing secrets filter* — rejected under criterion 3 and explicitly by the ticket instructing this document's own work; two filters at the same choke point would double the risk of a code path bypassing one while satisfying the other, exactly the failure mode a single, extended filter avoids by construction. *A fifth severity class specific to PII exposure, distinct from the four `02-governance-and-security/02-security-policy.md` §6 already fixes* — rejected directly by the specification's own instruction that exposure is "classified using the existing severity classes, never a new scale."
- **Consequences:** Binds `02-data-model-and-entity-design.md` to supply, for every builder-defined entity, a history mechanism capable of purging or de-identifying personal-data content from every retained version, not only the current one, and a write-mediation point capable of running the Consent and Minimization Check inline before a collection or use proceeds. Binds `01-application-construction-design.md` to expose, at the build surface, whatever a builder needs to disclose a purpose and record a consent or minimization basis in a form this document's check can read. Binds `03-software-and-architecture/06-non-functional-requirements.md`'s already-owned numeric retention ceilings to be readable by the Retention Sweep in the form §4.1 requires. Binds `04-security-controls-design.md`'s emission-boundary filter to carry the two additional match classes of §7.3 without this document altering that filter's secrets-matching criteria, choke-point placement, or blocking behavior. Binds `08-audit-and-traceability-design.md` to the seven-row evidence list of §8. Does not alter `06-compliance-and-data-residency-design.md`'s classification-tier mechanism, `02-tenant-isolation-and-access-control-design.md`'s Registry Accessor or connection-scoping mechanism, or `02-platform-data-model-design.md`'s never-hard-deleted convention for the platform registry, beyond the single reuse each is put to above.

## 12. Binding Rules

These rules hold for every element of this document and are subordinate to the specification and the charter.

- **The data-governance category is intrinsic and travels with the data it classifies, alongside the classification tier, never as a second competing scheme.** An unclassifiable or unrecorded category resolves to sensitive personal data, never to non-personal (§3.1).
- **The handling matrix is a resolved, cumulative obligation, read at the same points and under the same discipline the residency obligation already is.** A more restrictive tier or regime only adds to the category's floor obligation, never subtracts from it (§3.2).
- **Every governed personal-data element carries a Retention Obligation, evaluated by the mandatory, unconditional Retention Sweep**, which triggers deletion or de-identification on purpose end, consent withdrawal, or ceiling — whichever occurs first (§4.1–§4.2).
- **"Deleted" means field-level erasure where the row itself cannot be removed for a reason this document does not own, and a purge across every retained historical version where a history mechanism would otherwise retain the content** — never a claim of row-level or version-level irreversibility this document's mechanism does not deliver (§4.3).
- **A deletion already performed under a mistaken retention resolution is not recoverable by this document's mechanism.** This cost asymmetry is stated honestly, not understated (§4.4).
- **Deletion is bound by INV-04 and by the same connection-scoping and residency mechanisms that bind every other write; it holds no exemption** (§4.5).
- **A Consent and Minimization Check runs at the point of collection or use, before it proceeds, and refuses rather than flags a missing basis or an excess-of-scope collection.** Its concrete integration point is bound onto the not-yet-written construction and entity documents, never assumed settled here (§5.2).
- **Consent never widens access beyond the role-and-permission grant** already governed elsewhere (§5.4).
- **PII exposure is a blocking check, not a numbered invariant and never a guardrail metric.** It is classified through the existing four-class severity scale, with a sensitive-personal-data floor of High and an absolute exclusion of Low, and halts additionally where it coincides with an INV-01–INV-03 breach (§6).
- **The existing emission-boundary redaction filter is the mechanism this document's redaction requirement rides on, extended — never duplicated — with classification-driven and PII-shape/field-name match classes** (§7.1–§7.3).
- **Redaction never substitutes for retention, deletion, or consent, and uncertainty at every check this document fixes resolves toward the more protective outcome** — redaction, refusal, or the more restrictive default (§7.4 and throughout).
- **Every control this document fixes produces the evidence record §8 names**, as a fixed input `08-audit-and-traceability-design.md` designs storage and tamper-evidence around.
- **No specific jurisdiction, regime, or regulation is named anywhere in this document**, and no time-sensitive legal claim is asserted as verified (§1).
- **This document records exactly one ADR.** ADR-024 (§9) is the genuine, independent decision this document makes; every other design choice above realizes a location, structure, or boundary the cited specification and the cited upstream design documents already fix.
