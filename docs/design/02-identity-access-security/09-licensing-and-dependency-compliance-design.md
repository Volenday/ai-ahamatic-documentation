# Licensing and Dependency Compliance Design

## 1. Purpose and Reading Order

This document realizes `02-governance-and-security/08-legal-and-licensing-constraints.md` §3–§7 as concrete, enforced mechanism: the permitted/prohibited license-category check (§4), the third-party dependency policy that admits a dependency (§5), the attribution requirement (§6), and license-incompatibility as a blocking, escalating check (§7). It answers **how** — where each check runs, what it inspects, what it blocks, and how uncertainty resolves — never re-deciding what the specification already fixes.

This is the final document of the Identity, Access & Security layer. It also discharges two standing obligations handed to it by name: `05-ai-tooling-security-design.md` §4.3's open question on license-encumbered or reproduced *generated* content, which that document states explicitly is addressed by no mechanism it designs; and `01-technology-stack-design.md` §22.2's (ADR-012) demonstration that a dependency's license category is not a stable property, which requires this document's mechanism to re-check an already-admitted dependency, not only its first admission.

It is structured as a pyramid: first the license-category check itself (§3); then the dependency policy that check enforces, including re-evaluation on change (§4–§5); then the attribution requirement that follows from an admitted dependency's category (§6); then license-incompatibility as the blocking check that protects the whole (§7); then the generated-content question, answered on its own terms (§8); then the evidence this document's controls produce, expressed in the audit layer's own consolidated model (§9); then the one design decision this document records (§10); then its boundaries, precedence, and binding rules (§11–§13).

**Verified versus reasoned (`PROCESS.md` §12.3).** No specific scanning tool, similarity-detection product, or vendor is named or asserted as verified anywhere in this document — every mechanism is described structurally, consistent with `01-technology-stack-design.md` §22.2's own non-vendor-specific discipline. The one time-sensitive claim this document relies on — the Redis-to-AGPLv3 relicensing timeline — is already verified by `01-technology-stack-design.md` §22.2–§22.3 and is cited, not re-verified, here.

## 3. The License-Category Check

**What it inspects.** For every dependency proposed for incorporation — a library, module, template, asset, dataset, model, or other content brought in from outside the platform's own primitives or a builder's own built artifact — the check resolves a license identifier from that dependency's own declared distribution metadata, and maps that identifier to one of the five categories `02-governance-and-security/08-legal-and-licensing-constraints.md` §4 fixes: Permissive-grant, Condition-propagating, Restricted-field-of-use, Commercial/negotiated-rights, or No-license/unconfirmed. *Reasoned, not verified*: this document names no specific scanning tool or license-identifier database — which one is adopted is an implementation-detail choice this document leaves open, on the same non-vendor-specific discipline `01-technology-stack-design.md` §22.2 already holds.

**How an unresolvable or unrecognized license resolves.** Where the check cannot resolve a discoverable identifier, or resolves one it does not recognize against the fixed category table, the dependency is treated as No-license/unconfirmed and its status is Prohibited absolutely — the mechanism-level form of the specification's own rule that "the absence of a stated restriction is never treated as permission" and that uncertainty "resolves to the most restrictive applicable category." No judgment call weighs in; an unrecognized identifier is never treated as a probable match to a permitted category.

**Where it runs, and what it blocks.** The check runs before any change to the platform's own declared dependency set is accepted — a new dependency, a version change, or a new combination — and before any module, SDK-distributed component, or marketplace offering crossing the extension boundary is admitted, exactly the same boundary the platform's own security review protects (`02-governance-and-security/08-legal-and-licensing-constraints.md` §5). A resolved status of Prohibited blocks that change or that offering from advancing; the check is a precondition to admission, never a finding raised after the fact (§5's own "established before incorporation, never after"). What the check's output feeds — the blocking mechanism itself — is designed in §7, not here; this section produces the classified category, §7 is what the category's status does next.

## 4. Third-Party Dependency Policy Enforcement

**What admits a dependency.** A dependency is admitted only once §3's check resolves its category to Permitted, or to Permitted-under-condition with the condition confirmed satisfiable for the combination it enters (Condition-propagating, Restricted-field-of-use, or Commercial/negotiated-rights, each per `02-governance-and-security/08-legal-and-licensing-constraints.md` §4's own table). No dependency's category is assumed from a prior admission of a similarly named or similarly sourced dependency; every admission event re-runs §3's check fresh against the specific dependency and version being incorporated.

**Where admission is checked.** At the same two points §3 fixes: a change to the platform's own dependency manifest, and a module, SDK-distributed component, or marketplace offering crossing the extension boundary. Both are the same trust boundary the platform's own security review already protects for vulnerability risk (`02-governance-and-security/08-legal-and-licensing-constraints.md` §5); this document's check occupies that boundary for licensing risk, composing with it rather than opening a second admission point.

**Tracking.** For as long as a dependency remains incorporated, the platform maintains a record of every currently-incorporated third-party dependency, its resolved category, and its resolved license identifier — the generic means the specification requires (§5) to know at any time which obligations are carried. This tracked set is what §5's re-evaluation and §6's attribution generation both read from; it is not a separate ledger either mechanism maintains independently.

**Builder/built separation.** The same check is exposed, informationally, through whatever module- or marketplace-installation channel already serves a builder, so a builder can learn a candidate dependency's resolved category before choosing to incorporate it into their own built artifact. Exposure is informational, not enforced against the builder: the platform's own obligation is narrower — never itself supply a builder a primitive, module, or marketplace offering carrying a Prohibited or unconfirmed category — never to police what a builder separately chooses to add to their own built artifact, preserving INV-06 exactly as `02-governance-and-security/08-legal-and-licensing-constraints.md` §5's own closing bullet requires.

## 5. Re-Evaluation on Change — the Standing ADR-012 Obligation

The specification requires that "a change to a dependency is re-evaluated, not carried forward on assumption" (§5) — a rule this document's mechanism must satisfy for a dependency already admitted, not only at first admission. `01-technology-stack-design.md` §22.2 supplies the concrete demonstration of why: a caching technology's license category is checked "at the moment of adoption, on the evidence then current," because a permissively licensed dependency can leave that footing entirely without any change to the platform's own manifest entry for it — Redis left its permissive BSD terms for a dual source-available model in March 2024 and shipped Redis 8 under AGPLv3, carrying network copyleft, on 1 May 2025.

**Two triggers, not one.** §3's check re-runs on every dependency-manifest change (a version bump, a replacement, a new combination) — event-driven, and already required by §4 above. It additionally re-runs, independent of whether the manifest changed, on a periodically scheduled sweep — the **License Sweep** — over every currently tracked dependency (§4), re-resolving each one's category against then-current evidence. The event-driven trigger alone would not satisfy ADR-012's own demonstration: the Redis relicensing changed nothing in a consumer's manifest entry, so a mechanism that re-checks only on manifest change would carry a now-Prohibited dependency forward indefinitely, exactly the assumption §5 forbids.

**Consequence of a flip.** Where the License Sweep, or an event-driven re-check, resolves an already-admitted dependency's category to Prohibited or No-license/unconfirmed where it previously resolved otherwise, this is a license-incompatibility exactly as §7 defines it — "a dependency of the No-license/unconfirmed or Prohibited category... has been... incorporated" — classified and blocked on the same terms as a first-admission finding (§7). Remediation — replacing, negotiating, or otherwise resolving the now-incompatible dependency — is `05-meta-operations/08-change-management-and-evolution-policy.md`'s own mechanics, cited and not designed here; this document's own contribution stops at producing the finding.

## 6. Attribution Generation

**Attribution is derived, not hand-maintained.** Whenever §3's check confirms a dependency's category, it also captures, verbatim, whatever attribution-notice text that dependency's own license requires — into the tracked-dependency record §4 fixes. A regeneration step re-derives the platform's own aggregate attribution artifact — distributed with the platform's own primitives, its accompanying documentation, or its output, wherever the license requires — by concatenating the captured notice of every currently tracked dependency, every time that tracked set changes: an admission, a removal, a version replacement, or a License Sweep re-confirmation (§5). No person edits a static notice file by hand; the artifact is a byproduct of the same check that admits and re-checks the dependency it attributes.

**Cumulative across a combination.** Regeneration iterates the full current tracked set on every run, never a subset resolved once and left stale — removing one dependency drops exactly its notice on the next regeneration; adding one adds exactly its notice; satisfying one dependency's attribution condition never substitutes for another's, the specification's own §6 rule realized directly by iterating the whole set each time rather than tracking obligations independently per dependency.

**A gap is a license-incompatibility, not a cosmetic omission.** Where the regeneration step cannot produce the required notice text for a dependency §3 has already confirmed as carrying an attribution condition, that gap is itself classified and blocked under §7 below — Moderate severity per the specification's own table, unless the gap coincides with the dependency's underlying category being unresolved, in which case the underlying category's own severity governs instead.

**Builder/built separation.** The same generation mechanism, exposed through whichever channel already serves a builder (§4), produces the builder's own attribution artifact for their own incorporated dependencies. The platform generates and reproduces the attribution its own incorporated dependencies require; a built artifact's builder is responsible for reproducing the attribution their own incorporated dependencies require, using the same generation mechanism if they choose to; neither obligation discharges the other (`02-governance-and-security/08-legal-and-licensing-constraints.md` §6's closing bullet).

## 7. License-Incompatibility as a Blocking, Escalating Check

**Placed in the register `PROCESS.md` §11 fixes, and no other.** License-incompatibility is not a numbered invariant — none of INV-01 through INV-09 names it as its own property — and it is never treated as a guardrail metric, a measured value optimized against while other targets are pursued: the specification's own framing of these obligations as "floors, never spent" (`02-governance-and-security/08-legal-and-licensing-constraints.md` §8) is the direct rejection of the metric register for this finding. It is a **blocking check**, evaluated through `04-security-controls-design.md` §4.2's existing severity-translation step rather than a mechanism of its own.

**The mapping, added as further rows to that existing table, never a new scale.** The specification's own §7 table already assigns each condition directly to one of policy §6's four classes; this document's contribution is stating which of its own mechanisms produces each condition:

| Condition | Produced by | Severity |
|---|---|---|
| A Prohibited or No-license/unconfirmed dependency has been, or would be, incorporated into the platform's own primitives. | §3's check at first admission, or §5's License Sweep flipping an already-admitted dependency. | Critical. |
| A combination's license obligations cannot be reconciled, or a dependency is used outside its permitted field of use, once already incorporated. | §3's check at combination time, or §5's re-check discovering the same on an already-admitted dependency. | High. |
| A required attribution has not been, or would not be, reproduced. | §6's regeneration step, on a gap it cannot fill for a dependency otherwise confirmed. | Moderate. |
| A dependency's license category cannot be established with confidence. | §3's check, unresolved. | No lower than the most severe condition the dependency could turn out to fall under — the same deny-by-default discipline `04-security-controls-design.md` §4.2 already applies to an ambiguous vulnerability-severity mapping, applied here to an ambiguous license-category mapping. |

**Blocking, in any lifecycle phase.** A change that would introduce or leave unresolved any row above does not proceed — design, execution, a module or marketplace submission, or a self-correction attempt, exactly as `02-governance-and-security/08-legal-and-licensing-constraints.md` §7 requires. A Critical or High finding additionally blocks release, mirroring the release-blocking rule `02-governance-and-security/02-security-policy.md` §6 already fixes, without redefining its threshold. A Moderate finding is tracked and remediated on a managed path rather than blocking release on its own, and may not accumulate into a High or Critical condition. **This document stops at producing the classified finding** — the gate's own pass/fail evaluation and the rollback trigger a post-release Critical or High finding calls are `04-devops-and-cloud-infra/03-testing-and-quality-gates.md`'s and `04-devops-and-cloud-infra/05-release-and-rollback-protocol.md`'s own mechanics, cited, never redesigned here. How the halt is carried out and how escalation is requested and routed are the Meta-Operations documents' own, cited by the specification and not restated here.

## 8. The Generated-Content Question, Answered

**The question, restated precisely.** `05-ai-tooling-security-design.md` §4.3 states that license-encumbered, injected, or reproduced generated content is addressed by no mechanism it designs, and hands the question here on the distinction it draws: §3's check governs *declared* third-party dependencies — a manifest entry, a distribution identifier, discoverable metadata. A model may reproduce content, verbatim or near-verbatim, from its own training data into a suggestion with **no declared dependency to scan**. This is not a case where §3's check runs less thoroughly; it is a case where the precondition §3 depends on — a discoverable, declared dependency — does not exist to inspect.

**Decision: a distinct technique, composing with §3's chokepoint, not an extension of §3's own scan.** Extending a manifest-keyed check to inspect undeclared generated text would not be an extension of the same mechanism — the input shape is entirely different, and calling it an extension would misdescribe what actually changes. Instead: a **content-similarity check** compares AI-generated or AI-suggested output against a reference corpus of known licensed or copyrighted material, run at the same point §3's own check already occupies — before generated content is treated as admitted or incorporated — composing with an existing chokepoint rather than opening a second one. Where a match is found, it is routed through §3's own category table and §7's own blocking mechanism exactly as a declared dependency's finding would be; no new category and no new severity axis is created for this case.

**The honest limit, stated plainly rather than closed by assumption.** This technique detects only what its comparison corpus actually contains. A result of *no match* is recorded, and must be read, as exactly that — the absence of a detected match against the corpus compared — never as confirmation that the generated content carries no license obligation. No corpus of licensed or copyrighted material can be exhaustive; content reproduced from a source outside the corpus, or paraphrased enough to defeat similarity matching without changing its underlying obligation, is not addressed by this or any mechanism available now. **This is the mechanism-level degrade this document states honestly rather than re-deferring**, on the same discipline `05-ai-tooling-security-design.md` §3.3 applies to a misled suggestion and `08-audit-and-traceability-design.md` §6.3 applies to tamper-evidence: the check reduces the risk it can see; it does not, and is not claimed to, close the risk it cannot.

**This realizes a clause the specification already contains; it does not require one added.** `02-governance-and-security/08-legal-and-licensing-constraints.md` §4 already states that "category is what governs, not the source of the content," naming generated output alongside open-community and commercial sources as a source the category table already applies to. What was missing was a mechanism for resolving generated content to a category absent a declared dependency to scan; that mechanism is what this section supplies. No specification gap is raised.

## 10. Design Decision Records

### 10.1 ADR-026 — License-Category Check Composition, Standing Re-Evaluation, Derived Attribution, and the Generated-Content Detection Limit

- **Status:** Team-Approved.
- **Cost to reverse:** **Low** (`PROCESS.md` §12.1's cheapest rung). Every mechanism this decision fixes is a policy check over the tracked dependency set; reversing it removes a check location or a re-check trigger, and at worst leaves a dependency that must be re-evaluated or swapped under the ordinary policy this document already designs. No mechanism this decision fixes destroys, transforms, or irreversibly commits any data or external state.
- **Upstream decisions assumed:** `02-governance-and-security/08-legal-and-licensing-constraints.md` §4–§7 (authoritative, consumed in full); `01-technology-stack-design.md` §22.2 / ADR-012 (the standing obligation §5 discharges); `04-security-controls-design.md` §4.2 (the severity-translation step §7 composes with); `08-audit-and-traceability-design.md` §4.2–§4.3 (the event model §9 populates); `05-ai-tooling-security-design.md` §4.3 (the open question §8 answers). ADR-021 through ADR-025 remain Provisional and are not assumed settled; this decision depends on each only for the already-designed mechanism it consumes, never on its approval status.
- **Verified vs. reasoned:** The Redis-to-AGPLv3 relicensing timeline this decision's §5 reasoning relies on is already verified by `01-technology-stack-design.md` §22.2–§22.3 and is cited, not re-verified, here. Every other finding — the composition with the existing severity step, the two-trigger re-evaluation design, the derived-attribution mechanism, and the generated-content technique's own detection limit — is reasoned from the cited specification's and cited design documents' structural properties; no specific scanning tool, similarity-detection product, corpus, or vendor is named or asserted as verified.
- **Question this answers:** Given a dependency-license scan that must run before incorporation, never assume a category holds unchanged once a dependency is already admitted, produce attribution as a byproduct rather than a hand-maintained artifact, and account for content a model may reproduce with no declared dependency to scan — what single set of mechanisms satisfies all four without inventing a parallel severity scale, a second admission chokepoint, or an overclaimed detection guarantee?
- **Criteria applied, and how each resolved:**
  1. *Compose with the existing severity-classification step, rather than a new axis.* Decisive — the specification's own §7 states its severity framing is drawn from policy §6's existing four classes "never a new scale," so this document's blocking check adds rows to `04-security-controls-design.md` §4.2's existing table rather than defining a fifth severity axis.
  2. *An event-driven-only re-check versus an added periodic License Sweep.* Decisive for adding the sweep — ADR-012's own demonstration is that a license can change with zero change to the consumer's manifest entry, so a trigger keyed only to manifest change would carry a now-Prohibited dependency forward indefinitely, precisely the assumption the specification's §5 forbids.
  3. *A derived attribution artifact versus a hand-maintained one.* Decisive for deriving it — a hand-maintained artifact drifts from the tracked set the moment either changes without a matching edit; deriving it from the same check that admits and re-checks each dependency removes that drift by construction rather than by discipline.
  4. *Extending §3's own manifest-keyed scan to generated content versus a distinct technique.* Decisive for the distinct technique — the input shape (a declared manifest entry versus undeclared generated text) differs entirely, and describing a scan over one as an "extension" covering the other would misstate what the mechanism can actually detect; keeping the two separate keeps the generated-content technique's own honest limit visible rather than laundering it into the manifest scan's implied completeness.
- **Context:** This is the final document of the Identity, Access & Security layer, closing two standing obligations named to it by upstream documents: `05-ai-tooling-security-design.md` §4.3's open question and `01-technology-stack-design.md` §22.2's re-check requirement, alongside the specification's own §4–§7 mechanism this document was ticketed to design in full.
- **Decision:** (1) The license-category check (§3) resolves a dependency's category before incorporation and defaults an unresolved or unrecognized license to Prohibited. (2) Re-evaluation runs on two triggers — every manifest change, and a periodic License Sweep over the full tracked set (§5) — so an already-admitted dependency's category is never carried forward on assumption. (3) Attribution is generated as a byproduct of the same check, regenerated on every change to the tracked-dependency set, never hand-maintained (§6). (4) License-incompatibility is classified through `04-security-controls-design.md` §4.2's existing translation table, extended with this document's own rows (§7), never a new severity axis. (5) Generated-content risk is addressed by a distinct content-similarity technique at the same chokepoint as §3's check, whose result vocabulary (`no-match-against-corpus`, never `clear`) states its detection limit structurally rather than only in prose (§8–§9).
- **Alternatives considered:** *Checking license category only at first admission, with no periodic sweep* — rejected under criterion 2; ADR-012 names this exact insufficiency. *A hand-maintained NOTICE file, updated by convention when a dependency changes* — rejected under criterion 3; convention-based maintenance is precisely the drift risk the specification's "never abbreviated or omitted for convenience" rule exists to prevent. *A fifth severity axis specific to licensing, distinct from policy §6's four classes* — rejected directly by the specification's own instruction that license-incompatibility is framed "using the existing severity classes, never a new scale." *Extending §3's own dependency scan to also fingerprint AI-generated output* — rejected under criterion 4; the two inputs are not the same shape, and treating them as one mechanism would risk the generated-content case inheriting an unearned appearance of the manifest scan's completeness.
- **Consequences:** Binds no unwritten document to a new obligation it did not already expect: the comparison corpus and its own hosting for the generated-content similarity check (§8) are left to whichever future environment or tooling selection adopts one, on the same at-the-moment-of-adoption discipline ADR-012 already fixes, and this decision claims no authority over that future choice. Binds `05-meta-operations/08-change-management-and-evolution-policy.md` only on the terms the specification's own §8 already hands it — the remediation mechanics for a dependency a License Sweep finding requires replacing. Adds rows to `04-security-controls-design.md` §4.2's translation table without altering its structure, its other rows, or the gate mechanics it feeds. Adds `event_type` values to `08-audit-and-traceability-design.md`'s base record without altering that record's shape, storage, or tamper-evidence mechanism.

- **The charter prevails**, and the specification this document realizes prevails over this design wherever the two appear to conflict; this document is corrected to match the specification, never the reverse.
- **These obligations are floors, never spent.** No check, policy, attribution requirement, or blocking condition in this document is weakened to admit a dependency faster, reduce scan volume, or meet a deadline.
- **A breach overrides apparent gain.** An outcome this document's mechanisms would need to relax to permit — admitting a Prohibited dependency, carrying forward a category no longer confirmed, omitting a required attribution, or reading a generated-content non-match as a clearance it did not establish — is refused regardless of the value it appears to create.

This document owns the license-category check (§3), the dependency policy's admission point and re-evaluation on change (§4–§5), attribution as a generated artifact (§6), license-incompatibility as a blocking check (§7), and the resolution of the generated-content question (§8). ## 13. Binding Rules

These rules hold for every actor and every action subject to this model and are subordinate to the charter.

- **A dependency's license category is resolved before incorporation.** An unresolvable or unrecognized license defaults to No-license/unconfirmed and is prohibited absolutely; no judgment call weighs a source or reputation against the category table (§3).
- **Category governs permission exactly as the specification's own table fixes it.** This document's check never substitutes a source-based or reputation-based judgment for that table.
- **An already-admitted dependency's category is never carried forward on assumption.** It is re-checked on every manifest change and by the periodic License Sweep; a category that held for a prior version or a prior evidentiary state is not assumed to hold unchanged (§5).
- **Attribution is generated, never hand-maintained, and regenerated on every change to the tracked-dependency set.** A missing or incomplete attribution is a license-incompatibility, not a lesser concern (§6).
- **License-incompatibility is a blocking check, evaluated through the existing severity-translation step, never a new scale.** Critical or High blocks release; Moderate is tracked and remediated without blocking release on its own (§7).
- **Generated content is checked by a distinct technique whose result vocabulary never asserts a clearance it did not establish.** A non-match is recorded as exactly that — no match found against the corpus compared — never as confirmation of no license obligation (§8–§9).
- **The builder/built separation holds throughout.** The platform's obligation is to never itself supply a Prohibited or unconfirmed dependency; a builder's own choice of dependency for a built artifact remains the builder's own content, never a platform assumption on the builder's behalf.
- **Everything remains domain-neutral and platform-level.** No category, policy, or check in this document encodes the characteristics of any single domain; all remain valid for any software built on the platform.
- **This document records exactly one ADR.** ADR-026 (§10) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, category, or boundary the cited specification and cited upstream design documents already fix.
