# Compliance and Data Residency Design

## 1. Purpose and Reading Order

This document realizes `02-governance-and-security/05-compliance-and-data-residency.md` in full — data-classification tiers (§4), applicable compliance regimes (§5), per-region residency rules (§6), and the human-approval gate for a residency-violating action (§7) — as concrete, enforced mechanisms. It answers **how** INV-07 (residency adherence) becomes structurally true rather than procedurally observed: how a region obligation is resolved for a request, how that obligation is carried and enforced, how a classification tier travels with data as an intrinsic property, how a per-region rule becomes a constraint a request cannot pass, and where the human-approval gate for a residency-violating action concretely sits.

**This document creates the region-scoping mechanism.** No upstream design document defines one. `04-security-controls-design.md` §3.3 and §11 state that "tenant-, authorization-, and region-scoping remains exclusively `02-tenant-isolation-and-access-control-design.md`'s" — an over-attribution that document does not itself make: the word *region* appears nowhere in it, and its own §2 hands residency enforcement here explicitly ("Residency enforcement... each owned elsewhere, restated as a boundary in §11" — a restatement its own §11 does not in fact carry through, a gap this document does not treat as blocking since §2's statement is itself the operative handover). This document is that elsewhere. §3 below designs the mechanism, and §11 states the correction plainly so a later reader of `04-security-controls-design.md` §3.3/§11 is corrected by this document rather than misled by that one.

The mechanism composes with, and never duplicates, tenant scoping. It reuses the Registry Accessor, the Context Resolution Point, and the connection-acquisition function `02-tenant-isolation-and-access-control-design.md` §3–§5 already fix, extending each with one additional resolved value and one additional inline check — never a second accessor, a second resolution point, or a second scoping path. This is the same discipline that document's own §3.3 applies to request validation, held here in the reverse direction: region scoping must not become a second tenant-resolution mechanism, exactly as validation must never become a second region- or tenant-scoping mechanism.

**Verified versus reasoned (`PROCESS.md` §12.3).** Every claim in this document is **reasoned** — from the cited specification and the structural properties of the cited, already-written design document. No claim asserts any jurisdiction's current legal requirement as a checked fact; the specification's own regime categories (§6 below) are treated as domain-neutral obligation classes, never as a specific regulation, and no specific regime, jurisdiction, or regulation is named anywhere in this document.

It is structured as a pyramid: first the region-scoping mechanism itself, since nothing above it exists to build on (§3); then residency-follows-the-actor as that mechanism's governing rule (§4); then data-classification tiers as the property the mechanism resolves against (§5); then compliance-regime applicability as a further contributor to the same resolution (§6); then the per-region rules the mechanism enforces as a boundary (§7); then the human-approval gate as the mechanism's blocking control for the narrow class of action that approaches a violation (§8); then the evidence the mechanism must produce (§9); then the design decision this document records (§10); then the boundaries this document does not cross (§11), precedence (§12), and the binding rules that close it (§13).

## 2. Scope and What This Document Does Not Own

This document does **not** own, and does not decide:

This document fixes only the requirement each attribute must satisfy and the point at which it is read.
- **The full data-handling matrix built atop the classification tiers this document enforces** — retention, deletion, consent, minimization, and redaction — owned by `07-data-governance-and-privacy-design.md` (not yet written), realizing `02-governance-and-security/06-data-governance-and-privacy.md`, per that specification's own §4 and §8.

## 3. The Region-Scoping Mechanism

### 3.1 What This Section Corrects

`04-security-controls-design.md` §3.3 states that request validation "never becomes a path to observe another tenant, escalate authority, or reach across a region," and its §11 attributes "that scoping remains exclusively `02-tenant-isolation-and-access-control-design.md`'s." `02-tenant-isolation-and-access-control-design.md` names no region mechanism anywhere in its own text, and its §2 hands residency enforcement to this document by name. The word *region* in `04-security-controls-design.md` §3.3/§11 refers to a mechanism this document, not that one, defines. A reader of that document's §3.3/§11 should read "region" there as pointing here.

### 3.2 Extending the Registry Accessor's Return Value, Not Adding a Second Accessor

The Registry Accessor is, per `02-tenant-isolation-and-access-control-design.md` §3.1, the sole read path to `platform.tenants` and `platform.applications`, and already returns the actor's tenant binding, application scope, and resolved schema name. This document requires that same, already-sole read path to additionally return the **region-of-record** the tenant's or application's own registry row carries — an attribute this document requires exist on those rows, storage shape deferred (§2 above) — as one further value in the Registry Accessor's existing return, never as a second query, a second table, or a second accessor function. No component gains a new code path to the registry as a result of this requirement; the one that already exists returns one more field.

The actor's own region-of-record is read from the actor's already-established identity — the same identity `02-tenant-isolation-and-access-control-design.md` §3.1 already accepts as the Registry Accessor's sole input, established upstream by `03-authentication-and-identity-design.md` before the Registry Accessor is ever called. This document consumes that identity's region-of-record; it does not establish identity or design where that attribute lives on it.

### 3.3 The Resolved Residency Obligation

At the same **Context Resolution Point** `02-tenant-isolation-and-access-control-design.md` §4.1 already fixes — the single point, before any handler runs, at which tenant and application context is resolved into the frozen Resolved Request Context — this document requires one further value be resolved, from the same Registry Accessor call and the same already-established identity, and carried alongside that frozen object through the same request-scoped storage mechanism (§4.2 of that document): the **Resolved Residency Obligation**.

The Resolved Residency Obligation is the union of:

- the region-of-record of the acting identity (§4 below governs how this drives the resolution);
- the region-of-record of the tenant or application the request's action targets;
- the classification tier attaching to the data the action would read, write, or transfer, and the residency consequence that tier carries (§5);
- any compliance regime attaching to that data, that actor, or that action (§6).

It is resolved exactly once, at the same point tenant and application context is resolved, and — like the object it accompanies — is frozen at creation: no step downstream of the Context Resolution Point may recompute, widen, or narrow it. This is the same discipline `02-tenant-isolation-and-access-control-design.md` §4.1 applies to its own object, extended here to a second value resolved at the identical point, by the identical mechanism, rather than by a competing one.

### 3.4 The Region Boundary Check

`02-tenant-isolation-and-access-control-design.md` §4.2 and §5.1 fix one function — connection acquisition — as the sole gateway through which a request reaches a scoped database connection, and state that no downstream call is parameterized by anything other than the frozen Resolved Request Context. This document adds **one additional inline check to that same function**, run immediately alongside the connection-scoping role switch it already performs, never as a second gateway a request could reach by a different path: the **Region Boundary Check**.

Before the connection is returned to the caller, the Region Boundary Check evaluates the frozen Resolved Residency Obligation against the action the request is attempting — a read, a write, or a cross-region transfer — and:

- **refuses the request before the connection is ever acquired** if the action would violate any obligation in the union (§7 governs which per-region rule is being evaluated);
- **holds the request for human approval** (§8) rather than outright refusal, where the action matches one of the triggers `02-governance-and-security/05-compliance-and-data-residency.md` §7 names;
- **proceeds** only where every obligation in the resolved union is satisfied.

Because connection acquisition is already, by construction, the only function through which a component reaches a scoped connection (`02-tenant-isolation-and-access-control-design.md` §4.2's own argument, cited and not restated), and because the Region Boundary Check is now inline within that same function, there is no code path by which a request could acquire a connection to data, or perform a transfer of it, without this check having evaluated first. This is the "structurally impossible," not merely "checked and denied," register the tenant-isolation document uses for cross-tenant reach (§8 of that document), applied here at the code-path level.

### 3.5 The Honest Limit This Design States Plainly

The structural claim above is bounded to the platform's own code path: no application-level action reaches data or performs a transfer without the Region Boundary Check having run. It is not a claim about where bytes are physically stored, replicated, or routed at the infrastructure layer — that is `08-multi-region-distribution-design.md`'s topology to design, not yet written, and this document's guarantee is only as strong as that topology's own placement and routing decisions make it. Where the topology places a schema's underlying storage in a way inconsistent with a resolved obligation, no check at this document's own enforcement point can detect or correct it after the fact; this document's contribution is that no *code path this document governs* ever knowingly requests, initiates, or completes an action inconsistent with the resolved obligation, not that physical placement is itself proven correct. `08-multi-region-distribution-design.md` inherits this obligation model as a constraint its topology must satisfy (§11).

## 4. Residency-Follows-the-Actor, Realized

`02-governance-and-security/05-compliance-and-data-residency.md` §3 fixes the rule; this section states what "follows the actor" means at the point a request is served.

- **The acting identity's region-of-record is the primary driver of the Resolved Residency Obligation, never the region the platform's own infrastructure happens to occupy.** §3.2's resolution reads the actor's region-of-record from the already-established identity, never from where the handling process, container, or database instance is physically running for reasons unrelated to that actor. A request served by infrastructure located in one region carries the obligation of the actor's own region regardless.
- **Where the actor's region-of-record and the tenant's or application's region-of-record differ, the Resolved Residency Obligation is their union, not either alone.** §3.3's resolution folds in both region-of-record values; the Region Boundary Check (§3.4) requires every obligation in that union to be satisfied, never only the more permissive one. This is the mechanical form of `02-governance-and-security/05-compliance-and-data-residency.md` §3's cumulative-obligation rule: an actor in one region reaching data whose tenant carries a different region-of-record does not resolve to either region's obligation being dropped.
- **Obligations attach at every point the check runs, not only at rest.** The Region Boundary Check evaluates before a read, before a write, and before a transfer alike — storage, processing, and transfer are each a case of "the action the request is attempting" in §3.4's terms, and disclosure (returning resolved data to the requester) is the read-direction case of the same check, already covered by it; no separate mechanism is designed for disclosure because none is needed.
- **Uncertainty in resolving either region-of-record resolves to refusal.** If the Registry Accessor's extended return (§3.2) cannot establish an actor's or a tenant's region-of-record with confidence, the Resolved Residency Obligation cannot be established, and the Region Boundary Check treats this exactly as it treats an established obligation that would be violated — refusing the action rather than proceeding on an assumed, most-permissive default. This is the deny-by-default rule of `02-governance-and-security/05-compliance-and-data-residency.md` §3's last bullet, applied at this mechanism's own enforcement point.

## 5. Data-Classification Tiers as a Traveling Property

`02-governance-and-security/05-compliance-and-data-residency.md` §4 fixes four tiers, ordered least to most restrictive, and states that each tier's obligation is a floor the tier above only adds to. This section fixes how a tier is realized as a property that travels with data, rather than as a convention a consumer must remember to honor.

- **The tier is intrinsic to the data it classifies, not an attribute a consumer infers.** Every stored data element this document's mechanism governs carries its classification tier as a required property from the point it is created — an application's own `application_key`-scoped or `tenant_key`-scoped write (whichever key hierarchy `04-security-controls-design.md` §7.2 already encrypts it under) is, for this document's purposes, equally a write that must resolve a tier, whether the tier is platform-assigned (for platform-primitive data) or builder-configured (for a built artifact's own data, per the specification's own "for builder-defined data, the builder's own configuration" rule). This document does not design the storage shape of the tier attribute (§2); it fixes that the attribute must exist and must be read at the point the Resolved Residency Obligation is resolved (§3.3).
- **The tier's residency consequence is enforced at the same Region Boundary Check, never by a second mechanism.** The four tiers translate directly into what the Region Boundary Check adds to the resolved obligation:

| Tier | What the Region Boundary Check Adds to the Resolved Obligation |
|---|---|
| Unrestricted | Nothing beyond tenant isolation, which `02-tenant-isolation-and-access-control-design.md` already enforces independently of this mechanism. |
| Tenant-Bound | The actor's and the tenant's region-of-record, per §4 above — no fixed regional restriction beyond where the tenant and its actors actually operate. |
| Jurisdiction-Restricted | A hard regional constraint independent of tenant configuration: the Region Boundary Check refuses any action that would store, process, or transfer this data outside the region(s) the attaching obligation permits, regardless of what the tenant's own configuration requests. |
| Regime-Governed | The full union of obligations from every compliance regime attaching to the data (§6), folded into the resolved obligation exactly as any other cumulative component of it; where more than one regime's obligation differs, the Region Boundary Check enforces the most restrictive, never the union's most permissive member. |

- **An unclassifiable or unrecorded tier resolves to the most restrictive tier, not the least.** Where the tier attribute cannot be read, or cannot be established with confidence, at the point the Resolved Residency Obligation is resolved, the Region Boundary Check treats the data as Regime-Governed until it is explicitly classified — the same deny-by-default discipline `04-security-controls-design.md` §4.2 applies to an ambiguous vulnerability-severity mapping ("classified at the higher of the two classes in contention"), applied here to classification tier. This is the concrete form of `02-governance-and-security/05-compliance-and-data-residency.md` §3's "uncertainty resolves to refusal" rule as it bears on classification specifically.
- **This document does not design the handling matrix built atop the tiers it enforces.** Retention, deletion, consent, minimization, and redaction are `07-data-governance-and-privacy-design.md`'s in full (§2 above); this document's tier enforcement stops at the residency consequence — where data may be stored, processed, or transferred — and does not extend to how long it may be kept or how it must be redacted.

## 6. Compliance-Regime Applicability, as It Bears on the Mechanism

`02-governance-and-security/05-compliance-and-data-residency.md` §5 fixes four regime categories and the rules governing how they attach. This section states what each obligates the mechanism of §3 to do; it does not restate the regimes, name any specific regulation, or determine which regime applies to any given tenant's built artifact — that determination is jointly made by region and by what a builder has built, per the specification's own rule, and this document never makes it on the platform's behalf.

- **A regime that attaches contributes to the resolved obligation, never substitutes for or narrows another.** Whichever regime category attaches to a given action — determined elsewhere, by region and by builder configuration, never presumed here — its obligation is folded into the Resolved Residency Obligation (§3.3) as a further union member, exactly as a classification tier's obligation is (§5 above); the Region Boundary Check does not distinguish a regime-sourced obligation from a tier-sourced or region-of-record-sourced one when enforcing the union.
- **A cross-border transfer regime's condition is evaluated as a transfer-specific case of the same check.** Where the action the Region Boundary Check evaluates is a transfer of Jurisdiction-Restricted or Regime-Governed data from one region to another, the check requires both the originating and the receiving region's obligations to permit it (§7 below) — the mechanical form of the specification's cross-border-transfer-regime category attaching "whenever an action would move Jurisdiction-Restricted or Regime-Governed data across a region boundary."
- **A sector-specific or public-sector regime attaches only through the builder's own configuration or the tenant's own served body, never through a platform assumption.** Where either applies to a given tenant's built artifact, its obligation reaches the resolved obligation through the same builder-configuration path §5 above already states for a tier — an attribute the builder's own configuration supplies, read at resolution time, never a domain the platform infers on the builder's behalf. This preserves the builder/built separation the specification's §5 already states, and this document adds no mechanism that would erode it.
- **A regime adopted or amended after a tenant's obligations were first established is honored on the next resolution, not retroactively disregarded.** Because the Resolved Residency Obligation is resolved fresh at every request (§3.3) rather than cached from an earlier determination, a regime change is honored the moment it is reflected in whatever configuration or region-of-record the resolution reads — this document invents no versioning or grandfathering mechanism, because none is needed: the mechanism already re-resolves on every request.

## 7. Per-Region Residency Rules and Boundary Enforcement

`02-governance-and-security/05-compliance-and-data-residency.md` §6 fixes six per-region rules. This section states each as a constraint the Region Boundary Check enforces, with the deny-by-default discipline already stated in §3–§6 above applied identically here.

- **A region's obligations bind every tenant and actor present in it identically.** The Region Boundary Check draws no distinction by tenant identity when evaluating an obligation sourced from a region-of-record; the same resolved obligation applies to every actor and tenant whose resolution attaches to that region.
- **Storage and processing location follows the attaching obligation, never convenience.** For Jurisdiction-Restricted and Regime-Governed data, the Region Boundary Check's refusal (§3.4) is unconditional on administrative or infrastructure convenience — there is no parameter by which a caller can request that convenience override the resolved obligation, because the check's evaluation does not accept one.
- **The region boundary is its own trust boundary, coexisting with, never substituting for, the tenant boundary.** The Region Boundary Check runs as an additional evaluation alongside — not instead of — the connection-scoping switch `02-tenant-isolation-and-access-control-design.md` §5.1 already performs for tenant isolation; satisfying one never exempts a request from the other, exactly as `02-governance-and-security/02-security-policy.md` §3.2 and `02-governance-and-security/05-compliance-and-data-residency.md` §6 both require.
- **Cross-region transfer requires both regions' permission.** Where the action is a transfer, the Region Boundary Check evaluates the resolved obligation of both the originating and the receiving region before the transfer proceeds; either region's obligation forbidding it is independently sufficient to refuse the transfer, and the classification tier of the data being moved (§5) determines whether the tier itself excludes the transfer regardless of either region's own permission.
- **Obligations bind from the moment the platform begins operating in a region.** Because the Resolved Residency Obligation is resolved fresh at every request from the region-of-record the Registry Accessor's extended return supplies (§3.2), a tenant or built artifact already present in a region at the moment the platform begins operating there is subject to that region's obligation on its very next resolved request — no grace period or exemption is built into the resolution, because none is stated by the specification.
- **Ceasing operation in a region does not retroactively excuse a prior obligation.** Data already classified under a region's obligation (§5) retains that classification, and the tier's residency consequence, independently of whether the platform still operates in that region at the time a later request is resolved; this document's mechanism carries no "region no longer operated in" exception into the tier table of §5, because the specification states none.

## 8. The Human-Approval Gate for a Residency-Violating Action

`02-governance-and-security/05-compliance-and-data-residency.md` §7 fixes six triggers requiring human approval before an action proceeds, distinct from the halt-and-escalate rule for a violation already realized. The six triggers are not uniform in shape — some are proposals to promote platform-layer code or configuration toward Production; the rest are actions performed against already-resident tenant data at runtime. This document realizes the gate at the location each shape already has, rather than inventing one uniform location that would either duplicate an existing gate or leave the runtime case unenforced.

### 8.1 Promotion-Shaped Triggers — Realized at the Existing Production Deploy Gate

Two triggers are, by their own description, changes to the platform that reach Production through the pipeline: **beginning operation in a new region for the first time**, and **a change to how a compliance regime is recognized or honored by the platform**. `04-devops-and-cloud-infra/02-ci-cd-pipeline-spec.md` §6 already fixes that "a residency-relevant promotion carries its own additional gate... in addition to, and never satisfied by, the Production Deploy Gate." This document does not invent a second gate beside that one; it supplies the criteria that gate's own residency clause checks:

- **A promotion is residency-relevant** — triggering that clause — where it would begin the platform's operation in a region not previously covered by a Resolved Residency Obligation this mechanism has already been evaluating, or where it changes the resolution logic, the manifest, or the configuration by which a compliance regime is recognized or honored anywhere in §3–§6 above.
- **The approval is required before the promotion, never after.** Consistent with the pipeline spec's own no-bypass rule (§8 of that document), the residency clause's approval is a precondition of the Production Deploy Gate passing, not a follow-up action taken once the promotion has already completed.
- **This document's contribution stops at the criteria.** How the approval is requested, routed, and recorded at that gate is `05-meta-operations/04-human-in-the-loop-protocol.md`'s, cited by the specification's own §7 closing line and not redesigned here.

### 8.2 Runtime-Action Triggers — Realized as a Held State at the Region Boundary Check

The remaining four triggers are actions against already-resident data, evaluated at request time, not at promotion time: **moving Jurisdiction-Restricted or Regime-Governed data across a region boundary**, **reclassifying data from a more restrictive tier to a less restrictive one**, **changing which region governs a tenant's or actor's data by default**, and **any action where the applicable region obligation or compliance regime cannot be established with confidence**. None of these is a code promotion the pipeline spec's gate could evaluate; each is realized at this document's own enforcement point, the Region Boundary Check (§3.4).

- **The trigger produces a held state, not an outright refusal.** Where the action the Region Boundary Check evaluates matches one of the four triggers above, the check does not resolve to the ordinary refuse/proceed binary of §3.4; it resolves to a third outcome — **held pending approval** — that blocks the action from proceeding exactly as a refusal would, but is distinct from a refusal in that it is releasable by an explicit approval rather than permanently blocked.
- **What is blocked, concretely.** The action does not reach the point it would otherwise reach — the connection is not acquired for the write, the reclassification is not applied, the default-region change is not committed, or (for the fifth trigger) the action that could not be confidently resolved does not proceed — until the hold is released.
- **What releasing the hold requires.** An explicit, recorded approval decision, before the action is permitted to proceed; this document does not design how that decision is requested, routed, or recorded — that is `05-meta-operations/04-human-in-the-loop-protocol.md`'s, exactly as §8.1 states for the promotion-shaped case. This document's own obligation is that the Region Boundary Check produces the held state and does not release it on any basis other than that recorded approval — no timeout, retry, or default resolves a held action to "proceed."
- **The fifth trigger generalizes the deny-by-default rule already stated throughout this document into the approval gate itself.** Where §4's or §5's uncertainty already resolves to refusal for an ordinary request, this fifth trigger resolves the same uncertainty to a hold, not a refusal, specifically for the class of action §7 names as requiring approval before proceeding — extending deny-by-default from "refuse" to "hold for a governed decision" at exactly the point the specification's own §7 fixes it.

### 8.3 Reclassification Requires the Same Check, Regardless of Direction

Reclassifying data from a more restrictive tier to a less restrictive one is a write to the tier attribute itself (§5), and this document requires that write to pass through the same Region Boundary Check as any other action against that data — it is not a metadata update exempt from the mechanism because it changes the classification rather than the data's content. A reclassification in the other direction — toward a more restrictive tier — carries no approval requirement under §7, and this document adds none, consistent with the specification naming only the downward direction as the evasion risk requiring a governed decision.

## 9. Evidence Produced

Each control this document fixes is, at the same time, a place a specific kind of audit evidence must originate — the same pattern `04-security-controls-design.md` §6.1, `05-ai-tooling-security-design.md` §7, and `01-invariant-enforcement-design.md` §6 already establish for their own controls. This document states *that* each row below must be captured and *what* it contains; how it is captured, stored immutably, and made tamper-evident is `08-audit-and-traceability-design.md`'s in full (not yet written), inheriting this list exactly as it inherits the lists those three documents already hand it.

| This document's control (§ above) | The evidence it must produce |
|---|---|
| §3.4 Region Boundary Check — refusal | A record of every refused action: which obligation in the resolved union was violated, and the action's location (read, write, or transfer) — never the data content itself. |
| §3.4 Region Boundary Check — cross-region transfer | A record of every evaluated transfer: the originating and receiving region, the classification tier of the data moved, and whether both regions' obligations permitted it. |
| §5 Classification-tier resolution | A record of every action where the tier could not be established with confidence and was resolved to Regime-Governed by default. |
| §8.1 Production Deploy Gate residency clause | A record of every promotion flagged residency-relevant under this document's criteria, and the approval decision that released or blocked it. |
| §8.2 Region Boundary Check — held state | A record of every action held under one of the four runtime triggers, the trigger that produced the hold, and the approval decision (and its author) that released it. |
| §8.3 Downward reclassification | A record of every tier reclassification from a more restrictive tier to a less restrictive one, and the approval decision that authorized it. |

This is a fixed input list `08-audit-and-traceability-design.md` inherits and designs its capture and storage mechanism around; this document does not design that mechanism.

## 10. Design Decision Records

### 10.1 ADR-023 — Region-Scoping and Residency-Obligation Enforcement, and the Split Location of the Residency-Approval Gate

- **Status:** Approved (`DECISIONS.md` D-47, 2026-08-18).
- **Cost to reverse:** **Very high.** The mechanism this decision fixes is the enforcement point every subsequent residency-consequential read, write, or transfer of tenant and application data depends on; by the time the mechanism has been operating, tenant data has already been created, written, and possibly transferred under whatever resolution and enforcement behavior was in place. Reversing or materially weakening the mechanism does not merely change code — it requires re-establishing, for every already-resident data element, whether its actual physical residence and every action already taken against it were consistent with the obligation the corrected mechanism would have enforced, and correcting what cannot be undone (a transfer already completed) is not always possible by re-running code. This is graded at the same rung `implementation-document-map.md` already assigns this document, and is stated honestly at that grade rather than understated to make the decision look cheaper than it is.
- **Upstream decisions assumed:** `02-tenant-isolation-and-access-control-design.md` §3–§5 (the Registry Accessor, Context Resolution Point, and connection-acquisition function this mechanism extends rather than duplicates) and its own §2 (the explicit handover of residency enforcement to this document); `04-devops-and-cloud-infra/02-ci-cd-pipeline-spec.md` §6 (the residency-relevant-promotion clause at the Production Deploy Gate this decision realizes rather than duplicates); `04-security-controls-design.md` §7.2 (the key hierarchy this document's classification-tier enforcement composes with, cited, not re-derived). ADR-021 (KMS selection) and ADR-022 (provenance enforcement point) remain Provisional and are not assumed settled; this decision depends on neither.
- **Verified vs. reasoned:** Reasoned throughout. The argument is structural — reuse of an existing enforcement point over a new one, and a split gate location matched to trigger shape rather than a single uniform location — and makes no claim about any specific jurisdiction's current legal requirement, any specific regime, or any provider's or region's current infrastructure offering.
- **Question this answers:** Given that no upstream design document defines a region-scoping mechanism, and given the tenant-isolation mechanism's already-fixed Registry Accessor, Context Resolution Point, and connection-acquisition function, what concrete mechanism resolves a request's residency obligation once, carries it through execution, and enforces it as a boundary a request cannot cross by construction — composing with tenant scoping rather than duplicating it — and, given that a residency-relevant Production promotion already has a fixed gate at the CI/CD pipeline's §6 clause, where does the human-approval gate for the specification's other, runtime-shaped triggers concretely sit?
- **Criteria applied, and how each resolved:**
  1. *Reuse of an existing resolution and enforcement point over a new one.* Extending the Registry Accessor's return value and adding one inline check to the existing connection-acquisition function avoids building a second accessor, a second resolution point, or a second scoping path — exactly the discipline the ticket instructing this document's own work requires, and the same discipline `02-tenant-isolation-and-access-control-design.md` §5.3 applied when it added one import-boundary rule to an existing tool rather than building a second one. Decisive.
  2. *Structural evaluation before the action, not a predicate a caller could bypass.* The Region Boundary Check runs inline within the sole gateway to a scoped connection, before the connection is returned — mirroring the argument `02-tenant-isolation-and-access-control-design.md` §5.1 makes against a trusted predicate for tenant isolation, applied here to residency. Decisive; the alternative (a post-hoc audit of completed actions) would be detection, not prevention, and the specification's own register requires the latter.
  3. *Matching the approval gate's location to trigger shape, rather than forcing one uniform location.* Two of the specification's six triggers are promotion-shaped and already have a fixed gate (`04-devops-and-cloud-infra/02-ci-cd-pipeline-spec.md` §6); the other four are runtime actions against already-resident data that no promotion gate could evaluate, because no promotion occurs. Decisive: a single uniform gate location would either duplicate the pipeline spec's already-fixed clause (for the two promotion-shaped triggers) or leave the four runtime triggers with no enforcement location at all.
- **Context:** `04-security-controls-design.md` §3.3 and §11 attribute region scoping to `02-tenant-isolation-and-access-control-design.md` without that document ever claiming it; that document's own §2 hands residency enforcement here by name. This decision is the first design act discharging that handover, and closes the over-attribution by building the mechanism the handover anticipated rather than by editing either upstream document.
- **Decision:** (1) The Registry Accessor's existing, sole read path to the platform registry is extended to also return each tenant's and application's region-of-record, as one further value in its existing return — no second accessor is created (§3.2). (2) At the existing Context Resolution Point, a second frozen value — the Resolved Residency Obligation, the union of the actor's region-of-record, the target's region-of-record, the attaching classification tier's consequence, and any attaching compliance regime's obligation — is resolved alongside the Resolved Request Context and carried through the same request-scoped storage mechanism (§3.3). (3) The existing connection-acquisition function gains one inline check, the Region Boundary Check, evaluated immediately alongside its existing connection-scoping role switch, resolving to refuse, hold-for-approval, or proceed (§3.4). (4) The human-approval gate of the specification's §7 is realized at two locations matched to trigger shape: the two promotion-shaped triggers realize the already-fixed Production Deploy Gate residency clause, this document supplying its criteria (§8.1); the four runtime-action triggers realize a held state at the Region Boundary Check itself, releasable only by a recorded approval (§8.2).
- **Alternatives considered:** *A dedicated region registry or a per-region database role, mirroring tenant-isolation's per-schema role* — rejected: regions in this project are not established as a fixed physical-partition primitive by any upstream document, and binding this document's enforcement to a specific infrastructure shape would presume `08-multi-region-distribution-design.md`'s not-yet-made topology decision; the obligation-set model is topology-agnostic and composes with whatever shape that document later fixes, rather than constraining it in advance. *A single, uniform approval-gate location for all six §7 triggers* — rejected under criterion 3, as shown above. *A second, parallel approval gate independent of the Production Deploy Gate for the two promotion-shaped triggers* — rejected: the pipeline spec's §6 clause already exists and already states "in addition to, and never satisfied by" language anticipating exactly this document's realization of it; a second gate would duplicate a chokepoint the specification already fixed for this precise purpose.
- **Consequences:** Binds `08-multi-region-distribution-design.md` to design region topology and routing consistent with, and never weakening, the obligation model and the Region Boundary Check fixed here — that document inherits this mechanism as a constraint its topology must satisfy, not a decision it may revisit. Binds `02-platform-data-model-design.md` and `02-data-model-and-entity-design.md` (whichever settles it first) to supply the region-of-record and classification-tier attributes in a form the Registry Accessor and the Region Boundary Check can read at resolution time. Binds `04-devops-and-cloud-infra/02-ci-cd-pipeline-spec.md`'s Production Deploy Gate residency clause to consume the criteria fixed in §8.1, without this document redesigning that gate's own mechanics. Binds `05-meta-operations/04-human-in-the-loop-protocol.md` to design the routing, recording, and resolution mechanics for both the promotion-time and the runtime-held approval. Binds `08-audit-and-traceability-design.md` to the six-row evidence list of §9. Does not alter `02-tenant-isolation-and-access-control-design.md`'s own Registry Accessor, Context Resolution Point, or connection-scoping mechanics beyond the single extension and single inline check named above.

## 13. Binding Rules

These rules hold for every element of this document and are subordinate to the specification and the charter.

- **This document owns the region-scoping mechanism.** No upstream design document defines one; `04-security-controls-design.md` §3.3/§11's attribution of region scoping elsewhere is corrected, not restated, by this document (§3.1, §11).
- **Region scoping composes with tenant scoping and never duplicates it.** The Registry Accessor's existing return value and the existing connection-acquisition function are each extended by exactly one addition; no second accessor, resolution point, or scoping path is created (§3.2–§3.4).
- **Every request resolves a Resolved Residency Obligation exactly once, frozen alongside the Resolved Request Context, at the same Context Resolution Point.** No subsequent step may recompute, widen, or narrow it (§3.3).
- **The Region Boundary Check runs inline within the sole gateway to a scoped connection, before the connection is acquired.** No code path reaches a scoped connection, or completes a transfer, without this check having evaluated first (§3.4); its guarantee is bounded to the platform's own code path and does not by itself prove physical data placement (§3.5).
- **Residency follows the actor.** The acting identity's region-of-record drives the resolved obligation; where it differs from the tenant's or application's own region-of-record, the obligation is their union, never either alone (§4).
- **Classification is intrinsic and travels with the data it classifies.** An unclassifiable or unrecorded tier resolves to the most restrictive tier, never the least (§5).
- **A compliance regime only adds to the resolved obligation.** No regime narrows another, and none is presumed by the platform on a builder's behalf (§6).
- **A per-region rule is enforced as a constraint the Region Boundary Check applies, never as a convention a consumer must remember.** Cross-region transfer requires both regions' permission, evaluated at the same check (§7).
- **The human-approval gate is realized at the location its trigger's shape requires, never duplicated or invented beside an existing one.** Promotion-shaped triggers realize the existing Production Deploy Gate residency clause; runtime-action triggers realize a held state at the Region Boundary Check, releasable only by a recorded approval (§8).
- **Every control this document fixes produces the evidence record §9 names**, as a fixed input `08-audit-and-traceability-design.md` designs storage and tamper-evidence around.
- **No specific jurisdiction, regime, or regulation is named anywhere in this document**, and no time-sensitive legal claim is asserted as verified (§1, §6).
- **This document records exactly one ADR.** ADR-023 (§10) is the genuine, independent decision this document makes; every other design choice above realizes a location, structure, or boundary the cited specification and the cited upstream design documents already fix.
