# Authentication and Identity Design — AI ahaMatic

This document designs the concrete mechanism by which an actor's identity is authenticated, carried through a session, and handed to every downstream access decision the platform makes. It realizes `02-governance-and-security/04-auth-and-identity-spec.md` in full: the supported authentication methods, the session lifecycle and expiry mechanism, the step-up-authentication mechanism, the account-recovery mechanism's guardrails, and the structural closure of that specification's forbidden weakenings. It states **how** identity is established and carried forward; it does not re-decide what must hold — the specification's rules, and the two session-duration ceilings `03-software-and-architecture/06-non-functional-requirements.md` §10 fixes, are cited throughout, never restated or re-derived.

This is a Design-phase artifact closing the one named gap `02-tenant-isolation-and-access-control-design.md` states twice (§2, §11): that document "consumes an already-authenticated actor identity... it does not establish one." Its Registry Accessor (§3.1) and Context Resolution Point (§4.1) both take that identity as a precondition this document supplies. This document does not design the Registry Accessor, the Context Resolution Point, tenant isolation, or the role-and-permission matrix — each is already fixed and cited, never restated; this document's output is shaped to fit exactly what those mechanisms already consume.

---

## 1. Purpose and Reading Order

The document answers six questions, in pyramid order:

- **How is an actor authenticated at every entry point**, across all five actor classes the platform now recognizes.
- **How does an identity holding no credential, no enrolled factor, and no provider link obtain its first one**, and what keeps that path from becoming a way around every rule below it.
- **How does a session carry that identity forward in time**, and how is it issued, refreshed, and expired.
- **What concrete object arrives at the Context Resolution Point**, and how it gets there.
- **When does a session demand stronger verification mid-flight**, and how is that demand enforced.
- **What must account recovery never be able to do**, and how the mechanism holds that line structurally.

It is structured accordingly: authentication methods across every entry point and the first-credential establishment path that makes them reachable for a brand-new identity, then the session lifecycle and expiry mechanism that carries an authenticated identity forward, then the precise handoff of that identity to tenant isolation, then step-up authentication, then account-recovery guardrails, then any design-decision record this ticket warrants, then boundaries and handovers, then precedence, then binding rules.

## 2. Scope and What This Document Does Not Own

This document owns: the mechanism that establishes an actor's identity through multi-factor, single-sign-on, and federated/social authentication, the distinct non-interactive mechanism the platform's grant-bound actor classes use instead, and the first-credential establishment path by which an identity holding none of them obtains its first factor (§3, including §3.4); the session-issuance, -carriage, -refresh, and -expiry mechanism honoring the ceilings `06-non-functional-requirements.md` §10 fixes (§4); the concrete shape of the Authenticated Actor Identity object and how it reaches the Context Resolution Point `02-tenant-isolation-and-access-control-design.md` §4.1 already fixes (§5); the step-up-authentication mechanism and trigger set (§6); and the account-recovery mechanism's structural guardrails (§7).

This document does **not** own, and does not decide:

- **Tenant isolation, the Registry Accessor, the Context Resolution Point, connection-scoping, or the role-and-permission matrix's enforcement mechanics** (`02-tenant-isolation-and-access-control-design.md` §3–§8) — already fixed; this document supplies that document's sole external input and does not redesign anything downstream of it.
- **Who may do what once identity is established** — the role-and-permission matrix itself (`02-governance-and-security/03-access-control-and-tenancy-model.md` §5) and the least-privilege enforcement across the five actor classes (`02-tenant-isolation-and-access-control-design.md` §6) — authorization is a separate, subsequent determination this document's output feeds, never makes.
- **The numeric session-duration ceilings** — fixed at ≤ 30 minutes idle, ≤ 12 hours absolute, by `06-non-functional-requirements.md` §10; this document designs the mechanism that honors them, never a different value.
- **INV-01/INV-02's check location, blocking behavior, or evidence emission** (`01-invariant-enforcement-design.md` §5.1, §8) — already fixed; this document supplies the identity and session mechanics that check depends on, never a second check location.
- **The personas themselves, their hierarchy, or the three-way boundary among the AI-related actors** (`01-business-and-ux/04-personas-and-roles.md` §2.2, §5) — cited, never re-derived.
- **The autonomous platform-operating agent's preconditions, permitted actions, or halt-and-escalate duty** (`05-meta-operations/01-agent-operating-charter.md` §5–§8) — this document designs only how that agent's identity is authenticated and carried in a session; what the agent may then do is that charter's, entirely.
- **Secrets handling, credential-storage cryptographic primitives as a security posture, and the mandatory security-review trigger list** (`02-governance-and-security/02-security-policy.md` §4–§5, §7) — cited, never restated.
- **The outbound channel, medium, or interface through which anything this document's mechanism issues actually reaches a person** — including the enrollment grant §3.4 depends on. `BACKLOG.md` §1ar records that the platform's human-delivery obligation is specified (`05-meta-operations/04-human-in-the-loop-protocol.md` §6) while no design document yet fixes a mechanism; §3.4 names that dependency, states the one property the channel must satisfy, and designs no part of it.
- **A specific recovery-flow user experience** — a builder-facing or platform-UI concern outside this document's "how the mechanism holds" scope; this document designs only the guardrails the mechanism must never violate, not a screen flow.
- **The physical registry, bridge record, or role-binding tables `02-platform-data-model-design.md` §3–§4 already fixes** — cited, never restated; this document adds only the credential, enrollment, provider-link, and session structures that document explicitly defers to it (§3.1: "authentication mechanics — credentials, sessions, MFA — are `03-authentication-and-identity-design.md`'s").

## 3. Authentication Across Every Entry Point

The platform provides authentication as a domain-neutral primitive (C-02) at every entry point: the builder UI, the mobile-delivery runtime (C-20), every built application's own end-user surface, and the platform's own published programmatic contract (C-12, including its generated MCP surface, ADR-013). Every entry point routes through the same mechanism this section fixes — no entry point runs a second, parallel authentication path.

The five actor classes split into two groups by how they present themselves at that mechanism.

### 3.1 Interactive, Human-Verified Actors: Builder Personas and End Users

Builder personas (tenant owner, access administrator, application builder, operator, publisher, and the extender's own human operator managing its extension) and end-user personas (authenticated end user, public consumer, end-user administrator) authenticate interactively, through the three method families `04-auth-and-identity-spec.md` §4 fixes:

| Method Family | Mechanism This Document Designs |
|---|---|
| Multi-factor authentication | A first factor (a stored, salted-and-hashed password credential, or a registered WebAuthn public-key credential) combined with an independent second factor (a WebAuthn credential or a TOTP code), verified in sequence before an identity is established at MFA assurance. Credential material is stored only as a salted hash or a public-key reference — never in a recoverable form — under the platform's own secrets-handling posture (`02-governance-and-security/02-security-policy.md`, cited, not restated). |
| Single sign-on | An OIDC or SAML assertion, consumed from an identity provider a tenant has configured as trusted for its own builder personas or an application has configured as trusted for its own end users, mapped to a `platform.platform_users` (or the application's own end-user identity, `02-data-model-and-entity-design.md`'s) record via a stored provider-link, never by absorbing the provider's own identity store into the platform core (`04-auth-and-identity-spec.md` §4's platform obligation). |
| Federated / social authentication | The same OIDC-consumption mechanism as SSO, distinguished only by the identity provider being one an individual end user, rather than a tenant, has chosen to trust — never a platform-presumed or mandatory provider. |

**Which method or methods apply to which tenant, application, or role is builder-defined configuration, not a decision this document makes.** This section designs the primitives the platform makes available; a tenant's or builder's choice to require MFA, enable one SSO provider, or offer social login is configuration read by the mechanism below, never a platform assumption (`04-auth-and-identity-spec.md` §4).

A **public consumer** role, where a builder designates content or actions as ungated, is recognized by this mechanism establishing no identity at all — there is no governed action for that content to gate, so INV-02's "identity precedes every governed action" has nothing to precede. The moment a public consumer's request reaches a governed action (a write, a scoped read, an action a builder has configured to require identity), the same mechanism as any other end-user request applies, and an unestablished identity carries no standing (`04-auth-and-identity-spec.md` §3).

### 3.2 Non-Interactive, Grant-Bound Actors: Extender Runtime, Autonomous Agent, External Contract Consumer

Three actor classes do not sign in interactively at all, because none of them is a human presenting a factor at a screen. Each instead presents a credential that attests to an already-issued grant, and the mechanism verifies that credential rather than a password, a WebAuthn ceremony, or an SSO redirect.

| Actor Class | What Authenticates, Concretely | Why MFA/SSO/Federated Do Not Apply |
|---|---|---|
| **Extender, at runtime** (the running extension instance, distinct from its human operator, who authenticates per §3.1) | An OAuth2 client-credentials assertion: a client identifier and a signed secret or private-key-signed JWT, issued when the extension's grant (`tenant_<id>.tenant_users`, scoped per `02-tenant-isolation-and-access-control-design.md` §6) is configured, presented on each call to the Extension component's stable contract. | The extension is a running process, not a person; it has no factor to present interactively. Its credential attests to the tenant's own configuration decision to grant it a scope, exactly as `04-auth-and-identity-spec.md` §4's "auth methods are platform primitives; their application is builder-defined" already frames for the interactive families. |
| **Autonomous platform-operating agent** (`05-meta-operations/01-agent-operating-charter.md`) | A platform-issued service credential (a signed JWT bound to the agent's own `platform.platform_users` record and its `platform.steward_role_bindings` row), presented identically to any other steward-role credential at the point the agent enters the platform's own request path. This document designs only that the agent authenticates via this credential and is carried in a session exactly as any steward-bound identity is; **what the agent may then do — its preconditions, permitted actions, and halt-and-escalate duty — is `01-agent-operating-charter.md`'s, entirely, and is not restated here.** | The agent "operates the platform's own lifecycle — a role entirely internal to the platform" (`01-business-and-ux/04-personas-and-roles.md` §2.2); it is not a human establishing confidence through independent factors, and it holds no external identity provider to federate against. |
| **External contract consumer** (T70) | The same OAuth2 client-credentials mechanism as the extender runtime: a client identifier and signed secret or JWT assertion, issued when the tenant creates the client grant `02-governance-and-security/03-access-control-and-tenancy-model.md` §6 defines ("the scoping identity of an external caller... authorized to act against platform capabilities on a tenant's behalf"). | The external contract consumer "neither operates the platform nor assists a builder from within it" and "holds no more standing than any other client of that contract" (`01-business-and-ux/04-personas-and-roles.md` §2.2) — it is a caller of a published contract, not a party a tenant onboards through an interactive sign-in flow. |

**No exemption for autonomy or externality.** Each of these three credentials is verified by the same mechanism, produces the same shape of Authenticated Actor Identity (§5), and is carried in the same kind of session record (§4) as any interactive actor's — the distinction in this section is only in *what is presented*, never in whether it is checked, how strongly, or against a weaker standard. This matches `02-tenant-isolation-and-access-control-design.md` §6's finding that "the mechanism does not distinguish a human-directed external caller from an autonomous one; both are bound by the same issued grant, checked the same way" — extended here to the point of authentication itself, one step upstream of that document's own mechanism.

### 3.3 Assurance Levels

Authentication methods establish different strengths of confidence (`04-auth-and-identity-spec.md` §3). This document fixes three assurance levels, ordered low to high, recorded on every session (§4.2):

| Assurance Level | Established By |
|---|---|
| `single-factor` | One interactive factor alone (password or SSO/federated assertion with no second factor), or a non-interactive credential presented without an additional attestation. |
| `mfa-verified` | Two independent interactive factors, per §3.1's MFA row. |
| `service-credential` | A non-interactive, grant-bound credential per §3.2, cryptographically signed and verified against the issuing tenant's own grant record. |

A method establishes a level; whether that level suffices for a specific action is never decided by the method alone — it is decided by the step-up mechanism (§6), which may demand a higher level than the one a session currently holds.

### 3.4 First-Credential Establishment: How an Identity Holding No Factor Obtains Its First One

**The gap this subsection closes, confirmed directly rather than inherited.** `02-tenant-isolation-and-access-control-design.md` §11 names it and `BACKLOG.md` §1at records it, but each is one prior session's finding; the claim was re-verified against this document in full before anything was designed against it. §4.1 fixes the three structures a factor is stored in and every column each carries. §3.1–§3.3 fix the methods that *read* those rows and the assurance each read establishes. §4.3's "Establishment" is a *session's* establishment, conditioned on §3's verification having already succeeded against a row that exists. §6.1's first trigger fires in front of a **change** to an authentication basis that is already there. §7's recovery mechanism requires "channels the identity previously enrolled." No mechanism anywhere in this document writes the *first* row into any of the three structures for an identity holding none — the gap is real, and this subsection is that write path. It adds no table, no column, and no assurance level.

**The obligation's source, which is not this document's own specification.** `04-auth-and-identity-spec.md` carries no enrollment or first-credential section at all; the obligation is assigned from outside it, by `02-governance-and-security/03-access-control-and-tenancy-model.md` §4, whose closing sentence reads: "How the tenant owner first authenticates against that identity record — the credential, invite, or sign-in mechanism — is not this document's concern; it belongs to the authentication and identity design." This subsection realizes exactly that assignment and nothing wider. In particular it designs no signup, registration, onboarding, or qualification step: that same section's own thinness bullets already exclude them — "No self-service signup, public registration flow, or business/legal qualification process is modeled in this library" — and "Admission requires no criteria beyond the steward's own existing authority" (`DECISIONS.md` D-56, D-60, cited and not restated).

**The trigger is a state, not an act — and that is a design choice, not a description.** The mechanism below fires against the **zero-factor state**: a `platform.platform_users` row holding no non-revoked row in `platform.credentials`, in `platform.mfa_enrollments`, or in `platform.identity_provider_links`. Binding the mechanism to a state rather than to a named triggering act means it remains correct for every act that later produces that state, without any such act having to know this mechanism exists. Two consequences follow, and the second is a finding this subsection states rather than absorbs.

- **Owner admission is a caller, never the mechanism.** `02-tenant-isolation-and-access-control-design.md` §6.3 creates exactly one identity in the zero-factor state per admitted tenant, with credential issuance excluded from its own act by its own words — "It does not design credential issuance — password, invite, or federated sign-in — which remains `03-authentication-and-identity-design.md`'s in full." That act is the one designed producer of the zero-factor state in the library today, and it reaches this mechanism as a caller of it (below), never by writing a factor itself.
- **Builder admission is not a second caller, and checking that surfaced a further gap.** `02-tenant-isolation-and-access-control-design.md` §6.1's identity precondition is a foreign key to `platform.platform_users` that is, in that section's own words, "populated only once `03-authentication-and-identity-design.md`'s mechanism has established that identity." Builder admission therefore *presupposes* an established identity; it does not create one in the zero-factor state, and it is not a trigger of this mechanism. **What that resolution exposes is that no mechanism in the library writes the `platform.platform_users` anchor for a person being admitted under §6.1 at all** — §6.3 supplies the anchor for the owner case only. Anchor writes are `02-tenant-isolation-and-access-control-design.md`'s (that is where both the owner-case anchor write and the foreign-key precondition live), so this is a gap in that document, named here rather than absorbed into this one, which owns credential mechanics and not anchor creation. Nothing in this subsection depends on its closure: this mechanism reads the zero-factor state off whatever anchor exists, and is indifferent to which act wrote it.

**Where the write runs, over which connection, and in which transaction.** The write executes inside the same structural position the Authentication Gate already holds (§5.2), as one additional mandatory step of `components/isolation-and-trust`, the module `03-architecture-realization-design.md` §3.1 already assigns "Identity resolution, authentication-state handling, authorization decisioning, and the tenant-boundary primitives every other module assumes already hold" — the **Enrollment Gate**. It is not a second entry path into that module and not a parallel authentication path: an enrollment attempt reaches the same code the Gate reaches, is refused by the same deny-by-default posture, and produces no Authenticated Actor Identity object and no `platform.sessions` row. The connection is the platform-global one the Gate already writes `platform.sessions` over on every establishment (§4.3) — the three target tables and `platform.sessions` are all platform-global structures the Gate already holds write privilege on, so no administrative or provisioning connection is required here. This is the natural point of contrast with `02-tenant-isolation-and-access-control-design.md` §6.3, which had to reach for provisioning's own administrative connection precisely because its write targets a `tenant_<id>` schema no steward holds a grant on; nothing in this subsection writes into a tenant schema, so that reach is not needed and is not made. Every row the mechanism writes for one identity — a `platform.credentials` row, and a `platform.mfa_enrollments` or `platform.identity_provider_links` row where the identity's configured method requires one — **commits in a single transaction**, so no state exists in which an identity holds a partial factor set. Two properties depend on that atomicity and are stated where they are used, below.

**The authority the write requires is not any actor's session.** The identity being enrolled cannot authenticate, so it holds no session and no assurance level; and no other actor's session authorizes the write either. The write's sole authority is the artifact or assertion verified at the Enrollment Gate in the same synchronous step — a redeemed enrollment grant, or a verified provider assertion. There is no code path by which a session, a role, or a grant held by any *third* actor authorizes a first-factor write against another identity's anchor. This is what keeps the mechanism clear of the steward boundary `02-governance-and-security/03-access-control-and-tenancy-model.md` §4 fixes for the Tenant admission role — "Cannot act as, or in place of, a tenant owner once a tenant is admitted" — a boundary a mechanism in this shape can breach very easily, and the next paragraph states the one candidate design that would have.

**Two constructible paths, and one rejected outright.**

| Path | Mechanism | When It Is Constructible |
|---|---|---|
| **A — Enrollment grant** | A single-purpose, short-lived, signed artifact naming exactly one `platform_user_id`, issued by the same authority whose own admission act created that anchor, delivered to the person it names, and redeemed once at the Enrollment Gate to write that identity's own first factor set. Confers no identity, no session, and no standing on any governed action. | Always — it depends on no prior tenant configuration. Its one dependency is an outbound channel that can reach a person, which the platform does not yet have (below). |
| **B — Provider-link-first** | Where the identity's tenant has already configured a trusted identity provider (§3.1), the first factor *is* that provider's assertion: a successful, signature-verified assertion whose external subject matches the identity attribute the anchor already carries writes the identity's first `platform.identity_provider_links` row, and the same request then proceeds through §3.1's ordinary SSO path. No secret is issued and nothing has to reach the person out of band. | Only where a trusted provider is already configured for that tenant — which is never true for a brand-new tenant's first owner, for the structural reason below. |
| **Rejected — steward-mediated handoff** | The issuing authority is given a usable first factor for the identity and passes it to the person directly. | Never. It is not a weaker option to be traded off; it is foreclosed. An authority holding a usable factor for the tenant owner's identity *can* authenticate as that owner, which is precisely the act `02-governance-and-security/03-access-control-and-tenancy-model.md` §4's Tenant-admission boundary forbids. No expiry, single-use property, or policy statement removes the capability once the secret has been in the issuer's hands. |

**Path B rests on no new trust, and adds no new configuration surface.** The provider whose assertion establishes the link is one the tenant itself designated trusted under §3.1's already-fixed rule — "an identity provider a tenant has configured as trusted for its own builder personas" — and the match is against an identity attribute `platform.platform_users` already carries (`02-platform-data-model-design.md` §3.1). The subject-match is **checked, not structural**, and is stated as such: the platform verifies the assertion cryptographically, but that the asserted subject is the intended person rests on the tenant's own provider trust, exactly as it already does for every subsequent SSO sign-in that same link serves. Path B adds no trust that §3.1 had not already placed; what it adds is the one row that placement was missing.

**Path B is not constructible for the case that made this gap load-bearing, and that is a structural fact, not a scheduling one.** The identity `02-tenant-isolation-and-access-control-design.md` §6.3 creates is the first owner of a tenant admitted moments earlier. That tenant has no configured provider, because provider trust is the tenant's own configuration (§3.1) and no actor holds tenant-owner authority in it yet to make that configuration. A steward configuring one on the tenant's behalf is the same forbidden act as the rejected handoff above, reached by a different route. So Path B covers a builder joining an already-configured tenant — once that document's anchor gap above is closed — and it does not cover the first owner of any tenant the platform will ever admit. **That case depends on Path A, and therefore on delivery.**

**Path A's grant carries no new storage, and its single-use property is enforced by the state it changes rather than by a consumption record.** The grant is a signed artifact — the same signing capability §4.2 already relies on for the "signed, short-lived session token" the caller carries — naming one `platform_user_id`, an issuance time, a short expiry, and a nonce. The Enrollment Gate verifies three things in one synchronous step: the signature, the expiry, and that the named identity is *currently* in the zero-factor state. Redemption writes the identity's full configured factor set in one transaction, which flips that third condition; every replay of the same artifact thereafter fails it. No stored grant record is needed for replay prevention, because the enrollment the grant authorizes is itself the record that the grant has been used. This matters beyond economy: a stored grant row placed in `platform.credentials` — the only one of the three structures whose columns could carry it without a new table — would be a non-revoked credential row, which would take the identity *out* of the zero-factor state before it holds any real factor, and would thereby open §7's recovery path to an identity that has enrolled nothing. That is a forbidden weakening reached by a storage choice, and it is the reason the grant is stateless rather than stored.

**What the stateless grant does not buy, stated plainly.** An outstanding grant cannot be revoked before its own expiry, because there is no record to revoke — reissuing after a lost delivery leaves the earlier artifact live until it expires, and several may be live at once. All of them can do exactly one thing, and the first success voids every one; the mitigation is therefore a short expiry, and the mechanism claims nothing stronger. Where a grant is redeemed by someone other than the person it names, the exposure is the first-factor takeover of an identity that has never been used — for a first tenant owner, that is tenant-owner authority, and this design does not minimize that. Two properties bound it: the grant reaches no governed action of its own, and the compromise is **detectable at the point it matters**, because the legitimate holder's own redemption then fails the zero-factor condition rather than silently succeeding alongside it. The repair is an authorized revocation of the enrolled factor set, which returns the identity to the zero-factor state and reopens this path. **Which authority holds that revocation over another identity's factors is not decided here** — it is the role-and-permission matrix's (`02-governance-and-security/03-access-control-and-tenancy-model.md` §4–§5), and asserting it from a design document would be inventing a matrix entry. Nothing is left unusable in the interim: §4.4's existing "Tenant, application, or account removal" trigger already makes disabling the affected `platform.platform_users` account terminate every session it holds, which is the containment step, and it is already designed.

**Path A's one dependency is a delivery mechanism the platform does not have, named here and not designed here.** The grant must reach the person it names over a channel the issuing authority does not itself read — that property, not any particular medium, is what keeps Path A clear of the rejected handoff above. The platform has an obligation of this shape specified and no mechanism realizing it: `05-meta-operations/04-human-in-the-loop-protocol.md` §6 fixes that "The platform makes every routed request reach the human it names, through some means sufficient for them to learn of it," and states in the same breath that "it does not fix the channel, interface, or tool through which it is carried out"; `03-human-in-the-loop-design.md` §2 records the design-side absence, and `BACKLOG.md` §1ar records that the obligation is now specified while the mechanism remains open. **Two precisions this subsection owes rather than glosses.** First, that obligation's subject is an approval request routed to a human holding decision authority — not an enrollment artifact delivered to a person who holds no authority yet and cannot authenticate — so what Path A depends on is the *channel* a future design ticket picks, not the obligation itself, which does not reach this case. Second, the consequence is stated without softening: the write path designed here is complete and correct, and it is **inert for the first owner of every tenant the platform admits** until that channel exists. This subsection does not design it, name a medium, or state a timeliness figure — each belongs to the document that will own the channel, and choosing one here would be this document deciding another's mechanism.

**Step-up (§6.1) is structurally inapplicable to a first factor, and is not weakened to accommodate that.** §6.1's first trigger requires "a fresh, synchronous verification at `mfa-verified` assurance (or the identity's current maximum, whichever is higher)" before a write to `platform.credentials` or `platform.mfa_enrollments` proceeds. For an identity in the zero-factor state that requirement has no referent: there is no prior factor to re-verify and no current maximum to meet, so the gate cannot be satisfied — not because the standard is relaxed here, but because the material the standard operates on does not exist yet. **§6.1's trigger set is unchanged, and none of its five triggers is narrowed, re-worded, or given an exception.** Trigger 1 continues to apply in full to every subsequent change this identity ever makes to its authentication basis, including the second one — the first credential is the only write in the identity's life that this gate has nothing to check.

What replaces it is an assurance argument of the same shape, applied to the only material available. The grant's verification is fresh (the artifact is verified at the moment of the write, never earlier), synchronous (the write does not proceed until it succeeds), and specific to the one action it authorizes (it confers nothing else, and no earlier verification can be read to satisfy it) — the three properties §6.2 already demands of every step-up verification, restated against a grant instead of a factor — plus one §6.2 has no need to state, because a factor is not consumed by being used: the grant is self-voiding, since the state its redemption changes is its own use record. It is honestly weaker in exactly one respect, and the weakness is inherent rather than chosen: it rests on **one** independent channel, because an identity holding no factor has nothing for a second one to be independent of. That single-channel assurance is precisely why the grant's reach is bounded to one write and no standing: the mechanism does not raise its assurance, so it bounds what that assurance can reach.

**The boundary against recovery (§7), stated because the two are adjacent and a mechanism blurring them would be a forbidden weakening.** Both paths are decided by the same read of the same three structures, and they are mutually exclusive on it:

- **This subsection's path requires the zero-factor state** — no non-revoked row in any of the three. It is checked at grant issuance *and* re-checked at redemption, two checks rather than one, because the state can change between them and the redemption-time check is the one that is load-bearing.
- **§7's recovery path requires the opposite** — at least one previously enrolled channel, and in fact two independent ones. The dangerous direction, an un-enrolled identity reaching recovery, is already closed by §7's own words and needs no new rule here: "Where an identity has enrolled no independently verifiable second channel, recovery has no path to succeed and is refused, not weakened to one factor to accommodate the gap."
- **The reverse direction is closed here.** An identity that holds a factor cannot reach this subsection's path, so first-credential establishment can never be used as an un-gated credential reset that skips §6.1's step-up. An identity returns to the zero-factor state only by having its factors revoked, and revocation is itself a change to the authentication basis that §6.1's first trigger gates — so the zero-factor state is reachable, after the first time, only *through* the assurance this path lacks. That is the structural closure, not a policy about who may ask.

**`04-auth-and-identity-spec.md` §8's forbidden weakenings, each closed by a named structural property of this mechanism.** A first-credential path is where a bypass would hide, so each row states the property rather than an intention.

| Forbidden Weakening (`04-auth-and-identity-spec.md` §8) | The Structural Property That Closes It Here |
|---|---|
| Bypassing authentication for convenience, actor type, deadline, or apparent low risk. | Neither path establishes an identity, issues a `platform.sessions` row, or produces an Authenticated Actor Identity object (§5.1). A redeemed grant reaches exactly one write and no governed action; the enrolled identity then authenticates through §3 like any other, and §4.3 remains the only mechanism that establishes a session. There is no code path from a grant to a handler. |
| Silently downgrading a configured assurance requirement. | The transaction writes the identity's **full** configured factor set or nothing (above). An identity whose tenant configuration requires a second factor cannot come into existence holding only one — not because a check refuses the partial case, but because atomicity leaves no partial case to refuse. Which methods that configuration requires stays builder-defined, exactly as §3.1 already fixes ("Which method or methods apply to which tenant, application, or role is builder-defined configuration"); this mechanism reads it and never substitutes a platform default. |
| Sharing a single identity or session across more than one tenant or actor. | The grant names exactly one `platform_user_id` and the write targets that anchor alone. A first factor is established once per **identity**, never once per tenant binding, which is the direct reading of `02-platform-data-model-design.md` §5 — "the identity anchor is global precisely so one human's platform credential is not duplicated per tenant." A person who already holds an anchor and a factor in one tenant is, by definition, not in the zero-factor state, so admitting them to a second tenant issues no grant and writes no second credential; they authenticate with the factor they already hold. |
| An indefinite or non-expiring session. | No session is created by either path, so none can be unbounded. The grant itself is not a session — it carries no `platform.sessions` row, no assurance level, and no `absolute_expires_at`, and it expires on its own short horizon independent of §4's ceilings, which continue to govern every session the identity later holds. |
| A recovery path that restores access without independently re-establishing identity. | The two paths are mutually exclusive on the same zero-factor read (above), so this mechanism is never reachable by an identity that has something to recover, and §7 is never reachable by one that has not. Neither path can serve as the other's weaker substitute. |
| An auth flow that discloses whether an identity, tenant, or account exists to an unauthenticated or unverified requester. | A redemption response is uniform in shape whether the artifact is valid, expired, replayed, or names no identity at all, and whether the named identity exists, is in the zero-factor state, or is not — the identical enumeration posture §7 already fixes for recovery responses, applied to this surface rather than re-derived for it. Path B carries the same posture: an assertion that establishes no link fails through the same SSO path §3.1 fixes, and its response distinguishes a subject that matched no anchor from one whose identity is already enrolled in neither shape nor content. |
| Trusting an identity asserted by an unverified caller instead of establishing it directly. | Nothing here accepts an assertion of identity from the caller. Path A verifies a platform-signed artifact against the platform's own key and the anchor's own current state; Path B verifies a provider assertion cryptographically against a provider the tenant already designated trusted (§3.1). In both cases the caller supplies a credential the Gate checks, never a claim the Gate believes. |

**Evidence produced, checked against the standing index rather than minted reflexively.** `08-audit-and-traceability-design.md` §4.5 records that this document mints **no** dedicated `event_type` and populates that document's base record shape (§4.2) directly for authentication, session, step-up, and recovery events — "captured here as a documented absence, not an omission." Running the collision-and-fit test rather than inheriting the convention: no existing type covers a first-factor write, and the closest candidates were checked and rejected as poor fits rather than close ones — `builder-admission` and every other Authorization-and-grant type describe the creation or narrowing of a **grant**, and this mechanism creates none and confers no standing, so landing a first-factor write there would misfile it under a category §5 fixes for a different fact. What remains is the Identity-and-session family, which is exactly where this belongs and which carries no dedicated type by the established, deliberate convention above. **No `event_type` is minted, so `08-audit-and-traceability-design.md` §4.5 needs no new row and its count is unchanged.** Three capture points populate the base record directly, each distinguished by `source_mechanism` — the field §4.5 already establishes as the discriminator among paths within one shape:

- **Grant issuance** — `source_mechanism` the issuing path, `actor_kind` the issuing authority's own kind, `target_reference` the named `platform_user_id`, `what_was_inspected` the zero-factor condition evaluated at issuance, `outcome = applied`. The artifact itself is never captured, on that document's own base-record rule that "no field stores a secret" (`08-audit-and-traceability-design.md` §4.2).
- **Redemption or provider-link establishment** — `source_mechanism` the Enrollment Gate, `actor_kind = unresolved` (the enrolling person holds no established identity at the moment of the write, which is exactly the state that field's `unresolved` value exists for), `target_reference` the anchor and the factor rows written, `outcome = applied`.
- **Refusal** — the same shape at `outcome = refused`, with `result` carrying which of the three verification conditions failed, at the granularity §4.2's own `result` field already fixes for each mechanism's own vocabulary.

**What this subsection does not design, so no reader infers it from the mechanism's shape.** It designs no recovery-flow or enrollment user experience, on the identical exclusion §7 already states for recovery. It does not decide which methods any tenant's configuration requires, which stays builder-defined (§3.1). It designs no delivery channel, medium, or timeliness figure (above). It writes no anchor row, and closes no anchor gap. And it adds no assurance level: §3.3's three levels are unchanged, because neither path establishes an identity for a level to describe.

## 4. Session Lifecycle and Expiry

A session is the bounded period during which an authenticated identity is recognized without re-authenticating for every action (`04-auth-and-identity-spec.md` §5). This section designs the concrete mechanism that makes every rule of that section true, honoring the numeric ceilings `06-non-functional-requirements.md` §10 fixes — ≤ 30 minutes idle, ≤ 12 hours absolute — cited here, never restated as this document's own value.

### 4.1 The Session Record: Storage the Data Model Explicitly Deferred Here

`02-platform-data-model-design.md` §3.1 fixes that `platform.platform_users` is the global identity anchor and states plainly that "authentication mechanics (credentials, sessions, MFA) are `03-authentication-and-identity-design.md`'s; this table anchors the identity record those mechanics act on." This document adds the four platform-global tables that deferral names, without altering `platform.platform_users` or any table `02-platform-data-model-design.md` §3–§4 already fixes:

| Table | Purpose |
|---|---|
| `platform.credentials` | One row per enrolled first-factor credential: `credential_id` (UUIDv7, PK), `platform_user_id` (FK), `credential_type` (password-hash / webauthn-public-key), `credential_material` (a salted hash or a public-key reference — never a recoverable secret), `enrolled_at`, `revoked_at`. |
| `platform.mfa_enrollments` | One row per enrolled second factor: `enrollment_id` (UUIDv7, PK), `platform_user_id` (FK), `factor_type` (totp / webauthn), `factor_material`, `enrolled_at`, `revoked_at`. |
| `platform.identity_provider_links` | One row per external-provider mapping: `link_id` (UUIDv7, PK), `platform_user_id` (FK), `provider_id`, `external_subject`, `linked_at`, `revoked_at`. Realizes SSO and federated/social authentication's provider mapping (§3.1) without absorbing the provider's own identity store. |
| `platform.sessions` | The session record itself — the authority for whether a session is currently valid (§4.2). |

### 4.2 What a Session Record Carries, and Why It Is the Authority, Not the Bearer Token

`platform.sessions`: `session_id` (UUIDv7, PK), `platform_user_id` (FK), `actor_class`, `tenant_id` (FK, nullable — null for a steward-bound identity, including the autonomous agent, whose single context is the platform-global scope itself, never a per-tenant one; non-null for every other actor class, per §5 "a session belongs to exactly one identity and one tenant context"), `assurance_level` (§3.3), `auth_methods_used`, `established_at`, `absolute_expires_at` (`established_at` + the ≤ 12-hour ceiling, computed once and never recomputed), `last_active_at`, `status` (`active` / `expired` / `revoked`), `revoked_at`, `revoked_reason`.

**The session record, not the bearer credential the caller holds, is the authority for validity.** The caller carries a signed, short-lived session token referencing `session_id`; every request that reaches the Authentication Gate (§5.2) validates the token's signature *and* re-reads the `platform.sessions` row it references, checking `status = active`, `last_active_at` within the idle ceiling of the current time, and the current time before `absolute_expires_at`. A signature-valid token whose session row has been marked `revoked` or has passed either ceiling is refused identically to a forged one. This is the mechanism that makes grant revocation, credential change, and account/tenant removal (§4.4) actually terminate a session rather than merely being unable to prevent a still-valid, still-signed token from being honored until its own encoded expiry — the reason this document's ADR (§8) chooses a server-side record over a purely stateless token.

### 4.3 Establishment

A session is established the moment §3's mechanism successfully verifies an identity: an interactive actor completing its configured method(s) at §3.1, or a non-interactive actor's credential verifying at §3.2. Establishment creates exactly one `platform.sessions` row, sets `established_at` and `absolute_expires_at` together, and returns the bearer session token to the caller. No session is ever established without a corresponding record — there is no code path that issues a token without first writing the row the Authentication Gate will later re-read.

### 4.4 Expiry

`04-auth-and-identity-spec.md` §5 fixes six expiry triggers; this section is the mechanism that makes each one terminate a session in fact:

| Trigger | Mechanism |
|---|---|
| Idle expiry | The Authentication Gate compares the current time to `last_active_at` on every request; where the gap exceeds the ≤ 30-minute ceiling, the session is marked `expired` and the request is refused before any handler runs. |
| Absolute expiry | The Authentication Gate compares the current time to `absolute_expires_at`, computed once at establishment (§4.2) and never recomputed by any subsequent refresh (§4.5) — this is the structural closure of `04-auth-and-identity-spec.md` §8's forbidden weakening, "an indefinite or non-expiring session": no operation in this design ever writes a new, later value into `absolute_expires_at`. |
| Explicit termination | The actor's own termination call sets `status = revoked` directly; the next Authentication Gate check refuses the (now-revoked) token immediately, with no grace window. |
| Grant revocation | The grant-revocation operation (`02-tenant-isolation-and-access-control-design.md`'s binding-table mechanism) and this document's session mechanism run in the same transaction where the two tables are updated together: revoking a `tenant_<id>.tenant_users` row (or a `platform.steward_role_bindings` row) sets `status = revoked` on every `platform.sessions` row carrying that `platform_user_id` in that tenant context, in the same commit. |
| Tenant, application, or account removal | The same transactional pattern as grant revocation: removing, suspending, or disabling a tenant, application, or `platform.platform_users` account revokes every `platform.sessions` row it affects in the same commit as the removal itself. For a tenant or an application, the transition this row reacts to is `02-tenant-isolation-and-access-control-design.md` §6.2's Registry Status Mutator — the same explicit citation of an owning mechanism the Grant revocation row above already carries, owed to this row and supplied here (`BACKLOG.md` §1au(c)). The `platform.platform_users` half of the row has no such owning mechanism to cite: that document's §6.2 governs `platform.tenants` and `platform.applications` only, so what moves an account's own status is not fixed anywhere — stated rather than papered over with a citation that would not resolve. |
| Security-relevant credential change | Writing a new `platform.credentials` or `platform.mfa_enrollments` row, or revoking an existing one, revokes every other existing `platform.sessions` row of that `platform_user_id` in the same transaction — "every other existing session of that identity" ends, per §5, without exception for the session performing the change itself (which re-establishes fresh, at no lower an assurance level, immediately after). |

**Re-establishment after expiry is authentication, never resumption.** An expired or revoked session's token is refused at the Authentication Gate exactly as an invalid one is; there is no refresh path available to it (§4.5 refreshes only an active session before either ceiling). The identity must complete §3's mechanism again, at no less than the assurance level originally required for the action it seeks.

### 4.5 Refresh

An active session (neither ceiling reached, `status = active`) may refresh: the Authentication Gate issues a new bearer token referencing the same `session_id` and advances `last_active_at` to the current time on ordinary activity. Refresh **never** advances `absolute_expires_at` and **never** revives a session whose `status` has already become `expired` or `revoked` — refresh reads the same authority record §4.2 fixes and is bound by the same two checks every other request passes. A refresh attempted past `absolute_expires_at` is refused identically to any other request past that ceiling; the session must be re-established, not extended.

## 5. The Authenticated-Actor-Identity Handoff to Tenant Isolation

### 5.1 The Authenticated Actor Identity Object

By the time a request reaches `02-tenant-isolation-and-access-control-design.md` §4.1's Context Resolution Point, this document's mechanism has already produced and attached one object to the request: the **Authenticated Actor Identity**.

```
{
  platform_user_id,        // the platform.platform_users anchor (§4.1's Registry Accessor precondition)
  actor_class,             // builder persona | extender | end user | autonomous agent | external contract consumer
  session_id,              // the platform.sessions row this identity is currently carried by
  assurance_level,         // single-factor | mfa-verified | service-credential (§3.3)
  auth_methods_used,       // which method(s) established this session
  established_at,
  absolute_expires_at,
  step_up: {
    // per-trigger record, never a single cached flag — §6.2
    satisfied_triggers: [ { trigger, verified_at, method } ]
  }
}
```

This is deliberately the minimum shape the Registry Accessor and the Context Resolution Point already state they need. The Registry Accessor's signature "accepts only an already-authenticated actor identity (`platform_user_id`...) — never a client-supplied `tenant_id` or `application_id`" (`02-tenant-isolation-and-access-control-design.md` §3.1); this object supplies exactly that `platform_user_id`, verified, and nothing a caller could use to widen a registry read. The Context Resolution Point's step 1 states that "the request's already-established actor identity... is passed to the Registry Accessor" (§4.1 there); this object is that identity. Every other field of the Resolved Request Context that document assembles — `tenant_id`, `application_id`, `schema_name`, `role`, `permission scope`, `grant reference` — is resolved by the Registry Accessor from the actor's own binding rows (`02-tenant-isolation-and-access-control-design.md` §3.1, §6), not supplied by this object; this document does not decide or duplicate any of those fields.

`actor_class` is carried on this object because §3.2's three non-interactive classes authenticate identically to each other at the mechanism level, and the Registry Accessor distinguishes them structurally by *where their grant lives* (steward bindings versus tenant bindings), not by re-deriving actor type from the credential. Carrying `actor_class` here lets the Registry Accessor's lookup start from the correct binding table without inferring it from authentication method, which — per §3.2's table — is not a reliable signal on its own (an extender's runtime credential and an external contract consumer's credential are the same OAuth2 mechanism).

### 5.2 Where This Runs: the Authentication Gate, Inside Isolation and Trust

`03-architecture-realization-design.md` §3.1 places "identity resolution, authentication-state handling, authorization decisioning, and the tenant-boundary primitives every other module assumes already hold" inside the same module, `components/isolation-and-trust`, that houses the Context Resolution Point. This document's mechanism — §3's method verification, §4's session establishment and validity check — runs as the **Authentication Gate**, one mandatory step inside that module, immediately upstream of the Context Resolution Point: every request passes the Authentication Gate first, receiving the Authenticated Actor Identity object of §5.1, and only then reaches `02-tenant-isolation-and-access-control-design.md` §4.1's step 1. No request reaches the Context Resolution Point without having first passed the Authentication Gate — there is no second entry path into that module that skips it, matching the same import-boundary discipline `03-architecture-realization-design.md` §4.2 already builds and `02-tenant-isolation-and-access-control-design.md` §5.3 already extends by one rule.

An unauthenticated request — one that fails every check in §3 and §4 — never reaches the Context Resolution Point at all; the Authentication Gate refuses it directly, and no Resolved Request Context is ever assembled for it. This is the mechanism underneath `04-auth-and-identity-spec.md` §3's "an unestablished identity carries no standing": there is no code path by which an unestablished identity's request could be handed to the Registry Accessor.

## 6. Step-Up Authentication

### 6.1 Triggers

`04-auth-and-identity-spec.md` §6 fixes five triggers; this section is the mechanism that enforces each:

| Trigger | Mechanism |
|---|---|
| A change to the actor's own authentication basis (credentials, enrolled methods, recovery settings). | The Authentication Gate requires a fresh, synchronous verification at `mfa-verified` assurance (or the identity's current maximum, whichever is higher) before the write to `platform.credentials` or `platform.mfa_enrollments` proceeds — checked at the point of that specific write, not inferred from session assurance alone. |
| An action within a role capable of granting authority onward (a tenant owner or access administrator granting a role, `02-governance-and-security/03-access-control-and-tenancy-model.md` §5). | The Authentication Gate requires a fresh verification before the binding-table write (`tenant_<id>.tenant_users` insertion or `scope_type`/role change) proceeds; the write itself is `02-tenant-isolation-and-access-control-design.md`'s, but the step-up gate in front of it is this document's. |
| An action matching a mandatory security-review trigger (`02-governance-and-security/02-security-policy.md` §7 — a change to a trust boundary, secrets handling, or identity, authorization, or isolation mechanics). | The same fresh-verification gate as above, applied at the point such a change is proposed to merge or execute; this document does not restate §7's trigger list, only the gate that fires against it. |
| A discontinuity in session context (resumption in a context the platform cannot correlate with the original authentication — for example, a session token presented from a materially different network or device signal than the one recorded at establishment). | The Authentication Gate treats an uncorrelated resumption as a reduction in assurance and demands a fresh verification before the request proceeds, rather than trusting the still-valid session record's assurance level unmodified. |
| A builder-configured elevated-assurance action within a built application. | The Authentication Gate exposes step-up as a callable primitive any built application's own authorization logic may invoke for an action the builder has configured as requiring it; which actions require it is builder-defined content, never a platform assumption, exactly as `04-auth-and-identity-spec.md` §6 frames the method families themselves. |

### 6.2 Mechanism, and the Forbidden Weakenings It Structurally Closes

**Step-up cannot be satisfied by a cached prior verification.** Each triggering action records its own `{ trigger, verified_at, method }` entry in the Authenticated Actor Identity's `step_up.satisfied_triggers` list (§5.1) at the moment it is checked; the Authentication Gate never reads an *earlier* entry to satisfy a *different* trigger, and never reads any entry to satisfy the *same* trigger for a *later, distinct* action — every qualifying action demands its own fresh, synchronous verification, full stop. There is no session-level flag ("this identity did MFA recently") a step-up check can consult instead of demanding a new one; the only field a step-up check ever writes to is a new entry naming the specific action it gated.

**Step-up cannot be bypassed.** The action's handler is never invoked before the fresh verification succeeds — the Authentication Gate sits structurally in front of the handler for a matching trigger, the same position it holds for ordinary authentication (§5.2), so there is no code path that reaches the handler without passing the gate.

**Failure denies the action.** Where the fresh verification cannot be completed, or its result cannot be established (the identity provider is unreachable, the second factor fails, the correlation signal cannot be confirmed), the Authentication Gate refuses the action — deny-by-default (`02-governance-and-security/01-system-invariants.md` §3), never a partial or provisional proceed.

## 7. Account Recovery

Recovery is the process by which an identity that has lost its means of authenticating regains it (`04-auth-and-identity-spec.md` §7) — never the path by which an identity that has never held one obtains its first, which is §3.4's, and is mutually exclusive with this section on the same read of the same three structures (§3.4). This document designs the mechanism's guardrails only — never a specific recovery-flow user experience, which is a builder-facing or platform-UI concern outside this document's scope.

| Guardrail (`04-auth-and-identity-spec.md` §7) | How the Mechanism Holds It |
|---|---|
| Recovery never bypasses authentication before access. | Recovery is designed as a distinct authentication method, not an authorization exception: it runs through the same Authentication Gate (§5.2) as any other method, producing a fresh Authenticated Actor Identity at no lower an assurance level than the identity ordinarily requires — it never sets a flag that lets a subsequent request skip the Gate. |
| Recovery never rests on a single weak factor. | The recovery mechanism requires two independent verifications drawn from channels the identity previously enrolled (§4.1's `platform.credentials`, `platform.mfa_enrollments`, or `platform.identity_provider_links` rows) — never a single knowledge-based detail (a security question, an unverified email click) standing alone. Where an identity has enrolled no independently verifiable second channel, recovery has no path to succeed and is refused, not weakened to one factor to accommodate the gap. |
| Recovery never discloses more than it must. | Every recovery-flow response is identical in shape whether or not the requested identity, tenant, or method exists — the mechanism resolves internally which channels to challenge and returns the same "a recovery attempt has been initiated if eligible" response regardless, so an unverified requester cannot distinguish a valid target from an invalid one. This is the deny-by-default disclosure posture applied to enumeration, not merely to access. |
| Recovery never crosses a tenant boundary or elevates authority. | Recovery re-establishes a session bound to the same `platform_user_id`, the same `tenant_id` bindings, and the same assurance ceiling the identity held before losing access — the recovery mechanism has no write path to `tenant_<id>.tenant_users`, `platform.steward_role_bindings`, or any other grant table; it only re-verifies identity and re-issues §4's session record within grants that already existed. |
| Successful recovery ends every other existing session of the identity. | Recovery writes a new `platform.credentials` or `platform.mfa_enrollments` row (or revokes a compromised one) as part of completing, which is exactly the security-relevant credential change §4.4's mechanism already revokes every other session against, in the same transaction — recovery needs no separate revocation step; it is the same trigger, not a new one. |
| Recovery that cannot establish identity with confidence is refused. | Where either of the two required independent verifications (row above) fails or cannot be completed, the mechanism refuses the attempt outright — there is no partial-recovery or provisional-access state this design produces. |
| A change to the recovery flow is a mandatory security-review trigger. | Cited from `02-governance-and-security/02-security-policy.md` §7, not restated; this document states only that its own recovery mechanism is subject to that trigger like any other identity-mechanics change. |

## 8. Design Decision Records

Recorded inline, per the convention `01-technology-stack-design.md` §9 establishes. `02-tenant-isolation-and-access-control-design.md` §10 consumed ADR-018 and left ADR-019 as the next available identifier (ADR-017 remains separately reserved for `05-mobile-application-delivery-design.md`, `DECISIONS.md` D-25 — unaffected here); this document consumes ADR-019, and consumes ADR-067 for the first-credential establishment mechanism §3.4 adds (§8.2) — two ADRs in total, verified next-free against both `ADR-REGISTER.md` and the design library itself before minting.

### 8.1 ADR-019 — Session-Record-Backed Authentication: Server-Side Revocation Authority Over a Stateless Bearer Token

- **Status:** Team-Approved — decided under the `DECISIONS.md` D-16 delegation and recorded with its criteria; in force, no lead sign-off required (`01-technology-stack-design.md` §9; `DECISIONS.md` D-37, correcting this record's prior self-approved `Approved` label).
- **The question it answers:** Given that `04-auth-and-identity-spec.md` §5 and §8 require every session to be finite and require grant revocation, credential change, and account/tenant removal to terminate a session immediately — not merely fail to renew it at its own encoded expiry — what mechanism carries an authenticated identity forward across requests such that a revocation decision made at one moment is honored at the very next request, on any candidate stack?
- **Cost to reverse:** **High** — every request path that validates a bearer credential depends on this mechanism's shape; reversing it means re-deriving how every one of §4.4's six expiry triggers is enforced. **Low** for the specific signing algorithm or token encoding chosen for the bearer artifact itself, which carries no semantic weight beyond referencing `session_id`.
- **Upstream decisions assumed:** `01-technology-stack-design.md` §14.7 (ADR-004 — PostgreSQL as the V1.0 platform-global schema this document's four new tables live in); `02-platform-data-model-design.md` §3.1 (the `platform.platform_users` anchor this document's tables key against, and that document's explicit deferral of credential, session, and MFA storage here); `02-tenant-isolation-and-access-control-design.md` §4.1, §6 (the Registry Accessor and Context Resolution Point this document's output is shaped to feed); `01-invariant-enforcement-design.md` §5.1, §8 (the INV-02 check location this mechanism's identity and session output underlies).
- **Criteria applied, and how each resolved:**
  - **Immediate revocability on the four event-driven triggers of §4.4** (explicit termination, grant revocation, tenant/application/account removal, security-relevant credential change) — **decisive.** Only a mechanism with a server-side authority record that every request re-reads can honor a revocation the instant it happens; a purely self-contained bearer token cannot be reached into once issued, and this criterion alone rules that option out.
  - **Uniform fit across every entry point** (interactive human sessions at the builder UI and end-user surfaces, the mobile-delivery runtime, and the non-interactive credentials of §3.2) — **decisive against a cookie-only, no-bearer-artifact design.** A server-held cookie session has no natural analogue for a signed service-credential caller or a mobile runtime; a portable bearer token referencing a server-side record fits all four entry-point shapes identically.
  - **Per-request operational cost** — **considered, did not discriminate.** A session-record lookup and a revocation-list check cost the same on every request; this criterion is recorded as a finding, not dropped, because it is the reason the revocation-list variant looked initially attractive before the next criterion ruled it out.
  - **Information carried versus mechanism duplicated** — **decisive against the revocation-list-augmented token.** A revocation list checked on every request cannot express idle-timeout or absolute-ceiling state without accumulating fields that make it, in substance, a session record under a different name — so the "stateless-plus-list" option converges on this decision's own shape while being less direct about it.
- **Verified vs. reasoned:** Reasoned — the decision follows directly from the cited specification's own requirement (immediate termination on revocation, not eventual expiry) and the structural property that a purely stateless, self-contained bearer token (a JWT validated by signature alone, with no server-side lookup) cannot be revoked before its own encoded expiry without an additional revocation-list mechanism that duplicates most of the state a session record already holds. No time-sensitive ecosystem, tooling, or adoption claim is made.
- **Context:** `04-auth-and-identity-spec.md` §5's six expiry triggers include four (explicit termination, grant revocation, tenant/application/account removal, security-relevant credential change) that must take effect at the moment the triggering event occurs, not at the bearer token's own next natural expiry — a purely stateless token has no mechanism to be "reached into" and invalidated once issued.
- **Decision:** A server-side `platform.sessions` record (§4.1–§4.2) is the sole authority for session validity; the caller holds a short-lived, signed bearer token that references the record's `session_id` but carries no independent authority of its own. Every request re-reads the record's `status`, `last_active_at`, and `absolute_expires_at` at the Authentication Gate (§5.2); a signature-valid token whose record has been revoked or has passed either ceiling is refused identically to a forged one. `absolute_expires_at` is computed once at establishment and never recomputed by any refresh operation (§4.5).
- **Alternatives considered:** *A purely stateless bearer token (self-contained JWT, signature-validated only, no server-side lookup)* — rejected; it cannot honor immediate revocation on four of the six triggers §4.4 lists without a separate revocation-list mechanism that, once added, is itself a server-side authority record in substance, making the "stateless" framing illusory rather than actually simpler. *A revocation-list-augmented stateless token* — considered as a middle option; rejected in favor of the session record directly, because a revocation list checked on every request is operationally identical in cost to the session-record lookup this design already performs, while carrying strictly less information (it cannot express idle-timeout or absolute-ceiling state without becoming, in effect, the session record under a different name). *A purely server-side session with no bearer artifact at all (a server-held cookie session with no signed token)* — rejected as unsuitable for the non-interactive actor classes of §3.2, which authenticate via signed credential assertions rather than a browser-held cookie, and for the mobile-delivery runtime (C-20), where a portable, stack-neutral bearer artifact is the simpler integration surface across entry points.
- **Consequences:** Binds every entry point — builder UI, mobile-delivery runtime, built-application end-user surfaces, and the platform's published contract (C-12, including its MCP surface) — to validate the same session record shape at the Authentication Gate, rather than each entry point inventing its own validity check. Binds `02-tenant-isolation-and-access-control-design.md`'s Registry Accessor and Context Resolution Point to receive an Authenticated Actor Identity (§5.1) that is only ever produced by a Gate that has already performed this validation — no downstream mechanism re-checks session validity independently. Binds `04-scalability-availability-and-performance-design.md` to account for a `platform.sessions` row read on every request as part of that document's own connection- and load-profile design; this document does not design caching or read-scaling strategy for that lookup, and states plainly that it is a cost the mechanism imposes, not one it resolves.

### 8.2 ADR-067 — First-Credential Establishment: A State-Triggered Enrollment Gate, a Stateless Single-Purpose Grant Whose Use Record Is the State It Changes, and Step-Up Declared Structurally Inapplicable Rather Than Relaxed

- **Status:** Team-Approved — decided under the `DECISIONS.md` D-16 delegation and recorded with its criteria; in force, no lead sign-off required (`01-technology-stack-design.md` §9; `DECISIONS.md` D-37).
- **Why this is recorded as an ADR at all, tested rather than minted reflexively.** The contrary reading — that §3.4 merely supplies a missing write against structures §4.1 already fixed, and so decides nothing — was considered and rejected. Three of §3.4's determinations choose among alternatives with real, non-equivalent consequences: where the grant's single-use state lives (criterion 3, where the storable option is not merely less economical but reaches a forbidden weakening), whether the mechanism issues a session (criterion 4), and whether §6.1's step-up gate is applicable, adapted, or inapplicable (criterion 5) — the third of which resolves *against* the reading that would have widened an existing gate, and so changes what an already-approved mechanism covers rather than merely extending it to a new caller. It also overturns nothing and invents nothing: it forecloses one candidate design outright on an already-fixed specification boundary (criterion 2), which is a finding, not a preference. That is the test `02-tenant-isolation-and-access-control-design.md` §9 and `01-invariant-enforcement-design.md` §7 each apply when they decline to record a non-decision, and this clears it.
- **Cost to reverse:** **Moderate**, with one element graded separately rather than averaged into the whole. No table, column, or `event_type` is introduced, and no already-enrolled identity's access depends on which path enrolled it — §3's methods read the same three structures regardless of what wrote the rows, so reversing the enrollment shape touches no authentication or session path. What a reversal does touch is one write path and one durable inference: because the grant is stateless, the platform holds **no record that a given identity was enrolled by a grant rather than by a provider assertion** beyond the audit stream's own events, so a successor mechanism that needed to distinguish them for already-enrolled identities would have to reconstruct that from evidence rather than read it from state. **Low**, separately, for the choice between Path A and Path B for any given identity: that is decided per identity by whether a trusted provider is configured, and changing which path an identity takes requires no mechanism change at all. **Higher than the rest**, separately and honestly, for the decision to issue no session at redemption (criterion 4): reversing it would put a session-issuing path outside §4.3, which is the one property several of §3.4's forbidden-weakening closures rest on, so that element is not independently reversible in the way the others are.
- **Upstream decisions assumed:** `02-governance-and-security/03-access-control-and-tenancy-model.md` §4 (the assignment this decision realizes, its three thinness bullets, and the Tenant-admission role's own hard boundary, which is what forecloses criterion 2's rejected option — added by T85, `DECISIONS.md` D-60); `04-auth-and-identity-spec.md` §3, §4, §7, §8 (the gate rule, the method families, recovery's guardrails, and the seven forbidden weakenings §3.4's own table closes structurally); ADR-019 (§8.1 — the session record as the sole authority for validity, and `platform.sessions` as the only artifact §4.3 issues, which is what makes "no session at redemption" a meaningful property rather than a wording choice); ADR-065 (`02-tenant-isolation-and-access-control-design.md` §10.5 — the owner-admission act whose deliberate exclusion of credential issuance created the zero-factor state this mechanism answers, consumed unchanged and not re-opened); `02-platform-data-model-design.md` §3.1, §5 (the `platform.platform_users` anchor and its identity attributes, and the one-anchor-many-tenants rule that makes a first factor an identity-level fact rather than a per-binding one); `03-architecture-realization-design.md` §3.1 (the module the Enrollment Gate runs inside, unchanged); `08-audit-and-traceability-design.md` §4.2, §4.5 (the base record this mechanism populates directly, including its own "no field stores a secret" rule that keeps the grant artifact out of any event's content, and the standing index the no-minting finding was checked against). `08-audit-and-traceability-design.md`'s own ADR-025 remains Provisional — Pending Lead Approval; this decision depends only on its already-designed event model and its standing index, never on its approval status (`PROCESS.md` §12.2).
- **Verified vs. reasoned:** Reasoned throughout (`PROCESS.md` §12.3). Every claim is either a structural property (single-transaction commit of a factor set; the mutual exclusivity of two predicates over the same three tables; the absence of a session-issuing path outside §4.3; a signature-and-expiry check over an artifact the platform itself signed; the impossibility of a tenant having configured a trusted provider before it has an owner) or a direct application of a cited specification or design document. Two limits are stated as findings rather than resolved: an outstanding stateless grant cannot be revoked before expiry, and Path A is inert until a delivery channel exists. No claim rests on a time-sensitive ecosystem, tooling, vendor, or provider-behavior fact, and no product, vendor, or provider is named.
- **Context:** `02-governance-and-security/03-access-control-and-tenancy-model.md` §4 assigned first authentication to this document and named no mechanism. This document then designed the credential and enrollment structures (§4.1), the methods that read them (§3), the step-up gate in front of a credential *change* (§6.1), and recovery for an identity that has *already* enrolled a channel (§7) — and no path that writes the first row into any of the three structures. `02-tenant-isolation-and-access-control-design.md` §6.3 made that gap load-bearing rather than theoretical by designing an act that produces exactly one credential-less identity per admitted tenant, with credential issuance excluded from its own scope; `BACKLOG.md` §1at records it. Every tenant the platform will ever admit produces an owner identity that, until this decision, had no designed way to authenticate even once.
- **Question this ADR answers, phrased for reuse:** Where a document designs the structures a credential is stored in, the methods that read them, a step-up gate in front of changing them, and a recovery path for an identity that already has one — but no path that writes the first — what mechanism supplies that write: what triggers it, what authority it runs under given that the subject holds no session and no third actor may act in the subject's place, where the single-use property of any issuing artifact lives, does the applicable step-up gate apply, adapt, or not apply at all, and what separates the new path from the recovery path it structurally resembles?
- **Criteria applied, and how each resolved:**

  | # | Criterion | How It Resolved |
  |---|---|---|
  | 1 | Is the mechanism triggered by a named act, or by a state? | **A state — the zero-factor state.** Binding it to `02-tenant-isolation-and-access-control-design.md` §6.3's admission act specifically was rejected: it would make this mechanism's correctness depend on that act being the only producer of credential-less identities, which is true today and is not a property either document guarantees. A state trigger stays correct for any future producer without that producer knowing this mechanism exists — and, tested against §6.1's builder admission, it correctly returns *not a trigger*, because that path presupposes an established identity rather than creating one. That test is what surfaced the separate anchor gap §3.4 routes to the owning document. |
  | 2 | Can the issuing authority hand the first factor to the person directly? | **No — foreclosed, not traded off.** An authority holding a usable factor for a tenant owner's identity can authenticate as that owner, which is exactly the act `02-governance-and-security/03-access-control-and-tenancy-model.md` §4's Tenant-admission boundary forbids ("Cannot act as, or in place of, a tenant owner once a tenant is admitted"). No expiry, forced-rotation, or single-use property removes the capability once the secret has passed through the issuer's hands. This is the criterion that makes the delivery dependency unavoidable rather than a convenience, and it is why the mechanism states a *property* the future channel must satisfy — that the issuing authority does not read it — rather than a medium. |
  | 3 | Where does the grant's single-use property live? | **In the state the redemption changes, not in a stored record.** Three candidates: *(a)* stateless, single use enforced by the zero-factor condition the redemption itself flips — chosen; *(b)* a stored grant row inside `platform.credentials`, the only existing structure whose columns could carry one — **rejected on correctness, not economy**: such a row is a non-revoked credential row, which takes the identity out of the zero-factor state before it holds any real factor and thereby opens §7's recovery path to an identity that has enrolled nothing, a forbidden weakening reached through a storage choice; *(c)* a new grant table — rejected as unnecessary once (a) shows the state already carries the fact, and as state whose only purpose would be a replay prevention the zero-factor condition already provides. The honest cost of (a) is recorded rather than absorbed: an outstanding grant cannot be revoked before its expiry, and several may be live at once. |
  | 4 | Does redemption issue a session? | **No.** Issuing one was rejected: §4.3 conditions every session on §3's verification having succeeded, and a session issued by a grant would make the grant an authentication method in substance — the "bypassing authentication for convenience" weakening arriving through the front door, with §5.1's Authenticated Actor Identity object produced for an identity that has verified nothing. The enrolled identity instead authenticates through §3 immediately afterward, at its full configured assurance. The cost is one extra verification for the person, and the benefit is that §4.3 remains the sole session-issuing path, which several of §3.4's other closures depend on. |
  | 5 | Does §6.1's step-up gate apply to a first credential? | **Structurally inapplicable — and §6.1 is left untouched.** Three readings were weighed: *(a)* it applies and is satisfied at a lower bar — rejected outright, since that is the "silently downgrading a configured assurance requirement" weakening stated as a design; *(b)* §6.1's first trigger is re-worded to exempt a first write — rejected, because narrowing a trigger to fit a new path weakens an existing gate for every path, and §6.1's five triggers are not this decision's to edit; *(c)* the gate has no referent here, because there is no prior factor to re-verify and no current maximum to meet — chosen, and stated as a finding rather than an exemption. What replaces it is the grant's own verification, which reproduces all three properties §6.2 demands (fresh, synchronous, and specific to the action it authorizes) and adds a fourth §6.2 has no occasion to state (self-voiding), and is honestly weaker in one respect: it rests on a single channel, because an identity holding no factor has nothing for a second to be independent of. That single-channel assurance is why the grant's reach is bounded to one write and no standing. |
  | 6 | What separates this path from §7's recovery path? | **The same predicate, read once, that can only ever open one of them.** This path requires zero non-revoked rows across all three structures; §7 requires at least one, in fact two independent ones. The dangerous direction is already closed by §7's own words and needed no new rule. The reverse direction is closed here, and matters more than it first appears: an identity returns to the zero-factor state only through a revocation that §6.1's first trigger already gates, so this path can never serve as an un-gated credential reset. A single shared "establish or restore" mechanism was rejected — it would have exactly one predicate and two assurance standards, which is the conflation the specification's fifth forbidden weakening names. |
  | 7 | Does the mechanism mint an `event_type`? | **No — the documented-absence convention is followed, after the test rather than instead of it.** No existing type covers a first-factor write, and the nearest candidates were rejected as *poor* fits rather than close ones: `builder-admission` and every sibling Authorization-and-grant type describe a grant's creation or narrowing, and this mechanism creates no grant and confers no standing, so landing there would misfile the fact under a category §5 fixes for a different one. The correct family is Identity and session events, which carries no dedicated type by `08-audit-and-traceability-design.md` §4.5's own deliberate convention for this document. Three capture points populate the base record directly, discriminated by `source_mechanism`. Consequently `08-audit-and-traceability-design.md` §4.5 needs no row and no count change, and that document is not amended by this ticket at all. |

- **Decision:** (1) First-credential establishment is triggered by the **zero-factor state** — a `platform.platform_users` row with no non-revoked row in `platform.credentials`, `platform.mfa_enrollments`, or `platform.identity_provider_links` — never by a named admitting act; owner admission (`02-tenant-isolation-and-access-control-design.md` §6.3) is a caller, and builder admission (§6.1 there) is not a caller at all. (2) The write runs at the **Enrollment Gate**, one additional mandatory step in the Authentication Gate's own structural position (§5.2) inside `components/isolation-and-trust`, over the same platform-global connection the Gate already writes `platform.sessions` over — no administrative or provisioning connection, and no write into any tenant schema. (3) Its authority is never a session: not the subject's, which cannot exist yet, and not any third actor's; the sole authority is the artifact or assertion verified synchronously at the Gate in the same step as the write. (4) Two paths are constructible — a stateless, short-lived, signed, single-purpose **enrollment grant** naming one `platform_user_id`, and a **provider-link-first** path where the identity's tenant has already configured a trusted provider under §3.1; a steward-mediated handoff of a usable factor is foreclosed by the Tenant-admission boundary, not merely disfavored. (5) The grant's single-use property is the zero-factor condition its own redemption flips; no grant record is stored, and in particular none is stored in `platform.credentials`. (6) The full configured factor set commits in one transaction, so no identity can exist holding a partial set and no configured assurance requirement can be silently downgraded. (7) No session, assurance level, or Authenticated Actor Identity object is produced by either path; the enrolled identity then authenticates through §3 exactly as any other. (8) §6.1's step-up gate is structurally inapplicable to a first factor and is left unmodified; the grant's own verification supplies the assurance argument, weaker in exactly one respect that is stated rather than graded away. (9) This path and §7's recovery path are mutually exclusive on the same predicate. (10) No `event_type` is minted; three capture points populate `08-audit-and-traceability-design.md` §4.2's base record directly.
- **Alternatives considered:** *A steward- or issuer-mediated handoff of a usable first factor* — foreclosed under criterion 2 by an already-fixed specification boundary, not rejected on preference. *A stored enrollment-grant row inside `platform.credentials`* — rejected under criterion 3 because it opens §7's recovery path to an un-enrolled identity, a forbidden weakening arriving through a storage decision. *A new grant table* — rejected under criterion 3 as unnecessary state and outside this ticket's structural scope. *Issuing a session on redemption* — rejected under criterion 4; it would make the grant an authentication method in substance and put a session-issuing path outside §4.3. *Adding a fourth assurance level for a grant-bearing request* — rejected; a level describes an established identity's strength, and neither path establishes an identity, so the level would describe nothing and would invite a step-up check to be satisfied by it. *Re-wording §6.1's first trigger to exempt a first write* — rejected under criterion 5; narrowing an existing gate to fit a new path weakens it for every path. *A single shared "establish or restore" mechanism spanning this path and §7* — rejected under criterion 6; one predicate with two assurance standards is exactly the fifth forbidden weakening. *Minting a dedicated `event_type`* — rejected under criterion 7. *Designing the delivery channel here so Path A would be immediately usable* — rejected; the channel is another document's, `BACKLOG.md` §1ar records it as open, and deciding it here would be this document fixing a mechanism it does not own. What this decision does contribute to that future choice is one property the channel must satisfy — that the issuing authority does not itself read it — which follows from criterion 2 and is stated as a requirement on the channel, never as a design of it.
- **Consequences:** Binds no downstream document to a new access path, a new structure, or a new event type: from the moment the factor rows commit, the identity is an ordinary subject of §3's methods, §4's session mechanics, §6's step-up gate, and §7's recovery path, and none of them changes. Binds `08-audit-and-traceability-design.md` to nothing — its §4.5 index needs no row and its count is unchanged, which is why that document is not amended by this ticket at all. Leaves **one dependency and two gaps in other documents, each named rather than absorbed.** The dependency: Path A is complete and correct and **inert for the first owner of every admitted tenant** until an outbound delivery channel exists — the mechanism half of `BACKLOG.md` §1ar, whose obligation half `05-meta-operations/04-human-in-the-loop-protocol.md` §6 states for a differently-subjected case; a future design ticket owning that channel discharges it, and this decision states only the one property it must satisfy. The first gap: no mechanism writes the `platform.platform_users` anchor for a person admitted under `02-tenant-isolation-and-access-control-design.md` §6.1, whose own identity precondition presupposes one — that document owns anchor writes and this one does not, so it is routed there, and this mechanism does not depend on its closure. The second gap: which authority may revoke another identity's enrolled factor set, the repair path for a compromised redemption, is the role-and-permission matrix's (`02-governance-and-security/03-access-control-and-tenancy-model.md` §4–§5) and is not asserted here; containment in the interim is §4.4's already-designed account-disable trigger, so nothing is left without a response. Registering ADR-067 in `ADR-REGISTER.md` remains an Orchestrator tracker-maintenance action at this ticket's close (`PROCESS.md` §3), not discharged by this document.

## 11. Binding Rules

- **Every entry point authenticates through the same mechanism.** The builder UI, the mobile-delivery runtime, every built application's end-user surface, and the platform's own published contract each route through the same Authentication Gate (§5.2); no entry point runs a parallel authentication path.
- **Identity precedes every governed action, structurally.** No request reaches the Context Resolution Point, and no handler is ever invoked, without first passing the Authentication Gate; an unestablished identity has no code path that reaches a governed action.
- **A session's validity is decided by its server-side record, never by its bearer token alone.** Every request re-reads `platform.sessions` for `status`, `last_active_at`, and `absolute_expires_at`; a signature-valid token whose record has expired or been revoked is refused identically to a forged one.
- **`absolute_expires_at` is written once and never recomputed.** No refresh, no activity, and no operation this design defines ever extends a session past the ≤ 12-hour ceiling `06-non-functional-requirements.md` §10 fixes.
- **Six triggers terminate a session, each in the same transaction as its cause.** Explicit termination, grant revocation, tenant/application/account removal, and security-relevant credential change each revoke the affected `platform.sessions` row(s) atomically with the event that causes them; idle and absolute expiry are enforced by comparison at every request, not by a separate sweep the request path depends on.
- **Step-up demands a fresh verification, every time, for every trigger.** No step-up check is ever satisfied by an earlier verification recorded against a different — or the same — trigger; each qualifying action writes its own `step_up.satisfied_triggers` entry and none is ever read to satisfy an action it was not recorded for.
- **A first credential is established once per identity, never per tenant binding, and never by an authority acting in the identity's place.** The path is open only to an identity holding no non-revoked credential, enrolled factor, or provider link; it issues no session, no assurance level, and no Authenticated Actor Identity object; it commits the identity's full configured factor set or nothing; and no session held by any other actor authorizes a first-factor write against another identity's anchor.
- **Step-up is inapplicable to a first credential and is never relaxed to reach one.** §6.1's five triggers are unchanged and continue to apply in full to every subsequent change to an authentication basis; the first write is the only one for which the gate has no prior factor to re-verify, and the enrollment grant's own fresh, synchronous, single-purpose, self-voiding verification is what stands in its place — resting on one channel, and bounded to one write for exactly that reason.
- **First-credential establishment and recovery are mutually exclusive, decided by the same read.** An identity with nothing enrolled can never reach the recovery path, and an identity holding a factor can never reach the establishment path; neither is ever available as the other's weaker substitute.
- **Recovery re-authenticates through the same Gate; it never bypasses it.** Recovery requires two independent, previously-enrolled verification channels, discloses nothing to an unverified requester, never crosses a tenant boundary or elevates authority, and revokes every other existing session as the same credential-change trigger already fixes — recovery is a distinct authentication method, never an authorization shortcut.
- **Non-interactive actors are checked exactly as strictly as interactive ones.** The extender's runtime credential, the autonomous agent's service credential, and the external contract consumer's client credential are verified by the same Authentication Gate, produce the same shape of Authenticated Actor Identity, and are subject to the same session, expiry, and step-up mechanics as any human actor — no actor class is exempted by virtue of autonomy or externality.
- **Everything here remains domain-neutral.** No method, session field, trigger, or guardrail this document defines encodes the characteristics of any single domain, tenant, or application; every mechanism holds identically for any software built on the platform.
