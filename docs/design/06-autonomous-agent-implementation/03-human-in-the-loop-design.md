## 3. Approval Gate, Escalation, and Halt — Three Concepts, Two Genuinely New, One Already Built

Specification §3 fixes three concepts this document must realize as mechanism, and states explicitly that they must not be conflated. Each is checked in turn against what this library has already built, rather than assumed to need a fresh mechanism.

### 3.1 A Halt Is the Identical Mechanism H41 Built and H42 Reused, Under a Third Name

Specification §3 defines a halt: *"A halt is the agent stopping the action: not completing it, not working around it, not partially applying it, and not retrying it against the same condition. Every request and every escalation begins with a halt."* `05-meta-operations/02-agent-loop-constraints.md` §8 defines a hard stop, read directly at this document's own front matter: *"A hard stop means the loop does not run a further iteration, is not worked around, is not partially continued, and is not resumed against the same condition."* `02-token-and-compute-budget-design.md` §9.1 already found "pause" (`05-meta-operations/03-token-and-compute-budget.md` §8) to be this identical mechanism under a second name, differing only in the unit described — a "pass" for the loop guard, an "envelope" for the budget mechanism.

**A halt is the same mechanism a third time, differing only in unit again.** All three definitions forbid the identical four behaviors — no completion, no workaround, no partial application, no retry/resumption against the same condition — and all three are produced by the identical write H41 §5.4 and §8.5 already fix: the acting event's `outcome` set to `halted-and-escalated`, at the identical interception point, through the identical mechanism. HITL's own unit is **the action** itself — narrower than "a pass" (which counts every iteration regardless of outcome) and narrower than "an envelope" (which measures accumulated resource), but the identical stopping behavior applied to it. **This document builds no third halt implementation.** Every halt this document's own mechanics produce or consume is H41's own hard-stop mechanism, exactly as H42 already found for "pause."

### 3.2 A Gate Is Genuinely New: a Timing Property H41's Classifier Already Carries, Newly Named

An **approval gate** (specification §3: *"an enumerated point at which autonomy stops and a gated action may proceed only once a human holding the required authority approves it. A gate is foreseeable and standing: the class of action is known in advance to require approval"*) is not a mechanism H41 or H42 built independently — but it is also not a mechanism this document must build from nothing. H41 §4.1's classification table already tests every proposed action against charter §7's eleven classes *before* that action executes, as a closed lookup fixed at design time. A "gate," realized as mechanism, is precisely **the property that a §7-classified match is detected before the action's effect, never after** — a property H41's own classification-then-precondition-gate ordering (§3 of that document: classification, "then" precondition clearing) already and necessarily has, since the precondition gate's own single interception point (H41 §5.4) sits strictly downstream of classification (§4 below states the composition precisely). This document's own contribution is naming this timing property explicitly as "the gate," and building what happens once a gate-match is detected (§5–§7) — not building the detection itself.

### 3.3 An Escalation Is Genuinely New: the Routing Act, Distinct From the Stopping Act

An **escalation** (specification §3: *"the act of handing a decision to a human whenever the autonomy boundary is reached — at a gate, on a breach, on an exhausted bound, or on an unresolvable conflict"*) is distinct from a halt in exactly the way the outcome vocabulary already keeps them distinct: a halt is *what happens to the action* (it stops); an escalation is *what happens to the decision* (it is handed to a human). H41 and H42 build the former completely; neither builds the latter — H41 §4.3 states this explicitly ("this document does not design how that request is made, routed, recorded, or resolved"), and H42 §9.3 states the identical boundary for its own exhaustion condition. **This is the one of the three concepts this document genuinely designs as a new mechanism** — §5 below is where it is built.

### 3.4 The Gate/Halt Split Governs Which Resolutions Are Legal, Not Which Mechanism Fires

Specification §5's own closing bullet (quoted in full in this document's front matter) splits the thirteen trigger rows into two groups by what a human may do once escalation reaches them: **seven gate-shaped rows** (Production promotion, residency-relevant action, mandatory security review, third-party vendor risk trigger, backward-compatibility break, architectural-decision change, scope expansion) admit all three resolutions of §7 — authorize, decline, redirect. **Four halt-shaped rows** (invariant breach, irreversible action, reaction past an autonomous bound, unresolvable conflict) admit only decline or redirect — never authorize, because authorizing would mean permitting continuation past a condition no human may waive (specification §3: *"A human decision never relaxes a guarantee... it never waives an invariant, a severity threshold, a residency obligation, or a quality floor"*). **The third-party vendor risk trigger's own placement in the gate-shaped group is reasoned against this identical criterion, not assumed by analogy to the other six** — the row was added to specification §5 after this bullet was originally written (`DECISIONS.md` D-46). Its own citation (`02-governance-and-security/09-third-party-risk-management.md` §5) invokes `01-system-invariants.md` §3's general blocking-check principle alone, never §4's nine numbered invariants — the identical textual distinction D-46 used to find this row genuinely distinct from "Invariant breach or possible breach" in the first place — and authorizing past an unresolved trigger waives no invariant (it is not one of the nine), no severity threshold (`10-third-party-risk-management-design.md` §5.2 evaluates its own four-tier vocabulary directly, explicitly never translated onto the security-policy severity scale), no residency obligation, and no quality floor. It is a business/operational risk judgment a human holding the required authority may knowingly accept — structurally identical to the already-gate-shaped mandatory security-review row, which likewise blocks release on an unresolved risk-tier finding (an unresolved Critical or High vulnerability) a human may authorize past. Two rows are not named by that bullet's own two example lists — "escalation-mandating runtime signal or incident" and "uncertainty whether a trigger fires" — and are resolved by direct evidence rather than by assumption: §9's inventory shows that `06-incident-response-and-recovery-design.md`'s own `restore-executed` event records `outcome = applied` against a recorded `approval_reference` (that document, §14, cited in full at §9 below) — direct evidence that a human *can* authorize a specific recovery action to proceed, placing the incident/signal row in the **gate** group for at least the subset of incidents a human may authorize past. Uncertainty (the thirteenth row) carries no resolution vocabulary of its own; it resolves by being treated as whichever trigger it is presumed to match (§7 below), inheriting that trigger's own resolution set.

**This split is realized as a field-level constraint on the resolution record itself (§6.1), not a rule stated in prose for a human to remember.** For the four halt-shaped classes, the `resolution` field's own legal value set excludes `authorize`; a write attempting it is refused by the mechanism, not merely discouraged by policy.

## 5. How Approval Is Requested and Recorded

### 5.1 "Before the Action, Never After" Is Structural, Not a Rule This Document Imposes

Specification §6 requires the request precede the gated action. This is already guaranteed by construction, not merely asserted here: H41 §4.3 fixes that a §7 match "routes the action to human approval" **at classification** — strictly upstream of the precondition-clearing gate's own single interception point (H41 §5.4), which is the only point in the kernel's pipeline that may write `outcome = applied` (H41 §16's own Binding Rule). An action that has been classified as requiring approval never reaches that interception point at all until a resolution (§6 below) permits it to. There is no code path by which a §7-matched or hard-stop-routed action reaches `applied` before this document's own mechanism has resolved it — the ordering is a structural consequence of H41's own pipeline shape, never a discipline this document must separately enforce.

### 5.2 The Request's Content Is a View Over Already-Assembled Evidence

Specification §6 requires a request carry "the triggering condition, the specific action awaiting authorization, the invariants and gates evaluated for it, its reversible path, and the context a human requires to decide." Every one of these facts is already assembled by the point this document receives the routed action (§4.2): the triggering condition and the matched row (H41 §4.1's own table), the invariants and gates evaluated (H41 §5.1's five reads, already performed up to whichever precondition the classification or hard-stop bypass fired at), and the reversible-path finding (the INV-08 check H41 §5.1 row 4 and §4.1's own irreversible-action row both already read). **This document's own request mechanism composes these already-computed facts into one record; it introduces no second evidence-gathering pass.** The one fact this document itself supplies, and the one genuine content this section owns, is **routing**: which human holds the required authority.

### 5.3 Routing Reads an Already-Fixed Authority, Never Invents a Role

Specification §6 requires routing "to a human actor whose grant covers the decision, consistent with the role-and-permission matrix and least-privilege default of `02-governance-and-security/03-access-control-and-tenancy-model.md` §5, §8." This document does not design a new authority mapping: charter §7's own table already names, per row, which document's own citation fixes the authority a given class requires — a Production-scoped grant for promotion (charter §7 row 1, citing the access-control model §8 directly), the residency approval gate's own authority for a residency-relevant action (`06-compliance-and-data-residency-design.md` §8), the mandatory-security-review authority for a security-review trigger (`04-security-controls-design.md` §5.2), and so on for every row. **This document's routing mechanism is a lookup into these already-fixed citations, never an independently invented org chart.** Where a matched row's own owning document does not name a specific authority (the residual, generically-classified rows — architectural-decision change, scope expansion, unresolvable conflict), routing falls to the platform steward authority the access-control model's own least-privilege default already reserves for undelegated platform-layer decisions — read, never assigned, by this document.

### 5.4 Never Assumed, Implicit, or Inferred From Silence

The pending record this document produces (§10) carries an explicit `status` that remains `pending` until an affirmative resolution write occurs. **No scheduled process, timeout, or default transition ever flips it.** A request left unresolved indefinitely remains `pending` indefinitely — the deny-by-default posture applied to duration as well as to outcome, exactly as specification §6 requires: "a timeout, a non-response, or an ambiguous signal is never treated as consent."

### 5.5 What Is Recorded, and by Which Mechanism

Three distinct facts are recorded, and this document is the sole author of exactly one of them:

| Fact | Recorded By | Event Type |
|---|---|---|
| The request (the trigger firing) | The **owning document's own mechanism** — H41's kernel for a generically-classified action, or the specifically-typed owning document (residency, contract, environment-management, release, incident-response) for one already carrying a dedicated type | `autonomous-change`, `residency-hold`, `residency-promotion-approval`, `contract-breaking-change-detected`, `stage-promotion`, or the matched row's own already-fixed type — never a type this document mints |
| The decision (authorize/decline/redirect) | **This document**, for every class not already carrying a dedicated decision type | `approval-resolution` (§11) — reused by every one of the thirteen rows unless a more specific type already exists (`contract-change-signoff`, `residency-promotion-approval`, a `stage-promotion` follow-on) |
| The resumed action, where authorized | The **owning document's own mechanism**, exactly as it already produces its own `applied`/`proceeded` outcome | The matched row's own type, `approval_reference` populated |

This document mints no type for the first or third rows — both already exist, per each owning document's own mechanism. It mints exactly one type, `approval-resolution`, for the second row, and only where no more specific type already carries it (§11 states the H26c test this passes).

## 6. How an Approval Is Resolved and Autonomy Resumes

### 6.1 The Resolution Vocabulary, Constrained by Trigger Shape

A resolution is one of **authorize**, **decline**, or **redirect** (specification §7). Per §3.4 above, `authorize` is not a legal value against a halt-shaped trigger (invariant breach, irreversible action, reaction past an autonomous bound, unresolvable conflict) — the `approval-resolution` event's own write path refuses that value for those four rows, structurally, never merely by convention. Every resolution is recorded before any further action proceeds, per specification §7's own ordering.

### 6.2 An Authorization Names Exactly the Action Requested — What May Be Assumed on Resumption

Specification §7 fixes that "On authorization, the agent may take only the action that was requested" and that the resumed action "re-clear[s] every precondition... as it resumes." This document states precisely what a resumed action may assume unchanged and what it must re-establish, because resumption is where an under-designed mechanism would quietly assume time has not passed.

**May be assumed, unchanged:**
- **The classification match itself.** The action's declared shape (§4.1 of H41) has not changed merely because time has passed while it waited; re-classifying an unchanged action would be exactly the redundant second test §4 above forbids.
- **The identity and authority of the approving human**, and the content of the decision itself — both already fixed, immutably, on the `approval-resolution` event.

**Must be re-verified, because state may have moved:**
- **Every one of H41 §5.1's five preconditions**, including the invariant-check record and the reversible-path finding specifically — an invariant-check record current at request time may no longer be current at resolution time, and H41's own gate refuses a stale or missing read exactly as it refuses an absent one (§5.2 there).
- **H42's own budget-sufficiency check**, since the task's or session's accumulators do not pause while an approval is pending — a resumed action that was affordable at request time may not be affordable at resolution time, and §9.3 there already routes an exhaustion discovered on resumption through the identical hard-stop mechanism, never bypassed by the existence of an unrelated, already-granted authorization.
- **H41's own loop-guard counters.** A resumed action still consumes one iteration; if the task's iteration or retry ceiling was reached by other work while this request was pending, the ceiling still governs, and an authorization granted before the ceiling was reached does not exempt the resumed action from it.
- **Whether a new, unrelated Critical or invariant-violating condition has since arisen.** H41 §7.3's bypass and `04-observability-and-monitoring-design.md` §6.4's identical bypass fire independently of any pending or granted approval; a new Critical condition discovered between request and resolution halts the resumed action exactly as it would halt any other, regardless of the authorization already recorded for the original condition.

**An authorization confers no standing authority.** It is not reusable for a different action, a later action, or a broadened version of the same action (specification §7) — mechanically, the `approval_reference` field is a point reference to the specific `approval-resolution` event, and a subsequent, distinct action's own attempt to cite the same reference fails the classification-and-precondition pipeline exactly as an absent reference would, because the resumed action's own declared shape (§4.1) would not match the one the resolution named.

### 6.3 A Decline or a Halt-Class Resolution Leaves the Work Stopped, Structurally

Where an action is declined, or where the trigger was a breach, an exhausted bound, or an unresolvable conflict, the work remains halted (specification §7). This document does not build a mechanism to prevent "seeking a different approver for the same declined request" — H41 §7.2's own repetition check already catches it: an attempt to re-raise the identical action against an unchanged condition is a repeat, not a legitimate retry, and terminates the loop before a second request could even be composed. This document composes with that existing guard rather than duplicating it.

### 6.4 The Resumed Action Is Newly Traced

Per specification §7's own closing bullet, the resumed action produces its own event, linked via `approval_reference` to the `approval-resolution` (or specifically-typed) decision event — the identical linkage pattern every one of the fourteen documents in §9 already applies for its own specifically-typed case (`contract-change-signoff` → the resumed `contract-breaking-change-detected` release; `residency-promotion-approval` → the released promotion; `stage-promotion`'s own second row). This document generalizes the pattern for the residual case; it does not invent a new one.

## 7. Default to Halt When a Trigger Is Ambiguous

### 7.1 Ambiguity Is a Structural Property of a Closed Lookup, Never a Judgment the Agent Must Recognize

The ticket's own instruction is decisive here: a default that depends on the agent correctly recognizing its own uncertainty is weaker than one that follows structurally. **This document builds no separate ambiguity-detection step.** H41 §4.1's own closing row already makes the classifier exhaustive by construction: *"Whether every row above resolves negatively; if any cannot be established, this row matches. The closing rule, not a tenth decidable condition."* A closed lookup with a catch-all final row that fires whenever every other row cannot be shown to not-match has no third outcome by which an action could silently proceed unclassified — every action either matches a specific row or falls to the uncertainty row, and both routes reach this document identically (§4 above). Ambiguity is therefore not a state this document must detect; it is a state H41's classifier cannot fail to detect, by the shape of the lookup itself.

### 7.2 Ambiguity in the Mechanics Resolves Identically, by the Same Structural Property

Specification §8 names three further ambiguities — which human holds the authority, whether an existing approval covers the action, whether a prior resolution remains valid — each resolving toward a fresh request rather than a favorable reading. Each is mechanical, not a judgment call:

- **Which human holds authority** is resolved by §5.3's lookup; where a matched row's own citation is absent or does not resolve to a specific authority, routing falls to the platform steward default (§5.3) — never left unrouted, and never resolved by guessing.
- **Whether an existing approval covers the action** is resolved by the `approval_reference`'s own point-reference shape (§6.2): a reference either resolves to an exact match on the resumed action's own declared shape, or it does not. There is no partial-match reading — an approval that does not name the identical action structurally fails to cover it, which is the mechanical form of "resolves toward halting and requesting a fresh decision" specification §8 requires.
- **Whether a prior resolution remains valid** is resolved by §6.2's own re-verification list: a resolution's own decision content is immutable and always valid for what it decided, but the *action it authorized* must re-clear every precondition on resumption regardless — so "is the resolution still valid" is never a question this document answers by re-litigating the human's decision; it is answered by whether the resumed action still clears the preconditions the resolution never exempted it from.

### 7.3 A Halt on Ambiguity Is the Identical Recorded Event

Per specification §8's own closing bullet, defaulting to halt is itself a consequential action, produced by the identical mechanism §3.1 above establishes — no new record shape for "ambiguity" specifically.

## 8. Preconditions Bind Every Request, Record, and Resumption — Not a Third Composition at H41's Interception Point

The ticket asks this directly: two documents (H41 itself, and H42) have composed at H41's single interception point (the transition from precondition-5-clearing to execution); is this document a third?

**No.** H42 extended *what must be true for any action to become `applied`* by adding an ANDed budget-sufficiency condition at that one point — a genuine extension of the gate's own content. This document does not extend that content further. Specification §4's own text states the boundary precisely: *"Requesting approval, recording a decision, and resuming an authorized action are each themselves autonomous actions, so every precondition of `05-meta-operations/01-agent-operating-charter.md` §5 binds them."* This is an instruction that **the request, the record, and the resumption are new instances of ordinary autonomous action** — each one clears the identical (H42-amended) five-precondition gate at the identical interception point, exactly as any other action does. None of the three needs a further, sixth condition of its own: composing a request breaches no invariant on its own account (specification §4's own bullet: never discloses a secret, another tenant's state, or crosses a region boundary "in the act of asking"), and this is enforced by the identical precondition 3 read (H41 §5.1) every other action already clears — not a new check this document adds to the gate.

**This document is a producer of new *actions* that pass through the existing gate, never an editor of the gate's own *content*.** The distinction matters because it is exactly the boundary H41 §16's own Binding Rule protects: "No other point in the kernel's own pipeline writes an `outcome` of `applied`." A request, a decision-record, and a resumption each still write through that one point, under the one (now twice-extended, by H42 alone) condition set — this document adds a third autonomous-action *kind*, not a third *condition*.

## 10. Where Approval State Lives — A New Structure Is Owed

Per the standing discipline every document in this library applies (`BACKLOG.md` §1i and its successors, most recently H41 §11 and H42 §10), every structure this document's mechanism might plausibly need is checked against `02-platform-data-model-design.md` §3.1 before any new one is proposed — and, per the ticket's own instruction, this check reaches a different conclusion than H41's and H42's.

### 10.1 Why the Working-State Finding Does Not Transfer

H41 and H42 each found their own live counters and accumulators to be ephemeral, per-task or per-session working state, correctly hand to `05-agent-state-and-memory-design.md` rather than to the platform's persistent schema. **A pending approval is not that shape of fact**, for three reasons specific to this mechanism:

- **It must outlive the agent session, and often the task, that raised it.** A counter's live value is meaningless once its owning task ends; a pending approval remains meaningful — and must remain resolvable — for as long as no human has acted on it, independent of whether the raising session, task, or even the raising agent process, still exists.
- **It must be findable by the human who resolves it, not only reconstructable by the agent that raised it.** Every candidate H41 and H42 checked was working state a *resuming agent process* needed to read back. A pending approval must instead be *discoverable by a human* who was never party to the raising session — a fundamentally different access pattern the audit stream alone does not serve (below).
- **Its resolution must be durable and independently queryable**, not merely reconstructable after the fact from a full-stream scan.

### 10.2 Why the Audit Stream Alone Does Not Discharge the Need

`08-audit-and-traceability-design.md`'s own `audit_events` tables (§6.1 there) are append-only, per-tenant or platform-global, and carry no update privilege at all (§6.2). The triggering event (`held-pending-approval`) and the eventual resolution event are each captured there, durably and immutably — but **finding "every currently-pending approval a given human is authorized to resolve" from that store alone requires an anti-join scan for every unresolved trigger across every stream that human's authority spans**, which for a platform steward (whose authority, per `02-tenant-isolation-and-access-control-design.md` §4, "operates above all tenants") means scanning every tenant's own stream plus the platform-global one on every check — an access pattern this design's own tenant-isolation discipline treats as exceptional, never as a routine read path. The audit stream also carries no field naming *which human or role* a given pending request is routed to (§5.3's routing determination) — only what happened, never who must still act. A structure that is queryable by "what is outstanding, and for whom" is genuinely absent, and inventing a full-stream-scan workaround would be exactly the kind of second, competing mechanism this library's own discipline forbids building where a direct structure is warranted instead.

### 10.3 The Obligation, Stated Precisely

**Binds `02-platform-data-model-design.md` to a new structure — a platform-global, cross-tenant-safe pending-approval record — for discharge in a future, separately-ticketed amendment, on the identical shape `06-incident-response-and-recovery-design.md` §6.2 already used for its own fifth provisioning obligation to `01-environment-and-configuration-design.md`: never designed or provisioned here, but named precisely enough to be actionable.** The structure must carry, at minimum: an identifier; the matched trigger row (one of specification §5's thirteen); a reference to the raising `autonomous-change` or specifically-typed event (never a duplicate of that event's own content); the resolved required authority (§5.3); a `status` that is `pending` until an explicit resolution write and is never auto-transitioned (§5.4); and, once resolved, a reference to the `approval-resolution` (or specifically-typed decision) event that closed it. It is placed in the `platform` schema — never a per-tenant schema — because the majority of this document's own triggers are platform-layer (charter §7's own eleven classes bind the agent's platform-layer conduct, per specification §2), and a platform-global placement is what makes a steward's cross-tenant authority a structural property of the read path rather than a scan every check must repeat; a nullable tenant reference accommodates the minority of triggers (residency, a tenant-scoped incident) that concern one tenant's own data, on the identical pattern `platform.applications.region_of_record`(nullable) already establishes for an optional, per-row scoping fact.

**Finding: this document owes one new structure, precisely because the requirement it must satisfy — durable, cross-session, human-findable, independently resolvable — is a genuinely sharper requirement than the working state H41 and H42 both correctly declined to escalate into schema.** The check ran identically to theirs; the answer differs because the fact being checked differs.

## 12. Design Decision Records

### 12.1 ADR-054 — Trigger Enforcement Consumed From H41's Kernel, a Halt Confirmed as H41's Mechanism a Third Time, One New Decision Event Type, and a New Cross-Session Pending-Approval Structure

- **Status:** Approved (`DECISIONS.md` D-47, 2026-08-18).
- **Cost to reverse:** **High**, matching `implementation-document-map.md`'s own pre-assigned grade for this document — "the approval-trigger set and its recorded evidence; actions already taken autonomously under a superseded trigger set cannot be re-gated." Reasoned independently, as a genuine irreversibility rather than a configuration cost: once an action has been permitted to proceed — either autonomously, because it did not match any trigger under the trigger-set version then in force, or via an `approval-resolution` authorizing it — that action's own `outcome = applied` (or `proceeded`) is written once, to an append-only stream (`08-audit-and-traceability-design.md` §6.2), and stands permanently. If the trigger set is later found ambiguous or wrong and revised, the revision changes only which *future* actions match which row; it cannot reach back and re-classify an already-completed action, because doing so would mean editing a record this library's own append-only discipline forbids editing, and because the action's own real-world effect (a promotion already made, a change already merged, a recovery already executed) is not itself reversible merely by relabeling the classification that permitted it. This is distinct from, and more severe than, a schema-migration cost: reversing a *trigger-set* decision does not touch stored data at all, yet the actions taken under the superseded version remain permanently outside the corrected mechanism's reach — an asymmetry no lower grade captures.
- **Upstream decisions assumed:** ADR-052 (`01-agent-runtime-and-control-design.md` §13.1 — the classification step, the precondition-clearing gate and its single interception point, and the hard-stop mechanism this document consumes rather than rebuilds); ADR-053 (`02-token-and-compute-budget-design.md` §12.1 — the second document to compose at H41's interception point, and the pause/hard-stop identity this document extends to a third name); ADR-025 (`08-audit-and-traceability-design.md` §10.1 — the consolidated event model, the `approval_reference` field, and the `held-pending-approval`/`halted-and-escalated` outcome split this document's records populate). ADR-025, ADR-052, and ADR-053 remain Provisional; this decision depends on their already-designed content, never their approval status (`PROCESS.md` §12.2).
- **Verified vs. reasoned:** Reasoned throughout. No claim asserts any notification system's, identity provider's, or agent framework's current capability; every mechanism (the trigger-to-mechanism mapping, the gate/halt resolution-vocabulary split, the resumption re-verification list, the pending-approval structure's own fields) is a structural argument from the cited specification and the already-designed upstream documents' own content.
- **Question this answers:** Given a specification that defines an approval gate, an escalation, and a halt as three distinct concepts, a kernel that already classifies every proposed action against the identical closed trigger set this specification enumerates, a second document that already found "pause" to be that kernel's hard-stop mechanism under a different name, and fourteen already-written documents that have each routed an approval, escalation, or authorization point here with expectations that do not all describe the same kind of trigger — which of the three core concepts are genuinely new mechanisms this document must build, and which are further instances of a mechanism already built; does this document test a proposed action against the trigger set independently, or consume an already-built test; what must a resumed action re-verify that it may not simply assume from its own prior request; and does the approval state this document produces fit the working-state shape two prior documents in this layer already declined to escalate into schema, or does it genuinely differ?
- **Criteria applied, and how each resolved:**
  1. *Is a halt a mechanism this document must build, refine, or reuse unchanged?* Decisive for reuse unchanged (§3.1) — the loop-constraints specification's hard-stop definition, read directly rather than from a secondary quotation, is behaviorally identical to the HITL specification's own halt definition, differing only in the unit described (a pass, an envelope, an action) exactly as H42 already found for a second pair of these three definitions.
  2. *Does trigger enforcement require a second classifier, or does H41's existing lookup — together with `10-third-party-risk-management-design.md`'s own, for the one row outside H41's reach — already cover the full set this document must enforce?* Decisive for full coverage via already-built mechanisms, never one this document invents (§4) — twelve of HITL §5's thirteen rows are covered by H41 alone: eleven are charter §7's own eleven, already tested by H41 §4.1's closed lookup, and the twelfth (unresolvable conflict) is not a charter §7 row at all, reaching this document through H41's hard-stop mechanism instead, never through classification. The thirteenth (third-party vendor risk trigger, `DECISIONS.md` D-46) is neither — it reaches this document through `10-third-party-risk-management-design.md` §4.4's own already-built tiering and monitoring mechanism, consumed exactly as H41's two are, never re-tested.
  3. *Does this document compose a further condition at H41's single interception point, becoming a third extension alongside H42, or does it produce new instances of ordinary autonomous action that clear the existing (H42-amended) gate unchanged?* Decisive for the latter (§8) — specification §4's own text frames requesting, recording, and resuming as themselves autonomous actions subject to the existing preconditions, never as a license to extend the gate's own content a second time.
  4. *Does a builder-facing or steward-facing approval gate that reuses this document's request/record/resolve vocabulary thereby become a thirteenth enumerated trigger this document's own trigger-enforcement must test for?* Decisive for no (§9.1) — both cases reuse this document's general-purpose mechanics by explicit structural analogy the owning document itself drew, but neither action is ever routed through H41's kernel, because neither is the autonomous agent's own conduct; conflating "composes with this mechanism" with "is an enumerated trigger" would misstate what this document's own classification-consumption (§4) actually tests.
  5. *Does the pending-approval state this document produces fit the ephemeral, per-task working-state shape H41's and H42's own counters and accumulators already fit, or does it genuinely differ?* Decisive for genuine difference (§10) — a pending approval must outlive the raising session, be findable by a human who was never party to that session, and be independently resolvable, none of which any working-state candidate H41 or H42 checked needed to satisfy; a new platform-global structure is owed, not a flat non-obligation borrowed from their precedent.

- **Decision:** (1) A halt is H41's own hard-stop mechanism reused a third time, under a third name, for a third unit (an action); this document builds no third implementation (§3.1). (2) A gate is the timing property H41's classification-then-precondition-gate ordering already has; an escalation is the one genuinely new mechanism this document designs — the routing act, distinct from the stopping act (§3.2–§3.3). (3) Trigger enforcement is fully consumed from already-built upstream mechanisms, never invented here — H41's classification table for eleven rows, its hard-stop mechanism for the twelfth (unresolvable conflict), and `10-third-party-risk-management-design.md`'s own tiering and monitoring mechanism for the thirteenth (third-party vendor risk trigger) — and this document performs no independent test of any of the three (§4). (4) The request's content is a view over evidence H41's own gate already assembled; this document's own genuine contribution is routing to the required authority, read from each trigger's own already-fixed citation, never an invented role (§5). (5) A resumed action may assume its own classification match and the decision's own content unchanged, but must re-verify every precondition, the budget-sufficiency check, the loop-guard counters, and any newly-arisen Critical condition, none of which a prior authorization exempts it from (§6). (6) Ambiguity is detected structurally, as the closed lookup's own catch-all row, never as a judgment the agent must recognize (§7). (7) This document is not a third composition at H41's single interception point; it produces new instances of ordinary autonomous action that clear the existing, H42-amended gate unchanged (§8). (8) The consolidated inventory reconciles fourteen documents' expectations, finding two — a builder-facing promotion gate and a steward's exceptional-access grant — that reuse this document's mechanics without being instances of any enumerated trigger, stated as a reconciliation rather than assumed away (§9). (9) A new platform-global pending-approval structure is owed to `02-platform-data-model-design.md`, for the sharper cross-session, human-findable, independently-resolvable requirement this mechanism carries beyond H41's and H42's own working-state findings (§10). (10) Exactly one new audit-event type, `approval-resolution`, is minted for the residual decision case no existing type already carries (§11).
- **Alternatives considered:** *Building a dedicated ambiguity-detection step, separate from H41's classification table* — rejected under criterion 2; H41's own closing row already makes the lookup exhaustive by construction, and a separate detector would be a second, redundant test of the identical closed-lookup property. *Treating a builder-facing or steward-facing approval as a thirteenth enumerated trigger, to avoid stating an exception* — rejected under criterion 4; it would misrepresent what this document's own trigger-enforcement mechanism (§4) actually consumes, and would silently expand the closed set charter §7 and specification §5 both fix without authority to do so. *Extending H41's single interception point with a third ANDed condition, by analogy to H42's own extension* — rejected under criterion 3; specification §4's own text frames this document's own actions as ordinary autonomous actions subject to the existing gate, never as license for a further extension the specification does not itself require. *Treating the pending-approval state as ephemeral working state, on the same finding H41 and H42 reached for their own counters* — rejected under criterion 5; the cross-session, human-findable, independently-resolvable requirements are not properties any working-state candidate those two documents checked needed to satisfy, and forcing the finding to match theirs would leave a genuine gap the audit stream alone cannot close (§10.2). *A dedicated, per-tenant pending-approval table, mirroring the isolation-first placement of most tenant-scoped structures in this library* — rejected in §10.3; the majority of this document's own triggers are platform-layer, and a per-tenant placement would force a steward's already-established cross-tenant authority into a multi-schema scan on every check, the identical access-pattern cost §10.2 identifies as the reason the audit stream alone is insufficient.
- **Consequences:** Confirms, and alters none of, `01-agent-runtime-and-control-design.md`'s classification step, precondition-clearing gate, precedence engine, and hard-stop mechanism; `02-token-and-compute-budget-design.md`'s accumulator-and-ceiling mechanism and its own pause/hard-stop finding; and `08-audit-and-traceability-design.md`'s consolidated event model — each document's own content stands exactly as already designed. Binds `02-platform-data-model-design.md` to the new pending-approval structure named in §10.3, for discharge in a future, separately-ticketed amendment. Binds `05-agent-state-and-memory-design.md` (not yet written) to nothing beyond what H41 and H42 already bound it to — this document's own approval state is platform-schema content, not working state that document owns. Adds exactly one new `event_type`, `approval-resolution`, to `08-audit-and-traceability-design.md`'s model, reusing every other field and outcome value already fixed there.

## 15. Binding Rules

These rules hold for every element of this document and are subordinate to the specification and the charter.

- **A halt is H41's own hard-stop mechanism, reused unchanged under this document's own name.** No third halt implementation is ever built here; every halt this document produces or consumes is the identical mechanism H41 built and H42 already reused.
- **This document performs no independent test of a proposed action against the trigger set.** Every trigger match reaches this document through one of exactly two already-built H41 mechanisms — its classification table, or its hard-stop mechanism — never a third test this document invents.
- **A gate admits authorize, decline, or redirect; a halt admits only decline or redirect.** The resolution record's own legal-value set is constrained by which of the two groups the matched trigger falls in, enforced structurally, never left to a resolver's own judgment.
- **An authorization confers no standing authority and is never assumed to survive unchanged.** A resumed action re-verifies every precondition, the budget-sufficiency check, the loop-guard counters, and any newly-arisen Critical condition; only the classification match itself and the decision's own content may be assumed unchanged.
- **Ambiguity is a structural property of a closed lookup, never a judgment the agent must recognize.** The uncertainty row of H41's own classification table, and the identical closed-lookup discipline applied to every mechanical ambiguity in resolution, together make silent, unclassified passage structurally impossible.
- **This document is not a third composition at H41's single interception point.** Its own request, record, and resumption actions are ordinary autonomous actions that clear the existing, H42-amended gate unchanged; none of them adds a further ANDed condition to that point.
- **A mechanism reused by a document outside this document's own trigger set is not thereby a fourteenth enumerated trigger.** Composing with this document's request/record/resolve mechanics is distinct from matching one of specification §5's thirteen rows, and the two are never conflated (§9.1).
- **A pending approval is platform-schema content, never working state.** It must outlive the raising session, be findable by a human who was never party to it, and be independently resolvable — properties no working-state candidate this library has checked elsewhere needed to satisfy.
- **This document mints exactly one new audit-event type.** `approval-resolution` covers every trigger class no existing, more specifically-shaped type already carries; it introduces no second vocabulary for what an existing type already expresses.
- **The boundary against every not-yet-written Layer 6 sibling and the one cross-layer dependent is stated from this document's own side, and none may proceed as though this document's own mechanisms were still open for it to shape.**
- **Everything in this document remains platform-layer only.** No trigger, gate, or resolution rule governs an approval flow a builder configures inside their own built artifact; the builder/built separation the specification's own §2 fixes holds throughout.
