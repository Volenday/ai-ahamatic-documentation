## 3. Budget, Envelope, and Exhaustion — Realized as Mechanism

Specification §3 fixes the concepts; this section fixes the concrete structures that make each one operational inside the kernel H41 already built.

### 3.1 The Accumulators

For every task, and for the session it belongs to, the kernel maintains one **token accumulator** each — a running total of measured token consumption, reset to zero at task start (the task accumulator) or at session start (the session accumulator, §6.2 below). This is the concrete form of specification §3's "envelope": the token, compute, and cost budgets that "apply to it at once" are realized as exactly one metered, ceilinged quantity per scope — never three parallel running totals — for the reason §5 below states.

### 3.2 The Ceilings

Each accumulator is compared against a **configured ceiling** — a task ceiling and a session ceiling, distinct values, never a single figure applied to both. §4 below states precisely why this value is configured rather than a constant baked into the comparison, and what its current setting is.

### 3.3 Exhaustion, Realized

**Exhaustion** (specification §3: *"An envelope reaching or being unable to stay within its ceiling — the point at which no further consumption may proceed autonomously"*) is realized as either of two conditions, each sufficient alone: the accumulator's current value has reached its configured ceiling, or the accumulator's value cannot be established (the metering instrument an action's own execution channel produces did not report a usable figure). The second condition is the identical deny-by-default posture the specification's own §8 fixes for this exact case (*"Uncertainty about whether an envelope is exhausted resolves to pausing"*) and is never treated as a favorable default.

### 3.4 What Is Not a New Structure

No third concept — "budget," "envelope," or "cost-per-action accounting" — gets its own independent mechanism beyond the accumulator-and-ceiling pair above and the derivation rule of §5. This is the direct realization of specification §3's own closing distinction: *"A budget is a count of resource, distinct from the count of passes"* — the accumulator counts resource; H41's iteration and retry counters (already built, §6 below) count passes; neither this document nor H41 conflates the two.

## 4. The Ceilings and Their Epistemic Status

### 4.1 The Current Setting

`03-software-and-architecture/06-non-functional-requirements.md` §10 currently sets the per-task token ceiling at ≤ 500,000 tokens and the per-session token ceiling at ≤ 2,000,000 tokens (stated there as 4× the per-task figure). This document keys to those values and mints no number of its own, per specification §5's own boundary bullet: *"The concrete value is a number owned elsewhere... This document keys to those values and mints no number of its own."*

### 4.2 A Configured Value, Not a Constant the Mechanism Assumes

That same NFR document's §13 Binding Rules states plainly: *"Three of §10's values are judgments, not derivations, and revise on first operating data. The iteration ceiling and both token envelopes carry no specification-fixed basis and no empirical benchmark; they are initial figures, revisable once real operating data exists, and must never be cited as though derived."* Both token envelopes this document keys to are two of those three judgment values. The mechanism this document builds is therefore designed so that a revision to either figure changes exactly one read value, never the comparison logic, the accumulator structure, or any downstream composition point: the ceiling is a **configured value** the accumulator-comparison mechanism (§3.2) reads at evaluation time — sourced from NFR §10's current setting — never a literal number inlined into the comparison itself. This is the identical discipline H41's own loop guard already applies to the iteration and retry ceilings (§8.1 there: *"each compared against its own ceiling from `03-software-and-architecture/06-non-functional-requirements.md` §10 — iterations ≤ 10, retries ≤ 3"* — a read, not an inlined constant), extended here to the two values NFR §10 marks as judgments specifically.

### 4.3 Why This Matters Here Specifically

H41's own iteration and retry ceilings share the identical judgment status (NFR §13's rule names "the iteration ceiling and both token envelopes" together, three of six §10 values). H41 already carries that status correctly by reading a configured value rather than an inlined constant. This document does the same for its own two ceilings, and states the reason explicitly rather than only by precedent: a mechanism that hard-codes a judgment value invites exactly the citation drift `BACKLOG.md` §1w's family already catalogs — a number repeated in prose eventually diverges from the source it was drawn from. Reading the value at evaluation time, from the one place NFR §10 owns it, forecloses that drift by construction.

## 5. Cost Is Derived, Not a Third Independent Envelope

### 5.1 What the Map Row Already Settled

`implementation-document-map.md`'s own row for this document states the cost ceiling is *"derived from the token envelope at the prevailing rate — not independently fixed"* (`03-software-and-architecture/06-non-functional-requirements.md` §10's table, the identical wording). `DECISIONS.md` D-24's own criterion 6 reasons this narrowing explicitly: *"the token envelope is the real bound; cost follows at the prevailing rate"* — recorded, in that same entry's own words, "as a narrowing, not presented as compliance." This document realizes that narrowing as mechanism, not merely restates it: cost is never independently accumulated or independently ceilinged anywhere in this design.

### 5.2 Why Compute Collapses Into the Token Measure Too

The specification's own §3 requires three budgets that "move together." NFR §10's table, however, assigns a concrete figure to exactly one of the three: its own "Quantifies" column states that the ≤ 500,000-token and ≤ 2,000,000-token rows each quantify the **"Per-task token, compute, and cost envelope"** and **"Per-session token, compute, and cost envelope"** respectively — one number, stated as the quantification of all three named resources at once, not a token-only figure standing beside two others still to be fixed. No NFR §10 row assigns compute an independent figure. This document reads that absence as a deliberate finding rather than a gap to fill: for the platform's own kernel, an autonomous action's compute expenditure is realized entirely as the inference work performed over the tokens that action processes — there is no compute unit this kernel expends independently of processing tokens for it to meter separately. **This document therefore maintains exactly one metered, ceilinged accumulator pair per scope (§3.1) — the token accumulator — never a second, independent compute accumulator or ceiling.** Compute is bounded exactly when and because token consumption is bounded; no NFR gap is flagged to the spec-phase change process here, because NFR §10's own Quantifies wording already resolves the question this document would otherwise have had to ask.

### 5.3 Cost as a Derived Reading

Cost-per-action accounting (specification §6) is realized, for the cost dimension specifically, as a **read-time computation** over the token accumulator's own value — `cost = accumulated tokens × a configured rate` — never a value this document itself accumulates, compares against a ceiling, or gates an action on. The rate value is an externally supplied configuration this document does not source, verify, or embed: naming a concrete figure would assert a time-sensitive, vendor-specific fact the Writing Rules for this ticket forbid, and doing so would also contradict D-24's own criterion 6 reasoning that a currency figure "would date on the next pricing change... entirely external to the platform." Cost therefore has no exhaustion condition, no accumulator, and no pause-and-escalate trigger of its own: reaching the token ceiling (§4) is the only exhaustion condition either the token, the compute, or the cost dimension of the envelope ever produces, consistent with specification §5's own binding rule that "reaching a ceiling ends autonomy" — there being exactly one ceiling to reach.

## 6. Composition With the Kernel's Counter Architecture

### 6.1 A Different Quantity, the Same Timing

H41's kernel maintains exactly two per-task counters — iteration and retry (§8.1 there) — each a **count of passes**. This document's accumulators (§3.1) are a **count of resource**, the distinction specification §3's own closing bullet fixes (*"A budget is a count of resource, distinct from the count of passes"*). The two mechanisms are never merged: this document introduces no third value into H41's shared iteration counter, and H41's iteration counter is never read as a proxy for token consumption.

The two mechanisms nonetheless share **timing**, not **value**: H41 §7.1 fixes that *"Each pass through §4–§5's pipeline is one iteration, counted regardless of the outcome (proceed, refuse, halt)."* This document's token accumulators are metered and updated at the identical per-pass boundary — once per iteration — but by the **actual measured token count that specific action drew**, never by a fixed +1. "Per iteration" describes *when* the accumulator is touched; "a different quantity" describes *what* value accrues and against what ceiling it is compared.

### 6.2 Task and Session Scope, Bound Together

Specification §5's own nesting rule — quoted in full in this document's front matter — requires the per-task and per-session accumulators to bind together: every measured consumption increments **both** accumulators simultaneously, the identical dual-increment shape H41 already uses for retry passes (H41 §8.1: *"every retry pass increments both counters simultaneously"*). A task can exhaust the session accumulator's ceiling while remaining within its own task ceiling, exactly as the specification states; when that happens, the current task ends exactly as a task-ceiling breach would, and — because the session accumulator persists across every task the session contains (§10 below states this precisely) — no further task in that session begins autonomously until the exhaustion is resolved through escalation (§9).

### 6.3 Whichever Bound Is Reached First — No Ordering, No Priority

The specification is explicit that the budget envelope and the iteration/retry ceilings are parallel, independent bounds: §5's own text states *"Reaching a budget ceiling is a limit breach under that document's §8 exactly as reaching the iteration ceiling is; whichever bound is reached first ends autonomy."* This document's mechanism realizes that as two structurally independent tripwires evaluated at the same per-iteration boundary, neither depending on the other's state: a task may end because its iteration counter reaches 10 while its token accumulator sits far below 500,000, or because its token accumulator reaches 500,000 on iteration 3 of 10. Both conditions are checked identically and neither is evaluated first as a precondition to checking the other — there is no ordering rule between them because none is warranted: whichever condition is true first fires the identical hard-stop mechanism (§9.2), and the surviving accumulator or counter values are simply irrelevant to that outcome.

### 6.4 What Observability Already Covers Without Extension

`04-observability-and-monitoring-design.md` §3.2 already instruments "every runtime invariant, guardrail-metric, and non-functional target" as "a current-value gauge per target," and its §4.1 fixes the tag mechanism reading that instrumentation as including "a non-functional-target identifier (`06-non-functional-requirements.md` §4–§10)" — a range that already includes §10, where this document's own two ceilings live. **This document's accumulators are therefore already within observability's own already-designed instrumentation scope, and this document owes that mechanism no extension.** This is a check, not an assumption: the accumulator's current value is exactly the shape of fact that document's own §3.2 row already names, tagged to the identical NFR §10 target identifier that document's own severity lookup already resolves — no new signal class, no new tag, and no amendment to that document's own text.

## 7. Where the Budget Check Sits — Composed at H41's Interception Point, Never a Sixth Precondition

### 7.1 The Question, Answered Directly

**The budget check is a separate check, composed at the identical interception point H41 already fixed — never a sixth row appended to charter §5's five-precondition table.**

Specification §4's own text states that *"every precondition of `05-meta-operations/01-agent-operating-charter.md` §5 binds [every consuming action]"* — this is a statement that the five preconditions apply to a consuming action exactly as they apply to any other autonomous action, not an instruction to add a sixth precondition, and the specification's own closed-list framing of charter §5 (which H41's §5.1 already realized as exactly five ordered, short-circuiting reads) gives this document no authority to extend that table. Doing so would be precisely what this ticket's Writing Rules forbid: silently adding a precondition to another document's gate.

### 7.2 The Composition, Precisely

H41 §5.4 fixes the mechanical interception point as *"the transition from precondition 5 clearing... to the action's own execution,"* and that document's own §16 Binding Rule states *"No other point in the kernel's own pipeline writes an `outcome` of `applied`."* This document's budget-sufficiency check is composed at that **identical** point, immediately after precondition 5 has cleared and immediately before the write of `outcome = applied`: it does not introduce a second point in the kernel's pipeline that could write `applied` — it adds a further condition that must also hold at the one point that already does. Where the five preconditions clear but the budget-sufficiency check does not, the transition to `applied` does not occur; the identical `halted-and-escalated` outcome fires instead (§9.2), through the identical mechanism H41 already built for a precondition-5 failure — never a second halt vocabulary.

### 7.3 What the Sufficiency Check Evaluates

Consistent with specification §7's graceful-degradation rule (*"Where the remaining budget cannot cover an action through to a safe, reversible, traceable stopping state, the action is not begun autonomously"*), the check compares the action's **projected** consumption against the accumulator's remaining headroom under both the task and session ceilings. This document does not design a separate cost-estimation instrument: the projection is a reasoned estimate drawn from the task's own already-measured per-action consumption so far (§6.1's accumulator updates supply the only history available); for a task's first action, no such history exists and the check accordingly passes on the only basis available, a limitation stated honestly rather than papered over with an invented default.

### 7.4 What Composing Here Costs

Extending H41's own single interception point with an additional, ANDed condition is not free of consequence, and the cost is named explicitly rather than absorbed silently: **the transition H41 described as governed by "all five preconditions... have cleared in full" now also depends on this document's own sufficiency finding** — a fact H41's own text did not, and could not, state when it was written, since this document did not yet exist. This document's own composition is the discharge of the obligation H41's ADR-052 Consequences already named: *"Binds `02-token-and-compute-budget-design.md` (not yet written) to feed a limit breach into this document's own identical hard-stop mechanism (§8.4), never a second stop mechanism."* The cost is borne entirely by this document, in the form of the dependency stated here (§13); H41's own text is not amended, and no second interception point is introduced anywhere in the kernel's pipeline.

### 7.5 The Post-Execution Case — No Retroactive Edits

The projection in §7.3 is an estimate, and a projected-sufficient action's actual measured consumption (§6.1) can push an accumulator past its ceiling once the true figure is known. Because the audit record is append-only (`08-audit-and-traceability-design.md` §6.2: *"The only permitted write to an `audit_events` table is an insert"*), the action's own already-finalized `applied` outcome is never revisited. Instead, an accumulator crossing its ceiling as a result of actual (rather than projected) consumption governs only the **next** iteration: the sufficiency check of §7.2–§7.3 is evaluated again at the next iteration's own interception point, finds the ceiling already reached, and refuses to admit that iteration to execution — producing a new `halted-and-escalated` event exactly as any other ceiling breach does (§9.2), never an edit to the record already written for the action that caused the crossing.

## 8. Degrade Gracefully Near a Limit

### 8.1 What "Near" Means, Mechanically

Specification §7 requires the agent to narrow consumption "as accrued consumption approaches a per-task or per-session ceiling," without fixing a percentage. This document does not invent one. **"Near a limit" is realized as the identical, action-relative sufficiency test §7.3 above already performs on every iteration** — an action is refused not at some fixed fraction of the ceiling, but the moment remaining headroom cannot cover that specific action's own projected consumption through to a safe, reversible, traceable stopping state. This satisfies the Writing Rules' own instruction that the mechanism "stay correct when the numbers change": because the test is relative to remaining headroom and an action's own projected cost, it requires no re-tuning when NFR §10 revises either ceiling — a global percentage threshold would have needed a second configured value this document would then also have had to keep synchronized with the ceiling itself.

### 8.2 Degradation Narrows Which New Work Is Considered, Never How It Is Checked

**Degradation reduces ambition, never a guarantee** (specification §7's own words). This document realizes that as a rule about the classification step, not the checks: as headroom narrows, the kernel proposes fewer new actions — preferring to complete or safely close out work already in flight — but every action it does propose, degraded state or not, clears the identical five-precondition gate (H41 §5), the identical budget-sufficiency check (§7.2–§7.3 above), and produces the identical minimum trace. **No degraded-mode action ever takes a cheaper or parallel path through the kernel.** The only variable degradation touches is *how many* new actions the agent is willing to begin; it never touches *how* an already-proposed action is evaluated. This is what keeps degradation from becoming, in the ticket's own words, "a quiet reduction in correctness": there is no code path by which insufficient headroom weakens a check rather than simply narrowing what is attempted.

### 8.3 Reaching a Safe State Before the Ceiling

Where the sufficiency check of §7.3 finds no candidate new action fits within remaining headroom, the agent does not attempt one; per specification §7, it "reaches a clean stopping point and escalates rather than starting work that would exhaust the envelope mid-flight" — the identical pause-and-escalate mechanism §9 below fixes, invoked proactively, before the ceiling is technically breached, rather than only reactively once it is.

## 9. Mandatory Pause and Escalate on Budget Exhaustion

### 9.1 Pause and Hard Stop Are the Identical Mechanism Under Two Names

The ticket asks whether "pause" (specification §8) is distinct from the loop-constraints specification's "hard stop," or the same mechanism. **They are the same mechanism, realized once, in H41's kernel, under two specification-level names.** The two definitions are checked side by side:

| Specification | Definition (quoted) |
|---|---|
| `05-meta-operations/03-token-and-compute-budget.md` §8 | *"A pause means autonomous consumption stops: no further action draws against the exhausted envelope, the stop is not worked around, and consumption is not resumed against the same envelope."* |
| `05-meta-operations/02-agent-loop-constraints.md` §8 | *"A hard stop means the loop does not run a further iteration, is not worked around, is not partially continued, and is not resumed against the same condition."* |

Both forbid further autonomous action against the triggering condition, both forbid working around the stop, and both forbid resumption against the identical condition — differing only in whether the described unit is a "pass" (loop constraints) or an "envelope" (this document's own budget), the identical distinction §6.1 already draws between the two mechanisms' quantities. H41 §8.4 already anticipated this by name — *"the hard-stop mechanism is shared across all named limits; only which document owns the concrete ceiling differs"* — and this document's own exhaustion condition (§3.3) is exactly the additional named limit that reservation was written for. No second hard-stop implementation is built here.

### 9.2 The Mechanism, as Realized

On exhaustion (§3.3), whether detected proactively (§8.3) or at the sufficiency check of §7.2–§7.3, the identical composition H41 already fixes for every ceiling breach fires: the acting `autonomous-change` event's `outcome` is set to `halted-and-escalated`, with `what_was_inspected` naming the specific limit that fired — "the per-task token envelope" or "the per-session token envelope" — extending the identical naming convention H41 §8.5 already uses for the iteration and retry ceilings, the oscillation check, and the progress check. No new outcome value, no new event shape, and no second escalation vocabulary is introduced.

### 9.3 Escalation Is Mandatory, Never Worked Around

Consistent with specification §8's own rule that escalation past an exhausted envelope is mandatory — including where a self-correction attempt would otherwise draw against it — an exhausted accumulator routes the triggering condition to `03-human-in-the-loop-design.md` (Layer 6, not yet written) exactly as H41's own classification table already routes "any reaction past the autonomous bound" (H41 §4.1) to that same mechanism. This document does not design the request, routing, or recording of that escalation; it supplies the triggering fact and the exhausted envelope's identity, exactly as H41's §4.3 already establishes for every class this document's mechanism could match.

- **Status:** Provisional — Pending Lead Approval.

No claim asserts any model's, agent framework's, or pricing model's current capability or rate; every mechanism (the accumulator-and-ceiling comparison, the token-as-sole-metered-dimension finding, the sufficiency projection, the composition at H41's existing points) is a structural argument from the cited specification and the already-designed upstream documents' own content.
- **Question this answers:** Given a specification that names three budgets — token, compute, and cost — that "move together," an NFR table that assigns a concrete figure to only one of the three and marks that figure a revisable judgment rather than a derivation, a kernel whose own precondition gate is already a closed, five-row table this document may not silently extend, and a kernel whose own hard-stop mechanism already reserved a composition point for exactly this document's ceiling — how many independently-metered accumulators does this design actually need; how does the mechanism stay correct when the judgment values it depends on are later revised; where does a budget-sufficiency check sit relative to a five-precondition gate this document does not own; and is a "pause" a mechanism this document must separately build, or one H41 already built under a different name?
- **Criteria applied, and how each resolved:**
  1. *Does compute warrant its own independently-tracked accumulator and ceiling, or does it collapse into the token measure?* Decisive for collapse (§5.2) — NFR §10's own "Quantifies" column states the single token figure quantifies "the per-task token, compute, and cost envelope" as one combined value; inventing a second, independent compute figure would mint a number NFR itself never assigned, exactly the invented-scope this project's "no assumptions" rule forbids.
  2. *Is the ceiling value hard-coded into the comparison logic, or read as configuration?* Decisive for configuration (§4.2) — NFR §13's own binding rule states both token envelopes are judgments "revisable once real operating data exists," and a mechanism that inlines a value due to be revised invites exactly the citation drift `BACKLOG.md` §1w's family already catalogs.
  3. *Is the budget check a sixth precondition appended to charter §5's table, or composed at H41's existing interception point?* Decisive for composition at the existing point (§7) — the ticket's own Writing Rules forbid silently adding a precondition to another document's gate, and H41's own §16 Binding Rule fixes that no point beyond the precondition-5-to-execution transition may write `outcome = applied`; a new, separate interception point would violate that rule directly, while extending the existing transition with an additional ANDed condition does not.
  4. *Is "pause" a mechanism this document must build, or the identical mechanism H41 already built under the loop-constraints specification's "hard stop" name?* Decisive for identical (§9.1) — the two specifications' own definitions, checked side by side, forbid the identical set of behaviors (no further action, no workaround, no resumption against the same condition), differing only in naming the bound a "pass" versus an "envelope," and H41 §8.4 already reserved this exact composition point by name.
  5. *Does the session accumulator persist identically to H41's own per-task counters, or does it need a sharper cross-task requirement?* Decisive for a sharper requirement (§10) — specification §5's own nesting rule requires a task that stays within its own budget to still be able to exhaust the session's, which is only possible if the session accumulator survives across every task the session contains; treating it as reset-per-task exactly as H41's counters are would silently defeat that rule.
- **Context:** This is the second document of Layer 6, the first Layer 6 document to be written directly against H41's already-built kernel rather than the specifications alone, and the first to discharge a composition point (H41 §8.4) that document explicitly reserved by name for this one.
- **Decision:** (1) Exactly one metered, ceilinged accumulator pair — per-task and per-session token consumption — realizes the specification's three-budget concept; compute is bounded transitively through the token measure, and cost is a read-time computation over it, never independently accumulated or ceilinged (§3, §5). (2) Both ceilings are read as configuration sourced from NFR §10's current setting, never inlined constants, so a revision to either judgment value changes one read, not the mechanism (§4). (3) The budget-sufficiency check composes at H41's existing interception point as an additional condition on the transition to `applied`, never a sixth row on charter §5's five-precondition table, and the cost of that composition — H41's transition now depending on a fact H41's own text could not state when written — is named explicitly as this document's own obligation (§7). (4) Graceful degradation is realized as an action-relative sufficiency test, never a fixed percentage threshold, and narrows only which new actions the kernel proposes, never how an already-proposed action is checked (§8). (5) "Pause" and the loop-constraints specification's "hard stop" are the identical mechanism, realized once in H41's kernel; this document builds no second hard-stop implementation (§9). (6) This document owes no new schema and mints no new audit-event type; the session accumulator's cross-task persistence requirement is stated as a sharper boundary handed to `05-agent-state-and-memory-design.md` than H41's own per-task counters carry (§10–§11).
- **Alternatives considered:** *An independent compute accumulator and ceiling, separate from tokens* — rejected under criterion 1; no NFR figure exists to key it to, and inventing one would be exactly the scope invention this project's rules forbid. *Hard-coded ceiling constants inlined into the comparison logic* — rejected under criterion 2; NFR §13 explicitly anticipates revision, and the ticket's own Writing Rules require the mechanism stay correct when the numbers change. *A sixth row appended to H41's five-precondition table* — rejected under criterion 3; both the ticket's own instruction and H41's own closed-list realization of a specification-fixed five-item list forbid it. *A dedicated, new pre-classification gate positioned before H41's own pipeline, rather than composing at its existing interception point* — rejected under criterion 3 for the identical reason; H41's own binding rule fixes exactly one point that may write `applied`, and a second point would violate it directly. *A separate hard-stop implementation for budget exhaustion, distinct from H41's own* — rejected under criterion 4; the two specifications' own definitions are behaviorally identical, and H41 §8.4 already reserved the shared mechanism for this exact case. *Treating the session accumulator as reset-per-task, identically to H41's counters* — rejected under criterion 5; it would silently defeat specification §5's own nesting rule that a task within its own budget can still exhaust the session's.

Binds `05-agent-state-and-memory-design.md` (not yet written) to own the durable persistence, resumability, and provenance of both accumulators, with the session accumulator specifically requiring cross-task persistence within one session — a sharper requirement than H41's own counters, stated here for that document to accommodate. ## 15. Binding Rules

These rules hold for every element of this document and are subordinate to the specification and the charter.

- **Exactly one metered, ceilinged accumulator pair — per-task and per-session token consumption — realizes the specification's three-budget concept.** No independent compute accumulator or ceiling is ever introduced; compute is bounded through the token measure, per NFR §10's own combined quantification.
- **Cost is never independently accumulated or independently ceilinged.** It is a read-time computation over the token accumulator at a configured rate this document does not source or assert.
- **Both ceilings are read as configuration, never inlined as constants.** A revision to NFR §10's judgment values changes exactly the configured value read, never the comparison mechanism.
- **The budget check is composed at H41's existing interception point, never a sixth row on charter §5's five-precondition table.** No second point in the kernel's pipeline is ever authorized to write `outcome = applied`.
- **"Near a limit" is an action-relative sufficiency test, never a fixed percentage threshold.** An action is refused the moment remaining headroom cannot cover its own projected consumption through to a safe, reversible, traceable stopping state.
- **Degradation narrows which new actions are proposed; it never weakens how an already-proposed action is checked.** Every action, degraded state or not, clears the identical five-precondition gate and the identical sufficiency check.
- **"Pause" and the loop-constraints specification's "hard stop" are the identical mechanism under two specification-level names.** No second hard-stop implementation is built here.
- **A ceiling breach detected after an action's own outcome is finalized never retroactively edits that action's record.** It governs only the next iteration's own sufficiency check, consistent with the audit trail's append-only discipline.
- **The session accumulator persists across every task the session contains — a sharper requirement than H41's own per-task counters.** This boundary is stated explicitly to `05-agent-state-and-memory-design.md`, not absorbed here.
- **This document mints no new stored schema and no new audit-event type.** Every fact its own mechanism needs is either fixed configuration, working state handed to `05-agent-state-and-memory-design.md`, or content folded into the already-existing `autonomous-change` event.
- **No model, vendor, or pricing figure is named anywhere in this document.** The configured rate cost accounting composes with is sourced and verified elsewhere, never asserted here.
- **Everything in this document remains platform-layer only.** No ceiling, accumulator, or degradation rule governs a resource budget a builder sets on their own built artifact; the builder/built separation the specification's own §2 fixes holds throughout.
