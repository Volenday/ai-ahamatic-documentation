## 3. Context, Assembly, and Overflow — Realized as Mechanism

Specification §3 fixes the concepts; this section fixes the concrete structures that make each one operational inside the kernel H41 already built.

### 3.1 Context Is a Set of Sources, Never a Single Blob

Specification §3 defines context as *"the set of governing rules, current state, and task inputs the agent must hold in view for a given task — the invariants and floors that bound it, the governing documents it must conform to, the authority and scope that permit it, and the reconstructable state it acts upon."* This document realizes that set concretely as a **reference list**, resolved per task: one entry per governing document specification §5's table requires (§5 below), plus one entry for the current reconstructable state the task acts on (`02-governance-and-security/07-audit-and-traceability.md` §3, cited and not restated). Context is never realized as an undifferentiated block of text; each entry retains its own source, so a later contradiction (§6) or staleness check (§8) can be traced to the specific document or state fact it came from, never to "the context" as an opaque whole.

### 3.2 Assembly Is Gathering Plus Three Checks, Never Gathering Alone

Specification §3 defines assembly as *"the act of gathering that context before an action, establishing that it is correct, that it is sufficient for the task, and that it is non-contradictory."* Gathering (§5) is necessary but not sufficient: an assembly that gathers every required document but never checks them against each other, or never checks their currency, has not assembled anything in the specification's own sense. This document therefore realizes assembly as gathering plus three checks run over the gathered set, each owned by a distinct section below — non-contradiction (§6), window compliance (§7), and currency (§8) — never as a single, undifferentiated "context is ready" flag.

### 3.3 Overflow Is a Property of One Assembly, Never of Cumulative Consumption

Specification §3 defines overflow as *"assembled context exceeding the window or scope it is allowed — drawing more than the bound of §7 permits, rather than the sufficient, bounded context a task actually requires."* This document realizes overflow as a **per-assembly** comparison — the content gathered for one action's own evaluation against the window bound that same assembly may occupy (§7) — structurally distinct from H42's accumulator-and-ceiling comparison, which is **cumulative** across every action a task or session performs. The two comparisons share no accumulator and are never merged into one check (§7 states the distinction precisely).

## 4. Preconditions Bind Every Assembly — Testing the Three Shapes

Specification §4 opens with the identical framing H42 and H43 each opened with for their own actions: *"Because assembling context is itself an autonomous action, every precondition of `05-meta-operations/01-agent-operating-charter.md` §5 binds it. Gathering context confers no authority the underlying action would otherwise lack, and no volume of assembled context is a licence to act outside those preconditions."* The ticket's own question is direct: does this document compose a further condition at H41's single interception point, in H42's shape; does it produce ordinary new instances of autonomous action that clear the existing gate unchanged, in H43's shape; or is it neither?

### 4.1 Not H42's Shape

H42 extended *what must be true for any action to become `applied`* by adding an ANDed budget-sufficiency condition at H41's one interception point — the transition from precondition 5 clearing to execution (H41 §5.4, §16, quoted in full at this document's front matter). A further extension in that shape would mean: every action's own transition to `applied` additionally depends on a context-assembly finding, checked at the identical point, for that action. **This is not what this document builds**, and the reason is structural rather than a matter of preference: H42's condition (sufficient budget headroom) is checkable **at** the interception point, using only the already-computed accumulator value and the action's own already-classified shape — nothing about budget sufficiency is a precondition **for classification itself** to run. Context assembly is different in exactly the respect specification §3's own boundary bullet states: *"assembling correct, sufficient context is therefore the prerequisite to clearing every precondition"* — including precondition 1 (authority) and precondition 2 (scope), which H41 §4.1's own classification table already resolves from the action's declared shape and from judgment-call determinations that themselves require the governing document's content in view to make. Assembly cannot be a further ANDed condition checked **after** classification and precondition-clearing have already run, because those steps cannot be shown to have run correctly without it.

### 4.2 Not H43's Shape, Unmodified

H43 found that its own request, record, and resumption actions are **new instances of ordinary autonomous action** that clear the existing, H42-amended gate unchanged — each one a freestanding action with its own full classification-and-precondition-clearing pass and its own outcome, composing with the gate exactly as any other action does (H43 §8, quoted in full at this document's front matter). Assembly resembles this in the respect that matters most: it adds no further ANDed condition to *another* action's transition to `applied` (§4.1 above). But it differs from H43's own actions in one respect the ticket asks to be stated explicitly: H43's request, record, and resumption actions are each the **entire content** of their own task — a human-in-the-loop task consists of nothing but requesting, recording, or resuming. Assembly is not the entire content of any task; it is a **prerequisite** step whose own outcome determines whether the task's substantive action — the change to be evaluated, produced, promoted, or reacted to — is ever classified at all.

### 4.3 The Shape This Document Actually Takes

Assembly is realized as the step that **precedes** H41 §4's classification for a given task, clearing charter §5's five preconditions **for the act of gathering itself** — using the same five reads H41 §5.1 already performs, since gathering the required documents for a task and holding that task's own eventual action to its preconditions share the identical target, kind, and scope footprint. Where assembly cannot clear a precondition (the governing content cannot be shown to lie within authorized scope to gather, or the act of gathering would itself breach an invariant — INV-01 drawing cross-tenant content, INV-03 rendering a secret, INV-07 crossing a region boundary), the task's substantive action is never classified, because there is no assembled context for classification to run against. **This is the refinement this document's own front matter promised to state explicitly rather than assume**: assembly is closest to H43's shape — an ordinary new instance clearing the existing gate, adding no further condition to another action's own `applied` transition — but it sits temporally **upstream** of classification rather than composing at the same interception point **after** it, because it is the prerequisite specification §3 already names it as, not a parallel or subsequent action like H43's own three.

### 4.4 What Happens on Success

Where assembly clears its own preconditions and the checks of §6–§8 all pass, its own findings — the required-context set gathered, its non-contradiction, its window compliance, and its currency — populate the **same** `autonomous-change` event the task's substantive action's own classification-and-precondition-clearing pass continues to populate (§10 below), never a second event for a single continuous unit of work. Where assembly fails, its own halt produces that event on its own, because no substantive action yet exists to fold it into (§10).

## 5. Required Context Per Task Type — the Assembly Rule

Specification §5 fixes a closed table: a baseline every task assembles, and seven task-type rows, each keyed to the specific documents that type requires. This document does not restate that table — it is specification content, cited and applied, never re-enumerated — and its own contribution is the **rule** that reads it.

### 5.1 Keyed to the Same Declared Shape Classification Already Reads

H41 §4.1 fixes that every proposed action carries, at the point the agent forms it, *"a declared shape: its target..., its kind (evaluate, produce/apply, promote, react, contain, emit), and the triggering task or condition."* This document's assembly rule reads the identical declared shape — never a second description of the task assembled independently — and matches its **kind** against specification §5's seven task-type rows as a lookup, exactly as H41's own classification lookup matches the identical shape against charter §6–§7. Where a task's own declared shape spans more than one type, assembly gathers the **union** of what each matched type requires, per specification §5's own closing bullet, cited and not restated.

### 5.2 Two Distinct Uses of the Same Governing Content, Never Duplicated Work

A governing document named in specification §5's table serves two purposes that must not be conflated. First, several of the already-designed mechanisms this library depends on — the invariant checks (`01-invariant-enforcement-design.md`), the Region Boundary Check, the vulnerability-classification step — already read their own governing content directly to produce the check **results** H41 §4.1 and §5.1 consume as already-computed facts. This document adds nothing to that path; those mechanisms' own reads are not "assembly" in this document's sense, and are never re-performed here. Second, and distinctly, the agent's own reasoning — formulating what change to propose, resolving a judgment call H41 §4.1 marks as non-machine-decidable, evaluating a novel condition no existing check yet covers — requires the actual governing content **in view**, not merely a check result about it. Assembly's own work is entirely the second: gathering the baseline and type-specific documents' content into the agent's own working view, so its reasoning is grounded in what those documents actually say rather than in a remembered or assumed rendering of them.

### 5.3 Sufficiency Is a Floor, Never Exceeded by Convenience

Specification §5's own text is exact: *"A task assembles the context its type requires and no less; it never proceeds on a subset because more was inconvenient to gather... a task assembles everything it requires and nothing it does not."* This document realizes that as the gathering rule's own stopping condition: assembly gathers exactly the baseline plus the matched type row(s)' documents, and gathers no further document merely because it is available or plausibly relevant. This is what makes §7's window compliance checkable at all — an assembly that over-gathers cannot be distinguished, at the window check, from one that genuinely requires more than the window allows.

## 6. Document-Precedence and Conflict-Resolution — Detection and Routing, Never Resolution

Specification §6 requires assembled context be checked for contradiction before an action proceeds, and that a genuine conflict be resolved by the precedence order — never by this document. The distinction the ticket asks to be held at every point is exactly the one H41 §6.2 already draws for its own conflict-detection mechanism: **precedence resolves a conflict between two already-applied checks; assembly's own job is prior to that — presenting context in a form where such a conflict can be seen at all, and where two assembled documents disagree, routing the disagreement onward rather than adjudicating it.**

### 6.1 Detection Is This Document's Own Work

H41 §6.2 fixes that a conflict *"is not searched for proactively across the whole library. It surfaces at the single point... two already-applied checks... return results for the identical action that cannot both be honored."* That description covers a conflict between two check **results**. This document's own detection runs one step earlier, over the assembled **content** itself: where two documents gathered for the same task state rules that cannot both be honored for this specific action — not merely two different checks disagreeing, but the governing text itself in tension — assembly is the first point such a disagreement becomes visible, because it is the step that holds both documents' content in view together for the first time. Detecting this is squarely this document's own charge (specification §6: *"this document owns the requirement that assembled context be non-contradictory and how a contradiction is resolved"* — the requirement and the routing, never the resolution).

### 6.2 Resolution Is Never This Document's Own Work

Where a genuine content-level contradiction is detected, this document performs no ranking, no weighing, and no tiebreak of its own. It routes the two conflicting documents and the specific colliding rule to H41 §6's engine, which resolves it by the identical binary rule H41 §6.3 already fixes: *"the higher-ranked result prevails in full, and the lower-ranked one is not honored for this action at all — never partially honored, never traded down to make room for the higher-ranked guarantee."* An intra-rank conflict the engine itself cannot resolve (H41 §6.4) halts and escalates through H41's own mechanism, exactly as it does for any other action; this document invents no second halt path for that case.

### 6.3 The Ordinary Case Has No Conflict to Detect

Specification §6's own text states plainly that *"ordinarily every input governs its own concern and no precedence question arises."* This document's mechanism therefore runs the detection check on every assembly, but the overwhelming majority of assemblies never surface a match — each gathered document simply governs its own slice, and assembly's own output is the union of their content with no contradiction found. This is stated explicitly because it is the case that most distinguishes assembly's own work from H41's precedence engine: the engine exists to resolve the rare conflict; assembly exists to make every assembly checkable for one, whether or not this particular task ever produces one.

## 7. Context-Window and Scoping Limits — Distinct From, and Composing With, H42's Budget

Specification §7 binds assembly to two separate resources at once, stated together in the passage quoted in full at this document's front matter: the per-task and per-session token/compute/cost envelopes H42 already owns, **and** a finite context window whose concrete value NFR §8 owns. This document's own contribution is establishing precisely how the two differ and neither substitutes for the other.

### 7.1 Two Resources, Never One

| | H42's Budget | This Document's Window |
|---|---|---|
| **What it bounds** | Cumulative token/compute/cost consumption across every action in a task, and across every task in a session. | What may be simultaneously present as gathered content for **one** assembly. |
| **Scope of the accumulator** | Per-task and per-session, persisting across the task's own iterations (H42 §6.2). | Per-assembly; not accumulated across iterations or tasks — a fresh comparison each time assembly runs. |
| **Owning ceiling** | `03-software-and-architecture/06-non-functional-requirements.md` §10 (H42 §4.1). | `03-software-and-architecture/06-non-functional-requirements.md` §8, per specification §7's own citation. |
| **Composition with H41's kernel** | Composes at H41's single interception point as a further ANDed condition on the acting action's own `applied` transition (H42 §7.2). | Composes at §4.3 above — a prerequisite check clearing before classification runs, never a further condition on the acting action's own transition. |

Assembly, as an autonomous action in its own right (§4 above), draws against H42's existing token accumulator exactly as any other action does — this document adds nothing to that accumulator and mints no second one, per the Writing Rules' own instruction. Independently, the content assembly gathers must fit within the context window — a capacity bound H42's accumulators do not track, because a single assembly's own size and a task's cumulative consumption are different facts about different resources. Both bounds bind every assembly; neither is checked in place of the other, and reaching either ends the assembly identically (§7.3 below).

### 7.2 Degradation Reduces to "Nothing Extra Was Ever Gathered"

Specification §7 requires graceful degradation as the window nears its limit, and states explicitly: *"Degradation narrows what is assembled; it never drops a required input, so a task cannot be made to 'fit' by shedding context its type requires."* Composed with §5.3 above — assembly never gathers beyond the required floor to begin with — this leaves no optional content for degradation to trim: there is nothing gathered "for convenience" that a narrowing pass could remove, because §5.3's own stopping condition already excludes it. **Degradation is therefore not a separate mechanism this document builds**; it is the direct consequence of §5.3's sufficiency-is-a-floor rule applied under window pressure — assembly narrows to exactly the required set (which it does unconditionally, window pressure or not), and where that set alone does not fit the window, there is no further narrowing available.

### 7.3 Overflow That Cannot Be Avoided Halts, Never Proceeds Reduced

Where the required floor itself — baseline plus every matched type row, with no optional content ever added — exceeds the window, specification §7's own rule is exact: *"A task that requires more context than can be assembled within the window and scope is not carried out on a reduced context; it is halted and escalated."* This document realizes that as the same halt mechanism §4.4 and §8.3 below use: no partial assembly is ever handed to classification, and no required document is ever silently dropped to make the remainder fit.

## 8. The Prohibition on Missing or Stale Context — Staleness Detected Mechanically

Specification §8 treats stale context as missing, and forbids acting on a "remembered, assumed, or previously-valid version" of it. The ticket's own question is the harder half: how is staleness detected mechanically, rather than assumed away by trusting an assembly that was correct when it ran.

### 8.1 Currency Is Established by Reconciliation, Never by Elapsed Time Alone

`02-governance-and-security/07-audit-and-traceability.md` §3.3 already fixes that the reconstructable record is authoritative over recollection, and that every event carries a strictly ordered position within its own stream. This document's own currency check reuses that ordering rather than a wall-clock threshold: an assembled item is **current** if no event postdating its own capture, in the specific stream that item's own source mechanism writes to (an invariant-check record's stream, a configuration-change record's stream, the current reconstructable state's own stream), would change what that item states. An assembled item is **stale** the moment such a later event exists, regardless of how little wall-clock time has elapsed — and, consistent with the deny-by-default posture this library applies throughout, an assembled item whose currency **cannot be established either way** is treated as stale, never as current by default.

### 8.2 Consistent With, and a Generalization Of, H43's Own Resumption Rule

`03-human-in-the-loop-design.md` §6 designed exactly this problem for one specific case — an action resuming after an approval was pending — and fixed what may be assumed unchanged (the classification match itself, the decision's own content) against what must be re-verified (every one of H41's five preconditions, H42's budget sufficiency, H41's loop-guard counters, and any newly-arisen Critical condition), because none of those five pause while an approval is pending. This document's own rule is the **general** form of that same finding, applied to every pass through the pipeline rather than only to a resumption after a human-in-the-loop pause: on every iteration H41 §7.1 counts, assembly's own currency (§8.1 above) is re-established before that iteration's classification and precondition-clearing run, exactly as H43's own list re-establishes its five facts on a resumption specifically. This document does not contradict H43's own list — it is not a competing rule — it is the same reconciliation-against-the-record principle, stated once, of which H43's list is the instance that document needed for its own narrower case.

### 8.3 Missing, Stale, or Unresolvably Contradictory Context Halts Identically

Consistent with §4.4 and §7.3 above, a currency check that finds an assembled item stale, a required item that could not be gathered at all, or a contradiction §6.2 could not route to a resolution (H41 §6.4's intra-rank case) each produce the identical halt: the task's substantive action is never classified, and assembly's own event (§10 below) carries `outcome = halted-and-escalated`, naming which required item was missing, stale, or unresolvably contradictory. No partial or best-effort assembly is ever handed forward, and no missing or stale item is ever inferred, assumed, or substituted with a remembered version.

- **Question this answers:** Given a specification that binds context assembly to charter §5's five preconditions in language nearly identical to what H42 and H43 each used for their own actions, a map row that grades this document as owning no independent decision because precedence is fixed elsewhere, a required-context table the specification itself already closes and fixes, and two neighboring resources — H42's cumulative token budget and a context window the specification names but does not size — that must never be conflated, how does assembly actually compose with H41's single interception point without becoming a third or fourth extension of its content; how is the required-context rule realized without re-enumerating what specification §5 already enumerates or re-performing checks other mechanisms already perform against the same content; how does a context window differ from a token budget precisely enough that neither substitutes for the other; and how is staleness detected as a mechanical fact rather than assumed from an assembly's own past correctness?
- **Criteria applied, and how each resolved:**
  1. *Does assembly add a further ANDed condition to another action's own transition to `applied`, in H42's shape; does it produce freestanding new instances that compose at the same interception point, in H43's shape unmodified; or does it precede classification entirely?* Decisive for the third (§4) — specification §3's own words that assembly is "the prerequisite that makes the preconditions checkable" rule out H42's shape directly, since a condition checked at the interception point presupposes classification has already run, and assembly is not the entire content of any task the way H43's own three actions are, ruling out H43's shape unmodified.
  2. *Does the required-context rule re-enumerate specification §5's own table, or read it as a lookup against the identical declared shape H41's classifier already uses?* Decisive for the lookup (§5.1) — re-enumerating a closed, specification-fixed table would be exactly the kind of invented scope this project's no-assumptions rule forbids, and a second description of the task's own shape would duplicate H41's own declared-shape field for no reason.
  3. *Is degradation near the window a mechanism this document must separately build, or the direct consequence of the sufficiency-is-a-floor rule specification §5 already fixes?* Decisive for the latter (§7.2) — an assembly that never gathers beyond the required floor has no optional content left to trim, so a separate degradation mechanism would have nothing to act on that the floor rule does not already exclude.
  4. *Is a context window the identical resource H42's accumulators already track, differently named, or a genuinely distinct bound?* Decisive for genuinely distinct (§7.1) — specification §7's own text binds assembly to both at once, in the same sentence, which would be redundant if the two named the same fact; the per-assembly-versus-cumulative distinction is the concrete difference that makes the specification's own sentence coherent rather than duplicative.
  5. *Is staleness detected by an elapsed-time threshold, or by reconciliation against the reconstructable record's own ordering?* Decisive for reconciliation (§8.1) — an elapsed-time threshold would need a configured value this document would then have to keep synchronized with nothing in particular, whereas the record's own strictly-ordered stream (`08-audit-and-traceability-design.md` §3.3) already provides an exact, non-arbitrary answer to "has anything changed since," which is the actual question staleness asks.
- **Context:** This is the fourth document of Layer 6, the first whose own map row states in advance that it owns no independent decision, and the first required to test that grading explicitly against the precondition-composition precedent H41, H42, and H43 each set in turn.
- **Decision:** (1) Assembly is realized as a prerequisite step that clears charter §5's five preconditions for the act of gathering itself, ahead of H41's classification, rather than as a further ANDed condition on another action's own `applied` transition or as a freestanding instance composing at H41's existing interception point after classification has already run (§4). (2) The required-context rule reads specification §5's own closed table as a lookup keyed to the identical declared shape H41 §4.1's classifier already reads, gathering the union of every matched type's documents and no more (§5). (3) A genuine content-level contradiction among assembled documents is detected by this document and routed to H41 §6's engine for resolution; this document performs no ranking, weighing, or tiebreak of its own (§6). (4) A context window is a distinct, per-assembly, non-cumulative bound from H42's cumulative token/compute/cost envelope; both bind every assembly, neither substitutes for the other, and no numeric window value is named here (§7). (5) Degradation near the window reduces to the sufficiency-is-a-floor rule already excluding optional content, and an unavoidable overflow of the required floor halts rather than proceeding on a reduced set (§7). (6) Staleness is detected by reconciling an assembled item's own capture point against the reconstructable record's own ordering, never by elapsed time alone, generalizing rather than contradicting the resumption re-verification list `03-human-in-the-loop-design.md` §6 already built for its own narrower case (§8). (7) This document owes no new schema and mints no new audit-event type (§9–§10).
- **Alternatives considered:** *Composing the assembly check as a further ANDed condition at H41's existing interception point, by analogy to H42's own extension* — rejected under criterion 1; specification §3's own "prerequisite that makes the preconditions checkable" language directly contradicts a design where assembly is checked only after those preconditions have already been evaluated. *Re-enumerating specification §5's task-type table inside this document, for readability* — rejected under criterion 2; the ticket's own instruction and this project's spec-fidelity rule both forbid restating what a closed specification table already fixes. *A separate, percentage-based degradation threshold for the context window, mirroring a possible reading of "near a limit"* — rejected under criterion 3; nothing is left to trim once the sufficiency-is-a-floor rule is applied consistently, so a threshold would have nothing to act on and would need its own configured value for no structural reason. *Treating the context window as a second name for H42's own per-task token ceiling, to avoid building a second bound* — rejected under criterion 4; specification §7 binds assembly to both at once in one sentence, which is only coherent if the two are genuinely distinct resources. *An elapsed-time staleness threshold, configured alongside the window and budget ceilings* — rejected under criterion 5; it would need a third configured value with no principled basis, where the reconstructable record already answers the actual question exactly.
- **Consequences:** Confirms, and alters none of, `01-agent-runtime-and-control-design.md`'s classification step, precondition-clearing gate, and precedence engine; `02-token-and-compute-budget-design.md`'s accumulator-and-ceiling mechanism; and `03-human-in-the-loop-design.md`'s trigger-enforcement and resumption re-verification rules — each document's own content stands exactly as already designed.
