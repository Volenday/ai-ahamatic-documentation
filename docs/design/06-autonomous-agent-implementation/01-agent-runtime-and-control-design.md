## 3. The Agent Kernel — What It Is, and Where It Is Not

The **kernel** is the always-on control mechanism that intercepts every action the agent proposes to take autonomously, before that action has any effect, and either permits it to proceed through an already-existing execution channel, routes it to human approval, or halts and escalates. It is not a component of the built platform — none of the seven components `03-architecture-realization-design.md` §3 fixes (Isolation and Trust, Construction, Operation, Reach, Extension, Distribution, Evolution) realizes a Meta-Operations capability, and the kernel realizes none of C-01 through C-27. It is the platform-layer control system that governs how the agent itself acts *on* those components and on the platform's own delivery pipeline — a distinct concern from what the components themselves do (§9 states this placement precisely).

The kernel has four parts, composing in a fixed order for every proposed action within a task:

1. **Classification** (§4) — does the action match a permitted-autonomous class (charter §6) or an approval-required class (charter §7)?
2. **Precondition clearing** (§5) — for an action classified permitted, do all five of charter §5's preconditions hold?
3. **Precedence resolution** (§6) — invoked only where classification or precondition-clearing encounters a genuine conflict between two governing rules, never as a default arbiter.
4. **The loop guard** (§7–§8) — a cross-cutting fifth part, not per-action but per-task: it wraps repeated invocations of parts 1–3 across a task's own iterations, counting, detecting repetition, and requiring progress.

None of the four parts is a second copy of a mechanism this library already builds. Each is designed, in the sections that follow, to consume the result of an already-existing check — an invariant-check record, a signal's severity tag, a rollback's own bound — rather than compute it again.

## 4. Authority and Autonomy Boundary Enforcement — the Classification Step

Charter §6 fixes six permitted-autonomous classes; charter §7 fixes eleven approval-required classes (ten substantive plus the closing uncertainty rule), explicit and deny-by-default. This section builds the mechanism that decides, for one proposed action, which class or classes it matches — the enforcement the ticket asks for, not a restatement of the two lists.

### 4.1 The Classification Rule

Every proposed action carries, at the point the agent forms it, a declared shape: its target (a component module, a tier, an environment, a released artifact, a piece of stored configuration), its kind (evaluate, produce/apply, promote, react, contain, emit), and the triggering task or condition. Classification matches this declared shape against charter §6's six classes and charter §7's eleven classes as a **closed lookup**, never an open-ended judgment call applied fresh to each action:

| Charter §7 Class (cited, not restated) | Decided From | Full / Judgment |
|---|---|---|
| Any promotion to Production | The action's own declared target tier — equals Production or does not. | Full — a structural fact of the action's own shape. |
| Any residency-relevant action | The Region Boundary Check's own resolution (`06-compliance-and-data-residency-design.md` §3.4, §7–§8), read, never recomputed. | Full — composes with an already-existing check. |
| Any action meeting a mandatory security-review trigger | The vulnerability classification and review-trigger content (`04-security-controls-design.md` §4–§5), read. | Full — composes with an already-existing check. |
| Any irreversible action | The INV-08 check result for this action (`01-invariant-enforcement-design.md` §5.4), read. | Full — composes; this is the identical fact precondition 4 of §5 below also reads. |
| Any action that would breach, or cannot be shown not to breach, an invariant | Every applicable invariant-check record (`01-invariant-enforcement-design.md` §5–§6), read. | Full — composes. |
| Any runtime signal or incident mandating escalation | The escalation-mandating signal set (`04-observability-and-monitoring-design.md` §7) or the mandatory-escalation threshold set (`06-incident-response-and-recovery-design.md` §7), read. | Full — composes. |
| Any reaction past the autonomous bound | The self-correction ladder's own bound report or the rollback mechanism's own bound (`05-release-and-rollback-design.md` §8.4), read. | Full — composes with a not-yet-designed sibling's own reported fact, never this document's own count. |
| Any backward-compatibility break or managed deprecation | The INV-09 check result, read. | Full — composes. |
| Any change to a fixed architectural decision | Whether the action's own declared target matches an entry on the closed list `03-software-and-architecture/01-architecture-overview.md` §7 fixes. | Full — a maintained, closed list, not an interpretive judgment. |
| Any action outside authorized scope | Whether the action's own declared shape can be expressed in domain-neutral, generic-builder terms and pursues no non-goal of `01-business-and-ux/01-vision-and-charter.md` §4. | **Judgment** — the same shape of recorded, non-machine-decidable determination `01-invariant-enforcement-design.md` §5.2 already builds for INV-05's own judgment half, applied here to scope rather than to a merge. An unrecorded determination is treated as a fail, not silent permission, on the identical deny-by-default posture that document already applies. |
| Uncertainty about whether approval is required | Whether every row above resolves negatively; if any cannot be established, this row matches. | The closing rule, not a tenth decidable condition. |

Charter §6's six classes are classified the identical way, each decided structurally from the action's own declared shape or from an already-existing mechanism's own reported fact (whether a reversible/rollback bound remains open, whether the incident-response prohibitions of `06-incident-response-and-recovery-design.md` §8 are clear) — none of the six requires a judgment call, because §6 describes what the agent may do once every other check already holds, not a class requiring its own interpretation.

### 4.2 Approval-Required Always Wins

Where a proposed action matches both a §6 class and a §7 class — for example, "producing and applying a platform-layer change" (§6) that also happens to be a backward-compatibility break (§7) — the §7 match controls. This is not a numeric or weighted resolution; it is the direct consequence of charter §7's own closing rule that "an action need match only one class to require approval," applied mechanically: the classifier evaluates the full §7 table first, and a match on any row there routes the action to §4.3 below regardless of what §6 would otherwise have permitted.

### 4.3 What Classification Does and Does Not Decide

A §7 match routes the action to human approval; **this document does not design how that request is made, routed, recorded, or resolved** — `03-human-in-the-loop-design.md` (Layer 6, not yet written) owns the mechanics in full, exactly as charter §7's own text already assigns them there. This document's own obligation ends at producing the classification and handing the matched class, and the evidence behind the match, to that mechanism.

A §6-only match (no §7 row matches) proceeds to the precondition-clearing gate of §5. An action matching neither list — a truly novel shape the closed lookup cannot place — falls to the uncertainty row and is treated as approval-required, never as silently permitted; this is the same deny-by-default posture charter §5's own closing bullet applies to its five preconditions, extended here to classification itself.

## 5. The Precondition-Clearing Gate — Charter §5, Built Here

`06-incident-response-and-recovery-design.md` §8 already states the load-bearing fact this section discharges: *"`05-meta-operations/01-agent-operating-charter.md` §5 already fixes that every autonomous action — including every recovery action a response invokes — clears five preconditions before it proceeds... This document does not build a second gate that checks its own prohibitions — it supplies the content the charter's own already-structural precondition-clearing mechanism checks against."* That document assumed the gate exists and bears real weight. This section is where it is actually built, and it is designed to bear exactly that weight: every autonomous action in this library — an incident-response recovery action, a self-correction attempt, a rollback, a routine platform-core change — passes through this identical gate before it executes, with no second, parallel gate anywhere else in the library.

### 5.1 The Five Preconditions, Realized as Reads, Not Re-Derivations

The gate evaluates charter §5's five preconditions in the fixed order the specification lists them, short-circuiting on the first that cannot be established — deny-by-default, so no benefit accrues to evaluating the remaining four once one has already failed:

| # | Precondition (charter §5, cited) | Established From | Composes With |
|---|---|---|---|
| 1 | Within granted authority | The classification step's own affirmative §6 match (§4.1 above). **Not re-evaluated independently** — a second, redundant authority check would be exactly the kind of duplicate gate this document is instructed not to build. | §4 above. |
| 2 | Within authorized scope | The judgment-half determination §4.1's own table already requires for the "outside authorized scope" §7 row, read as a negative (no non-goal pursued, expressible in generic-builder terms) — the same record, read the other way, never computed twice. | §4.1 above. |
| 3 | Breaches no invariant | Every applicable invariant-check record `01-invariant-enforcement-design.md` §5–§6 produces for this action, required to show `held` for each — never `violated` or absent. A missing record (the check has not yet run) is treated identically to a failed one, per the deny-by-default rule. | §10 below. |
| 4 | Retains a reversible, recoverable path | The INV-08 check result specifically (`01-invariant-enforcement-design.md` §5.4) — the identical fact charter §7's "any irreversible action" row and §4.1's table above already read. | §10 below. |
| 5 | Leaves its minimum trace | The six-element minimum-traceability check `08-audit-and-traceability-design.md` §9 already fixes (attribution, invariant-and-gate evaluation, reversible path, backward-compatibility result, approval where required, outcome), required to show every element establishable. | §5.4 below. |

No precondition is evaluated by a mechanism this document invents. The gate's own work is the composition — reading five already-designed results together, in a fixed order, and refusing the action where any one is missing or negative — never a sixth, independent determination of any of the five facts.

### 5.2 Uncertainty Resolves Against Autonomy

Where any of the five reads above cannot be completed — the invariant-check record has not yet been produced, the minimum-traceability check has not yet run — the gate does not wait, retry, or proceed on a favorable assumption. It refuses the action, exactly as charter §5's own closing bullet requires, and routes it to the halt-and-escalate duty (§8 below), not to a pending or deferred state.

### 5.3 The Precedence Engine's Role Inside This Gate

Ordinarily, the five reads above simply return their already-computed answer and the gate proceeds or refuses. The document-precedence engine (§6) is invoked from inside this gate **only** where two of the reads that feed it genuinely disagree about the same action — for example, an invariant-check record shows `held` while a governance-guardrail document's own gate (read as part of precondition 2's scope determination) shows the action forbidden on a ground the invariant check does not cover. This is the narrow, sharp condition charter §4's own rule reserves precedence for ("invoked only for a genuine, irreducible conflict... it never overrides the specific rule a document owns within its own slice, which is honored without invoking precedence") — not a step the gate runs on every action.

### 5.4 Discharging the Mechanical Interception Point — `08-audit-and-traceability-design.md`'s Own Consequences Obligation

That document's ADR-025 Consequences clause binds "`05-meta-operations/01-agent-operating-charter.md` and the two cited protocols to place the minimum-traceability check's mechanical interception point in the agent's own execution pipeline, and to emit one event per self-correction-ladder rung, consistent with §8–§9 without this document designing either pipeline." This document discharges the first half of that obligation concretely — the second (one event per self-correction-ladder rung) is `06-self-correction-and-fallback-design.md`'s own to emit, cited at §8.2 below and never designed here: **the interception point is the transition from precondition 5 clearing (§5.1's row 5) to the action's own execution.** An action's `autonomous-change` event (already fixed by `08-audit-and-traceability-design.md` §9, minted by neither document fresh) has its `outcome` field populated `applied` **only** at the moment all five preconditions of §5.1 have cleared in full; where precondition 5 specifically fails, the event's `outcome` is set to `halted-and-escalated` — "never `held-pending-approval`, because this is a violation already found... not a governance decision pending before a violation could occur," per that document's own held/halted distinction. No other point in the kernel's own pipeline writes to that field, and no action's effect is realized before this point is reached — this is what makes the interception structural rather than a convention a future change could relocate without noticing.

## 6. The Document-Precedence Engine — Charter §4, Built Here

`PROCESS.md` §11 states the trap this section exists to avoid explicitly: *"Never infer conflict precedence from reading order or from the map's layout; conflict precedence is owned solely by `05-meta-operations/01-agent-operating-charter.md` §4."* The specification pyramid derives Business & UX first; capability intent nonetheless ranks sixth in conflict precedence, below the charter, the invariants, and the Governance/Architecture/DevOps floors. This section builds the engine that realizes charter §4's actual rank order and nothing else — never the derivation order of `context-document-map.md` or `implementation-document-map.md`, and never the cost-to-reverse order of `PROCESS.md` §12.1. All three are distinct orderings (`PROCESS.md` §12.1), and this engine is keyed to exactly one of them.

### 6.1 The Rank Lookup

Charter §4's own table fixes seven ranks, cited here by number and label only — the engine's rank-lookup table is built directly from that table, never re-derived from any other document's layout:

| Rank | Governing Layer (charter §4) |
|---|---|
| 1 | The charter itself |
| 2 | The invariants |
| 3 | Governance & Security guardrails |
| 4 | Software & Architecture constraints |
| 5 | DevOps & Cloud Infra protocols |
| 6 | Capability intent and success targets |
| 7 | Meta-Operations conduct |

Every governing document this library cites resolves to exactly one rank via this table, fixed at design time and never recomputed at runtime or inferred from where a document sits in either the spec or the design pyramid. **This document is itself a Meta-Operations document (rank 7)** — the engine it builds does not rank *other* documents at rank 7 merely because this document belongs to that family; it ranks each cited document at its own true rank from the table above, including ranking the charter it is itself realizing at rank 1, above itself.

### 6.2 Conflict Detection

A conflict is not searched for proactively across the whole library. It surfaces at the single point named in §5.3: two already-applied checks — each honored within its own slice, per charter §4's "precedence resolves conflicts, not ownership" rule — return results for the identical action that cannot both be honored. The overwhelming majority of actions never reach this point; each governing document's own check simply returns its answer and the gate of §5 proceeds.

### 6.3 Resolution — the Floor Rule, Made Concrete

Where a genuine conflict is detected, the engine looks up the rank of the document that produced each of the two conflicting results and applies charter §4's own rule: **the higher-ranked result prevails in full, and the lower-ranked one is not honored for this action at all — never partially honored, never traded down to make room for the higher-ranked guarantee.** This is the precise, concrete form of charter §4's own rule that "a higher guarantee is never relaxed to satisfy a lower objective": resolution is binary, not a weighted trade-off computed between the two results.

**Worked example, using only already-fixed content.** Suppose an action would advance `01-business-and-ux/02-prd.md`'s time-to-first-operating-artifact target (rank 6) but the same action meets `02-governance-and-security/02-security-policy.md` §7's mandatory security-review trigger (rank 3). The engine looks up ranks 6 and 3, finds rank 3 higher (lower number, higher precedence per charter §4's own ordering), and the review proceeds exactly as `04-security-controls-design.md` already fixes it — the action does not proceed faster, more leniently, or partially reviewed to preserve the rank-6 target. The target is simply not met on this action's own schedule; charter §4's own heading holds exactly: "Invariants and floors are never spent for a lower layer."

### 6.4 Intra-Rank Conflicts Are Not This Engine's to Resolve

The rank table orders **ranks**, not the documents within one rank. Where two documents of the *identical* rank conflict — two Governance & Security guardrails (both rank 3), or, per charter §4's own closing bullet, two invariants of equal standing (both rank 2) — the engine has no further basis to prefer one over the other; charter §4 fixes no intra-rank ordering, and inventing one (by document number, by which was written first) would be an authority this document does not have. Per charter §4's own rule — *"an unresolvable conflict halts and escalates... including a conflict among invariants of equal standing... the conflict is never resolved by relaxing either guarantee"* — the engine does not attempt a tiebreak. It routes the action to the halt-and-escalate duty (§8 below) exactly as an unmet precondition does.

## 7. The Loop and Termination Guard

`02-agent-loop-constraints.md` §4 fixes that "each iteration is itself an autonomous action" and that every precondition of charter §5 binds it. The loop guard is therefore not a fifth, independent gate: it is the mechanism that invokes the classification-and-precondition pipeline of §4–§5 once per iteration, wraps it in a per-task counter, and adds the three guards §6–§7 of the loop-constraints specification require — repetition detection, the progress requirement, and the hard stop.

### 7.1 What Is Counted, Per Task

A **task** (`02-agent-loop-constraints.md` §3) is the unit every counter below is scoped to; every counter resets to zero at task start and applies to no other task. Each pass through §4–§5's pipeline is one **iteration**, counted regardless of the outcome (proceed, refuse, halt). A pass that re-attempts a prior action against a **meaningfully changed condition** additionally increments the **retry** counter; a pass re-attempting an action against an unchanged condition is not a legitimate retry at all — it is caught by the repetition check of §7.2, never counted as a retry and never permitted to proceed.

### 7.2 Repetition Without Progress

Each iteration's own `autonomous-change` or `invariant-check` record (already produced by §5's gate, `01-invariant-enforcement-design.md` §6.1, and `08-audit-and-traceability-design.md` §4.2) is compared against the immediately preceding iterations' own records within the same task, using the fields those records already carry — `what_was_inspected`, `result`, `outcome` — with no new field or structure minted for the comparison. Two conditions terminate the loop before the ceiling is reached:

- **An oscillating loop.** The proposed action's own target and kind (§4.1) match an iteration already attempted in this task, and the condition that produced the prior result has not meaningfully changed. This is not treated as a retry (§7.1); it is a repeat, and the loop terminates and escalates rather than proceeding.
- **A no-op cycle.** The iteration's own record shows no advance over the immediately preceding one — an identical `what_was_inspected`, an identical `result`, and an identical `outcome` — with no changed state, no resolved sub-goal, and no narrowed uncertainty establishable from the record itself. Per `02-agent-loop-constraints.md` §7, "consuming iterations, resources, or time is never itself progress"; a cycle that produces none of the three is a loop violation and terminates.

Both checks reuse the audit trail's own already-captured content as the comparison basis — the identical pattern `06-incident-response-and-recovery-design.md` §5.1 already uses when it confines containment to an already-structural boundary rather than inventing a new one: this document adds no new state-tracking structure for loop detection, only a comparison over records that already exist for another reason (§11 states this precisely as part of the storage check).

### 7.3 The Bypass — a Critical Signal Never Reaches the Loop Guard at All

Consistent with `04-observability-and-monitoring-design.md` §6.4's rule that a signal naming an already-violated invariant or an already-Critical vulnerability "is never routed through §6.1–§6.3 at all... bypassing the ladder entirely," this document's own precondition gate (§5.1, row 3) applies the identical bypass at the point it reads the invariant-check record: where that record itself shows a Critical or invariant-violating condition, the gate does not proceed to complete the remaining preconditions, does not consult the loop guard's own counters, and does not attempt repetition or progress evaluation — it halts and escalates immediately under `02-governance-and-security/01-system-invariants.md` §3, exactly as that document's own binary blocking-check rule requires. This check runs **before**, not as part of, iteration counting — an iteration that would have been the eleventh, or the first, is treated identically once a Critical condition is found.

## 8. The Ceilings, Their Nesting, and the Counter Architecture

### 8.1 Two Independent Counters, One Shared Budget

The kernel maintains exactly two counters per task: an **iteration counter**, incremented on every pass through §4–§5 regardless of kind, and a **retry counter**, incremented only on a legitimate retry pass (§7.1), each compared against its own ceiling from `03-software-and-architecture/06-non-functional-requirements.md` §10 — iterations ≤ 10, retries ≤ 3. The retry counter is not a separate budget layered on top of the iteration counter; every retry pass increments **both** counters simultaneously, which is the concrete mechanism realizing `02-agent-loop-constraints.md` §5's own words that "a retry consumes an iteration exactly as any other pass does."

### 8.2 The Self-Correction Ladder Shares the Same Iteration Counter

`02-agent-loop-constraints.md` §5 fixes that "every self-correction and fallback attempt... is an iteration and counts against the task's ceiling," and that the ladder's own maximum-attempt count (≤ 3, `03-software-and-architecture/06-non-functional-requirements.md` §10) is "a distinct, nested bound owned by that document." This document's own contribution is the composition point: **every rung `06-self-correction-and-fallback-design.md`'s own ladder mechanism runs (Layer 6, not yet written) increments this document's own shared iteration counter identically to any other pass** — the ladder does not maintain a competing count of task-level iterations, only its own internal rung position (first attempt, second, third), which this document does not design or bound beyond citing the ≤ 3 ceiling. This is the boundary stated from this document's side, for the sibling that will consume it: the ladder's own three rungs are drawn from, never additive on top of, the shared iteration budget.

### 8.3 The Nesting, Enforced as Arithmetic, Not Merely Cited

Because the retry counter (≤ 3) and the self-correction ladder's own attempt count (≤ 3, reported to but not computed by this document) both draw from the identical shared iteration counter (§8.1–§8.2), the worst case is exactly the figure `03-software-and-architecture/06-non-functional-requirements.md` §10 states: 3 + 3 = 6 of the 10 available iterations, leaving 4 for the pass that actually advances the task. The kernel enforces this by construction, not by a separately-computed check: because both nested ceilings write to the same iteration counter the outer ceiling reads, a task cannot exhaust its nested budgets without the shared counter itself approaching 10 — there is no path by which the two nested ceilings could be reached while the outer counter under-reports, because every increment to either nested counter is, by §8.1–§8.2's own design, simultaneously an increment to the outer one.

### 8.4 Reaching Any Ceiling Ends the Task Identically

Whichever of the three ceilings — iteration (≤ 10), retry (≤ 3), or the self-correction ladder's own reported bound (≤ 3, that document's to enforce internally) — is reached first, the same hard-stop mechanism fires: the loop does not run a further pass, is not worked around, and is not resumed against the same condition, per `02-agent-loop-constraints.md` §8's own rule. This document also treats reaching a token, compute, or cost envelope (`02-token-and-compute-budget-design.md`, Layer 6, not yet written) as an identical limit breach, without defining the envelope itself — the hard-stop mechanism is shared across all named limits; only which document owns the concrete ceiling differs.

### 8.5 Every Hard Stop Is the Identical Audit-Stream Event, Never a New One

A ceiling breach, a detected repetition, or a no-op cycle each produces the identical composition §5.4 already fixes: the acting `autonomous-change` or `invariant-check` event's own `outcome` is set to `halted-and-escalated`, with `what_was_inspected` naming the specific limit or rule that fired (the iteration ceiling, the retry ceiling, the oscillation check, the progress check). No new event type is minted for any of the four conditions (§12 confirms this against the full grep discipline `BACKLOG.md` §1v requires).

### 9.1 Not an Eighth Component

`03-architecture-realization-design.md` §3 fixes exactly seven components, one per primitive family (C-01–C-27), plus the shared `guardrail/` module. ### 9.2 The Kernel Introduces No New Execution Channel

Every action the kernel permits (§4–§5) is carried out through a channel another already-designed document owns, never a channel the kernel invents for itself:

- **A change to platform-core source** (a `components/*` or `guardrail/` file) clears the identical Merge Gate `02-ci-cd-pipeline-design.md` fixes for any change, agent-authored or human-authored — the same import-boundary mechanism (`03-architecture-realization-design.md` §4, ADR-014) checks it, with no agent-specific bypass.

- **A runtime observation or reaction** reads the identical signal and severity mechanism `04-observability-and-monitoring-design.md` §4 fixes, through the same access boundary any other authorized reader uses.
- **A rollback or restore** invokes the identical mechanism `05-release-and-rollback-design.md` and `06-incident-response-and-recovery-design.md` already fix, never a parallel path.

Because the kernel joins none of `components/*`'s own dependency graph — it is a control system that decides *whether and when* to invoke these already-existing channels, not a component that executes inside them — none of `03-architecture-realization-design.md` §4.1's five forbidden directions applies to it directly: it imports nothing from `isolation-and-trust`, holds no per-tenant instance (its own authority is platform-layer only, per charter §2's own scope bullet — "what authority a builder grants their own built artifact... is never absorbed into this document"), imports no generated artifact, depends on no specific extension, and carries no region-specific logic. ### 9.3 `BACKLOG.md` §1u — Checked, Not Resolved

## 15. Precedence and Ownership Boundaries

When a rule in this document meets any other consideration, it is resolved by the precedence order of `05-meta-operations/01-agent-operating-charter.md` §4, at whose apex the Vision and Charter sits — the identical order §6 above builds the engine for.

- **The charter prevails**, and both specifications this document realizes prevail over this design wherever the two appear to conflict; this document is corrected to match the specification, never the reverse.

## 16. Binding Rules

These rules hold for every element of this document and are subordinate to the two specifications and the charter.

- **The permitted-autonomous/approval-required split is enforced by a closed classification lookup, never an open-ended judgment applied fresh per action.** Sixteen of the seventeen charter classes resolve structurally; the one judgment-requiring row (out-of-scope) requires an explicit, recorded determination, on the identical shape `01-invariant-enforcement-design.md` §5.2 already builds — an unrecorded determination is a fail, never silent permission.
- **An approval-required match always controls over a permitted match on the same action.** No action proceeds autonomously merely because it also satisfies a §6 class; a single §7 match is sufficient to require approval.
- **The precondition-clearing gate composes entirely from already-designed results; it re-derives none of the five.** No section of this document, and no future amendment to it, may introduce an independent evaluation of authority, scope, an invariant, reversibility, or minimum trace — each is a read of a result another document already owns.
- **The mechanical interception point for the minimum-traceability gate is fixed at the transition from precondition 5 clearing to execution, and nowhere else.** No other point in the kernel's own pipeline writes an `outcome` of `applied`.
- **The document-precedence engine is keyed exclusively to charter §4's own seven-rank table.** It is never built from, seeded by, or checked against the specification pyramid, the design-phase layer pyramid, or the cost-to-reverse order — three distinct orderings that must never collapse into one another.
- **Precedence resolution is binary, never a weighted trade-off.** The higher-ranked result prevails in full; the lower-ranked one is not honored for that action at all, consistent with charter §4's own rule that "a higher guarantee is never relaxed to satisfy a lower objective."
- **An intra-rank conflict is never resolved by an invented tiebreak.** Two documents, or two invariants, of equal standing that genuinely conflict halt and escalate; the engine does not rank within a rank.
- **The iteration, retry, and self-correction ceilings share one budget, not three independent ones.** Every retry and every self-correction rung increments the identical shared iteration counter; the nested ceilings' worst case is enforced by that construction, not by a separately-computed check.
- **A Critical or invariant-violating condition bypasses the loop guard entirely, before iteration counting applies.** This composes with, and never redesigns, `04-observability-and-monitoring-design.md` §6.4's identical bypass.
- **The kernel introduces no eighth component and no new execution channel.** Every action it permits is carried out through a channel another already-designed document owns; the kernel decides whether and when to invoke it, never how.
- **This document mints no new stored schema and no new audit-event type.** Every fact its own mechanisms need is either an already-existing audit-stream record, read or extended with existing fields, or ephemeral working state handed in full to `05-agent-state-and-memory-design.md`.
- **The boundary against every not-yet-written Layer 6 sibling and the one cross-layer dependent is stated from this document's own side, and none may proceed as though this document's own mechanisms were still open for it to shape.**
- **Everything in this document remains platform-layer only.** No authority, precedence rank, ceiling, or classification rule governs what a builder configures inside their own built artifact; the builder/built separation charter §2 fixes holds throughout.
