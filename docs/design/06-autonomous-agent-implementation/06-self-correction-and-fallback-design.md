## 3. The Observability Bypass — the Boundary That Bounds This Document's Entire Scope

Before any detection signal, rung, or ceiling is designed, the boundary that determines whether this document's mechanism is ever reached at all must be stated, because it is the difference between correcting and compounding harm the ticket names explicitly.

`04-observability-and-monitoring-design.md` §6.4 fixes, verbatim: *"A signal whose tag names an invariant already violated, or a vulnerability already classified Critical, is never routed through §6.1–§6.3 at all — it halts and escalates immediately under `02-governance-and-security/01-system-invariants.md` §3, bypassing the ladder entirely..."* `01-agent-runtime-and-control-design.md` §7.3 fixes the identical bypass at its own precondition gate, reading the same invariant-check record: such a condition "halts and escalates immediately... and does not attempt repetition or progress evaluation... before, not as part of, iteration counting." `05-release-and-rollback-design.md` §6.4 states the identical rule a third time for the rollback-triggering case specifically.

**This document's ladder therefore governs a strictly narrower set than "all errors."** A signal is a candidate ladder input only where it is, at the point it is evaluated, reversible and recoverable, breaches no invariant already violated, and carries no Critical vulnerability classification — the three conditions `04-observability-and-monitoring-design.md` §7 already fixes for permitting *any* autonomous reaction at all. Every signal failing any one of those three never enters this document's mechanism; it is not a signal this document classifies, dispositions, or even sees as a candidate — it is intercepted upstream, at the identical point every other Critical bypass in this library already fires, before this document's own §4 classification ever runs.

**This is stated first, and structurally, because it is what keeps correction from becoming compounding.** A mechanism that first checked whether a Critical condition existed and only then decided not to correct it would still have to reason about the condition; a mechanism that never receives the condition in the first place cannot compound it by construction. §8 below returns to this as one of the structural foreclosures rather than a policy this document must separately enforce.

## 4. Error- and Regression-Detection Signals — Consuming the Fixed Payload, Never a Second Vocabulary

Specification §5 enumerates the signals that trigger or forbid a correction. This document classifies each against an already-built mechanism; it defines no signal, no threshold, and no severity of its own.

### 4.1 The Primary Payload

`04-observability-and-monitoring-design.md` §6.1 supplies the concrete payload this document's Rung 1–3 mechanism consumes at the moment a runtime regression signal fires: *"which target breached (the `severity_source` tag, §4.1), the severity attached to it, its measured persistence past the threshold, and whether the tag names an invariant or a guardrail-metric quantification."* This document does not evaluate the payload's own severity or persistence — those are already fixed by that document's own tag mechanism (§4.1 there) — it consumes the payload as given and treats it as eligible for the ladder only where §3's bypass does not already claim it.

### 4.2 The Full Signal Set, Resolved to Already-Built Mechanisms

Specification §5's own table enumerates a broader set than the observability payload alone. Each row resolves to a signal an already-built mechanism produces, never a second evaluation this document performs independently:

Where it cannot be established that the agent's own work holds every guarantee it must, the identical deny-by-default posture every mechanism in this library already applies governs: the work is treated as in error and enters the ladder or escalates, never proceeds on a favorable assumption. This document adds no second uncertainty rule beyond the one specification §5 itself already fixes.

## 5. The Ordered Fallback Ladder

On a signal that clears §3's bypass and resolves, under §4, to a ladder-eligible condition, the agent recovers along the fixed, ordered sequence below. Each rung's precondition, its composition with an already-built mechanism, and the rule that forbids skipping it are stated together, because a rung reached without its precondition established is exactly the compounding-harm failure mode this document exists to prevent.

### 5.1 Rung 1 — Retry

**Precondition.** The condition that caused the original failure has meaningfully changed since the last attempt against it. This is not a determination this document's own mechanism makes independently: `01-agent-runtime-and-control-design.md` §7.1–§7.2 already draws the identical distinction between a legitimate retry (a changed condition) and a repeat (an unchanged one), and already terminates a repeat before this document's own classification runs (§4.2 above). A Rung 1 attempt is, in every structural respect, an ordinary retry under that document's own definition — it is not a second retry concept this document invents alongside it.

**Composition.** A Rung 1 attempt is classified and precondition-cleared through `01-agent-runtime-and-control-design.md`'s existing pipeline exactly as any other action is, under the permitted-autonomous class that document's own §6 names to this document by title: *"Reacting within the autonomous bound. The agent may take a bounded self-correction within the limits `05-meta-operations/07-self-correction-and-fallback-protocol.md` sets... in response to a health signal that permits an autonomous reaction."* Because a Rung 1 attempt genuinely is a retry under that document's own §7.1 definition, it increments **both** the shared iteration counter and the retry counter (§8.1 there: *"every retry pass increments both counters simultaneously"*) — this document adds no third counter and no exception to that rule for the ladder's own first rung. It also draws against `02-token-and-compute-budget-design.md`'s existing accumulators, and re-assembles context under `04-prompt-and-context-assembly-design.md`'s own rule automatically, inheriting that document's own staleness re-verification without this document building a second one.

### 5.2 Rung 2 — Safe Alternative

**Precondition.** A different, in-bounds path to the intended outcome exists that clears every one of `01-agent-runtime-and-control-design.md` §5's five preconditions and holds every invariant and floor in full. An alternative that could reach the outcome only by relaxing a guarantee is not a safe alternative under this document's own rule, and is never taken; the agent moves to Rung 3 or escalates instead.

**Composition.** A Rung 2 attempt is a distinct action from the one that failed — it is not a retry of the same action under a changed condition — so it does not qualify as a retry under `01-agent-runtime-and-control-design.md` §7.1's own definition and increments only the shared iteration counter, never the retry counter. It clears the identical (H42-extended) five-precondition gate any other autonomous action clears, at the identical single interception point, and introduces no exception, no relaxed check, and no second gate.

### 5.3 Rung 3 — Rollback

**Precondition.** `05-release-and-rollback-design.md` §4's own "shown, not assumed" mandatory-rollback-path check finds a path that restores the tier's last known-good state within the applicable recovery-target ceiling of that document's §8, and that path can complete without itself breaching a guarantee (that document's §5.1's third bullet). Where the constraint that document's §5 fixes for a state-changing release cannot be met, that document's own mechanism already refuses the rollback, and it is treated here exactly as any other unavailable or insufficient rung.

**Composition.** Rung 3 invokes `05-release-and-rollback-design.md` §3–§11's mechanism exactly as that document's own §7 already fixes: *"This document owns the rollback mechanism; the ladder owns when it is reached... this document supplies only what Rung 3 executes once reached."* This document does not redesign the rollback path, its triggers, or its recovery target, and does not compute whether a given attempt stays within `05-release-and-rollback-design.md`'s own bounds — that determination is entirely that document's own.

### 5.4 Rung 4 — Human Escalation

**Precondition.** Retry, a safe alternative, and a rollback are each unavailable, insufficient, or exhausted. Escalation is the terminal rung and is not itself a self-correction attempt bounded by the ceiling of §6 — reaching it consumes no further attempt budget.

**Composition.** `03-human-in-the-loop-design.md` owns the request, routing, recording, and resolution mechanics in full; this document states only that this rung is reached, never how the resulting escalation is carried out.

### 5.5 Advancement and the Prohibition on Skipping

**A broader rung is reached only where the narrower ones are unavailable or insufficient — and whether that is so is itself a recorded determination, never a silent judgment call.** This is the identical shape `01-agent-runtime-and-control-design.md` §4.1 already builds for its own non-machine-decidable "outside authorized scope" row: an unrecorded determination that a narrower rung was unavailable is treated as a fail, not as silent permission to skip ahead. An agent may not reach for Rung 3 while Rung 1's own precondition (§5.1) remains establishable, and may not reach for Rung 2 while a legitimate retry (a meaningfully changed condition) is still available — each rung's own unavailability or insufficiency is established and recorded on the acting event's own `result` field before the next rung is attempted, on the identical field every other classification in this library already populates rather than a second record this document invents.

**Each rung re-clears every precondition, on every attempt.** No rung is exempted from `01-agent-runtime-and-control-design.md` §5's five-precondition gate merely because an earlier rung already cleared it once for a different action; each rung attempt is its own autonomous action, clearing the gate anew.

## 6. The Maximum-Attempts Ceiling — Derived, Not Chosen

### 6.1 The Value and Its Status

`03-software-and-architecture/06-non-functional-requirements.md` §10 fixes the ceiling at ≤ 3 autonomous self-correction attempts on a given error, across retry, safe alternative, and rollback combined — never a per-rung allowance of three attempts each. This document keys to that value and mints no number of its own.

**The derivation, read directly rather than assumed.** NFR §10 states the reasoning verbatim: *"the self-correction ceiling is derived: the autonomous ladder has exactly three rungs — retry, safe alternative, rollback — and a fourth attempt re-treads a rung already classified as a no-op rather than a fresh attempt."* The ceiling is exactly the ladder's own length, fixed by this document's own structure (§5 above), not an independently chosen number.

**This status is carried forward, not merely cited once.** NFR §13's own Binding Rules distinguish the derived value from the iteration ceiling and both token envelopes, which are judgments revisable on first operating data: *"The self-correction ceiling in the same table is derived from the fixed length of the autonomous ladder and carries no such revision expectation."* Unlike the iteration ceiling `01-agent-runtime-and-control-design.md` keys to and the envelopes `02-token-and-compute-budget-design.md` keys to — each correctly carried as a configured, revisable value by those documents — this document's own ceiling is never cited as awaiting revision on operating data; a future revision to it would have to change the ladder's own length (adding or removing a rung), not merely retune a number.

### 6.2 A Repeated Ineffective Correction Earns No Fresh Attempt

Consistent with the derivation above, a retry against an unchanged condition, or a rung attempt that makes no traceable progress, is a no-op under `01-agent-runtime-and-control-design.md` §7.2 and is caught, and terminated, by that mechanism before it ever reaches this document's own attempt counter — it is never counted as a fresh attempt against the ceiling, because it was never a legitimate rung attempt in the first place (§5.1, §4.2 above).

### 6.3 Nested Within the Outer Bounds, Never Independently of Them

The attempt ceiling bounds the ladder from within; the iteration ceiling and the token, compute, and cost envelope bound it from without, exactly as `01-agent-runtime-and-control-design.md` §8.2–§8.3 already fixes: every rung attempt increments the shared iteration counter identically to any other pass, and the worst-case nesting NFR §10 fixes (three retry-ceiling passes plus three self-correction attempts, ≤ 6 of the task's 10 iterations) is enforced by that shared counter's own construction, not by a second computation this document performs. Whichever bound — this document's own attempt ceiling, the iteration ceiling, or the token envelope — is reached first ends autonomous correction and escalates (§7 below); this document never widens its own ceiling to compensate for headroom remaining in another.

## 8. Without Compounding Harm — How the Mechanism Forecloses It Structurally

Specification §3 defines compounding harm as "worsening the condition a recovery exists to resolve — spreading it, breaching a guarantee to reach recovery, or advancing into a state that cannot be safely left." This document's real safety property is not an instruction to the agent to be careful; it is the structural fact that every path by which a correction could compound harm is closed **before** the correction executes, not detected after.

- **Spreading the condition is foreclosed by §3's bypass.** A signal that has already crossed into Critical or invariant-violating territory never reaches this document's mechanism at all; there is no rung this document could invoke on exactly the condition where a wrong correction would do the most damage, because the ladder is never offered the chance.
- **Breaching a guarantee to reach recovery is foreclosed by precondition 3 of `01-agent-runtime-and-control-design.md` §5.1, checked before every rung executes, not after.** Every rung — retry, safe alternative, or rollback — clears that precondition as part of the identical gate any other autonomous action clears; a correction that would breach an invariant fails the check and never executes. This is not a rule the agent could choose to disregard: the gate is the single interception point that decides whether the action's `outcome` may ever transition to `applied` at all (`01-agent-runtime-and-control-design.md` §5.4, §16).
- **Advancing into an unrecoverable state is foreclosed by the identical gate's precondition 4 (INV-08).** A rung that could only proceed by leaving the platform in a state it cannot safely leave fails the reversibility precondition before it executes, for the identical structural reason.
- **Repeated ineffective correction is foreclosed by the attempt ceiling (§6) and the no-op detection it composes with (§6.2), not by an instruction to stop trying.** A retry against an unchanged condition never reaches the point of consuming a fresh attempt at all.
- **A rung that would need to over-correct or under-correct is foreclosed by the no-skip rule (§5.5).** A rollback attempted while a retry remains genuinely available is refused at the point that determination is checked, not discovered as a mistake afterward.

**The residual limit, stated plainly.** This foreclosure holds only for harm this library's own invariants, floors, and reversibility guarantee can register. A correction whose worsening is not expressible as an invariant breach, a guardrail-metric violation, or an irreversibility — a purely opportunistic or reputational cost with no attached floor — is not caught by any precondition this section names, because no mechanism in this library's own scope classifies it as a guarantee to protect. This document does not close that gap, and does not claim to; it forecloses compounding harm exactly to the extent this library's own guarantees define what harm is.

`08-audit-and-traceability-design.md`'s own ADR-025 Consequences bind the charter and its two cited protocols "to place the minimum-traceability check's mechanical interception point in the agent's own execution pipeline, and to emit one event per self-correction-ladder rung." `01-agent-runtime-and-control-design.md` §5.4 already discharged the first half concretely. **This document discharges the second half.**

### 10.2 The Reconciliation the Ticket Asks For, Resolved Explicitly

**"One event per rung" (ADR-025's Consequences, and §8's own binding rule quoted at this document's front matter) and "Rung 3 mints nothing new" (`05-release-and-rollback-design.md` §14) both hold, because they answer two different questions.** "One event per rung" is a **cardinality** requirement: every rung attempt — whichever rung — produces its own distinct `event_id`, sequenced within the task's own stream, so the full ladder is reconstructable from the events alone, exactly as `08-audit-and-traceability-design.md` §8 requires. "Rung 3 mints nothing new" is a **taxonomy** constraint: which discriminated `event_type` a given rung's own event uses is determined by which already-existing mechanism that rung actually invokes, never by which position it occupies in the ladder. Rungs 1 and 2 invoke the generic kernel pipeline and therefore produce the generic `autonomous-change` type; Rung 3 invokes `05-release-and-rollback-design.md`'s own specifically-shaped mechanism and therefore produces that mechanism's own already-existing type. **Both rules are satisfied at once because neither one is actually about the other's dimension**: every rung attempt is its own event (cardinality, satisfying ADR-025), and no rung invents a type the mechanism it invokes did not already have (taxonomy, satisfying `05-release-and-rollback-design.md` §14). Treating "one event per rung" as though it meant "one new event *type* per rung" would have forced a fabricated Rung-3-specific type in direct contradiction of that document's own inheritance rule; this document takes neither side of a false choice, because the two rules were never in conflict once cardinality and taxonomy are held apart.

### 10.3 What This Section Does Not Introduce

No detection classification (§4), no bypass determination (§3), and no forbidding-condition halt (§7) produces a separate event of its own beyond the acting rung's own already-described event: each finding lands on that same event's `what_was_inspected` and `result` fields, exactly as every prior document in this library already folds a further finding into an action already producing an event rather than minting a second record of the same occurrence.

This is the identical H26c test every prior design document in this library applies: a genuinely new definitional fact would justify a new type; a recurrence under an already-typed mechanism does not, and every fact this document's own mechanism needs is the latter.

## 13. Precedence and Ownership Boundaries

## 14. Binding Rules

These rules hold for every recovery this document's mechanism governs and are subordinate to the specification and the charter.

- **A Critical or invariant-violating signal never reaches this document's mechanism at all.** The observability bypass is checked first, structurally, before any detection signal, rung, or ceiling; this is the boundary that keeps correcting from becoming compounding, stated as mechanism, not as an instruction to be careful.
- **Every detection signal is classified against an already-built mechanism; this document mints no signal, no threshold, and no severity of its own.**
- **Each rung's precondition is established from an already-built check, and a rung's own unavailability or insufficiency is a recorded determination, never a silent judgment.** An unrecorded skip is treated as a fail, on the identical deny-by-default posture every judgment call in this library already applies.
- **A rung attempt clears every precondition of `01-agent-runtime-and-control-design.md` §5 anew, on every attempt; no rung is exempted because an earlier rung already cleared the gate for a different action.**
- **The attempt ceiling is derived from the ladder's own three-rung length, never chosen, and carries no revision expectation on new operating data — a status distinguished explicitly from the iteration ceiling's and the token envelopes' own judgment status.**
- **A repeated ineffective correction earns no fresh attempt.** A retry against an unchanged condition, or a rung with no traceable progress, is caught and terminated as a no-op before it is counted.
- **Every forbidding condition routes to the identical hard-stop mechanism `01-agent-runtime-and-control-design.md` already built and `02-token-and-compute-budget-design.md` and `03-human-in-the-loop-design.md` already reused; this document builds no fifth implementation.**
- **Compounding harm is foreclosed by preconditions checked before a rung executes, never detected after — with the honest residual limit that harm this library's own guarantees do not classify is not caught by any mechanism this document owns.**
- **The ladder's own attempt count and current rung are reconstructed on resume from the task's own audit stream, scoped per detected error, using an already-existing field and an already-existing comparison mechanism; no new structure is owed.**
- **"One event per rung" is a cardinality rule; which discriminated type a rung's event carries is a taxonomy question answered by which already-existing mechanism that rung invokes.** Rungs 1 and 2 produce `autonomous-change` events; Rung 3 inherits `rollback-executed`; Rung 4 inherits `03-human-in-the-loop-design.md`'s own outcome vocabulary. This document mints no new event type.
- **A self-correction and an incident response are two distinct instruments that may invoke the same rollback or retry action for different reasons; neither absorbs the other.**
- **The boundary against `07-change-management-and-evolution-design.md`, the one not-yet-written Layer 6 sibling, is stated from this document's own side, and that document may not proceed as though this document's own mechanisms were still open for it to shape.**
- **Everything in this document remains platform-layer only.** No detection rule, ladder rung, attempt ceiling, or forbidding condition governs what a builder configures inside their own built artifact; the builder/built separation the specification's own §2 fixes holds throughout.
