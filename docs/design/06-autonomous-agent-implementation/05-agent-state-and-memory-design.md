## 4. Preconditions Bind Every Persistence, Resume, and Handoff — Which Shape This Document Takes

Specification §4's own text, quoted in full in this document's front matter, states that persisting, resuming, and handing off state are each themselves autonomous actions subject to charter §5's five preconditions. Four documents have already positioned themselves relative to H41's precondition-clearing gate and its single interception point: **H41 built the gate** (§5 there); **H42 extended what must be true for any action to become `applied`**, adding an ANDed budget-sufficiency condition at that one point (§7 there); **H43 produced freestanding new instances of ordinary autonomous action** — its own request, record, and resumption actions — that clear the existing, H42-amended gate unchanged, adding no further condition to it (§8 there); **H44 found itself temporally upstream of classification entirely**, a prerequisite step whose own outcome determines whether classification ever runs (§4 there). This document tests its own actions against all four shapes rather than assuming one.

### 4.1 Reconstruction Introduces No Action at All

The mechanism §5.1–§5.2 below builds — recomputing a counter's or a task accumulator's current value from the task's own audit stream — is not an action of any of the four shapes above, because it is not an action. It is a **read** of content H41's and H42's own gate already writes at their own, already-cleared interception point (H41 §5.4; H42 §7.2). Nothing is proposed, evaluated, or applied by reading an already-written record; there is no proposal to classify, no precondition to clear, and no gate to compose with. This is the identical reasoning H41 §7.2 already applied to its own loop-detection comparison — a read over already-captured records, not a second write — extended here to a resume's own counter values.

### 4.2 The Session Accumulator's Own Write Is Folded Into an Already-Gated Action, Not a Separate One

The one genuinely new structure this document owes (§5.3, §9) is written once per iteration, at the identical timing H42 §6.1 already fixes for its own task accumulator's update — "metered and updated at the identical per-pass boundary... by the actual measured token count that specific action drew." This document's own session-accumulator increment rides the same already-gated action's own execution; it is not a second, independently classified action any more than H42's own task-accumulator update is. No new interception point is introduced, and no fourth extension of H41's gate content is added — H42 remains the gate's sole extension (H43 §8 already confirmed this and this document does not disturb it).

### 4.3 Resume and Handoff, Where Not Already H43's, Are H43's Shape Extended to Two Further Triggers

Specification §7's own resume and handoff requirements are broader than the one trigger H43 designed for: H43 built request, record, and resumption **for the approval-pending case specifically**. This document's own subject includes a resume triggered by an interruption or a session boundary with no approval involved, and a handoff to another execution context or process that is not an escalation to a human. Neither is a new shape: each is realized as **the identical H43 shape** — an ordinary new instance of autonomous action that clears the existing, H42-amended gate unchanged, adding no further condition to it — triggered by a different condition than H43's own approval-resolution trigger. Where the trigger *is* specifically an approval resolution or an escalation, H43's own mechanism governs it in full, exactly as already designed, and is not redesigned here (§7 below states the composition precisely).

**The finding, stated plainly:** this document introduces no fifth shape and extends H41's gate content no further than H42 already has. Two of its four mechanisms (reconstruction, the session-accumulator write) introduce no new action at all; the other two (a non-approval-triggered resume, a non-escalation handoff) are H43's own shape, applied to triggers H43 did not itself need to cover.

## 5. What May Be Persisted — the Inherited Inventory, Resolved

Specification §5's own table enumerates what may and may not be persisted, keyed to the document that owns each bound; it is cited, not restated here. Three prior documents each deferred a specific item from that table to this document because they could not resolve it themselves; a fourth checked the identical boundary and found it owes this document nothing. Each is resolved individually below.

### 5.1 H41's Iteration and Retry Counters — Reconstructed From the Task's Own Stream, Never Independently Persisted

H41 §11 found its own iteration and retry counters to be "working state the agent process holds during continuous execution," genuinely `05-agent-state-and-memory-design.md`'s subject, and stated the boundary this document must not absorb without stating: "whether and how that count survives a resume after an interruption is that document's to design, not absorbed here."

**The resolution.** During continuous execution within one uninterrupted pass, the two counters remain exactly what H41 found — in-process values, held only for the duration of the task's own continuous run, needing no durable store of their own. **On any resume** — after a pause, an interruption, or a session boundary — the resuming process does not read a remembered or separately-persisted value. It **recomputes each counter's current value by reading the task's own already-captured audit stream**, scoped to this task alone via the `actor_reference` field `08-audit-and-traceability-design.md` §4.2 already fixes to resolve "the acting identity or agent process and its triggering task/condition": the iteration counter's value is the count of `autonomous-change`/`invariant-check` events already captured for this task, counted regardless of outcome, exactly as H41 §7.1 already counts a pass "regardless of the outcome (proceed, refuse, halt)"; the retry counter's value is the count of those same events already marked as a legitimate retry pass under H41 §7.1's own distinction. **No new field, no new event type, and no independently-writable counter row is introduced.** This is not a restatement of H41's own loop-detection mechanism (§7.2 there, which compares adjacent iterations within one continuous run) — it is the same principle, reading, applied at a different moment: not *has this iteration repeated the last one*, but *what is the true count so far*, both answered from the identical already-captured, already-attributed, already-ordered stream.

**Why this discharges H41's own deferral rather than merely restating it.** H41 explicitly left open *whether and how* a count survives a resume; this section states the *how*, concretely, as a design decision this document is answerable for — a reconstruction algorithm keyed to `actor_reference` and `sequence_no`, never a claim that the question resolves itself.

### 5.2 H42's Task Token Accumulator — the Identical Reconstruction, a Different Quantity

H42 §10 found its own task token accumulator to be, "identical reasoning to H41 §11's own finding for the iteration and retry counters," working state resetting to zero at task start, not surviving past the task's own end.

**The resolution.** The identical mechanism §5.1 builds applies here unchanged in shape, differing only in what is summed rather than counted: on a resume, the task accumulator's current value is recomputed as the sum of the measured token consumption already recorded on this task's own `autonomous-change` events (the content H42 §7.2, §9.2 already places on that event's own fields), scoped by the identical `actor_reference` filter. This is the concrete answer to the identical deferral H42 §10 left open for its own accumulator, on the same grounds §5.1 already states for H41's counters — a genuinely new definitional mechanism (reconstruction from the record) applied a second time to a different quantity, never a second, independently-invented mechanism.

### 5.3 H42's Session Token Accumulator — the Sharper Requirement, and the One Genuine Difference

H42 §10 flagged its own session accumulator explicitly as needing more than its task accumulator: it "must survive across every task the session contains," a session accommodating "roughly four full tasks" per `DECISIONS.md` D-24's own criterion 5, verified directly in that source (front matter above). H42 handed this document that requirement "with the explicit requirement that its persistence mechanism span task boundaries within one session, a stronger requirement than the per-task-only lifetime H41's own counters carry."

**Why the reconstruction mechanism of §5.1–§5.2 does not extend here.** Reconstruction depends on one structural fact: `08-audit-and-traceability-design.md` §4.2 fixes `actor_reference` as resolving to "the acting identity or agent process and its triggering task/condition," and that document's §8 renders the identical fact for the autonomous-agent case as resolving to "the specific agent process identifier and the specific triggering task or condition" — which is exactly what makes a **per-task** filter over the stream sufficient to isolate one task's own events. **No field on the base record correlates events across multiple tasks belonging to one session** — `actor_reference` names a process and a task, never a session as a third, independent dimension. Reconstructing a session total would therefore require either assuming one agent process maps to exactly one session (an assumption this document has no citation to make, and one the resume mechanism itself must not depend on, since a session surviving a process restart is exactly the case a session boundary names in specification §3's own definition of a resume), or scanning the stream for every task any given process or actor has touched and testing session membership by inference — the identical full-stream-scan pattern H43 §10.2 already rejected for its own, structurally analogous case, and rejected for a reason that applies with equal force here: **this value is read at the identical high frequency H42 §6.1 already fixes** — once per iteration, of every task, for the life of the session — never once per resume, the far rarer frequency §5.1–§5.2's reconstruction actually runs at. A per-iteration full-stream aggregation is not the occasional reconstruction those two sections perform; it is the routine access pattern H43 §10.2 already found the audit stream's own append-only, per-stream structure is not shaped to serve cheaply.

**The resolution: this document owes a new structure.** Unlike H41's and H42's task-scoped values, and unlike H43's pending-approval record (which needed a structure for entirely different reasons — human-findability and independent resolvability, never present here), the session accumulator needs a structure because the fact it must answer — a running total across an open-ended, still-accumulating set of tasks, read at every iteration of every one of them — is not one the audit stream's own already-fixed correlation fields make cheaply derivable, and inventing a new correlation field on that record is this document's to name as a requirement, never its own schema to redesign (`08-audit-and-traceability-design.md` owns that schema in full, §2 above). §9 below names this structure precisely, on the identical precedent H43 §10.3 and H45's own §9.1 (`BACKLOG.md` §1aa) already set.

### 5.4 H44's Assembled-Context Reference List and Currency Markers — Nothing Survives a Resume, Because Nothing Needs To

H44 §9 found its own assembled-context reference list and per-item currency markers to be working state, "identical in kind to H41's own iteration and retry counters," existing "only for the duration of the pass that produced it," and handed both to this document.

**The resolution differs from §5.1–§5.2, and the difference is the point.** H44 §8.2 already states, as its own general currency rule, that "on every iteration H41 §7.1 counts, assembly's own currency (§8.1 above) is re-established before that iteration's classification and precondition-clearing run" — including the very first iteration after a resume, which H44's own text does not treat as a special case requiring anything different from any other iteration. Because assembly is **always** re-run fresh, on every pass, whether or not a pause preceded it, there is no gap for a persisted or reconstructed copy to fill: the mechanism that would carry the list across a resume already does not exist for any other iteration either, and inventing one only for the resume case would create exactly the two-tier inconsistency H44's own rule is designed to prevent. **This document therefore designs no persistence, and no reconstruction, for the assembled-context reference list or its currency markers.** The correct resolution is not a mechanism but a confirmation: H44's own rule already covers the resume case in full, and this document adds nothing to it.

### 5.5 H43's Pending-Approval Record — Confirmed, Not Absorbed

H43 §10 checked the identical boundary this document now checks for every other inherited item, and reached the opposite finding for its own case: the pending-approval record "must outlive the agent session, and often the task, that raised it," "must be findable by the human who resolves it, not only reconstructable by the agent that raised it," and "must be durable and independently queryable" — three properties none of §5.1–§5.3's items share, because each of those is read only by the resuming agent process itself, never by a third party who was never part of the raising session. H43 accordingly bound the structure to `02-platform-data-model-design.md` directly, never to this document.

**This document confirms that boundary rather than absorbing it.** The pending-approval record is platform-schema content on H43's own reasoning, not working state on this document's; nothing in §5.1–§5.4 revisits that finding, and this document adds no second claim on the structure H43 already named. The connection between the two documents runs the other way: §7 below states precisely how this document's own resume mechanism supplies the counter and accumulator values H43 §6.2's resumption re-verification list already requires to be checked.

## 6. State-Integrity and Provenance Rules

Specification §6 requires that carried state be attributable, reconciled against the reconstructable record rather than the agent's own memory, intact between write and use, traced through any change as an appended transition, and treated as stale or unattributed wherever any of those cannot be established. This document realizes each requirement as a further use of a mechanism already built, never a second scheme.

### 6.1 Provenance Is the Identical Attribution Mechanism, Read, Never a Second Scheme

"Every piece of carried state carries its provenance," per specification §6, realized here as: the reconstructed counters and accumulators of §5.1–§5.3 carry no provenance field of their own, because their own value **is** a function of already-attributed content — every event summed or counted already carries `actor_reference` and `source_mechanism` (`08-audit-and-traceability-design.md` §4.2) fixing the specific process, task, and mechanism that produced it. A reconstructed value's provenance is therefore never a separate fact to establish; it is inherited automatically from the records it was computed over, and is exactly as attributable as the least-attributable record among them — which, per that document's own attribution rule (§3.1: "An action whose initiator cannot be resolved is captured as unattributed"), is never less than fully attributed for any event the gate already admitted.

### 6.2 A Second Provenance, Never the Same One

`09-ai-assisted-builder-tooling-design.md` (H45) fixed a distinct provenance vocabulary — `ai-suggested` and `builder-approved` — carried on a suggestion record, describing where a **committed artifact** originated. This document's own provenance, per specification §3's own definition ("the record of where a piece of state came from, when, and under whose authority and trigger"), describes where a piece of **working state** came from — a counter's value, an accumulator's total — never a committed artifact's origin. **The two share no vocabulary.** Nothing in this document's mechanism uses, reads, or writes `ai-suggested`, `builder-approved`, `pending`, `confirmed`, or `discarded`; nothing in H45's mechanism reads a counter or an accumulator. They are two instances of the specification-level concept "provenance," applied to two disjoint subjects, realized by two entirely separate mechanisms, and this document keeps them separate explicitly rather than letting the shared word invite conflation.

### 6.3 Integrity — Intact Because There Is Nothing Separate to Diverge

Specification §6 requires persisted state remain "valid, consistent, and uncorrupted between the point it is written and the point it is used." For the reconstructed values of §5.1–§5.2, this holds by construction: because no independent copy of a counter or a task accumulator is ever written, there is no window between a write and a later use in which the two could diverge — every use recomputes from the same authoritative source, at the moment of use, per the identical rule specification §6 itself states ("the reconstructable record is authoritative, not the agent's memory"). For the session accumulator of §5.3 — the one genuinely independent, mutable-by-increment value this document introduces — integrity is protected two ways: **first**, it is written only at the identical single point H42 §6.1 already fixes for its own task-accumulator update, never a second write path, so no code path exists by which the two could be updated inconsistently with each other; **second**, because the audit event recording that same action's own token consumption is emitted synchronously, "at the moment the action is evaluated or its outcome is finalized" (`08-audit-and-traceability-design.md` §3.2), the session accumulator's own value and the stream's own token-consumption content for the identical span are never more than one already-atomic action apart. Where a divergence is ever detected between the session accumulator's stored value and what the session's own task set would sum to — a corruption, a missed increment — it is treated exactly as specification §6 requires: not integral, re-derived from the authoritative stream for the affected span before being trusted again, never assumed correct by default. This is a bounded, divergence-triggered reconciliation, never the routine per-iteration scan §5.3 already rejected as the accumulator's normal operating mode.

### 6.4 Uncertainty Resolves Against Trusting the State

Where the reconstruction of §5.1–§5.2 encounters a gap in the task's own stream — a broken position in the `sequence_no` ordering, or a hash-chain mismatch of the kind §6.3 there mechanizes and §13's own Binding Rules summarize as detecting "alteration, deletion, and reordering from the anchor's own point forward" — the counter or accumulator value is not estimated, interpolated, or assumed favorable; the read fails closed, exactly as H41 §5.2 already requires for any of its own five precondition reads that cannot be completed, and the condition routes to the identical halt-and-escalate mechanism H41 §5.4, §8.5 and H43 §3.1 already build — this document invents no second halt vocabulary of its own, consistent with H43 §3.1's own finding that a halt is H41's mechanism reused, never rebuilt. Where the session accumulator's own row cannot be read at all, it is treated as exhausted, never as empty — the identical deny-by-default posture H42 §3.3 already fixes for its own accumulator ("the accumulator's value cannot be established... is never treated as a favorable default"), applied here to the structure this document adds.

## 7. Safe Resume and Handoff — Composing With H43 §6 and H44 §8, Never a Third Rule

Specification §7 requires a resume proceed only from a trustworthy checkpoint, re-clear every precondition, treat stale state as missing, and — for a handoff — carry only what is needed and nothing prohibited. Two already-fixed rules already govern most of this ground; this document's own contribution is the substrate those two rules read, not a third, competing rule.

### 7.1 What This Document Supplies to H43's Own List

H43 §6.2 already fixes precisely what a resumed action must re-verify, including — quoted in full in this document's front matter — "H41's own loop-guard counters. A resumed action still consumes one iteration; if the task's iteration or retry ceiling was reached by other work while this request was pending, the ceiling still governs." That sentence presupposes a true, current counter value is available to check against the ceiling at the moment of resume. **§5.1–§5.2 above is precisely where that value comes from.** This document builds no new resumption rule alongside H43's; it supplies the one input H43's own rule already names but does not itself produce — the reconstructed counter and accumulator values a resumed action's re-verification pass reads before it proceeds. The same holds for H43's own budget-sufficiency re-verification ("H42's own budget-sufficiency check... a resumed action that was affordable at request time may not be affordable at resolution time") — the task and session accumulators §5.2–§5.3 make available are exactly what that check reads.

### 7.2 This Document's Own Currency Rule Is H44's, Applied to a Different Subject

H44 §8.1–§8.2 already generalizes staleness detection as reconciliation against the reconstructable record's own ordering, and states explicitly that this is "the general form" of H43's own narrower resumption list. §5.1–§5.2's reconstruction mechanism is a further instance of that identical principle — applied not to a governing document's own content (H44's subject) but to a counter's or accumulator's own current value (this document's subject). **This document does not compete with H44's rule or add a second definition of currency**; it is the same reconciliation-against-the-record principle, read a third time, for a third subject, exactly as H44 §8.2 itself frames its own relationship to H43 ("it is not a competing rule").

### 7.3 A Resume Not Already H43's Own Trigger

Per §4.3 above, a resume triggered by an interruption or a session boundary — never an approval resolution — is realized as an ordinary new instance of autonomous action, clearing the existing gate unchanged, applying the identical re-verification discipline H43 §6.2 already lists (every one of H41's five preconditions, H42's budget sufficiency, H41's loop-guard counters, any newly-arisen Critical condition) against the values §5.1–§5.3 make available. Where the trigger *is* specifically an approval resolution, H43's own mechanism governs the resume in full, exactly as designed, and this document adds nothing to that case beyond the counter and accumulator values §7.1 already states it supplies.

### 7.4 A Handoff Is a Transfer of References, Never of Content

Specification §7 requires a handoff carry "the reconstructable state of the work, its provenance, its progress toward termination, and any authorization it rests on" while never carrying a secret, sensitive data, cross-tenant state, or residency-violating state. Because §5.1–§5.3's own mechanism already holds nothing but opaque references and numeric totals — a task identifier, a session identifier, the `sequence_no` position the receiving context should reconstruct from, and, where relevant, an `approval_reference` H43 already fixes — a handoff realized as the transfer of exactly those references, and nothing else, trivially satisfies the prohibition: **there is no content in the payload for the prohibition to apply to.** The receiving execution context does not receive a copy of the counters, the accumulator totals, or the assembled-context list; it receives the identifiers necessary to reconstruct or read each one itself, through the identical mechanisms §5.1–§5.4 already build. Where a handoff is an escalation to a human, `03-human-in-the-loop-design.md` owns the routing, recording, and resolution in full, exactly as specification §7's own text assigns it there, and this document adds nothing to that case. Reproducibility (specification §3) follows directly from this design: because reconstruction is a deterministic function over an immutable, ordered stream, any two reconstructions from the same reference yield the identical result, by construction, never a divergent one dependent on unrecorded state.

## 8. The Prohibition on Retaining Sensitive Data in Memory

### 8.1 No Field Exists to Hold What Is Prohibited

Every structure §5 fixes — the reconstructed counters and accumulators of §5.1–§5.2, and the session-accumulator row of §5.3 (named precisely at §9 below) — carries only numeric totals and opaque identifiers: a count, a token sum, a task or session reference, a `sequence_no` position. **None carries a content field of any kind.** A secret cannot be retained in a structure with no field capable of holding arbitrary content; the same holds for personal or sensitive data. This is the identical structural guarantee `08-audit-and-traceability-design.md` §3.1 already establishes for its own base record ("no event ever inlines directly-identifying content as its means of attribution... every actor and target reference is an opaque identifier") — inherited here rather than independently re-argued, because every value this document's own mechanism reads or writes is already governed by that guarantee before this document touches it.

### 8.3 Composition, Never a Second Classification

Where this document's own reasoning needs to state what "personal or sensitive data" or "a secret" means, it cites `02-governance-and-security/02-security-policy.md` §4 and `07-data-governance-and-privacy-design.md` §3–§8 and defines nothing of its own. ## 13. Precedence and Ownership Boundaries

- **The charter prevails**, and the specification this document realizes prevails over this design wherever the two appear to conflict; this document is corrected to match the specification, never the reverse.
- **No reconstruction, accumulator, resume, or handoff is ever trusted over the record it was derived from.** Where a value this document's mechanism produces and the audit stream it was derived from disagree, the stream governs, consistent with specification §6's own rule that the reconstructable record, not the agent's memory, is authoritative.
- **The prohibition on retention is never relaxed to make a resume, a handoff, or a reconstruction more convenient.** No structure this document fixes ever gains a content field to carry a secret, personal or sensitive data, cross-tenant state, or residency-bound state, regardless of the convenience it would offer; uncertainty resolves toward not retaining, never toward proceeding.

## 14. Binding Rules

These rules hold for every element of this document and are subordinate to the specification and the charter.

- **A counter's or an accumulator's current value is reconstructed from the task's own already-captured audit stream on every resume, never trusted from a remembered or independently-persisted copy.** This holds for H41's iteration and retry counters and H42's task token accumulator alike; no independent counter or task-accumulator row is ever introduced.
- **The session token accumulator is the one item genuinely owed a new structure, because no field correlates events across the multiple tasks one session spans, and reconstructing it at the frequency it is read would repeat the full-stream-scan pattern this library has already rejected once.** It is written only at the identical single point the task accumulator is already updated, never a second write path.
- **The assembled-context reference list and its currency markers are never persisted, by this document or any other — because they are already re-derived on every iteration, a resume creates no gap for a persisted copy to fill.**
- **The pending-approval record remains `03-human-in-the-loop-design.md`'s own obligation to `02-platform-data-model-design.md`, confirmed here, never duplicated or reassigned.**
- **Reconstruction and the session-accumulator write introduce no new autonomous action; a resume or a handoff not already `03-human-in-the-loop-design.md`'s own is that document's identical shape, applied to a different trigger — never a fourth extension of the kernel's gate content, and never a fifth precondition shape.**
- **This document's own provenance and `09-ai-assisted-builder-tooling-design.md`'s artifact provenance share no field, vocabulary, or mechanism.** One describes where a piece of working state came from; the other describes where a committed artifact came from, and the two are never conflated.
- **State integrity rests on the audit stream's own already-fixed attribution, ordering, and tamper-evidence, never on a second, independently-computed guarantee.** A divergence between a maintained value and what the stream would independently support is treated as an integrity failure, re-derived before being trusted again, never assumed correct by default.
- **A handoff transfers only opaque references — a task, a session, a stream position, an approval reference where one exists — never content.** This is what makes the prohibition on carrying a secret, personal or sensitive data, cross-tenant state, or residency-bound state hold by construction rather than by a check this document must separately enforce.
- **No structure this document fixes carries a field capable of holding a secret, personal or sensitive data, cross-tenant state, residency-bound state, or domain content.** Uncertainty about whether a value is free of any of the five resolves toward not persisting it, never toward proceeding.
- **This document mints no new stored schema beyond the one obligation of §9, and no new audit-event type.** Every other fact its own mechanism needs is either an already-existing, already-durable audit-stream record, read and never duplicated, or genuinely never persisted at all.
- **The boundary against every not-yet-written Layer 6 sibling is stated from this document's own side, and none may proceed as though this document's own mechanisms were still open for it to shape.**
- **Everything in this document remains platform-layer only.** No persistence, resume, handoff, or retention rule governs what state a builder configures inside their own built artifact; the builder/built separation the specification's own §2 fixes holds throughout.
