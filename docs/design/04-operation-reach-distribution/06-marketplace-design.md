# Marketplace Design — AI ahaMatic

This document realizes `01-business-and-ux/02-prd.md`'s C-13 row and `03-software-and-architecture/05-integration-and-extensibility-spec.md` §6 as concrete mechanism: the means to offer and obtain published software and extensions with every platform guarantee preserved across what is offered, the offering and obtaining mechanism itself, and the discoverability model. This is a Design-phase artifact realizing, in addition to `01-business-and-ux/02-prd.md`'s C-13 row and `03-software-and-architecture/05-integration-and-extensibility-spec.md` §6 in full (plus §4 and §7, cited for the boundary rules and trust-boundary confinement dimensions this document composes with rather than redefines): `02-governance-and-security/03-access-control-and-tenancy-model.md` §7 in full (the sole-mediated-interaction rule), plus §5 and §8; `06-integration-and-extensibility-design.md` in full, especially §5, §8, §9, and §10 (the Extender-origin trust mechanism this document adopts for one marketplace shape, and the explicit statement of availability, not decision, for the marketplace origin); `04-publishing-and-delivery-design.md` in full (the reachability model this document never re-implements and the bidirectional boundary its own §11.2 already states); `02-tenant-isolation-and-access-control-design.md` §3, §5, §6, and §8 in full (the structural-impossibility argument this document's exchange mechanism must not break); `04-security-controls-design.md` §5 in full (the platform-team-only scope of the existing review-trigger manifest, and the explicit open question for this document); `09-licensing-and-dependency-compliance-design.md` §3, §4, §5, §6, and §7 (the license-category, dependency-policy, attribution, and incompatibility mechanisms this document composes with rather than rebuilds); `03-architecture-realization-design.md` §3.1, §4.1, and §10 (the Extension component's registry, the dependency-direction rule this document's own mechanism is checked against, and the three-origin authorship finding); `02-platform-data-model-design.md` §3 in full (the schema hierarchy this document constrains and hands one addition to); and `08-audit-and-traceability-design.md` §4.2 and §4.3 (the consolidated audit event model this document's evidence populates). ## 1. Purpose and Reading Order

This document answers six questions:

- **How an artifact moves from one tenant to another when no structure joining two tenants exists anywhere in this design** — the structural problem this document exists to solve, stated first because every later section is checked against it (§3).
- **What isolation strength and review mechanism a marketplace submission requires** — the trust determination two prior documents each deferred here by name, made on this document's own terms (§4).
- **How the six submission constraints the specification fixes are satisfied** — composing with an existing mechanism wherever one exists, and designing only the one that is genuinely this document's own (§5).
- **What offering and obtaining actually do**, for each of the three shapes a marketplace item may take, and how an item is found (§6).
- **Which of the platform's guarantees hold across an obtained item, and what preserves each one** (§7).
- **What this document owns relative to the connector marketplace (C-25), and what that document must still determine for itself** (§9).

It is structured as a pyramid: the structural problem and its resolution first, because every later mechanism must be checked against it; then the trust determination that resolution makes possible to state precisely; then the six submission constraints realized against both; then the offering, obtaining, and discoverability mechanism; then guarantee preservation; then the evidence this mechanism produces; then the connector-marketplace boundary; then where marketplace state lives; then the design decision record, and the closing sections.

## 3. The Structural Problem: An Artifact Crosses a Tenant Boundary Where No Structure Joins Two Tenants

### 3.1 The Problem, Stated Precisely

`02-governance-and-security/03-access-control-and-tenancy-model.md` §7 fixes the marketplace as "the sole mediated interaction between one builder and another" and, in the same breath, that it "is not an exception to tenant isolation": a tenant that offers or obtains software or extensions does so "through an explicit, mediated exchange of published artifacts, never by granting another tenant direct reach into its data, configuration, or environment." `02-tenant-isolation-and-access-control-design.md` §8 restates the same conclusion from the mechanism's own side: a marketplace transaction "exchanges a published artifact — an object one tenant obtains, not a grant that lets it reach into another tenant's own schema, connection, or registry visibility." Both documents state the shape the exchange must take. Neither designs the mechanism that takes it.

`02-tenant-isolation-and-access-control-design.md` §8 also fixes why this is hard: cross-tenant access is not merely forbidden by policy, it has **no structural path to occur**, because all three of the following hold at once — no naming path (no table, view, or foreign key in this design can name two tenants together, `02-platform-data-model-design.md` §4.1), no grant path (the connection-scoping mechanism grants a connection privilege only on the schemas the Resolved Request Context resolves for the current actor, `02-tenant-isolation-and-access-control-design.md` §5.1), and no silent path (the mandatory self-verification read would catch a mis-scoped connection before any cross-tenant data is returned, §5.2). **A marketplace design in which any of these three facts would have to fail for the exchange to work has broken the invariant the whole isolation model rests on.** This is the test every mechanism below is checked against.

### 3.2 The Resolution: A Deposit, Not a Door

**An offering is a deposit, not a door.** The offering tenant, using nothing but its own already-legitimate access to its own data, produces an immutable, platform-owned copy of what it offers. The obtaining tenant, using nothing but its own already-legitimate authority to construct or register within its own tenant, produces a new instance from that platform-owned copy. At no point does any actor's connection, grant, or query ever need to name, address, or resolve into a schema belonging to a tenant other than its own.

This resolves into two steps, and the boundary between them is exactly where the marketplace's own mediation lives:

| Step | Who Performs It | Whose Connection Is Active | What It Produces |
|---|---|---|---|
| **Deposit** (at offering) | The offering tenant's own Publisher-role actor, inside its own already-resolved request. | The offering tenant's own already-scoped connection — the same one it already holds to view or manage its own content. | An immutable, self-contained copy, held in **platform-global, tenant-independent storage** — never a tenant schema, and never a reference back into one. |
| **Instantiate** (at obtaining) | The obtaining tenant's own builder-persona actor — an Application builder for the application shape, an Extender for the module shape — performing an ordinary, already-existing action of its own component. | The obtaining tenant's own already-scoped connection — the same one it already holds to construct or register anything of its own. | A new, tenant-owned instance (a constructed application, or a registered extension), seeded from the platform-owned copy. |

No mechanism named above ever opens a connection scoped to a tenant other than the one already driving the request. The **marketplace obtain transaction** itself — recorded by `components/reach` (§6.2) — does not instantiate anything; it only confirms the offering is currently offered and hands the obtaining tenant a resolved reference to the platform-owned copy. **Obtaining a reference and activating it are two different acts, performed by two different mechanisms, and the second is never performed by the marketplace on the obtaining tenant's behalf.**

### 3.3 Why the Deposit Step Diverges by Shape, and Why That Divergence Is Structural, Not Arbitrary

Whether the deposit step requires any new work depends entirely on where the offered content already lives — a fact fixed by the shape, not a choice this document makes:

- **A module's or an SDK-distributed component's underlying artifact is already platform-accessible, opaque object content, never tenant-schema-resident data.** `06-integration-and-extensibility-design.md` §8 already fixes that a registered extension's `artifact_reference` names "an opaque reference to the extension's compiled WASM module, never inline platform-core source" — the compiled artifact itself was never a row in any `tenant_<id>` or `tenant_<id>_app_<id>` schema. Depositing one of these shapes to the marketplace catalog is therefore a **reference copy**: the catalog's own row names the same already-platform-accessible artifact the offering tenant's own registration already names, with no read into any tenant schema required at all.
- **A published built application's content genuinely lives inside the offering tenant's own per-application schema, as structured, referenced data.** `03-software-and-architecture/05-integration-and-extensibility-spec.md` §8.3 already fixes that "a marketplace offering is obtained at an identified, immutable version," and `02-platform-data-model-design.md` §3.2 fixes the physical shape that guarantee rests on: `tenant_<id>.application_versions` and its manifest child `tenant_<id>.application_version_manifest_entries`, which hold **references** into the offering application's own per-application schema (`entity_catalog`, `relationship_catalog`, and the construct instances and bindings those catalogs name), never the resolved content itself. Depositing this shape therefore requires one genuine step this document names: **Offering Content Resolution** — the offering tenant's own already-resolved request reads the named version's manifest and resolves each reference against its own per-application schema, through the Entity Access Gateway exactly as any other read of that content already would (`02-data-model-and-entity-design.md` §4.1) — this document adds no second gateway and no exemption from it, the identical discipline `06-integration-and-extensibility-design.md` §9 already applies to a sandboxed extension's own reach — and writes the resolved, self-contained result to platform-global storage. The read happens once, inside the offering tenant's own connection, and the tenant schema is never touched again afterward.

**Architecturally, this divergence is forced by the fixed dependency table, not merely convenient.** `03-architecture-realization-design.md` §3.1 places C-13's mechanics inside `components/reach`; §4.1's allowed-dependency table permits Reach to depend on Operation, and Operation on Construction, but names no edge from Reach to Construction directly. Offering Content Resolution is therefore performed by composing through the allowed chain — Reach invokes Operation's own, already-existing version-and-manifest read path (the mechanism `03-builder-facing-version-control-design.md` already provides for the offering tenant's own version history), which in turn reaches the Entity Access Gateway inside Construction exactly as it already does for any other read of that content. No new dependency edge is added anywhere. Symmetrically, the **Instantiate** step at obtaining is never performed by Reach itself — Reach has no allowed edge to Construction or to the Extension component either — so it is, and must be, the obtaining tenant's own subsequent, independent action against `components/construction` (an ordinary C-04/C-06 construction, seeded from the platform-owned snapshot) or `components/extension` (an ordinary extension registration, naming the platform-owned artifact reference). **The same shape that isolation requires — the marketplace mediates the cross-tenant-facing handoff; the tenant's own pre-existing mechanism performs the within-tenant activation — is also the only shape the fixed dependency table permits.** Two independent constraints arrive at the identical mechanism.

### 3.4 Checked Against the Three Structural Facts

- **No naming path.** The marketplace catalog's `artifact_reference` (§10) is a plain, non-enforced value, following the identical convention `07-cross-system-data-layer-design.md` §3.2's `connector_reference` and `02-platform-data-model-design.md`'s ADR-037 already establish for a cross-schema-adjacent reference that must never become an enforced foreign key. Nothing about it lets a query construct address a tenant's own schema; for the application shape, it names a platform-global, tenant-independent snapshot, never a `tenant_<id>` or `tenant_<id>_app_<id>` identifier.
- **No grant path.** Depositing and obtaining each execute entirely within the acting tenant's own already-resolved connection (§3.2's table); no database privilege is ever granted from the offering tenant's own schema to the obtaining tenant's, and none is added by this document. The Instantiate step draws its authority from the obtaining tenant's own pre-existing grant to construct or register within its own tenant — never from anything the offering tenant holds.
- **No silent path.** Every read the Offering Content Resolution step performs runs through the Entity Access Gateway and inside a connection the mandatory self-verification read (`02-tenant-isolation-and-access-control-design.md` §5.2) already covers; every write the Instantiate step performs runs inside the obtaining tenant's own connection, subject to that identical, unconditional check. This document adds no code path that could mis-scope a connection in either direction, because it opens no connection of its own outside the one each acting tenant's own request already resolved.

**No fourth path is added.** `02-tenant-isolation-and-access-control-design.md` §8 already states the marketplace "is not a fourth path around these facts," because a marketplace transaction exchanges an object, not a grant. This document's mechanism is the concrete form of that sentence: at no point does an offering tenant's connection reach an obtaining tenant's schema, or the reverse, and platform-global storage — never a tenant schema — is the only thing either side's connection ever touches that the other side also touches.

## 4. The Marketplace-Origin Trust Determination

### 4.1 The Question Restated, and Why Two Documents Could Not Answer It

`04-security-controls-design.md` §5.3 scopes its own review-trigger manifest to platform-team-authored paths only and states plainly that "no isolation-strength or review-trigger determination is made" for marketplace-submitted code, naming this document as the place that determination belongs. `06-integration-and-extensibility-design.md` §10 goes further: it offers its own capability-scoped WASM sandbox mechanism as **availability, not decision** — stating explicitly that a marketplace-submitted module is not, on the strength of that document alone, covered by the Extension Invocation Point, registered under its tenant-scoped registration record, or granted reach through its SDK surface. That same section names the property the question actually turns on: not the Extender persona specifically, but **"the property of being externally-authored, contract-bound code the platform did not write."**

**This document adopts that argument's own logic, not merely its conclusion.** The deciding property is not who authored an artifact, and not which persona submitted it — it is whether the artifact executes inside the platform-core process at all. A module does. A published built application and an SDK-distributed component do not, for two different reasons stated below. Applying the WASM-sandbox mechanism uniformly to every marketplace shape regardless of this distinction would be exactly the uniform-treatment error `03-architecture-realization-design.md` §10 already had to correct once for the Extender origin (§10.4 there) — mechanically extending a mechanism built for one property to artifacts that do not carry it.

### 4.2 Three Shapes, Three Trust Profiles

| Shape | Does It Execute Inside the Platform-Core Process? | What Determines Its Trust Profile | Mechanism Adopted |
|---|---|---|---|
| **Published built application** | **No.** Under D-09's no-code commitment, a built application is configuration and data only — constructs, bindings, and entity/schema definitions (`01-application-construction-design.md` §4.1–§4.2) — never executable code the platform-core process runs on the offering tenant's behalf. | Whether its *content* validates, exactly as any builder-authored content already must. | None beyond what already governs any construction. §4.3. |
| **Module** | **Yes**, once registered and invoked — through the Extension Invocation Point, inside the dedicated WASM host `06-integration-and-extensibility-design.md` §5.3 already embeds. | The property `06-integration-and-extensibility-design.md` §10 names: externally-authored, contract-bound code the platform team never wrote or reviewed. | The Extender-origin mechanism in full, extended to this origin. §4.4. |
| **SDK-distributed component** | **No.** It is code an Extender builds against the SDK's own published contract and distributes for another tenant's own systems to run — wherever that tenant deploys it, never inside the platform-core process. | The grant its own calls back into the platform ever carry — never the code's own execution, which the platform never hosts. | The already-designed External Contract Consumer grant model. §4.5. |

**One mechanism does not serve all three, and the divergence tracks a single, structural fact — where the artifact executes — rather than three separately negotiated exceptions.**

### 4.3 Published Built Application: No Isolation Mechanism, Because There Is No Code to Isolate

A published built application offered through the marketplace is, in its entirety, the same kind of content D-09 already fixed as never containing builder-authored code: constructs, bindings, and the entity and schema definitions a builder configures (`02-platform-data-model-design.md` §2, "no table below stores builder-written code, scripts, or logic"). Once obtained and instantiated (§3.2's Instantiate step), this content enters the obtaining tenant's own per-application schema through the ordinary construction mechanism (C-04/C-06) and is validated by the same Validation Engine that validates any hand-configured content (`02-data-model-and-entity-design.md`) — with no exemption and no separate path, because the mechanism it enters through does not distinguish content a builder typed from content a construction action seeded from an obtained snapshot.

**The mandatory security review's own trigger condition — crossing the extension boundary — is therefore not met by this shape on its own.** `02-governance-and-security/02-security-policy.md` §3.2 fixes the extension boundary as "the point separating the platform core from builder- and third-party-supplied extensions." A pure configuration-and-data offering, carrying no bound module of its own, never reaches that boundary — there is no external extension content in it to cross it with. Where a published-application offering does reference a bound module, that module is a distinct offering in its own right, and the review fires at *that* module's own admission (§4.4), never twice for the same underlying code. This is not an exemption this document invents for the application shape; it is the honest consequence of a trigger condition this document did not write, applied to a shape that structurally never meets it.

### 4.4 Module: Adopting the Extender-Origin Mechanism in Full

**Decision: a marketplace-submitted module is registered, resolved, and invoked through the identical Extension Invocation Point and capability-scoped WASM sandbox `06-integration-and-extensibility-design.md` §5–§9 already designs for the Extender origin — extended to cover this origin, not duplicated for it.**

The criteria this document applies, and how each resolves:

| # | Criterion | How It Resolves |
|---|---|---|
| 1 | Does the deciding property (externally-authored, contract-bound, in-process-executing code) differ between an Extender-authored module and a marketplace-submitted one? | **No.** Once obtained and registered, a marketplace-sourced module is, structurally, the identical artifact type: a compiled WASM binary, invoked through the same Extension Invocation Point, confined by the same fixed host-function import surface. The only difference is how the registering tenant came to hold the artifact reference — directly authored, or obtained through §3's deposit-and-instantiate mechanism — and `06-integration-and-extensibility-design.md` §5.4's confinement dimensions do not vary by that fact. |
| 2 | Does reusing the existing mechanism, rather than designing a variant, weaken any confinement dimension for the marketplace case specifically? | **No — it is, if anything, the more conservative choice.** A marketplace module may be obtained by many tenants independently, each issuing its own grant at registration; the mechanism's own capability confinement (§4.5 below) already bounds each such grant to exactly what its own registering tenant authorizes, regardless of how many tenants have obtained the same underlying artifact. |
| 3 | Does the mediation the marketplace performs (offering, review, obtaining) itself establish that a module is trustworthy, such that no separate isolation mechanism is needed? | **No, decisively.** `03-architecture-realization-design.md` §10.3 already fixes the distinction this document must not lose: a contract — or, here, a mediated exchange — constrains *shape*, never *trustworthiness*. Treating "the platform mediated this transaction" as sufficient vetting would be exactly the error the ticket producing this document warns against, and exactly the error §10.3 already named for the SDK contract specifically. |
| 4 | Should the marketplace instead design its own, distinct sandboxing mechanism for this origin? | **No.** Doing so would duplicate a mechanism `06-integration-and-extensibility-design.md` §10 explicitly offers as available, would fragment the extension registry's own resolution behavior (`03-architecture-realization-design.md` §3.1) across two parallel sandboxes for what is, once registered, the identical artifact type, and would gain no confinement strength criterion 1–2 did not already establish as unnecessary. |

**Registration is performed by the obtaining tenant's own Extender-role actor, exactly as for a directly-authored module.** The obtaining tenant, after obtaining a reference to a marketplace-deposited module artifact (§6.2), creates its own `tenant_<id>.extension_registrations` row — the identical table and mechanism `06-integration-and-extensibility-design.md` §8 already fixes — naming the marketplace-sourced `artifact_reference` in place of a self-compiled one, and choosing its own `granted_operations` set. **This is where the obtaining tenant's own residual mitigation lives, exactly as it already does for the Extender origin**: `06-integration-and-extensibility-design.md` §5.5 states the honest limit that capability confinement bounds reach, never intent within a granted reach, and that the residual mitigation is how narrowly a tenant scopes the grant it issues at registration — a decision that document already places with the registering tenant, and this document does not narrow or widen it for a marketplace-sourced artifact.

**The honest limit is inherited, and it now spans more than one tenant's own choice.** `06-integration-and-extensibility-design.md` §5.5's residual — that no isolation mechanism bounds what an in-grant module chooses to do with a legitimately granted reach — applies to a marketplace-obtained module exactly as it applies to an Extender-authored one, with one difference stated plainly: because the same underlying artifact may be obtained and separately granted by many tenants, that residual now recurs once per obtaining tenant's own registration, never once for the whole marketplace. Each tenant's own grant-scoping decision at registration is independent of every other's, and no tenant's careful scoping protects another's careless one.

### 4.5 SDK-Distributed Component: Composing With the Already-Designed External Contract Consumer Grant

An SDK-distributed component never enters the platform-core process. It is built by an Extender against the SDK's own published, `builder-tooling`-tagged contract surface (`05-api-contract-design.md` §3.2) and distributed for the obtaining tenant's own systems to run wherever that tenant deploys it — a client integration, a background service, or any other external caller. Once integrated, its every call back into the platform is exactly one more invocation of the SDK by an **external contract consumer** — an actor class `02-tenant-isolation-and-access-control-design.md` §6 already recognizes and already bounds: "a client grant... issued by a tenant, scoped to whatever the tenant grants and never wider." That mechanism does not distinguish a hand-written integration from one obtained through the marketplace; both are resolved identically, through the same Registry Accessor, the same connection-scoping mechanism, and the same self-verification read, because both hold nothing more than the obtaining tenant's own already-issued grant.

**No new isolation mechanism is designed for this shape, because the platform never hosts its execution to isolate.** The residual risk this shape carries is a supply-chain risk over the *package's own content* — whether it contains malicious logic that, once integrated, might misuse the grant its own obtaining tenant issues it, or attempt to exfiltrate whatever credential that tenant supplies it — the identical category of risk `09-licensing-and-dependency-compliance-design.md` §3 already scans for in any incorporated dependency, extended here to a marketplace-obtained one rather than duplicated for it (§4.6).

### 4.6 The Mandatory Security Review, Concretely

`04-security-controls-design.md` §5.2's manifest triggers on a *touched code path* inside the platform-core repository — a check that presumes the platform team can see, and has already reviewed, everything the manifest maps. A marketplace submission breaks that presumption entirely: the platform team may never see the submission's own source, only its compiled artifact (module, SDK-distributed package) or its configuration content (application), and the submission was never "touched" by a platform-team change to begin with — it is new to the platform's review pipeline the moment it is first offered. **This is what makes the marketplace review genuinely this document's own to design, and it is designed as a distinct trigger condition composing with the existing classification step, not a second classification scale.**

| Trigger Element | What It Inspects | Composes With |
|---|---|---|
| **Structural capability-manifest check** (module and, where declared, SDK-component shapes) | Whether the submission's own declared capability or grant-request manifest names any operation outside the closed, `builder-tooling`-tagged catalog the Extension Invocation Point's fixed host-function import surface already recognizes (`06-integration-and-extensibility-design.md` §5.3, §7). | Deterministic; a request naming an operation outside that closed set is refused outright, with no human review needed to reach that refusal — the same "there is no import a guest could request that reaches further than the platform explicitly offers" guarantee already fixed. |
| **Vulnerability scanning** | The submission's own artifact, where inspectable — source, if disclosed, or the compiled binary otherwise — against the existing SCA/SAST-equivalent scanning layer. | `04-security-controls-design.md` §4.1's scanning layer and §4.2's severity-translation step, unmodified; a Critical or High classification blocks the submission from ever reaching `offered` status, exactly as it already blocks any other admission. |
| **Mandatory human review — always, once per submission and once per material version change** | Whether the declared manifest requests any operation in a fixed, sensitive subset (any operation reaching the cross-system data layer's own credential-handling host functions, or any operation this document's own manifest names as secret-adjacent), or whether the scanning layer's own classification is inconclusive. | Fires **unconditionally** on first submission — never gated by a manifested-path check the way §5.2's platform-team trigger is, because there is no prior platform-team baseline for a marketplace submission to be "unchanged" against. This is the one point at which the marketplace review is *more*, not less, exacting than the platform-team-only mechanism: the platform has never seen this code before, so nothing about it can be treated as already-reviewed. |

**This is a genuinely different trigger condition from §5.2's, and it is composed with the existing severity-translation step and license/dependency mechanism rather than duplicating either.** `04-security-controls-design.md` §5.2's manifest remains scoped to platform-team-authored paths, exactly as that document's §5.3 already fixes and exactly as this document leaves it; nothing here extends, narrows, or reinterprets it. The blocking behavior a Critical/High finding produces is identical to any other admission's, per §4.2 of that document, cited and not redesigned.

### 4.7 Engaging the Argument in Both Directions

`06-integration-and-extensibility-design.md` §10's own argument — that the deciding property is not the Extender persona but the property of externally-authored, contract-bound, platform-team-unreviewed code — is affirmed here for the module shape and is explicitly declined for the other two, on the same reasoning stated once rather than twice: **a property that a candidate mechanism exists to close only applies where the artifact carries that property.** A published built application carries no code the mechanism would confine; an SDK-distributed component carries code the platform never hosts to confine. Extending the WASM sandbox to either would not add confinement — it would apply a mechanism to a target it has nothing to hold.

## 5. The Six Submission Constraints, Realized

## 6. The Offering and Obtaining Mechanism, and Discoverability

### 6.1 Offering

Offering is the offering tenant's own Publisher-role action (`02-governance-and-security/03-access-control-and-tenancy-model.md` §5, "publish built software, and offer or obtain software and extensions through the marketplace... a reach role, not a granting role") that deposits an immutable copy or reference into platform-global marketplace state (§10), gated by every constraint of §5. An offering attempt that fails any constraint — an unresolved license category, an unfilled attribution, an unresolved incompatibility, or a review that has not completed — produces no catalog row at all: exactly as `09-licensing-and-dependency-compliance-design.md` §3 already treats a refused admission (never incorporated, never a lingering row), a refused offering leaves no discoverable trace.

| Shape | What the Deposit Step Does |
|---|---|
| Published built application | Offering Content Resolution (§3.3) resolves the named, immutable version's manifest against the offering tenant's own per-application schema, through the Entity Access Gateway, and writes the resolved, self-contained snapshot to platform-global storage. |
| Module | A direct reference copy — the catalog names the same already-platform-accessible artifact reference the offering tenant's own `extension_registrations` row already names. No tenant-schema read occurs. |
| SDK-distributed component | A direct reference copy of the already-platform-accessible distributed package artifact. No tenant-schema read occurs. |

### 6.2 Obtaining

Obtaining is the obtaining tenant's own Publisher-role action that (1) confirms the named offering is currently `offered`, (2) resolves the platform-global artifact reference or snapshot the offering names, and (3) hands that reference to the obtaining tenant, recorded as an audit event (§8) linking the offering to whatever the obtaining tenant subsequently does with it. **Obtaining does not construct, register, or activate anything.** The obtaining tenant's own subsequent, separate action — an ordinary construction (C-04/C-06) seeded from the resolved snapshot for the application shape, or an ordinary extension registration (§4.4) naming the resolved reference for the module shape — is what turns an obtained reference into working, tenant-owned state, performed entirely within the obtaining tenant's own already-legitimate authority over its own tenant.

An SDK-distributed component's "obtaining" is simpler still: the obtaining tenant retrieves the distributed package artifact for integration into its own, external systems; the platform performs no activation step of any kind, because there is nothing inside the platform for it to activate.

### 6.3 Discoverability

The marketplace catalog (§10) is queried through a read-only interface `components/reach` exposes alongside its existing publishing mechanics (`03-architecture-realization-design.md` §3.1's own placement of "the discoverability/obtainability of published software and extensions" inside that module). Any authenticated builder-persona actor may query the catalog for currently `offered` items, filtered by shape and by whatever descriptive metadata (name, description, category) an offering carries — reading the catalog exposes only what the offering tenant itself chose to make public by offering, never that tenant's own private data, configuration, or environment, and is therefore not a cross-tenant reach in the sense §3 guards against. This document fixes only that such a read-only, catalog-scoped query interface exists; the specific ranking, categorization taxonomy, or presentation of search results is an execution-phase concern this document does not design, on the identical restraint `04-publishing-and-delivery-design.md` §6.3 already applies to what content a Surface presents.

### 6.4 The Honest Limit: Withdrawal Does Not Reach What Was Already Obtained

**Withdrawing an offering removes it from future discovery and obtaining. It does not, and cannot, reach an instance any tenant already obtained and activated.** Once the Instantiate step (§3.2) has run — a construction committed to the obtaining tenant's own schema, or an extension registration committed to the obtaining tenant's own `extension_registrations` row — that instance is the obtaining tenant's own state, held inside its own connection scope, exactly as any other content it constructed or registered would be. There is no structural path back into that state for the marketplace mechanism to retract it, on the identical reasoning §3.4 already establishes for why no path exists to reach it in the first place: the same absence that keeps the exchange from becoming a cross-tenant door also keeps it from becoming a cross-tenant undo. This is stated plainly, on the model `06-integration-and-extensibility-design.md` §5.5 and `05-mobile-application-delivery-design.md` already set for an honest limit, rather than implied and later discovered: an offering tenant that withdraws a defective or newly-incompatible offering has stopped its further spread, never reversed its past one.

## 10. Where Marketplace State Lives — Constrained Here, Handed Over

This document's mechanism requires exactly one genuinely new structure: a platform-global record of every marketplace offering. It requires no new per-tenant structure — a deliberate finding, checked rather than assumed, stated below.

### 10.1 The One New Structure: a Platform-Global Marketplace Catalog

A marketplace offering — which tenant offered it, what shape it is, a reference to its deposited content, and its current license, security-review, and offering status — is platform-global data in the identical sense `platform.applications` and `platform.host_providers` already are: it necessarily names a specific tenant (the offering tenant), but it is never itself tenant-scoped data, because its entire purpose is to be readable by every other tenant's own discoverability query (§6.3). This document constrains `02-platform-data-model-design.md` to add, in the `platform` schema, a structure capable of representing, without loss:

- the offering's own identity, and the offering tenant it belongs to (a plain reference to `platform.tenants`, following the identical convention `platform.applications.tenant_id` already uses);
- which of the three shapes this ticket names the offering is;
- an `artifact_reference`, carried as a plain, origin-and-shape-discriminated value **never an enforced foreign key** — for the application shape, naming the platform-global snapshot the Offering Content Resolution step (§3.3) produced; for the module and SDK-distributed-component shapes, naming the same already-platform-accessible artifact reference the offering tenant's own registration already names — the identical discipline `07-cross-system-data-layer-design.md` §3.2's `connector_reference` and ADR-037 already establish for a value that must resolve differently depending on what it names, never a value forced into one schema's own foreign-key shape;
- its current offering status — `offered` or `withdrawn` — with no default state before `offered`, because a submission that has not yet satisfied §5's six constraints produces no row at all (§6.1);
- when the status was most recently set, and the resolved identity of the Publisher-role action that set it — the identical convention `platform.applications.publication_status_set_at`/`publication_status_set_by` already establishes for the same shape of fact on a different table;
- whatever descriptive metadata (name, description, category) makes the offering discoverable (§6.3), left unenumerated here on the identical restraint `platform.platform_configuration`'s own key/value/description shape already applies to a structure whose specific content is an operational concern of the document that consumes it, not a schema decision this document pre-empts.

**This document does not add the table.** Naming the concrete columns, types, and indexing is `02-platform-data-model-design.md`'s to do, exactly as that document's own §3.2 already anticipates for a structure a later document constrains without itself owning.

### 10.2 No New Per-Tenant Structure — a Deliberate Finding, Not an Oversight

**H31 already established that a hand-over is not automatic; this document checks, rather than assumes, whether it owes one.** For each shape:

- **Module.** Obtaining a module composes entirely with the already-existing `tenant_<id>.extension_registrations` table (`06-integration-and-extensibility-design.md` §8, `02-platform-data-model-design.md` §3.2); the obtaining tenant's own row is indistinguishable in shape from a directly-authored module's, differing only in where its `artifact_reference` value came from — a fact the audit trail records (§8's `marketplace-obtain` event), not a fact the operational schema needs a second column to carry.
- **Published built application.** Obtaining an application composes entirely with the ordinary construction mechanism (C-04/C-06) and the existing `platform.applications` row; the resulting application is, from the moment it is constructed, indistinguishable in shape from one built from a blank slate. Provenance — which offering, if any, seeded it — is fully reconstructable from the audit trail's own `marketplace-obtain` event (§8) linking the offering to the resulting construction, on the identical reconstructability principle `08-audit-and-traceability-design.md` §3.3 already fixes: "the sequence of events... is sufficient on its own... to reconstruct what happened... without recourse to memory, assumption, or an actor's own account." A redundant provenance column on `platform.applications` would duplicate what the audit trail already guarantees, and this document declines to add one.
- **SDK-distributed component.** The platform stores nothing about this shape once obtained — the artifact leaves the platform's own storage entirely, for the obtaining tenant's own external systems to hold. There is no state to add anywhere.

**No per-tenant table is added by this document.**

## 11. Design Decision Records

### ADR-043 — The Marketplace Exchange Mechanism and the Per-Shape Trust Determination

- **Status:** Approved (`DECISIONS.md` D-47, 2026-08-18).
- **Cost to reverse:** **High** (`PROCESS.md` §12.1). The deposit-and-instantiate mechanism, the marketplace catalog's own `artifact_reference` discrimination, and the per-shape trust determination together form the packaging and guarantee-preservation contract every marketplace item is already offered against; reversing any part of it — changing how an artifact is referenced, which mechanism a shape is confined by, or the review trigger's own condition — requires re-classifying every already-offered catalog row and, for the module shape, every already-registered `extension_registrations` row sourced from one, against a new shape. Not Brutal or Very high: no builder-defined entity data is touched by the decision itself, and no already-completed cross-region transfer or deletion-style action is performed by any mechanism this document designs — the exposure is to the *contract* every future submission flows through, matching the architecture-and-API-contract rung, not the data-model rung. - **The question this ADR answers, phrased for reuse:** Given a specification that fixes the marketplace as the sole mediated interaction between one builder and another and, in the same breath, as never an exception to tenant isolation; given a tenant-isolation design whose own structural-impossibility argument rests on no table, grant, or silent path ever joining two tenants; and given three offered shapes that differ in whether they carry executable code the platform itself must confine — what mechanism moves a published artifact from one tenant to another without creating the fourth path the isolation model forbids, and what isolation strength and review condition does each shape require, decided on the shape's own structural properties rather than assumed uniform across all three?
- **Criteria applied, and how each resolved:**

  | # | Criterion | How It Resolved |
  |---|---|---|
  | 1 | Does the exchange require any connection to be scoped to a tenant other than the one already driving the request, in either direction? | **No, by construction** — every read and write §3's mechanism performs executes inside the acting tenant's own already-resolved connection; platform-global storage, never a tenant schema, is the only structure either side's connection also touches. |
  | 2 | Is the deposit-and-instantiate split consistent with the fixed component dependency-direction table, or does it require a new edge? | **Consistent, with no new edge** — Reach's existing allowed dependency on Operation (and Operation's own existing dependency on Construction) carries the deposit step's read; the instantiate step is performed by the obtaining tenant's own, separate action against Construction or Extension directly, never by Reach reaching either. |
  | 3 | Does the deciding property for the trust determination track authorship, the submitting persona, or where the artifact executes? | **Where it executes, decisively** — `06-integration-and-extensibility-design.md` §10's own argument is affirmed for the module shape (which executes inside the platform-core process) and explicitly does not transfer to the other two (which do not), on the reasoning of §4.7. |
  | 4 | Does adopting the existing Extender-origin mechanism for the module shape weaken any confinement dimension relative to designing a marketplace-specific variant? | **No** — the mechanism's own confinement dimensions do not vary by how a registering tenant came to hold an artifact reference, and a variant mechanism would fragment the extension registry's own resolution behavior for no confinement gain. |
  | 5 | Does the mandatory review for a marketplace submission compose with the existing severity-translation step, or does it require a second scale? | **Composes** — the marketplace-specific trigger condition (§4.6) feeds the identical classification and blocking mechanism `04-security-controls-design.md` §4.2 already fixes; only the condition that fires the trigger is new, never a second severity scale. |
  | 6 | Is a new per-tenant structure genuinely owed, or does obtaining compose entirely with mechanisms that already exist? | **Composes entirely** — checked per shape in §10.2, following H31's own precedent that a hand-over is not automatic. |

- **Decision:** (1) An offering deposits an immutable copy or reference into platform-global, tenant-independent storage, performed entirely within the offering tenant's own already-resolved connection; obtaining resolves that deposit into a reference the obtaining tenant then activates through its own, pre-existing, tenant-sovereign mechanism — never through a mechanism the marketplace itself performs on the obtaining tenant's behalf (§3). (2) The trust determination is made per shape, on the structural fact of where each shape's artifact executes: no isolation mechanism for a published built application (§4.3, no code exists); the Extender-origin capability-scoped WASM sandbox, extended to this origin, for a module (§4.4); the already-designed External Contract Consumer grant model, unmodified, for an SDK-distributed component (§4.5). (3) The mandatory security review for a marketplace submission is a distinct trigger condition — a structural capability-manifest check, existing vulnerability scanning, and an unconditional first-submission human review — composing with, never duplicating, the existing severity-classification and blocking mechanism (§4.6). (4) The six submission constraints are realized by composing with an existing mechanism for five of the six, and by this document's own review-trigger design for the sixth (§5). (5) Exactly one new platform-global structure — a marketplace catalog — is constrained and handed to `02-platform-data-model-design.md`; no per-tenant structure is added (§10).
- **Alternatives considered:** *A live cross-tenant reference or synchronized view, rather than a deposited copy* — rejected under criterion 1; any live link back to the offering tenant's own schema would be exactly the fourth path `02-tenant-isolation-and-access-control-design.md` §8 already forbids. *Applying the WASM sandbox uniformly to every marketplace shape regardless of execution location* — rejected under criterion 3; this would reproduce the uniform-treatment error `03-architecture-realization-design.md` §10.4 already withdrew once, applied here to a different origin boundary. *Designing a marketplace-specific sandboxing mechanism distinct from the Extender-origin one* — rejected under criterion 4; no confinement gain, and a fragmented registry. *Treating the marketplace's own mediation of the exchange as itself sufficient vetting, with no independent review* — rejected explicitly in §4.4's criterion 3, on the identical distinction `03-architecture-realization-design.md` §10.3 already draws between contract shape and trustworthiness. *Overloading `platform.applications` or `tenant_<id>.extension_registrations` to also serve as the marketplace catalog* — rejected under criterion 6; conflates "having a copy" with "offering a copy," and would force every construction or registration row to carry marketplace-specific metadata most of them will never use. *A redundant provenance column on `platform.applications` recording which offering seeded it* — rejected under criterion 6; the audit trail's own `marketplace-obtain` event already makes this fact fully reconstructable without it.
- **Consequences:** Binds `02-platform-data-model-design.md` to add the one platform-global structure this document constrains but does not define (§10.1), on a future, separately-ticketed amendment. Binds `07-connector-marketplace-design.md` to build on the deposit-and-instantiate mechanism, the six-constraint realization, and the trust-determination method of this document, while making its own first-order determination for a connector's own credential-handling risk and its own catalog-shape question (§9), neither decided here. Adds no obligation to `06-integration-and-extensibility-design.md`'s Extension Invocation Point, confinement mapping, or SDK-compatibility mechanism, `09-licensing-and-dependency-compliance-design.md`'s check or sweep mechanism, `04-publishing-and-delivery-design.md`'s reachability gate, or `08-audit-and-traceability-design.md`'s record shape — each is consumed exactly as already designed, extended only where §8 above names a new `event_type` or a second `source_mechanism` within an existing one.

## 13. Precedence and Ownership Boundaries

When a rule in this document meets any other consideration, it is resolved by the fixed precedence of `02-governance-and-security/01-system-invariants.md` §6.

- **The specification prevails.** Nothing in this document narrows, expands, or alters `03-software-and-architecture/05-integration-and-extensibility-spec.md` §4, §6, or §7, or `02-governance-and-security/03-access-control-and-tenancy-model.md` §7; where a realization choice here appears to conflict with either, the specification governs and this document is corrected, not the reverse.
- **Mediation is never read as vetting.** Every place this document states that the marketplace mediates an exchange, that statement describes the exchange's shape alone; it is never treated as having established that a mediated submission is trustworthy, a determination made in full by the confinement mechanism of §4.4 or the External Contract Consumer grant of §4.5, never inferred from mediation itself (`03-architecture-realization-design.md` §10.3).
- **The three-shape boundary is never collapsed.** This document's trust determination diverges by shape on the structural fact of where each shape's artifact executes; treating any one shape's mechanism as covering another would reproduce the uniform-treatment error `03-architecture-realization-design.md` §10.4 already withdrew once.
- **Invariants are floors, never spent.** INV-01, INV-05, and INV-06, which the deposit-and-instantiate mechanism of §3 and the per-shape trust determination of §4 exist to keep true across every marketplace transaction, are never degraded to widen an offering's reach, meet a deadline, or satisfy a request.
- **A breach overrides apparent gain.** An outcome that would let an offering or an obtain action create a cross-tenant structure, admit an unreviewed marketplace module to platform-core execution beyond its own registered grant, or leave a submission's license or security-review obligation unresolved is refused regardless of the value it appears to create.

This document owns the deposit-and-instantiate exchange mechanism (§3), the per-shape marketplace-origin trust determination (§4), the realization of the six submission constraints (§5), the offering, obtaining, and discoverability mechanism (§6), the guarantee-preservation account (§7), the connector-marketplace boundary (§9), and the constraint on where marketplace state must fit (§10). It does not own, and none of the following documents' authority is diminished by this one:

- **The specification this document realizes** — remains authoritative; this document consumes it and never edits, narrows, or widens it.
- **The Extender-origin trust mechanism's own internals** — the Extension Invocation Point, the WASM host, and the confinement mapping — `06-integration-and-extensibility-design.md`'s, in full.

## 14. Binding Rules

- **An offering deposits an immutable copy or reference into platform-global, tenant-independent storage; it never creates a live reference back into the offering tenant's own schema.** Every read the deposit step performs executes inside the offering tenant's own already-resolved connection (§3).
- **Obtaining resolves a reference; it never constructs, registers, or activates anything.** The obtaining tenant's own, separate, pre-existing mechanism performs activation, entirely within its own already-legitimate authority (§3, §6.2).
- **No mechanism in this document opens a connection scoped to a tenant other than the one already driving the request.** This is checked, not assumed, against all three of `02-tenant-isolation-and-access-control-design.md` §8's structural facts on every mechanism above (§3.4).
- **The marketplace-origin trust determination is made per shape, on the structural fact of where each shape's artifact executes, never uniformly.** No isolation mechanism for a published built application; the Extender-origin capability-scoped WASM sandbox, extended, for a module; the External Contract Consumer grant, unmodified, for an SDK-distributed component (§4).
- **Mediation is never read as vetting.** No statement that the marketplace mediates an exchange is treated as having established that what is exchanged is trustworthy (§4.4, §13).
- **The mandatory security review for a marketplace submission is a distinct trigger condition, composed with the existing severity-classification and blocking mechanism, never a second severity scale.** It fires unconditionally on first submission, because no platform-team baseline exists for a marketplace artifact to be "unchanged" against (§4.6).
- **Every one of the six submission constraints is satisfied before an offering reaches `offered` status; an offering attempt that fails any of them produces no catalog row at all.** (§5, §6.1)
- **Withdrawing an offering never reaches an instance already obtained and activated.** No structural path exists for the marketplace mechanism to retract what a tenant's own construction or registration has already committed (§6.4).
- **No new per-tenant structure is added by this document.** Obtaining composes entirely with the construction mechanism, the extension-registration mechanism, or nothing at all, depending on shape (§10.2).
- **This document owns the general marketplace mechanism only.** The connector marketplace inherits the exchange mechanism, the six-constraint realization, and the trust-determination method, and makes its own first-order determination for a connector's own credential-handling risk, packaging, and discovery (§9).
- **Everything remains domain-neutral and platform-level.** No mechanism, shape, or constraint in this document encodes the characteristics of any single domain, category of software, or example offering; all remain valid for any module, any application, any SDK-distributed component, and any tenant, in any region.
- **This document records exactly one ADR.** ADR-043 (§11) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, boundary, or invariant the cited specification and cited upstream design documents already fix.
