# Builder-Facing Version Control Design — AI ahaMatic

This document realizes `01-business-and-ux/02-prd.md`'s C-21 row as concrete mechanism: the versioning model for applications built on the platform, the builder-facing history, comparison, and revert semantics over those versions, the immutability and provenance of every versioned artifact, the safe-revert constraints that keep a revert from corrupting live data, and the explicit boundary that separates this builder-facing version control from the platform's own internal change and version control. This is a Design-phase artifact realizing, in addition to C-21's own row: `01-application-runtime-and-lifecycle-design.md` §7.2, §7.4 (the identity anchors this document must anchor to, and the constraint its §7.4 places on this document by name — the same anchor `02-builder-facing-environment-management-design.md` already respects for stages); `02-builder-facing-environment-management-design.md` §4–§6, §9, §12 (the stage model, what a promotion moves, and the deferral of demotion and reverse-promotion to this document's own revert semantics); `02-data-model-and-entity-design.md` §3.2–§3.3, §3.5, §6, §7, §8 (the four catalogs, the process-definition catalog family, the two compatibility determinations this document composes with rather than re-derives, and the insert-only instance shape safe revert rests on); `01-application-construction-design.md` §3, §4, §6 (the construct/binding vocabulary a version's own manifest represents, without loss); `02-platform-data-model-design.md` §3, §9, §10 (the schema hierarchy this document constrains and hands a new structure to, per `BACKLOG.md` §1i's standing rule); `08-audit-and-traceability-design.md` §4.2–§4.3, §6 (the consolidated audit event model this document's evidence composes with, and the immutability precedent this document's own version-history discipline reuses rather than re-derives); and `05-ai-tooling-security-design.md` §5 (the provenance vocabulary this document must never conflate with its own).

## 3. Three Terms This Document Must Not Conflate

### 3.1 "Stage" Is Already Fixed, and Is Read Here, Never Redefined

`02-builder-facing-environment-management-design.md` §3 fixes "stage" as one of an application's own three builder-facing environments — Development, Testing, Production — disambiguated there from both the platform's own environment tiers and the build/configure/publish/operate lifecycle axis `01-application-runtime-and-lifecycle-design.md` §7 fixes. This document adds no further meaning to the word: every occurrence of "stage" below names exactly one of that document's three environments, reused without amendment. §4.2 states this document's own relationship to that already-fixed axis; it is not a fourth meaning of "stage," and does not need to be argued as one.

### 3.2 "Provenance" Already Names a Different Fact, One Layer Over

`05-ai-tooling-security-design.md` §5 fixes "provenance" as a property of an artifact *fragment* the AI-assisted builder tooling produces — whether that fragment is `ai-suggested` or `builder-approved` — enforced at the Merge Gate before any fragment may cross a trust boundary. This document's own use of the word names a categorically different fact: **which builder action produced a given version**, never whether any content inside that version originated from AI-assisted tooling. §10.2 states the distinction in full and names this document's own concept **version provenance** wherever ambiguity would otherwise be possible, so that a reader never mistakes one document's fact for the other's.

### 3.3 "Release," As the Capability's Own Summary Uses It, Names No Third Artifact

C-21's own row describes its purpose as letting a builder "version, compare, revert, and **manage the releases** of the applications they build." This document does not introduce a "release" as a construct distinct from a version or a stage — doing so would open a third vocabulary collision alongside the two §3.1–§3.2 already close. What that phrase names is fully discharged by the combination this document and `02-builder-facing-environment-management-design.md` already provide: a builder manages what is effectively in production by promoting a version's own content to the Production stage (that document's mechanism) and by being able to compare, and if needed revert, whatever configuration currently occupies any one stage (this document's mechanism, §6–§7). No further artifact is designed here to carry the word "release."

## 4. What a Version Is, Concretely

### 4.1 The Versioning Model

**A version is an immutable, point-in-time capture of one stage's own configuration content, produced by an explicit, builder-triggered checkpoint action — never an automatic snapshot taken on every configuration write.** Concretely, a version's own content is a reference set, never a duplicate, naming:

- every build-surface-flagged construct's own current instance row (`entity_catalog`/instance-table content, `02-data-model-and-entity-design.md` §3.3, §8.1), by `record_id` and its current `version_id`;
- every binding — structural, behavioral, or access — currently in force, realized as `relationship_catalog` rows (§3.3 there);
- every entity's own currently-active schema, realized as each affected `entity_catalog` row's `current_schema_version_id` (§3.2 there);
- every process definition's own currently-active version, realized as each affected `process_definition_catalog` row's `current_version_id` (§3.5 there).

This is deliberately **congruent with, and no narrower than, what `02-builder-facing-environment-management-design.md` §6.1 fixes a promotion moves** — constructs, the three binding kinds, and the entity/schema/field/relationship definitions of `02-data-model-and-entity-design.md` §3.2's four catalogs — and this document extends it by one further element that document's own promotion boundary does not name: the process-definition catalog family of §3.5 there. Excluding process definitions from a version's own scope would leave a builder able to version a schema change but not a process change, an asymmetry no upstream document motivates; including them is a genuine extension this document is free to make, per `01-application-runtime-and-lifecycle-design.md` §7.4's own framing that a later document "may define a richer notion of... a version... without this document anticipating or narrowing it." Should a future amendment to the promotion mechanism itself come to move process-definition content, this document's version scope already accommodates it without change.

**A version never captures ordinary, non-build-surface entity instance data.** The identical exclusion `02-builder-facing-environment-management-design.md` §6.1 already states for promotion holds here on the same reasoning: the records a built application's own end users and processes accumulate are never configuration, and are never part of what a version references, restores, or is compared against.

### 4.2 A Version Is Orthogonal to a Stage; Promotion Does Not Create One

A version is scoped to exactly one stage's own history — its content is, by definition, a capture of whatever a single stage's own schema currently holds, and every stage (Development, Testing, Production) carries its own independent, append-only sequence of versions, each identified by a `version_marker` monotonic within that one `(application_id, stage)` pair, on the identical naming convention `schema_version_catalog.version_marker` and `process_definition_version_catalog.version_marker` already establish for their own, narrower scopes (`02-data-model-and-entity-design.md` §3.2, §3.5). This is the resolution the ticket instructing this document requires stated plainly: **the two axes are orthogonal.** A stage names *which sibling schema* an application's current configuration occupies; a version names *a point in that one schema's own configuration history*. Neither is derived from the other, and neither document's mechanism substitutes for the other's.

**A promotion does not create a version, and consuming a version is never a precondition a promotion checks.** `02-builder-facing-environment-management-design.md` §6.1 already fixes that a promotion moves the source stage's *current* configuration state, read live through the Entity Access Gateway, into the destination stage — never a captured version object. This document adds no obligation to that mechanism: a promotion proceeds, or is blocked, exactly as that document's §6.4 already fixes, whether or not either the source or the destination stage happens to have any version history at all. A builder *may* choose, as a matter of practice this document does not mandate, to capture a version of a stage immediately before promoting out of it or into it — doing so is what makes that stage's pre-promotion state recoverable by revert later (§9) — but this document introduces no check, gate, or blocking condition on `02-builder-facing-environment-management-design.md` §6.3's own promotion sequence, because doing so would be a redesign of a mechanism this document does not own.

### 4.3 Every Version Anchors to the Same, Unchanging Identity

`01-application-runtime-and-lifecycle-design.md` §7.2 fixes `application_id` and `tenant_id` as fixed at construction and carried unchanged through every subsequent transition; §7.4 states the constraint this document inherits by name, identically to the constraint `02-builder-facing-environment-management-design.md` §4.1 already respects for a stage. Every version this document's mechanism captures names the identical, unchanging `application_id` and its already-resolved `tenant_id` — never a new identity, never a rebinding, and never a second application record standing in for a version. A version, exactly like a stage, is a fact recorded *about* one unchanging application, never a fact that creates another one.

## 5. Where Version and History Structures Live — Constrained Here, Defined There

Per `BACKLOG.md` §1i's standing rule and the constrain-and-hand-over precedent `02-platform-data-model-design.md` §3.2 already establishes for `administrative_scope_grants`, `extension_registrations`, `external_system_connections`, and the stage-schema mapping structure `02-builder-facing-environment-management-design.md` §4.4 most recently added, this document does not define a table in a schema it does not own. It constrains `02-platform-data-model-design.md` to add, at the per-tenant level, a structure capable of representing, without loss:

- which application (an `application_id`, constrained to the tenant's own `platform.applications` rows) and which of the three stages (Development, Testing, or Production — reusing `02-builder-facing-environment-management-design.md` §4.4's own stage vocabulary, never a fourth value) a version belongs to;
- a `version_marker`, monotonic within one `(application_id, stage)` pair, per §4.2;
- when the version was captured, and the resolved identity of the builder action that captured it — the version-provenance fact §10.2 fixes;
- the version's own manifest — the reference set §4.1 names, capable of holding an arbitrary number of construct, binding, schema-version, and process-definition-version references without loss, and never storing a duplicate of any referenced row's own content;
- for a version produced by a revert action (§7) rather than an ordinary checkpoint, which earlier version (by its own `version_marker` within the same stage) the revert restored.

**This structure needs a row for Development, unlike `02-builder-facing-environment-management-design.md` §4.4's own stage-schema mapping structure, which needs none there.** That document's structure records where a stage's schema physically lives, and Development needs no such row because its schema is exactly the one construction already produces; this document's structure records a *history of configuration states*, and Development is where a builder configures in the first place — the stage most likely to accumulate the richest version history of the three. `02-platform-data-model-design.md` defines the physical table, its columns, and its constraints; this document defines only what must be representable and why, exactly as `01-application-construction-design.md` §6 and `02-builder-facing-environment-management-design.md` §4.4 already do for the structures each constrains without owning.

## 6. History and Comparison — the Builder-Facing Surface

**History** is the ordered list of a stage's own captured versions, each identified by its `version_marker`, its capture time, and the resolved identity of the builder action that produced it (§10.2) — an ordinary read against the structure §5 constrains, narrowed to the already-resolved `application_id` and the stage the builder is inspecting. Where the stage being inspected is not Development, the read composes with `02-builder-facing-environment-management-design.md` §5.4's own extension of the Context Resolution Point — the Resolved Stage — exactly as any other stage-scoped action already does; this document adds no second resolution mechanism for "which stage's history."

**Comparison** is a read-only operation over two versions' own manifests — of the same stage, or of two different stages' own most recent versions, where a builder wants to see what a prospective promotion would change before promoting — resolving each referenced construct, binding, schema version, or process-definition version through the Entity Access Gateway exactly as any other read does, and presenting which references were added, removed, or point to different underlying content between the two. The platform's own mechanism interprets no domain meaning in what it finds different: it states that a binding's condition-and-parameter content differs, or that a construct's field content differs, never *why* that difference matters to a builder's own subject matter — the identical discipline `01-application-runtime-and-lifecycle-design.md` §4.1's step 3 already applies to a Behavioral binding's own condition content.

**Comparison produces no audit event.** It is a read with no consequential effect, on the identical precedent `03-data-administration-design.md` §8 already states for its own read operations — no dedicated evidence row exists for a read, and this document introduces none for its own.

## 7. Revert — Composed From Two Already-Fixed Write Paths, Never a Third

### 7.1 What Revert Restores, and What It Structurally Cannot Reach

**A revert restores a stage's own current configuration to what an earlier, captured version of that same stage recorded — never entity instance content.** Because instance data is insert-only and never updated or deleted (`02-data-model-and-entity-design.md` §8.1), a configuration revert cannot itself destroy, alter, or reach any record a built application's own end users or processes have accumulated: the write surface a revert may touch is exactly the write surface §4.1 already bounds a version's own manifest to — constructs, bindings, and definitional catalog content — categorically excluding ordinary entity instance data, on the identical structural exclusion `02-builder-facing-environment-management-design.md` §6.1 already fixes for promotion. This is the affirmative half of C-21's own safe-revert obligation, and it holds **by construction**, not by policy: there is no code path in this document's mechanism through which a revert action could write to an ordinary instance table at all.

### 7.2 Reverting Instance-Shaped Content — Constructs

A construct is represented as an entity instance of a build-surface-flagged entity (`02-data-model-and-entity-design.md` §3.3), and every instance write is insert-only (§8.1 there): reverting a construct's own field content to what an earlier version captured is realized as an **ordinary Gateway-mediated instance write** — a new instance row sharing the construct's own stable `record_id`, whose field values match the captured version's content, superseding whatever the construct's own current row holds. This is not a new write path: it clears the Validation Engine's ordinary validity, consistency, and referential-correctness checks (`02-data-model-and-entity-design.md` §4.2) exactly as any other instance write does, and is refused exactly where any other write would be refused — most concretely, where the construct's own governing entity has evolved to a schema under which the captured field content is no longer valid. This document adds no new refusal shape for this case; the ordinary discipline already suffices.

### 7.3 Reverting Definitional Content — Schema and Process-Definition Shape

Every entity's own `current_schema_version_id`, and every process definition's own `current_version_id`, is a pointer to an append-only, never-updated catalog row (`02-data-model-and-entity-design.md` §3.2, §3.5). Reverting a definitional element to what an earlier version captured therefore cannot resurrect or mutate the old `schema_version_catalog` or `process_definition_version_catalog` row itself — this library's insert-only discipline forecloses that everywhere else, and this document does not carve an exception for revert. Instead, **reverting definitional content is realized as an ordinary proposal of a new `schema_version_catalog` or `process_definition_version_catalog` row, whose content matches the captured version's content** — a proposal that passes through the identical Entity Access Gateway, in the identical definitional mode, that any other schema or process-definition evolution already passes through (`02-data-model-and-entity-design.md` §4.2, §3.5).

**This is the composition the two hard determinations require, and this document performs no other.** The proposal's own `backward_compatible_with_prior` or `in_flight_compatible_with_prior` determination is made by the Validation Engine, at the moment this reverted content is proposed, on the identical discipline `02-data-model-and-entity-design.md` §7 and §3.5 already fix for any newly proposed version — this document never re-evaluates either determination itself, and never substitutes its own judgment of compatibility for the Engine's. Where the determination resolves `true`, the reverted content is adopted as an ordinary evolution. Where it resolves `false`, or cannot be established with confidence, the proposal is refused the ordinary path and routed to whatever managed path `02-data-model-and-entity-design.md` §7 already fixes for a backward-incompatible evolution generally — never adopted silently, and never a case this document invents a second refusal shape to handle.

### 7.4 What Every Revert Itself Produces

Whether reverting instance-shaped content (§7.2) or definitional content (§7.3), a successful revert produces a **new** version in the target stage's own history — one further `version_marker`, one greater than the stage's current maximum, whose content equals the version being restored to. No already-recorded version, and no already-recorded catalog row, is ever rewritten or deleted to perform a revert. This is why the ADR grading this document records (§13) treats history as genuinely non-re-derivable: a revert extends the sequence forward, and the sequence itself is never edited in place, on the identical append-only discipline every catalog and instance structure in this library already carries.

## 8. The Deferred Demotion, Resolved

`02-builder-facing-environment-management-design.md` §6.2 designs promotion as sequential and one-directional, with no demotion or reverse-promotion mechanism of its own, and defers recovering from a bad promotion to this document's revert semantics. **This document answers that deferral plainly: reverting an application in a stage is within this document's revert model, never a distinct operation.** Recovering from a promotion a builder regrets means reverting the *destination* stage's own configuration to whichever version of that same stage's own history preceded the promotion — an ordinary application of §7 above, targeting the one stage the promotion wrote to, never a cross-schema mechanism that moves content backward through Development, Testing, and Production the way `02-builder-facing-environment-management-design.md` explicitly declines to build. No second recovery mechanism is introduced here alongside it, and no demotion, reverse-promotion, or cross-stage rollback of any kind is designed by this document either — recovery is always same-stage revert, to a version of that stage's own recorded history.

## 9. The Honest Limit: What Safe Revert Does Not, and Cannot, Close

**A stage's configuration can be reverted only to a version that was actually captured.** Because version capture is an explicit, builder-triggered checkpoint (§4.1) — never an automatic side effect of any configuration write, and never a precondition `02-builder-facing-environment-management-design.md` §6.3's promotion mechanism checks (§4.2) — a promotion into a stage that was never preceded by a builder capturing a version of that stage's prior configuration leaves nothing for a later revert to restore. This is not a refusal this mechanism issues; it is the absence of a target a refusal could even name. **This document does not, and cannot, make every promotion recoverable** — recoverability is a direct function of whether a builder chose to checkpoint beforehand, and this document introduces no obligation on `02-builder-facing-environment-management-design.md`'s own promotion mechanism to force that choice, because doing so would be a redesign of a mechanism this document does not own (§2). A builder who never versions a stage before promoting into it has, by that omission, no revert path back out of the promotion — stated plainly here rather than concealed behind an unconditional safe-revert claim.

**A second, narrower limit is stated for completeness.** Reverting a *configuration* to an earlier state never reaches, and never needs to reach, whatever real-world consequence an application's own end users or processes already produced while the now-superseded configuration was current — an effect a Command's own invocation once produced, a record a Surface's own submission once created, or any other instance-level effect an application already had. §7.1's guarantee is that a revert cannot corrupt that data; it is never a claim that reverting the configuration also reverses, reconciles, or otherwise undoes what already happened under it. The platform's own guarantee is about what an application is configured to do, going forward; it is never a guarantee about what an application already did.

## 10. Immutability and Provenance

### 10.1 Immutability

**A captured version, once written, is never altered or deleted.** This is not a cryptographic tamper-evidence mechanism of the kind `08-audit-and-traceability-design.md` §6 already designs for the audit trail — this document introduces no hash-chain, no external anchor, and no second tamper-evidence scheme for a version's own manifest. It is the identical, ordinary insert-only discipline every catalog and instance structure in this library already carries (`02-data-model-and-entity-design.md` §8.1): the structure §5 constrains is written once per version and never updated in place. This document fixes the requirement only — that no version row is ever the target of an update or a delete; the connection-scoped, role-and-permission enforcement that makes that requirement structural rather than aspirational is the identical mechanism that already enforces the same boundary for every other structure in this design, and this document does not design that enforcement a second time.

The fact that a version was captured, and the fact that a revert occurred, are each themselves audited under the consolidated model (§12) — and *that* record, unlike the version's own manifest, does enjoy the audit trail's own tamper-evidence mechanism, because it is an ordinary audit event composing with that already-fixed mechanism, never a second one this document builds for itself.

### 10.2 Version Provenance, Named Apart From AI-Tooling Provenance

**Version provenance is which builder action produced a given version — never whether any content inside that version originated from AI-assisted tooling.** Every version this document's mechanism captures records the resolved identity of the builder action that produced it (an explicit checkpoint, or a revert, per §5) — the same resolved-actor discipline `01-application-construction-design.md` §7 already establishes for a construction or configuration action, applied here to a version-capture or revert action.

**This document's own mechanism never inspects, stores, or duplicates the AI-suggested/builder-approved state `05-ai-tooling-security-design.md` §5 fixes.** By the time any construct, binding, or definitional content is committed to a schema at all — and is therefore capturable in a version's own manifest — that content has already cleared the Merge Gate's own provenance check (ADR-022 there), which admits no content still recorded as `ai-suggested`. A version's own manifest, and this document's own version-provenance record, therefore never need to carry, check, or re-derive that state; it was already settled, exhaustively, before the content this document versions ever existed to be versioned. The two provenance facts compose without either duplicating the other.

## 11. The Boundary Against the Platform's Own Change Management and Evolution Policy, Stated Bidirectionally

**Versioning a builder's own application is not an instance of the platform's own change management, and triggers no obligation that policy fixes for the platform's own evolution.** `05-meta-operations/08-change-management-and-evolution-policy.md` governs the platform core, builder tooling, and the governing library's own backward-compatibility obligation, deprecation and migration rules, documentation-update requirement, and human-review triggers (its §2 fixes this scope explicitly, and explicitly excludes "what change management a builder applies to their own built artifact"). This document's own mechanism — capturing a version, comparing two, or reverting a stage — shares no code path, no gate, and no evidence record with that policy's own machinery, on the identical "zero shared code path, gate, or evidence record" discipline `02-builder-facing-environment-management-design.md` §8 already states for its own boundary against the platform's CI/CD and environment topology.

**One composition point is not a boundary breach, and is stated so a reader does not mistake it for one.** `02-data-model-and-entity-design.md` §7 already fixes that a builder-defined schema evolution found backward-incompatible — including one this document's own revert mechanism proposes (§7.3) — is routed to whatever managed, announced path that document cites (`05-meta-operations/08-change-management-and-evolution-policy.md` §6, and gate G-6). This document does not decide, extend, or dispute that citation; it consumes it exactly as already fixed. That a single, human-reviewed gate happens to sit downstream of both a platform-core evolution and a builder's own backward-incompatible schema revert does not collapse the two into one mechanism — the *trigger*, the *content*, and the *ownership* of each remain entirely distinct, and this document introduces no shared code path of its own beyond the one already fixed upstream.

|---|---|---|---|
| `version-capture` | The version-capture action (§4.1), for an explicit builder checkpoint of one stage's own current configuration. | The application and stage acted on (by opaque reference), and the new `version_marker`. | `applied` (manifest recorded) or `refused` (the acting identity's resolved standing does not include the grant to version the named application). |
| `version-revert` | The revert action (§7), restoring one stage's own configuration to an earlier captured version of that same stage. | The application and stage acted on, the target version being restored to, and the new `version_marker` the revert itself produces. | `applied` (the restore completed, whether via an ordinary instance write or an ordinary, compatible schema/process-definition proposal); `refused` (the acting identity lacks the grant, the target version does not exist for that stage, an instance write fails ordinary validity, or a definitional proposal is determined backward-incompatible and routed to the managed path of §11 rather than adopted). |

**A revert's own underlying schema or process-definition proposal, where §7.3 triggers one, produces its own already-existing event — `entity-schema-definition`, `schema-evolution-determination`, or `process-definition-authoring` (`02-data-model-and-entity-design.md` §12) — in addition to, and never in place of, this document's own `version-revert` event.** This document mints no new type for that underlying step; the two events are emitted from the same action and are reconstructable together from the stream's own sequencing (`08-audit-and-traceability-design.md` §3.3), without a dedicated link field this document adds for the purpose.

**No event is produced for comparison** (§6) — a read with no consequential effect, on the same precedent `03-data-administration-design.md` §8 already states for its own reads.

**Landing category, stated honestly where the fit is imperfect.** Neither `version-capture` nor `version-revert` describes a tenant-boundary check, a security control, a residency obligation, an invariant halt, or an autonomous-agent change; per `08-audit-and-traceability-design.md` §4.3's own closest-fit rule, and following the identical precedent `01-application-construction-design.md` §9 and `02-builder-facing-environment-management-design.md` §10 already set for their own construction, configuration, and promotion events, both land under **Authorization and grant events**: each is, in substance, an exercise of a builder's own grant over the named application, and grouping both alongside construction, configuration, and promotion evidence keeps one application's full construction-through-promotion-through-versioning history reconstructable from a single category.

No row above stores a version's own manifest content; `target_reference` identifies the application, stage, and version by opaque reference, per `08-audit-and-traceability-design.md` §4.2's own field discipline.

## 13. Design Decision Records

### 13.1 ADR-040 — The Versioning and Revert Model: Composed From Two Already-Fixed Write Paths, Never a Third

- **Status:** Provisional — Pending Lead Approval.
- **Cost to reverse:** **High** (`PROCESS.md` §12.1; matches `implementation-document-map.md`'s own pre-assigned grade for this document). The versioning and provenance model this decision fixes is not the physical shape of every builder's own stored configuration or instance data — that shape is `01-application-construction-design.md`'s and `02-data-model-and-entity-design.md`'s own, each graded Very high and Brutal, and neither is touched by this decision. What is expensive to reverse is narrower but still real: once builders have captured versions and performed reverts against the structure §5 constrains, that structure holds a genuine history — a record of past configuration states, several of which may reference catalog rows that have themselves since evolved further. Reversing this decision's own shape does not migrate builder-defined entity data, but it cannot simply be re-derived from the application's *current* configuration state either, because the versions being reshaped describe *past* states that current state no longer holds. This is the specific reason the grade is High rather than Moderate: the structure is a genuine historical record, not a re-derivable index, from the moment a builder's first version is captured.
- **Upstream decisions assumed:** `01-application-runtime-and-lifecycle-design.md` §7.2, §7.4 (the identity anchors this decision anchors to, and the constraint that a version may not rebind `application_id`); `02-builder-facing-environment-management-design.md` §4–§6, §9, §12 (the stage vocabulary this decision reuses without amendment, what a promotion moves, and the demotion deferral this decision resolves); `02-data-model-and-entity-design.md` §3.2–§3.3, §3.5, §4.1–§4.2, §6, §7, §8.1 (the four catalogs, the process-definition catalog family, the Entity Access Gateway, the two compatibility determinations this decision composes with and never re-derives, and the insert-only instance and catalog shape this decision's own revert mechanism relies on); `01-application-construction-design.md` §3–§4, §6 (the construct/binding vocabulary a version's manifest represents); `02-platform-data-model-design.md` §3.2–§3.3 (the constrain-and-hand-over precedent this decision's own structure follows); `05-ai-tooling-security-design.md` §5 (the provenance vocabulary this decision's own version-provenance concept is disambiguated from); `05-meta-operations/08-change-management-and-evolution-policy.md` (the managed path this decision's own backward-incompatible reverts are routed to, never redesigned). ADR-021 through ADR-039 remain Provisional and are not assumed settled; this decision depends on none of their approval status beyond the mechanisms they already fix.
- **Verified vs. reasoned:** Reasoned throughout. No time-sensitive ecosystem, product, or vendor claim is made; every finding derives from the cited specification and the cited, already-written upstream design documents' own content.
- **Question this answers:** Given that a promotion moves only an application's current configuration state and designs no version, comparison, revert, or provenance mechanism of its own; given that two compatibility determinations bearing directly on safe revert are already recorded once, upstream, by the entity and process-definition mechanism and must never be re-derived; and given that instance data is insert-only and therefore never itself reachable by a configuration revert — what is the smallest versioning model that captures an application's own configuration history per stage without rebinding its identity, composes revert entirely out of two already-fixed write paths rather than a third mechanism, and states honestly which reverts are safe by construction, which require the already-fixed managed path, and which case this mechanism cannot make safe at all?
- **Criteria applied, and how each resolved:**
  1. *An explicit, builder-triggered checkpoint versus an automatic snapshot on every configuration write.* Decisive for an explicit checkpoint — automatic snapshotting would multiply the version history at the rate of ordinary configuration edits, defeating history's own purpose as a curated sequence of restore points, and would force a versioning side effect onto the construction and configuration mechanism this document does not own.
  2. *Version scope congruent with, and extended beyond, what a promotion moves — including the process-definition catalog family a promotion's own boundary does not name.* Decisive for extending — process definitions are as much an application's own configuration as an entity's schema is, and excluding them would leave an arbitrary asymmetry between what a builder can version for a schema change and for a process change, with no basis in any upstream document.
  3. *Reverting definitional content as an ordinary new schema or process-definition-version proposal versus a dedicated resurrection of the old catalog row.* Decisive for an ordinary new proposal — every catalog row in this library is append-only once written; resurrecting an old row requires an update this library's own insert-only discipline forecloses everywhere else, and proposing new content that happens to match old content composes with the Validation Engine's already-existing compatibility determination rather than asking this document to invent a second one for the reverse direction.
  4. *A synchronous refusal for a backward-incompatible revert, leaving the managed path to a separate, later process, versus a held-pending-approval outcome analogous to a single release-gate approval.* Decisive for refusal — the managed path is a multi-step, scheduled process (announcement, a finite adaptation window, human review) this document does not own or design the mechanics of; representing it as a single held/release toggle would misstate what actually stands between refusal and later adoption.
  5. *Reverting a stage's configuration to an earlier version of the same stage versus a dedicated demotion or reverse-promotion mechanism.* Decisive for the former — it reuses the identical write surface already fixed for revert generally, requires no cross-schema mechanism the way promotion needs, and directly discharges the deferral `02-builder-facing-environment-management-design.md` §6.2 already names, without this document inventing a second recovery path alongside it.
- **Context:** This is the third document of the Operation, Reach & Distribution layer, and the first whose central mechanism — safe revert — depends on composing with two compatibility determinations two different upstream documents each record once, on the express instruction that a downstream consumer never re-derive either. It resolves a deferral `02-builder-facing-environment-management-design.md` named by title one ticket ago (demotion and reverse-promotion), and disambiguates its own vocabulary from two adjacent, already-written uses of near-identical terms (stage, provenance) before any substantive design could proceed, on the identical discipline that document's own §3 already modeled for its own two collisions.
- **Decision:** (1) A version is an immutable, builder-triggered checkpoint of one stage's own current configuration — constructs, bindings, and entity/schema/field/relationship/process-definition catalog content — never entity instance data and never an automatic snapshot (§4.1). (2) A version is orthogonal to a stage: each stage carries its own independent, append-only version history, and a promotion neither creates nor consumes a version (§4.2). (3) Every version anchors to the same, unchanging `application_id` and `tenant_id` a stage already anchors to, never a rebinding (§4.3). (4) Reverting instance-shaped content (constructs) is an ordinary Gateway-mediated instance write; reverting definitional content (schema or process-definition shape) is an ordinary proposal of a new catalog row whose content matches the captured version, evaluated by the Validation Engine's already-existing compatibility determination and never a second one this document invents (§7). (5) A stage's own bad promotion is recovered by reverting that same stage to an earlier version of its own history — never a distinct demotion or reverse-promotion mechanism (§8). (6) A promotion never preceded by a captured version leaves nothing for revert to restore; this is an honest limit this document states rather than closes (§9). (7) Version immutability reuses the library's ordinary insert-only discipline, never a second tamper-evidence mechanism; version provenance (which builder action produced a version) is named and kept apart from the AI-tooling provenance attribute, which this document's mechanism never inspects or duplicates (§10). (8) This mechanism shares no code path, gate, or evidence record with the platform's own change-management and evolution policy, and composes without redesigning the one already-fixed routing point a backward-incompatible revert may reach (§11). (9) Two new audit event types, `version-capture` and `version-revert`, land under Authorization and grant events as the closest fit (§12).
- **Alternatives considered:** *Automatic, per-write version snapshotting* — rejected under criterion 1; it defeats history's own curatorial purpose and forces a side effect onto a mechanism this document does not own. *Excluding process definitions from a version's own scope, to stay exactly congruent with promotion's own boundary* — rejected under criterion 2; the asymmetry it produces has no basis in any upstream document. *Resurrecting or mutating an old catalog row to perform a revert* — rejected under criterion 3; it violates the insert-only discipline every other structure in this library observes. *A held-pending-approval outcome for a backward-incompatible revert, modeled on the Production approval gate* — rejected under criterion 4; the managed path it would represent is a longer, scheduled process no single held/release toggle correctly models. *A dedicated demotion or reverse-promotion mechanism, alongside revert* — rejected under criterion 5; it duplicates a recovery path the same-stage revert already provides, and reopens a mechanism `02-builder-facing-environment-management-design.md` deliberately declined to build.
- **Consequences:** Binds `02-platform-data-model-design.md` to add the per-tenant version-history structure this document constrains (§5), without this decision predetermining that document's own column types, constraints, or physical shape. Adds no obligation to `02-data-model-and-entity-design.md`'s Entity Access Gateway, its two compatibility determinations, or its insert-only instance and catalog shape — each is composed with exactly as already designed, never extended or re-decided. Adds no obligation to `02-builder-facing-environment-management-design.md`'s stage model or promotion mechanism — its demotion deferral is discharged (§8) without this decision adding a check, gate, or blocking condition to that mechanism's own sequence. Adds no obligation to `05-meta-operations/08-change-management-and-evolution-policy.md` — the one routing point this decision reaches is consumed exactly as `02-data-model-and-entity-design.md` §7 already fixes it, never extended or disputed. Adds no obligation to `08-audit-and-traceability-design.md`'s record shape, storage, or tamper-evidence mechanism — only the two new `event_type` values within its existing model (§12).

## 16. Binding Rules

These rules hold for every application, stage, version, and revert subject to this model and are subordinate to the charter.

- **"Stage," "provenance," and "release" carry exactly the meanings §3 fixes, never a fourth.** This document's own use of each term never drifts into an adjacent document's already-fixed meaning, and no third artifact called "release" exists anywhere in this design.
- **A version is an explicit, builder-triggered checkpoint of one stage's own configuration — constructs, bindings, and entity/schema/field/relationship/process-definition catalog content — never entity instance data and never an automatic snapshot.** (§4.1)
- **A version is orthogonal to a stage.** Each stage carries its own independent version history; a promotion neither creates nor consumes a version, and no check on promotion depends on one existing. (§4.2)
- **Every version anchors to the same, unchanging `application_id` and `tenant_id`.** No version rebinds an application to a new identity. (§4.3)
- **No table is defined by this document in a schema it does not own.** The version-history structure is constrained here and defined by `02-platform-data-model-design.md`. (§5)
- **Comparison is read-only and produces no audit event.** (§6, §12)
- **Revert composes entirely from two already-fixed write paths — an ordinary Gateway instance write, and an ordinary schema or process-definition-version proposal — never a third mechanism.** Neither compatibility determination is re-derived by this document. (§7)
- **A revert never writes to ordinary entity instance data.** The write surface a revert may touch is exactly the write surface a version's own manifest names. (§7.1)
- **A revert never rewrites or deletes an already-recorded catalog row, instance row, or version; every restoration is a new row extending the sequence forward.** (§7.4)
- **A stage's own bad promotion is recovered by reverting that same stage to an earlier version of its own history, never by a demotion or reverse-promotion mechanism.** No such mechanism is designed by this document. (§8)
- **A promotion never preceded by a captured version leaves nothing for revert to restore.** This is an honest limit, stated plainly, never closed by an unconditional safe-revert claim. (§9)
- **Version immutability is the library's ordinary insert-only discipline, never a second tamper-evidence mechanism; version provenance is which builder action produced a version, never whether any content was AI-suggested.** (§10)
- **This mechanism shares no code path, gate, or evidence record with the platform's own change-management and evolution policy.** The one routing point a backward-incompatible revert may reach is consumed exactly as already fixed upstream, never extended. (§11)
- **Every control this document fixes produces the evidence §12 names**, landing under Authorization and grant events as the closest available category, stated honestly rather than forced into an invented one.
- **Everything remains domain-neutral and platform-level.** No version, stage, or revert rule in this document encodes the characteristics of any single domain; all remain valid for any software built on the platform.
- **This document records exactly one ADR.** ADR-040 (§13) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, boundary, or invariant the cited specification and cited upstream design documents already fix.
