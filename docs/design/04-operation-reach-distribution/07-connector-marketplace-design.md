## 3. What Is Inherited From `06-marketplace-design.md`, Without Re-Derivation

`06-marketplace-design.md` §9 fixes precisely what a connector inherits from the general marketplace mechanism "without re-deriving it," and this document takes that instruction literally rather than restating the reasoning behind it.

### 3.1 The Deposit-and-Instantiate Mechanism, Unmodified

A connector is, structurally, artifact content of the identical kind `06-marketplace-design.md` §3.3 already establishes for the module shape: "already platform-accessible, opaque object content, never tenant-schema-resident data." An offering tenant's own connector — whether platform-team-authored, Extender-authored, or itself obtained from the marketplace — is a compiled artifact (a WASM module, for the Extender-authored and marketplace-submitted origins) or an in-process module reference (for the platform-team-authored origin); no connector's own artifact content is ever a row inside an offering tenant's per-application schema. **Depositing a connector to the marketplace catalog is therefore a reference copy, identically to a module**: the catalog's own row names the same already-platform-accessible artifact reference the offering tenant's own registration already names, with no read into any tenant schema required. Obtaining resolves that reference and hands it to the obtaining tenant; obtaining never constructs, registers, or activates anything, exactly as `06-marketplace-design.md` §6.2 fixes for the module shape. The obtaining tenant's own, separate, subsequent action — registering the connector under its own tenant (§6.3 below) — is what turns an obtained reference into working, tenant-owned state.

Checked against `02-tenant-isolation-and-access-control-design.md` §8's three structural facts, on the identical reasoning `06-marketplace-design.md` §3.4 already applies to every shape it covers: no naming path (the catalog's `artifact_reference` is a plain, non-enforced value, following the identical convention `07-cross-system-data-layer-design.md` §3.2's `connector_reference` and ADR-037 already establish); no grant path (depositing and obtaining each execute entirely within the acting tenant's own already-resolved connection); no silent path (every read and write runs inside a connection the mandatory self-verification read already covers). **No fourth path is added by admitting a connector rather than a module or an application.** The identical reasoning applies without modification, because nothing about a connector's own shape differs from a module's on any of the three facts the check is run against.

### 3.2 Why the Mechanism Fits `components/extension`, Not `components/reach` — a Second, Independent Convergence

`06-marketplace-design.md` §3.3 finds that the general marketplace's own deposit-and-instantiate split is "forced by the fixed dependency table" because C-13 sits inside `components/reach`, whose only allowed path to a tenant's own schema-resident content runs through Operation's own version-and-manifest read path. C-25 sits somewhere else entirely: `03-architecture-realization-design.md` §3.2 places "the cross-system data layer (C-24) and the connector marketplace (C-25)... inside `components/extension`, per the capability model's Extension family membership" — not inside Reach at all.

This placement makes the mechanism simpler for a connector than for the general marketplace's application shape, not harder, and it is a second, independent convergence worth stating explicitly rather than assuming away: because a connector's artifact is always opaque, already-platform-accessible content (§3.1) — never tenant-schema-resident data requiring an Offering Content Resolution step — depositing and obtaining a connector requires no read into Construction at all. The mechanism fits entirely within Extension's own already-allowed dependency on Isolation and Trust (`03-architecture-realization-design.md` §4.1's allowed-edge table), which every mechanism in this design already consumes for connection-scoping and the Resolved Request Context. **No new dependency edge is added, and none is needed** — the same "the marketplace mediates the cross-tenant-facing handoff; the tenant's own pre-existing mechanism performs the within-tenant activation" shape `06-marketplace-design.md` §3.3 identifies as the only shape the fixed table permits for C-13, and the identical shape falls out here for C-25 from the fact that Extension already houses both the connector marketplace's own mechanism and the extension registry the obtaining tenant's activation step (§6.3) uses — the offering-and-obtaining mechanism and the activation mechanism it hands off to are, for a connector, two operations of the same component rather than two components composed across an allowed edge.

### 3.3 The Six Submission Constraints, Composed Without Exemption

`06-marketplace-design.md` §5 realizes the specification's six submission constraints — license category, attribution, no unresolved incompatibility, mandatory security review, no cross-tenant reach, no domain content — against existing mechanisms. `03-software-and-architecture/05-integration-and-extensibility-spec.md` §8.5 fixes that "a connector offered through the connector marketplace crosses the extension boundary and satisfies every submission constraint of §6... before it is offered," identically to any other marketplace submission. This document inherits every constraint's realization unmodified for the license, attribution, incompatibility, and no-domain-content rows (§5 below); the mandatory-security-review and no-cross-tenant-reach rows are where a connector's own properties require this document's own determination, made in §4 and §5.

### 3.4 The Trust-Determination Method, Reapplied Not Inherited

`06-marketplace-design.md` §4.1 states the method plainly: "the deciding property is not who authored an artifact, and not which persona submitted it — it is whether the artifact executes inside the platform-core process at all," and §9 names this a "method to reapply, not a conclusion to inherit unexamined." §5 below reapplies it in full.

## 4. The Credential Boundary for Third-Party Connector Code

### 4.1 The Problem, Stated Precisely

C-25's own row fixes the rule this section exists to satisfy: "credentials a connector uses to reach an external system are never exposed in code, configuration, logs, or stored state (INV-03)" (`02-governance-and-security/02-security-policy.md` §4). A marketplace-obtained connector is externally-authored code the platform did not write, and its entire purpose is to authenticate to an external system on a tenant's behalf. `07-cross-system-data-layer-design.md` §4.2 already narrows the general credential guarantee for exactly this reason, for any connector regardless of origin: "a credential's purpose requires transmitting it, in usable form, to a system it does not control — the moment of use is a deliberate crossing, not a leak," and the platform's own guarantee is "the credential is never exposed anywhere *other than* that one authorized crossing." What that document does not state — because it is agnostic to which document answers the marketplace origin's own trust question (`07-cross-system-data-layer-design.md` §2) — is exactly where the boundary between the connector's own code and the credential's own value falls for **third-party** connector code specifically, code the platform team never reviewed and whose author may not act in the tenant's interest. That is this document's own question to answer.

### 4.2 Two Mechanisms Already Bear on the Answer

Two already-designed mechanisms fix most of the answer before this document adds anything:

- **`06-integration-and-extensibility-design.md` §5.3–§5.4 fixes that a host function is a caller, never a bypass, and that "no host function ever passes raw secret or key material into a guest's linear memory."** Where a host function must authenticate to an external system on an extension's behalf, "the authentication is performed host-side, entirely outside the guest's own reach." A marketplace-submitted connector, once obtained and registered, dispatches through the identical Extension Invocation Point a module does (§5 below) — so this rule already governs it without modification.
- **`07-cross-system-data-layer-design.md` §4.2 restates the identical discipline at the Connector Resolver specifically:** "resolution and outbound authentication happen entirely inside the Connector Resolver — host-side, never surfaced to the guest." The credential is unwrapped only transiently, at the point of the outbound call, using the tenant's own key-custody hierarchy (`04-security-controls-design.md` §7.2–§7.3, `02-platform-data-model-design.md` §8) — never given to the guest to hold, inspect, or forward.

**Neither mechanism, on its own, states what a connector's own guest code is permitted to control about the crossing it triggers.** A connector's entire value is that it knows a specific external system's own protocol — its request shapes, its endpoints, its response formats — knowledge the platform's own generic host functions cannot encode for every possible external system. The credential boundary this document must draw is therefore not "does the guest ever see the credential" (already closed, structurally, by the mechanisms above) but **"what can the guest's own declared request shape control, and does any of that control let a legitimately-scoped connection be misdirected."**

### 4.3 The Mechanism: Protocol Content Is the Guest's; Credential Attachment and Destination Are the Host's

**Decision: a connector's guest code builds the protocol-specific content of an outbound call — its path, body, and headers other than authentication — and hands that content to a host function that resolves the tenant's own registered connection, attaches the credential per a declared, closed authentication scheme, and dispatches to the tenant's own registered endpoint. Neither the credential's value nor the destination endpoint is ever a parameter the guest supplies at invocation time.**

- **The credential's value never crosses into guest memory, at any point.** This is the boundary §4.2's two mechanisms already fix, restated here as the floor this document does not relax: the host function performs the unwrap-and-attach step entirely host-side, using the same transient, point-of-use-only discipline `04-security-controls-design.md` §7.2 already fixes for any other credential.
- **The authentication scheme is declared, not raw, and drawn from a closed vocabulary.** A connector's own manifest declares which of a fixed, platform-defined set of attachment shapes its calls require — for example, a bearer token in a named header, an API key as a named query parameter, or a signing scheme applied to the request — the same closed-vocabulary discipline `06-integration-and-extensibility-design.md` §5.3 already applies to every host-function import: "there is no import a guest could request that reaches further than the platform explicitly offers." No declared scheme, and no host function realizing one, ever offers the guest a parameter that would return the attached value to it.
- **The destination is resolved from the tenant's own registration, never accepted as a guest-supplied override.** `tenant_<id>.external_system_connections.external_system_identity` (`02-platform-data-model-design.md` §3.2) is the tenant's own declared identifier for the specific external system its connection reaches, fixed at registration and read by the host function from the Resolved Request Context's own connection resolution — never from a value the connector's own call could supply as an alternative. **This is the connector-specific half of the boundary a module does not need, stated precisely**: a module's host functions reach platform capabilities whose destination is fixed by the platform itself; a connector's host function reaches a destination the *tenant* fixes at registration, and the one thing that must never happen is a connector's own declared interface accepting a parameter that substitutes a different destination for the tenant's own registered one. Without this rule, a connector could request the host attach a live, unwrapped-at-use credential to a request the connector itself directs anywhere it chooses — achieving exfiltration without the guest ever holding the credential's value, exactly by exploiting the one property §4.2's mechanisms do not, on their own wording, foreclose.
- **The response is untrusted input, validated at the boundary identically to any other Connector Resolver call.** `07-cross-system-data-layer-design.md` §4.3 already governs what happens to whatever the external system returns; this document adds no second validation step for a connector's own response specifically.

### 4.4 What Is Exposed, and What Is Not, Stated Exactly

- **Never exposed, structurally, regardless of the connector's own origin or intent:** the credential's own value, to the guest, to a log, to an error, to a response, or to any tenant other than the one whose connection it authenticates. No host function import exists through which a guest could request the raw value, and none is added by this document (§5.3, §5.4 of `06-integration-and-extensibility-design.md`, adopted without modification, §5 below).
- **Never redirectable, structurally:** the destination the credential is attached and sent to. It is resolved from the tenant's own registration record at the point of the outbound call, never from a guest-supplied parameter, closing the vector described in §4.3.
- **Exposed, by the crossing's own necessary purpose, and never claimed otherwise:** the credential's value, in unwrapped, usable form, to the one external system the tenant's own registration names — the identical, honestly-stated narrowing `07-cross-system-data-layer-design.md` §4.2 already fixes for any connector regardless of origin. This document adds nothing to, and takes nothing away from, that narrowing; it fixes only where the boundary of "the one authorized crossing" falls for third-party code specifically, which is: at the host function's own outbound call, resolved and destined entirely from the tenant's own registration, never at any point the connector's own guest code touches.
- **What this document does not, and cannot, guarantee:** identically to `07-cross-system-data-layer-design.md` §4.1's own "sharp edge, stated plainly" — the external system's own subsequent handling of a credential it was authorized to receive is outside this design's reach by definition. This document's mechanism guarantees the platform's own side of the crossing; it makes no claim about the receiving system's own conduct.

### 4.5 The Honest Limit, Inherited and Not Closed Further

**Closing the raw-value and destination-redirection vectors does not close the data-flow and intent-composition residual `06-integration-and-extensibility-design.md` §5.5 and `07-cross-system-data-layer-design.md` §6 already name, and this document does not claim to close it further.** A connector holding a legitimate, tenant-scoped registration and a legitimate grant to read some entity through the Entity Access Gateway can compose the two — reading data it is authorized to read and sending it, in its own request body, to the one external system its own registration legitimately authorizes reaching — without any confinement dimension above being violated, because no dimension was exceeded: the credential never left the host, the destination was never redirected, and the outbound content passed whatever validation applies to it. This is precisely the residual `07-cross-system-data-layer-design.md` §6 states as the vector `06-integration-and-extensibility-design.md` §5.5 already named its own cross-system data layer as, and this document inherits it for the connector case on identical terms, closed no further here than it was there. The only available mitigation remains how narrowly a tenant scopes the grant and the connection it registers at the point both are created — a decision this document does not narrow or widen for a marketplace-sourced connector relative to a directly-authored one.

## 5. The Marketplace-Submitted Connector's Trust Determination, Reapplied

### 5.1 Reapplying the Method

`06-marketplace-design.md` §4.1's method: weigh whether the artifact executes inside the platform-core process, and let that fact, not the submitting persona, decide the mechanism. Applied to a connector:

| Origin | Does It Execute Inside the Platform-Core Process? | Mechanism |
|---|---|---|
| Platform-team-authored, offered through the connector marketplace catalog for discoverability only | **Yes**, but governed by the ordinary governed-pipeline review `04-security-controls-design.md` §5.2 already fixes — this document adds nothing and decides nothing for this row. | Unaffected by this document. |
| Extender-authored | **Yes**, once registered and invoked — through the identical Extension Invocation Point and capability-scoped WASM sandbox `06-integration-and-extensibility-design.md` §5–§9 already designs, dispatched through the Connector Resolver per `07-cross-system-data-layer-design.md` §3.2's own statement that "an Extender-authored connector dispatches through the identical Extension Invocation Point a module does." | Already governed by `06-integration-and-extensibility-design.md`; this document's connector marketplace adds only the offering-and-obtaining mechanics (§6), not a new execution mechanism. |
| **Marketplace-submitted** | **Yes**, identically to the Extender-authored row once obtained and registered — the property `06-marketplace-design.md` §4.4 already establishes for the marketplace-submitted module (structurally the identical artifact type once registered, differing only in how the registering tenant came to hold the artifact reference). | **This document's own determination, reapplying `06-marketplace-design.md` §4.4's criteria rather than assuming its conclusion — §5.2 below.** |

### 5.2 Same Conclusion as the Module Case, on the Identical Criteria — and One Genuine Difference

**Decision: a marketplace-submitted connector is registered, resolved, and invoked through the identical Extension Invocation Point and capability-scoped WASM sandbox `06-marketplace-design.md` §4.4 already adopts for a marketplace-submitted module — extended to this origin, not duplicated for it. The isolation mechanism is unmodified. The mandatory review's own manifest inspection gains exactly one connector-specific item, never a new trigger condition or a new severity scale.**

Reapplying `06-marketplace-design.md` §4.4's four criteria, rather than assuming they resolve identically:

| # | Criterion | How It Resolves for a Connector |
|---|---|---|
| 1 | Does the deciding property (externally-authored, contract-bound, in-process-executing code) differ between a marketplace-submitted module and a marketplace-submitted connector? | **No.** Once obtained and registered, both are the identical artifact type — a compiled WASM binary, invoked through the same Extension Invocation Point, confined by the same fixed host-function import surface. A connector's host functions additionally include the credential-attachment and dispatch functions §4.3 fixes; §5.4's confinement dimensions apply to those functions exactly as to any other. |
| 2 | Does reusing the existing mechanism, rather than designing a variant, weaken any confinement dimension for the connector case specifically? | **No — for the same reason `06-marketplace-design.md` §4.4 already gives for the module case.** Each obtaining tenant's own registration independently bounds its own grant, regardless of how many tenants obtain the same underlying connector artifact; a connector obtained by many tenants carries no shared credential state across them, because each tenant supplies its own credential at its own registration (§6.3). |
| 3 | Does the marketplace's own mediation of the exchange establish that a connector is trustworthy, such that no separate isolation mechanism is needed? | **No, decisively — for the identical reason `06-marketplace-design.md` §4.4 already gives.** A mediated exchange constrains shape, never trustworthiness (`03-architecture-realization-design.md` §10.3); this is affirmed here without qualification. |
| 4 | Does a connector's additional property — that it carries a credential to an external system, a property no other marketplace shape carries — warrant a mechanism beyond the one criteria 1–3 already establish as sufficient? | **Not a new mechanism; one additional, deterministic inspection item within the existing structural capability-manifest check.** §4.6's existing mandatory-review trigger already fires unconditionally for every connector submission without modification: its own criterion — "whether the declared manifest requests any operation reaching the cross-system data layer's own credential-handling host functions" — is met by every connector's manifest as a matter of definition, since reaching those host functions is the entire purpose of a connector. What the credential-handling property adds is not a reason to review *more often*; it is one further, mechanically checkable fact the existing structural check must additionally verify: **that the connector's own declared interface never accepts a guest-suppliable parameter that would substitute for the destination the tenant's own registration resolves** (§4.3). This is deterministic — checkable directly from the manifest's own declared parameter shape, exactly as the existing check's closed-operation-set inspection already is — and it composes with, rather than duplicates or supersedes, `04-security-controls-design.md` §4.1–§4.2's existing scanning and severity-translation layer; no second severity scale and no new trigger condition is created. |

**The mandatory human-review row of `06-marketplace-design.md` §4.6 already reaches every connector submission without modification, because its own criterion is met by every connector's manifest as a matter of definition.** This document does not restate that trigger; it states only the one additional deterministic item the reviewer's own manifest inspection must check for this shape specifically (criterion 4 above), and the license/attribution/incompatibility rows compose unmodified (§3.3).

### 5.3 The Honest Statement of What This Does Not Decide

This document does not design a second sandboxing mechanism, a second severity scale, or a second review pipeline for the connector case. Where a future document — a connector-specific credential-scheme catalog, for instance — introduces a new attachment shape not covered by the closed vocabulary §4.3 names, extending that vocabulary is that future document's own determination, composing with the manifest check above rather than replacing it.

## 6. Packaging, Discovery, and Reuse

### 6.1 Packaging, by Origin

| Origin | What the Artifact Is | How It Is Deposited |
|---|---|---|
| Platform-team-authored | An in-process module reference inside `components/extension`, governed by the ordinary registry resolution `03-architecture-realization-design.md` §3.1 already fixes. | A reference copy naming the existing in-process reference; no new artifact form. |
| Extender-authored or marketplace-submitted | A compiled WebAssembly module (§5.1), registered as an opaque `artifact_reference`, together with a declared manifest naming: the closed set of `builder-tooling`-tagged host-function operations it requires (`granted_operations`, mirroring `tenant_<id>.extension_registrations`'s own column); the declared authentication scheme(s) its calls require, drawn from the closed vocabulary §4.3 fixes; and descriptive metadata for discovery (§6.2). | A reference copy, identically to a module (§3.1) — no tenant-schema read occurs, because the artifact was never tenant-schema-resident. |

**No connector artifact ever contains, declares, or requests inline the credential value itself.** The manifest's authentication-scheme declaration names a *shape* of attachment (§4.3), never a value; the value is supplied by the obtaining tenant at registration (§6.3), into its own connection record, never into the connector's own artifact or manifest.

### 6.2 Discovery

A read-only query interface, exposed from `components/extension` alongside the extension registry `03-architecture-realization-design.md` §3.1 already places there — never from `components/reach`, on the placement finding of §3.2 above. Any authenticated builder-persona actor may query the connector catalog (§9.1) for currently `offered` connectors, filtered by descriptive metadata (name, description, the external-system class the connector declares itself for) — reading the catalog exposes only what the offering tenant chose to make public by offering, on the identical restraint `06-marketplace-design.md` §6.3 already applies to the general marketplace's own catalog. This document fixes only that such an interface exists; ranking, categorization taxonomy, and presentation are execution-phase concerns this document does not design, on the identical restraint `06-marketplace-design.md` §6.3 and `04-publishing-and-delivery-design.md` §6.3 already apply.

### 6.3 Obtaining and Registration — Reuse Without Shared State

Obtaining a connector resolves the offering's platform-global artifact reference and hands it to the obtaining tenant, exactly as `06-marketplace-design.md` §6.2 fixes for a module; it constructs, registers, or activates nothing. The obtaining tenant's own, separate registration act is what makes the connector usable, and it is where reuse across tenants and per-tenant independence are both satisfied without conflict:

1. **The obtaining tenant registers the connector's artifact reference under its own `tenant_<id>.extension_registrations` row**, exactly as `06-marketplace-design.md` §4.4 fixes for a marketplace-obtained module — naming the marketplace-sourced `artifact_reference` and choosing its own `granted_operations` set, never wider than the manifest §6.1 declares.
2. **The obtaining tenant separately creates its own `tenant_<id>.external_system_connections` row** (`02-platform-data-model-design.md` §3.2), supplying its own credential (wrapped by its own `tenant_key`), its own `declared_region_of_record`, and its own `external_system_identity` — the tenant's own fact about which specific instance of the external system its connection reaches. `connector_origin` is set to `marketplace`, and `connector_reference` names the `extension_registrations` row created in step 1, following the identical plain-value, origin-discriminated convention ADR-037 already establishes for the `extender-authored` origin — a marketplace-sourced connector is, once both rows exist, structurally indistinguishable in shape from a directly Extender-authored one, differing only in provenance, which the audit trail (§9 of this document) carries.
3. **The same underlying artifact may be obtained and registered by any number of tenants independently, and each tenant's own credential, grant, and connection remain entirely its own.** `02-platform-data-model-design.md` §3.2 already fixes that `external_system_connections` "already carries connector identity, credential reference, and declared region-of-record per tenant" — a connector is *reused* (one artifact, one catalog row, one review) while each tenant's own connection is never shared, referenced, or made visible to any other tenant's registration. This is the identical reuse-without-shared-state property `06-marketplace-design.md` §4.4 already states for a module obtained by many tenants, restated here for the connector case because it is the property that makes "reusable, pre-built connectors" (C-25's own phrase) coherent with tenant isolation rather than in tension with it.

### 6.4 The Honest Limit, Restated for the Connector Case

**Withdrawing a connector offering never reaches an instance already obtained and registered**, on the identical reasoning `06-marketplace-design.md` §6.4 already states for a module or application: once a tenant's own `extension_registrations` and `external_system_connections` rows exist, that state is the tenant's own, and no structural path exists for the marketplace mechanism to retract it. An offering tenant that withdraws a defective or newly-incompatible connector has stopped its further spread, never reversed a tenant's already-registered use of it.

### 8.2 Against the Cross-System Data Layer (C-24)

- **Every connector this document admits and distributes is a Connector Resolver implementation, reached exclusively through the Unified Access Interface `07-cross-system-data-layer-design.md` §3.2 defines — never a second access path.** This is ADR-034's own Consequences clause, binding this document by name, and this document's mechanism realizes it rather than reopening it: nothing in §4 or §5 above grants a connector, of any origin, any reach into an external system other than through the Connector Resolver's own dispatch (§4.3), and nothing in this document's offering-and-obtaining mechanism (§6) constructs, activates, or invokes a connector directly — that remains the obtaining tenant's own registration act (§6.3) and, at request time, the Connector Resolver's own dispatch, exactly as `07-cross-system-data-layer-design.md` §3.2 already fixes for any connector regardless of how it was obtained.
- **This document does not redesign the Unified Access Interface, either resolver, or the five guarantees §4 of that document realizes.** It states, for the connector marketplace specifically, how a connector reaches the point of registration `07-cross-system-data-layer-design.md` §5 already reads from (§6.3); it does not touch what happens after registration, which remains entirely that document's own mechanism.
- **The credential-and-connection record this document's registration step writes into is the identical `tenant_<id>.external_system_connections` structure `07-cross-system-data-layer-design.md` §5 already constrains and `02-platform-data-model-design.md` §3.2 already defines.** This document adds no second connection record, no second credential store, and no second declared-region-of-record column; it is one more origin (`marketplace`) populating a structure that already exists for exactly this purpose.

## 9. Where Connector-Marketplace State Lives — Constrained Here, Handed Over

### 9.1 The One New Structure: a Platform-Global Connector Catalog, Distinct From the General Marketplace's Own

**Decision: the connector marketplace requires its own, separate platform-global catalog structure — never a fourth `shape` value in `06-marketplace-design.md` §10's own catalog.** Reapplying that document's own criterion 6 discipline (checking rather than assuming a structure is owed, and checking rather than assuming an existing structure may be silently extended):

| # | Criterion | How It Resolves |
|---|---|---|
| 1 | Does every column the general marketplace catalog already carries (offering identity, shape, `artifact_reference`, offering status, descriptive metadata) already express what a connector offering needs? | **No.** A connector offering additionally needs the declared authentication-scheme vocabulary its calls require (§4.3, §6.1) and the external-system class it declares itself for — content no application, module, or SDK-distributed-component offering carries, and content that would sit unused on every non-connector row if forced into the general catalog's own shape-agnostic metadata blob. |
| 2 | Is extending `06-marketplace-design.md`'s own `shape` enum to a fourth value an edit this ticket, or this document, is authorized to make? | **No.** `06-marketplace-design.md` §9 states plainly that "this document does not extend its own vocabulary to a fourth on C-25's behalf"; that document is a read-only dependency input to this ticket, and a design ticket does not edit another design document inline (`PROCESS.md` §1, `CLAUDE.md`). Treating the general catalog as silently extensible would violate that boundary regardless of the technical merits. |
| 3 | Does the deposit-and-instantiate *mechanism* (§3.1) require the offering and the underlying artifact to share one physical catalog table? | **No.** The mechanism is shape-agnostic behavior — a reference copy at deposit, a resolved reference at obtain — that composes identically regardless of which table's row records the "offered" state. Reusing the mechanism has never required reusing the general marketplace's own table, exactly as `06-marketplace-design.md` §4.4 already reuses `06-integration-and-extensibility-design.md`'s sandbox mechanism without reusing that document's own registration table. |

**A platform-global connector catalog is therefore constrained here and handed to `02-platform-data-model-design.md`, exactly as `06-marketplace-design.md` §10.1 hands over its own.** The structure must represent, without loss: the offering's own identity and the offering tenant it belongs to (a plain reference to `platform.tenants`); the connector's own origin (`platform-team-authored`, `extender-authored`, or `marketplace` — the identical three-value vocabulary ADR-037 already fixes for `external_system_connections.connector_origin`, reused rather than reinvented); an `artifact_reference`, carried as the identical plain, non-enforced, origin-discriminated value `06-marketplace-design.md` §10.1 and ADR-037 already establish for this shape of cross-schema-adjacent reference; the declared authentication-scheme vocabulary and external-system class descriptive metadata that make the offering discoverable and reviewable (§5.2, §6.2); its current offering status (`offered` or `withdrawn`, no default state before `offered`, on the identical reasoning `06-marketplace-design.md` §10.1 already states); and when the status was most recently set, and by whom, following the identical convention that document's own catalog and `platform.applications.publication_status_set_at`/`_by` already establish. **This document does not add the table.** Naming the concrete columns, types, and indexing is `02-platform-data-model-design.md`'s to do.

### 9.2 No New Per-Tenant Structure — Checked, Not Assumed

**Connector activation composes entirely with two already-existing per-tenant structures; this document adds neither a new table nor a new column to either.** §6.3 already states the mechanism: `tenant_<id>.extension_registrations` carries the obtaining tenant's own artifact reference and granted-operations set, exactly as it already does for a directly-authored or marketplace-obtained module; `tenant_<id>.external_system_connections` carries the obtaining tenant's own credential, declared region, and external-system identity, exactly as it already does for a directly-authored connector. The only new fact either row carries for the marketplace case is a value (`connector_origin = marketplace`) both tables' own vocabularies already accommodate (§9.1; ADR-037). **This document is, in this respect, in the same position `06-marketplace-design.md` §10.2 and H31 before it were found to be in: a hand-over is not automatic, and this document checks rather than assumes one is owed.** Having checked, it owes exactly one platform-global structure (§9.1) and no per-tenant structure at all — a hybrid of H32's finding (one new platform-global structure, no per-tenant structure for the module shape) and H31's finding (no structure owed at all), because this document's own new obligation is confined to the catalog alone.

## 11. Design Decision Records

### ADR-044 — The Connector Credential Boundary, the Reapplied Trust Determination, and the Separate Connector Catalog

- **Status:** Provisional — Pending Lead Approval, consistent with every design-phase ADR recorded since ADR-021.
- **Cost to reverse:** **High** (`PROCESS.md` §12.1). The credential-boundary mechanism (host-side attachment, destination pinned to the tenant's own registration, a closed authentication-scheme vocabulary) is the packaging contract every connector a tenant registers is already written against; reversing any part of it — allowing a guest-suppliable destination, or a different attachment-scheme vocabulary — requires every already-registered connector and every already-declared manifest to be re-validated or re-issued against the new contract. Not Brutal or Very high: no builder-defined entity data is touched, and no already-completed cross-region transfer or deletion-style action is performed by any mechanism this document designs — the exposure is to the *contract* every future connector submission and registration flows through, matching the architecture-and-contract rung `06-marketplace-design.md`'s own ADR-043 is graded at, not the data-model rung. Not Moderate or Low: the contract binds every connector the marketplace has ever offered and every tenant connection registered against one, not a single document's own internal structure.
- **Upstream decisions assumed:** `07-cross-system-data-layer-design.md` §3, §4, §5, §9 (ADR-034 — the Unified Access Interface, the Connector Resolver, the five guarantees this decision's credential-boundary mechanism extends, and the Consequences clause binding this document to treat every admitted connector as a Connector Resolver implementation reached exclusively through that interface); `06-integration-and-extensibility-design.md` §5, §6, §8, §9 (ADR-033 — the capability-scoped WASM sandbox this decision reapplies unmodified for the marketplace-submitted connector, and the closed host-function-import discipline the destination-pinning addition composes with rather than duplicates); `06-marketplace-design.md` §3, §4, §5, §9 (ADR-043 — the deposit-and-instantiate mechanism, the per-shape trust-determination method this decision reapplies, the six submission constraints, and the two open questions this decision answers); `02-tenant-isolation-and-access-control-design.md` §3, §5, §8 (ADR-018 — the three structural facts this decision's inherited exchange mechanism is checked against); `04-security-controls-design.md` §5, §7.2–§7.3 (ADR-021 — the key-custody operational model a connection's credential reference resolves through, and the platform-team-only scope this decision's own review addition composes with rather than extends); `02-platform-data-model-design.md` §3.2 (ADR-037 — the `connector_origin`/`connector_reference` plain-value, origin-discriminated convention this decision's catalog and registration mechanism both reuse rather than reinvent); `09-licensing-and-dependency-compliance-design.md` §3–§7 (ADR-026 — the license, attribution, and incompatibility mechanism this decision composes with unmodified); `03-architecture-realization-design.md` §3.1, §3.2, §4.1 (ADR-014 — the placement of C-24 and C-25 inside `components/extension`, and the dependency-direction table this decision's own mechanism is checked against in §3.2). ADR-021 through ADR-043 remain Provisional — Pending Lead Approval and are not assumed settled; this decision depends on their already-designed content, never on their approval status (`PROCESS.md` §12.2).
- **Verified vs. reasoned:** Reasoned throughout. This decision adopts, without re-verifying, the WASM-sandbox verification `06-integration-and-extensibility-design.md` §5.2 already performed (checked 2026-08-07); it asserts no new time-sensitive ecosystem, product, or vendor claim of its own.
- **Context:** `06-marketplace-design.md` §9 named two determinations explicitly as this document's own to make — a connector's own trust determination and its catalog-shape question — and named the credential-handling risk as the specific reason the trust question could not simply inherit the module case unexamined. `07-cross-system-data-layer-design.md` §4.2 already narrows the general credential guarantee to exclude the one necessary crossing, for any connector regardless of origin, but is explicitly agnostic to which document answers the marketplace origin's own trust question; neither document states where the boundary between a connector's own guest code and the credential's own value falls for third-party connector code specifically.
- **The question this ADR answers, phrased for reuse:** Given a capability whose entire purpose is to let externally-authored code authenticate to a system the platform does not control, and given that the credential such code uses can never be exposed to it directly, what must the code be permitted to control about the crossing it triggers, what mechanism enforces that boundary structurally, and does the credential-handling property that distinguishes a connector from every other marketplace shape change the isolation mechanism, the review mechanism, or the catalog structure that shape already has available?
- **Criteria applied, and how each resolved:**

  | # | Criterion | How It Resolved |
  |---|---|---|
  | 1 | Does the existing host-side-authentication discipline (`06-integration-and-extensibility-design.md` §5.4, `07-cross-system-data-layer-design.md` §4.2) fully close the credential-exposure vector for third-party connector code on its own, or does a connector's own declared interface retain a control that could defeat it? | **Not fully, on its own wording** — the existing discipline closes the credential's *value*; it does not, on its own, state that the *destination* the value is attached and sent to must also be resolved host-side rather than guest-suppliable. §4.3's destination-pinning rule closes the residual criterion 1 identifies. |
  | 2 | Does the connector case require a different isolation mechanism than the marketplace-submitted module case, or does the same mechanism, checked against the same criteria, still resolve the same way? | **The same mechanism, checked and confirmed, not assumed** (§5.2) — every one of `06-marketplace-design.md` §4.4's four criteria resolves identically for a connector on the property that decides them (in-process execution once registered), with the sole addition being one deterministic manifest item, not a different mechanism. |
  | 3 | Does the credential-handling property warrant a new mandatory-review trigger condition, or does the existing trigger already reach every connector submission? | **Already reaches every connector submission, by that trigger's own wording** — its criterion (any operation reaching the cross-system data layer's own credential-handling host functions) is met by every connector's manifest as a matter of definition, since reaching those host functions is a connector's entire purpose. No new trigger condition is added. |
  | 4 | Is a connector's own catalog need already expressible by the general marketplace's existing catalog columns, or does it require content no other shape carries? | **Requires content no other shape carries** (§9.1) — the declared authentication-scheme vocabulary and external-system class have no analogue in an application, module, or SDK-distributed-component offering. |
  | 5 | Is extending the general marketplace's own `shape` enum to a fourth value an edit available to this document? | **No** — that document is a read-only dependency input, and its own §9 explicitly declines to pre-extend its vocabulary on this document's behalf. |

- **Decision:** (1) A connector's guest code builds the protocol-specific content of an outbound call; a host function resolves the tenant's own registered connection, attaches the credential per a declared, closed authentication scheme, and dispatches to the tenant's own registered endpoint — neither the credential's value nor the destination is ever a guest-suppliable parameter (§4.3). (2) A marketplace-submitted connector is registered, resolved, and invoked through the identical Extension Invocation Point and capability-scoped WASM sandbox already adopted for a marketplace-submitted module, unmodified; the mandatory security review's existing manifest check gains exactly one deterministic, connector-specific inspection item — that the connector's own declared interface never accepts a guest-suppliable destination override — and no new trigger condition or severity scale (§5.2). (3) The connector marketplace requires its own, separate platform-global catalog structure, distinct from the general marketplace's own, constrained here and handed to `02-platform-data-model-design.md` (§9.1); no per-tenant structure is added, because connector activation composes entirely with `tenant_<id>.extension_registrations` and `tenant_<id>.external_system_connections`, both already existing (§9.2).
- **Alternatives considered:** *Treating the existing host-side-authentication discipline as sufficient on its own, with no destination-pinning addition* — rejected under criterion 1; it would leave open a path to attach a live credential to an attacker-directed request without the guest ever holding the credential's value, defeating the boundary's own purpose through the one control the existing wording does not foreclose. *Designing a connector-specific sandboxing mechanism distinct from the Extender-origin one* — rejected under criterion 2, on the identical reasoning `06-marketplace-design.md` §4.4 already rejects it for the module case: no confinement gain, and a fragmented registry. *Adding a new mandatory-review trigger condition specific to credential-handling code* — rejected under criterion 3; the existing trigger already reaches every connector submission by its own wording, and adding a second condition for a case the first already covers would duplicate rather than strengthen the check. *Extending `06-marketplace-design.md`'s own `shape` enum to a fourth value* — rejected under criteria 4 and 5; the content genuinely differs, and the edit is not this document's to make regardless of the technical merits. *Adopting the workflow-engine adoption constraints the ticket producing this document mis-cited as governing a connector's own reach* — rejected; those constraints govern the platform's own choice of infrastructure dependency, not the admission of a tenant-facing, third-party-submitted artifact, and this document relies instead on `07-cross-system-data-layer-design.md` §4's five guarantees and `06-marketplace-design.md` §5's six submission constraints, both of which are the constraint sets that actually govern this case.
- **Consequences:** Binds `02-platform-data-model-design.md` to add the one platform-global connector-catalog structure this document constrains but does not define (§9.1), on a future, separately-ticketed amendment. Binds every host function realizing a connector's own credential-attachment or dispatch capability to resolve its destination from the invoking tenant's own `external_system_connections` row and never from a guest-supplied parameter — a constraint any future document extending the connector's own host-function surface must preserve. Adds no obligation to `07-cross-system-data-layer-design.md`'s Unified Access Interface or Connector Resolver dispatch logic, `06-integration-and-extensibility-design.md`'s Extension Invocation Point or confinement mapping, `09-licensing-and-dependency-compliance-design.md`'s check or sweep mechanism, or `08-audit-and-traceability-design.md`'s record shape — each is consumed exactly as already designed, extended only where §10 above names a new `event_type`.

## 14. Binding Rules

- **A connector's own guest code never holds the credential it authenticates with, and never controls the destination that credential is attached and sent to.** The value is attached and dispatched entirely host-side, resolved from the tenant's own registration; neither is ever a guest-suppliable parameter (§4.3, §4.4).
- **This is the one authorized crossing, stated exactly.** The credential is exposed, in unwrapped form, only to the one external system the obtaining tenant's own registration names, at the host function's own outbound call — never to the guest, never to any other tenant, and never to a destination the connector's own declared interface could substitute (§4.4).
- **Closing the raw-value and destination-redirection vectors does not close the data-flow and intent-composition residual `06-integration-and-extensibility-design.md` §5.5 and `07-cross-system-data-layer-design.md` §6 already name.** This document inherits that residual for the connector case and closes it no further (§4.5).
- **A marketplace-submitted connector is registered, resolved, and invoked through the identical Extension Invocation Point and capability-scoped WASM sandbox already adopted for a marketplace-submitted module, unmodified.** The credential-handling property adds one deterministic manifest item, never a new isolation mechanism, a new review trigger, or a new severity scale (§5.2).
- **The mandatory security review already reaches every connector submission as a matter of definition.** No connector's manifest can avoid triggering it, because reaching the credential-handling host functions is a connector's entire declared purpose (§5.2).
- **Every one of the six submission constraints applies to a marketplace-obtained connector exactly as to a directly-authored one; a marketplace origin creates no exemption** (§3.3).
- **Every connector this document admits and distributes is a Connector Resolver implementation, reached exclusively through the Unified Access Interface — never a second access path.** This document opens none (§8.2, ADR-034's Consequences).
- **A connector is reused while each tenant's own connection remains its own.** The same underlying artifact may be registered by any number of tenants; no tenant's own credential, grant, or connection is ever shared, referenced, or made visible to another tenant's registration (§6.3).
- **Withdrawing a connector offering never reaches an instance already obtained and registered.** No structural path exists for the marketplace mechanism to retract what a tenant's own registration has already committed (§6.4).
- **The connector marketplace requires its own platform-global catalog, distinct from the general marketplace's own; no per-tenant structure is owed beyond what already exists.** `tenant_<id>.extension_registrations` and `tenant_<id>.external_system_connections` already carry everything a marketplace-sourced connector's registration needs (§9).
- **Everything remains domain-neutral and platform-level.** No mechanism, scheme, or constraint in this document encodes the characteristics of any single domain, external system, or example connector; all remain valid for any connector, any tenant, and any region.
- **This document records exactly one ADR.** ADR-044 (§11) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, boundary, or invariant the cited specification and cited upstream design documents already fix.
