# Builder-Facing Environment Management Design — AI ahaMatic

This document realizes `01-business-and-ux/02-prd.md`'s C-23 row as concrete mechanism: the means for a professional builder to promote the applications they build across Development, Testing, and Production stages — the stage model, the promotion and gating rules, per-tenant/per-application isolation, and the optional human-approval gate on promotion to Production. It answers **how**, never re-deciding what the specification already fixes, and never designing the platform's own environment topology, which is a distinct, platform-internal concern this document bounds against rather than realizes.

This is a Design-phase artifact realizing, in addition to C-23's own row: `01-application-runtime-and-lifecycle-design.md` §7 (the identity anchors this document must anchor to, and the constraint its §12 places on this document by name); `01-application-construction-design.md` §3, §4, §6 (the construction action and configuration model this document's Development stage already is); `02-platform-data-model-design.md` §3, §9, §10 (the schema hierarchy this document constrains and hands a new structure to, per `BACKLOG.md` §1i's standing rule); `02-tenant-isolation-and-access-control-design.md` §3, §5, §6 (the Registry Accessor, Context Resolution Point, connection-scoping, and schema-level-bridge precedent this document's promotion mechanism composes with); `06-compliance-and-data-residency-design.md` §3.3–§3.4, §8 (the Region Boundary Check this document's writes compose with, and the held-state precedent for its own approval gate); and `08-audit-and-traceability-design.md` §4.2–§4.3 (the consolidated audit event model this document's evidence composes with).

**Verified versus reasoned (`PROCESS.md` §12.3).** Every finding in this document is **reasoned** — from the cited specification and the cited, already-written upstream design documents. No time-sensitive ecosystem, product, or vendor claim is made anywhere in this document.

## 1. Purpose and Reading Order

This document answers five questions:

- **What must never be confused with what** — the two vocabulary collisions a reader of this document and its neighbors would otherwise fall into, disambiguated before anything else is designed (§3).
- **What concretely carries a "stage," given that a built application's identity may not be rebound for the purpose of promotion, and its stages must nonetheless be strictly isolated** — the central tension this document exists to resolve (§4).
- **What the three stages are, concretely, and how per-tenant/per-application isolation holds for each** (§5).
- **What moves when an application is promoted, in what order, and what blocks a promotion** (§6–§8).
- **What evidence this mechanism produces, and what design decision this document records** (§9–§10).

It is structured as a pyramid: first the two collisions this document must not fall into (§3); then the identity/isolation tension and its resolution (§4); then the stage model built on that resolution (§5); then promotion and gating (§6); then the human-approval gate (§7); then the boundary against the platform's own CI/CD and environment topology (§8); then the residency question (§9); then evidence (§10); then the design decision (§11); then boundaries, precedence, and binding rules (§12–§14).

## 3. Two Vocabulary Collisions This Document Must Not Fall Into

### 3.1 The Platform's Own Tiers Are a Different Subject, With Adjacent Names

**The platform's own environment tiers are Development → Staging → Production** (`04-devops-and-cloud-infra/01-environment-and-config-spec.md` §4). **This document's builder-facing stages are Development → Testing → Production.** The two vocabularies share two of three names and differ in the middle one, and they govern entirely different subjects: the platform's tiers govern how the platform's own core code and configuration are promoted toward serving every tenant; this document's stages govern how one builder's one built application is promoted toward serving that application's own end users. C-23's own definition (`01-business-and-ux/02-prd.md` §4) requires the two be "kept strictly separate" — a builder-facing concern, distinct from the platform's own internal environment topology, which remains that spec's alone.

**Stated plainly, once, so no later section needs to restate it:** wherever this document uses "Development," "Testing," or "Production" unqualified, it means one of *this application's own three stages*, never a platform tier. Wherever this document needs to refer to the platform's own tiers, it names them explicitly as "the platform's own tiers" or cites `04-devops-and-cloud-infra/01-environment-and-config-spec.md` directly. No promotion this document designs advances platform-layer code or configuration through the platform's own tiers, and no action against the platform's own tiers advances a builder's application through this document's stages (§8).

### 3.2 "Stage" Already Names a Different Axis One Layer Below

`01-application-runtime-and-lifecycle-design.md` §7 uses "stage" for the four positions of a *different* axis entirely — build → configure → publish → operate, the lifecycle transitions every built application passes through regardless of which of *this* document's three environments it currently occupies. That document's own §7.4 already anticipates the collision by name: "whatever this document eventually defines as... 'a stage' of a built application must anchor to the same `application_id`." The two axes are orthogonal — an application in its Development environment is simultaneously somewhere on the build/configure/publish/operate axis (most concretely, "configure," since Development is exactly where a builder configures constructs and bindings), and an application already being operated (in the runtime sense) may be operating from its Development, Testing, or Production environment depending on who is reaching it and how (§5.4).

**This document's own usage, fixed once:** every occurrence of "stage" in this document means one of the three builder-facing environments — Development, Testing, Production — never a build/configure/publish/operate position. Where this document needs to refer to the other axis, it says "lifecycle transition" and cites `01-application-runtime-and-lifecycle-design.md` §7 directly, never "stage" unqualified.

## 4. The Central Tension and Its Resolution

### 4.1 What Must Not Change

`01-application-runtime-and-lifecycle-design.md` §7.2 fixes three identity anchors — `application_id`, `tenant_id`, and `schema_name` — as fixed at construction and carried, unchanged, through every subsequent transition. §7.4 states the constraint this document inherits by name: whatever this document defines as "a stage" of a built application "must anchor to the same `application_id`... never a rebinding of the application to a new identity for the purpose of... promotion." A design in which each of Development, Testing, and Production is its own `platform.applications` row — its own `application_id` — would violate this directly: the three would no longer be stages *of one application*, anchored to one identity, but three separate applications a promotion copies content between. This document does not adopt that design, for exactly the reason its own dependency forbids it.

### 4.2 What Must Be Isolated

C-23 simultaneously requires "the isolation that keeps each builder's environments strictly separate per tenant and per application" (`01-business-and-ux/02-prd.md` §4). Strict separation means, concretely, that Development's data, Testing's data, and Production's data must never be the same stored rows — a builder's test fixtures must never leak into, or be overwritten by, production records, and vice versa. A single schema shared by all three stages, distinguished only by a stage column on every table, would not meet this: it would make isolation a predicate a query must remember to apply, exactly the "assumed, not verified" failure mode `01-technology-stack-design.md` §14.5 already rejects for tenant isolation, reintroduced here for stage isolation instead.

### 4.3 The Resolution: One Identity, Sibling Schemas

**`application_id` and `tenant_id` remain singular and unchanged across all three stages of one application. What varies per stage is which physical schema currently holds that stage's own catalog rows and entity data — realized as sibling per-application schemas, one per stage, all scoped to the same, unchanging `application_id`.**

- **Development is exactly the schema `01-application-construction-design.md` §3's construction action already produces**, named and shaped exactly as `02-platform-data-model-design.md` §3.3 already fixes (`tenant_<tenant_id>_app_<application_id>`), holding `application_metadata` and `application_key` before any builder-defined content exists, and every builder-defined entity, construct, and binding a builder subsequently configures. This document changes nothing about how that schema is produced or populated. `platform.applications.schema_name` (§3.1 of that document) continues to name it, unaltered, as the Development stage's schema — never reassigned, exactly as `01-application-runtime-and-lifecycle-design.md` §7.2 fixes.
- **Testing and Production are additional, structurally identical schemas, materialized on first promotion into each, never at construction.** Each carries the identical two platform-owned tables (`application_metadata`, `application_key`) any per-application schema carries before builder-defined content exists, and is registered — not in `platform.applications`, which keeps exactly the two-column identity-and-Development-schema shape it already has — but in a new, per-tenant structure this document constrains and §4.4 hands to `02-platform-data-model-design.md` to define physically.
- **No new `platform.applications` row, and no reassignment of the row's existing `schema_name` column, occurs anywhere in this design.** The identity anchor `application_id`/`tenant_id` names exactly one application, always; what a promotion changes is never that identity, but which sibling schema a given request or action is resolved against (§5.4).

This is why the tension resolves without trade-off: identity stays exactly as fixed, because nothing about it changes when a stage is added; isolation is structural, not conventional, because Testing's and Production's data live in schemas with no table, view, or grant connecting them to Development's or to each other's, exactly the same discipline `02-platform-data-model-design.md` §4.1 already uses to make tenant isolation structural rather than assumed.

### 4.4 Where the New Structure Lives — Constrained Here, Defined There

Per `BACKLOG.md` §1i's standing rule and the precedent ADR-037 and the `administrative_scope_grants`/`extension_registrations`/`external_system_connections` tables already set (`02-platform-data-model-design.md` §3.2), this document does not define a table in a schema it does not own. It constrains `02-platform-data-model-design.md` to add, at the per-tenant level, a structure capable of representing, without loss:

- which application (an `application_id`, constrained to the tenant's own `platform.applications` rows) a row describes;
- which of the two stages beyond Development — Testing or Production — the row describes (Development needs no row here, per §4.3);
- the physical `schema_name` that stage currently resolves to;
- when that stage's schema was first materialized;
- which stage the schema's current content was most recently promoted from, for provenance (§6.1, §10);
- for a Production-stage row only, whether promotion into it requires an explicit human-approval decision (§7), a builder-configured value this document does not fix a default for.

This document additionally constrains `02-platform-data-model-design.md` §3.3's `application_metadata` table: every stage's own copy of it must record which stage its own schema realizes, alongside the `application_id`/`tenant_id` it already records. Without this, the mandatory self-verification read (`02-tenant-isolation-and-access-control-design.md` §5.2) — which proves a connection's application/tenant boundary by comparing this table's content against the Resolved Request Context — could not detect a defect that mis-scoped a connection to a *different stage of the same application*, since `application_id` and `tenant_id` alone would still match. Extending that same self-description with the stage it realizes closes this gap using the identical mechanism, never a second one (§5.4).

`02-platform-data-model-design.md` defines the physical table, its columns, and its constraints; this document defines only what must be representable and why, exactly as `01-application-construction-design.md` §6 already does for the data model it constrains without owning.

## 5. The Three Stages, Concretely

### 5.1 Development

Development is not a capability this document adds — it is the application `01-application-construction-design.md` §3 already produces, configured exactly as that document's §4 already fixes, with zero change to the construction action, the configuration model, or how a builder brings a construct or a binding into existence. Every construction and configuration action a builder performs targets Development's schema, always, because that is the only schema construction ever produces and the only one `01-application-construction-design.md`'s mechanism ever writes to.

### 5.2 Testing and Production

Neither exists until an application is first promoted into it (§6). Materializing a stage's schema on first promotion is structurally identical to what construction already does for Development — a new, empty schema and its two platform-owned tables, nothing else — and this document introduces no second construction mechanism to produce it; it is the same schema-creation action, invoked for a sibling schema of the same `application_id` rather than for a new one (§4.3).

### 5.3 Per-Tenant, Per-Application Isolation — Composing With, Never Substituting For, Tenant Scoping

Every stage's schema is provisioned exactly as `02-tenant-isolation-and-access-control-design.md` §5.1 already provisions any application schema: one database role, scoped to that schema alone, using ordinary `GRANT`/`REVOKE`, with no schema granted to any role by default. A stage boundary adds no isolation strength of its own beyond what schema-scoped connection-scoping already provides for any application schema — it is not a second tenant-scoping path, and no mechanism in this document narrows or widens the tenant boundary `02-tenant-isolation-and-access-control-design.md` §3–§8 already fixes. Isolation between two stages of one application is the identical mechanism as isolation between two different applications of one tenant (§4.3's sibling-schema design), composing with, never duplicating, the connection-scoping and self-verification mechanism already fixed there.

Cross-stage access, where a promotion genuinely needs it (§6.3), is possible for exactly the reason `02-platform-data-model-design.md` §4.2's schema-level bridge is possible between two applications of one tenant: both schemas already sit inside the same tenant's connection and credential scope. This document's promotion mechanism reuses that same precedent — never a bridge between tenants, and never a standing grant outside the promotion action itself (§6.3).

### 5.4 Which Stage a Request Targets

**Every construction and configuration action, without exception, targets Development.** No mechanism in this document changes this (§5.1).

**Every runtime request (`01-application-runtime-and-lifecycle-design.md` §3–§5) targets exactly one stage, resolved once, at the same Context Resolution Point that already resolves tenant and application context.** This document extends that already-fixed resolution point (`02-tenant-isolation-and-access-control-design.md` §4.1) with one further resolved value — the **Resolved Stage** — carried in the same frozen Resolved Request Context object, never a second resolution mechanism: an application- and tenant-scoped actor's own request narrows to a stage exactly as it already narrows to an application (`02-tenant-isolation-and-access-control-design.md` §3.1's "act as application X" row, extended by one further narrowing dimension, "and this application's stage Y"), and an end-user request against a published application resolves, by default and without any caller-supplied override, to that application's Production stage — because publishing (`04-publishing-and-delivery-design.md`, not yet written) is what extends reach to end users at all, and this document does not design, or presume, any path by which an end user's request could resolve to a stage other than Production. This document fixes the resolved value and the extension point only; whether and how a builder's own tooling exposes "preview my Testing stage" as a UI concept is not this document's to design.

Once a stage is resolved, connection acquisition switches the active database role to the stage's own schema exactly as it already does for any application schema (§5.3), and the mandatory self-verification read (`02-tenant-isolation-and-access-control-design.md` §5.2) compares the connected schema's own self-description — now including the stage it realizes (§4.4) — against the Resolved Stage. A mismatch is treated identically to an application/tenant boundary mismatch: the request halts before any further query executes, per the halt behavior `01-invariant-enforcement-design.md` §3.3, §5.1 already fixes. This document adds no second check location; it extends the one already there with one further comparison.

## 6. Promotion — What Moves, and How

### 6.1 What Promotion Moves

**A promotion moves the application's own configuration — its constructs, its structural, behavioral, and access bindings, and its entity, schema, field, and relationship definitions (`02-data-model-and-entity-design.md` §3.2's four catalogs) — from the source stage's schema into the destination stage's schema. A promotion never moves entity instance data.** Each stage accumulates its own records independently, from the moment its schema is first materialized (§5.2), through whatever actors reach it under §5.4's resolution — a builder's own test activity against Testing, or an end user's own activity against Production. This is the concrete form C-23's isolation requirement takes at the level of data, not only of schema: Testing's records are never overwritten by, and never overwrite, Production's, because a promotion's own write set never includes an entity instance row.

This is deliberately narrower than what `03-builder-facing-version-control-design.md` (C-21, not yet written) will eventually define as "a version" of a built application. This document does not design version comparison, revert semantics, or artifact immutability — it states only that whatever moves during a promotion is the application's current configuration state at the moment of promotion, and that this is the minimum this document needs to state for its own mechanism to be complete; C-21's own document may define a richer notion of "version" that a promotion consumes, without this document anticipating or narrowing it (`01-application-runtime-and-lifecycle-design.md` §7.4).

### 6.2 Sequential and One-Directional — No Skip

**Promotion advances a stage in exactly one order, Development → Testing → Production, and never skips a stage.** No specification text requires or forbids this ordering; it is this document's own reasoned decision (§11), adopted because Testing exists specifically to validate a configuration under conditions closer to Production before Production is risked, and a promotion path that could bypass it would defeat that purpose entirely rather than merely weaken it. This is stated as an independently-adopted, builder-facing choice, analogous in shape to — but never derived from, and never binding upon — the platform's own one-directional, sequential promotion ordering (`04-devops-and-cloud-infra/01-environment-and-config-spec.md` §4); the two orderings exist for unrelated reasons and neither obliges the other.

This document designs no demotion, rollback, or reverse-promotion mechanism. Recovering an earlier configuration state is `03-builder-facing-version-control-design.md`'s revert semantics once that document exists, or `05-meta-operations/07-self-correction-and-fallback-protocol.md`'s recovery mechanics where a promotion itself fails mid-action (§6.4); this document's own promotion action moves in one direction only.

### 6.3 The Promotion Mechanism

A promotion is initiated by an actor whose already-resolved standing (`02-tenant-isolation-and-access-control-design.md` §6) includes the grant to promote the named application — a tenant-scoped builder role (operator or publisher, `01-business-and-ux/04-personas-and-roles.md` §5) narrowed to that application exactly as `tenant_<id>.tenant_user_application_scope` already narrows any other builder grant, never a caller-supplied identifier. This is a distinct authorization dimension from a construct's own access binding (§4.2.4 of `01-application-construction-design.md`): View and Invoke govern an end user's or another system's reach into an already-configured construct's own runtime behavior; promoting an application between stages is never itself a construct action, and no access binding governs it.

Given that grant, the promotion action:

1. **Confirms the destination stage's schema exists, materializing it first if this is the first promotion into that stage** (§5.2) — structurally identical to the construction action's own schema-creation step, applied to a sibling schema of the same `application_id`.
2. **Reads the source stage's four catalogs, in full, through the Entity Access Gateway** (`02-data-model-and-entity-design.md` §4.1) — an ordinary Gateway-mediated read, never a second read path opened for promotion specifically.
3. **Writes the read content into the destination stage's own catalogs, through the same Gateway, as one all-or-nothing operation** — a failed write leaves the destination stage's prior content (if any) exactly as it was, per the identical deny-by-default discipline `02-data-model-and-entity-design.md` §4.2 already fixes for any Gateway-mediated write; a promotion never completes partially.
4. **Records provenance** — which stage the destination's new content was promoted from (§4.4) — as part of the same write, never a separate, un-atomic bookkeeping step.

Both schemas already sit inside the same tenant's connection and credential scope, exactly as `02-platform-data-model-design.md` §4.2's schema-level bridge already establishes for two applications of one tenant (§5.3); this document's promotion reuses that same structural fact for two stages of one application, never inventing a second cross-schema access mechanism. No connection this action acquires has any privilege to name a schema belonging to a different tenant, for the identical reason `02-tenant-isolation-and-access-control-design.md` §8 already gives for why cross-tenant access has no structural path to exist.

### 6.4 What Blocks a Promotion

A promotion does not proceed, and is refused before any read or write occurs, where any of the following holds:

- **The acting identity's resolved standing does not include the promotion grant for the named application** (§6.3) — refused exactly as any other ungranted action is, per the deny-by-default posture `02-tenant-isolation-and-access-control-design.md` §6 already fixes.
- **The promotion targets a stage other than the one immediately following the source stage** — a request to promote directly from Development to Production, skipping Testing, is refused (§6.2).
- **Any check the Entity Access Gateway already runs on the read or the write fails** — the Validation Engine, the Consent and Minimization Check, or classification/category resolution refusing either the read from the source or the write to the destination halts the promotion before it completes, per that document's own already-fixed discipline; this document adds no new refusal shape of its own.
- **The promotion targets Production and the application's own configuration requires explicit human approval, and that approval has not yet been recorded** (§7) — the action produces a held state rather than either an outright refusal or completion.
- **The Region Boundary Check refuses or holds the underlying write** (§9) — composed with, never bypassed, exactly as any other write against a scoped connection.

## 7. The Human-Approval Gate for Promotion to Production

### 7.1 The Trigger

C-23 fixes that "promotion to Production may require explicit human approval" — an optional, builder-configured condition, never a platform-mandated one for every application. This document fixes the trigger as: **an attempted promotion from Testing to Production, where the application's own Production-stage configuration (§4.4) records that promotion into it requires approval.** No other promotion — Development to Testing, or a Testing-to-Production promotion for an application that has not configured the requirement — triggers this gate. This document does not fix a default value for the configuration itself; whether an application requires this approval by default is a builder-facing configuration choice this document leaves to whichever builder-tooling surface exposes it, consistent with the builder/built separation already applied to every other configuration choice in this design library.

### 7.2 The Held State

Where the trigger fires, the promotion action (§6.3) does not proceed to step 2 of its own sequence. It resolves to a **held** state — distinct from a refusal, and releasable only by an explicit, recorded approval decision, exactly the register `06-compliance-and-data-residency-design.md` §8.2 already establishes for its own runtime-action approval triggers, reused here for a structurally similar but substantively distinct purpose: that document's held state protects a residency obligation; this document's protects a builder's own governance choice over their own application's most consequential stage. The two are never conflated, and this document's held promotion is never released by, and never counted toward, any residency approval, and vice versa.

**What is blocked, concretely.** The destination stage's schema is not written to, and its prior content (if any) is left exactly as it was, until the hold is released. No timeout, retry, or default resolves a held promotion to "applied" — the same discipline `06-compliance-and-data-residency-design.md` §8.2 already states for its own held actions.

### 7.3 What This Document Hands to the Human-in-the-Loop Protocol

This document's own obligation stops at producing the held state and never releasing it except on a recorded approval. **How the approval is requested, routed, recorded, and resolved is `05-meta-operations/04-human-in-the-loop-protocol.md`'s in full**, exactly as `06-compliance-and-data-residency-design.md` §8 already hands its own approval mechanics to that same document. This document designs no approval UI, no routing logic, and no escalation path.

## 8. The Boundary Against the Platform's Own CI/CD and Environment Topology

**A builder promoting their own application is not a platform release, and triggers none of the platform's own pipeline gates.** `04-devops-and-cloud-infra/02-ci-cd-pipeline-spec.md` §4–§7 fixes the Merge Gate and the two Deploy Gates that a change to platform-layer code or configuration must pass before reaching the platform's own Production tier; none of those gates evaluates, is evaluated by, or is even aware of, this document's own Stage Promotion mechanism. Conversely, this document's own promotion mechanism never advances platform-layer code or configuration through the platform's own environment tiers, and never depends on, or is blocked by, any state of the platform's own pipeline. The two mechanisms share no code path, no gate, and no evidence record: this document's `stage-promotion` event (§10) is never folded into, and never substitutes for, any `pipeline-scan`, `vulnerability-classification`, or deploy-gate event the platform's own pipeline already produces (`08-audit-and-traceability-design.md` §4.3).

`04-devops-and-cloud-infra/01-environment-and-config-spec.md` is read on this ticket's own instruction as the boundary this document must state accurately, never as a specification this document realizes — that spec's own tiers, its promotion ordering, its per-region configuration boundaries, and its Production protection are realized by `01-environment-and-configuration-design.md` (Layer 5, not yet written), a document distinct from this one, designing a distinct subject, for a distinct audience.

## 9. Residency: Is a Stage Promotion a Data Movement?

`06-compliance-and-data-residency-design.md` §3.4's Region Boundary Check treats a cross-region transfer as requiring both regions' permission; §8.2 holds four runtime-action triggers for human approval, one of which is "moving Jurisdiction-Restricted or Regime-Governed data across a region boundary." This document determines, and states plainly, whether a stage promotion is such a movement.

**Finding: a stage promotion is not a cross-region data movement, for two independent reasons.**

- **A promotion moves configuration catalog rows, never entity instance content** (§6.1). The four catalogs a promotion reads and writes (`02-data-model-and-entity-design.md` §3.2) describe the *shape* of an entity — its fields, their classification tier, their governance category — never the classified *content* itself. The residency mechanism's per-tier consequence (`06-compliance-and-data-residency-design.md` §5) attaches to data being stored, processed, or transferred; a catalog row describing what a field's classification tier *will be, once populated* carries no content for that consequence to attach to.
- **Every stage of one application shares exactly one `region_of_record`.** `02-platform-data-model-design.md` §3.1 fixes `region_of_record` as a column on `platform.applications` — one row, one value, per `application_id` (§4.3 above; this document adds no second identity, and therefore no second `region_of_record`). Because Development's, Testing's, and Production's schemas are all sibling schemas of the same, single application identity (§4.3), every promotion between them is, by construction, a movement within the same resolved region-of-record, never across one. There is no code path in this design by which a promotion's source and destination stage could resolve to different `region_of_record` values, because both resolve to the identical `platform.applications` row.

**The honest limit.** This finding rests on the region topology as it exists in this design library today — one `region_of_record` per application, with no per-stage regional differentiation defined anywhere. Should `08-multi-region-distribution-design.md` (not yet written) ever introduce a mechanism that places different stages of one application in different physical regions, this finding would need revisiting by that document, which inherits this document's obligation model as a constraint its own topology must satisfy, exactly as it already inherits `06-compliance-and-data-residency-design.md`'s (`06-compliance-and-data-residency-design.md` §11). This document does not design for that hypothetical, because no authorized document today creates it.

**This finding does not exempt a promotion's own writes from the Region Boundary Check.** Every write a promotion performs (§6.3) still acquires its connection through the same function that already carries the Region Boundary Check inline (`06-compliance-and-data-residency-design.md` §3.4); this document's finding is that the check will find no cross-region obligation to enforce for a stage promotion specifically, not that the check is bypassed for one. Where an unrelated obligation (an unresolved `region_of_record`, for instance) would refuse or hold any other write against the application's schema, it refuses or holds a promotion's write identically, composed with, never duplicated by, this document's own mechanism.

## 11. Design Decision Records

### 11.1 ADR-039 — The Stage Model: Sibling Per-Application Schemas Under One Unchanging Identity

- **Status:** Provisional — Pending Lead Approval.
- **Cost to reverse:** **Moderate** (`PROCESS.md` §12.1; matches `implementation-document-map.md`'s own pre-assigned grade for this document). The stage and promotion topology is substrate-shaped: reversing the sibling-schema design — for example, to a single shared schema distinguished by a stage predicate — requires re-deriving the stage-schema mapping and the promotion mechanism, but does not reshape `platform.applications`' own already-fixed identity columns, and does not migrate builder-defined entity content in a way a schema-per-application reversal would. Not Brutal or Very high: no application's own `application_id` or `tenant_id` ever changes under this decision, and each stage's own schema is re-derivable from the same construction mechanism already fixed, rather than requiring a data migration of already-stored content across a changed partitioning boundary.
- **Upstream decisions assumed:** `01-application-runtime-and-lifecycle-design.md` §7.2, §7.4 (the identity anchors this decision anchors to, and the constraint that a stage may not rebind `application_id`); `01-application-construction-design.md` §3–§4 (the construction action and configuration model this decision's Development stage already is, unaltered); `02-platform-data-model-design.md` §3.1, §3.3, §4.2 (the registry, the per-application schema shape, and the schema-level-bridge precedent this decision's cross-schema promotion reuses); `02-tenant-isolation-and-access-control-design.md` §3–§6 (the Registry Accessor, Context Resolution Point, connection-scoping, and least-privilege enforcement this decision composes with rather than duplicates); `06-compliance-and-data-residency-design.md` §3.4, §8.2 (the Region Boundary Check this decision's writes compose with, and the held-state precedent this decision's own approval gate reuses in shape, never in substance). ADR-021 through ADR-038 remain Provisional and are not assumed settled; this decision depends on none of their approval status beyond the mechanisms they already fix.
- **Verified vs. reasoned:** Reasoned throughout. No time-sensitive ecosystem, product, or vendor claim is made; every finding derives from the cited specification and the cited, already-written upstream design documents' own content.
- **Question this answers:** Given that a built application's identity (`application_id`, `tenant_id`) may never be rebound for the purpose of promotion, and given that C-23 simultaneously requires each of an application's environments to be strictly isolated per tenant and per application, what concrete structure carries a "stage" such that identity stays exactly as fixed while isolation is structural rather than assumed — and, given that structure, what is the smallest promotion mechanism that moves an application forward through its stages without wiring into, or duplicating, the platform's own CI/CD or environment topology?
- **Criteria applied, and how each resolved:**
  1. *Sibling schemas of one unchanging application identity versus a separate `platform.applications` row per stage.* Decisive for sibling schemas — a separate row per stage would mean three distinct `application_id` values for what must remain one application, directly violating the constraint `01-application-runtime-and-lifecycle-design.md` §7.4 places on this document by name; the sibling-schema design keeps identity exactly as fixed while still giving each stage a schema boundary as strong as the one already proven for tenant and application isolation.
  2. *Promoting configuration only versus promoting configuration and entity data together.* Decisive for configuration-only — promoting entity data would mean a promotion could overwrite an already-populated destination stage's own records (most consequentially, Production's), which is both a data-safety risk C-23's isolation language does not ask this document to accept and a violation of the isolation it does ask for: each stage's data remaining genuinely its own, accumulated independently, is what "strictly separate" means at the level of content, not only of schema.
  3. *Sequential, one-directional promotion versus arbitrary stage-to-stage promotion.* Decisive for sequential — an arbitrary-order promotion would let Production be reached without ever passing through Testing, defeating the reason Testing exists at all; no specification text requires this ordering, so it is recorded here as this document's own reasoned choice, explicitly not derived from, and not binding upon, the platform's own analogous ordering.
  4. *A dedicated, builder-facing approval gate at the point of promotion versus reusing or wiring into the platform's own Production Deploy Gate or the residency approval gate.* Decisive for a dedicated gate — the ticket instructing this document explicitly forbids wiring a builder's own promotion into the platform's pipeline (§8), and the residency approval gate (`06-compliance-and-data-residency-design.md` §8.2) protects a categorically different obligation; reusing either would conflate two distinct governance concerns under one mechanism, which composing-with-what-exists does not require here because neither existing gate was built to protect this concern.
- **Context:** This is the second document of the Operation, Reach & Distribution layer, and the first to design a mechanism that must actively disambiguate its own vocabulary from two adjacent, already-written uses of near-identical terms (§3) before any substantive design could proceed. It is also the first document to add a structure to `02-platform-data-model-design.md`'s schema hierarchy since ADR-037, following the identical constrain-and-hand-over discipline that decision and its two predecessors (`administrative_scope_grants`, `extension_registrations`, `external_system_connections`) already established, rather than defining a table in a schema this document does not own.
- **Decision:** (1) `application_id` and `tenant_id` never change across an application's Development, Testing, and Production stages; what changes per stage is which sibling per-application schema currently holds that stage's own catalog rows and entity data (§4.3). (2) Development is exactly the schema construction already produces, unaltered; Testing and Production are additional schemas materialized on first promotion into each, registered in a new per-tenant structure this document constrains and hands to `02-platform-data-model-design.md` to define (§4.4, §5.1–§5.2). (3) A promotion moves only configuration — constructs, bindings, and entity/schema/field/relationship definitions — never entity instance data, as one atomic, Gateway-mediated read-then-write between sibling schemas of one tenant (§6.1, §6.3). (4) Promotion is strictly sequential and one-directional, Development → Testing → Production, with no skip and no reverse-promotion mechanism of this document's own (§6.2). (5) Promotion to Production is held, releasable only by a recorded approval, wherever the application's own configuration requires it — a builder-configured, optional condition, never a platform-mandated default (§7). (6) This mechanism shares no code path, gate, or evidence record with the platform's own CI/CD pipeline or environment topology (§8). (7) A stage promotion is not a cross-region data movement under the residency mechanism, because it moves no classified content and because every stage of one application shares exactly one `region_of_record` (§9). (8) One new audit event type, `stage-promotion`, is added, landing under Authorization and grant events as the closest fit (§10).
- **Alternatives considered:** *A separate `platform.applications` row per stage* — rejected under criterion 1; it rebinds identity, which this document's own upstream dependency forbids. *Promoting entity data alongside configuration* — rejected under criterion 2; it risks overwriting a stage's own accumulated records and undermines the isolation C-23 requires. *Arbitrary-order or skip-permitted promotion* — rejected under criterion 3; it defeats Testing's own purpose. *Wiring the Production approval gate into the platform's own Production Deploy Gate, or into the residency approval gate* — rejected under criterion 4; both conflate a builder-facing governance choice with a distinct, platform-facing or residency-facing mechanism this document is expressly instructed not to entangle it with. *A stage column on a single shared schema, distinguishing rows by stage rather than by schema boundary* — rejected under §4.2's own reasoning; it makes isolation an application-layer predicate rather than a structural guarantee, repeating the exact failure mode already rejected for tenant isolation.
- **Consequences:** Binds `02-platform-data-model-design.md` to add the per-tenant stage-schema mapping structure and the `application_metadata` stage extension this document constrains (§4.4), without this decision predetermining that document's own column types, constraints, or physical shape. Binds `03-builder-facing-version-control-design.md` (C-21, not yet written) to define its own notion of "a version" independently of, and without narrowing, what this document defines a promotion to move (§6.1); this decision does not anticipate or design that document's mechanism. Binds `04-publishing-and-delivery-design.md` (C-10, not yet written) to the default this document fixes — an end-user request resolves to the Production stage — without this decision designing publishing's own reachability model (§5.4). Binds `05-meta-operations/04-human-in-the-loop-protocol.md` to design the routing, recording, and resolution mechanics for the approval this document's held state requires (§7.3). Adds no obligation to `04-devops-and-cloud-infra/01-environment-and-config-spec.md` or `04-devops-and-cloud-infra/02-ci-cd-pipeline-spec.md` — neither is realized, extended, or re-decided by this document (§8). Adds no obligation to `08-audit-and-traceability-design.md`'s record shape, storage, or tamper-evidence mechanism — only the one new `event_type` value within its existing model (§10).

## 13. Precedence and Ownership Boundaries

When a rule in this document meets any other consideration, it is resolved by the fixed precedence of `02-governance-and-security/01-system-invariants.md` §6, which this document inherits rather than restates.

- **The charter prevails**, and the specification this document realizes prevails over this design wherever the two appear to conflict; this document is corrected to match the specification, never the reverse.
- **The identity anchors are a floor, never spent.** No mechanism in this document implies, requires, or would be simplified by rebinding an application's `application_id` or `tenant_id` for the purpose of promotion; every mechanism above is designed to carry both, unchanged, across every stage.
- **Tenant isolation is a floor, never spent.** No stage boundary in this document ever becomes a second tenant-scoping path, and no promotion mechanism ever crosses a tenant boundary; every read and write this document's mechanism performs clears the identical checks any other caller clears.
- **The platform/builder-facing boundary is a floor, never spent.** No mechanism in this document ever wires a builder's own promotion into the platform's own pipeline gates or environment tiers, and no platform-layer promotion ever advances a builder's application through this document's stages.
- **A breach overrides apparent gain.** An outcome this document's mechanisms would need to relax to permit — a stage skip, a promotion that overwrites another stage's own data, a Production promotion released without a recorded approval where one was required, or a promotion bypassing the Entity Access Gateway or the Region Boundary Check — is refused regardless of the value it appears to create.

This document owns the two vocabulary disambiguations (§3), the stage model and its resolution of the identity/isolation tension (§4–§5), the promotion mechanism and its gating rules (§6), and the human-approval gate's trigger and held state (§7). It does not own, and none of the following documents' authority is diminished by this one:

## 14. Binding Rules

These rules hold for every application, stage, and promotion subject to this model and are subordinate to the charter.

- **This document's stages are never confused with the platform's own tiers, and "stage" in this document never means a build/configure/publish/operate lifecycle transition.** Every occurrence of Development, Testing, or Production in this document names one of this application's own three environments; the platform's own tiers are named explicitly wherever they are meant (§3).
- **An application's `application_id` and `tenant_id` never change across its Development, Testing, and Production stages.** What changes per stage is which sibling per-application schema currently holds that stage's own content, never the identity itself (§4.1, §4.3).
- **Development is exactly the schema construction already produces; no second construction mechanism exists for it.** Every construction and configuration action targets Development, always (§5.1).
- **Testing and Production are structurally identical sibling schemas, materialized on first promotion, registered in a structure this document constrains and `02-platform-data-model-design.md` defines.** No table is defined by this document in a schema it does not own (§4.4, §5.2).
- **Stage isolation composes with tenant isolation and never becomes a second scoping path.** Every stage's connection-scoping and self-verification is the identical mechanism already fixed for any application schema, extended by one further comparison, never a parallel one (§5.3, §5.4).
- **Every runtime request resolves to exactly one stage, once, at the same Context Resolution Point that already resolves tenant and application context.** No downstream call is parameterized by a stage a caller could supply independently of that resolution (§5.4).
- **A promotion moves configuration only, never entity instance data.** Each stage's own records are accumulated independently, from the moment its schema exists (§5.2, §6.1).
- **Promotion is sequential and one-directional — Development, then Testing, then Production — and no stage is ever skipped.** This document designs no demotion or reverse-promotion mechanism of its own (§6.2).
- **A promotion to Production is held, never released except by a recorded approval, wherever the application's own configuration requires it.** No timeout, retry, or default releases a held promotion (§7.2); routing that approval is `05-meta-operations/04-human-in-the-loop-protocol.md`'s (§7.3).
- **This mechanism shares no code path, gate, or evidence record with the platform's own CI/CD pipeline or environment topology.** A builder's promotion is never a platform release, and a platform release never advances a builder's application through this document's stages (§8).
- **A stage promotion is not a cross-region data movement, because it moves no classified content and every stage of one application shares exactly one region-of-record — stated as a finding bounded to the region topology this design library defines today, never as a claim about a topology not yet designed (§9).**
- **Every control this document fixes produces the evidence §10 names**, landing under Authorization and grant events as the closest available category, stated honestly rather than forced into an invented one.
- **Everything remains domain-neutral and platform-level.** No stage, promotion rule, or gate in this document encodes the characteristics of any single domain; all remain valid for any software built on the platform.
- **This document records exactly one ADR.** ADR-039 (§11) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, boundary, or invariant the cited specification and cited upstream design documents already fix.
