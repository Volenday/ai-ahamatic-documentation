# Application Runtime and Lifecycle Design — AI ahaMatic

This document opens the Operation, Reach & Distribution layer by realizing `01-business-and-ux/03-platform-capability-model.md`'s application-operation and lifecycle-continuity rows (C-07, C-08) as concrete mechanism: the runtime model on which every built application executes, and the mechanism that carries a built application from build through configure, publish, and operate as one governed flow. It answers **how**, never re-deciding what the specification and the already-fixed design library have already settled.

**⚠ The deployment shape is fixed and is not reopened here.** `03-architecture-realization-design.md` §7.1 fixes that "per product" means the platform as a whole — one platform-core deployable serves every tenant and every application, horizontally scaled by identical, stateless replicas, with tenant and application context resolved per request via the registry. §7.3 further fixes that the web presentation tier serves both the builder UI and the built-application web runtime as its own container image. This document's subject is what executes **inside** that fixed shape — the runtime model and the continuity mechanism — never a second deployment topology, a per-tenant or per-application process, or a weighing of isolation strategies already closed by that document.

This is a Design-phase artifact realizing, in addition to the PRD's C-07 and C-08 rows and the run-time portions of `01-business-and-ux/05-user-journeys.md`: `01-application-construction-design.md` §3–§4, §6–§7 (the construct/binding vocabulary this runtime executes, and the identity/context every construction and configuration action already runs inside); `03-architecture-realization-design.md` §3–§5, §7 (the module boundary, the dependency-direction mechanism, the three-layer separation, and the fixed deployment shape this runtime operates within); `02-data-model-and-entity-design.md` §3.2–§3.3, §3.5, §4.1, §4.4, §9.6–§9.7 (the Entity Access Gateway, now four checks, and the still-open Surface-to-entity-content binding question this document inherits rather than resolves); `02-tenant-isolation-and-access-control-design.md` §3, §5–§6 and `03-authentication-and-identity-design.md` (the Authentication Gate and Context Resolution Point this runtime is a consumer of, never a second path); `06-compliance-and-data-residency-design.md` §3.3–§3.4 (the Region Boundary Check, which binds a running application's own requests exactly as any other caller's); `04-workflow-and-process-automation-design.md` §3.2 (the four boundary-crossing step kinds a process crosses into at runtime); `05-api-contract-design.md` §2, §4 (the built-application contract tier a running application exposes); `02-platform-data-model-design.md` §3 (the schema hierarchy, per `BACKLOG.md` §1i's standing rule); and `08-audit-and-traceability-design.md` §4.2–§4.3 (the consolidated audit event model this document composes with).

**Verified versus reasoned (`PROCESS.md` §12.3).** Every finding in this document is **reasoned** — from the cited specification and the cited, already-written upstream design documents. No time-sensitive ecosystem, product, or vendor claim is made anywhere in this document.

## 1. Purpose and Reading Order

This document answers four questions:

- **How does a stored configuration become a running application at request time** — what resolves a request to an application, what materializes a Surface, what executes a Command, and how the runtime stays generic across every application it serves (§3–§5).
- **How does the runtime compose with every request-time mechanism already fixed above it**, never opening a second identity, scoping, or data-access path (§3, §6).
- **What makes build → configure → publish → operate one governed flow rather than four stages a builder stitches together** — what carries identity and version across the transitions, what survives each, and where a transition can fail without stranding an application (§7).
- **Which run-time and build-time journeys this mechanism must preserve, and what in this design preserves them** (§8).

It is structured as a pyramid: first the runtime model — request resolution, Surface materialization, and Command invocation, each composing with an already-fixed mechanism (§3–§5); then the domain-neutrality argument that keeps the runtime generic (§6); then lifecycle continuity as a mechanism, not a narrative (§7); then the journeys this design preserves (§8); then the three bidirectional boundaries against C-27, C-06, and C-09 (§9); then the evidence this mechanism produces (§10); then the design decision this document records (§11); then its boundaries, precedence, and binding rules (§12–§14).

## 3. Request Resolution to a Running Application

### 3.1 Entry Points Converge on One Component, Never a Second Path

A run-time request reaches a built application through one of several channels — the web presentation tier's built-application web runtime (`03-architecture-realization-design.md` §7.3), a direct consumer of the generated per-application contract (C-12, C-20 once designed), or the platform's own agent-facing MCP surface where the built-application tier is reached that way. Every channel converges on the same destination: the Operation component (`components/operation`, `03-architecture-realization-design.md` §3.1), which holds "the runtime execution of built software" and no other component's responsibility. This document designs what happens once a request reaches that component; it does not design, and does not anticipate, any channel-specific mechanism — each remains owned where the map already places it (§2).

### 3.2 No Second Identity or Scoping Path

Every request — regardless of channel or of whether its ultimate actor is a builder testing an application or an end user reaching one — passes the Authentication Gate (`03-authentication-and-identity-design.md` §5.2) and then the Context Resolution Point (`02-tenant-isolation-and-access-control-design.md` §4.1) exactly as any other request against the platform. The Operation component runs strictly downstream of both: it receives the frozen Authenticated Actor Identity and Resolved Request Context already produced for the request, and never authenticates an actor or resolves a tenant or application a second time. For an end-user actor, `application_id` resolves to exactly the one application the request's own contract path names (`05-api-contract-design.md` §2) — never a value the runtime negotiates, widens, or infers independently of what the Context Resolution Point already resolved.

The Region Boundary Check (`06-compliance-and-data-residency-design.md` §3.4) runs inline at connection acquisition exactly as for any other request. **Operating a running application confers no exemption from it:** a built application's own request is bound by the identical Resolved Residency Obligation as any platform-primitive request, refused or held exactly as that mechanism already fixes.

### 3.3 Resolving the Targeted Construct

The specific construct a request targets — a Surface or a Command — and the action class it invokes (View or Invoke) are resolved from the generated built-application contract operation the request calls (`05-api-contract-design.md` §2, §3.2, §4), by opaque reference. The runtime never infers a construct or an action class independently of what the generated contract already names for that operation; there is no second mapping from request to construct that this document maintains alongside the one the contract-generation mechanism already produces.

### 3.4 No Per-Application Runtime Instance

Nothing in this section, or in §4–§5 below, spins up a per-tenant or per-application process, worker, or long-lived in-memory instance. Materializing a Surface and invoking a Command are ordinary, request-scoped execution inside whichever stateless platform-core replica happens to serve the request (`03-architecture-realization-design.md` §7.1–§7.2) — the same replica that, on its very next request, may serve a different tenant's different application entirely. A running application's own reachability never depends on which replica served a prior request, and this document introduces no mechanism that would make it so.

## 4. Materializing a Surface

A Surface is realized, per `02-data-model-and-entity-design.md` §3.3, as an `entity_catalog` row flagged as build-surface content, related to other constructs by `relationship_catalog` rows of the three binding kinds. **Materializing a Surface is resolving, at request time, the current state of that construct's own structure and content** — nothing this document defines as a second, parallel representation of it.

### 4.1 The Sequence

1. **Access check.** The Resolved Request Context's own role must hold a View (or, for a submission, an Invoke) access binding on the targeted Surface — enforced by `02-tenant-isolation-and-access-control-design.md` §6's least-privilege enforcement mechanism, exactly as for any other role-gated action. An actor lacking the binding is refused before any content is read, and the refusal is captured exactly as any other INV-02 check (§10).
2. **Structural resolution.** The Surface Materializer reads every Structural binding attached to the Surface — which child constructs compose it, and in what arrangement — through the Entity Access Gateway (`02-data-model-and-entity-design.md` §4.1), because a binding is a `relationship_catalog` row and the Gateway is the sole path through which any component reads a builder-defined entity's catalog rows. This is an ordinary Gateway-mediated catalog read, never a second read path this document opens for construct configuration specifically.
3. **Behavioral resolution.** Every Behavioral binding attached to the Surface, and to each child construct the structural resolution surfaced, is evaluated through the same Gateway read — its condition-and-parameter content determines what is actually presented (for example, whether a child construct renders at all). The runtime supplies no interpretation of what a condition *means*; it evaluates the condition exactly as `01-application-construction-design.md` §4.1 already defines a behavioral binding's own generic shape, and dispatches on the result.
4. **Content resolution, where the Surface presents entity content.** Where the (still-open, §2) binding between the Surface and the entity data it presents resolves to specific records, those records are read through the Entity Access Gateway's ordinary instance-read path, clearing whichever of the Gateway's four checks the read implicates in fixed order: the Validation Engine's referential-correctness inspection of what is being returned; the Consent and Minimization Check, where the content is personal or sensitive data; classification-tier and data-governance-category resolution; and — because the invoking identity is, in this case, precisely a resolved end-user role reaching entity content through a construct — the fourth, End-User Record-Reach Check (`02-data-model-and-entity-design.md` §4.4), narrowing which records are actually returned to whatever a record-level Behavioral binding permits.

**This document is the first to exercise the fourth check in the register it was built for.** `02-data-model-and-entity-design.md` §4.4 fixes the check's precondition as "a resolved end-user role reaching content through a construct" — exactly the shape of every Surface materialization an end-user actor triggers. This document does not redesign the check; it is the runtime moment at which that precondition is, structurally, always satisfied for an end-user reach and never satisfied for a platform-internal or automated-step reach, exactly as `02-data-model-and-entity-design.md` §9.7 already resolves for a process-automated Gateway call.

### 4.2 No Fast Path for "Just a Render"

The Surface Materializer never bypasses the Gateway because the caller is a runtime render rather than an administrative or construction-time actor. Every read of catalog rows or instance data this section performs is a Gateway call, on identical terms to any other caller — the same "engine-originated confers no exemption" discipline `04-workflow-and-process-automation-design.md` §5.2, §6 already states for the workflow engine, applied here because a runtime is, if anything, an even stronger temptation to introduce a second, "trusted," unmediated read path for the sake of render latency. No such path exists in this design.

### 4.3 A Surface With No Bound Entity Content

Where a Surface presents no entity content at all — purely structural or static content, composed only of other constructs and their own presentation — step 4 above has nothing to resolve, and the fourth check's own precondition (reaching *content* through a construct) does not fire, because there is no content to narrow. This is not a gap; it is the same conditional-applicability discipline the Consent and Minimization Check and the fourth check already carry for themselves (`02-data-model-and-entity-design.md` §4.1, §4.4, §9.7), applied here to a Surface that, by its own configuration, has nothing for the check to bound.

## 5. Invoking a Command — the Construct Invocation Point

Every Invoke — whether against a Command, or a Surface submitted by an end user (`01-application-construction-design.md` §4.2.4: Invoke covers "the ability to trigger a construct's own behavior — to submit a Surface, or to execute a Command") — passes through one generic mechanism, the **Construct Invocation Point**. This document does not design two invocation mechanisms for two construct kinds; a Surface submission and a Command execution are the same invocation, reached from two different constructs.

### 5.1 The Sequence

1. **Access check.** Identical to §4.1's step 1, evaluated against the Invoke class rather than View.
2. **Behavioral resolution.** Every Behavioral binding attached to the invoked construct is evaluated through the Entity Access Gateway exactly as in §4.1's step 3. Where the condition does not hold, the invocation is refused before any further effect occurs — deny-by-default, the specification's own posture applied here at the point an invocation's own gating condition is checked.
3. **Effect dispatch.** Where the condition holds, the Construct Invocation Point dispatches the construct's own configured effect to whichever mechanism the effect's own parameter content designates, never a fifth mechanism this document invents alongside the four already fixed elsewhere:
   - An effect on builder-defined entity data is dispatched as an ordinary Gateway write (`02-data-model-and-entity-design.md` §4.2), clearing the identical four-check gauntlet §4.1's step 4 already describes for a read, now applied to a write — including the fourth check, narrowing which records the invocation may affect, not only which it may read.
   - Where the invoked construct is the one an already-authored process definition's Action step references (`04-workflow-and-process-automation-design.md` §3.2), the process engine is simply one more actor reaching this same Invoke path — the Command's own invocation mechanism is unchanged by who or what triggers it, exactly as that document's own §6 already fixes for an automated rule step's reach into the Entity Access Gateway.
   - Where the construct's own configured effect reaches an extension, it is dispatched through the Extension Invocation Point (`06-integration-and-extensibility-design.md` §6, §9) as an ordinary caller — "an extension is a caller, never an exemption," and the Construct Invocation Point adds no exemption of its own on the way in.
   - Where the construct's own configured effect reaches an external system, it is dispatched through the Connector Resolver (`07-cross-system-data-layer-design.md` §3.2, §4) as an ordinary caller, on the identical composing discipline.

### 5.2 What This Section Does Not Decide

The shape of a Behavioral binding's own condition-and-parameter content, and which of the four composed mechanisms above a given construct's own configuration designates, are `01-application-construction-design.md`'s configuration model, consumed here and never defined here. This document is the dispatcher that routes an already-configured invocation to whichever mechanism the construct's own binding already names; it is not a fifth effect mechanism, and it does not decide, on a builder's behalf, what a Command should do.

## 6. Domain-Neutrality Through the Runtime Mechanism

`01-application-construction-design.md` §5 already makes the structural argument that no domain assumption can enter through the build surface, because the build surface has nothing for one to enter as — a builder's every choice is confined to *which* constructs exist and *how* they are bound, never *what kind of thing* a construct or binding can be. This document does not restate that argument; it states what the runtime specifically does to keep it true one layer further downstream, where a construct's own configuration is finally executed rather than merely stored.

- **The runtime operates only over the closed vocabulary, never over what a construct or binding is "for."** Surface materialization (§4) and Command invocation (§5) each dispatch on the fixed, generic shapes `01-application-construction-design.md` §4.1–§4.2 already fix — a construct's kind, a binding's kind, a condition-and-parameter shape, an action class — and on nothing else. There is no branch anywhere in §4–§5 keyed to what a builder's own subject matter *means*; every dispatch decision is a property of the construct/binding's own generic shape, never of its content.
- **Every effect this runtime dispatches lands in an already-generic mechanism.** The Entity Access Gateway, the process engine, the Extension Invocation Point, and the Connector Resolver are each themselves domain-neutral by the same argument their own owning documents already make; the Construct Invocation Point (§5) adds no domain-specific routing logic of its own — it routes on the construct's own generic configuration, never on an inference about what that configuration is trying to accomplish.
- **The runtime is, by construction, identical code for every application it serves.** Because §3.4 already establishes that no per-application instance exists, and because §4–§5 dispatch only on generic construct/binding shape, the same runtime code path materializes a Surface and invokes a Command for every tenant's every application — the difference between one built application and another is entirely a difference in the catalog rows the Gateway returns for a given `application_id`, never a difference in the runtime code that reads them.

## 7. Lifecycle Continuity (C-08) — the Mechanism

C-08 is "the means to move a built application end to end — build, configure, publish, operate — as one continuous, governed flow" (`01-business-and-ux/02-prd.md` §4). This section designs what makes that true structurally, not a restatement of the four stages in order.

### 7.1 The Boundary, Stated Bidirectionally

**This document owns continuity across the four transitions; it does not own the publishing act itself.** `04-publishing-and-delivery-design.md` (not yet written; `implementation-document-map.md`, Layer 4) owns what publishing does — the reachability model, audience and access scoping, and the failure and empty-state delivery paths for the *publish* stage. Stated in reverse: whatever that document designs governs **reach** — who or what may discover and access a published application, and through which channel — it does not alter, gate, or re-materialize the runtime execution §3–§5 already make available to any already-authorized actor from the moment an application's configuration exists. Publishing extends reach to reach classes an application did not previously have; it does not create a second runtime, and this document's mechanism does not wait for a publish action to begin operating an application for an actor already holding a grant to reach it.

### 7.2 The Identity That Survives Every Transition

Three facts, fixed once and never reassigned, are what make the four stages one flow rather than four independently-scoped ones:

| Anchor | Fixed At | Carried Through |
|---|---|---|
| `application_id` | Construction (`01-application-construction-design.md` §3) | Every configuration action, every runtime request (§3.2–§3.3), and whatever `04-publishing-and-delivery-design.md` eventually designs for the publish stage — none mints a second identifier for the same application. |
| `tenant_id` | Construction, resolved from the acting identity's own context, never caller-supplied (`01-application-construction-design.md` §3) | Identical to `application_id` — never re-resolved or re-bound at any later stage. |
| `schema_name` / the per-application schema | Construction, alongside the `platform.applications` row (`02-platform-data-model-design.md` §3.3) | The same schema holds every construct and binding a builder configures, and every read this document's runtime performs — there is no export step between "configured" and "running," because both stages read and write the identical catalog rows in the identical schema. |

**This is why continuity is structural, not procedural.** Construction, configuration, and operation do not exchange a snapshot, an export, or a compiled artifact between stages — `01-application-construction-design.md` §3–§4 writes catalog rows into the schema `02-platform-data-model-design.md` §3.3 fixes at construction, and §3–§5 above reads the identical rows, in the identical schema, through the identical Entity Access Gateway. There is no hand-off step at which configuration could drift from what the runtime executes, because there is only ever one stored representation of an application's own configuration, consumed by every stage identically.

### 7.3 Where "Operate" Begins, Concretely

**Operation begins the instant configuration exists; it is not a fifth action a builder separately performs.** `01-application-construction-design.md` §3's own empty-state discipline already establishes that a newly constructed application exists before any construct is configured, and that each configuration action is separate and optional. The moment a Surface or Command with a View or Invoke access binding exists, it is already reachable by a runtime request from any actor the binding's own role already covers (§4.1, §5.1) — subject only to whatever `04-publishing-and-delivery-design.md` eventually gates for reach *beyond* that already-granted population. There is no explicit "start operating" or "deploy" action in this design for the runtime to wait on; the boundary between "configured" and "running" is not a boundary this mechanism crosses, because there is none to cross.

### 7.4 What Version Control and Environment Promotion Anchor To

`03-builder-facing-version-control-design.md` (C-21) and `02-builder-facing-environment-management-design.md` (C-23) each depend on this document (`implementation-document-map.md`, Layer 4); this document does not anticipate, design, or narrow either. What this document fixes, for both to build on: whatever either eventually defines as "a version" or "a stage" of a built application must anchor to the same `application_id` §7.2 fixes — never a rebinding of the application to a new identity for the purpose of versioning or promotion. This document states the anchor those two mechanisms must respect; it does not design what a version or a stage concretely is.

### 7.5 Where a Transition Can Fail Without Stranding an Application

| Transition | Failure Mode | Why It Does Not Strand the Application |
|---|---|---|
| Construction | The construction action fails partway. | `01-application-construction-design.md` §3 fixes construction as producing exactly one row and one schema, or nothing — there is no partial-construction state; a failed attempt leaves no application to be stranded. |
| Configuration | A structural, behavioral, or access-binding write fails. | Every configuration write is a Gateway-mediated write (`02-data-model-and-entity-design.md` §4.2), all-or-nothing per write; a failed write leaves every already-committed construct and binding exactly as it was, per the identical deny-by-default discipline that document already fixes. |
| Operate (a single request) | A runtime request fails mid-execution — a refused check, a downstream effect's own failure, or a crashed replica. | No request holds state the application depends on beyond that request's own outcome; the next request is served by any stateless replica (§3.4), resolving the identical `application_id`/`schema_name` through the registry exactly as before. A failed request never leaves the application's own stored configuration or data in a different state than its last successfully committed write. |
| Publish | A publish attempt fails or is withdrawn. | Not this document's mechanism (§7.1) — but the constraint this document places on `04-publishing-and-delivery-design.md` is that a failed or withdrawn publish action must leave the application's own configuration, data, and existing reach exactly as before the attempt; publishing exposes reach to what §3–§5 already execute, and a failure to expose it further is never a regression of what was already reachable. |

**The stateless deployment shape is what makes the operate-stage row true, and this document introduces no competing mechanism.** `03-architecture-realization-design.md` §7.1–§7.2 already fixes that no replica is tenant- or application-specific and that onboarding an application is a data-layer event, never a deployment event; this document relies on that already-fixed property rather than designing a second, per-application recovery or state-preservation mechanism to achieve the same result.

## 8. Journeys Preserved

### 8.1 The Build-Time "Operation and Observation" Journey

`01-business-and-ux/05-user-journeys.md` §3 names "Operation and observation" as the operator's own experience of "running the built software, carrying it through its lifecycle as one continuous governed flow, and observing its real-world health and behavior" (C-07, C-08, C-09). §3–§7 above are the mechanism that makes the C-07/C-08 portion of that experience hold: an operator's own requests against a running application clear the identical runtime path any other actor's do (§3–§5), and the continuity §7 fixes is what lets the operator experience "one flow" rather than four disconnected mechanisms. The C-09 portion — observing health and behavior — is preserved only in the sense that this document's own mechanism is a source of the signals `04-observability-and-monitoring-design.md` will measure (§9.3); this document does not itself preserve an observability experience it does not design.

### 8.2 Run-Time Journeys (`01-business-and-ux/05-user-journeys.md` §4)

| Run-Time Journey | What Preserves It |
|---|---|
| Authenticated use | §3.2's composition with the Authentication Gate and Context Resolution Point recognizes the actor's identity before any handler runs; §4.1/§5.1's access checks enforce exactly the builder-defined access the actor was granted, never more. |
| Public use | §3's Authentication Gate composition recognizes an unauthenticated actor as `04-auth-and-identity-spec.md` §3 already fixes — establishing no identity at all where the builder has exposed a Surface without requiring one; the moment such a request reaches a governed action, §4.1/§5.1's ordinary access checks apply identically. |
| End-user administration | An end-user administrator's own reach is bounded exactly as any other end-user role's — by the access bindings the builder configured (§4.1, §5.1) — never by an authority this document grants beyond the built application, per `05-user-journeys.md` §4.1's own rule that such authority never reaches the tenant or the platform. |

**Every boundary of §4.1 there holds by construction.** A run-time journey is confined to one built application within one tenant because §3.2's Context Resolution Point never resolves more than one; no run-time journey reaches a platform primitive because §4–§5's mechanisms dispatch only into already-generic, platform-owned mechanisms, never into a construction or configuration action (§9.2); and the permissions an end user encounters are exactly what the builder configured, because §4.1/§5.1 read no access rule this document invents.

### 8.3 Critical Paths and Non-Happy-Path States

- **G-1 (isolation) and G-2 (identity/access enforced first)** hold across every runtime request because §3.2 composes with, never bypasses, the mechanisms that already make both true; a running application confers no exemption (§3.2).
- **G-4 (regional obligations)** holds because §3.2's Region Boundary Check composition applies identically to a running application's own requests.
- **G-5 (reversible operation and recovery)** is the property §7.5 states row by row: no transition this document designs leaves an application in a state from which it cannot recover, and the operate-stage row rests on the already-fixed stateless deployment shape rather than a new mechanism.
- **Empty states (`05-user-journeys.md` §7.1).** "A newly constructed application exists before any data is modeled or any end user is admitted" and its sibling empty states hold directly from §7.3: an application with no construct configured yet has no operation for the generated contract to expose, and the runtime remains coherent — there is nothing to materialize or invoke, and nothing in §3–§5 requires there to be.
- **Error states (§7.2 there).** Denied action and isolation refusal are exactly the INV-02 and INV-01 refusals §3.2, §4.1, and §5.1 already compose with; residency refusal is exactly the Region Boundary Check composition of §3.2. This document adds no new refusal shape of its own.
- **Failure and recovery states (§7.3 there).** "Contained fault" and "escalation" are the mechanisms `05-meta-operations/07-self-correction-and-fallback-protocol.md` owns in full; this document's own contribution is that a runtime fault never leaves an application's stored configuration or data inconsistent (§7.5), which is the precondition that protocol's own containment depends on for this layer.

## 9. Boundaries Against Three Adjacent Capabilities

### 9.1 Against C-27 — Data Administration (`03-data-administration-design.md`)

C-27 operates before any application exists, serving a builder's own entities through a generic administrative interface derived automatically from entity definitions — its own interface excludes every construct-flagged `entity_catalog` row by construction (`03-data-administration-design.md` §3.3) and so never invokes a Surface or a Command at all. This document's runtime never derives from, substitutes for, or is reachable through C-27's own derivation mechanism; and C-27's derivation never depends on, and is never exposed through, this document's runtime. Neither absorbs the other: C-27 presumes no application has been configured; this document presumes one has been, and is running.

### 9.2 Against C-06 — Application Configuration (`01-application-construction-design.md`)

That document configures — it brings a construct or a binding into existence, or changes one. This document runs — it reads an already-configured construct and dispatches its already-configured effect. Stated bidirectionally: no runtime request this document designs performs a construction or configuration action as a side effect of servicing it (§3–§5 read and dispatch; they never write a new construct, binding, or application row), and no construction or configuration action `01-application-construction-design.md` §3–§4 designs itself executes a construct — it only brings one into being, ready for this document's runtime to later execute.

### 9.3 Against C-09 — Observability (`04-observability-and-monitoring-design.md`, not yet written)

That document, once written, observes the real-world health and behavior of the platform and built software; this document runs it. This document's mechanism — every request §3 resolves, every check §4–§5 clear or refuse, every audit event §10 composes with — is a source of the signals that document will measure, alert on, and feed to self-correction; this document does not itself define what is measured, what threshold triggers an alert, or what signal mandates escalation. Stated in reverse: `04-observability-and-monitoring-design.md` does not redesign, relocate, or duplicate any mechanism this document fixes — it instruments and measures what already exists here, never a second runtime path of its own.

## 11. Design Decision Records

### 11.1 ADR-038 — The Construct Invocation Point and the Structural-Continuity Lifecycle Mechanism

- **Status:** Approved (`DECISIONS.md` D-47, 2026-08-18).
- **Cost to reverse:** **High** (`PROCESS.md` §12.1). Every construct any builder has configured is executed through the Construct Invocation Point and the Surface Materializer this decision fixes; reversing the single-dispatcher shape for a per-construct-kind or per-effect-mechanism dispatch pattern requires re-deriving every already-running application's own execution path, not merely changing a check or a policy going forward. Not Very high or Brutal: no stored data moves, and no already-committed catalog row or instance changes shape — the reversal cost is entirely in re-deriving runtime dispatch logic, not in migrating stored content.
- **Upstream decisions assumed:** `03-architecture-realization-design.md` §3–§5, §7 (the module boundary, the dependency-direction mechanism, and the fixed deployment shape this runtime executes inside and does not reopen); `01-application-construction-design.md` §4.1–§4.2, §5 (the closed construct/binding vocabulary and its own domain-neutrality argument, which §6 above extends one layer downstream); `02-data-model-and-entity-design.md` §4.1, §4.4 (the Entity Access Gateway, including its fourth check, this document's every read and write composes with); `02-tenant-isolation-and-access-control-design.md` §4, §6 and `03-authentication-and-identity-design.md` §5.2 (the Context Resolution Point and Authentication Gate this runtime consumes and never re-establishes); `06-compliance-and-data-residency-design.md` §3.4 (the Region Boundary Check this runtime's requests compose with); `04-workflow-and-process-automation-design.md` §3.2, §5.2, §6 (the Action-step composition and the "no engine-originated exemption" discipline this decision extends to the runtime generally); `06-integration-and-extensibility-design.md` §6, §9 and `07-cross-system-data-layer-design.md` §3.2, §4 (the Extension Invocation Point and Connector Resolver this decision's effect dispatch composes with); `05-api-contract-design.md` §2–§4 (the generated built-application contract this runtime's request resolution consumes). ADR-021 through ADR-037 remain Provisional and are not assumed settled; this decision depends on none of their approval status beyond the mechanisms they already fix.
- **Verified vs. reasoned:** Reasoned throughout. No time-sensitive ecosystem, product, or vendor claim is made; every finding derives from the cited specification and the cited, already-written upstream design documents' own content.
- **Question this answers:** Given a fixed deployment shape with no per-application process, a closed construct/binding vocabulary already fixed elsewhere, and four independently-owned effect mechanisms (the Entity Access Gateway, the workflow engine, the Extension Invocation Point, and the Connector Resolver) that a construct's own configured behavior may need to reach, what is the smallest runtime mechanism that materializes a Surface and invokes a Command generically across every application, composes with every already-fixed request-time mechanism rather than duplicating any of them, and makes build → configure → publish → operate one governed flow rather than four independently-scoped stages?
- **Criteria applied, and how each resolved:**
  1. *A single, generic Construct Invocation Point versus a dispatch mechanism specific to each construct kind or each target effect mechanism.* Decisive for a single dispatcher — a per-kind or per-target mechanism would scatter the identical access-check-then-behavioral-resolution sequence across multiple call sites, each a separate opportunity to omit a check the single dispatcher instead runs once, in one place, for every invocation regardless of what it ultimately dispatches to.
  2. *Composing with the four already-fixed effect mechanisms versus a runtime-owned effect path for at least one of them (most plausibly, entity writes, given how frequently the runtime would use it).* Decisive for composing — introducing a runtime-specific write path for entity data would duplicate the Entity Access Gateway's own four-check gauntlet or, worse, create a second path a defect could bypass one of those checks through; this is the identical discipline `04-workflow-and-process-automation-design.md` §5.2 already applies to the workflow engine, and a runtime is, if anything, a stronger temptation to relax it than an engine is.
  3. *Lifecycle continuity as structural (shared identity and shared catalog state) versus a staged hand-off, export, or compiled-artifact mechanism between build, configure, and operate.* Decisive for structural — a hand-off mechanism would create exactly the drift risk (a builder's live configuration diverging from what an exported or compiled artifact executes) that this document's own writing rules warn against treating as a narrative rather than a mechanism; reading the identical catalog rows at every stage removes the possibility of drift by removing the second representation that could drift from the first.
  4. *Relying on the already-fixed stateless deployment shape for operate-stage recoverability versus designing a dedicated per-application state-preservation or recovery mechanism.* Decisive for reliance — `03-architecture-realization-design.md` §7 already fixes that no replica is application-specific and that onboarding is a data-layer event; a second, runtime-owned recovery mechanism would duplicate a guarantee that shape already provides for free, and would reopen a deployment-topology question this document is explicitly instructed not to reopen.
- **Context:** This is the first document of the Operation, Reach & Distribution layer, and the first to execute — rather than merely store — the construct/binding vocabulary `01-application-construction-design.md` fixed and `02-data-model-and-entity-design.md` gave physical shape to. It is also the first document to exercise the Entity Access Gateway's fourth check in the register it was built for (an end-user role reaching content through a construct, §4.1), and the document `03-builder-facing-version-control-design.md`, `02-builder-facing-environment-management-design.md`, `04-publishing-and-delivery-design.md`, `08-multi-region-distribution-design.md`, and `04-observability-and-monitoring-design.md` each depend on (`implementation-document-map.md`, Layer 4), so an unstated or drifting runtime model here would propagate into each.
- **Decision:** (1) A request resolves to a running application entirely by composing with the already-fixed Authentication Gate, Context Resolution Point, and Region Boundary Check — never a second identity, scoping, or residency mechanism (§3). (2) Surface materialization and Command invocation are two faces of one generic mechanism, the Construct Invocation Point, dispatching on a construct's own closed-vocabulary shape and never on domain content (§4–§6). (3) An invocation's effect is dispatched to exactly one of four already-fixed mechanisms — the Entity Access Gateway, the workflow engine via an Action step, the Extension Invocation Point, or the Connector Resolver — never a fifth, runtime-owned effect path (§5). (4) Lifecycle continuity is realized structurally, through three identity anchors (`application_id`, `tenant_id`, `schema_name`) that never change across stages and one stored representation of configuration that every stage reads and writes identically, never a hand-off, export, or compiled artifact between them (§7.2). (5) Operation begins the instant configuration exists, with no separate "deploy" action for the runtime to wait on (§7.3). (6) No transition this document owns can strand an application in an unrecoverable state, and the operate-stage guarantee rests on the already-fixed stateless deployment shape rather than a dedicated recovery mechanism of this document's own (§7.5). (7) No new audit event type is warranted; every consequential runtime action lands under an event type an existing mechanism already owns (§10).
- **Alternatives considered:** *A dispatch mechanism specific to each construct kind, or to each of the four target effect mechanisms* — rejected under criterion 1; it scatters one sequence across many call sites. *A runtime-owned write path for entity data, for latency or convenience* — rejected under criterion 2; it duplicates or risks bypassing the Entity Access Gateway's own gauntlet. *A staged export, snapshot, or compiled-artifact hand-off between build/configure and operate* — rejected under criterion 3; it introduces a second representation of configuration that could drift from the first, which this document's own writing rules identify as the failure mode to avoid. *A dedicated per-application recovery or state-preservation mechanism for the operate stage* — rejected under criterion 4; it duplicates a guarantee the already-fixed deployment shape already provides, and risks reopening a topology question this document may not reopen. *A new audit event type for the runtime's own dispatch decision, or for a Behavioral binding's own condition evaluating false* — rejected in §10; the first would double-record a fact its own effect mechanism already captures, and the second would begin treating a built application's own business logic as platform-level evidence.
- **Consequences:** Binds no obligation onto `01-application-construction-design.md`'s closed construct/binding vocabulary or configuration model — every read and dispatch this decision fixes consumes that model exactly as already designed. Binds no obligation onto `02-data-model-and-entity-design.md`'s Entity Access Gateway, `04-workflow-and-process-automation-design.md`'s engine-integration boundary, `06-integration-and-extensibility-design.md`'s Extension Invocation Point, or `07-cross-system-data-layer-design.md`'s Connector Resolver — each is composed with exactly as already designed, never extended or re-decided. Binds `03-builder-facing-version-control-design.md` and `02-builder-facing-environment-management-design.md` to anchor whatever they define as a version or a stage to the same `application_id` this decision fixes (§7.2, §7.4), without this decision predetermining either document's own mechanism. Binds `04-publishing-and-delivery-design.md` to a bidirectional boundary (§7.1) — it governs reach, never re-materializing the runtime this decision already makes available to an already-authorized actor. Adds no obligation to `08-audit-and-traceability-design.md`'s record shape, storage, or tamper-evidence mechanism, and adds no new `event_type` (§10). Adds no obligation to `03-architecture-realization-design.md`'s deployment shape — this decision executes inside it and does not propose reopening it.

## 14. Binding Rules

These rules hold for every request, construct, and transition subject to this model and are subordinate to the charter.

- **The deployment shape is fixed and is never reopened by this document.** No mechanism above implies, requires, or is simplified by a per-tenant or per-application process, image, or deployment unit (§3.4).
- **No component outside the already-fixed Authentication Gate, Context Resolution Point, and Region Boundary Check establishes identity, scope, or residency for a runtime request.** Every request this document's mechanism serves composes with all three; none is re-established or bypassed (§3.2).
- **Every read or write of a construct's own catalog rows or the entity data it presents passes through the Entity Access Gateway, including its fourth check where the invoking identity is a resolved end-user role reaching content through a construct.** No fast path exists for a runtime render or a runtime write (§4, §5).
- **Surface materialization and Command invocation are one generic mechanism, the Construct Invocation Point, never a mechanism specific to one construct kind.** A Surface submission and a Command execution reach the identical Invoke path (§5).
- **An invocation's effect is dispatched to exactly one of four already-fixed mechanisms — the Entity Access Gateway, the process engine, the Extension Invocation Point, or the Connector Resolver — never a fifth, runtime-owned effect path.** "Engine-originated," "extension-originated," and "connector-originated" each confer no exemption from the check any other caller clears (§5.1).
- **The runtime dispatches only on a construct's or binding's own generic, closed-vocabulary shape, never on domain content.** The same runtime code path serves every application; the difference between applications is entirely in the catalog rows the Gateway returns, never in the runtime code that reads them (§6).
- **Lifecycle continuity is structural, not procedural.** `application_id`, `tenant_id`, and `schema_name` are fixed at construction and never reassigned; every stage reads and writes the identical stored configuration, with no export, snapshot, or compiled-artifact hand-off between build, configure, and operate (§7.2).
- **Operation begins the instant configuration exists; there is no separate deploy action.** A construct with a View or Invoke access binding is reachable by any actor the binding already covers, from the moment it is configured (§7.3).
- **No transition this document owns can strand an application in an unrecoverable state.** Construction and configuration are each all-or-nothing; a runtime request's failure never leaves stored configuration or data inconsistent; the operate-stage guarantee rests on the already-fixed stateless deployment shape (§7.5).
- **This document owns continuity across the four transitions; it does not own publishing, version control, or environment promotion.** Each remains a distinct, later document's own mechanism, bound only to respect the identity anchor this document fixes (§7.1, §7.4).
- **Everything remains domain-neutral and platform-level.** No mechanism in this document encodes the characteristics of any single domain; all remain valid for any software built on the platform.
- **This document records exactly one ADR.** ADR-038 (§11) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, boundary, or invariant the cited specification and cited upstream design documents already fix.
