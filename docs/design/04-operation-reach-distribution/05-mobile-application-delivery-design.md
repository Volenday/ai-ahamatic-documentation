## 1. Purpose and Reading Order

This document answers five questions:

- **What already exists before this document, and what narrow remainder it actually designs** — because D-11 and D-25 have already answered most of what "offline mobile" could have meant (§5).
- **What mobile targets are in scope, and what is not** (§3), and **what may legitimately differ between a built application's web and mobile forms, and what may never differ** (§4).
- **What a local store and a durable write queue concretely are, verified against current evidence** — and the honest limit on what any of it can guarantee before a queued write reaches a server-side check (§6).
- **What device capability and mobile publishing require beyond structured-data offline behavior** — the Expo module set already committed, and the app-store, versioning, and update-propagation constraints a server-side publish/withdraw mechanism cannot reach (§7–§8).
- **What this document hands to, and never absorbs from, `02-platform-data-model-design.md`** — and the finding that, unlike its three most recent Layer-4 precedents, it hands over nothing at all (§9).

It is structured as a pyramid: first scope and boundary (§2–§4); then the central design problem — offline structured data and its honest limit (§5–§6); then device capability and publishing constraints specific to a mobile target (§7–§8); then the one storage question this document must settle, resolved to "none" (§9); then evidence (§10); then the design decision this document records (§11); then boundaries, precedence, and binding rules (§12–§14).

## 2. Scope and What This Document Does Not Own

This document owns: the supported mobile-target scope (§3); web/mobile parity and permitted divergence (§4); the local relational store, the fast key-value store, and the durable write queue that together realize D-25's local-persistence decision, and the honest limit on what they guarantee (§5–§6); the device-capability surface as it bears on parity (§7); the publishing, versioning, and update-propagation constraints specific to a mobile target (§8); and the finding that no storage obligation is handed to `02-platform-data-model-design.md` (§9).

This document does **not** own, and does not decide:

- **The sync posture, or whether the platform supports bidirectional synchronization.** `DECISIONS.md` D-11 already fixes server-authoritative data with optimistic UI via a standardised client library; this document does not reopen that question, and nothing below introduces version columns, sync tombstones, or a per-table conflict rule of any kind. Where this document's own write queue could be mistaken for a step toward one, §6.7 states the limit that keeps it from becoming one.
- **The mobile-delivery runtime itself.** `01-technology-stack-design.md` §19 (ADR-009) already fixes React Native with Expo; this document builds a local-persistence and offline-write mechanism on top of that already-committed runtime and does not re-evaluate the runtime choice.
- **The Entity Access Gateway, any of its four checks, referential integrity, or migration-safety.** `02-data-model-and-entity-design.md` owns all of it; §6.4 below states precisely which of those checks a queued write has *not* yet cleared, never re-implementing or narrowing any of them.
- **Authentication, session mechanics, or the treatment of an unauthenticated or expired actor.** `03-authentication-and-identity-design.md` owns all of it; a mobile client authenticates through the identical Authentication Gate as any other client, and §6.6 states where a long-offline queued write's replay meets that document's own, already-fixed expiry mechanism without this document designing a second one.
- **Tenant isolation, the Registry Accessor, or connection-scoped access.** `02-tenant-isolation-and-access-control-design.md` owns all of it; a dequeued write is bound by it exactly as any other request is.
- **Residency obligations, the Region Boundary Check, or classification-tier resolution.** `06-compliance-and-data-residency-design.md` owns all of it; §6.5 states a caching *limit* this document adds on top of that mechanism, never a substitute for it, and never a claim that this document's own enforcement point can detect where a device physically carries cached data once content has already been served to it.
- **The built-application contract's shape, versioning, or generation.** `05-api-contract-design.md` owns all of it; a dequeued write is an ordinary call against that contract, never a second contract this document defines.
- **General publishing: reachability, audience scoping, withdrawal's server-side mechanism, or the publication-status fact itself.** `04-publishing-and-delivery-design.md` owns all of it, and its own §11.1 already states the boundary bidirectionally; §8 below owns only what is specific to shipping and distributing a *mobile artifact*, never a second reachability gate.
- **The physical shape of any platform-schema structure.** `02-platform-data-model-design.md` owns it; §9 states the finding that this document constrains nothing there.
- **Audit-event record shape, storage, or tamper-evidence.** `08-audit-and-traceability-design.md` owns all of it; §10 states that this document mints no new type.
- **Any independent technology, topology, or scope decision beyond the one named in §11.** This document records exactly one ADR.

## 3. The Supported Mobile-Target Scope

`DECISIONS.md` D-05 fixes that the platform adds mobile as a delivery target while remaining web-focused, explicitly declining desktop and robotic process automation (`OPEN-GAPS-FOR-REVIEW.md` item 3). `01-technology-stack-design.md` §17.3 already fixes the mechanism this scope is realized through: **one platform-authored mobile runtime that renders builder-defined applications from server-driven definitions** — the platform does not generate a fresh native codebase per built application, and generating one in another language is C-22 (future, unauthorized). This document's scope is bounded by that mechanism, not by an independent survey of mobile platforms.

| In scope | Out of scope |
|---|---|
| iOS and Android, phone and tablet form factors, via the single React Native/Expo runtime ADR-009 already commits to. | Any platform C-20 does not name — desktop, wearable OS (watchOS, Wear OS), television OS, or automotive platforms; each is out of scope on the identical web-focused reasoning `DECISIONS.md` D-05 and `OPEN-GAPS-FOR-REVIEW.md` item 3 already state, restated here as this document's own boundary rather than re-argued. |
| One installed binary serving every tenant and every application — a builder-facing tenant/application selection happens inside the running app, exactly as the web form resolves `tenant_id`/`application_id` from the request's own address (`01-application-runtime-and-lifecycle-design.md` §3.2), never as a separate binary per tenant. | A white-labeled or per-tenant binary. Nothing in C-20, D-05, or the runtime mechanism above requires or anticipates one, and building one would multiply the app-store review and versioning burden §8 already treats as an external constraint by the number of tenants — a cost this document does not adopt without an authorizing decision it does not have. |
| Operating-system version support bound to whatever the Expo SDK's own currently-supported platform matrix requires, revisited at each Expo SDK upgrade. | A fixed OS-version number stated here. Pinning one would be exactly the class of time-sensitive claim `PROCESS.md` §12.3 requires be checked before it decides anything, and it would date before this document's next reader opens it; the matrix is delegated to the runtime's own maintenance cycle rather than restated as a number this document owns. |

**Why one binary, stated as a finding rather than assumed.** Because the mobile runtime renders from server-driven definitions rather than generating per-application code, nothing about a second tenant's or application's content requires a second compiled artifact — the identical "the churn lives on the server" property `01-technology-stack-design.md` §17.3 already states. This is the fact §9 below rests its finding on.

## 4. Web/Mobile Parity and Permitted Divergence

C-20 requires that every platform guarantee holding for non-mobile output hold equally for mobile output, and `01-business-and-ux/05-user-journeys.md` §4.2 requires the same run-time journey to carry the same guarantees on a mobile target as on the non-mobile form. `01-technology-stack-design.md` §19.2 already corrects a reading of this requirement worth restating rather than re-arguing: **the parity required is parity of guarantees — isolation, authorization, data integrity, residency — never pixel-identical rendering.** This document holds that correction and states what it means concretely for a mobile client's request path and for the two adjacent capabilities this document must not blur.

### 4.1 Never Divergent

Every request a mobile client makes converges on the identical destination a web client's request does — the Operation component, reached through the identical Authentication Gate, Context Resolution Point, Entity Access Gateway, and Region Boundary Check (`01-application-runtime-and-lifecycle-design.md` §3.1–§3.2). This document introduces **no mobile-specific authorization mechanism, no mobile-specific tenant-scoping path, and no mobile-specific residency exemption.** A request's channel — mobile, web, or the platform's own agent-facing contract surface — is never a parameter any check above reads; "engine-originated," "administrative," and "mobile" each confer no exemption, on the identical discipline `02-data-model-and-entity-design.md` §4.4 already states for its own fourth check and `04-workflow-and-process-automation-design.md` §5.2 already states for the workflow engine.

### 4.2 Permitted Divergence

| Dimension | What May Differ | Why the Divergence Is Permitted |
|---|---|---|
| Rendering | A mobile client renders through native platform components; a web client renders through the DOM. Visual presentation is not required to be pixel-identical across the two. | `01-technology-stack-design.md` §19.2's own correction: C-20 and user-journeys §4.2 require parity of guarantees, never of rendering. |
| Device-capability access | A mobile client may expose capabilities with no web equivalent — camera, biometric authentication, barcode scanning, precise location (§7) — and a web client is never required to simulate them. | These are capabilities a browser sandbox structurally cannot offer identically; requiring parity here would either strip the mobile artifact of its own genuine advantage or fabricate a web-side capability that does not exist, neither of which any specification obligation requires. |
| Timing and immediacy of consistency | A mobile client operating under D-25's optimistic-UI-plus-queue mechanism (§5–§6) may show a write as applied before the server has actually committed it, for a bounded interval while offline or reconnecting; an online web client ordinarily sees the committed (or rejected) outcome within one round trip. | This is a divergence in *when* the guarantee is confirmed, never in *what* the guarantee is — the same Gateway checks apply to the write in both cases, before either client's UI reflects a final, server-confirmed state (§6.6). |
| App-store review, binary versioning, and update propagation | A mobile artifact's own shell is subject to app-store review and a versioned binary; a web artifact is not. | These are constraints external to the platform's own publish/withdraw mechanism, imposed by a mobile distribution channel a web deployment never passes through (§8). |

### 4.3 The Boundary Against Two Adjacent Capabilities, Restated From This Document's Side

`04-publishing-and-delivery-design.md` §11.1 already states this boundary bidirectionally; this document holds its own side of it rather than restating the whole. That document's publish/withdraw gate governs reachability of the built-application contract surface any client — including a mobile client — ultimately calls; this document does not design a second reachability gate, and §8.3 below states precisely what remains once that document's own gate has already refused or served a request. `05-api-contract-design.md` §2's built-application contract tier is the identical surface a mobile client calls; this document defines no second contract concept, no second versioning scheme, and no second response convention for the built-application tier itself.

## 5. What Already Exists Before This Document

Two upstream decisions have already answered most of what "offline mobile behavior" could have meant, and D-25's own framing correction — that recognizing the question had already shrunk is what makes this document's remaining decision small — is the premise this section holds before any mechanism is designed.

- **The server always holds final authority over data (`DECISIONS.md` D-11).** No version columns, no sync tombstones, no per-table conflict rule exist anywhere in this design, and nothing below introduces any. A mobile client's local copy of anything is a cache or a pending intention, never a peer authoritative store.
- **Responsiveness is delivered by one standardised client library pattern — optimistic UI, with the library owning the request queue and the rollback when the server rejects a change** (`01-technology-stack-design.md` §21.2; candidate libraries TanStack/React Query or RTK Query, ADR-011 not reopened by this document). This document does not replace that library's own optimistic-update and rollback UX; §6.3 states precisely what this document adds *alongside* it, because §6's verified finding is that the library's own persistence mechanism does not, by itself, deliver what D-25 requires.
- **One platform-authored mobile runtime reaches the platform through the identical channel as every other client** (§3, §4.1). A mobile client authenticates through the same Authentication Gate, is resolved through the same Context Resolution Point, and dispatches every write through the same Construct Invocation Point (`01-application-runtime-and-lifecycle-design.md` §5) as a web client. This document adds nothing server-side; every mechanism below is client-resident.

**What remains, narrowly.** Given the above, the only genuine gap D-25 identifies is: reads that survive a restart, writes that survive being offline, and credentials held safely — realized as a local relational store, a fast key-value store, and an explicitly designed write queue (§6), never a synchronization engine.

## 6. The Local Store and the Durable Write Queue

### 6.1 The Local Relational Store

**Candidate: `expo-sqlite`, with Drizzle ORM as the typed query layer over it.**

`expo-sqlite` is first-party to the committed mobile runtime (ADR-009) — it ships as part of the Expo SDK rather than as an independently-maintained community package — and is **verified 2026-08-10** as actively maintained, consistent with D-25 criterion 3's preference for a first-party dependency over one that would add to the layer whose ecosystem-maintenance claims already caused one reversal (ADR-007 → ADR-009).

`expo-sqlite` supplies no typed query layer of its own, and D-25 requires one. Drizzle ORM is **verified 2026-08-10** to carry native `expo-sqlite` support, with a type-safe query builder and typed schema definitions generated from a TypeScript schema declaration. **This document's own local schema is a compile-time-known shape, not a runtime-defined one**: the local store holds no builder-defined entity at all — only a generic read-cache table and the write-queue table of §6.3, both fixed at the mobile runtime's own build time and never varying per tenant or application, unlike the server's own builder-defined, runtime-unbounded schema (`02-data-model-and-entity-design.md`, in full). A typed schema declaration fits a fixed, build-time-known table set precisely, which is what this document's own local store is; this document does not compare Drizzle against the server's own choice of data-access abstraction, which is `01-technology-stack-design.md`'s to decide and is not reopened, restated, or drawn on here.

### 6.2 The Fast Key-Value Store, Split by Secrecy

**Candidates: `expo-secure-store` for secret material; `expo-sqlite/kv-store` for non-secret settings and the query-cache persister.**

Both are first-party to the committed mobile runtime, **verified 2026-08-10** as actively maintained as part of the Expo SDK. D-25 names one "fast key-value store," and this document splits it in two by what each holds, rather than adopting one store for both:

- **`expo-secure-store`** holds the session bearer token (`03-authentication-and-identity-design.md` §4.2's authority-referencing token) and the device-bound symmetric key §6.3 uses to encrypt write-queue payload content. It is encrypted at rest by the OS's own keychain/keystore primitive — the property secret material requires and settings do not.
- **`expo-sqlite/kv-store`** — a first-party API built on `expo-sqlite`, drop-in-compatible with the community `AsyncStorage` interface — holds non-secret settings and the standardised query library's own persisted-cache metadata (§5). Using it, rather than a community key-value library such as `react-native-mmkv`, avoids introducing an independently-maintained dependency for a purpose the already-adopted local relational store already supplies a first-party primitive for; `react-native-mmkv` was **checked 2026-08-10** and found to carry a healthy maintenance signal, but is not preferred here on D-25 criterion 3 grounds precisely because a first-party equivalent already exists.

**No secret and no settings value is ever stored in the wrong one of the two.** A component reading a token has no function available to it that reads the settings store, and vice versa — the split is structural, not a convention a future change could blur unnoticed, on the identical "no function available that bypasses the mediation point" discipline this library already applies to the Registry Accessor (`02-tenant-isolation-and-access-control-design.md` §3.1) and the Entity Access Gateway (`02-data-model-and-entity-design.md` §4.1).

### 6.3 The Durable Write Queue, Explicitly Designed

**Verified 2026-08-10, re-confirming D-25's `[verified 2026-08-03]` finding: the standardised query library does not deliver write durability by default.** In its default network mode, an offline mutation attempt can error immediately rather than pause; even where pause-and-resume is configured, resuming a persisted paused mutation after an app restart requires the caller to register a default mutation function for its own key and explicitly invoke a resume step after restoring the persisted cache — and the library's own issue tracker records mutations becoming stuck in a paused state under ordinary failure conditions. This confirms, rather than merely repeats, D-25's finding: **durability does not fall out of adopting the library**, and this document's write queue is designed independently of, and does not depend on, the library's own persistence plugin succeeding at this. This verification was run specifically against TanStack/React Query, the library D-25 evidences; RTK Query's own offline-mutation behavior was not independently re-checked here, and either candidate remains ADR-011's to select, not reopened by this finding.

**The queue's physical shape.** One row per pending write, held in the local relational store (§6.1), typed through the same query layer:

| Field | Purpose |
|---|---|
| `queue_entry_id` | A locally-generated identifier, unique per pending write. |
| `operation_reference` | The built-application contract operation this write targets (`05-api-contract-design.md` §2) — an opaque reference, resolved exactly as any other request resolves one (`01-application-runtime-and-lifecycle-design.md` §3.3). |
| `payload_ciphertext` | The write's own request payload, encrypted before insertion under the device-bound key held in `expo-secure-store` (§6.2) — never stored as plaintext (§6.4 states why). |
| `enqueued_at` | When the write was first queued, client-side. |
| `attempt_count` | How many replay attempts have been made. |
| `status` | One of `queued`, `in-flight`, `applied`, `refused`, `expired` — a terminal outcome vocabulary the mobile client renders against (§6.6), never silently discarded. |
| `last_error` | Populated on `refused` or `expired`, carrying whatever refusal the built-application contract's own response convention returned (`05-api-contract-design.md` §4) — never a second error vocabulary this document invents. |

**Draining the queue.** On reconnection, each `queued` entry is replayed, in enqueue order, as an ordinary call against the built-application contract — indistinguishable, at the server, from a request made by a client that was never offline at all. This document designs nothing server-side; the replay is dispatched through the identical Authentication Gate → Context Resolution Point → Construct Invocation Point path (§4.1, §5) any other request passes through, with backoff between attempts on a transient failure and a terminal `refused` or `expired` status on one that is not.

### 6.4 What a Queued Write Is, Structurally, Before It Reaches Any Check

**A queued write has cleared no server-side check.** Not the Validation Engine's validity, consistency, or referential-correctness inspection; not the Consent and Minimization Check; not classification-tier or data-governance-category resolution; not the Region Boundary Check; not the End-User Record-Reach Check — none of `02-data-model-and-entity-design.md` §4.1's four Gateway checks, and none of `06-compliance-and-data-residency-design.md` §3.4's residency check, has run over a write sitting in this document's own queue, because every one of those mechanisms requires a connection this document's own subject — a disconnected device — by definition does not have. This is stated plainly rather than assumed away: **queuing a write is optimistic client-side state, never a claim that any check has passed**, and this document's own mechanism makes no assertion to the contrary anywhere in its design.

**Consequently, the client cannot classify what it is queuing, and this document does not ask it to try.** A component client-side attempting to determine whether a given write's target carries Jurisdiction-Restricted or Regime-Governed classification would be re-implementing, unmediated and offline, a determination `06-compliance-and-data-residency-design.md` §5 and `07-data-governance-and-privacy-design.md` §3.1 already fix as resolved once, server-side, at the Gateway — exactly the "second mediation point" this library's own composing discipline exists to prevent. Instead, this document extends the identical deny-by-default rule those two documents already apply to an unclassifiable tier or category — resolve to the most restrictive, never the least — to the one case neither document anticipated: **every queued write's payload is treated as maximally sensitive for the sole purpose of at-rest protection**, encrypted under the device-bound key (§6.3) regardless of what it actually contains, without this constituting an actual classification determination — that determination remains the Gateway's alone to make, once the write reaches it online.

### 6.5 What May Be Cached Locally, and What May Not

The local relational store's read-cache mirrors content a Surface has already resolved through the Gateway while online (`01-application-runtime-and-lifecycle-design.md` §4.1's step 4) — content whose classification tier the server response already carries, unlike a queued write's own unresolved payload (§6.4). This document places one limit on what is retained, on top of the classification mechanism it does not own:

- **Unrestricted and Tenant-Bound tier content** may be persisted to the local store for offline-read and optimistic-UI purposes, on the same query-cache-persister mechanism the standardised library already provides (§6.2), cleared on the same triggers that clear the session (§6.6).
- **Jurisdiction-Restricted and Regime-Governed tier content is not persisted to the local store.** It may be held only in memory for the duration the Surface displaying it remains active, and is cleared on backgrounding or session end. This is the on-device application of the minimization principle `07-data-governance-and-privacy-design.md` §5.2's Consent and Minimization Check already enforces — bounding collection and use to a basis's own disclosed purpose — applied to caching specifically, which is itself a use of the data.

**The honest limit this places, stated plainly.** `06-compliance-and-data-residency-design.md` §3.4's Region Boundary Check governs the platform's own code path — it refuses, holds, or permits an action before a connection is acquired, and its guarantee is bounded to that code path, never to where a byte physically ends up once served. **This document's own mechanism carries that same kind of bound one hop further: once content has been served to a mobile client at all, no check this document or any cited upstream document owns can detect or control where the physical device carrying that content travels thereafter.** The minimization bound above is this document's own contribution to bounding that residual risk — never a claim that it eliminates it. Device-level protections (OS keychain-backed disk encryption, device passcode enforcement, remote wipe) are a device-security and mobile-device-management concern this document does not own and does not design a mechanism for.

### 6.6 When a Queued Write Reaches the Server and a Check Refuses It

`01-technology-stack-design.md` §21.3 already names the "silent rejection" problem — hours of offline work refused wholesale on reconnect with no interim feedback — as the reason a pure server-authoritative posture with no optimistic layer was rejected. This document's own obligation, given that D-11 already accepted optimistic UI specifically to avoid that problem, is to make sure a *queue's* own refusal does not silently reproduce it one layer down.

- **A dequeued write that clears every check is recorded `applied` (§6.3); the client's own optimistic UI is confirmed, never rolled back.** No new mechanism is designed for this path — it is the ordinary success path the standardised library's own optimistic-update model already renders (§5).
- **A dequeued write refused by any Gateway or residency check is recorded `refused`, carrying the built-application contract's own refusal content (`05-api-contract-design.md` §4), and is surfaced to the end user as a reconciliation state — never silently discarded.** This is the composition point with D-11's own rollback mechanism: the standardised library already owns rolling an optimistic update back on a server rejection; this document's own addition is that the rollback fires from a queue entry discovered on reconnect, potentially long after the optimistic UI was first shown, rather than only from an immediate round-trip failure the library's own default assumes.
- **A dequeued write whose replay fails at the Authentication Gate — because the session's idle or absolute ceiling (`03-authentication-and-identity-design.md` §4.4) has passed while the device was offline — is recorded `expired`, not `refused`, and requires re-authentication before any further replay is attempted.** This document introduces no mobile-specific session exemption and no extended ceiling for an offline device; the identical ≤30-minute idle / ≤12-hour absolute rule applies regardless of channel, and a long-offline queue is exactly the case most likely to encounter it.

### 6.7 The Honest Limit

**This document does not, and cannot, guarantee that every queued write eventually applies.** A write may be refused because the state it assumed no longer holds, because the session has expired, or because a schema evolution the queue's own stale local cache never learned about has since made the operation's own reference invalid. What this document guarantees instead is narrower and stated precisely: **no queued write is ever silently dropped without a terminal, user-visible status (§6.3, §6.6), and no queued write is ever treated as having cleared a check it has not** (§6.4). This is the identical shape of honest limit `06-integration-and-extensibility-design.md` §5.5 already states for capability confinement — "this bounds *reach*; it does not vet *intent*" — and `03-builder-facing-version-control-design.md` §9 already states for safe revert — "this document does not, and cannot, make every promotion recoverable." Each of those two limits is structural, not a caveat a future revision closes; this document's own limit is the same kind, for the same reason: no mechanism operating on a disconnected device can substitute for a check that structurally requires a connection.

## 7. Device Capability Beyond Structured Data

C-20 names "the device-capability... expectations mobile artifacts must meet" alongside offline behavior. `01-technology-stack-design.md` §19 (ADR-009) already commits the device-capability surface to the Expo module set — camera, biometric authentication, secure storage, geolocation, and barcode scanning, each verified there as first-party or, where not, checked for maintainer concentration risk (§19.1). This document does not re-select or re-verify that surface; it states only the parity consequence already fixed at §4.2: a capability with no web equivalent is a permitted divergence, never a guarantee this document must fabricate a web-side substitute for. Where a builder's own construct binds to a device capability (for example, a Command whose configured effect reads a barcode), that binding is ordinary builder-defined configuration under `01-application-construction-design.md`'s already-fixed vocabulary — this document adds no new binding kind, no new action class, and no device-specific construct type.

## 8. Mobile-Specific Publishing Constraints

`04-publishing-and-delivery-design.md` owns reachability, audience scoping, the publication-status fact, and withdrawal's server-side mechanism in full (its own §11.1 already states this boundary by name). This document owns only what a mobile distribution channel adds on top of that already-fixed mechanism.

### 8.1 App-Store Review and Binary Versioning, Bounded Against Builder Content

**An ordinary builder configuration change requires no app-store submission at all.** Because the mobile runtime renders builder-defined applications from server-driven definitions (§3), a new Surface, a new binding, or an updated entity schema is picked up by an already-installed app the next time it fetches its server-driven definitions — exactly as a web client's next request reflects the identical change, with no binary involved. App-store review and a versioned binary apply only to the platform-authored runtime shell itself — its own native code, its own bundled Expo modules, and any change to how it renders rather than what it renders — never to a builder's own content. This is the concrete mobile-specific constraint C-20 names that `04-publishing-and-delivery-design.md` explicitly does not reach (its own §11.1): a server-side publish action has no app-store analogue, and a runtime-shell update has no server-side analogue; the two constraints are independent, and this document does not conflate them.

### 8.2 Update Propagation

The platform-authored runtime shell's own updates propagate through the already-adopted Expo build tooling (`01-technology-stack-design.md` §19.3's consequences already name "Expo module set and build tooling" as a standing obligation this document must specify): an over-the-air JavaScript-bundle update for a change confined to the shell's own rendering logic, requiring no new native module and therefore no app-store review; a new binary submission, subject to app-store review, only where a change to a native module or a bundled Expo dependency requires one. This document does not re-decide Expo's own build-tooling adoption — it applies what ADR-009 already committed to, rather than selecting a second update mechanism alongside it.

### 8.3 Withdrawal's Own Honest Limit

`04-publishing-and-delivery-design.md` §8.2 already fixes that unpublishing ends new reach immediately, because its own gate is evaluated on every end-user request, not only at session establishment — and this holds identically for a mobile client's request, with no new mechanism required (§4.1). **What that mechanism cannot do, and what this document states plainly rather than conceals, is retract an already-installed binary from a device, or remove the runtime shell's own listing from an app store the platform does not operate.** A withdrawn application's mobile client, even one already installed on a device, is refused at the server-side gate exactly as any other client is (§4.1) — the reachability guarantee holds regardless. But de-listing the platform-authored shell from Apple's or Google's own store — a distinct, mobile-store-specific action, exercised through the identical Publisher-role grant `04-publishing-and-delivery-design.md` §10 already fixes — reaches an external review-and-removal process this platform does not control, and no timing guarantee of the kind §8.2's "immediately" already makes for the server-gated case can be made for it. This document names the constraint; it does not, and cannot, design a mechanism that closes it, because the process it would need to control belongs to a third party.

## 9. Where Mobile-Specific State Lives

Per `BACKLOG.md` §1i's standing rule and the constrain-and-hand-over precedent `02-platform-data-model-design.md` §3.2 already establishes for the three most recent instances — the administrative-scope grant, the stage-schema mapping, and the version-history structure, all discharged by H30a — this document checked whether it, too, owes a storage obligation to that document. **It does not, and this is stated as a finding rather than an omission.**

- **The local relational store, the fast key-value store, and the write queue (§6) are exclusively client-resident.** Nothing in their design is written to, read from, or synchronized against any platform-schema structure; `02-platform-data-model-design.md` gains no new table, no new column, and no new obligation from this document.
- **The one artifact this document could have made a per-tenant or per-application fact — the mobile binary itself — is not one, per §3's own finding.** One installed binary serves every tenant and every application; a store listing is a build-time constant of the platform-authored runtime, not a value that varies per tenant the way `platform.applications.schema_name` or `publication_status` does. There is accordingly no registry row for a mobile store listing to occupy, and this document introduces none.

**No new ADR is recorded for this finding.** It applies §3's own already-stated architecture (one platform-authored runtime, server-driven definitions) rather than deciding anything new; the one genuine decision this document makes is recorded in §11.

## 10. Evidence Produced

**This document adds no new `event_type`.** The local write queue (§6.3) is a client-side replay mechanism; every write it eventually dispatches produces exactly the evidence the ordinary Gateway and runtime dispatch already produce for that write (`01-application-runtime-and-lifecycle-design.md` §10's own table), because the dequeued write is, at the server, indistinguishable from a request made by a client that was never offline. The queue's own dequeue-and-replay action is not a consequential action distinct from the write it forwards, on the identical reasoning `01-application-runtime-and-lifecycle-design.md` §10 already applies to the Construct Invocation Point's own dispatch decision: auditing the replay separately from the write's own already-captured outcome would double-record one fact under two event types, the opposite of the consolidated base-record and discriminated-type model `08-audit-and-traceability-design.md` §4.2–§4.3 already fix.

A queue entry's own local `status` transitions (§6.3, §6.6) are client-side application state, rendered to the end user for reconciliation (§6.6) — they are not platform audit evidence, because no consequential platform-level action occurs at the moment a client-resident status field changes; the platform-level action they eventually produce is captured exactly once, when the replay actually reaches the server, under whatever event type that write already carries.

- **Criteria applied, and how each resolved:**
  1. *Is the candidate first-party to the committed mobile runtime, or does it introduce an independently-maintained dependency the maintenance layer that already caused one reversal (ADR-007 → ADR-009) would have to absorb?* Decisive for `expo-sqlite`, `expo-secure-store`, and `expo-sqlite/kv-store` over a community alternative for the same purpose (§6.1–§6.2); not decisive against Drizzle, which supplies a capability (a typed query layer) no first-party candidate offers at all, and which D-25 itself requires.
  2. *Does the candidate's own current maintenance or end-of-life status foreclose it?* Decisive against Realm/Atlas Device SDK, re-confirmed rather than merely inherited (§11's Verified field); not decisive against any candidate actually adopted here.
  3. *Is the local store's own schema fixed at build time, or does it hold builder-defined, runtime-unbounded structure the way the platform's own server-side datastore does (`02-data-model-and-entity-design.md`)?* Decisive for adopting a typed, schema-first query layer here: the local store's own tables — a generic read-cache table and the write-queue table — are fixed at the mobile runtime's own build time and never builder-defined, so a compile-time-known-table premise fits this schema precisely (§6.1). This document draws no comparison to, and takes no position on, the server's own choice of data-access abstraction, which remains `01-technology-stack-design.md`'s alone.
  4. *Does the client library's own persistence mechanism deliver write durability by default, or must one be designed?* Decisive, and re-verified rather than assumed: it does not (§6.3), which is what makes an explicitly designed queue necessary rather than a redundant addition.
  5. *Where the client cannot resolve a write's classification tier because no Gateway access exists offline, what is the safe default?* Decisive for treating every queued write's payload as maximally sensitive for at-rest protection, extending the library's own existing deny-by-default discipline rather than inventing a new one (§6.4).
  6. *Where a device may physically leave a region the server-side Region Boundary Check cannot observe, what may the local store retain, and for how long?* Decisive for excluding Jurisdiction-Restricted and Regime-Governed content from persistent local storage, bounding rather than eliminating the residual risk (§6.5).
  7. *What must the queue distinguish so a refusal discovered after reconnect is surfaced rather than silently dropped?* Decisive for a terminal, user-visible outcome vocabulary (`queued`/`in-flight`/`applied`/`refused`/`expired`) composing with, rather than replacing, D-11's own optimistic-UI rollback mechanism (§6.6).
- **Decision:** (1) The local relational store is `expo-sqlite`, with Drizzle ORM as its typed query layer (§6.1). (2) The fast key-value store is split by secrecy: `expo-secure-store` for the session token and the write-queue's own encryption key; `expo-sqlite/kv-store` for settings and the standardised query library's own persisted-cache metadata (§6.2). (3) The write queue is an explicitly designed table in the local relational store, replayed on reconnection through the identical, unmodified server-side request path any other client uses, never a second server-side mechanism (§6.3). (4) Every queued write's payload is encrypted at rest under the device-bound key, treated as maximally sensitive regardless of actual content, because its classification cannot be resolved offline (§6.4). (5) Jurisdiction-Restricted and Regime-Governed content is never persisted to the local store, held only in memory for the active Surface's own duration (§6.5). (6) A dequeued write's outcome — applied, refused, or expired for session reasons — is recorded with a terminal, user-visible status and is never silently discarded (§6.6). (7) No storage obligation is handed to `02-platform-data-model-design.md` (§9).
- **Alternatives considered:** *A synchronization engine (PowerSync, ElectricSQL, Turso offline sync)* — rejected by D-25 itself on criterion 1 there (D-11 removed the problem these solve), not reopened here. *Realm / the Atlas Device SDK* — rejected, re-confirmed end-of-life rather than assumed still current. *Firebase or Supabase as the local or sync layer* — rejected by ADR-010's portable-subset rule, cited and not re-argued. *Relying on the standardised query library's own persistence plugin alone for offline-write durability* — rejected on criterion 4, re-verified rather than assumed; this remains, as D-25 already found, "the tempting option and the one that fails silently." *A single, undifferentiated key-value store for both secrets and settings* — rejected on the structural mediation-point discipline of §6.2; splitting by secrecy costs nothing this document's own architecture does not already pay for tokens. *Letting the client attempt its own classification or residency determination before deciding whether to queue a write* — rejected on criterion 5; this would re-implement, offline and unmediated, a determination the Gateway alone is positioned to make. *Retaining all cached content indefinitely for maximal offline resilience* — rejected on criterion 6; this would extend the residency risk §6.5 already bounds rather than close it. *Silently dropping a queued write refused on reconnect* — rejected on criterion 7; this is exactly the "silent rejection" problem `01-technology-stack-design.md` §21.3 already named as a reason to reject a purely server-authoritative posture with no interim feedback.

## 14. Binding Rules

These rules hold for every mobile client, request, and locally-queued write subject to this model and are subordinate to the charter.

- **No mobile-specific authorization, tenant-scoping, or residency exemption exists anywhere in this design.** A mobile channel is bound by the identical Authentication Gate, Context Resolution Point, Entity Access Gateway, and Region Boundary Check as any other channel (§4.1).
- **Parity is parity of guarantees, never of rendering.** Visual presentation, device-capability access, and the timing of consistency confirmation may legitimately differ between a mobile and a non-mobile form; isolation, authorization, data integrity, and residency may never differ (§4).
- **No synchronization engine, version column, sync tombstone, or per-table conflict rule exists in this design.** `DECISIONS.md` D-11's server-authoritative posture is not reopened by anything this document adds (§2, §5, §6.7).
- **A queued write has cleared no server-side check until it is actually dequeued and dispatched.** No mechanism in this document treats a queued write as validated, consented, classified, residency-cleared, or record-reach-narrowed before that dispatch occurs (§6.4).
- **Every queued write's payload is encrypted at rest, treated as maximally sensitive regardless of its actual content, because the client cannot resolve its classification offline.** (§6.4)
- **Jurisdiction-Restricted and Regime-Governed content is never persisted to the local store.** It is held only in memory for the active Surface's own duration and cleared on backgrounding or session end (§6.5).
- **No queued write is ever silently discarded.** Every dequeued write reaches a terminal, user-visible status — applied, refused, or expired — and a refusal or expiry is surfaced for reconciliation, never dropped (§6.6, §6.7).
- **A dequeued write is an ordinary request against the built-application contract, dispatched through the identical, unmodified server-side path any other client uses.** No second server-side mechanism, contract, or response convention is designed for it anywhere in this document (§5, §6.3, §11).
- **An ordinary builder configuration change requires no app-store submission.** Only a change to the platform-authored runtime shell's own native code or bundled modules does (§8.1).
- **A server-side publish or withdraw action's reachability guarantee holds for a mobile client exactly as for any other; retracting an already-installed binary or a store listing is a distinct, externally-mediated action this document names but does not control the timing of.** (§8.3)
- **No table, column, or storage obligation is added to `02-platform-data-model-design.md` by this document.** (§9)
- **No new audit `event_type` is added by this document.** Every consequential effect a dequeued write produces is captured exactly once, by whichever mechanism it already composes with (§10).
- **Everything remains domain-neutral and platform-level.** No mechanism, gate, or rule in this document encodes the characteristics of any single domain; all remain valid for any software built on the platform.
- **This document records exactly one ADR.** ADR-017 (§11) is the genuine decision this document makes, discharging the obligation owed since `DECISIONS.md` D-25; every other design choice above consumes a mechanism, boundary, or invariant the cited specification and cited upstream design documents already fix.
