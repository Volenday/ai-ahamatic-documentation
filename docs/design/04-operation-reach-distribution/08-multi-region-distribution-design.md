# Multi-Region Distribution Design — AI ahaMatic

This document closes Layer 4 by realizing `01-business-and-ux/02-prd.md`'s C-14 row as concrete mechanism: the region topology, the unit of physical regional placement, and the routing that let the platform operate across regions while every core component remains region-agnostic. It answers **how**, never re-deciding what the specification or the already-fixed design library have already settled, and it discharges the honest limit `06-compliance-and-data-residency-design.md` §3.5 states about itself: that document's guarantee is a code-path guarantee, "only as strong as [this document's] own placement and routing decisions make it." This document is that topology.

This is a Design-phase artifact realizing, in addition to C-14's own row and release gate G-4 (`01-business-and-ux/02-prd.md` §4, §5): `03-software-and-architecture/01-architecture-overview.md` §4–§5 (the Distribution component's purpose, its allowed dependencies, and the forbidden direction — Isolation and Trust or Operation depending on region-specific logic to function); `02-governance-and-security/05-compliance-and-data-residency.md` (the obligations this design honors, consumed, never re-decided); `06-compliance-and-data-residency-design.md` §3–§9, §11 (the Resolved Residency Obligation, the Region Boundary Check, and the constraint this document inherits as an obligation-model floor); `02-tenant-isolation-and-access-control-design.md` §3–§5, §8 (the Registry Accessor, the Context Resolution Point, and the structural-impossibility register this document's own placement argument is checked against); `01-application-runtime-and-lifecycle-design.md` §3–§5, §7 (the request-resolution sequence this document's routing composes with, never duplicates); `02-builder-facing-environment-management-design.md` §4–§5, §9 (the stage model, and the finding this document is named to confirm or revise); `04-publishing-and-delivery-design.md` §5 and its Boundaries/Binding Rules (the reachability boundary already stated from the other side); `05-mobile-application-delivery-design.md` (its honest limit, inherited unchanged); `03-architecture-realization-design.md` §3.1, §4.1–§4.2, §7 (the module structure, the dependency-enforcement mechanism, and the fixed deployment shape this topology extends); `01-technology-stack-design.md` §20.1 (ADR-010's portable-subset rule); `02-platform-data-model-design.md` §3.1, §7 (the region catalog, the two `region_of_record` columns, and `tenant_host_connections`); and `08-audit-and-traceability-design.md` §4.2–§4.3 (the consolidated event model this document's evidence composes with).

## 1. Purpose and Reading Order

This document answers eight questions:

## 3. What a Region Is, as a Deployed Thing

`03-architecture-realization-design.md` §7.1 fixes that "one deployable" means the platform as a whole: one deployment of the platform-core service serves every tenant and every application, with no per-tenant or per-application build, image, or process, and tenant/application context resolved per request via the registry. That statement was written for a platform operating in one place. This section fixes what changes to realize C-14, and what does not.

### 3.1 What Stays Identical

- **The deployable itself is unchanged.** One container image, built from one source tree, holding the seven component modules and the `guardrail/` module of `03-architecture-realization-design.md` §3. No region-specific fork, variant, or build target exists anywhere in the source tree.
- **No component module contains a hardcoded region identifier**, on the identical discipline `03-architecture-realization-design.md` §4.1's second row already fixes for tenant identifiers: there is no per-region subclass, branch, or module variant inside `components/isolation-and-trust`, `components/operation`, `components/construction`, `components/reach`, `components/extension`, or `components/evolution`.
- **Horizontal scaling by stateless, identical replicas is unchanged.** No replica is region-specific in the sense that its own code differs from any other replica's; every replica, in every region, runs the identical image.
- **Tenant and application context continues to resolve per request, via the registry**, exactly as already fixed — this document adds one further resolution this same discipline covers (§6), never a second resolution mechanism.

### 3.2 What Changes

**"One deployable per product" is realized, under C-14, as one identical deployable instantiated once per operating region — never as a rewrite of the deployable, and never as a return to a per-tenant or per-application split.** Concretely:

- **The platform is N regional instances of the identical image**, where N is however many regions the platform currently operates in (§9 states how a region is added). Each instance is horizontally scaled by its own pool of stateless replicas, exactly as `03-architecture-realization-design.md` §7.2 already fixes for the single-region case — that fixture is now applied per region rather than once globally.
- **Each regional instance is backed by a regionally-resident managed PostgreSQL instance** (ADR-010's portable subset — managed PostgreSQL, no provider-unique construct), holding the tenant and application schemas physically placed in that region (§4).
- **A tenant's own schema hierarchy is served by exactly one regional instance, never split and never simultaneously live in two.** `03-architecture-realization-design.md` §7.1's "one deployment serves every tenant" is not contradicted by this — it is now read region-scoped: within one operating region, one deployment instance serves every tenant physically placed there; across regions, the platform is several such deployments, distinguished only by which regionally-resident PostgreSQL instance each connects to and which tenants' data therefore resolve there. No deployment instance is tenant- or application-specific in the sense `03-architecture-realization-design.md` §4.3 already forbids; every deployment instance in every region remains capable of serving any tenant assigned to it, resolved per request exactly as before.
- **The platform-global registry (`platform.tenants`, `platform.applications`, `platform.platform_users`, and the rest of the `platform` schema, `02-platform-data-model-design.md` §3.1) retains exactly one authoritative write location.** Every operating region holds a read-only replica of it, kept current by ordinary PostgreSQL streaming or logical replication — a portable, provider-neutral capability, not a provider-unique managed service, and therefore inside ADR-010's subset. A write to the platform-global schema (admitting a tenant, changing a `region_of_record`, establishing a session) is always directed to the one authoritative instance, regardless of which region received the request that triggered it; the concrete provisioning of the replication topology is infrastructure work this document hands to `01-environment-and-configuration-design.md` (§11), not a mechanism this document designs.

**Why a replica in every region, rather than a single authoritative instance every region reads across a network boundary for every request.** The one lookup every request needs before it can be routed at all — which region a tenant's own data physically resides in (§6) — must be resolvable without a cross-region round trip on the platform's single most frequent code path, or every request anywhere would pay a cross-region latency cost regardless of where its own tenant is placed, and the platform's resilience to one region's own unavailability would collapse to the resilience of whichever region happens to hold the sole authoritative registry. A local, regionally-resident read replica removes both costs for reads; only a genuine platform-global write (rare relative to request volume) pays a cross-region cost, and that cost already exists in the single-region design as an ordinary write-path property, not a new one this topology introduces.

## 4. The Unit of Physical Regional Placement

`02-platform-data-model-design.md` §3.1 fixes `region_of_record` on both `platform.tenants` and `platform.applications`; §7's `tenant_<id>.tenant_host_connections` records provider and region **per tenant**, with no equivalent per-application table anywhere in that document. This section decides the placement unit against that state, not from either column's existence alone.

### 4.1 The Candidates, Checked

| # | Candidate | What Would Have to Be True | Is It? |
|---|---|---|---|
| 1 | Application-scoped placement — each application's schema independently assigned a physical region. | A per-application host-connections structure would need to exist, parallel to `tenant_host_connections`, recording which region each application's own schema is committed to. | **No.** `02-platform-data-model-design.md` §7 defines exactly one host-connections table, scoped to the tenant, not the application. No such structure exists for an application independently of its tenant. |
| 2 | Tenant-scoped placement — a tenant's entire schema hierarchy (its own `tenant_<id>` schema and every `tenant_<id>_app_<id>` schema beneath it) committed to one region together. | `tenant_host_connections` — the one host-connections structure that does exist — would need to be sufficient, on its own, to answer "which region hosts this application's schema" for every application of that tenant. | **Yes.** Every application schema is named `tenant_<tenant_id>_app_<application_id>` (`02-platform-data-model-design.md` §3.3) — nested under its own tenant's identifier in the schema's own name, the same physical co-location fact ADR-004 already fixes for the partitioning shape itself. A tenant's `tenant_host_connections` row is therefore sufficient, alone, to answer the placement question for every application that tenant has or will construct — no second table is needed because no second fact exists to record. |

**Finding: the tenant is the unit of physical regional placement.** A tenant's own `tenant_host_connections` row (§7) is the single, authoritative, already-existing record of where that tenant's entire schema hierarchy — the tenant-level schema and every application schema nested beneath it, at every stage (§5) — physically resides. This document adds no new structure to record this fact (§11); it already exists.

### 4.2 What `platform.applications.region_of_record` Is, Then

Given placement is tenant-scoped, `platform.applications.region_of_record` cannot be a second, independent placement instruction — no structure exists for it to instruct a placement into. It is, instead, exactly what `06-compliance-and-data-residency-design.md` §3.3 already reads it as: one further contributor to the **Resolved Residency Obligation**'s union, alongside the actor's own region-of-record and the classification tier — an obligation an application's own configuration may carry, narrower or different from its tenant's, without that obligation itself moving any byte.

**This is a genuine consequence, stated plainly rather than left implicit.** Where an application's own declared `region_of_record` is incompatible with the region its tenant is actually placed in (§4.1), no mechanism in this document, and no mechanism in `06-compliance-and-data-residency-design.md`, silently reconciles the two. The Resolved Residency Obligation's union (that document's §3.3) folds in both values; the Region Boundary Check (that document's §3.4) requires every obligation in the union to be satisfied; an obligation the tenant's own physical placement cannot satisfy is, by that document's own already-fixed deny-by-default rule (§4), refused on every action against that application, indefinitely, until the incompatibility is corrected. This document does not build a second check to catch the misconfiguration earlier — the already-fixed Region Boundary Check already catches it, on every request, for the entire time the incompatibility persists. Preventing the incompatibility from being configured in the first place is a builder-tooling or admission-time concern this document does not own and does not design a mechanism for.

## 5. Stage Differentiation by Region — `02-builder-facing-environment-management-design.md` §9's Finding, Confirmed

That document's §9 finds that a stage promotion is not a cross-region data movement, for two reasons: a promotion moves configuration catalog rows, never classified content; and every stage of one application shares exactly one `region_of_record`, because Development, Testing, and Production are sibling schemas of one unchanging `application_id`/`tenant_id` (its own §4.3). Its own honest limit states plainly that the finding is bounded to the topology as that library defines it today, and that **this document**, if it ever placed different stages of one application in different physical regions, would be the one to revisit it.

**This topology does not do that, and the reason is the same fact §4 already establishes.** Placement is tenant-scoped (§4.1) — a tenant's entire schema hierarchy is physically co-located in one region, and every one of an application's sibling stage schemas (`tenant_<id>_app_<id>` for Development; the two further sibling schemas `tenant_<id>.application_stage_schemas` names for Testing and Production, `02-platform-data-model-design.md` §3.2) is a schema of that same tenant's hierarchy. There is no mechanism anywhere in this document — no per-stage region column, no per-stage host-connections structure, no routing branch keyed to stage — that could place one stage of an application in a region different from where its own tenant, and therefore every one of its sibling stages, already resides.

**`02-builder-facing-environment-management-design.md` §9's finding stands, unamended.** This document's own routing (§6) resolves a region from the tenant alone, never from a stage; a stage is resolved separately, downstream, at the Context Resolution Point exactly as that document's own §5.4 already fixes, and the two resolutions never interact.

## 6. Request Routing: The Region Resolution Point

### 6.1 Why This Runs Ahead of the Existing Sequence, Not Inside It

`01-application-runtime-and-lifecycle-design.md` §3.2 fixes that every request passes the Authentication Gate and then the Context Resolution Point. The Context Resolution Point's own connection-acquisition step (`02-tenant-isolation-and-access-control-design.md` §4.2, §5.1) is what actually opens a scoped database connection — and under this document's topology, that connection is to one specific region's own PostgreSQL instance (§3.2). No connection can be acquired without first knowing which region to acquire it in. The region resolution this document adds must therefore run **ahead of the Authentication Gate**, not downstream of it and not interleaved with any step of the sequence those two mechanisms already fix — a request cannot even reach a running Authentication Gate check inside the correct region's own deployment instance until it is known which instance that is.

This is a genuinely new step, stated as such rather than folded into an existing one: the **Region Resolution Point**, realized inside `components/distribution` (§8), running as the first action any deployment instance takes on an inbound request, before any other component module's handler runs.

### 6.2 Deriving the Region: A Second, Narrower Read Path, Justified

The Registry Accessor (`02-tenant-isolation-and-access-control-design.md` §3.1) is, by its own fixed signature, the sole read path to `platform.tenants`/`platform.applications` — but it "accepts only an **already-authenticated** actor identity... never a client-supplied `tenant_id` or `application_id` used to widen a result set." Region resolution needs exactly what that signature forbids: it must run **before** any identity is authenticated, and it is necessarily keyed by a value the request's own address supplies — the tenant or application the request's own path names (`01-application-runtime-and-lifecycle-design.md` §3.3's "resolved... by opaque reference" already establishes that a request's target is identifiable from its own address before authentication completes).

**Reusing the Registry Accessor for this purpose would therefore be a category error, not a convenience.** It would require either weakening the accessor's own "no caller-supplied widening identifier" guarantee — the exact discipline that keeps a tenant-scoped actor's query from returning more than its own row — or authenticating before routing, which is structurally impossible given §6.1. This document instead opens a **second, deliberately narrower read path**: the Region Resolution Point reads only the `region_of_record` and the `tenant_host_connections` row for the tenant named in the request's own address, from the local, regionally-resident read replica of the platform-global schema (§3.2) — no other column, no other table, and no write capability of any kind. It is narrower than the Registry Accessor in every dimension that matters: it returns one value, it never resolves role, permission, or grant content, and it is never consulted again once the request has been routed — the Registry Accessor's own, full resolution runs afterward, unmodified, inside whichever region's Authentication Gate and Context Resolution Point the request now reaches (§6.3).

**This is the one named exception to `02-tenant-isolation-and-access-control-design.md` §5.3.** That document's own import-boundary rule (§5.3, restated by ADR-062 to close a letter/purpose gap `BACKLOG.md` §1u surfaced) forbids any module outside `components/isolation-and-trust` from obtaining a handle capable of directly querying `platform.tenants` or `platform.applications`, by any means — not merely by importing the Registry Accessor's own data-access module. The read of `region_of_record` above is exactly the query that rule would otherwise forbid; §5.3 now names the Region Resolution Point as the sole exception, bounded to exactly the read this section describes — `region_of_record` only, for the one tenant the request's own address names, before authentication, never resolving role, permission, or grant content. This document does not restate §5.3's own terms; the exception's scope is that document's to state, and is stated there.

### 6.3 The Sequence

1. **An inbound request reaches any operating region's own entry point.** Ordinary DNS, optionally with a latency- or geography-based hint steering a request toward a nearby region — this hint is a performance convenience only, and its correctness is never load-bearing (§6.4).
2. **The Region Resolution Point reads the tenant's own `region_of_record`/`tenant_host_connections` row (§6.2) from the local replica.** No connection to any tenant- or application-scoped schema is attempted before this step completes.
3. **If the resolved region matches the region this deployment instance is already running in, the request proceeds unmodified into the existing sequence** — the Authentication Gate, then the Context Resolution Point, then every mechanism downstream of it, exactly as already fixed, with no branch or exception introduced by this document anywhere in that sequence.
4. **If it does not match, the request is redirected to the correct region's own entry point**, using an ordinary, portable HTTP redirect or reverse-proxy forward — a mechanism every ADR-010-compliant provider's container runtime already supports natively, never a provider-unique global-routing product. The redirected request re-enters at step 1 against the correct region, where step 3 now holds.
5. **Where the tenant's own region cannot be resolved with confidence** — no `tenant_host_connections` row exists, or the value is unset — **the request is refused**, never routed on an assumed or most-permissive default: the identical deny-by-default rule `06-compliance-and-data-residency-design.md` §4 already fixes for an unresolvable `region_of_record`, applied here one step earlier, before any region has even been entered (§12).

### 6.4 Why the Entry Tier's Own Correctness Is Never Load-Bearing

**A geo-DNS or anycast hint at step 1 is a performance optimization, never a correctness mechanism, and this document depends on it for neither.** Should the hint route a request to the "wrong" region first — stale DNS caching, an imprecise anycast decision, or simply the nearest edge not being the tenant's own region — step 2 through step 4 still produce the correct outcome: the Region Resolution Point runs inside whichever region actually received the request, using the platform's own portable code, and redirects if necessary. Correctness therefore never depends on any provider-specific routing product's own accuracy, only on the platform's own Region Resolution Point running correctly in every region — which, being the identical code in every deployment instance (§3.1), it does. This is the concrete reason ADR-010's portable-subset rule (`01-technology-stack-design.md` §20.1 — "no provider-unique managed service for anything on which correctness depends") is satisfied here without exception: the only thing this document's correctness depends on is ordinary DNS resolution to *some* operating region and the platform's own container-native redirect capability, both inside the portable subset.

## 7. Division of Labor: Locality Versus Permission

`06-compliance-and-data-residency-design.md` §3.4 fixes the Region Boundary Check and its outcomes; §3.5 states plainly that its guarantee "is only as strong as that topology's own placement and routing decisions make it," and hands this document the obligation to make that true. This section states which mechanism decides what, and why neither substitutes for the other.

- **The Region Resolution Point (§6) decides locality: which physical region actually serves this request at all.** It runs once, at the very front of request handling, before any identity is established and before any obligation has been resolved. Its own outcome is binary — this region, or redirect/refuse — and it evaluates nothing about what the request is trying to do; it does not know, and does not need to know, whether the action being requested is a read, a write, or a transfer.
- **The Region Boundary Check (that document's §3.4) decides permission: given a request now correctly running inside its tenant's own resolved region, is the specific action it is attempting consistent with the full Resolved Residency Obligation** — the actor's own region, the target's, the classification tier, and any attaching compliance regime? It runs downstream of Region Resolution, inside the Context Resolution Point's own connection-acquisition step, exactly as already fixed, on every read, write, and transfer alike.
- **Neither substitutes for the other, and a request correctly routed by this document's mechanism can still be refused or held by the Region Boundary Check.** Locality answers "is this the right region"; permission answers "is this specific action allowed, given everything the resolved obligation requires" — a request that has cleared locality has answered only the first question. Conversely, no amount of Region Boundary Check enforcement can correct a request that this document's own mechanism ever routed to a region physically incapable of honoring its obligation in the first place — which is exactly why §4.1's placement-unit finding, and the redirect discipline of §6.3, exist: they are what make the Region Boundary Check's own guarantee actually hold, rather than merely be asserted.

### 7.1 What This Document Does Not Attempt to Close

`05-mobile-application-delivery-design.md` §6.5 states its own honest limit: once content has been served to a mobile client at all, no mechanism on the platform's own code path can detect or control where the physical device carrying that content travels thereafter. This document's own mechanism governs where the platform's own **server-side** data physically resides and which region serves a request against it — it does not extend, and cannot extend, to a device already holding served content. This limit is inherited unchanged; nothing in this document narrows or widens it, and nothing here attempts to close it.

## 8. The Forbidden Direction, Held

`03-software-and-architecture/01-architecture-overview.md` §5.1 fixes Distribution as depending on Isolation and Trust and on Operation; §5.2 fixes the forbidden direction absolutely: "Isolation and Trust or Operation depending on region-specific logic to function." `03-architecture-realization-design.md` §3.1 already places "region topology and routing" inside `components/distribution`, and §4.1's fifth row already asserts, at Full coverage, "no import path from `isolation-and-trust` or `operation` into `distribution` or into any region-configuration module."

**This document's mechanism holds inside that existing guarantee without extending it.** The Region Resolution Point (§6), the tenant-scoped placement read (§4), and every region-configuration value this document reads live entirely inside `components/distribution` — the module that document's own §3.1 already assigns this exact responsibility to. No component this document touches gains a region-specific branch: `components/isolation-and-trust`'s Authentication Gate and Context Resolution Point, and `components/operation`'s runtime, run identically in every region, on the identical code, exactly as §3.1 above states; the only thing that differs per region is which regionally-resident connection they are, by the time they run, already scoped against — a fact resolved entirely upstream of them, inside Distribution, never inside either module itself.

**No extension of the dependency-direction mechanism is required.** The existing, Full-coverage rule already forbids the one direction this document's mechanism could plausibly have introduced (a region-configuration import reaching into Isolation and Trust or Operation), and this document introduces no import in that direction. The concrete registration of `components/distribution`'s own new source paths (the Region Resolution Point's own module) in the dependency-cruiser configuration is an implementation detail `08-coding-standards-and-patterns-design.md` and the toolchain itself resolve, not a rule this document adds to the table `03-architecture-realization-design.md` §4.1 already fixes.

**This finding is scoped to `03-architecture-realization-design.md` §4.1's five rules; it does not address the sixth, `02-tenant-isolation-and-access-control-design.md` §5.3 — a distinct rule, owned by a different document, restricting `platform.tenants`/`platform.applications` access rather than region-specific logic (`BACKLOG.md` §1u).** §6.2 above states how the Region Resolution Point's own registry read composes with that rule; §5.3 states the exception in full.

## 9. Region Admission and Release Gate G-4

### 9.1 What Region Admission Is, Concretely

Bringing a new operating region online is: provisioning a regionally-resident managed PostgreSQL instance (§3.2); deploying an identical instance of the platform-core deployable, connected to it; establishing a read-only replica of the platform-global schema into that instance (§3.2); and adding the new region's row to `platform.regions` (`02-platform-data-model-design.md` §3.1). No tenant is placed there merely by this event — a tenant's own placement remains the distinct, later act of setting its `tenant_host_connections` row (§4.1).

### 9.2 The Existing Gate Already Reaches It — No Second Gate Is Introduced

`06-compliance-and-data-residency-design.md` §8.1 already fixes that "beginning operation in a new region for the first time" is one of the two promotion-shaped triggers realized at the Production Deploy Gate's own, already-existing residency clause (`04-devops-and-cloud-infra/02-ci-cd-pipeline-spec.md` §6) — approval required before the promotion, never after. Region admission, as defined in §9.1, is exactly that trigger: it is a platform-layer change that reaches Production through the pipeline, not a per-tenant runtime action. This document supplies no new criteria beyond what §8.1 already states and introduces no second gate for it; the existing residency-relevant-promotion clause already reaches this action in full.

### 9.3 Composition With Release Gate G-4

G-4 (`01-business-and-ux/02-prd.md` §5) states that once the platform operates in a region, a release that does not honor that region's obligations may not serve it. This document's topology discharges G-4 through the composition of two already-fixed mechanisms, adding nothing new to either:

- **At the point a new region is admitted**, the Production Deploy Gate's residency clause (§9.2) already requires the promotion be evaluated for exactly this — whether the release honors the obligations of the region it would begin serving — before that region ever goes live.
- **For every request thereafter**, the Region Boundary Check (§7) already refuses or holds any action inconsistent with the resolved obligation, on every request, in every region, for as long as the platform operates there — and this document's own placement discipline (§4) is what makes that enforcement meaningful rather than merely asserted, because a tenant's data now genuinely resides only in the region its obligation permits.

No release, region-admission event, or ongoing-operation check this document introduces sits outside these two already-fixed mechanisms; G-4 is honored by their composition, not by a third gate.

## 13. Design Decision Records

### 13.1 ADR-045 — Tenant-Scoped Physical Placement, a Pre-Authentication Region Resolution Point, and Portable, Platform-Owned Redirect Over Provider-Unique Global Routing

- **Status:** Provisional — Pending Lead Approval.
- **Cost to reverse:** **High**, stated above the ordinary cloud-substrate rung (`PROCESS.md` §12.1) for a reason independent of, but consistent with, the map's own pre-assigned grade: reversing which region a tenant is placed in is not an infrastructure-configuration change — it requires physically relocating that tenant's already-resident schema hierarchy across a region boundary, which is itself exactly the class of action the Region Boundary Check governs as a cross-region transfer requiring both regions' permission and, for Jurisdiction-Restricted or Regime-Governed data, a recorded human approval (`06-compliance-and-data-residency-design.md` §7, §8.2). A reversal is therefore a governed data migration, not a redeploy — costlier than an ordinary cloud-provider or infrastructure change (Moderate–high), because resident data must move under approval rather than configuration alone being rewritten, but not Brutal or Very high, because no schema *shape* changes and no sync-posture machinery is introduced — only where already-shaped data physically resides.
- **Upstream decisions assumed:** ADR-005 (`03-architecture-realization-design.md` §7 — the fixed deployment shape this document extends into a per-region instantiation, never re-derives); ADR-023 (`06-compliance-and-data-residency-design.md` §10.1 — the Resolved Residency Obligation and Region Boundary Check this topology satisfies as a constraint, never weakens); ADR-018 (`02-tenant-isolation-and-access-control-design.md` §10.1 — the Registry Accessor and Context Resolution Point this document's own routing composes with and is checked against for why it cannot reuse the accessor directly); ADR-039 (`02-builder-facing-environment-management-design.md` §11 — the sibling-schema stage model this document's §5 finding depends on); ADR-010 (`01-technology-stack-design.md` §20.3 — the portable-subset rule this document's redirect mechanism stays inside); ADR-004 (`01-technology-stack-design.md` §14.7 — the schema-per-tenant/per-application partitioning this document's placement-unit finding is checked against). ADR-021 through ADR-044 remain Provisional and are not assumed settled; this decision depends on their already-designed content, never their approval status (`PROCESS.md` §12.2).
- **Verified vs. reasoned:** Reasoned throughout. The placement-unit determination, the routing mechanism, and the redirect-over-global-routing argument are each structural arguments from the cited specification and the cited, already-written design documents' own content; no claim asserts any cloud provider's or managed service's current replication or routing capability as independently verified — every infrastructure mechanism named (streaming replication, container-native redirect) is treated as an ordinary, generic capability inside ADR-010's portable subset, not a product-specific fact.
- **Question this answers:** Given the fixed one-deployable-per-product shape and a residency obligation model already fixed elsewhere that states its own guarantee is only as strong as this document's placement and routing decisions make it, what unit of physical regional placement resolves the tension between two existing `region_of_record` columns and one existing per-tenant host-connections table without assuming an answer from either; what routing mechanism gets an inbound request to the region that unit is actually placed in, composing with the already-fixed request-resolution sequence rather than duplicating it; and how does that mechanism hold inside the existing forbidden-dependency-direction guarantee and the existing portable-infrastructure rule without extending either?
- **Criteria applied, and how each resolved:**
  1. *Does a structure already exist sufficient to answer the placement question for the candidate unit, or would a new one be required?* Decisive for tenant-scoped placement (§4.1) — `tenant_host_connections` already answers it for every application of a tenant, by construction of the schema-naming convention itself; application-scoped placement has no such structure and would require inventing one.
  2. *Can the existing Registry Accessor be reused for pre-authentication routing, or does its own fixed signature structurally forbid it?* Decisive against reuse (§6.2) — the accessor requires an already-authenticated identity and forbids a caller-supplied widening identifier; routing needs both violated by definition, so reuse would weaken the accessor's own guarantee rather than compose with it.
  3. *Does correctness depend on any provider-unique global-routing product, or can it rest entirely on the platform's own portable code?* Decisive for the latter (§6.4) — a redirect issued by the platform's own identical, region-resident code, using an ordinary container-native mechanism, delivers correct routing regardless of what routed the request there first, keeping the entry tier's own accuracy a performance concern rather than a correctness dependency, inside ADR-010's subset.
  4. *Does region admission need a new gate, or does an existing one already reach it?* Decisive for reuse (§9.2) — `06-compliance-and-data-residency-design.md` §8.1 already names "beginning operation in a new region" as a promotion-shaped trigger realized at the existing Production Deploy Gate residency clause; a second gate would duplicate a chokepoint already built for this exact purpose.
- **Context:** This is the document that closes Layer 4, and the one three already-written documents in this library each explicitly named as the place their own honest limit or open finding would be resolved: `06-compliance-and-data-residency-design.md` §3.5/§11 (the topology its own guarantee depends on); `02-builder-facing-environment-management-design.md` §9 (the stage-differentiation finding this document could trigger a revision of); and `04-publishing-and-delivery-design.md` §5 (the routing half of a boundary it already stated its own side of). A superseded draft of this document existed and was set aside before this ticket; this record is independent of it.
- **Decision:** (1) The tenant is the unit of physical regional placement; every application, and every stage of every application, inherits its tenant's own physical region through the schema-naming co-location already fixed elsewhere, and `tenant_host_connections` is the sole record of it — no new placement structure is created (§4.1). (2) `platform.applications.region_of_record` is consumed as an obligation input to the Resolved Residency Obligation's union, never as an independent placement instruction; an incompatibility between an application's own declared obligation and its tenant's actual placement is refused by the already-fixed Region Boundary Check on every action, not separately detected or prevented by this document (§4.2). (3) `02-builder-facing-environment-management-design.md` §9's finding — that a stage promotion is not a cross-region data movement — stands unamended, because tenant-scoped placement structurally co-locates every sibling stage schema of one application (§5). (4) A new, pre-authentication Region Resolution Point, realized inside `components/distribution`, reads a tenant's own region from a second, deliberately narrower read path than the Registry Accessor, and either passes the request through unmodified or redirects it, using a portable, container-native mechanism never dependent on a provider-unique global-routing product for correctness (§6). (5) The Region Resolution Point decides locality; the already-fixed Region Boundary Check decides permission; neither substitutes for the other (§7). (6) This mechanism holds entirely inside the existing forbidden-dependency-direction rule and requires no extension of the dependency-enforcement mechanism (§8). (7) Region admission is realized entirely at the already-existing Production Deploy Gate residency clause; no second admission gate is introduced, and release gate G-4 is discharged by the composition of that gate and the Region Boundary Check, not by a third mechanism (§9). (8) This document owes no new schema structure; the one infrastructure element it requires — a regionally-resident registry replica — is handed to Layer 5 (§11). (9) One new audit event type, `locality-resolution-refusal`, is added, for the one genuinely new definitional fact this mechanism introduces (§12).
- **Alternatives considered:** *Application-scoped placement* — rejected under criterion 1; no structure exists to record it, and introducing one would duplicate, at a finer grain, a fact `tenant_host_connections` already settles once per tenant. *Deriving region from the existing Registry Accessor, accepting an unauthenticated caller-supplied identifier as a narrow, documented exception* — rejected under criterion 2; this would be the exact "no caller-supplied widening identifier" guarantee weakened for one caller, the failure mode that mechanism exists to prevent, applied to itself. *Relying on a provider's own global load-balancing or geo-routing product as the authoritative, correctness-bearing router* — rejected under criterion 3 and under ADR-010's own rule; it would make platform correctness depend on a provider-unique managed service for the one property (regional data locality) this design most needs to be provider-neutral about. *A dedicated region-admission gate, distinct from the Production Deploy Gate's own residency clause* — rejected under criterion 4; the clause already exists, already anticipates exactly this trigger, and a second gate would duplicate rather than strengthen it. *Modeling stage-level regional differentiation now, in anticipation of a future capability that might need it* — not adopted; no authorized document defines such a capability today, and §5's finding is stated as bounded to the topology as it exists, exactly as `02-builder-facing-environment-management-design.md` §9 itself already reasons for the identical situation.
- **Consequences:** Binds `01-environment-and-configuration-design.md` (Layer 5, not yet written) to provision the per-region read-replica topology of the platform-global schema (§3.2) and the region-admission infrastructure sequence (§9.1), without this decision predetermining the concrete replication product or pipeline mechanics. Does not weaken, narrow, or extend `06-compliance-and-data-residency-design.md`'s Region Boundary Check or Resolved Residency Obligation — this decision satisfies both as a constraint, per that document's own §3.5 and §11. Confirms `02-builder-facing-environment-management-design.md` §9's finding without amendment. Completes `04-publishing-and-delivery-design.md` §5's boundary statement from this document's side, without either document re-deciding the other's fact. Adds no obligation to `02-platform-data-model-design.md`'s schema (§11) and exactly one new `event_type` to `08-audit-and-traceability-design.md`'s model (§12).

## 16. Binding Rules

These rules hold for every region, request, and placement decision subject to this model and are subordinate to the charter.

- **The platform-core deployable is unchanged by multi-region operation.** One image, one source tree, no region-specific fork, branch, or variant anywhere in `components/*` or `guardrail/` (§3.1).
- **"One deployable per product" is realized as one identical deployable instantiated once per operating region — never a rewrite of the deployable, and never a return to a per-tenant or per-application split.** A tenant's own schema hierarchy is served by exactly one region's instance, never split (§3.2).
- **The tenant is the unit of physical regional placement.** Every application, and every stage of every application, inherits its tenant's own placement; no per-application or per-stage placement structure exists (§4.1, §5).
- **An application's own `region_of_record` is an obligation, never a placement instruction.** Where it is incompatible with its tenant's actual placement, every action against that application is refused by the already-fixed Region Boundary Check, on every request, until corrected (§4.2).
- **`02-builder-facing-environment-management-design.md` §9's finding that a stage promotion is not a cross-region data movement stands unamended.** No mechanism in this document places different stages of one application in different regions (§5).
- **The Region Resolution Point runs first, ahead of the Authentication Gate and every other step of the already-fixed request-resolution sequence, because no connection can be acquired without first knowing which region to acquire it in.** It never opens a second identity or scoping mechanism, and it reads a second, deliberately narrower path than the Registry Accessor, justified structurally rather than by convenience (§6.1–§6.2); this read is the one named exception to `02-tenant-isolation-and-access-control-design.md` §5.3 (that document's §10.3, ADR-062), never a general license to read further.
- **An unresolvable region-of-record refuses the request before any region-scoped connection is attempted, never on an assumed or most-permissive default.** (§6.3, step 5)
- **No mechanism in this document depends on a provider-unique global-routing product for correctness.** An entry-tier hint is a performance convenience only; correctness rests entirely on the platform's own portable, identical, region-resident redirect logic (§6.4).
- **Locality and permission are two distinct mechanisms, and neither substitutes for the other.** The Region Resolution Point decides which region serves a request; the Region Boundary Check decides whether a specific action within that region is permitted (§7).
- **No mechanism in this document requires a region-specific branch inside Isolation and Trust or Operation, and no extension of the dependency-direction enforcement mechanism is required to hold this guarantee.** (§8)
- **Region admission is realized entirely at the already-existing Production Deploy Gate residency clause; no second admission gate exists.** Release gate G-4 is discharged by the composition of that gate and the Region Boundary Check (§9).
- **This document decides whether and how a request reaches the correct region; `04-publishing-and-delivery-design.md` decides whether an application is reachable at all.** Neither absorbs the other, and this document's own routing runs ahead of that document's gate for every request, regardless of that request's eventual reachability outcome (§10).
- **No table, column, or storage obligation is added to `02-platform-data-model-design.md` by this document.** The one infrastructure element required — a regionally-resident registry replica — is handed to Layer 5 (§11).
- **Every control this document fixes produces the evidence §12 names**, landing under Residency and compliance events as the closest available category; no event is recorded for an ordinary, correctly-resolved routing decision or a redirect.
- **Everything remains domain-neutral and platform-level.** No jurisdiction, regulatory regime, geographic region, or cloud provider is named anywhere in this document; every mechanism above remains valid for any tenant, in any operating region.
- **This document records exactly one ADR.** ADR-045 (§13) is the genuine, independent decision this document makes; every other design choice above consumes a mechanism, boundary, or invariant the cited specification and cited upstream design documents already fix.
