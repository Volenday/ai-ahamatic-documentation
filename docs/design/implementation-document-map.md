# Implementation Document Map — AI ahaMatic

A meta index ("digital shelf") of the **design / implementation documents** required to carry AI ahaMatic from its completed specification ("what") to a buildable design ("how"). It is the design-phase counterpart to `docs/spec/context-document-map.md`: where that map indexes **what** each specification must cover, this map indexes **how** each capability, guardrail, and governed concern is designed and built.

AI ahaMatic is a generic, multi-purpose Enterprise Low-Code Application Platform (LCAP) serving **professional builders**. The citizen-developer build model is a deliberate strategic exclusion, not a gap; no design document indexed here may reintroduce it, and every design document realizes a platform-level, domain-neutral primitive — never a feature of a single vertical. This framing is inherited from `01-business-and-ux/01-vision-and-charter.md` through every entry below and is never re-decided in the design phase.

Every entry below is **derived from the specification library, not invented**: each specification implies one or more design documents. This map introduces no new capability or scope. It states **what each design document must define** and **how the documents depend on one another** — not the detailed design, which each later ticket produces.

Every design document, when written, realizes its cited specification(s) without narrowing, expanding, or altering them. Where a design reveals a genuine gap or error in the specification, that gap is flagged to the spec-phase change process, never fixed inside a design document.

---

## How to read this map

Each design document is indexed with six fields:

- **Document Name** — the canonical filename of the design artifact, written to `docs/design/`.
- **What It Must Define** — the "how" the document must answer: the concern it owns, the core objective, and the mechanisms, structures, technologies, and decisions it is charged with recording. Stated as the document's charge, not as pre-made choices — this map scopes the decision; the design ticket makes it.
- **Realizes** — the specification document(s) and capability IDs (`01-business-and-ux/02-prd.md` §4, `01-business-and-ux/03-platform-capability-model.md` §5; span **C-01–C-26**) the design document makes real. Traceability is mandatory: a design document realizes its cited "what", it never restates it.
- **Depends On** — the other design documents that must hold first. Fine-grained, per-capability dependency follows the authoritative "Depends On" graph of `01-business-and-ux/02-prd.md` §4 and the family-level ordering of `01-business-and-ux/03-platform-capability-model.md` §5 — cited here, never restated.
- **Build Status** — the readiness flag: **Buildable now**, **Gated — prerequisite open**, or (for future capabilities) excluded from the pyramid entirely (see Future / Not-Yet-Authorized capabilities).
- **Cost to Reverse** — what it would cost to undo the most expensive decision the document owns, on the fixed five-grade scale **brutal / very high / high / moderate / low**. The ordering, the scale, and the rules that follow from them are owned by `PROCESS.md` §12.1 and cited here, never redefined: this map records only the per-document annotation. It is not a build order, not a priority, and not a readiness signal.

### Readiness legend

| Flag | Meaning |
|---|---|
| **Buildable now** | The design ticket can proceed against the frozen spec. |
| **Gated — prerequisite open** | A named, still-open prerequisite must be resolved before this design (or the flagged portion of it) can be written. Two prerequisites are currently open: the **C-18 BPMN-modeling assumption** (`BACKLOG.md` §3) and three **deferred NFR numeric values** (`BACKLOG.md` §1). |

### Cost-to-reverse legend

A distinct legend from the readiness one above, and never merged with it: readiness says whether a design can be written now; cost to reverse says what undoing it would cost once written. The five grades are fixed by `PROCESS.md` §12.1 and are neither extended nor renamed here. Each row is annotated at the **highest-cost decision that document owns**, mapped onto §12.1's chain — data model and database → sync posture → architecture and API contract → cloud provider → client surface → languages and frameworks.

| Grade | What reversal costs |
|---|---|
| **Brutal** | Reversal reshapes stored builder or tenant data, or the schema that holds it. §12.1's most expensive rung. |
| **Very high** | Reversal forces a change to the data model, or to the shape or placement of data already stored, though the document does not own the schema itself. |
| **High** | Reversal changes the architecture's component structure or a published contract: code and topology change, stored data does not. |
| **Moderate** | Reversal changes the infrastructure substrate or the client surface — the application is portable, its realization is re-done. |
| **Low** | Reversal changes languages, frameworks, tooling, or conventions: mechanical and contained. §12.1's cheapest rung. |

Where a document's cost genuinely straddles two grades, the **higher** grade is stated with its reason in the same cell; no hybrid grade is created. A document that owns no independent decision — one that only enforces something the frozen specification already fixed — is still graded, from what reversing its *mechanism* would cost.

**Verified versus reasoned (`PROCESS.md` §12.3).** Every grade in this map is **reasoned** from structural properties — what a document owns, and what undoing it would touch — not verified against an external source. None rests on a time-sensitive claim, and none records or implies an approval: a grade states a decision's reversal cost, never its status.

Future / Not-Yet-Authorized capabilities (**C-22, C-26**) receive **no scheduled design document** and appear in no pyramid layer; they are recorded separately below.

## Naming convention for design documents

Stated once, applied to every document indexed below:

- **Location** — all design ("how") documents are written to `docs/design/`. The specification library in `docs/spec/` is read-only for the design phase.
- **Filename** — lowercase kebab-case, ending in `-design.md`, distinguishing a design artifact from its `docs/spec/` source at a glance.
- **One ticket per document** — each row is its own atomic design ticket; no ticket scopes beyond the single document it owns, and a document blocked by an open prerequisite waits rather than being partially improvised.
- **No names** — role references only, in every design document.

## Design layers and dependency ordering

The map is ordered as a pyramid, foundational → complex. Each layer may depend only on the layers beneath it; a design document may not assume a decision a more-foundational layer has not yet made.

| Layer | What It Realizes | Depends On |
|---|---|---|
| 1 · Design Foundation | The technology and structural realization the whole design phase inherits — the "how" bedrock the specification deliberately excluded. | — |
| 2 · Identity, Access & Security | The guardrails that bound all build: invariants, security, identity, access, tenancy, residency, privacy, audit, licensing. Also realizes the Isolation and Trust component (C-01–C-03), whose capabilities *are* the guardrail enforcement. | Layer 1 |
| 3 · Data, Construction & Contracts | The build-side capability designs: modeling, constructing, configuring, automating, extending, and unifying cross-system data (C-24), plus the contracts they expose. | Layers 1–2 |
| 4 · Operation, Reach & Distribution | The run-, publish-, and deliver-side capability designs, plus builder-facing version and environment management, the general marketplace, and the connector marketplace (C-25). | Layers 1–3 |
| 5 · Infrastructure, Deployment & Operations | How platform work itself ships and stays healthy: environments, pipeline, quality gates, observability, release, incident recovery. | Layers 1–4 |
| 6 · Autonomous-Agent Implementation | How the autonomous builder itself is built and governs its own conduct across the lifecycle. | Layers 1–5 |

**One cross-layer exception.** `ai-assisted-builder-tooling-design.md` (C-19, Layer 3) additionally depends on the Autonomous-Agent Implementation layer, because C-19 explicitly inherits the Meta-Operations guardrails (`05-meta-operations/01-agent-operating-charter.md`, `05-meta-operations/04-human-in-the-loop-protocol.md`) per `01-business-and-ux/02-prd.md` §4. It is the only capability design that reaches into Layer 6. Every other dependency respects the layer ordering above.

**One per-row refinement.** The layer table states **coarse** ordering; the per-row **Depends On** is **fine-grained**, naming only the documents whose decisions a row cannot be written without. `tenant-isolation-and-access-control-design.md` (Layer 2) is the one row where the two visibly differ, and it is recorded here so the difference reads as deliberate rather than as drift. That document realizes the brutal rung (C-01, C-03, INV-01, gate G-1), and its genuine upstream constraint is the multi-tenancy **partitioning shape** — a decision recorded in `technology-stack-design.md` §14.7, not in `architecture-realization-design.md`. Its former dependency on `architecture-realization-design.md` was the Layer 2 → Layer 1 convention restated per-row, not a decision that document alone owns, so it is replaced by the dependency that is structural. The row therefore stays within the coarse ordering — its Layer 1 dependency is now `technology-stack-design.md` — and creates no second cross-layer exception. **The dependency nonetheless survives transitively:** `invariant-enforcement-design.md`, which the row retains for INV-01 enforcement, itself depends on `architecture-realization-design.md`, so the brutal-layer document is *not* free of the high-layer one. Whether that document's own dependency is itself merely conventional is not assessed here; it is flagged, not cascaded. Recording the replacement dependency states **where the constraint lives**, and neither reports nor assumes an approval: §14.7's partitioning shape is provisional, and is itself held open by the sync-posture question (`BACKLOG.md` §3) that constrains the schema.

> **Derivation order is not conflict-precedence order.** This map's pyramid is a *reading/derivation* order. It does **not** establish which document wins a conflict. Conflict precedence among the realized specifications is owned solely by `05-meta-operations/01-agent-operating-charter.md` §4 (`PROCESS.md` §11); nothing in this map's layout may be read as altering it.

> **Nor is it a cost-to-reverse order.** The pyramid is equally not the order in which *decisions* are made or the order of what they cost to undo — a third, deliberately distinct ordering owned by `PROCESS.md` §12.1. The **Cost to Reverse** column is an annotation laid over the existing structure, not a sequence: no layer is renumbered, no document moves between layers, and no row is re-sequenced to match its grade. Reading that column as a build order would collapse two of the three orderings §12.1 keeps apart, and lose the information each carries.

## Map authority

- **This map is navigational, not authoritative.** It routes and scopes design work; it does not decide it. If this map ever conflicts with a specification document, **the spec prevails** — the map is corrected to match the spec, never the reverse. If it conflicts with a completed design document over a decision that design owns, the design document governs its own particulars and the map is corrected to match.
- **Derivation order ≠ conflict-precedence order ≠ cost-to-reverse order.** The pyramid layout is a reading/derivation order only; conflict precedence is owned solely by `05-meta-operations/01-agent-operating-charter.md` §4 (`PROCESS.md` §11); and cost to reverse — the order *decisions* are made, and what gates what — is owned by `PROCESS.md` §12.1. These are three distinct orderings; this map records the per-document cost annotation without owning, redefining, or re-sequencing to any of them, and collapsing any two loses the information each carries.

## Binding notes

- **The specification library is frozen for this phase.** Every design document consumes `docs/spec/`; none edits it. A genuine spec gap or error found while designing is flagged to the spec-phase change process, never fixed in a design document.
- **Traceability is mandatory.** Every design document realizes the specification(s) it cites and does not restate them; a design element with no "what" to realize is out of scope.
- **The domain-neutral, professional-builder LCAP framing holds throughout.** No design document encodes a single domain, collapses the platform toward one vertical, or reintroduces the excluded citizen-developer model.
- **Each row is its own ticket.** No design ticket scopes beyond the single document it owns; a document blocked by an open prerequisite waits, it is not partially improvised.
- **Open prerequisites gate specific designs, not the phase.** The C-18 BPMN assumption (`BACKLOG.md` §3) and the three deferred NFR numeric values (`BACKLOG.md` §1) block only the design documents flagged **Gated** above; every other document is buildable now.
